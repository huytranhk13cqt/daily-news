## 1. dbt Core 2.0 Alpha 3 Lands Versioned-Model Pointers and Catalog Federation

| Field | Value |

### 🔭 Overview (Tổng)
dbt Labs cut `dbt-core` v2.0.0-alpha.3 on 29/06/2026, the third alpha in the v2.0 line that opens the Rust-based Fusion engine under an Apache-2.0 surface. The alpha is squarely aimed at consumers of versioned models — the feature that lets a project ship `dim_customers_v1` and `dim_customers_v2` side by side — and at teams that already work across more than one catalog. The release is on PyPI as `dbt-core==2.0.0a3` and is intended for evaluation rather than production. For analytics-engineering teams, the relevant question is whether the new defaults change how downstream consumers reference models that move through breaking changes.

### 🔬 Details (Phân)
The headline behaviour is an automatic unsuffixed view: a versioned model `dim_customers_v2` now also materialises a view at the canonical name `dim_customers` that always points to the current `latest_version`. The pointer is generated by default and can be turned off per-model with `latest_version_pointer: {enabled: false}` or globally via the project flag `latest_version_pointer_enabled_by_default: false`. Three other changes matter operationally. First, the maximum seed size considered for `state:modified` hashing is now configurable through `--maximum-seed-size-mib`, with incremental hashing and line-ending normalisation, which fixes the long-standing pain of bloated state files on projects with large CSV seeds. Second, the dbt-fusion runtime gains catalog federation between Snowflake Horizon and Unity Catalog, so a single project can resolve relations that live in two governance planes. Third, the Snowflake and BigQuery adapters now expose JavaScript UDFs as first-class objects, and the DuckDB adapter is bumped to the just-released DuckDB 1.5.4.

In context, this alpha is part of the steady drumbeat dbt Labs started with the v2 announcement in early June, when the project framed v2 as the open-source base on which the Fusion engine and dbt Platform sit. The pointer-view default closes a usability gap competitors already cover differently — Snowflake's Dynamic Tables and BigQuery's table snapshots both expose stable aliases — and it is friendlier to BI tools that cache table names and rebuild dashboards when a name shifts. The cost is one extra view per versioned model, plus a small but measurable compile-time bump on projects with hundreds of versioned models.

### 🎯 Takeaway (Hợp)
Teams already on the v2 alpha track should pin a version policy: either accept the new pointer view default and document the canonical names for BI consumers, or set `latest_version_pointer_enabled_by_default: false` before upgrading so that nothing materialises silently. Production migration is still premature — wait for the first beta — but the catalog federation and seed-size flags are worth piloting in a feature branch.

### 💡 Example
```yaml
# models/marts/customers.yml
# Opt out of the new default per-model, then expose a hand-picked alias.
models:
  - name: dim_customers
    latest_version: 2
    latest_version_pointer:
      enabled: false
    versions:
      - v: 1
      - v: 2

# dbt_project.yml — project-wide opt-out, useful while you migrate BI tools.
flags:
  latest_version_pointer_enabled_by_default: false
  maximum_seed_size_mib: 16
```

## 2. Apache Kafka 4.3.1 Fixes a Streams RocksDB Native Memory Leak

| Field | Value |
|---|---|
| 📅 Date | 25/06/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `apache-kafka` · `kafka-streams` · `rocksdb` |
| ⚡ Impact | High |

### 🔭 Overview (Tổng)
The Apache Kafka PMC announced 4.3.1 on 25/06/2026, a bugfix release in the 4.3 line that landed in May. Twenty-three contributors signed off on the release notes. The headline reason to upgrade is a fix for a native memory leak in Kafka Streams' RocksDB state stores — the same class of bug that has historically led to OOM-kills on long-running Streams instances after weeks of uptime. Anyone running 4.3.x in production should treat this as a recommended upgrade, especially Streams jobs with large materialised state. Broker-only deployments are less affected but still get the consolidated bug fixes.

### 🔬 Details (Phân)
The leak originated in how Streams' `RocksDBStore` handled native handles when state stores were re-opened after a task rebalance. Under steady state the leak was small, but a Streams instance that bounced between partitions during repeated rebalances could accumulate hundreds of megabytes of unfreed native memory over a multi-day window — invisible to the JVM heap, visible only in the container's resident set size. The 4.3.1 fix closes RocksDB column-family handles on task close and adds a defensive cleanup path when a store is opened with a stale handle. The release notes also bundle smaller corrections across Connect and the broker; the upgrade is binary-compatible, so a standard rolling restart against a 4.3 cluster is sufficient.

The wider context is that Kafka 4.3 was Confluent and the PMC's first release to make share groups — the Kafka equivalent of pull-based queues introduced as KIP-932 — generally available, and the rebalance protocol churn in early 4.3 deployments stressed exactly the RocksDB code paths that this bugfix patches. Teams running Streams on Kubernetes and seeing pod evictions tied to memory limits should look at this release first before reaching for larger memory requests. For non-Streams users the upgrade is still worth folding into the next maintenance window because the broker patches address a handful of edge-case races that surface under heavy ZK-to-KRaft migrations.

### 🎯 Takeaway (Hợp)
Roll 4.3.1 into your next Kafka maintenance window and prioritise it if you operate Streams on container platforms with strict memory limits. Pair the upgrade with a graph of container RSS over the next two weeks — that is the only place the leak shows up — to confirm the regression is gone.

### 💡 Example
```bash
# Rolling upgrade of a Kafka 4.3.x cluster to 4.3.1.
# Stage one broker at a time; verify ISRs are restored before moving on.
KAFKA_VERSION=4.3.1
curl -O "https://downloads.apache.org/kafka/${KAFKA_VERSION}/kafka_2.13-${KAFKA_VERSION}.tgz"
tar xzf "kafka_2.13-${KAFKA_VERSION}.tgz"

# Per broker:
systemctl stop kafka
ln -sfn "$(pwd)/kafka_2.13-${KAFKA_VERSION}" /opt/kafka
systemctl start kafka

# Then check under-replicated partitions before moving to the next broker.
/opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --under-replicated-partitions
```

## 3. CISA Adds SimpleHelp OIDC Bypass to KEV as Attackers Drop Djinn Stealer

### 🔭 Overview (Tổng)
CISA added CVE-2026-48558, an authentication bypass in SimpleHelp's OpenID Connect (OIDC) integration, to the Known Exploited Vulnerabilities catalog on 29/06/2026 — the first SimpleHelp entry in KEV history. The bug carries a CVSS 10.0 score and is being actively exploited to drop a Node-based loader called TaskWeaver and a cross-platform infostealer called Djinn Stealer onto endpoints managed by compromised SimpleHelp servers. SimpleHelp is a remote monitoring and management tool that managed service providers, IT teams and field-support organisations use to reach edge devices, kiosks, retail terminals and lightly-managed laptops, which is why this lands on an IoT digest as well as a security one. The KEV add comes with a 14-day federal remediation deadline under BOD 26-04 — patches must be applied by 13/07/2026.

### 🔬 Details (Phân)
The flaw lives in deployments that pair SimpleHelp with a generic OIDC provider or Azure AD OIDC. An unauthenticated attacker can submit a forged token containing arbitrary identity claims and receive back a fully authenticated `Technician` session, which is the role that owns file transfer and command execution on every managed endpoint. The token-validation path failed to verify the `iss` and audience claims against the configured issuer, so any signed-or-unsigned token whose payload mapped to an existing technician username was accepted. There is no need for MFA bypass because the bypass happens before the MFA check is reached. The active campaign uses the access to deploy TaskWeaver, a thin Node.js loader, which then stages Djinn Stealer — an information stealer that targets Windows, macOS and Linux, lifts browser data, SSH keys, cloud credential files and crypto wallets, and exfiltrates to attacker-controlled MQTT-style brokers. Public scans put the exposed and vulnerable population at roughly 1,000 SimpleHelp servers reachable on the open internet, and Blackpoint's MDR team has published indicators for the loader.

The IoT framing is the supply-chain one. SimpleHelp sits above thousands of MSP customer fleets, and a compromised technician session inherits trusted-administrator status on every endpoint that server manages — point-of-sale, building automation gateways, signage controllers, and Linux edge boxes included. The same dynamic that made the Kaseya VSA campaign destructive in 2021 applies here: one compromised RMM cascades into hundreds of downstream networks. CISA's 14-day clock is unusually short — most KEV entries get the standard three-week deadline under BOD 22-01 — which is the agency signalling that exploitation volume is high.

### 🎯 Takeaway (Hợp)
Audit every SimpleHelp deployment that uses OIDC this week, upgrade to the patched 5.5.x or 6.0.x build, and rotate every technician credential and active session token. If your environment uses an MSP that runs SimpleHelp, ask the provider for written confirmation of patch status and IoC sweep results before 13/07/2026 — đừng đợi tới deadline mới yêu cầu bằng chứng.

## 4. Home Assistant Replaces Its Matter Server With a matter.js-Based Stack

| Field | Value |

### 🔭 Overview (Tổng)
Home Assistant published "The Matter upgrade you've been waiting for" on 23/06/2026, announcing Matter Server 9.0 — a complete replacement of the Python-based Matter server with one built on the `matter.js` reference implementation. The new server is a drop-in replacement that migrates existing pairings on first start, and it ships with first-class support for Matter 1.5.1, with Matter 1.6 support landing immediately after. For Home Assistant users, the practical wins are faster device reconnection, a Thread mesh visualisation that exposes per-link signal quality, certificate-revocation checks during commissioning, and a hard gate that refuses uncertified development devices unless the operator explicitly opts in. The release is significant beyond Home Assistant: it is one of the largest production deployments of `matter.js` and validates that path for other open-source Matter controllers.

### 🔬 Details (Phân)
The migration matters because the old Python server lagged the Matter SDK by months on every spec point release and had developed reliability quirks around large fabrics (more than 50 devices) and busy Thread networks. `matter.js` is the upstream JavaScript implementation maintained by the same engineers who steer the Connectivity Standards Alliance reference work, so the Home Assistant maintainers get spec-level updates as the SDK ships rather than as a downstream port. The new Thread mesh view renders the network as a graph: routers and end devices as nodes, parent-child and router-router relationships as edges, with link-quality coloured per RSSI. That is the kind of information that previously required a Silicon Labs sniffer and a packet capture. On commissioning, the server now performs an online certificate-status check against the Connectivity Standards Alliance distributed compliance ledger, so a device whose attestation certificate has been revoked is rejected at pairing time rather than silently joined to the fabric.

The breaking-change story is narrower than the version bump suggests: existing fabrics, devices and credentials are migrated automatically, and the UI surface in Home Assistant is unchanged. The operational risk is around the certificate-revocation gate and the uncertified-device guard, both of which are on by default and will reject hardware that worked yesterday. Anyone building or evaluating prototype Matter devices in a Home Assistant lab will need to opt those devices in manually under settings, which is a deliberate friction. The wider ecosystem read is that the Connectivity Standards Alliance's push to harden Matter against certificate-recall failure modes is now being enforced at the controller layer, not just at the spec level.

### 🎯 Takeaway (Hợp)
Update Matter Server to 9.0 in the next maintenance window and inspect the new Thread mesh view before assuming the network is healthy — many users discover one underpowered router that they did not know was the bottleneck. If you run unattested prototype hardware on the same Home Assistant instance, pre-stage the per-device opt-in before upgrading so commissioning does not silently break.

### 💡 Example
```yaml

# Most fields keep their old defaults; the two new ones to know are
# require_attestation_check and allow_uncertified_devices.
log_level: info

allow_uncertified_devices: false      # default; flip to true for lab work
beta_versions: false                  # opt-in to Matter 1.6 preview builds
thread_dataset:
  channel: 25
  pan_id: 0x4321
  network_name: ha-thread-mesh
```
