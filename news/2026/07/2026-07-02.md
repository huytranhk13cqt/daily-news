## 1. Amazon OpenSearch's New Log-Analytics Engine Hits GA With DataFusion and Parquet Storage

### 🔭 Overview (Tổng)
AWS announced general availability of a purpose-built log-analytics engine inside Amazon OpenSearch Service on 01/07/2026. The engine is enabled at domain creation as a new setting, benchmarked against OpenSearch 3.5, and is available in every commercial AWS Region at launch. It is aimed at teams that currently run OpenSearch mainly to store and query high-cardinality logs — application, security, or infrastructure — and pay the cost of Lucene indexing on data that is almost never re-read. AWS pitches the release as up to 4x better price-performance on log workloads and as much as 70% smaller on-disk than the classic engine.

### 🔬 Details (Phân)
The new engine stores data as Apache Parquet with an inverted index alongside for text search, and routes incoming queries through an Apache Calcite parser that decides between two execution paths per predicate. Analytical shapes — aggregations, group-bys, scans — run on Apache DataFusion's columnar vectorised executor, while text search and boolean filters continue to run on Lucene. AWS's headline numbers are ingestion at 1.78 million documents per second versus 647 thousand on the classic engine, an aggregation like error-count-by-service in 717 milliseconds (3.9x faster), a log-volume-by-host query at 252 milliseconds (70x faster on that specific shape), and storage roughly 80% smaller than raw JSON and 52% smaller than Lucene. Timestamp columns get row-group pruning, which is what drives the multi-order-of-magnitude speedups on time-bounded analytics.

The positioning is important. Elastic and OpenSearch have been under sustained pressure from columnar SQL log engines — ClickHouse, Grafana Loki with its recent Parquet backend, and Datadog's Husky — and this release is AWS's response inside the OpenSearch ecosystem rather than in a new product. The trade-off comes in the API surface: the new engine supports Piped Processing Language (PPL) and SQL at launch, but the classic Query DSL is not supported. Teams that have dashboards or alerts written against the DSL will need to translate them before flipping the switch. Because the setting is per-domain, most shops will pilot the engine on a fresh log domain rather than migrate an existing one.

### 🎯 Takeaway (Hợp)
If you run OpenSearch primarily for observability logs, spin up a parallel domain with the new engine, replay a week of production traffic and compare cost-per-query on your five worst dashboards. The likely win is real, but only after you have inventoried every consumer that still speaks Query DSL and rewritten it in PPL or SQL.

### 💡 Example
```bash
# Create a new OpenSearch Service domain with the log-analytics engine enabled.
# Requires the AWS CLI updated post-01/07/2026.
aws opensearch create-domain \
  --domain-name logs-la-engine \
  --engine-version "OpenSearch_3.5" \
  --cluster-config InstanceType=or2.medium.search,InstanceCount=3 \
  --domain-endpoint-options EnforceHTTPS=true \
  --advanced-options '{"log_analytics_engine.enabled":"true"}'

# Query in PPL — this shape hits the DataFusion path.
curl -X POST "https://$DOMAIN_ENDPOINT/_plugins/_ppl" \
  -H 'Content-Type: application/json' \
  -d '{"query":"source=app_logs | where @timestamp > date_sub(now(), interval 1 hour) | stats count() as c by service"}'
```

## 2. Databricks Details Lakebase's SafeKeeper–PageServer Split and Names It LTAP

| Field | Value |
|---|---|
| 📅 Date | 30/06/2026 |
| 🏷️ Topic | Research |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `databricks-lakebase` · `postgres-storage` · `ltap-architecture` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
Databricks published an architectural deep-dive on 30/06/2026 that opens up how Lakebase — its managed Postgres service unveiled earlier in 2026 — decomposed the classic Postgres storage layer into two independently scalable services. The post also introduces a term, LTAP (Lake Transactional/Analytical Processing), for the pattern where the same physical data serves online transactions and analytical queries without a separate replication pipeline. For data platform architects the interesting bit is not the marketing label but the underlying design and the numbers Databricks now attaches to it.

### 🔬 Details (Phân)
Lakebase's storage split places all durability in SafeKeeper, a Paxos-replicated write-ahead-log service that is the only component that ever acknowledges a commit to the client. PageServer sits behind SafeKeeper and materialises data pages from the log for both row-store reads and columnar analytical reads. The mechanism that makes LTAP work is a row-to-columnar transcoding step during PageServer materialisation: Postgres tuples are re-emitted as Arrow-shaped columnar blocks, with an "overflow" side channel that preserves fields whose types do not map cleanly (arrays, hstore, custom domains). Analytical readers pin an LSN and read a consistent columnar snapshot, so warehouse queries and OLTP writes cannot interfere except through cache pressure. Databricks quotes 5x higher write throughput and 2x lower read latency against a monolithic Postgres deployment — the numbers are unaudited but plausibly in range given the design.

The positioning is against Neon, AlloyDB and Aurora DSQL, all of which decompose Postgres storage in different ways. Neon's PageServer is closest architecturally; AlloyDB's columnar engine sits inside the same process; Aurora DSQL leans harder on distributed timestamp ordering. Databricks' argument is that keeping the columnar copy inside PageServer (rather than in a separate warehouse) is what removes the ETL step for analytics. The cost of the pattern is that "columnar-in-storage" is only useful once your analytical workload actually pushes down to that path — a workload that does `SELECT *` on wide rows will not benefit and pays the transcoding overhead.

### 🎯 Takeaway (Hợp)
If you already run a Postgres-plus-warehouse pipeline for a transactional application, this post is worth reading end-to-end before your next architecture review — the LTAP pattern is a real design choice, not just a rebrand of HTAP. Do not port workloads yet; wait for third-party benchmarks and for Databricks to publish the columnar-pushdown coverage matrix.

### 💡 Example
```sql
-- Illustrative: an LTAP workload on Lakebase.
-- 1. OLTP write from the app — hits SafeKeeper, acked at commit.
INSERT INTO orders (order_id, customer_id, total_cents, placed_at)
VALUES (gen_random_uuid(), $1, $2, now());

-- 2. Analytical scan from a BI tool on the same table, same instance —
--    the query planner picks the columnar path in PageServer.
SELECT date_trunc('hour', placed_at) AS hour,
       count(*)                       AS orders,
       sum(total_cents) / 100.0       AS revenue
FROM   orders
WHERE  placed_at >= now() - interval '24 hours'
GROUP  BY 1
ORDER  BY 1;
```

### 🔭 Overview (Tổng)
Snowflake announced Cortex Sense on 30/06/2026, an AI service that builds and maintains a semantic understanding of a Snowflake account by ingesting metadata and usage signals rather than reading the underlying rows. It is designed to sit under Cortex Agents so that natural-language questions land on the right tables and joins without the platform team having to hand-craft a semantic view for every domain. Private preview opens in mid-July 2026. The claim that matters for anyone building on Cortex is that Snowflake now says it can lift agent accuracy from 24.1% to 86.3% on their internal text-to-SQL benchmark while cutting per-query cost.

### 🔬 Details (Phân)
Cortex Sense pulls signals through Snowflake Horizon Connectors: past query text, transformation lineage (dbt, Coalesce, Matillion), BI-tool metric definitions, table and column descriptions, and access patterns. From those it builds a searchable knowledge index that ranks candidate tables and joins for a given user query using four weighted signals — relevance, authority, popularity and freshness — and then hands the ranked context to an agent as grounding. Snowflake reports a per-query cost drop from $1.76 to $0.59 on the same benchmark, driven by the agent no longer inspecting many candidate tables in-band. A continuous-evaluation loop feeds accepted queries back as training data. Access control is RBAC-scoped: private preview supports a single role per account, with per-role contexts coming later.

Context matters here. Semantic views in Snowflake — the hand-authored YAML that maps business terms to columns — are powerful but expensive to build and drift within weeks of shipping. Cortex Sense is Snowflake's answer to the same problem Cube, dbt Semantic Layer, LookML and the Malloy model try to solve, but without asking the customer to author anything. The trade-off is trust: an automatically inferred semantic layer is only as accurate as the metadata under it. Environments with sparse column descriptions and inconsistent naming will get a lower ceiling than environments with rigorous documentation, and the framework needs a way to surface confidence so that agents know when to ask a clarifying question.

### 🎯 Takeaway (Hợp)
If you already run Cortex Agents on Snowflake, request private preview access and pilot Cortex Sense on a domain where the metadata is clean — the reported accuracy lift is real only if the connectors have signal to work with. Continue investing in dbt model descriptions and BI metric definitions in the meantime; those become the training corpus.

| ⚡ Impact | High |

### 🔭 Overview (Tổng)
Espressif tagged ESP-IDF v6.1-beta1 on 29/06/2026, the first beta of the 6.1 line, alongside a v6.0.2 bugfix on the same day. The release opens preview support for a new chipset, ESP32-S31, adds several Wi-Fi credentialing modes, and — most importantly for anyone already in production — carries two security actions that firmware teams need to plan around. The first is a hardening fix for a JPEG-decoder vulnerability (GHSA-v6r2-f6p2-88cj). The second is that ECDSA Secure Boot V2 is disabled on ESP32-H2, ESP32-C5 and ESP32-P4 due to a newly discovered flaw; RSA-based Secure Boot V2 remains available on those parts.

### 🔬 Details (Phân)
On the feature side v6.1-beta1 adds Wi-Fi OWE-Only mode in SoftAP, DPP multi-configuration for stations, and runtime attach/detach of sleep-retention modules, which is useful for battery-powered designs that want to swap between low-power and full-runtime configurations without a full reboot. The mbedTLS bump to 4.1.0 removes 192-bit curve support, which will silently break any device attestation flow that still uses P-192. Breaking changes are unusually broad for a beta: MQTT moves out of the core into the component manager as `espressif/mqtt`, FreeRTOS headers are stripped from peripheral drivers (so many BSPs will fail to compile until includes are fixed), the LCD API is unified with a new colour-format model, SPI drivers no longer accept `ESP_INTR_FLAG_SHARED`, the SPI flash struct is privatised, and PSA persistent keys must be re-imported. A known issue on the ESP32-C2 v2.0 causes Wi-Fi TX to fail after light sleep.

The security piece needs care. Devices on H2, C5 or P4 currently running ECDSA Secure Boot V2 stay bootable — the fix is a policy change for new provisioning — but Espressif's advisory says teams evaluating those parts for a project should switch to RSA-3072 Secure Boot V2 until an ECDSA-safe path returns. For a fleet already in the field the practical impact is that any signing infrastructure that assumes ECDSA everywhere needs to be gated by chip revision. The JPEG advisory is more mundane but should be picked up quickly on any device that decodes images from an untrusted network source (dashboards, camera preview, e-paper displays with dynamic content).

### 🎯 Takeaway (Hợp)
Pin v6.0.2 in production for now, mirror v6.1-beta1 in a dedicated CI branch, and audit signing infrastructure for ECDSA-on-H2/C5/P4 assumptions. If you ship an image decoder, pull the JPEG advisory patch through even if you cannot move to 6.1 yet.

### 💡 Example
```bash

cd $IDF_PATH
git fetch --tags espressif
git checkout -b eval/idf-6.1-beta1 v6.1-beta1
./install.sh esp32,esp32c6,esp32s3,esp32p4
. ./export.sh

# In your project's sdkconfig: force RSA-3072 Secure Boot V2 on H2/C5/P4.
# CONFIG_SECURE_BOOT=y
# CONFIG_SECURE_BOOT_V2_RSA_SCHEME=y
# CONFIG_SECURE_SIGNED_APPS_RSA_SCHEME=y
# # Do NOT set CONFIG_SECURE_BOOT_V2_ECDSA_SCHEME on ESP32-H2/C5/P4.

idf.py build
```

### 🔭 Overview (Tổng)
Home Assistant 2026.7 shipped on 01/07/2026 with a set of changes that are individually small but collectively force most self-hosted installations to plan the upgrade rather than click Update. Purpose-specific triggers and conditions are graduated out of Labs; the Logbook is rebuilt as an Activity Timeline; ZHA gains a full-page device view with cluster, binding, signature and neighbour tabs; and there is a dedicated proxy settings panel for infrared and radio-frequency remotes. The two items to check before pressing Update are that `zwave-js-server` 3.9.0 or higher is now required and that several automation triggers have been renamed, so any YAML that still references the old names will silently stop firing.

### 🔬 Details (Phân)
The trigger renames are targeted at ambiguity. `battery.low` becomes `battery.became_low`, `update.update_became_available` becomes `update.became_available`, and `vacuum.docked` becomes `vacuum.returned_to_dock`. Under the hood, users on Home Assistant OS need version 18 or newer for the new Raspberry Pi bootloader EEPROM update entity to appear, and the ZHA full-page device view replaces the accordion cards for coordinator diagnostics.

The Z-Wave JS server dependency is where the most breakage will happen. The `zwave-js-server` add-on that most Home Assistant users run is auto-updated, but people who run the server outside the add-on (Docker, systemd, or bundled in Zwave2Mqtt-style stacks) will get a "schema mismatch" error and their Z-Wave integration will refuse to start until they roll their server forward to 3.9.0. The purpose-specific triggers pattern is worth understanding beyond the two renames: it is the direction Home Assistant is taking to make automations self-documenting and to let the UI generate them from a semantic template rather than a raw event.

### 🎯 Takeaway (Hợp)
Grep your `automations.yaml` for the three renamed triggers, upgrade `zwave-js-server` first if you run it standalone, then upgrade Home Assistant itself. Nếu bạn còn dùng Mycroft hay MS Teams integration thì đây là tuần cuối, sau bản này bị xoá luôn.

## 6. Raspberry Pi rpi-sb-provisioner 2.3 Adds Device Identity and Fleet-Scale Full-Disk Encryption

| Field | Value |
|---|---|
| 📅 Date | 01/07/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | IoT |
| 🔑 Keywords | `raspberry-pi` · `secure-boot` · `full-disk-encryption` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
Raspberry Pi published rpi-sb-provisioner 2.3 on 01/07/2026, a major revision of its secure-boot provisioning toolchain aimed at organisations that ship Pi-based hardware in the thousands. Two features are the headline: a Device Identity system that ties every Pi to an immutable identity registered against the operating organisation's account, and Image Description Provisioning (IDP), which lets the toolchain produce fully custom partition layouts and OS images without being constrained to Raspberry Pi OS or its derivatives. Together they close the last gaps that pushed larger integrators toward custom bootloader work.

### 🔬 Details (Phân)
The new stack is built around a companion library called `rpi-fw-crypto` that performs asymmetric cryptography inside a boundary that never exposes device-unique private keys to the host. Full-disk encryption keys are derived from `rpi-fw-crypto` material rather than stored on-device, and provisioning servers now sign material that is cryptographically bound to a specific server identity, so a stolen SD card image cannot be re-imprinted onto a different Pi in a different facility. The pre-boot authentication environment lets the operator require a passphrase, a network handshake, or a Yubikey before Linux starts. On the operator side, 2.3 ships a manufacturing database, an audit log and a web UI, so teams that used to run provisioning from a bash script can now see, per serial number, when a device was flashed, what image, and who signed off. `rpi-image-gen` remains the tool for authoring the base image; `rpi-sb-provisioner` orchestrates the run.

The wider read is that Raspberry Pi is treating industrial and edge deployments as first-class rather than a side use of the consumer product. Historically, teams that wanted attested boot and disk encryption on a Pi wound up hand-assembling `pi-secure-boot-signer`, `cryptsetup`, and a home-grown REST service. IDP explicitly acknowledges the customers building on non-standard Linux distributions — Yocto, Buildroot, and Alpine derivatives — and adds them as supported paths rather than forcing a rebase on Raspberry Pi OS. The trade-off is that the full pipeline now assumes an internet-connected provisioning server and an account, so fully-air-gapped manufacturing lines will need to run a local mirror.

### 🎯 Takeaway (Hợp)
If you provision Pi hardware at scale, plan a migration to 2.3 within the next quarter — the audit trail and web UI alone justify it. Teams shipping non-Raspberry-Pi-OS images should pilot IDP against a single product line first and validate that the FDE-key derivation flow works with the field-replacement process before rolling it out fleet-wide.

### 💡 Example
```bash
# Provision a fleet Pi with rpi-sb-provisioner 2.3 using an
# image description that opts in to full-disk encryption and
# Device Identity registration.
sudo apt update && sudo apt install rpi-sb-provisioner=2.3.*

rpi-image-gen build \
  --profile     product-A \
  --distro      debian-bookworm \
  --output      /var/lib/rpi-images/product-A.img

rpi-sb-provisioner run \
  --image           /var/lib/rpi-images/product-A.img \
  --idp             /etc/rpi-sb/product-A.idp.yaml \
  --enable-fde \
  --register-device \
  --org             acme-devices \
  --audit-log       /var/log/rpi-sb/product-A.jsonl
```
