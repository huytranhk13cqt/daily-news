### 🔭 Overview (Tổng)
ClickHouse extended its Claude-powered Agents service, launched at Open House 2026 in May, to the Managed Postgres tier on 02/07/2026. The integration lets a user pose a plain-English question that the agent decomposes into a Postgres query, a ClickHouse query, or both, and merges the results in one response. The pitch is aimed at teams that already run OLTP on Postgres and analytics on ClickHouse and today write glue code to correlate the two.

### 🔬 Details (Phân)
The agent inspects Postgres schemas automatically, runs read-only SQL by default, and exposes several purpose-built skills. A migration skill walks a user through the discovery, schema-design, type-mapping and validation steps of moving a table from Postgres to ClickHouse. A performance-tuning skill reads Query Insights and native metrics — CPU, memory, disk, connections, cache hit ratio, deadlocks — and recommends fixes like missing indexes. The runtime is built on LibreChat (ClickHouse's open-source acquisition) and speaks the Model Context Protocol, so third-party MCP servers can be plugged in as extra context sources.

The broader position matters for data platform teams choosing where OLTP+OLAP consolidation should happen. Databricks pushed its LTAP pattern earlier in the week, Snowflake published Cortex Sense on 30/06, and ClickHouse's answer is that if you already run analytics in ClickHouse, adding Managed Postgres and a shared agent is a simpler path than porting existing OLTP to a Postgres-derived storage engine. The trade-off is that Managed Postgres is still in public beta with a 50% discount for beta users, and the agent's write path is deliberately not enabled by default — automated fixes and self-healing are marked as roadmap items rather than shipped features.

### 🎯 Takeaway (Hợp)
If you already run ClickHouse Cloud and have a small Postgres footprint you would rather not migrate, spin up Managed Postgres in beta, wire the CDC pipeline into ClickHouse, and pilot the agent on one production analyst workload. Keep the agent read-only until the self-healing path lands, and treat the migration skill as scaffolding — not a replacement for a data engineer's review.

## 2. LogHouse Crosses 1.59 Quadrillion Rows Across Three Clouds With 33-Geoshard Architecture

### 🔭 Overview (Tổng)
ClickHouse's Sergey Veletskiy published a deep-dive on 30/06/2026 documenting how the internal LogHouse observability platform grew from 19 PiB two years ago to 431 PiB of uncompressed data and 1.59 quadrillion rows today, a 23x increase. The post is worth reading for teams who operate multi-region observability at scale — the design choices, not the headline numbers, are what generalise. Peak ingestion sits at roughly 80 GiB/s and 190 million rows/s across about 5,800 concurrent inserts.

### 🔬 Details (Phân)
LogHouse now spans 33 geoshards across 36 cells running on AWS, Google Cloud and Azure. Most regions host a single cell; a handful of high-traffic regions host multiple. The largest single cell handles 21 GiB/s, 61 million rows/s and 620 inserts/s at peak. On the write path, Async Inserts batch small writes server-side and cut part creation by 4x to 24x depending on table shape, daily partitioning replaced monthly for the largest tables, and an S3 spillover buffer holds writes durably while a cell is unavailable. On the read path, a three-level Distributed table hierarchy — local, regional, global — hides the topology from queries; regional and global tables use dictionary-driven shard pruning to skip cells that cannot contribute to a result, which is what keeps cross-continent queries under one second. Compression averages 16x, so the 431 PiB uncompressed corpus lives on 27 PiB of disk.

Compositionally, SysEx (system table exports) is 78% of the volume and 93% of the rows, and OpenTelemetry handles the remaining ~95 PiB. The 2025 predecessor post at 100 PB documented moving off pure OTel; this one documents the wire-format and buffering choices that got the platform to a quadrillion rows without a rewrite. The generalisable pattern is that write amplification and metadata scan cost — not raw storage — are what constrain a multi-region observability system at this size.

### 🎯 Takeaway (Hợp)
If you run an observability platform above a few PB, treat this post as reference architecture: async inserts, daily partitioning for the biggest tables, and dictionary-based shard pruning are all directly portable. Not every team needs 33 geoshards, but the shard-pruning technique buys back interactive query latency at any multi-region scale.

### 💡 Example
```sql
-- Sketch: dictionary-based shard pruning on a global Distributed table.
CREATE DICTIONARY shard_by_region
(
    region     String,
    shard_key  UInt32
)
PRIMARY KEY region
SOURCE(CLICKHOUSE(host 'meta' user 'ro' db 'meta' table 'regions'))
LAYOUT(HASHED())
LIFETIME(300);

CREATE TABLE logs_global AS logs_local
ENGINE = Distributed(
    global_cluster,
    default,
    logs_regional,
    dictGetUInt32('meta.shard_by_region', 'shard_key', region)
);

-- A query that filters by region reads only cells whose shard_key
-- matches, so a Sydney-only query does not touch us-east or eu-west.
SELECT count()
FROM   logs_global
WHERE  region = 'ap-southeast-2'
  AND  timestamp >= now() - INTERVAL 15 MINUTE;
```

### 🔬 Details (Phân)
The headline feature is catalog federation between Snowflake Horizon and Unity Catalog: models declared in one governance layer can be discovered and queried from the other without a duplicate catalog entry. JavaScript UDFs are now supported for Snowflake and BigQuery via a native macro, and the Spark adapter picks up the `insert_overwrite` incremental strategy that the Databricks adapter already had. BigQuery gains reservation support so that jobs can be routed to a specific reservation, and the bundled DuckDB is bumped to 1.5.4. Versioned models get an unsuffixed view that always points to the current latest version, with configuration knobs to customise the name pattern or turn the behaviour off — the default is on, so a repository that already ships a table called `orders` next to `orders_v2` will now conflict on the auto-generated view. Configurable seed size for state comparison defaults to 1 MiB, JSON schema export via `dbt man --schema catalogs` is available for catalogs.yml v2, and the Rust toolchain used to build the Fusion CLI moves to 1.96.

The context is that dbt 2.0 is the release where the Fusion runtime, catalog federation, and dbt login stop being opt-in previews and become the assumed path. Teams still on dbt-core 1.11 keep long-term support, but any team piloting Fusion needs the alpha to test their model graph end-to-end. Migration risk clusters around the versioned-model naming rule and the manifest serialisation changes that keep landing in each alpha; the release notes call out several manifest fixes for snapshot materialisations, which imply that a full `dbt parse` cycle is required before comparing state.

### 🎯 Takeaway (Hợp)
Pin dbt-core 1.11.12 in production, spin up 2.0.0-alpha.3 in a dedicated CI job, and specifically test versioned-model builds and state comparison against a saved manifest. If you are on Snowflake or Databricks and evaluating Iceberg-shaped catalog federation, this alpha is the first version worth running with a real project.

## 5. Antmicro Publishes Zephyr Sensor Anomalies Library for Background On-Device ML

### 🔭 Overview (Tổng)
Antmicro published the Zephyr Sensor Anomalies library on 30/06/2026 through the Zephyr Project blog, an open-source component for running anomaly detection on Zephyr-based devices without stealing time from the primary application thread. It targets the common industrial-IoT pattern where a device streams sensor data to the cloud and wants a lightweight local check to catch drift or fault before anything hits the network. The library ships two ML backends, a device-tree-driven sensor discovery layer, and a callback API for anomaly events.

### 🔬 Details (Phân)
The library supports Kenning Zephyr Runtime and emlearn as pluggable backends, so a team can train a model in Kenning, export it, and run inference from the same Zephyr project. Sensor providers are declared through the device tree — the library walks the tree at init, subscribes to the sensors that are marked as anomaly sources, and hands them to the detector. Detection runs on its own thread with an optional sliding window and smoothing step, so an application can either read raw sensor samples on its own cadence or subscribe to a callback that fires only when a detector emits an anomaly. Evaluation ships with time-based metrics — detection delay, fault detection rate, false alarm rate — that are more useful for multi-sample anomalies than a classification F1 score would be.

The positioning is worth calling out. Edge Impulse and Arduino's own predictive-maintenance stack cover roughly the same problem shape, but they assume you are shipping a specific board or SDK. Antmicro's library sits at the Zephyr layer, so any Zephyr-supported chip — nRF, STM32, ESP32, RISC-V microcontrollers — is a target as long as the sensors are exposed through the standard sensor API. The trade-off is that model training and quantisation still happen outside the device, and the two backends have different constraints on model size and operator coverage.

### 🎯 Takeaway (Hợp)
If you already ship a Zephyr fleet, add the library as an out-of-tree module on one device family and pilot it with a trivial vibration or current-draw model. The interesting evaluation is not accuracy — it is how much CPU headroom you keep during a normal duty cycle when the detector thread is active.

### 💡 Example
```c
/* Illustrative: initialise the anomaly detector on a Zephyr device. */
#include <zephyr/kernel.h>
#include <sensor_anomalies/detector.h>

static void anomaly_cb(const struct anomaly_event *ev, void *user)
{
    printk("Anomaly on %s: score=%.3f window=%u samples\n",
           ev->sensor_name, (double)ev->score, ev->window_samples);
}

int main(void)
{
    const struct sensor_provider *prov = sensor_provider_get_default();
    struct anomaly_detector det = {
        .provider   = prov,
        .backend    = ANOMALY_BACKEND_EMLEARN,
        .model_id   = "vibration_v3",
        .window_ms  = 250,
        .smoothing  = ANOMALY_SMOOTHING_EMA,
        .callback   = anomaly_cb,
    };

    if (anomaly_detector_init(&det) != 0) {
        return -1;
    }
    return 0;
}
```

### 🔭 Overview (Tổng)
Espressif announced the ESP-BSP Generator on 30/06/2026, a web tool that lets a developer pick a proven Espressif dev-kit BSP as a starting point and produce a fully-shaped BSP component for their own PCB. It targets the exact pain point that anyone doing custom ESP32 hardware has hit — copying `esp-bsp/esp-box-3`, hand-editing pin maps, updating Kconfig, and hoping the peripheral drivers still resolve. The generated package follows the same layout and board-API conventions as the official BSPs, so an application built against ESP-BOX-3 can retarget with a component swap.

### 🔬 Details (Phân)
The workflow is web-based: load a starter configuration (ESP-BOX-3, ESP32-S3-EYE, ESP32-C3-LCDKit and other official kits), edit pin assignments and enable or disable features to match your schematic, and generate a downloadable BSP package. Espressif's post frames the output as "production-style", meaning it includes the component manifest, board APIs, drivers wired to the correct peripherals, and a Kconfig that resolves without warnings. The generator lives at `bsp-generator.espressif.tools/` and is complementary to the existing `esp-bsp` GitHub repository — the repo continues to be the canonical source for reference boards, and the generator is the tool for deriving a new board from one of them.

The context is that Espressif is closing the last friction points around going from prototype to custom hardware inside ESP-IDF. Yesterday's ESP-IDF v6.1-beta1 tightened peripheral drivers and unified the LCD API; the BSP Generator makes the leap from a `esp-box-3` reference project to a bespoke enclosure a matter of an afternoon rather than a week. The trade-off is coverage: only the officially-supported dev kits are starter templates, so a team building on a rare peripheral combination still has to hand-assemble the last mile.

### 🎯 Takeaway (Hợp)
The next time you spin a custom ESP32 board, generate the BSP from the closest dev kit rather than forking a checked-in board directory. Diff the generated component against your existing hand-rolled BSP as a sanity check — a mismatch is more likely to be your bug than the generator's.

### 💡 Example
```bash

#   idf_component_register(SRCS "main.c"

```
