### 🔭 Overview (Tổng)
ClickHouse tagged the 26.6 release on 03/07/2026, timed to the project's 10th open-source anniversary and headline-billed as 56 new capabilities, 79 performance improvements and 366 bug fixes. The three items that matter for a data engineer picking up the release are hypothetical skip indexes, cascading refreshable materialized views, and an experimental streaming-query mode. Together they cover the three most-asked-for gaps in the 25.x line — cheaper index tuning, saner MV pipelines, and a first-class push model on top of the analytical engine.

### 🔬 Details (Phân)
Hypothetical skip indexes let a session evaluate what a proposed index would prune before any granule is written. On the UK properties dataset with 487 million rows the release notes show a set index at a 128-granule group configuration skipping 77% of granules for a London district query, and a per-granule variant reaching a 92% skip ratio; the same session can compare configurations without a rebuild. Cascading refreshable materialized views introduce a `REFRESH DEPENDS ON` clause so downstream views inherit refresh timing from their parents instead of racing against independent schedules, which eliminates the "stale downstream" window that operators used to paper over with sleep-based refreshes. Streaming queries — enabled with `SETTINGS enable_streaming_queries = 1` and the `STREAM` suffix — keep a cursor and emit new rows as blocks arrive, so a consumer can `SELECT ... STREAM` a materialized view and get pushed updates without polling.

The performance thread has a concrete number too: a 16-layer nested query drops from about 98 ms on 26.5 to 30 ms on 26.6, roughly a 3x improvement in analysis-time overhead that shows up on any BI tool that ships deeply-templated SQL. Around the headliners the release lands `ALTER TABLE ... ADD ENUM VALUES`, a `system.documentation` table wired into the CLI `help` command, native GeoJSON parsing plus Mapbox vector tile functions, an `aiEmbed` function targeting Ollama and OpenAI, and PNG output for query results. The migration story is straightforward for read-only workloads; anything using `REFRESH` on chained materialized views should audit the schedule graph before enabling the new dependency mode because implicit ordering assumptions from the 25.x refresh model no longer hold.

### 🎯 Takeaway (Hợp)
Pull 26.6 into a staging cluster, run your slowest analytical query with a hypothetical skip index instead of guessing a granularity, and pilot cascading refreshes on the ugliest MV chain you own. Streaming queries are worth a proof-of-concept for near-real-time dashboards, but keep them in preview clusters until 26.7 promotes the flag out of experimental.

### 💡 Example
```sql
-- Hypothetical skip index: measure skip ratio without building the index.
SELECT count()
FROM   properties
WHERE  district = 'Camden'
SETTINGS
    additional_skipping_index =
        'district_idx TYPE set(0) GRANULARITY 128',
    log_skip_ratio = 1;

-- Cascading refresh: downstream MV inherits its parent's schedule.
CREATE MATERIALIZED VIEW analytics.orders_daily
REFRESH EVERY 5 MINUTE
AS SELECT toDate(ts) AS d, sum(amount) FROM orders GROUP BY d;

CREATE MATERIALIZED VIEW analytics.orders_weekly
REFRESH DEPENDS ON analytics.orders_daily
AS SELECT toStartOfWeek(d) AS w, sum(sum_amount)
   FROM   analytics.orders_daily GROUP BY w;

-- Streaming query: push new rows to the client as they arrive.
SELECT sku, sum(qty) AS q
FROM   orders
GROUP  BY sku
STREAM
SETTINGS enable_streaming_queries = 1;
```

## 2. Databricks Details the gpu-monitor Stack Keeping Its AI Fleet Reliable

| Field | Value |

### 🔭 Overview (Tổng)
Databricks published a detailed operational post on 01/07/2026 explaining how it keeps GPU jobs healthy across the fleet running its AI products. The value for other teams is not the specific tooling but the failure taxonomy and the check schedule — the post separates GPU failures into crashed jobs, silent slowdowns, and numerical corruption, then maps each to a stage in the health-check pipeline. Anyone operating multi-node training or inference at more than a handful of nodes will recognise the gaps this framing exposes in their own stack.

### 🔬 Details (Phân)
The `gpu-monitor` service runs three phases. Active bootstrap checks fire before a job is scheduled and cover GPU compute validation, NVLink peer connectivity, intra-node NCCL all-reduce correctness, RDMA NIC bandwidth, ECC memory health, PCIe integrity and NVIDIA DCGM diagnostics. Passive continuous checks run for the life of a workload and watch NVLink lane status, clock throttling reasons (`HW_SLOWDOWN`, `HW_THERMAL_SLOWDOWN`), cumulative RDMA port downtime rather than flap count, XID errors, PCIe AER uncorrectable errors and thermal gradients between the GPU core and HBM. Periodic multi-node active checks run between jobs and sweep NCCL collective bandwidth from 8-byte to 2 GB payloads with per-size pass criteria — the post quotes `BusBW ≥ 250 GB/s` at 1 GB and a 750-microsecond latency threshold for small payloads.

The operational lesson buried in the post is that `NCCL_IB_TIMEOUT` at the InfiniBand layer fires at roughly seven seconds with retries, before PyTorch's own NCCL watchdog timeout. A single port-down window past the IB threshold crashes the job regardless of what the watchdog is set to, so a team relying on watchdog tuning to survive fabric hiccups is measuring the wrong knob. Databricks also stress-tests hardware with its most demanding internal workloads — the KARL reinforcement learning trainer, agentic coding pipelines and document intelligence — to surface fabric flakiness and thermal hotspots before customer jobs ever land on the nodes.

### 🎯 Takeaway (Hợp)
If you run GPU training larger than a single node, audit which of the three check phases your monitoring covers and add the ones you are missing — silent slowdown is the category most stacks under-instrument. Treat the IB timeout as the true watchdog and set application-level timeouts to match, not the other way round.

### 💡 Example
```yaml
# Illustrative NCCL / DCGM health-check schedule inspired by Databricks' post.
bootstrap:
  interval: on-job-launch
  checks:
    - dcgmi diag -r 3            # short diagnostics
    - nccl-tests all_reduce_perf -b 1G -e 2G -f 2
    - ib_write_bw --duration=15
periodic:
  interval: 30m-between-jobs
  checks:
    - nccl-tests all_reduce_perf -b 8 -e 2G -f 2
    - dcgmi diag -r 2
continuous:
  interval: 10s
  metrics:
    - nvidia_smi.clocks_throttle_reasons
    - dcgm.xid_errors
    - dcgm.rdma_port_downtime_cumulative_ms
    - dcgm.thermal_gradient_core_hbm
timeouts:
  # Align app-level timeout with the InfiniBand watchdog, not the other way.
  ib_watchdog_seconds: 7
  app_timeout_seconds: 10
```

### 🔬 Details (Phân)
The adapter tags each query with `@@dbt_model_name`, `@@dbt_materialized`, `@@dbt_core_version` and `@@dbt_databricks_version` out of the box, so a query landing in `system.query_history` can be joined straight back to a model and materialization type. Profile-level custom tags live under a `query_tags` block in `profiles.yml` and let a team stamp cost-center, environment and owning-team on everything without editing models. The positioning is that Databricks and Snowflake have been converging on the same "tag every query" story for a year now, but until this preview the dbt-databricks side depended on manual `set_query_tag` macros that broke across adapter upgrades. Snowflake shipped native dbt query tags in dbt-snowflake 1.9; this release brings the Databricks adapter to feature parity, and does it inside the standard adapter so no additional package is needed. The trade-off worth flagging is that `system.query_history` retention on Databricks is limited and finance-grade attribution still needs an export sink — the preview is for observability, not billing reconciliation.

### 🎯 Takeaway (Hợp)
Turn the auto-tags on across every dbt-databricks project this week; the cost is zero and the observability payoff is immediate. Layer profile-level tags for team and cost-center, then wire a scheduled export of `system.query_history` into your own lakehouse if you need attribution windows longer than a few days.

### 💡 Example

```yaml
  target: default
  outputs:
    default:
      type: databricks
      host: adb-1234.5.azuredatabricks.net
      http_path: /sql/1.0/warehouses/abcd1234
```

```sql
-- system.query_history — attribute compute time by dbt model.
SELECT
    query_tags['@@dbt_model_name']    AS model,
    query_tags['@@dbt_materialized']  AS materialization,
    query_tags['team']                AS team,
    sum(execution_time_ms) / 1000     AS seconds
FROM   system.query_history
WHERE  query_tags['@@dbt_core_version'] IS NOT NULL
  AND  start_time >= current_date - INTERVAL 7 DAYS
GROUP  BY model, materialization, team
ORDER  BY seconds DESC
LIMIT  25;
```

### 🔭 Overview (Tổng)
Raspberry Pi released rpi-sb-provisioner 2.3 on 01/07/2026, the third minor release of the secure-boot provisioning tool aimed squarely at industrial and OEM users deploying fleets of Raspberry Pi boards. The two headline changes are device identity — every provisioned board is stamped with an immutable identity that survives OS updates and factory resets — and image description provisioning, which turns the previously fixed-function provisioner into a programmable one that can lay down arbitrary partition schemes. Both fold into Raspberry Pi Connect for Organisations, letting a device association persist across resets.

### 🔬 Details (Phân)
The identity flow uses `rpi-fw-crypto` for asymmetric cryptography so that private-key material never leaves the provisioning server unencrypted; the on-device counterpart also holds encryption key material that can be used for full disk encryption downstream. Image description provisioning is where the practical scope widens — the provisioner now takes a description of partition layout, filesystem types and per-partition attributes as input, so an OEM shipping a custom Yocto-derived image can use the same tooling as an integrator using a `pi-gen` variant. The release blog highlights a bulk-provisioning web UI, an audit log and a manufacturing database aimed at contract-manufacturer workflows; those features build on the CLI so anything that can be done from the UI can also be scripted.

The change that matters for existing users is that upgrading past 2.3 rewires how identities are minted. Devices provisioned on 2.2 or earlier without device identity will not automatically gain one — a re-provision is required, and Raspberry Pi recommends coordinating that with the next OS refresh so the disruption is bounded. For anyone already leaning on Connect for Organisations, the persistence guarantee removes the biggest operational nuisance of the previous flow, which was that a factory reset broke device-to-fleet association and needed manual reattachment.

### 🎯 Takeaway (Hợp)
If you ship Raspberry Pi hardware in fleets larger than a hundred units, adopt 2.3 on your next manufacturing batch and gate device identity on new boards from day zero. Existing installations can stay on 2.2 until the next scheduled OS refresh, but plan the identity rollout with the same care as a certificate rotation.

```cpp
// Illustrative UNO Q + Modulino Movement anomaly-detection loop.
#include <Modulino.h>
#include <edge-impulse-sdk/classifier/ei_run_classifier.h>

ModulinoMovement imu;
constexpr size_t WINDOW = 128;
static float features[WINDOW * 3];

void setup() {
    Serial.begin(115200);
    Modulino.begin();
    imu.begin();
}

void loop() {
    for (size_t i = 0; i < WINDOW; ++i) {
        float x, y, z;
        imu.read(x, y, z);
        features[i * 3 + 0] = x;
        features[i * 3 + 1] = y;
        features[i * 3 + 2] = z;
        delay(10);
    }
    signal_t sig;
    numpy::signal_from_buffer(features, WINDOW * 3, &sig);
    ei_impulse_result_t r;
    run_classifier(&sig, &r, false);
    if (r.anomaly > 0.6f) {
        Serial.println("anomaly detected");
    }
}
```
