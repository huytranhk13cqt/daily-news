### 🔭 Overview (Tổng)
Databricks published a Gated Public Preview of Auto Upgrades on 06/07/2026, a Unity Catalog control-plane feature that quietly enables best-practice table capabilities on existing managed tables once every client touching them can handle the change. The feature targets the long tail of tables that never got Liquid Clustering, Deletion Vectors or Column Mapping because nobody remembered to run the ALTER, and it lands as part of the broader push at DAIS 2026 to make the lakehouse defaults competitive with Snowflake and BigQuery without asking platform teams to backfill. For anyone maintaining hundreds of Unity Catalog schemas, the release is the first time Databricks has offered a hands-off way to close the gap between "current best practice" and "what production actually runs on".

### 🔬 Details (Phân)
The seven features on the initial upgrade list are Liquid Clustering, Deletion Vectors, Column Mapping, Parquet V2, Catalog Commits, Row Tracking and Checkpoint V2. Databricks observes access patterns over a rolling 100-day window and only flips a feature on when three conditions all hold: every Databricks client that touched the table supports it, the table is still active (idle tables are skipped so they don't get quietly rewritten), and no external clients have shown up during observation. Once every existing table in a schema qualifies, the same feature becomes the default for new tables created in that schema, so the upgrade path is monotonic rather than a per-table decision.

Positioning-wise this closes the well-known gap where Delta table properties documented in release notes never actually reach production because turning them on requires knowing every consumer is compatible. External Iceberg or Trino readers, in particular, block many teams from adopting Deletion Vectors or Column Mapping today, and Auto Upgrades encodes that check into the platform instead of a Confluence page. The safety envelope is deliberately conservative — only GA features with no performance or cost regression qualify, every change is logged distinctly in `DESCRIBE HISTORY` and system tables, and any upgrade remains reversible; a per-table disable is respected permanently and never re-flipped by later observation windows.

### 🎯 Takeaway (Hợp)
If your Unity Catalog fleet has been sitting on Delta protocol 2/3 for years, spend a sprint auditing which tables are still touched by non-Databricks readers and either register those clients or explicitly disable Auto Upgrades on the tables they use — because once the 100-day window elapses everything else gets Liquid Clustering and Deletion Vectors for you. Keep an eye on the `system.access.table_lineage` view during the preview so you notice if a forgotten external Trino service shows up and blocks a schema-wide flip.

### 💡 Example
```sql
-- Opt a sensitive table out of Auto Upgrades — the setting is respected forever.
ALTER TABLE main.finance.gl_journal
  SET TBLPROPERTIES ('delta.autoUpgrade.enabled' = 'false');

-- Audit which features were flipped, when, and by which observation window.
SELECT table_name,
       feature_name,
       previous_state,
       new_state,
       event_time
FROM   system.upgrades.table_feature_events
WHERE  catalog_name = 'main'
  AND  event_time > current_timestamp() - INTERVAL 30 DAYS
ORDER  BY event_time DESC;
```

## 3. Confluent Maps Out Kafka SASL PLAIN vs SCRAM and Why Only One Hot-Reloads Credentials

| 🔑 Keywords | `apache-kafka` · `sasl-scram` · `credential-rotation` |

### 🔭 Overview (Tổng)
Confluent published a deep dive on 06/07/2026 explaining why credential rotation on Kafka brokers behaves so differently depending on the SASL mechanism, and why the interesting distinction is really about where credentials live rather than the crypto. The post walks through PlainLoginModule, ScramLoginModule and Confluent's FileBasedLoginModule side by side and shows exactly which one requires a broker restart to pick up a rotated secret. For anyone operating multi-tenant Kafka with quarterly credential rotation obligations, it is the first vendor doc that puts the three modules on the same page with concrete JAAS snippets.

### 🔬 Details (Phân)
The core observation is that PlainLoginModule loads its `user_alice=…` entries once at broker startup from static JAAS configuration; rotating that password means editing the file and rolling the brokers, which is why teams with strict rotation SLAs quietly avoided PLAIN even where TLS made it acceptable on the wire. ScramLoginModule instead stores salted SCRAM credentials in the cluster metadata log — KRaft today, ZooKeeper on legacy clusters — so the broker fetches and updates them dynamically via the Admin API without a restart. Confluent's FileBasedLoginModule fills the middle by watching a JSON file on disk with a configurable `refresh_ms` interval, giving hot-reload semantics for teams that still want PLAIN-style flat-file credential distribution.

The post is unusually blunt about the operational trade-offs. SCRAM adds a cryptographic verifier stored in cluster metadata, so credential deletion is now a distributed operation rather than a file edit, and getting the metadata log wrong is worse than getting a JAAS file wrong. FileBasedLoginModule keeps the local-file simplicity but only works with Confluent's own module, so open-source Apache Kafka deployments effectively choose between "restart to rotate" or "invest in the SCRAM control plane". The configuration example ties this back to real listeners — `customer_plain`, `customer_scram` and `customer_file` — and shows that a broker can mix all three simultaneously on different listener names, which is the pattern most migrations end up on.

### 🎯 Takeaway (Hợp)
If your Kafka fleet still ships PLAIN credentials in a static JAAS file and your compliance team is asking for shorter rotation windows, pick SCRAM-SHA-512 for internal producers and consumers and leave FileBasedLoginModule as a bridge for legacy CLI clients you cannot re-provision. The migration is worth doing before your next audit; hot-reload without downtime is only free if you architect for it in advance.

### 💡 Example
```properties
# Three Kafka listeners, three credential stories on the same broker.
# customer_plain requires a restart to rotate; customer_scram and
# customer_file both hot-reload without downtime.
listener.name.customer_plain.plain.sasl.jaas.config= \
  org.apache.kafka.common.security.plain.PlainLoginModule required \
  username="broker" password="broker-secret" \
  user_alice="alice-secret";

listener.name.customer_scram.scram-sha-512.sasl.jaas.config= \
  org.apache.kafka.common.security.scram.ScramLoginModule required;

listener.name.customer_file.plain.sasl.jaas.config= \
  io.confluent.kafka.server.plugins.auth.FileBasedLoginModule required \
  config_path="/etc/kafka/apikeys.json" refresh_ms="10000";
```
