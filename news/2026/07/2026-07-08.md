## 1. Databricks Ships Contextual Policies in Omnigent to Govern AI Agents by Session State

| Field | Value |

### 🔭 Overview (Tổng)
Databricks published a design note on 07/07/2026 introducing Contextual Policies in Omnigent, the agent-governance framework it open-sourced earlier this year. The release moves Omnigent from stateless per-action inspection toward policies that remember what has happened in the current session and change the permissioning envelope as context accumulates. The paper is signed by Matei Zaharia, David Nasi, Xiangrui Meng, Kecheng Cao and Tomu Hirata, which is unusually senior for a mid-year platform update and signals that Databricks is treating agent governance as a first-class layer of its AI stack rather than a demo policy set.

### 🔬 Details (Phân)
The concrete addition is that a policy is now allowed to keep and update arbitrary variables that are visible only to that policy for the lifetime of a session — tools used, documents opened, dollars spent, an accumulated risk score. On every subsequent tool call the policy sees not just the pending action but the running tally, so restrictions can tighten monotonically rather than being decided in isolation. Four built-in policies ship in the release: a Google Drive policy that implements a Bell-LaPadula "no write-down" model after a confidential file is read, a risk-score policy that escalates from silent approval to user confirmation as sensitive material accumulates, a cost policy that pauses at a soft cap and blocks expensive model calls at a hard cap, and an intent-based authorisation policy that locks tool access to the tool set inferred from the user's opening request.

The framing worth reading closely is the Lethal Trifecta section. Omnigent argues that prompt injection is only dangerous when an agent simultaneously has access to untrusted content, sensitive data, and an external channel, and that a contextual policy can break the trifecta by refusing the third leg once the first two have already occurred in the same session. Because Omnigent is a meta-harness — the same policies apply to Claude Code, Codex and any custom agent built on the OpenAI or Anthropic SDKs — the effect is that a team can standardise agent guardrails once and enforce them across whichever runtime individual users pick. The GitHub repo is at github.com/omnigent-ai/omnigent, with policy documentation at omnigent.ai/docs/policies/overview.

### 🎯 Takeaway (Hợp)
If you already run more than one agent framework in production, treat this as the moment to move guardrails out of framework-specific configs and into an Omnigent policy layer, starting with the intent-based authorisation and cost policies as low-risk wins. Đọc kỹ phần Lethal Trifecta trước khi cho phép các agent tự do đọc file sensitive rồi mới gọi tool ngoài — đó là cái contextual policy thực sự chặn được.

### 💡 Example
```python
# Sketch of a custom contextual policy that escalates approval as risk grows.
class RiskScorePolicy(Policy):
    def init_state(self):
        return {"risk": 0}

    def on_tool_call(self, action, session):
        if action.tool == "read_file" and "confidential" in action.args["path"]:
            session["risk"] += 5
        if action.tool.startswith("http.") and session["risk"] >= 5:
            return Decision.REQUIRE_USER_CONFIRMATION
        if session["risk"] >= 15:
            return Decision.BLOCK
        return Decision.ALLOW
```

## 2. ClickHouse Puts chDB Inside AWS Lambda MicroVMs as the Agent's Local Data Engine

### 🔭 Overview (Tổng)
ClickHouse published a joint post with AWS on 07/07/2026, written by Auxten Wang and AWS Solutions Architect Nakul Mishra, positioning chDB — the embedded build of ClickHouse — as the local data engine for agentic workloads. The release confirms chDB is the only data-infrastructure launch partner for the newly announced Lambda MicroVMs, and lays out an architecture in which each agent session gets a private chDB instance running in the same process, with 8-hour state retention and suspend/resume that stops billing during idle time. The interesting move for the DE audience is the pitch that agent memory should be a queryable database inside the process, not a longer prompt or a remote vector store.

### 🔬 Details (Phân)
The technical argument is grounded in a cost calculation that data teams should recognise. The authors quantify how instability compounds into token spend: a 2 percent tool-call error rate cascades through retries to roughly a 20 percent agent-level failure rate, and one documented case shows seven retries on a 14 KB-token prompt burning around 100,000 tokens. Removing the network hop by embedding the query engine turns those retries from paid LLM round-trips into local function calls. On the data-model side chDB is used as a single engine for structured tables, time-series and vector search with embeddings, and the memory tables are append-only MergeTree with a `version` and `is_deleted` column so an agent's belief history is preserved rather than overwritten.

The federation story is the reason a database engineer should care rather than skim it as an LLM piece. A single chDB SQL statement joins a Parquet file on S3, a Postgres row from RDS via the `postgresql()` table function and a lookup against a remote ClickHouse Cloud instance, which is a genuinely useful shape for enrichment queries that agents want to issue as one-shot calls. The Pandas-compatible API is called out as intentional, since agents already generate idiomatic Python well and can lean on familiar `sess.query(...)` patterns. The trade-off is that per-session chDB is not a shared cache and does not replace ClickHouse Cloud — it is a local execution layer, and cross-agent data still needs to land in the central warehouse or object storage.

### 🎯 Takeaway (Hợp)
If you are building agent workloads on Lambda, prototype the Lambda MicroVMs preview with chDB before you invest more in a hosted vector database — the token savings on retries alone can justify the switch. Keep the append-only MergeTree pattern for memory tables so you can audit an agent's belief evolution instead of only its final answer.

### 💡 Example
```python
import chdb
from chdb.session import Session

# Private per-agent memory that survives MicroVM suspend/resume.
sess = Session("/tmp/agent")
sess.query("""
CREATE TABLE IF NOT EXISTS memory (
    memory_id UUID,
    content   String,
    embedding Array(Float32),
    version   UInt64,
    is_deleted UInt8 DEFAULT 0,
    created_at DateTime64(3) DEFAULT now64()
) ENGINE = MergeTree ORDER BY (memory_id, version)
""")

# One statement, three sources - no remote query engine involved.
sess.query("""
SELECT u.tier, avg(t.amount), p.category
FROM s3('s3://lake/txn.parquet') AS t
JOIN postgresql('rds:5432','users','...') AS u USING (uid)
JOIN remote('clickhouse-cloud','products','...') AS p USING (sku)
GROUP BY u.tier, p.category
""")
```

### 🔭 Overview (Tổng)
The AWS Big Data Blog announced on 07/07/2026 that Glue interactive sessions now speak Apache Spark Connect natively, closing a long-standing gap for teams that wanted to develop against Glue clusters from a local IDE without a custom kernel. The feature ships in Glue 5.1 built on Spark 3.5.6-amzn-1 and works with any PySpark 3.5.6-compatible client, meaning VS Code, PyCharm and JupyterLab can now attach to serverless Glue as a remote runtime. For platform teams that have kept a hybrid of Glue notebooks plus separate local development environments, this is the first vendor-supported way to collapse both into one workflow.

### 🔬 Details (Phân)
Spark Connect is the decoupling API introduced in Spark 3.4 that lets a lightweight client speak to a remote driver via gRPC, but the AWS integration is the piece that has been missing on the managed side. The new Glue support handles the awkward parts explicitly: a helper for background token refresh handles the 30-minute credential expiry that used to break long-running local sessions, the Spark Live UI grows a dedicated Connect tab so operators can see which local session owns which job, and JDBC connections to Redshift, Aurora and DocumentDB are wired through so joins across those sources work from a laptop. The pricing model stays serverless DPU-per-second, so idle IDE time does not accrue charges.

The context is that SageMaker Unified Studio already ships with Glue interactive sessions, but external IDE users had to write custom Jupyter kernels or use `%%glue` magic in notebooks — both of which broke source control, testing and profiler tooling. Spark Connect turns Glue into just another remote Spark endpoint that a normal `SparkSession.builder.remote(...)` call resolves against, which is what most competing offerings from Databricks Connect and EMR Serverless have supported for a year. The trade-off worth flagging is that Spark Connect still does not expose the full RDD API, so any Glue job that leans on low-level RDD operations or custom `mapPartitions` code cannot yet be run through the new endpoint and has to stay on the notebook or job runner path.

### 🎯 Takeaway (Hợp)
If your team already tolerates running Spark jobs in Glue notebooks, move the day-to-day dev loop to a local IDE with Spark Connect this sprint and keep the notebook only for exploratory shared work. Verify your existing jobs use DataFrame or SQL APIs before you migrate — RDD-heavy pipelines will still need the classic Glue job runner until Spark Connect closes that gap.

### 💡 Example
```python
# Attach a local VS Code or PyCharm session to Glue 5.1 via Spark Connect.
from pyspark.sql import SparkSession
import boto3, os

session = boto3.Session()
glue = session.client("glue")
conn = glue.get_dataframe_connection(
    RoleArn=os.environ["GLUE_ROLE_ARN"],
    GlueVersion="5.1",
    NumberOfWorkers=5,
    WorkerType="G.1X",
)

spark = SparkSession.builder.remote(conn["ConnectionString"]).getOrCreate()
spark.sql("SHOW DATABASES").show()
spark.read.parquet("s3://lake/gold/orders/").filter("day = current_date()").count()
```

### 🔭 Overview (Tổng)
CNX Software covered on 07/07/2026 Mercedes-Benz's release of the Automotive Rapid DEvelopment Platform, published on Mercedes-Benz's own GitHub under Apache 2.0. ARDEP V2 is a small STM32-based development board with matching power-IO shields, built in partnership with Frickly Systems and actively used inside Mercedes-Benz's FlexCAR Rolling Chassis research vehicle. For the automotive-adjacent embedded audience the release matters less for the board itself and more because a Tier-1 OEM is willing to open-source a Zephyr-based reference platform, including hardware files, firmware and diagnostic stacks.

### 🔬 Details (Phân)
The V2 main board is built around an STMicroelectronics STM32G474VE, an Arm Cortex-M4F running up to 170 MHz with 128 KB SRAM and 256 KB of flash. On-board connectivity leans hard on automotive networking: two CAN-FD transceivers and one LIN transceiver, plus USB-C for host tooling and Arduino-compatible headers for custom carriers. The PowerIO shield adds six high-side driver outputs rated 3 A continuous per channel, six digital inputs tolerant to 48 V, and per-channel diagnostics with LED fault indication — the shape you need for prototyping body controllers and low-voltage actuator interfaces without a full BCM stack. Firmware is built on Zephyr RTOS with UDS (Unified Diagnostic Services) support and DFU capability over both CAN and USB.

The positioning is the interesting piece. Automotive engineers have long relied on paid AURIX or Renesas evaluation boards and closed-source diagnostic stacks; ARDEP puts the same class of features — CAN-FD, LIN, UDS, DFU — on a Cortex-M4 that costs a few dollars and ships with schematic and layout files in both KiCad and Altium formats. Because Mercedes-Benz is running ARDEP inside FlexCAR rather than as a marketing artefact, the firmware is likely to keep pace with real-world development rather than bit-rot after launch. A Crowd Supply crowdfunding campaign is in preparation but there is no price yet, and the licensing choice — Apache 2.0 for both hardware design and firmware — is unusually permissive for automotive-grade IP.

### 🎯 Takeaway (Hợp)

The trade-offs are the ones you would expect: a single-core 240 MHz RISC-V is not going to run heavy LVGL animations at 60 FPS, and the ES8311 is a competent audio codec rather than a high-fidelity one.
