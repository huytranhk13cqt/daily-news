### 🔭 Overview (Tổng)
Luke Gannon published on 10/07/2026 the ClickHouse ADBC driver 0.1.0, a Rust implementation of the Arrow Database Connectivity standard that keeps query results in Apache Arrow columnar format from the server through to the caller. The driver is the first mainstream columnar database implementation of ADBC targeting general analytics clients rather than a single ecosystem plug-in, and it drops directly into Python, Ruby, R, Go, Java, JavaScript and C. For teams that have been paying the row-to-Arrow conversion tax when pulling ClickHouse results into pandas, Polars or dbt Fusion, the release removes an entire staging step from the data path.

### 🔬 Details (Phân)
The concrete design decisions matter for adoption. The driver is written in Rust and compiles natively for each supported language, connects over ClickHouse's HTTP interface with TLS enabled by default, and understands a `clickhouse://` URI scheme for automatic detection. It supports both ClickHouse Cloud and self-hosted deployments and covers columnar query execution returning Arrow record batches, streaming inserts that accept Arrow data without a SQL statement, plus connection pooling and statement management. The Ruby entry point installs through the shared columnar-tech installer and the `red-adbc` gem, and the same underlying binary backs the other language bindings.

The strategic reading is where the release lands in the wider stack. ADBC was designed to replace ODBC and JDBC for analytics and AI workloads, and the ClickHouse driver is a signal that a large columnar vendor now considers Arrow the wire format, not just an in-memory layout. That change matters immediately for dbt Fusion, dbt Labs' Rust query execution engine, which drove much of the priority work on this driver and gets seamless integration without an interpreter round trip. It also matters for anyone who has watched JDBC turn a warm 200 ms ClickHouse query into a two-second pandas DataFrame because of the row-oriented staging step.

The roadmap is honest about gaps. Schema and catalog discovery still requires side channels, bulk ingest cannot yet auto-create tables, and JSON column serialisation is waiting on the upstream Arrow spec to standardise. Language-specific analytics recipes are also promised but not yet published, which is worth calling out because the driver's value depends on downstream libraries handling the Arrow batches idiomatically rather than converting back to rows.

### 🎯 Takeaway (Hợp)
If you are running a Python or dbt pipeline against ClickHouse and profiling shows time spent in the result-decode path rather than in the query itself, swap the driver to ADBC and measure the tail. The gain scales with row count and column width, so wide analytical result sets will feel it more than small dashboards.

### 💡 Example
```python
import adbc_driver_manager as adbc
import pyarrow as pa

conn = adbc.connect(
    driver="clickhouse",
    db_kwargs={"uri": "clickhouse://default:@localhost:8443/default"},
)
with conn.cursor() as cur:
    cur.execute("SELECT event_type, count() AS n FROM events GROUP BY event_type")
    table = cur.fetch_arrow_table()

df = table.to_pandas(zero_copy_only=True)
print(df.head())

with conn.cursor() as cur:
    ingest = pa.table({"event_type": ["click"], "n": [1]})
    cur.adbc_ingest("events_hourly", ingest, mode="append")
```

### 🔭 Overview (Tổng)
Databricks announced on 10/07/2026 the general availability shape of Feature Views, a Unity Catalog object that lets a team define a machine-learning feature once and consume the same definition for historical training tables and online inference lookups. The primitive is the platform's latest attempt to erase training/serving skew — the class of bug where a model performs well on backtests and mispredicts in production because the online feature was computed differently. For any organisation running MLflow-tracked models against Lakebase or Model Serving, this is the object type that finally makes feature reuse a governed operation rather than a copy-paste convention.

### 🔬 Details (Phân)
The concrete plumbing is worth reading. Feature Views take a single feature definition, generate the historical training data automatically for experimentation, and can be materialised into managed pipelines via a `materialize_features()` call. Streaming sources are first class: RollingWindow aggregates are declared inline and Databricks quotes an end-to-end p99 of about 200 ms from an incoming event to online availability, driven by Spark Realtime Mode and Lakebase as the streaming-optimised online store. Every Feature View lives inside Unity Catalog with lineage, access controls and standard governance, and MLflow tracks feature dependencies alongside model versions so a model registered against a given Feature View resolves back to the same definition at inference time.

The competitive framing is where the release sits in the market. Feast, Tecton and AWS SageMaker Feature Store have all shipped variants of the "define once, serve twice" pattern; the differentiator here is that the definition is a first-class Unity Catalog object rather than a side-catalog owned by the ML platform, so access, audit and lineage flow through the same policy layer as tables and volumes. The Genie Code prompt path lowers the entry cost — data scientists can bootstrap Feature Views from natural language in a notebook — but the underlying object model is still declarative code, which keeps CI/CD workflows familiar. Adoption cost is the caveat: teams already invested in an external feature store need a migration plan, and Feature Views are pinned to Databricks-managed infrastructure rather than a portable spec.

### 🎯 Takeaway (Hợp)
If your fraud, personalisation or churn model has drifted from its offline evaluation, port one feature to a Feature View this sprint and compare the online p99 against your current pipeline. Fifty-line YAML feature stores kept in a side repo are the first thing worth retiring.

### 💡 Example
```python
from databricks.feature_engineering import feature_view, RollingWindow

@feature_view(
    catalog="prod",
    schema="ml_features",
    online_store="lakebase.customer_online",
    tags={"team": "risk"},
)
def customer_txn_features(txn):
    return txn.select(
        "customer_id",
        RollingWindow("5 minutes").sum("amount").alias("amt_sum_5m"),
        RollingWindow("1 hour").count().alias("txn_cnt_1h"),
    )

customer_txn_features.materialize_features(
    backfill_start="2026-06-01",
    trigger="continuous",
)
```

### 🔭 Overview (Tổng)
Cloudflare shipped on 10/07/2026 Smart Tiered Cache for Public Cloud Regions, an upgrade that lets the CDN pick a sensible upper-tier point of presence when the origin sits behind anycast IPs on AWS, GCP, Azure or Oracle Cloud. The problem it solves is a familiar one for engineers who publish data-lake extracts, model artifacts or streaming manifests to an object store — the CDN cannot tell which cloud region actually holds the object, and misrouted upper tiers introduce hundreds of milliseconds of cross-continent latency that shows up in dashboards as unexplained tail spikes. This release closes that gap for the four major clouds.

### 🔬 Details (Phân)
The mechanism is a multi-layered map. Cloudflare refreshes cloud provider IP-range files every few hours to associate subnets with regions, then continuously probes latency to keep a database of upper-tier candidates fresh on a fifteen-minute cadence. A weighted vote across the subnets in a region picks the primary upper tier and a fallback, and where probe data is thin the nearest Tier 1 point of presence acts as the default. The customer-facing surface is a region hint that can be set from the dashboard under Caching, from the API, or from Terraform, so the change fits both click-ops and infrastructure-as-code environments. The four clouds ship on day one, with additional providers on the roadmap.

The impact reading matters most for teams distributing large or hot files. A dataset artifact hosted on an S3 bucket in ap-southeast-2 was previously at risk of being pulled through a US or European upper tier because the anycast address gave no regional hint; with the update, the upper tier can now be pinned to APAC. For engineers running an analytics dashboard behind a CDN, or shipping model weights and feature exports to edge locations, that is a straight cache-hit-ratio improvement without any origin work. The trade-off is subtle: relying on Cloudflare's IP-to-region map means new cloud regions or renumbered ranges may lag until the next refresh cycle, so anyone on the bleeding edge of cloud availability zones should validate before assuming coverage.

### 🎯 Takeaway (Hợp)
If you serve data-plane assets from a public-cloud object store behind Cloudflare, flip on the region hint next week and watch the origin egress counters. Any drop in origin bytes translates directly to lower cloud egress cost, which is usually the biggest line item in this pattern.

### 💡 Example
```hcl
resource "cloudflare_ruleset" "smart_tiered_cache_hint" {
  zone_id = var.zone_id
  name    = "Public cloud origin region hint"
  kind    = "zone"
  phase   = "http_config_settings"

  rules {
    expression  = "http.host eq \"assets.example.com\""
    description = "Pin AWS ap-southeast-2 upper tier"
    action      = "set_config"
    action_parameters {
      cache = true
      origin_cache_control = true
      smart_tiered_cache_public_cloud = {
        provider = "aws"
        region   = "ap-southeast-2"
      }
    }
  }
}
```

The board sells for 6.50 USD in its bare form and 7.95 USD as a DIP variant with headers pre-soldered, which places a Matter-capable microcontroller near the price point of a plain ESP32-C3. For anyone building a small Matter-native accessory or a mesh sensor node, this is the smallest module on the market that combines the newer 5 GHz Wi-Fi 6 path with a Thread radio.

### 🔬 Details (Phân)
The technical envelope is tuned for compact designs. The ESP32-C5HF4 runs a RISC-V high-frequency core at up to 240 MHz with a low-power core at 48 MHz, backed by 384 KB SRAM, 320 KB ROM and 4 MB SPI flash. Wireless coverage spans dual-band 802.11ax Wi-Fi 6 on 2.4 and 5 GHz, Bluetooth 5.0 LE with Mesh, and 802.15.4 for Zigbee, Thread and Matter, terminated on an IPEX antenna connector rather than an on-module chip antenna. Nineteen GPIO are exposed — eleven on standard 2.54 mm castellated headers and eight more on a 12-pin FPC connector — and USB Type-C handles power and programming. Power management supports both 5 V USB and a 3.7 V lithium battery through the SGM40567 charging controller, with a 13 µA deep-sleep number that is usable for a coin-cell-adjacent sensor.

Competitively the Stamp-C5 sits between the XIAO ESP32-C5 at 21 x 17.8 mm and NiceMCU's Mini at 27.9 x 17.8 mm; the differentiator is the FPC connector that adds eight extra GPIO without growing the footprint. That matters because the biggest complaint with earlier ESP32-C series modules has been that Matter-plus-Wi-Fi-6 comes at the cost of pin count, forcing designers to add an expander for even simple sensor rigs. Espressif's own ESP-Matter SDK covers the software path, so the module drops into Home Assistant or Apple Home projects that already track the ESP32-C series.

### 🔭 Overview (Tổng)
Benjamin Cabé released on 10/07/2026 Zephyr Podcast episode #043, which walks through a batch of in-flight changes that between them broaden Zephyr's architecture coverage and move it closer to POSIX-style application portability. The two headline items are a proposed device filesystem giving `/dev`-style access to drivers and initial RISC-V support for two new boards — the CDAC THEJAS32 processor developed in India and the WCH CH32V103EVT evaluation board. For teams evaluating Zephyr against FreeRTOS or NuttX for a next-generation firmware, this is the episode that maps how the upstream tree is shaping up for the next release train.

### 🔬 Details (Phân)
The technical substance is thicker than a normal podcast summary suggests. The proposed device filesystem exposes device nodes under a `/dev`-like tree so applications can open a driver by path with POSIX semantics, which is the missing piece that keeps existing Linux-native code from moving to Zephyr without a wrapper layer. New hardware support includes the Microchip SmartFusion2 FPGA-plus-SoC, AMD Zynq UltraScale+ MPSoC, Radxa ROCK 3B and Adafruit's TRRS Trinkey. On the wireless side, a substantial Bouffalo Lab BL61x Wi-Fi driver lands, and initial DWC2 USB host controller support arrives with ESP32-specific handling. Storage gets eMMC HS400 enhanced strobe support, and audio gains an I2S shell that can generate tones for testing. Twister, the in-tree test runner, now supports per-platform compiler selection and a per-test coverage matrix dashboard that maps tests to the source lines they exercise.

The strategic reading is that Zephyr is picking up two trends at once. RISC-V is broadening from the well-known SiFive and Espressif variants to national-level and low-cost commercial silicon like THEJAS32 and CH32V103, which pushes Zephyr into more procurement conversations in cost-sensitive markets. The POSIX-style device layer aligns with the Arduino Core-zephyr effort and with LF Edge projects that want a Linux-shaped API surface on a real RTOS. The trade-off is churn: multiple subsystems changing at once means integrators tracking mainline should expect API drift between releases and should plan for one focused rebase per subsystem before the next LTS.

### 🎯 Takeaway (Hợp)
If your firmware roadmap depends on Zephyr, watch the device-filesystem RFC and pilot it on a non-shipping board before it lands in stable; portability wins now can save a wrapper crate later. RISC-V teams working with CDAC or WCH silicon can move procurement discussions forward on the strength of the mainline patches rather than waiting for the next release notes.
