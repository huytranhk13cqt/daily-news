## 1. Confluent Tableflow Goes GA on Both Iceberg and Delta Lake, Cutting the Kafka-to-Lakehouse ETL Layer

### 🔭 Overview (Tổng)
Mohtasham Sayeed Mohiuddin published on 10/07/2026 the general availability announcement for Confluent Tableflow with both Apache Iceberg and Delta Lake as first-class output formats. Tableflow is the managed Confluent Cloud path that "continuously converts Kafka topics into open table formats so analytics engines can query streaming data as tables — without writing or maintaining ETL pipelines." For any team that has been maintaining a Kafka Connect sink into S3 plus a Spark or Flink job to compact Parquet and register Iceberg manifests, this is the release that lets the entire pipeline collapse into a checkbox on the topic.

### 🔬 Details (Phân)
The plumbing sequence is worth walking through because it defines the boundary of what Tableflow owns and what stays with the caller. Tableflow consumes committed Kafka segments through the Kora storage layer, converts records into Parquet files sized for analytics, generates Iceberg or Delta Lake metadata, and publishes the table through either a built-in Iceberg REST catalog, AWS Glue or Unity Catalog. Schema Registry stays the source of truth for schema mapping and evolution, so nullable columns, integer-to-long widening and decimal precision growth flow through automatically without a Tableflow-specific mapping file. Downstream, the same table can be queried from Snowflake, Databricks, AWS Athena, Amazon Redshift, Trino or BigQuery, which covers the majority of an average lakehouse footprint.

The competitive framing sits at two levels. Against writing your own sink, Tableflow removes the Iceberg commit coordination, the manifest compaction and the small-file cleanup that most in-house pipelines under-invest in until they hit a query-plan explosion. Against alternatives like Redpanda's own Iceberg output or the streaming Iceberg writers in Kafka Connect, Tableflow's differentiator is the two-format GA and the managed catalog: a topic can now materialise into both an Iceberg table and a Delta Lake table in parallel, which matters for shops that run analytics on Databricks Runtime and inference on Snowflake off the same data. The trade-off is scope. Tableflow is opinionated about Parquet as the storage layer, so use cases that need row-level Iceberg branching, custom partition specs or hand-tuned Bloom filters still belong in an application-managed writer.

### 🎯 Takeaway (Hợp)
If you run a Kafka-to-lakehouse pipeline where the raw topic and the analytics table are effectively the same shape, spend an afternoon this week wiring a non-production topic through Tableflow and comparing the resulting Iceberg or Delta table against your current sink output. The compaction and catalog registration overhead is the piece that reads first on operational cost.

### 💡 Example
```yaml
apiVersion: cluster.confluent.io/v1
kind: TableflowIntegration
metadata:
  name: orders-iceberg
spec:
  cluster: prod-lakehouse
  source_topic: orders.raw
  formats:
    - iceberg
    - delta
  catalog:
    type: rest
    uri: https://tableflow.confluent.cloud/iceberg
  storage:
    bucket: s3://lakehouse-prod/orders
    partition_by:
      - source: event_time
        transform: hour
  schema_registry:
    subject: orders-value
    evolution: forward_compatible
```

## 2. Confluent Ships a Queues for Apache Kafka Guide That Puts Share Consumers on the Documented Path

| 🏷️ Topic | Tutorial |

### 🔭 Overview (Tổng)
Jonathan Lacefield published on 10/07/2026 the first in-depth Getting Started guide to Queues for Apache Kafka, the queue-semantics mode that shipped in Confluent Cloud on 3 March 2026 and in Confluent Platform 8.2. The feature is KIP-932's landing in a supported form: a share group and a matching KafkaShareConsumer API that let more consumers work a single partition than the classic 1:1 consumer group model allows. The article is worth reading not because the release is new but because it is the first walkthrough that documents the acquisition lock lifecycle, delivery-attempt semantics and Java-client migration path in one place.

### 🔬 Details (Phân)
The technical model is a break from the twenty-year-old Kafka consumer contract. Instead of the broker assigning partitions to consumers and letting the client track offsets, the broker acquires records under a time-limited lock — thirty seconds by default — and hands them to a share group member. The member then acknowledges, releases, rejects or renews the record individually, which is closer to SQS or RabbitMQ semantics than to a Kafka consumer group. Delivery-attempt counts are tracked per record with a configurable maximum, currently five, and both implicit and explicit acknowledgement modes are supported so existing Java code paths can migrate incrementally.

The trade-off matrix is the piece the article makes concrete. Share groups scale beyond partition count, which fixes the "we have three consumers but the partition is stuck" pattern that pushed teams toward Pulsar or SQS. In exchange, they cost the strict per-key ordering guarantee that classic consumer groups provide, so anything driven by a Kafka key that must land in order — for example, a per-user event stream — should stay on the classic consumer. Confluent Cloud enables share groups on Enterprise and Dedicated clusters, Confluent Platform is on version 8.2, and non-Java clients are still on the H2 2026 roadmap, which is the calendar item most engineering teams will need to track before committing to a queue-shaped design.

### 🎯 Takeaway (Hợp)
If a queue-shaped workload has been misfitted onto a Kafka consumer group in your stack — for example, a task pool where you added partitions just to raise consumer count — port one non-critical workload to a share group this sprint and benchmark tail latency under load. The main risk is the ordering assumption; audit downstream handlers first.

### 💡 Example
```java
import org.apache.kafka.clients.consumer.KafkaShareConsumer;
import org.apache.kafka.clients.consumer.ShareAcknowledgeType;

Properties props = new Properties();
props.put("bootstrap.servers", "kafka:9092");
props.put("group.id", "billing-task-share");
props.put("group.protocol", "share");
props.put("share.acknowledgement.mode", "explicit");
props.put("share.max.delivery.attempts", "5");

try (KafkaShareConsumer<String, String> consumer =
        new KafkaShareConsumer<>(props)) {
    consumer.subscribe(List.of("billing.tasks"));
    while (running) {
        var records = consumer.poll(Duration.ofSeconds(1));
        for (var record : records) {
            try {
                process(record.value());
                consumer.acknowledge(record, ShareAcknowledgeType.ACCEPT);
            } catch (TransientException e) {
                consumer.acknowledge(record, ShareAcknowledgeType.RELEASE);
            }
        }
    }
}
```

## 3. Evan Hahn Makes the Case for STRICT Tables in SQLite as a Default, Not an Option

| Field | Value |
|---|---|
| 📅 Date | 11/07/2026 |
| 🏷️ Topic | Coding |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `sqlite` · `strict-tables` · `type-safety` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
Evan Hahn published on 11/07/2026 a walk-through arguing that new SQLite databases should be built with STRICT tables enabled from the first CREATE. STRICT tables were added in SQLite 3.37.0 back in November 2021, but the flag has stayed off by default because it breaks the loose type affinity that SQLite is famous for. The essay's contribution is a concrete demonstration of what the flag catches, when the trade-offs actually bite, and how to migrate an existing schema without downtime, which is the missing piece that has kept the feature underused for four years.

### 🔬 Details (Phân)
The mechanical difference is precise. A non-strict SQLite column typed as INTEGER will silently accept the string `'garbage'`, storing it as text; a STRICT column raises `cannot store TEXT value in INTEGER column`. Numeric coercion where lossless — `'123'` into an INTEGER column — still succeeds, so the mode is not brittle for common ORM patterns. The allowed column types are also narrowed to INT, INTEGER, REAL, TEXT, BLOB and ANY, which means schemas that leaned on `DATETIME`, `JSON` or `UUID` as documentation-only type hints have to move to TEXT plus a CHECK constraint or a generated column. The `ANY` type is the safety valve when a column really does need to hold heterogeneous data.

The essay is honest about the sharp edges. There is no ALTER TABLE path to add STRICT to an existing table, so migration is the classic CREATE new / INSERT SELECT / DROP old / RENAME dance that has to be scripted carefully in busy databases. Older SQLite libraries — anything before 3.37 — cannot open a database that contains a STRICT table, which matters for embedded shipping products with a long tail of installed clients. The author reports that STRICT mode's runtime overhead is not measurable in his benchmarks, so the argument reduces to migration cost versus the class of bugs the flag catches at INSERT time rather than at read time three days later.

### 🎯 Takeaway (Hợp)
For any new SQLite-backed service — an application cache, an embedded device store, a CLI database — write `CREATE TABLE ... STRICT` from day one; the migration overhead only exists if you defer the decision. For an existing production database, schedule the CREATE/INSERT/DROP/RENAME migration behind a feature flag and validate reads before flipping traffic.

### 💡 Example
```sql
CREATE TABLE people_strict (
    id     INTEGER PRIMARY KEY,
    name   TEXT    NOT NULL,
    age    INTEGER NOT NULL CHECK (age >= 0),
    joined TEXT    NOT NULL CHECK (joined LIKE '____-__-__T__:__:__%')
) STRICT;

INSERT INTO people_strict (name, age, joined)
VALUES ('Ada', 36, '2026-07-11T09:00:00Z');

-- Rejected at INSERT time in STRICT mode:
INSERT INTO people_strict (name, age, joined)
VALUES ('Bob', 'thirty', '2026-07-11T09:00:00Z');
-- Error: cannot store TEXT value in INTEGER column
```

### 🔭 Overview (Tổng)
CNX Software reported on 11/07/2026 that BrisbaneSilicon has opened Crowd Supply pledges for the ELM11-Feather, a Gowin GW1NR-9-based FPGA development board shaped to the Adafruit Feather footprint at a 39 USD pledge tier including two 24-pin headers and a USB-C cable. The board's differentiator is not the FPGA fabric alone but the EmbluaOS firmware, which runs a PicoRV32 softcore at up to 75 MHz and lets a developer flash and execute Lua scripts directly against GPIO, PWM, UART, SPI and I2C without cross-compiling C. For embedded engineers who want the freedom of a real FPGA on a Feather-sized board and the iteration speed of a scripting REPL on the same silicon, this is the first commercial module that ships both in one flow.

### 🔬 Details (Phân)
The fabric budget defines the ceiling of what the board can do. The Gowin GW1NR-LV9 exposes 8,640 LUTs and 6,480 flip-flops backed by 17,280 bits of shadow SRAM and 486 Kbit of block SRAM, plus 64 Mbit of PSRAM and 608 Kbit of user flash on the module. That is enough for a soft PicoRV32 with a working memory map, a small custom peripheral bus and a handful of protocol engines, but not for stacking a full Cortex-A-class softcore alongside anything else. Up to 276 user I/O are theoretically available on the GW1NR die; the board exposes headers with 16 and 11 pins for GPIO, PWM, UART, SPI and I2C, deliberately omitting analog pins to keep the Feather footprint. Power is USB-C or LiPo with a 500 mA charger and a 500 mA 3.3 V regulator, and a hardware watchdog plus five status LEDs round out the debug surface. The Arvore IDE assists with Gowin-side project development while EmbluaOS handles the Lua REPL and flash storage, so a developer can iterate at scripting speed and drop into SystemVerilog only when a peripheral needs it.

The niche this fills is worth calling out because it is narrow but underserved. The QuickFeather and Fomu boards demonstrated Feather-form FPGAs before, but both required a full open-source toolchain rebuild for each iteration and offered no runtime script layer; a first-project developer typically stalled at the Yosys or Symbiflow build step. The ELM11-Feather trades some fabric size for a productised out-of-box path, which puts it directly against the Sipeed Tang Nano series and Machdyne's Lichee Tang boards. The Feather footprint is the practical differentiator because it drops into the existing Adafruit FeatherWing accessory ecosystem for battery management, LoRa and displays without redesigning a carrier board. Delivery is targeted for November 2026, which sets the practical adoption window at four months out.

### 🎯 Takeaway (Hợp)
If a project has been stuck between a full FPGA breakout that a Lua-first developer will not touch and an ESP32 that cannot generate the custom clocked bus the peripheral needs, back an ELM11-Feather and use the four-month lead time to design a FeatherWing carrier for the analog and RF pieces. The Lua REPL is the pedagogical hook that gets non-HDL engineers writing peripheral code without leaving the board.

### 💡 Example
```lua
-- EmbluaOS Lua script running on the PicoRV32 softcore
-- Toggle a status LED and read an I2C sensor every second.
local led  = gpio.pin(15)
local i2c  = i2c.open(0, {sda = 6, scl = 7, hz = 400000})
local BME  = 0x77

led:mode("output")

while true do
    led:write(1)
    i2c:write(BME, {0xF4, 0x25}) -- oneshot measure
    local raw = i2c:read(BME, 0xFA, 3)
    local adc = (raw[1] << 12) | (raw[2] << 4) | (raw[3] >> 4)
    print(string.format("temp raw = %d", adc))
    led:write(0)
    time.sleep_ms(1000)
end
```
