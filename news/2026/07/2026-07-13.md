## 1. Apache Polaris 1.6 Ships Security Hardening, Live-Migration Register-Table Overwrite and Ordered Event Listeners

| Field | Value |
|---|---|
| 📅 Date | 10/07/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `apache-polaris` · `iceberg-rest-catalog` · `live-migration` |
| ⚡ Impact | High |

### 🔭 Overview (Tổng)
Danica Fine and EJ Wang published on 10/07/2026 the release notes for Apache Polaris 1.6, the open-source Iceberg REST catalog that Snowflake donated to the ASF in 2024. The 1.6 release is not a marquee feature drop; it is the version that closes off enough security, migration and event-pipeline gaps to let large data platforms treat Polaris as a first-class multi-tenant governance layer rather than a demo. For any team currently running Polaris behind AWS Glue or Databricks Unity as a compatibility catalog, this is the first release where the JWT handling, the register-table endpoint and the event listener contract are all production-grade in a single hop.

### 🔬 Details (Phân)
The security hardening is the most visible change. JWT tokens must now carry the expected `polaris` issuer or Polaris rejects them, closing the token-confusion path where a JWT minted for a peer service could be replayed against the catalog. Access tokens are redacted from authentication logs, so a shipping-off-logs pipeline no longer leaks bearer material into observability storage. AWS STS role-session names became configurable through the `SESSION_NAME_FIELDS_IN_SUBSCOPED_CREDENTIAL` feature flag, letting operators compose CloudTrail session identifiers from realm, catalog and principal fields for downstream audit correlation. Entity-name validation now rejects the ASCII control range plus `\:*?"<>|#+`, which prevents catalog schema names that would break shell tooling or path handlers.

The live-migration story is the second half of the release. The register-table endpoint now accepts `overwrite=true` semantics so that a metadata pointer can be atomically swapped without dropping and recreating the table, preserving grants, policies and downstream references. A new `REGISTER_TABLE_OVERWRITE` authorization operation is separately gate-keepable, so the destructive path can be granted to migration tooling without opening general write access. Views received the same registration parity as tables, closing the last gap that forced view migrations through hand-rolled CREATE OR REPLACE. Event listeners moved to dedicated thread pools with ordered per-listener delivery, decoupled from the request lifecycle, and event persistence now sanitises credentials, tokens and PII at the pipeline level before any listener sees them.

The ecosystem updates matter for integration planning. Apache Spark 4.0 is now a top-level client target, the Python client picks up 3.14 support, the CLI ships a REPL mode, and Azure SAS token issuance honours the operator-configured duration instead of the previous hardcoded one-hour limit. Kubernetes deployments gained rootless container support and a dedicated maintenance-pod pattern, which is the change that lets a Polaris cluster be rolled through a maintenance window without exposing the request pods to schema-repair traffic.

### 🎯 Takeaway (Hợp)
If you have a Polaris deployment carrying non-trivial Iceberg tables, plan the 1.6 upgrade in the next sprint and let the register-table overwrite path handle the next metadata migration you were going to do out-of-band. For a new deployment starting today, wire `SESSION_NAME_FIELDS_IN_SUBSCOPED_CREDENTIAL` into your realm/catalog/principal template from day one so CloudTrail entries carry the identifiers you need at incident time.

### 💡 Example
```yaml
polaris:
  authentication:
    jwt:
      required_issuer: "polaris"
      redact_bearer_in_logs: true
  aws_sts:
    session_name_fields_in_subscoped_credential:
      - realm
      - catalog
      - principal
  event_listeners:
    executor:
      core_size: 8
      queue_capacity: 4096
    ordered_delivery: true
    sanitize_before_dispatch:
      - credentials
      - tokens
      - pii
```

## 2. Snowflake Introduces Per-Account Hostnames to Isolate App Services, Streamlit and Container Services URLs

| Field | Value |
|---|---|
| 📅 Date | 10/07/2026 |

| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
Chhaya Pandey and Steven Rhodes published on 10/07/2026 the general availability of per-account hostnames for Snowflake App Services, which covers Streamlit apps, Notebooks and Snowpark Container Services. Previously an App Services URL was either a subdomain of a single global `snowflake.app` namespace or scoped to a whole region, which meant a firewall wildcard, a Content Security Policy header or a private-link DNS rule that trusted the domain trusted every account in that region. The new URL pattern moves each account into its own hostname compartment, which is the piece that lets an enterprise put a per-account rule in front of Snowflake-hosted apps without opening the region.

### 🔬 Details (Phân)
The URL pattern is now `<app-id>.<orgname>-<accountname>.<region>.<cloud>.snowflake.app`, which puts the org and account name in the second label from the right and makes wildcard rules bind at the account level. The certificate story matches the URL story: Snowflake now issues per-account certificates with wildcard SANs limited to the leftmost DNS label, so an app deployed under an account gets a name whose TLS chain does not overlap with sibling accounts. The migration is opt-in and gated on two SQL calls per account. First, an operator invokes `SYSTEM$ISSUE_PER_ACCOUNT_APP_SERVICE_CERTIFICATE()` to trigger certificate issuance; then setting the account parameter `ENABLE_PER_ACCOUNT_APP_SERVICE_URL = TRUE` swaps the URL generator over. PrivateLink customers follow the same steps but flip `ENABLE_PER_ACCOUNT_APP_SERVICE_PRIVATELINK_URL` for the internal endpoint.

The security envelope this closes has been raised by regulated customers for two years. With region-scoped hostnames, a compromised Streamlit app in one account could serve HTTP responses under a domain that another account's browser session had already trusted, which put pressure on cookies with Domain= scopes and on any redirect flow that trusted the origin. Per-account hostnames also cleanly enable firewall wildcards like `*.acme-prod.ap-southeast-2.aws.snowflake.app`, which is what most enterprise egress reviews had been blocked on. Availability is broad — every region except US Gov West 1 and China (Ningxia) — and the feature is off by default, so a team can turn it on account by account without a fleetwide flag day.

### 🎯 Takeaway (Hợp)
If your Snowflake footprint has more than one account or you host Streamlit or Container Services under firewall or CSP rules, enable per-account URLs on your staging account this week and audit the wildcard rules and browser cookies that used to trust the global domain. The migration is per-account and reversible, so this is a low-risk change to sequence ahead of any Native App or Snowpark Container Services production launch.

### 💡 Example
```sql
-- Run in each account, using ACCOUNTADMIN
USE ROLE ACCOUNTADMIN;

CALL SYSTEM$ISSUE_PER_ACCOUNT_APP_SERVICE_CERTIFICATE();

ALTER ACCOUNT SET ENABLE_PER_ACCOUNT_APP_SERVICE_URL = TRUE;

-- Optional: private endpoint
ALTER ACCOUNT SET ENABLE_PER_ACCOUNT_APP_SERVICE_PRIVATELINK_URL = TRUE;

-- New URL pattern:
-- https://<app-id>.acme-prod.ap-southeast-2.aws.snowflake.app
```

### 🔭 Overview (Tổng)
Karolina Ruiz Rogelj and Melvyn Peignon published on 10/07/2026 the announcement that ClickHouse now ships as a Docker Hardened Image under Docker's DHI programme, distributed from `dhi.io/clickhouse-server`. The problem the release targets is familiar to anyone deploying open-source databases through an enterprise security review: the standard `clickhouse/clickhouse-server` image sits on Ubuntu 22.04, and any modern scanner flags the base layer's Perl, wget, apt and their transitive dependencies as medium-severity findings even though those tools are dormant in a running container. The DHI variant strips the toolchain that raises the flags without changing how the daemon starts.

### 🔬 Details (Phân)
The published Docker Scout numbers give the actual delta. The standard image reports eight medium and eleven low severity findings across 111 packages; the hardened image reports zero medium and fourteen low, with the remaining low-severity issues confined to core libraries like glibc and OpenSSL where no upstream fix exists across distributions yet. The hardened image runs as a non-root user by default, omits the package manager, and carries SLSA Level 3 provenance so a downstream signer can verify the build lineage cryptographically. The docker-run invocation is intentionally identical apart from the registry: `docker run -d --ulimit nofile=262144:262144 -e CLICKHOUSE_PASSWORD=... dhi.io/clickhouse-server:26.2-debian13`. Docker's team, not ClickHouse, maintains the base and pushes CVE patches, which means the SLA on future advisories now sits with Docker's security programme rather than with the ClickHouse release cadence.

The developer-experience gap that hardened images normally introduce is closed with two pieces. A `dev` variant that carries the usual debugging tools is published on the same tag family, so a team that wants a shell in the container for reproducing a support case has a direct swap. Separately, `docker debug dhi.io/clickhouse-server:26.2-debian13` attaches a full toolset ephemerally without rebuilding the image, which keeps the shipped artefact minimal while giving on-call access to strace, gdb and clickhouse-client on demand. Against alternative hardening paths — distroless base images, Chainguard's variants, or hand-rolled multi-stage builds — the DHI approach differentiates by keeping the operator-facing command identical, which is the piece that decides whether a rollout has to touch every downstream Helm chart or CI pipeline.

### 🎯 Takeaway (Hợp)
If your ClickHouse deployment has an open enterprise security ticket citing base-image findings, swap the registry to `dhi.io/clickhouse-server:<version>-debian13` on a staging cluster this week and let Docker Scout close the finding on its own scan. The command-surface parity means the pull-request diff is one line in your compose or Helm values, so the change is easy to sequence ahead of a broader base-image programme.

### 💡 Example
```bash
# Standard image (unchanged, for comparison)
docker run -d --ulimit nofile=262144:262144 \
  clickhouse/clickhouse-server

# Hardened image
docker run -d --ulimit nofile=262144:262144 \
  -e CLICKHOUSE_PASSWORD=mysecretpassword \
  dhi.io/clickhouse-server:26.2-debian13

# Verify the CVE delta yourself
docker scout quickview clickhouse/clickhouse-server:latest
docker scout quickview dhi.io/clickhouse-server:26.2-debian13

# Attach a full toolset to the hardened container without rebuilding
docker debug dhi.io/clickhouse-server:26.2-debian13
```

### 🔭 Overview (Tổng)
The PoWA team published on 12/07/2026 the release of powa-archivist 5.2.0, the core sampling extension for the PostgreSQL Workload Analyzer. PoWA is the multi-instance performance-monitoring stack most commonly used to run pg_stat_statements aggregation, waits sampling, hypopg-driven index recommendations and per-query historical charts against a fleet of PostgreSQL clusters. The 5.2.0 release is the version that qualifies the archivist against the upcoming PostgreSQL 19 major, which is the piece any team already running PoWA needs to sequence before their PG19 upgrade window.

### 🔬 Details (Phân)
The headline change is PostgreSQL 19 support in the archivist extension, which is the sampler that runs inside the monitored database and pushes metric snapshots to the dedicated PoWA repository database. PG19 introduces two new statistics views — `pg_stat_recovery`, which exposes standby-side replay and lag metrics, and `pg_stat_lock`, which surfaces per-lock contention with waiter identities — and the 5.2.0 archivist wires both into its scheduled sampler so the PoWA UI can render them alongside pg_stat_statements without a custom collector. This is the same integration pattern the archivist has used since 4.x for pg_qualstats and pg_stat_kcache, so the operational surface for the PoWA repository schema does not change; only the source-side sampling widens.

The dependency chain around the release is worth reading. The archivist is one of three moving parts — archivist inside each monitored instance, the powa-collector daemon that pulls samples on a schedule, and the powa-web UI that renders the aggregated storage — and mismatched versions across those three have been the most common upgrade regression in the last two majors. The 5.2.0 release notes do not flag breaking schema changes, so an in-place update against an existing PoWA repository is the expected path, but the collector and web components need to be pulled to their matching 5.2.x tags before PostgreSQL 19 is introduced into the monitored fleet, otherwise the two new statistics views will not surface. For teams currently on PostgreSQL 17 or 18 without an immediate PG19 upgrade in sight, the practical impact is modest: no new features against older majors are called out in the announcement.

### 🎯 Takeaway (Hợp)
If PoWA is in the monitoring path for your PostgreSQL fleet and PG19 sits in your upgrade backlog for H2 2026, bump the archivist to 5.2.0 and align the collector and web versions before you touch a single production instance. For a fleet already stable on PG17 or PG18, this is a low-priority cadence upgrade you can defer to the next quarterly patch window.

### 💡 Example
```sql
-- On each monitored PostgreSQL 19 instance
ALTER EXTENSION powa UPDATE TO '5.2.0';

-- Confirm the new PG19 views are visible to the sampler
SELECT relname
  FROM pg_class
 WHERE relname IN ('pg_stat_recovery', 'pg_stat_lock');

-- Sanity-check the archivist snapshot job
SELECT srvid, snapts, aggts, snap_status
  FROM powa_snapshot_metas
 ORDER BY snapts DESC
 LIMIT 5;
```

### 🔭 Overview (Tổng)
Jean-Luc Aufranc published on 12/07/2026 the second part of the Beelink EQi review, which is the first published field test of Intel's Wildcat Lake platform in a consumer mini PC. Wildcat Lake is the successor to the N-series Twin Lake parts and is aimed at the same low-TDP fanless-adjacent form factor, so the numbers in this review are the first data point most edge-computing and thin-client buyers have on what the platform actually delivers before they commit a fleet purchase. For IoT and industrial teams that use N100 or N150 mini PCs as gateway hardware, this piece is the read on whether Wildcat Lake earns a place on the next refresh cycle.

### 🔬 Details (Phân)
The processor under test is the Intel Core 3 304, a 15 W hybrid part with one performance core and four efficiency cores, base clock 1.50 GHz, boost 4.3 GHz. Graphics is a single-Xe-core iGPU running at up to 2.3 GHz and the SoC embeds an Intel AI Boost NPU rated at 15 TOPS, which is the differentiator the N-series parts do not carry. The review unit ships with 16 GB LPDDR5-6400 soldered plus 512 GB UFS 3.1 storage and two M.2 slots. On single-thread Cinebench R23 the part scores 1,732 points against the N100's roughly 918, a ~89 percent uplift; multi-thread reaches 4,863. PCMark 10 lands at 5,294, ahead of the N100 at 3,150 but still behind an AMD Ryzen 5 7530U reference at 5,586, which is the practical ceiling in this price band.

The infrastructure numbers are the part most gateway and edge deployments will care about. The 10 GbE port hits 9.41 Gbps bidirectional line-rate under iperf3, the 2.5 GbE port carries 2.35 Gbps and Wi-Fi 6E measures 1.77 Gbps down, so the board holds up as a small NAS front end or as an inline network probe. Idle draw sits at 5.7 to 7.2 watts depending on link activity, sustained Cinebench holds at 19.5 watts, and peak CPU temperature under stress is 86 °C without thermal throttling, which is within the envelope a fanless enclosure could target with a modest heat spreader. The caveat is a Thunderbolt 4 issue: the ports refuse to negotiate a PCIe link for an eGPU while DisplayPort alt-mode continues to drive a triple-display configuration, which points at a controller firmware or driver bug rather than a silicon problem. Pricing is 509 USD pre-order, 609 USD MSRP.

### 🎯 Takeaway (Hợp)
If your edge or gateway fleet is on N100 or N150 hardware and the workload is CPU-bound or NPU-adjacent, put a single Wildcat Lake unit on the bench and run your inference or packet-inspection load against it — the single-thread gain and the 15 TOPS NPU move the platform out of "N-series plus" territory. Hold off on any Thunderbolt-attached expansion plan until Beelink or Intel publishes a driver update that resolves the PCIe negotiation regression.
