### 🔭 Overview (Tổng)
Nick Joung, Ian Ackerman and Julia Powell published on 10/07/2026 the Public Preview announcement of Feature Views, the Databricks managed framework for defining an ML feature once and using it for both historical training and production inference. The pitch is aimed at the operational gap that most existing feature stores leave open: teams end up building one path for offline features in Spark, a second path for streaming features in Structured Streaming or Flink, a third path for online lookup during serving, and then hand-write a fourth path to keep the three in sync. Feature Views collapses those four paths into a single declared object under Unity Catalog governance, which is the piece that lets a fraud or recommendation team drop the self-managed streaming and online store infrastructure they were previously carrying.

### 🔬 Details (Phân)
The developer surface is the Feature Engineering Client SDK plus a single API call. A data scientist declares a feature locally in a notebook and calls `materialize_features()`, which registers the feature in Unity Catalog and triggers a Databricks-managed pipeline that handles backfilling, stream feature expiration and stale-row removal on its own. The materialization orchestrates two existing GA products under the hood: Lakebase as the streaming-optimised online store that minimises write amplification, and RTM as the runtime layer that keeps offline and online representations aligned. Rolling-window aggregations run at millisecond resolution through Spark Realtime Mode, which processes each event and updates the aggregate incrementally instead of recomputing the window per query. The announcement puts end-to-end p99 latency at 200 ms from event ingestion to online availability, which is the number a fraud-detection team needs to see before it will move a sub-second signal off a hand-rolled Kafka+Redis pipeline.

The governance envelope is what differentiates the release from a client-side feature store library. Feature Views become first-class Unity Catalog objects with discovery, access control and full lineage; MLflow records the feature dependencies alongside the model artefact; and Model Serving performs the online feature lookup automatically at inference time, so the serving path does not have to be re-implemented per project. The Skyscanner customer quote in the post frames the practical effect as "our data scientists go faster and focus on what drives traveler value, not how to compute it," which matches the pattern of moving feature glue code from application repositories into the platform. The main caveat is scope: streaming materialization requires an Enterprise-tier workspace in a Lakebase-supporting region, so the on-ramp for the Standard tier is the batch-only path until Lakebase widens its regional footprint. Public Preview also means the SDK, API surface and Unity Catalog object model are still allowed to shift, so downstream automation should pin SDK versions.

### 🎯 Takeaway (Hợp)
If your team is running a feature store on Databricks that carries a separate streaming pipeline into a self-managed online store, spin up a Feature View in a dev workspace this sprint and let `materialize_features()` produce the same feature you already hand-wire — the parity check is a one-notebook effort, and it tells you how much bespoke glue code you can retire. Hold off on rewriting production feature pipelines until GA if you need stable APIs or if your primary region does not yet carry Lakebase.

### 💡 Example
```python
from databricks.feature_engineering import FeatureEngineeringClient, RollingWindow

fe = FeatureEngineeringClient()

@fe.feature(
    source_table="prod.transactions.stream",
    online_store="lakebase",
    ttl="30d",
)
def transactions_last_5m(txn):
    return (
        RollingWindow(window="5 minutes")
        .over("account_id")
        .agg(
            txn_count=("txn_id", "count"),
            spend_sum=("amount", "sum"),
        )
    )

# One call registers the feature in Unity Catalog,
# starts the managed streaming pipeline, and wires
# the online lookup for Model Serving.
fe.materialize_features(
    view="ml.risk.transactions_last_5m",
    trigger="continuous",
)
```

### 🔭 Overview (Tổng)
Luke Gannon published on 10/07/2026 the ClickHouse ADBC driver 0.1.0, developed in partnership with Columnar and distributed through the ADBC Driver Foundry. ADBC — Arrow Database Connectivity — is the Apache Arrow project's contemporary answer to the ODBC and JDBC standards that anchored the row-oriented world. The problem it targets is the shape mismatch at the driver boundary: ClickHouse stores and processes data in columns, but a JDBC or ODBC client forces the server to materialise rows before shipping, and the client then reconstructs columns in Arrow or pandas after landing. The new driver removes that double-conversion by keeping the entire wire format in Apache Arrow from server to application.

### 🔬 Details (Phân)
The 0.1.0 release ships as an ADBC driver with matching language bindings: Ruby via the `red-adbc` gem, R via the standard ADBC R packages, Python for pandas and Polars users, and additional bindings in C, Go, Java and JavaScript. The install path is unified through a new package-manager surface: `dbc install clickhouse` fetches the driver into any of the supported ecosystems, and Ruby usage is a two-line quick-start that connects, ingests via an Arrow RecordBatch and reads results back without ever touching a row-oriented buffer. The BI and modelling reach matters as much as the language spread; the driver is called out as compatible with dbt Fusion, Microsoft Power BI and other ADBC-aware tools, which is the tier of coverage that lets an analytics team drop the ODBC dependency on a Windows-only reporting host and standardise on a single columnar transport for both notebooks and dashboards.

The positioning against ODBC and JDBC is worth reading carefully for planning. The blog frames ADBC as bringing the same driver-boundary standardisation that ODBC and JDBC established for rows into the columnar world; in practice that means the driver-side connection, prepared-statement and cursor primitives are the same as an ADBC driver for DuckDB, Snowflake or BigQuery, so a client that already speaks ADBC does not need per-database code paths. The release does not publish throughput numbers, and the ClickHouse server-version floor is not called out explicitly, so a production evaluation still needs a benchmark run and a compatibility check against your current server tag before displacing an ODBC hop. Version numbering — 0.1.0 — is an honest signal that API stability and edge-case behaviour are not yet at the level of the mature JDBC path.

### 🎯 Takeaway (Hợp)
If your team runs pandas, Polars or R notebooks against ClickHouse and is watching a chunk of ingest time disappear into row→column conversion, install `red-adbc` or the Python ADBC bindings on a bench box this week, wire the ClickHouse ADBC driver via `dbc install clickhouse`, and measure the transport time on a representative query. Hold off on retiring your ODBC dependency until you have benchmarked a real workload and validated the driver against the ClickHouse version you actually run in production.

### 💡 Example
```python
# pip install adbc_driver_manager adbc_driver_clickhouse
import adbc_driver_clickhouse.dbapi as clickhouse
import pyarrow as pa

with clickhouse.connect(
    host="clickhouse.example.internal",
    port=9440,
    user="analytics",
    password="…",
    secure=True,
) as conn:
    with conn.cursor() as cur:
        cur.execute(
            "SELECT toDate(ts) AS d, count() AS c "
            "FROM events WHERE ts >= today() - 7 GROUP BY d ORDER BY d"
        )
        # Arrives as an Arrow table – no row→column round-trip.
        table: pa.Table = cur.fetch_arrow_table()

df = table.to_pandas(types_mapper=pa.ArrowDtype)
print(df.head())
```

### 🔬 Details (Phân)

The development kit ships with microphones, an accelerometer, a gas sensor, a camera connector, a Bluetooth module, serial flash and a JTAG/USB-UART debug bridge, which is the shape of dev kit a hardware engineer expects when the target application is a condition-monitoring or health-wearable proof of concept. ### 🔭 Overview (Tổng)
Debashis Das published on 13/07/2026 the first coverage of Brechel Electronic's BE-IIS-HPP-T1S and BE-IIS-HPP-T1L, two Raspberry Pi HAT+ boards that add 10 Mbit/s Single-Pair Ethernet (SPE) over a twisted-pair segment. SPE is the wiring standard the automotive and industrial-automation worlds have been standardising on since IEEE 802.3cg (10BASE-T1S, multi-drop) and 802.3cu (10BASE-T1L, long-reach): a single twisted pair carries both data and, for T1L, Power over Data Line, replacing the four-pair CAT5e cabling that most factory-floor rewires still expect. The Brechel boards are aimed squarely at the evaluation, prototyping and educational bench where a Raspberry Pi is the cheapest reasonable host for a real SPE endpoint.

### 🔬 Details (Phân)
The two boards differ where the standards themselves differ. The T1S variant is built around a Microchip LAN8651 PHY and runs a shared-bus multi-drop topology with up to eight nodes per segment and a run length of up to 25 metres, which is the topology field crews already deploy for sensor and actuator loops. The T1L variant uses the Analog Devices ADIN1110 PHY, runs point-to-point over long-reach cabling and carries transformer isolation rated 2,250 V DC for 60 seconds, which is the rating a control-panel install needs. Both boards land as HAT+ form-factor cards at 65 mm × 56 mm, draw roughly 35 mA at 5 V or 9 mA at 3.3 V, and — importantly for a bench that already stacks a display, a camera or a UPS — support stacking up to five distinct HATs without SPI or GPIO conflicts through the BE-IIS HAT++ ecosystem. Compatible hosts are Raspberry Pi 2, 3, 4, 5, Zero and Zero 2W for T1S, with T1L dropping the Pi 2 and Pi Zero variants where the extra current headroom is needed.

Availability and pricing come with two useful details. The T1S board sells at 95.54 EUR (~US$115) and the T1L at 113.07 EUR (~US$135), both through DigiKey and Brechel's own Tindie storefront, shipping from Germany. For teams that need to run 10BASE-T1S or T1L traffic into an existing Raspberry Pi–hosted Linux stack, the practical impact is that the interface appears as a standard eth1 to the kernel after loading the vendor driver, so wiring an SPE endpoint into an existing MQTT, OPC UA or Modbus TCP flow is a matter of routing rather than a full protocol translator. Against alternatives — hand-rolled STM32-based SPE bridges, or industrial PoE gateways — the HAT+ approach differentiates on cost per bench and on the fact that the Pi already carries a Python and Node-RED toolchain.

### 🎯 Takeaway (Hợp)
If your team is prototyping an industrial gateway that has to speak 10BASE-T1S or T1L to a downstream sensor loop, order both boards on Tindie or DigiKey and stand up a two-Pi bench where one carries T1L against a long-reach cable pull and the other terminates a shared T1S bus. Do this before you commit to the more expensive STM32 or Renesas-based reference designs — the HAT+ pair is fast enough to confirm your protocol stack works end-to-end and cheap enough to leave running as a permanent lab node.

### 🔬 Details (Phân)
The hardware bill of materials is a Pi 4 Model B (2 GB) inside a 92 × 68.3 × 57.5 mm metal enclosure at 630 g, mated with the RAK6421 HAT+ that carries four sensor slots (A, B, C, D) and two IO slots, wired to a RAK13300 LoRa module in the standard SKU or a RAK13302 HP module in the higher-power variant. Pricing is US$169.99 for the standard SKU on AliExpress and US$175.99 for the HP model on the RAKwireless store, and the reviewer's caveats are that the enclosure has no water-resistance rating and that the SD card image is closer to a Meshtastic install than to a turnkey NMS.
