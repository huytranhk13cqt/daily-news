## 1. dbt-core 1.12.0rc3 Virtualizes Macros to Cut Parse-Time Memory and Fixes Overloaded UDF DAG Resolution

### 🔭 Overview (Tổng)
The dbt Labs release automation cut the third release candidate for dbt-core 1.12.0 on 14/07/2026 at 22:48 UTC. rc3 is a short changelog — one feature, one fix, and one under-the-hood change — but the under-the-hood entry is the one that matters for anyone running a project large enough that `dbt parse` has become a wall-clock hurdle. The pull request titled "virtualize macros" restructures how the manifest holds macro definitions, replacing eager materialisation with a lazy view over both `flat_graph` and `WritableManifest` so the parse phase and the macro-generation step touch less resident memory. The release also lands the CLI-hints work started in rc1 and rc2 and closes a DAG-resolution bug that had been folding overloaded user-defined functions into the wrong dependency edge.

### 🔬 Details (Phân)
The concrete changes come from three merged pull requests. #15524, by @ash2shukla and @peterallenwebb, is the macro virtualization: `flat_graph` and `WritableManifest` now expose lazy views over the underlying node collection, so the interpreter does not build a full materialised copy of the graph or the writable manifest just to answer a "give me all macros" query — the memory and CPU that used to go into that build are the numbers rc3 is chasing. #15501, by @aahel, fixes a real correctness bug: when a project defined multiple overloads of the same user-defined function and one overload was absorbed into another node, the absorbed dependency was dropped from the DAG. That is the class of bug that only appears on projects with adapter-specific UDFs (Snowflake, BigQuery, Databricks) and it produces confusing "model built without dependency X" runtime failures rather than a clean error. #15510, by @ash2shukla, adds context-aware hints to the CLI so that when a user runs an ambiguous command dbt now emits a targeted "did you mean" style suggestion based on usage patterns.

The rc3 tag comes ten days after rc1 (07/07/2026) and five days after rc2 (09/07/2026), so the cadence points at a GA candidate in the next window rather than a rewrite. rc2 was the release that flipped the 1.9-era and 1.10-era flags to default true, which is the breaking change users need to plan around before jumping from 1.11.x to 1.12.0 — rc3 does not touch that surface. There are no adapter-side changes in the notes, so provider adapters (dbt-snowflake, dbt-bigquery, dbt-databricks) do not need to move in lockstep. Automation that pins dbt-core should still avoid `>=1.12.0` until GA lands because the parse-time behaviour change may perturb custom parse-time hooks that read the pre-virtualization manifest structure directly.

### 🎯 Takeaway (Hợp)
If your project spends more than a few seconds in `dbt parse` on a warm cache, pull rc3 into a scratch environment (`pip install 'dbt-core==1.12.0rc3'`) and rerun `dbt parse --profiles-dir …` with the same manifest to measure the memory and time delta before GA. Teams that lean on overloaded UDFs — Snowflake secure UDFs, BigQuery persistent UDFs, Databricks Python UDFs — should also rerun a `dbt build --select +<affected_model>+` on rc3 and diff the DAG against 1.11.x to confirm the #15501 fix restores any dependency they were relying on.

## 2. Databricks Promotes Trigger.AvailableNow for OpenSharing Streaming to GA on Runtime 18.0

| Field | Value |
|---|---|
| 📅 Date | 14/07/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `delta-sharing` · `structured-streaming` · `trigger-availablenow` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
The Databricks July 2026 release notes announced on 14/07/2026 that `Trigger.AvailableNow` is now Generally Available for OpenSharing streaming reads. OpenSharing — the open-source Delta Sharing implementation that Databricks and non-Databricks recipients use to read shared tables — previously accepted only the `Trigger.Once` and `Trigger.ProcessingTime` triggers on Structured Streaming reads, both of which have specific limitations that made large-backlog ingestion awkward. The GA promotion closes that gap: recipients can now read a shared table with the same "process everything available, honour `maxFilesPerTrigger`, then stop" semantics that native Delta already provides.

### 🔬 Details (Phân)
The concrete change is a trigger-mode addition on the `deltaSharing` streaming source. `Trigger.AvailableNow` captures the provider's table version at stream start, then processes the entire backlog as multiple micro-batches — each honouring `maxFilesPerTrigger` — and terminates automatically when the captured version is exhausted. That is a materially different contract from `Trigger.Once`, which is officially deprecated and processed the whole backlog as a single micro-batch regardless of file count, and from `Trigger.ProcessingTime`, which runs continuously without a natural stopping point. The version-awareness matters because the provider table can advance mid-stream; `AvailableNow` explicitly does not chase those new versions, so the recipient gets a deterministic "catch up to this snapshot" job that a scheduler can drive on a cron cadence. The minimum runtime is Databricks Runtime 18.0 for `responseFormat=delta`; older runtimes silently fall back to the pre-existing trigger behaviour.

Ecosystem positioning is worth flagging. The OpenSharing streaming path is the on-ramp for recipients that consume shared tables from a Databricks or Unity Catalog provider — Snowflake Reader accounts, BigQuery external tables and self-hosted Spark clusters increasingly consume Delta Sharing feeds this way. Prior to this GA, teams driving nightly ingest jobs into an external warehouse had to choose between the deprecated `Once` trigger (which risked OOM on wide fact tables) and rewriting the job as a batch read that lost the CDF-style change tracking. `AvailableNow` restores parity with a native Delta streaming read and unblocks the pattern of scheduled backfills that fold cleanly into an Airflow or Databricks Workflows DAG. The trade-off is the Runtime 18.0 floor: recipient clusters still on 17.x get no error, just the pre-existing behaviour, so an inventory pass on recipient runtime versions is the first step before rolling this out to production.

### 🎯 Takeaway (Hợp)
If your team ingests a Delta Sharing feed on a schedule and has been carrying `Trigger.Once` as a temporary workaround, plan a bump to Runtime 18.0 on the recipient side and switch the trigger to `AvailableNow` — the migration is a single option change on the `readStream`, and the payoff is the removal of a deprecated trigger from your pipeline. Non-Databricks recipients should confirm their Spark deployment ships the matching delta-sharing client build before flipping.

### 💡 Example
```scala
import org.apache.spark.sql.streaming.Trigger

val query = spark.readStream
  .format("deltaSharing")
  .option("startingVersion", 0)
  .option("ignoreChanges", true)
  .option("maxFilesPerTrigger", 10)
  .table("vaccine.vaccine_us.vaccine_us_distribution")
  .writeStream
  .format("delta")
  .option("checkpointLocation", "/mnt/checkpoints/vaccine_us")
  .trigger(Trigger.AvailableNow)          // GA on DBR 18.0+
  .toTable("bronze.vaccine_us_distribution")

query.awaitTermination()
```

### 🔭 Overview (Tổng)
Eva Donaldson, Senior Technical Account Manager at AWS, published on 14/07/2026 a walkthrough of an automated regression-test framework for Amazon Redshift patch and maintenance events. Redshift patches — the periodic maintenance windows the service triggers to roll the cluster software forward — are a recurring source of subtle regressions for teams that layer BI tools, dbt models and application drivers on top of a provisioned cluster: the cluster is technically up, but a specific `pg_catalog` view has changed shape, or a JDBC prepared-statement path throws where it used to succeed. The post ships a CloudFormation template that wires EventBridge to a Fargate task that runs a scripted test suite on the freshly patched cluster and posts results to S3 and SNS, so the team is told about the regression before end users are.

### 🔬 Details (Phân)
The architecture is a linear event chain. EventBridge subscribes to Redshift cluster event notifications; when a patch, reboot or modification event fires, an AWS Lambda function pulls credentials from AWS Secrets Manager and invokes a Fargate task on an ECS cluster. The Fargate container — pushed to Amazon ECR — executes four validation phases against the patched cluster: JDBC driver tests that exercise the `DatabaseMetaData` API and connection lifecycle, ODBC driver tests that call `SQLTables` and `SQLColumns`, a battery of approximately 35 catalog SQL queries against `pg_catalog`, `information_schema` and the `svv_*` system views, and a set of custom performance-benchmark queries compared to a stored baseline. Results land in S3 and an SNS topic notifies the on-call channel; the Fargate task then terminates so the framework carries no idle cost between patches. Deployment is a single `aws cloudformation deploy` call against the supplied `template.yaml` with parameters for the target cluster and the notification topic.

The scope is deliberately narrow. The framework runs against provisioned Redshift only — Redshift Serverless is not mentioned in the post, and Serverless does not emit the same maintenance-window event stream, so a Serverless-first team will need to adapt the EventBridge rule if they want equivalent coverage. The Fargate container needs a VPC with private subnets and a NAT gateway to reach the cluster and pull the ECR image, which is an infrastructure prerequisite worth planning for a landing zone. Secrets Manager holds the cluster credentials the tests use, so the deployment carries a rotation obligation. The benchmark phase is only as good as the stored baseline queries — the post ships a scaffold rather than a workload-specific benchmark suite, so teams should treat the 35-query catalog block as the ready-to-run piece and the performance benchmarks as a template to populate with their own SLA-relevant queries.

### 🎯 Takeaway (Hợp)
If your Redshift patch cadence has ever produced a "why did the dashboard break overnight" incident, deploy the CloudFormation stack into a non-production account this week, populate the benchmark queries with the 5–10 queries your dashboards depend on, and let the next natural patch event trigger the suite end-to-end so you learn about the notification and S3 report pathways before you need them in production. Teams running Redshift Serverless should treat this as a design reference rather than a drop-in template and rewrite the EventBridge rule against Serverless's own event surface.

### 💡 Example
```bash
# Deploy the framework against a target provisioned Redshift cluster.
aws cloudformation deploy \
  --template-file template.yaml \
  --stack-name redshift-patch-testing \
  --capabilities CAPABILITY_NAMED_IAM \
  --parameter-overrides \
      ClusterIdentifier=analytics-prod \
      SecretsManagerArn=arn:aws:secretsmanager:ap-southeast-2:…:secret:redshift/analytics-prod \
      NotificationTopicArn=arn:aws:sns:ap-southeast-2:…:oncall-redshift \
      VpcId=vpc-0abc… \
      PrivateSubnetIds=subnet-0def…,subnet-0ghi…

# The EventBridge rule is now live. Trigger a rebuild-index maintenance
# action to smoke-test the pipeline before waiting for the next patch.
aws redshift reboot-cluster --cluster-identifier analytics-prod
```

### 🔭 Overview (Tổng)
Jean-Luc Aufranc published on 14/07/2026 the first coverage of Forgix, a 36 × 18 mm development board that pairs a Raspberry Pi RP2354B microcontroller with an Efinix Trion T8F49 FPGA in the Teensy 4.0 pin footprint. The MCU-plus-FPGA form factor is a small niche — prior boards in the space are Pico-Ice (RP2040 + Lattice ICE40) and Shrike-lite (RP2040 + Renesas ForgeFPGA) — but the niche matters for embedded teams that need cycle-accurate custom logic sitting next to a firmware CPU without stepping up to a full Zynq or PolarFire SoC. Forgix is the first board in this category to pair the RP2354B, which brings both Arm and RISC-V cores, with an Efinix Trion part, which uses a proprietary quantum-cell fabric rather than the more familiar LUT4/LUT6 architectures.

### 🔬 Details (Phân)
The RP2354B on Forgix is the dual-core variant of the Pi Foundation's second-generation microcontroller: dual Arm Cortex-M33 at 150 MHz plus dual Hazard3 RISC-V at 150 MHz, 520 KB SRAM, 2 MB stacked flash. The Efinix Trion T8F49 sits alongside in a BGA-49 package measuring 3 × 3 mm and contributes 7,384 logic elements, 8 embedded multipliers and 122.88 kbit of internal RAM. External memory is a 16 Mbit QSPI PSRAM. Power comes in on USB Type-C at 5 V and is stepped down to 3.3 V I/O and 1.1 V for the FPGA core. The pin fan-out routes both castellated and through-hole pins to either the MCU or the FPGA, which is what makes the board a genuine drop-in for existing Teensy 4.0 breakouts rather than a lookalike that requires a custom carrier. On the debug side, a Tag-Connect TC2030 pad exposes SWD to the RP2354B, and the FPGA is loaded via a Bitstream loader running as a host-side Python script over USB.

Software support is pitched at hobbyist and prototype workflows rather than production tooling. The vendor released the KiCad hardware design files, PDF schematics, the RP2354 C firmware and the host-side Python bitstream loader through a Bitbucket repository; Control Paths, the same team behind other Efinix hobbyist boards, provides supplementary tooling documentation. Efinix's own Efinity IDE — the toolchain that produces a .hex bitstream for the Trion — is the FPGA build path, and it is worth flagging that Efinity is a closed-source, licensed toolchain with a free hobbyist tier rather than a Yosys/nextpnr flow. Board availability is direct through the vendor storefront at forgix.tech for USD 50 plus shipping and taxes, so a small engineering evaluation lot is a straightforward purchase rather than a distributor negotiation.

### 🎯 Takeaway (Hợp)
If your embedded team has a workload that needs deterministic custom logic — a fast SPI slave that has to shift data on a specific clock edge, a real-time video line buffer, a protocol bridge with tight jitter budgets — but doesn't justify a Zynq or SmartFusion redesign, order two or three Forgix boards from forgix.tech and stand up a bench that runs the Efinity IDE against the T8F49 while the RP2354B carries the control plane. Budget time for the Efinity licensing step because it is not a Yosys workflow.

### 🔭 Overview (Tổng)
Jean-Luc Aufranc published on 14/07/2026 coverage of the IoTLabs wM-Bus Gateway, an ESP32-based receiver that bridges Wireless M-Bus utility-meter telemetry into Home Assistant through ESPHome. Wireless M-Bus is the European standard for utility metering that gas, water and electricity meters use to emit periodic short-range packets at 868 MHz — a protocol that has been present in the smart-metering rollout across the EU for a decade but that is still awkward to receive on the home-automation side. Most existing options are either bare RTL-SDR dongles paired with wmbusmeters on a Raspberry Pi, or expensive vendor-specific gateways. The IoTLabs device turns the receive side into a small ESPHome-managed appliance that appears natively in Home Assistant.

### 🔬 Details (Phân)
The hardware is a Semtech SX1276-based RFM95/RFM96 receiver on the 868 MHz band, driven by a dual-core ESP32 with the usual Wi-Fi and Bluetooth Low Energy radios integrated. A 1.3-inch OLED screen sits on the front for basic status, and the antenna path exposes an external SMA connector for the wM-Bus band plus the internal 2.4 GHz antenna for the ESP32 radios. Power is 5 V over microUSB. The device receives T1 and C1 wM-Bus frames — the two most common modes used by domestic gas and water meters — and is explicitly compatible with the wmbusmeters library, which is what makes it useful without needing to reverse-engineer a proprietary payload. The physical envelope is 70 × 36 × 15 mm, small enough to sit on a shelf inside the range of the meter cabinet.

The integration path is where the device differs from a raw SDR receive dongle. The stock firmware ships an ESPHome build, which means Home Assistant discovers the device as a native ESPHome node rather than through a bridging container, and the device can act simultaneously as a Bluetooth proxy for other BLE sensors on the same site. Configuration is a YAML file — the vendor publishes a `blueprint.yaml` on GitHub that a user can drop into an ESPHome dashboard, and outputs can be routed via MQTT, the ESPHome native API, REST endpoints or raw TCP/UDP sockets. The source code and binary firmware releases live at IoTLabs-pl/wM-Bus-Gateway, and a web-based flasher is available for the initial provisioning so a user does not need esptool locally. Availability is roughly USD 50 through Lectronz and Tindie storefronts, which puts the gateway squarely in the same price band as an RTL-SDR plus enclosure but with the software integration already done.

### 🎯 Takeaway (Hợp)
If your Home Assistant install currently reads utility usage from a manual meter photo or an on-meter LED pulse counter and you live in a jurisdiction where the meter is wM-Bus capable, order the IoTLabs gateway from Lectronz or Tindie and target a first read in an evening — the ESPHome integration removes the RTL-SDR-plus-wmbusmeters-container path that is otherwise the fastest way to reach the same data. Confirm your local meter uses T1 or C1 mode at 868 MHz before ordering, because meters that use only the S1 mode or the 169 MHz band will not decode on this hardware.
