### 🔭 Overview (Tổng)
The Apache Airflow project cut the first beta of a dedicated Java Task SDK on 13/07/2026 at 18:14 UTC under the tag `java-sdk/1.0.0-beta1`. This is a direct outgrowth of the experimental language-SDK work that shipped with Airflow 3.3.0 on 06/07/2026, and it marks the first time a non-Python runtime has been offered as a first-class citizen for authoring Airflow tasks. Historically the only supported path for Java or Kotlin logic in Airflow was to shell out through `BashOperator`, package the JVM code into a container and drive it through `KubernetesPodOperator`, or use adapter operators such as `SparkSubmitOperator`. The Task SDK model instead lets JVM code participate in the coordinator handshake directly, without a wrapper process.

### 🔬 Details (Phân)
The release is scoped narrowly: the tag lists "First release of the Apache Airflow Java SDK (beta)" and ships five downloadable assets on the GitHub release page. It composes with the coordinator layer that 3.3.0 introduced, so a JVM task talks to the same task-instance API surface that Python tasks use. The DAG-authoring layer remains Python; the Java SDK does not attempt to describe DAG topology in Java. What it does provide is a way to author the executable body of a task in Java, then reference that body from a Python DAG through the language-agnostic task interface that the 3.3.0 release exposed. The pairing matters because it separates orchestration (still in Python) from task implementation (now selectable per-task), which mirrors the way modern polyglot systems already run: schedulers in one language, business logic in whichever language the team owns.

Positioning against alternative execution paths, the Java SDK trades startup latency and packaging overhead against operational fit. A `KubernetesPodOperator` firing a JAR carries per-invocation container-start cost and a distinct log stream; a Java SDK task runs in a process the coordinator already knows about, so the log stream, retry policy, deferrable-task hooks and asset-partition mappings that 3.3.0 shipped apply without translation. The trade-off in the beta is that the API surface is not yet frozen — anything shipped as a `-beta1` under Apache versioning is explicitly subject to breaking change before GA, so integration into a production DAG should be scoped to a non-critical task with a short rollback plan. The parallel Go SDK track flagged as experimental in 3.3.0 has not cut its own beta yet, so JVM shops are ahead of Go shops on this on-ramp.

### 🎯 Takeaway (Hợp)
If your Airflow deployment currently runs Java or Kotlin logic through `KubernetesPodOperator` or a shell-out to `spark-submit`, pull down `java-sdk/1.0.0-beta1` into a scratch dev environment, port a single low-risk task and measure the reduction in per-task startup latency and log-stream friction. Do not port critical DAGs until the SDK moves out of beta because the `-beta1` tag makes no API-stability commitment.

## 2. AWS Publishes Reference Architecture for Apache Celeborn Remote Shuffle Service Bridging EMR on EKS and EMR on EC2

### 🔭 Overview (Tổng)
Suvojit Dasgupta, Avinash Desireddy, Melody Yang and Vishal Vyas published on 15/07/2026 a detailed reference architecture for deploying Apache Celeborn as a Remote Shuffle Service in front of Amazon EMR. Spark's default shuffle model ties intermediate shuffle data to the executor lifecycle: kill an executor — which happens routinely on Spot capacity or after dynamic allocation trims a stage — and its shuffle blocks disappear with it, forcing the stage to be recomputed. Celeborn is the open-source Apache project that decouples shuffle data from executor lifetime by pushing shuffle blocks to a dedicated worker tier, and this post is AWS's first published pattern for wiring Celeborn to both flavours of EMR from the same shuffle cluster.

### 🔬 Details (Phân)
The architecture places Celeborn on its own EKS cluster running the community Helm chart at image tag `0.6.2`, deployed with three master replicas holding a Raft quorum on gp3 EBS volumes and three or more worker replicas that pin four `hostPath` mounts to local NVMe (`/mnt/nvme/disk1-4`) for shuffle IO. The primary and dashboard ports (9097 RPC, 9098 UI) are exposed through an internal Network Load Balancer inside a shared VPC so that EMR on EKS jobs (submitted via `StartJobRun` or the Spark Operator) and EMR on EC2 jobs (submitted as EMR Steps) route to the same Celeborn masters. Job submissions carry the same Spark config block regardless of EMR flavour: `spark.shuffle.manager=org.apache.spark.shuffle.celeborn.SparkShuffleManager`, `spark.shuffle.service.enabled=false`, `spark.celeborn.master.endpoints=<NLB_DNS>:9097`. Four flags are called out as compulsory for EMR compatibility: `spark.celeborn.client.spark.push.unsafeRow.fastWrite.enabled=false`, `spark.dynamicAllocation.shuffleTracking.enabled=false`, `spark.sql.adaptive.localShuffleReader.enabled=false`, and `spark.celeborn.client.spark.shuffle.fallback.policy=NEVER`.

The operational story is Spot economics. Spark's built-in external shuffle service can preserve shuffle data across executor death only when the executor and the shuffle service share a node — which is why Spot interruptions have historically been the main reason teams keep shuffle-heavy Spark workloads on on-demand capacity. With Celeborn's push-based model and its `spark.celeborn.client.push.replicate.enabled=true` toggle, shuffle blocks live on the Celeborn worker tier with a single replica, so an executor can die on Spot interruption without losing its stage output — the post cites Spot as delivering "up to 90 percent" compute discount that the architecture aims to unlock. The trade-off is a second Kubernetes cluster to run and observe: the ADOT collector is wired to Amazon Managed Service for Prometheus for metrics, and Raft state on EBS carries a durability obligation. The post does not publish concrete latency or throughput numbers — treat this as a reference architecture rather than a benchmark, and plan a synthetic TPC-DS or workload-mirroring run on your own data before committing.

### 🎯 Takeaway (Hợp)
If your EMR Spark bill has a large shuffle component and you have avoided Spot for the shuffle-heavy stages, stand up the Celeborn EKS chart on a small three-master, three-worker footprint against a non-production EMR cluster this sprint and rerun a representative Spark job with the compulsory config block flipped on. Measure the recompute reduction under a scripted executor kill before proposing Spot migration for the shuffle-heavy stages. Non-AWS Spark deployments can lift the same architecture without change — the Celeborn side is vendor-agnostic.

### 💡 Example

  --virtual-cluster-id "${VIRTUAL_CLUSTER_ID}" \
  --name "tpcds-with-celeborn" \
  --release-label "emr-7.9.0-latest" \
  --job-driver "{
      \"sparkSubmitJobDriver\": {
          \"entryPoint\": \"s3://jobs/tpcds/query.py\",
          \"sparkSubmitParameters\": \"
              --conf spark.shuffle.manager=org.apache.spark.shuffle.celeborn.SparkShuffleManager
              --conf spark.shuffle.service.enabled=false
              --conf spark.celeborn.master.endpoints=${NLB_DNS}:9097
              --conf spark.celeborn.client.spark.push.unsafeRow.fastWrite.enabled=false
              --conf spark.dynamicAllocation.shuffleTracking.enabled=false
              --conf spark.sql.adaptive.localShuffleReader.enabled=false
              --conf spark.celeborn.client.spark.shuffle.fallback.policy=NEVER
              --conf spark.celeborn.client.push.replicate.enabled=true
          \"
      }
  }"
```

### 🔭 Overview (Tổng)
Avijit Goswami, Bill Tarr, Pratik Das and Srividya Parthasarathy published on 15/07/2026 a walkthrough of a new integration that lets Salesforce Data 360 (the platform formerly branded Data Cloud) read Apache Iceberg tables in Amazon S3 without copying data. The mechanism is the AWS Glue Data Catalog Iceberg REST endpoint, which speaks the standard Iceberg REST protocol so that any Iceberg-aware engine — Data 360's compute layer in this case — can enumerate namespaces, discover snapshots and fetch table metadata directly from Glue. Combined with AWS Lake Formation's credential-vending model for S3 file access, that is enough to serve queries from Data 360 straight against the S3 data files, sidestepping the ingest pipeline that would otherwise materialise a copy into the Data 360 storage tier.

### 🔬 Details (Phân)
The wiring has three moving parts. First, the Iceberg REST endpoint runs on Glue: it resolves an Iceberg table's current snapshot, schema and partition spec, and returns the S3 location the engine should read. Second, Lake Formation manages the access grant: a dedicated `data_cloud_user` IAM identity is granted `lakeformation:GetDataAccess` on the target resources, the `AWSGlueServiceRole` is attached, and the Lake Formation setting "Allow external engines to access data in Amazon S3 locations with full table access" is enabled — this is the toggle that unlocks the credential-vending path for non-AWS engines. Third, the Data 360 side connects with an AWS access key and secret access key mapped to that IAM identity. The post walks through creating the Iceberg table in Athena (`CREATE TABLE … LOCATION 's3://…/iceberg/churn' TBLPROPERTIES ('table_type'='iceberg', 'format'='PARQUET', 'write_compression'='ZSTD')`), populating it with 20 insert statements, then registering the S3 location with Lake Formation and issuing the Data 360 external file federation configuration.

The architectural claim is stronger than a typical "connector" integration. Zero-copy federation means the Iceberg table itself does not need to be replicated into Data 360; snapshot progression on the Iceberg side is visible to Data 360 at query time because the Glue REST endpoint returns the current metadata pointer on every read. That in turn means the CDC-style backfill jobs that used to sync AWS-side warehouses into Data 360 can be retired for the tables covered by this pattern — with the corresponding reduction in storage cost and in the reconciliation window between source-of-truth and derived warehouse. The caveats are jurisdictional and topological: the S3 location and the Glue catalog need to be in the same AWS account and region as the Lake Formation registration, and the network-egress cost of Data 360 reading S3 from a foreign region will show up on the bill if the query pattern is heavy. There is no minimum Data 360 version cited in the post — treat "recent" as the practical prerequisite.

### 🎯 Takeaway (Hợp)
If your organisation runs both an AWS data lake on Iceberg and Salesforce Data 360, and your Salesforce team currently receives an S3-to-Data-Cloud sync job for a subset of those tables, evaluate replacing that sync with the Glue Iceberg REST + Lake Formation federation for a single medium-size table this week. The success metric is straightforward: the sync job disappears from your Airflow or Step Functions DAG and Data 360 dashboards continue to reflect the same numbers as the Athena queries. Confirm Lake Formation's external-engine flag is on before granting the IAM permissions — the two changes need to land together.

## 4. Reverse-Engineered Rocket Driver Reaches Byte-Exact int8 Convolution on Rockchip RK3576 NPU

| Field | Value |
|---|---|
| 📅 Date | 15/07/2026 |
| 🏷️ Topic | Research |
| 🌐 Domain | IoT |
| 🔑 Keywords | `rockchip-rk3576` · `mainline-linux` · `npu-driver` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
Jean-Luc Aufranc published on 15/07/2026 a report on Ga Hing Woo (Jiaxing Hu) extending the mainline-Linux Rocket NPU driver — originally written by Tomeu Vizoso for the RK3588's 6 TOPS neural processing unit — to the smaller RK3576. Rocket is the DRM-based driver that gives mainline kernels a fully open-source path for programming Rockchip NPUs, in contrast with Rockchip's own closed-source RKNPU/RKLLM userspace stack that shipped on their downstream kernels. Extending Rocket to a second SoC is significant because the RK3576 is the mid-range chip that Radxa ROCK 4D and a growing crop of single-board computers ship with, and mainline NPU support has been the missing piece stopping those boards from running Linux distributions on stock upstream kernels while still using the NPU.

### 🔬 Details (Phân)
The technical achievement is a byte-exact int8 convolution on a single Rocket-programmed task against a CPU reference implementation. Byte-exact rather than approximate matters because the NPU is programmed at the tensor-tile level, and off-by-one tile addressing or wrong quantisation-scale placement will still produce plausible-looking output that differs by a bit or two — matching a reference CPU output byte-for-byte is the strict correctness proof. What made the work hard is that Rockchip's Technical Reference Manual gives zero mentions of the terms "CNA", "CMAC" or "convolution" across 4,381 pages, so the compute-register layout had to be recovered by observing register writes from the Rockchip binary driver on the downstream kernel and correlating them with input tensors. Chained layer execution — running two or more layers back-to-back without CPU intervention between them — is not yet solved because that path routes through a sub-MMIO sequencer whose state is not exposed to the driver; that limitation is documented in the report as the next open problem.

Performance figures cited on the Radxa ROCK 4D running the Kiln runtime on top of the extended Rocket driver: Llama-3.2-1B at roughly 13 tokens per second, Qwen2.5-1.5B at roughly 9 tokens per second, MobileNet at approximately 169 frames per second. These numbers are single-task rather than chained — the LLM figures come from running the transformer layers as a sequence of single-task submissions with CPU-side glue, which explains why they trail the raw compute the NPU could deliver if chaining were solved. The code lives in two GitHub repositories: `gahingwoo/linux-rk3576-npu` for the kernel patches and instructions, and `gahingwoo/kiln` for the userspace RKNPU/RKLLM-compatible runtime; a research paper archived at doi.org/10.5281/zenodo.21348017 documents the methodology and measurements.

### 🎯 Takeaway (Hợp)
If your embedded platform target is the RK3576 and you have been holding back from mainline Linux because the NPU only worked on Rockchip's downstream kernel, pull the `gahingwoo/linux-rk3576-npu` patch series against your kernel of choice and reproduce the MobileNet-scale workload before planning a full port. Watch the chained-layer work: once the sub-MMIO sequencer problem is solved, the LLM token-per-second numbers will move materially. Đây là bước quyết định cho việc mainline NPU stack có thật sự thay được driver đóng của Rockchip trong 6-12 tháng tới.

### 💡 Example

### 🔭 Overview (Tổng)
Naush Patuck published on 15/07/2026 a co-branded guide on the Raspberry Pi news site, developed with Intel and Ultralytics, that walks through deploying Ultralytics YOLO26 on Raspberry Pi 4 and Raspberry Pi 5 using Intel's OpenVINO 2026.2 runtime. The interesting move here is the platform choice: OpenVINO started life as Intel's CPU/GPU/VPU inference stack and has historically been positioned against Intel silicon, but the recent OpenVINO releases have added Arm CPU support that turns the runtime into a portable deployment target across x86 edge boxes and Arm-based single-board computers. This guide is the first officially co-authored pattern from Raspberry Pi, Intel and Ultralytics that leans on that portability specifically for a modern YOLO model.

### 🔬 Details (Phân)
The install path is a standard Python virtual environment on 64-bit Raspberry Pi OS: `python3 -m venv ~/venvs/ov-rpi`, activate, then `pip install openvino onnx ultralytics`. OpenVINO 2026.2 requires Python 3.10 or newer and ships wheels for CPython 3.10, 3.11, 3.12 and 3.13. Export from the Ultralytics side is a one-line call — `model.export(format="openvino", imgsz=640)` — that emits an OpenVINO IR pair (`.xml` + `.bin`) alongside the source `yolo26n.pt` weights, and the runtime side loads it with `Core().read_model(...)` followed by `compile_model(model, "CPU")`. The guide recommends Raspberry Pi 4 (Cortex-A72 at 1.8 GHz, up to 8 GB RAM) for prototypes and lightweight services, and Raspberry Pi 5 (Cortex-A76 at 2.4 GHz, up to 16 GB RAM) for sustained camera workloads.

The most important caveat is the target device — the guide explicitly compiles the model against the `"CPU"` device. OpenVINO 2026.2 does not target the Raspberry Pi 5's Hailo AI HAT+ or any external NPU through this path; the inference runs entirely on the Arm CPU cores. A companion note in the article calls out that Arm platforms execute quantised models in simulation mode, meaning that even if the source graph is quantised to int8 the runtime falls back to floating-point on Arm, so the traditional "quantise for edge speedup" playbook does not automatically apply. The Ultralytics YOLO26 nano variant (`yolo26n.pt`) is the working example throughout — the guide does not publish specific FPS figures inline and instead points readers to the Ultralytics documentation for the performance comparison plot. Treat the exercise as a portability and integration proof rather than a peak-performance benchmark: the value is having a single OpenVINO deployment shape that a Pi fleet and an Intel NUC fleet can both consume from the same artefact registry.

### 🎯 Takeaway (Hợp)
If your edge-vision fleet is already on OpenVINO for x86 gateways and you are considering Raspberry Pi 4 or Pi 5 for the next expansion, follow the export-and-compile path in this guide to produce a single OpenVINO IR that both fleets consume, and use `yolo26n.pt` as your baseline before scaling to `yolo26s` or larger. Do not expect the Pi 5's Hailo NPU to kick in — the CPU device is the only supported target on this path today. Nếu workload đòi tốc độ cao, cân nhắc chạy song song Hailo runtime cho các mô hình đã convert sang HEF, và giữ OpenVINO cho các mô hình chưa có HEF build.

model = YOLO("yolo26n.pt")

import openvino.properties as props

core.set_property({props.cache_dir: "./ov_cache"})
model = core.read_model("yolo26n_openvino_model/yolo26n.xml")

```
