## 1. ESP-IDF v5.5.5 Ships JPEG Decoder Fix and Disables ECDSA Secure Boot V2 on ESP32-H2, ESP32-C5 and ESP32-P4

| Field | Value |

| 🏷️ Topic | Security |

### 🔭 Overview (Tổng)
Espressif cut ESP-IDF v5.5.5 on 17/07/2026 at 15:35 UTC as a maintenance release on the v5.5 stable branch, and the release carries two items that firmware teams should pay attention to regardless of whether they are ready to upgrade. The JPEG decoder receives strict input checks tied to the security advisory GHSA-v6r2-f6p2-88cj, and ECDSA-based Secure Boot V2 is now disabled at build time on ESP32-H2, ESP32-C5 and ESP32-P4 because the ECDSA flow itself has been found to contain a vulnerability that is not fixable in the affected silicon. Everything else in v5.5.5 is the usual accumulated backport set for the branch, but these two items reshape what "secure boot on these SoCs" means in practice.

### 🔬 Details (Phân)
The JPEG advisory GHSA-v6r2-f6p2-88cj addresses a class of malformed input that could be used to attack devices that decode remote or user-supplied JPEG images, so any firmware pulling images over the network or from an SD card without validation should treat the v5.5.5 upgrade as security-driven, not opportunistic. Espressif also adds a new configuration option, CONFIG_SPIRAM_ENC_EXEMPT, that lets firmware carve out an unencrypted PSRAM region reachable via MALLOC_CAP_SPIRAM_NO_ENC — this is a deliberate escape hatch for workloads where the PSRAM encryption overhead dominates a hot path and the data being placed there is not sensitive. In parallel, v5.5.5 documents the disablement of ECDSA Secure Boot V2 on ESP32-H2, ESP32-C5 and ESP32-P4: the RSA-based Secure Boot V2 flow remains functional and is now the recommended path on these parts, while ECDSA Secure Boot V2 refuses to build on them.

Context for the Secure Boot change: Secure Boot V2 was designed to allow either RSA-3072 or ECDSA-P256/P384 keys, and RSA is the historical default. Espressif's guidance is that products shipping on ESP32-H2, ESP32-C5 or ESP32-P4 that had planned to use ECDSA-P256 for smaller signature sizes should migrate to RSA-3072 or defer to a future silicon revision — there is no fixable workaround at the IDF layer. Devices already fused with ECDSA-based Secure Boot keys are not automatically bricked, but any new build using ECDSA on these SoCs will now be rejected, and Espressif treats it as an unfixable classification for the affected silicon families. Alongside the v5.5.5 cut, v6.0.2 remains the current v6.0-branch stable and v6.1-beta1 continues as the pre-release track for the v6.1 branch, so teams on newer branches should confirm the same fixes have been backported before treating v5.5.5 as the only patched line.

Operationally, upgrading to v5.5.5 is a standard IDF component bump and no API changes are called out for the JPEG or Secure Boot subsystems on the RSA path. Teams that had adopted the ECDSA Secure Boot flow on the affected SoCs will need to re-tape their signing pipeline and re-fuse a fresh RSA key pair on any pre-production units, which is not free but is far less painful than shipping a device with a Secure Boot flow that is now considered broken.

### 🎯 Takeaway (Hợp)
If your product ships firmware that decodes untrusted JPEG data or is on the ESP32-H2, ESP32-C5 or ESP32-P4 with a planned ECDSA Secure Boot V2 flow, land the v5.5.5 upgrade this sprint and audit the signing pipeline for a forced switch to RSA-3072 before any additional pre-production fusing. Nếu sản phẩm dùng RSA Secure Boot V2 và không decode JPEG từ nguồn ngoài, đây vẫn là bản patch nên mainline sớm nhưng không có deadline gấp.

### 💡 Example
```bash

# Migrate the signing pipeline from ECDSA-P256 to RSA-3072 before re-fusing.
idf.py --preview set-target esp32c5
idf.py menuconfig
#   Security features
#     [*] Enable hardware Secure Boot in bootloader
#     Select the secure boot version = "Secure Boot V2"
#     Signing scheme                 = "RSA-3072"   # was: "ECDSA-P256"

# One-off generation of the new signing key. Store off-device in the HSM.
espsecure.py generate_signing_key --version 2 --scheme rsa3072 secure_boot_rsa3072.pem

# Optional escape hatch introduced in v5.5.5 for PSRAM-heavy hot paths.
# Only for non-sensitive buffers — anything with secrets stays in the
# encrypted default pool.
sdkconfig.defaults:
CONFIG_SPIRAM_ENC_EXEMPT=y
```

### 🔭 Overview (Tổng)
Databricks announced on 17/07/2026 that Meta's Muse Spark 1.1 model is now available through Databricks' Unity AI Gateway with the same governance surface as native foundation models, joining OpenAI, Anthropic and Amazon Bedrock as registerable external providers. The framing in the release is that the AI Gateway acts as the front door for any model, so data teams can register a provider once at the account level, then let downstream users, notebooks, jobs and Genie Agents call it through OpenAI-compatible endpoints without holding raw API keys. This is the first Muse Spark 1.1 integration outside Meta's own inference endpoint and is offered in Public Preview across AWS, Azure and GCP.

### 🔬 Details (Phân)
Technically, Muse Spark 1.1 speaks the OpenAI Responses API shape, which is what lets Databricks register it under the OpenAI provider type in Unity Catalog: administrators supply a Meta API key, a base URL of https://api.meta.ai/v1, and an API path of /openai/v1/responses. Governance is standard Unity Catalog: EXECUTE, READ_METADATA and MANAGE privileges apply to the registered model just as they do to a table, and API keys are stored encrypted at the gateway — either under platform-managed keys or, for customers on the customer-managed encryption feature, under a customer-controlled KMS root. The gateway records per-call token counts, latency and status codes so cost attribution rolls up to workspace, user or app rather than being spread across each team's individual OpenAI keys.

Positioning-wise, this release lands into a market where "you can register any OpenAI-compatible model" has become table stakes but "you can register it and then apply the same GRANT/REVOKE model your tables already use, with encrypted key custody and unified spend telemetry" is still the differentiator. AWS Bedrock, Snowflake Cortex and Google Vertex AI each have their own version of this, but Databricks is putting the pattern behind Unity Catalog specifically, which means the same governance object catalog now covers datasets, feature tables, ML models and third-party LLM endpoints. The practical implication for a data platform team is that the previous pattern of shipping OpenAI keys as workspace secrets and hoping individual teams reported spend correctly can be retired: a single registration in Unity Catalog serves every downstream consumer with per-user token accounting.

Two caveats worth noting before adoption. First, Public Preview means the feature requires account administrator opt-in and terms are not yet locked, so treat any migration as reversible rather than a final commitment. Second, Muse Spark 1.1 itself is also in Meta-side Public Preview, so the model is still moving; Databricks' registration flow decouples the provider registration from the client-side model call, which means a client can be pointed at a different model version without a workspace-wide reconfiguration when GA arrives.

### 🔭 Overview (Tổng)
Databricks' July 2026 platform release notes surfaced Managed Iceberg materialized views in Public Preview, alongside GA of Scala and Java UDFs in Unity Catalog and a Beta release of the Anthropic managed ingestion connector. The Iceberg materialized view item is the substantive one for lakehouse architects because it is the first time Databricks-managed materialized views can be read directly by external Iceberg engines — Trino, Snowflake, Athena, or any Iceberg-compatible reader against the Unity Catalog Iceberg REST endpoint — rather than being locked behind a Databricks-only interface. The materialized view still supports incremental refresh, so downstream consumers get a refreshed table view without waiting for a full recompute cycle.

### 🔬 Details (Phân)
The DDL to opt into the new mode is a small extension of CREATE MATERIALIZED VIEW: adding USING ICEBERG on the definition tells Unity Catalog to materialise the result as an Iceberg table with a full manifest chain that external readers can traverse, rather than as a Delta table wrapped in a materialised-view control plane. The Public Preview limits are that external Iceberg engines can read the materialised view but cannot write into it — Databricks retains exclusive write ownership so that the incremental-refresh planner can reason about the deltas that arrived since the last refresh — and enablement currently requires a Databricks account team opt-in per workspace. Incremental refresh continues to work with the usual constraints (append-friendly aggregations, deterministic joins), which matters because the whole point of this integration is that a downstream Trino or Snowflake reader sees a rolling incremental view of Databricks-owned data without operating on the underlying Delta tables directly.

The other two release items add up to a coherent DE story around the same date. Scala and Java UDFs in Unity Catalog going GA closes a long-running gap where Python UDFs were the only governed option — JVM-based UDFs now inherit the same Unity Catalog privileges (EXECUTE, READ_METADATA, MANAGE) and are documented as offering noticeably better throughput than Python UDFs for CPU-bound transforms across serverless and classic compute. The Anthropic managed ingestion connector Beta ingests Compliance API data — audit activity, users, roles and Claude interaction records — into Databricks as governed tables, which is niche but the natural fit for security teams that already run Databricks as their audit lake and want first-party Claude usage telemetry alongside the rest of their identity data.

Adoption implications are practical: for teams currently exposing Databricks-hosted materialised aggregates to external readers via Delta Sharing or scheduled Iceberg snapshots, the Managed Iceberg MV path replaces that plumbing with a first-party read surface. The trade-off is Public Preview scope — enablement requires a Databricks account manager conversation, and the initial preview does not cover every Delta-side MV feature (row filters and column masks are being tracked but not documented as included at preview), so treat it as production-ready for straightforward aggregate MVs and stage a migration rather than a full cutover.

### 🎯 Takeaway (Hợp)
If your architecture already exposes Databricks-hosted aggregates to Trino or Snowflake readers via Delta Sharing or Iceberg snapshots, request enablement of Managed Iceberg materialized views in one non-production workspace this week and rebuild a single aggregate MV against USING ICEBERG to validate the incremental-refresh cadence against a real downstream engine. Nếu chưa export sang Iceberg external reader, giữ nguyên Delta MV cho đến khi feature ra GA.

### 💡 Example

```sql
-- Iceberg readers (Trino, Snowflake, Athena) can read via the Unity Catalog
-- Iceberg REST endpoint. Databricks keeps write ownership.
CREATE MATERIALIZED VIEW analytics.daily_active_users
USING ICEBERG
AS

    event_date,
    country_code,
    COUNT(DISTINCT user_id) AS dau
FROM lakehouse.events.pageviews_bronze
GROUP BY event_date, country_code;

-- Iceberg snapshot on their next query without a full recompute.

```

### 🔭 Overview (Tổng)

The interesting part is not that a hobbyist has cloned a macropad — that happens weekly — but that the emulated device is OpenAI's official Codex Micro control surface for the ChatGPT desktop app, and the Core2 firmware ships with all six agent keys, six command keys, four analog-stick directions and dial actions bound to the Core2's 2-inch touchscreen. It slots into ChatGPT desktop on macOS today and reportedly on Windows, with Linux still unsupported by ChatGPT itself.

### 🔬 Details (Phân)
Technically the firmware is built with PlatformIO on the Arduino framework and lives at github.com/imliubo/codex-micro-4-core2. The trick that makes it work is that Work Louder's Codex Micro exposes itself over Bluetooth Low Energy as a vendor-defined HID, not a generic HID keyboard, and OpenAI's ChatGPT desktop client identifies the peripheral by its BLE vendor descriptor. The Core2 firmware mimics that descriptor byte-for-byte, so ChatGPT desktop enumerates it as a real Codex Micro and enables the same integration surface — task-status colour indicators, battery reporting, command remapping and push-to-talk — that ships on the original hardware. The Core2's touchscreen is what carries the six agent and six command "keys" that the physical device exposes as caps, and the built-in inertial-measurement unit handles the four-axis analog-stick and the rotary dial.

The economics are what will make this circulate: the original Codex Micro shipped at $230 and is currently out of stock, with Work Louder taking pre-orders on a 25-key variant at $125, while an M5Stack Core2 is $59.90 on Amazon or $46.90 on AliExpress. That is a roughly four-to-five-times price gap for a functionally equivalent input surface for anyone who already accepts a touchscreen instead of mechanical keycaps. Positioning-wise, this fits an emerging pattern of "official AI-assistant control surface" hardware (also seen in Anthropic's dev macropad experiments and Cursor's community keycaps) getting immediately clone-firmware'd onto commodity ESP32-based devkits — the ESP32-D0WDQ6-V3 dual-core Xtensa in the Core2 has more than enough headroom for a BLE HID role, and the M5Stack ecosystem's OS and touchscreen driver stack removes most of the bring-up cost.

Caveats to keep in mind: this is a hobbyist firmware relying on OpenAI's willingness to trust HID-vendor identifiers, so a future ChatGPT desktop update that adds cryptographic pairing to Codex Micro would break the impersonation overnight. It also depends on macOS and Windows — Linux remains unsupported because ChatGPT desktop itself does not ship a Linux client — and the firmware author explicitly notes the Windows path is untested at the code level even though the design should work.
