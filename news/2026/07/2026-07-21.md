### 🔭 Overview (Tổng)
dbt Labs tagged dbt-core v2.0.0-alpha.5 on 20/07/2026 as the latest pre-release on the v2.0 line, and this alpha is the first cut to make the v2 catalogs.yml architecture usable across the three most common warehouse targets — Snowflake, BigQuery via the biglake_metastore, and Databricks via Unity Catalog — through the new `catalog_database` field. It sits alongside a Redshift datasharing migration to SHOW TABLES plus SVV_REDSHIFT_COLUMNS, a new `defer_job_id` environment variable, a batch of parse-time correctness fixes, and a set of Python 3.15 and driver bumps that push the transitive stack forward. This is still an alpha, not the shipping v2, but it is the release that lets platform teams start prototyping v2 catalogs against real project structures instead of documentation.

### 🔬 Details (Phân)
The catalogs.yml v2 changes are the substantive body of the alpha. The new `catalog_database` field lets a project declare the physical database or catalog that a v2 catalog resolves to, and dbt-core now gives that value priority over both model-level config and target-level defaults — the practical effect is that a project can express, for example, "this Snowflake catalog resolves in ANALYTICS_PROD_CAT for prod, DEV_CAT for dev" without threading it through every model. The Redshift datasharing path has moved off information_schema and onto SHOW TABLES combined with SVV_REDSHIFT_COLUMNS, which is the pattern the Redshift team recommends for cross-database datasharing scenarios and unblocks projects that consume shared datashares from a producer cluster. The BigQuery adapter picks up biglake_metastore as a first-class catalog kind, and Databricks lines up Unity Catalog as its counterpart, so v2 becomes coherent across the three major managed warehouses in one alpha rather than staged over multiple ones.

Deferral gets a targeted addition: the new `DBT_CLOUD_DEFER_JOB_ID` environment variable makes dbt-core append a job-scoped parameter to the deferral manifest URL, which lets teams pin defer to the manifest produced by a specific dbt Cloud job rather than the latest production manifest. A related fix populates `defer_relation` on graph.nodes entries and corrects its wire shape to match the DeferRelation dataclass — both of which were producing subtle staleness issues in slim-CI workflows that relied on the relation metadata. State-modified selection now handles environment-aware Jinja in configs correctly, which is a class of false positives that had been quietly re-executing untouched models in some setups. Adapter-specific correctness fixes are dense: Spark schema existence now runs through `show databases` instead of an information_schema query that Spark 3.5+ rejects; Snowflake warehouse restoration uses canonical upper-cased names to avoid the "warehouse not found" case-mismatch class of failures; BigQuery treats 403 access-control failures as ignorable permission errors during discovery; and the Redshift Jinja compiler is patched so `!~` and `!~*` POSIX regex-negation operators no longer trip false-positive diagnostics.

Two behavioural changes to plan around. Microbatch lookback now produces N+1 batches — the current batch plus N previous — which corrects prior arithmetic that under-counted the current batch and would look like an off-by-one for anyone with lookback tests. `dbt retry` now preserves the `--full-refresh` flag for incremental models, which is a welcome fix but changes the behaviour of any CI job that was relying on retry silently downgrading to an incremental rerun. Dependency-wise, the Snowflake driver goes to 0.21.14, the BigQuery ADBC driver moves to 0.21.0.dev+dbt0.21.13 with HTTPS_PROXY / NO_PROXY support (useful for anyone behind a corporate egress proxy), and pyo3 jumps from 0.27 to 0.29 so dbt-core now builds against Python 3.15. Security-wise, the dbt docs server drops two ad-hoc SQL query endpoints (POST `/api/v1/query`, GET `/api/v1/tables`) that were unused and expanded the attack surface of a docs preview accidentally left reachable.

### 🎯 Takeaway (Hợp)
Platform teams already tracking dbt-core v2.0 should pull the alpha into a sandbox this week to prototype v2 catalogs against a Snowflake or Unity target, confirm the microbatch N+1 lookback matches expectations, and audit any CI jobs that leaned on `dbt retry` silently dropping `--full-refresh`. Nếu đang chạy production trên v1.12 hoặc v1.11 thì đừng thay vội — alpha chỉ để prototype, đợi beta hoặc rc trước khi lên kế hoạch migrate.

### 🔭 Overview (Tổng)
Databricks published on 20/07/2026 a customer-authored engineering post walking through how Glaspoort, a Dutch fiber-network operator, runs Lakebase database branching in production behind a customer-facing application. Lakebase branching uses copy-on-write to fork a database instantly with no data copy and lets each branch diverge only where it is written — the operational primitive that database vendors have been converging toward since Neon popularised the pattern and that Databricks has now positioned inside its own transactional layer. What makes this write worth reading is not the feature announcement but the concrete CI/CD topology Glaspoort actually shipped: ephemeral per-PR branches with a one-hour TTL, migrations replayed against each fresh branch, and a deliberate decision to fork development and acceptance directly from production instead of stacking environments hierarchically.

### 🔬 Details (Phân)
The environment topology is where Glaspoort broke from the default pattern. Rather than dev → acceptance → prod as a chain of branches, both dev and acceptance branch straight from production, which the team calls out as an escape from the "reset-from-parent trap" — the scenario where refreshing a stale intermediate environment forces deletion of every child branch that inherited from it and re-provisioning of access controls. Each pull request receives an ephemeral branch with a 1-hour TTL cut from production, migrations are replayed against that fresh branch, the updated app image is deployed to a staging slot, and full integration tests run against the migrated branch — first at PR time and again at merge time, giving each change two validation passes before it reaches real environments. Migrations are treated as the authoritative source of truth rather than the databases themselves, so a refreshed branch that lacks a change simply replays the migration to catch up — no manual reconciliation, no snapshot restore.

Authentication avoids static credentials entirely: the application generates short-lived tokens with a 60-minute TTL via `databricks postgres generate-database-credential`, and the connection pool refreshes them proactively with an async password callback before expiry. Access control leans on a single database user, with authorization enforced at the application layer and object-level grants applied manually at production — child branches inherit those grants automatically on creation, which is what makes the branch-from-prod topology operationally cheap. The team is candid about the current rough edges: object-level grants are still managed manually rather than declared as code (called out as "the clearest item on our list to improve"), and there is no per-user database authorization because the app user model is single-identity. Migration replay is skipped for PRs that don't modify schemas via a git diff check, which cuts CI time for the majority of application-only changes.

On the promotion model, Glaspoort evaluated two shapes — merge-after-CI (fast, but PRs can stack while promotion runs) and merge-after-acceptance (independent workflows, but developers wait behind acceptance gates) — and chose merge-after-CI to optimise for team velocity with overlapping work, adding a separate crisis pipeline for urgent fixes and validating stacked migrations as a unit before production. Reported operational outcome: a tenfold increase in iteration speed and the disappearance of shared-environment coordination conversations that used to precede refresh days. Read this as a repeatable pattern rather than a marketing claim — the specific architectural choices (branch-from-prod, migrations-as-truth, 60-minute tokens, ephemeral 1-hour TTL) are portable to any Lakebase, Neon, or copy-on-write Postgres deployment.

### 🎯 Takeaway (Hợp)
If you're evaluating Lakebase branching, or already running Neon or a similar copy-on-write Postgres, adopt the branch-from-prod topology deliberately: cut dev and acceptance directly from production, let migration replay carry schema forward, and keep tokens short-lived. Nếu đang stack dev → uat → prod và vướng "refresh day" mỗi cuối sprint, đây chính là mô hình cần thử đầu tiên.

### 💡 Example
```yaml
# Sketch of the per-PR Lakebase branch step in Azure DevOps.
- stage: PR
  jobs:
    - job: CreateEphemeralBranch
      steps:
        - script: |
            BRANCH_NAME="pr-$(System.PullRequest.PullRequestId)"
            databricks lakebase branches create \
              --parent prod \
              --name "$BRANCH_NAME" \
              --ttl-hours 1
            echo "##vso[task.setvariable variable=DB_BRANCH]$BRANCH_NAME"
        - script: |
            # Migrations are the source of truth — replay against the fresh branch.
            npm run migrate -- --url "$(build-connection-string $DB_BRANCH)"
        - script: |
            # Token TTL is 60 minutes; pool refreshes proactively.
            databricks postgres generate-database-credential \
              --instance lakebase-prod \
              --branch "$DB_BRANCH" \
              --ttl-minutes 60 > .pgcred
        - script: npm run test:integration
```

### 🔭 Overview (Tổng)
Efinix announced on 20/07/2026 the Titanium Edge FPGA family, four devices — Ti40, Ti70, Ti95, and Ti125 — that span roughly 39K to 123K logic elements on a 16 nm TSMC process and target edge AI, machine vision, robotics, medical, and industrial systems. The line is positioned against the mid-range Xilinx Artix / Altera Agilex 5 tier that has become the practical option for teams that need FPGA flexibility on the edge without paying the power budget or die size of the datacenter-oriented families. Two specific features distinguish the launch beyond the routine logic-element table: hardware ML-DSA-65 post-quantum signature support and hardware single-event-upset (SEU) detection and correction, both baked into the fabric rather than left to soft IP.

### 🔬 Details (Phân)
The Ti125 sits at the top of the range with up to 122,792 logic elements (109,440 XLR cells), 288 DSP blocks, 5.9 Mbit of embedded SRAM, and 36 HVIO / 62 HSIO / 84 HSIO2 pins. MIPI CSI/DSI runs up to 2.5 Gbps, memory support tops out at DDR3L 1,333 Mbps, and the SiP variants integrate SPI flash and 512 Mbit of HyperRAM on package to reduce PCB footprint by up to 60% — which matters for medical-endoscope and industrial-camera form factors where board area is the binding constraint. Efinix quotes a 50% reduction in static power versus prior generations, which for a fabric-only device is a meaningful shift for battery-adjacent designs like handheld ultrasound or field-inspection drones.

The security additions are the substantive differentiators. ML-DSA-65 — the NIST-standardised post-quantum digital signature algorithm formerly known as CRYSTALS-Dilithium — is exposed as a hardware primitive, which means a designer can put boot-time image signature verification and secure firmware update onto a schedule that survives the shift away from ECDSA without paying the soft-IP area cost. Hardware SEU detection and correction covers the class of transient bit flips that industrial and aerospace-adjacent deployments have historically had to guard against with EDAC in soft logic; putting it in the fabric lowers both the area cost and the design complexity of certifying against IEC 61508 / DO-254 workloads. Neither is unique to Efinix — Lattice Nexus 2 and Altera Agilex 5 both offer variants of these — but the combination at this price and process node is the interesting positioning.

Availability follows a staged ramp. Ti125 and Ti95 are currently sampling; Ti125 SiP is scheduled for August 2026; Ti70 and Ti40 arrive in Q4 2026. Efinix has not announced pricing, which reads as a signal that the go-to-market is contract-driven for the initial customer set rather than distributor-catalogue. Toolchain-wise, Efinity IDE remains the software stack, and the family targets the same Riscv Sapphire soft-core lineage that runs on the current Titanium and Trion families — so existing Efinix HDL and Sapphire firmware ports should carry across, though Ti-Edge-specific IP (ML-DSA-65, SEU) will need explicit integration.

### 🎯 Takeaway (Hợp)
For edge-AI or industrial-vision teams that were queueing an FPGA refresh cycle in H2 2026 and need post-quantum-ready signature verification on the boot path, put Ti95 or Ti125 on the evaluation short-list once samples arrive and validate the ML-DSA-65 and SEU flows against your certification target early. Nếu chỉ cần logic-element count và không quan tâm PQC hoặc SEU thì Ti40 (Q4) sẽ hợp lý hơn về BOM.

### 🔭 Overview (Tổng)
Geniatech announced on 20/07/2026 the XPI-3576-CM5, a compute module that mounts a Rockchip RK3576 SoC onto a 55 × 40 mm 8-layer PCB with two 100-pin B2B connectors laid out to match the Raspberry Pi CM4 / CM5 mechanical footprint. This is not a Raspberry Pi product — it is a third-party module that reuses the CM5 form factor so existing carrier boards, thermal solutions, and reference designs built for CM4 / CM5 can host an RK3576 without redesign. For fleet operators who have already standardised on CM4 or CM5 for edge-AI gateways or industrial displays, the module is a drop-in path to a 6 TOPS NPU and LPDDR5 without switching mechanical platforms.

### 🔬 Details (Phân)
The RK3576 on this module ships as an octa-core big.LITTLE combination — four Cortex-A72 cores at 2.2 GHz and four Cortex-A53 cores at 1.8 GHz — with a Mali-G52 MC3 GPU at 1 GHz and a 6 TOPS (INT8) AI accelerator that supports INT4, INT8, INT16, BF16, and TF32 mixed operations. RAM is offered at 4 GB, 8 GB, or 16 GB LPDDR5, storage at 32 GB / 64 GB / 128 GB eMMC, plus a Lite storage-less variant for applications booting from external eMMC or NVMe. Connectivity is broad for a CM-class module: Gigabit Ethernet via a RealTek RTL8211F PHY, dual-band WiFi 6 and Bluetooth 5.3 through an Ampak AP6275S module, one HDMI, one 4-lane MIPI DSI, one 4-lane MIPI CSI-2 camera input, one USB 3.0, one USB 2.0 OTG, a PCIe Gen 2.0 x1 lane, up to 28 GPIOs, and a CAN bus. Pricing is not publicly disclosed — Geniatech is targeting the B2B channel.

The competitive framing against Raspberry Pi's own CM5 is straightforward. CM5 uses a BCM2712 quad-core Cortex-A76 at 2.4 GHz with no on-die NPU; the XPI-3576-CM5 trades that stronger single-core CPU for an octa-core big.LITTLE plus the 6 TOPS NPU and a wider AI dtype set. For workloads that were already offloading to a USB or PCIe accelerator on a CM5 carrier, moving to the XPI-3576-CM5 collapses the accelerator onto the module and reclaims the PCIe / USB slot; for CPU-bound loads it is likely a net downgrade. The CM5 compatibility claim covers mechanical and connector layout — not signal-for-signal drop-in — so carrier boards still need pin-map validation before deployment, especially around HDMI, CSI, and PCIe lane routing where Rockchip and Broadcom differ. Target applications called out by Geniatech include industrial control, edge-AI gateways, smart displays, medical devices, in-vehicle terminals, and robotics — the same lane where AAEON, Radxa, and Firefly have been shipping RK3576 modules under different form factors for the past two quarters.

### 🎯 Takeaway (Hợp)
For teams already committed to the CM4 / CM5 carrier ecosystem who need a 6 TOPS NPU on-module for edge inference, the XPI-3576-CM5 is worth requesting a sample and validating pin compatibility against your existing carrier board — especially HDMI, CSI, and PCIe lanes. Nếu chưa lock vào CM footprint và ưu tiên CPU đơn nhân mạnh, CM5 chính hãng vẫn là lựa chọn hợp lý hơn.
