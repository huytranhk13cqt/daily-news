## 2. Databricks Publishes Two-Stage Retrieve-Then-Classify Pattern for 100k+ Label Taxonomies

### 🔭 Overview (Tổng)
Databricks published on 20/07/2026 an engineering write-up on a problem that keeps recurring in data platforms — classifying documents against a taxonomy of 100,000 or more labels — where the naive approach of passing every label into an LLM prompt breaks on context, cost, and quality all at once. The proposed pattern is a two-stage pipeline: retrieve a shortlist of candidate labels via hybrid vector plus lexical search, then let AI Classify pick from that shortlist. It is not a new architecture in the abstract, but the piece pins down the specific primitives — Qwen3-Embedding-8B for embeddings, BM25 plus cosine similarity fused via Reciprocal Rank Fusion, an in-memory index of roughly 1.6 GB for 100k float32 embeddings — that a team could actually build against inside Databricks today.

### 🔬 Details (Phân)
The retrieval stage does the heavy lifting. Every label is embedded with Qwen3-Embedding-8B and indexed in memory at roughly 1.6 GB for 100k labels using float32; the same embedding model encodes each incoming document at query time, cosine similarity produces the semantic ranking, and BM25 over the label surface text produces the lexical ranking. Reciprocal Rank Fusion merges the two ranked lists to a single top-k shortlist — the write-up's argument for RRF over a weighted sum is that RRF is parameter-free, avoids the score-normalisation problem when the two rankers have different distributions, and handles the frequent case where a label is a strong lexical match but a mediocre semantic one (or vice versa). The classification stage then hands the document plus the top-k shortlist to the AI Classify function, and the LLM's job collapses from "pick one of 100,000" to "pick one of maybe 20" — a task frontier models handle reliably.

The model comparison is the piece to read carefully rather than skim. The authors benchmarked GPT-5.6 Luna, GPT-5.4 mini, Gemini 3.5 Flash, and Claude Sonnet 5 as the classification-stage LLM against the same retrieved shortlists, and the accuracy-versus-cost trade-off shifts materially depending on how deep you set the retrieval — deeper top-k improves recall but shifts more work back to the LLM. No explicit latency or throughput numbers are published, which is the honest gap in the piece: the article is pitched as a design pattern and cost/accuracy discussion, not a production benchmark. The three motivating use cases — biomedical entity linking against UMLS, vendor normalisation across 100k+ merchants, and company deduplication — are canonical fat-taxonomy problems that most data platforms hit sooner or later, and the pattern is portable to any warehouse-plus-LLM stack, not just Databricks.

The Databricks-specific primitives used are AI Classify as the classification function, AI Query as the embedding driver for the taxonomy pass, vector search for the retrieval index, and SQL as the execution surface — the piece notes AI Classify "can be run with SQL" but does not print the exact syntax and points readers at a companion tutorial notebook instead. Practical implication: teams that already have a labelled taxonomy sitting in a Delta table can prototype the retrieval stage in a day with `ai_embed` and hybrid search, and only bring in AI Classify once the shortlist quality is validated at recall@20 or better.

### 🎯 Takeaway (Hợp)
For any team wrestling with fat-taxonomy classification — UMLS, NAICS, GICS, merchant taxonomies, product hierarchies — build the retrieval stage first, validate recall@20 on a hand-labelled holdout before wiring the LLM stage, and default to Reciprocal Rank Fusion over weighted-sum fusion so you avoid the score-normalisation trap. Đừng cố nhét taxonomy 100k label vào prompt của LLM; luôn tách hai tầng retrieve-rồi-classify, rẻ hơn và chính xác hơn nhiều.

### 💡 Example
```sql
-- Two-stage retrieve-then-classify sketch on Databricks.
-- Stage 1: hybrid retrieval over an embedded label taxonomy.
WITH doc AS (
  SELECT
    doc_id,
    ai_embed('qwen3-embedding-8b', doc_text) AS doc_vec,
    doc_text
  FROM landing.incoming_docs
),
shortlist AS (
  SELECT
    d.doc_id,
    l.label_id,
    -- Reciprocal Rank Fusion of semantic + lexical ranks (k=60 is conventional).
    (1.0 / (60 + rank() OVER (PARTITION BY d.doc_id ORDER BY cosine_sim(l.label_vec, d.doc_vec) DESC))) +
    (1.0 / (60 + rank() OVER (PARTITION BY d.doc_id ORDER BY bm25_score(l.label_text, d.doc_text) DESC)))
      AS rrf
  FROM doc d
  CROSS JOIN taxonomy.labels l
  QUALIFY rank() OVER (PARTITION BY d.doc_id ORDER BY rrf DESC) <= 20
)
-- Stage 2: AI Classify picks the winner from the 20-label shortlist.
SELECT
  s.doc_id,
  ai_classify(d.doc_text, collect_list(s.label_id)) AS predicted_label
FROM shortlist s
JOIN doc d USING (doc_id)
GROUP BY s.doc_id, d.doc_text;
```

The release lands with 18 components spanning audio, video, and on-device AI, a unified data-flow model with a component system that Espressif positions as more modular and reusable than the ADF stack, and API stability across every v1.0 component. Target chips are the ESP32, ESP32-S3, ESP32-P4, and ESP32-S31 — the S31 pickup matters because it aligns the framework with Espressif's newer AI-focused silicon rather than only the legacy audio-oriented parts.

### 🔬 Details (Phân)
The 18 components are the substance of the release. New modules include `esp_player` (multimedia player with demux, decode, and render), `esp_video_render` (video composition with multi-backend display and overlay), `esp_asrc` (audio sample-rate converter with an HW-SW co-design), and `gmf_fft` (fixed-point Q15 FFT/IFFT with PIE acceleration). Existing modules picked up meaningful additions: `gmf_core` gained a variable-sized block data queue and a data-bus factory, `gmf_audio` added `aud_muxer`, `aud_howl`, and `aud_asrc` elements, and `gmf_ai_audio` added `ai_vad` (voice activity detection), `ai_ns` (noise suppression), and `ai_doa` (direction of arrival) — the last three are the ones that turn ESP-GMF from an audio pipeline framework into an on-device conversational-audio stack. Video processing added hardware-blend and multi-region overlay, and MJPEG→RGB decode was added specifically on the ESP32-S31.

Codec support is expanded via esp_audio_codec v2.5: G722 codec is now available in both encode and decode paths, and OGG decode is new. G722 in particular matters for VoIP-adjacent applications on ESP32 devices — it is the standard 7 kHz wideband codec that DECT, SIP endpoints, and many enterprise conferencing systems already speak, so an ESP32-P4 endpoint can now bridge into that ecosystem without a soft codec detour. The rest of the release is API stabilisation and a broadening of chip support: every v1.0 component ships with stable APIs, and Espressif frames this as the point at which teams should start building product code against ESP-GMF rather than treating it as evaluation-only.

Two caveats are worth naming. The blog post does not publish benchmarks — no RAM footprints per component, no latency numbers for the ASRC or FFT paths, no comparison against ESP-ADF on the same hardware — so any migration from ADF still needs a pass on your actual application to size the working-set delta. And there is no explicit ESP-ADF-to-ESP-GMF migration guide; the framing is that ESP-GMF is architecturally distinct rather than a drop-in replacement, so an existing ADF pipeline will need to be re-expressed against the ESP-GMF component graph. Ecosystem-wise, the framework's positioning inside `esp-idf` means it lines up with the same build system and component manager teams already use, so integration cost into an existing esp-idf project is mostly a `idf.py add-dependency` and a component wire-up.

### 🎯 Takeaway (Hợp)
For teams building voice, audio, or edge-vision products on ESP32-S3 / P4 / S31 who have been holding off on ESP-ADF or waiting for the next-gen framework to stabilise, this is the release to start prototyping against — begin with `esp_player` for the pipeline shape and layer in `ai_vad` / `ai_ns` if the product is voice-facing. ### 🔬 Details (Phân)
Supported silicon covers the nRF54L15 and nRF54LM20A. The architectural choice — no Zephyr, no nRF Connect SDK — is the debate worth flagging. The tradeoff is that the core dodges the complexity budget of Zephyr's device-tree / Kconfig model, its build system, and its RTOS scheduling model — which lowers the barrier for a "flash-and-see" workflow but gives up the peripheral abstraction, RTOS features, and battle-tested driver stack Zephyr provides. Nordic's own SDC (SoftDevice Controller) and MPSL (Multi-Protocol Service Layer) binaries are still used for the LE / Channel Sounding radio stack, so the Bluetooth path is not homegrown, and mbedTLS covers the crypto primitives — the "bare-metal" here means application-layer bare-metal on top of Nordic's supported radio blobs, not radio-firmware-from-scratch.

Distribution is via Arduino Boards Manager as of 1.0.8, with source at `github.com/lolren/nrf54-arduino-core` under MIT for project-owned contributions (third-party components retain their originals: Nordic 5-Clause for SDC/MPSL, Adafruit attribution for the Bluefruit52Lib examples). The example workflow the README recommends is to run the `Diagnostics/CleanBringUp` sketch first to verify board detection, then load `Bluefruit52Lib/Peripheral/bleuart` to bring up a phone-visible BLE UART peripheral — the Bluefruit52 name comes from the reused Adafruit compatibility layer that gives nRF52 Arduino sketches a straight path to nRF54L. Security features like secure boot, TrustZone, and the nRF54L Key Management Unit are not called out in the release notes; teams that need attestation or signed-image boot will need to layer those on top or fall back to nRF Connect SDK.

BLEUart bleuart;  // BLE UART service (Nordic UART Service, phone-compatible).
