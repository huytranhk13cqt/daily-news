## 1. Databricks Lakebase Postgres Positions Itself as a Native Orchestration Layer for Long-Running AI Agents

### 🔭 Overview (Tổng)
Databricks published a reference architecture that reframes Lakebase, its managed Postgres service inside the lakehouse, as the coordination fabric for long-running agentic workloads instead of just an OLTP sidecar. The post walks through a document-processing agent that uses two Postgres tables for a durable work queue, `LISTEN/NOTIFY` for real-time UI updates, and MLflow Tracing plus Unity Catalog for governance. The framing matters because most teams currently glue together Redis, RabbitMQ, or Celery to run agent fleets, and each of those is a governance island the lakehouse cannot see.

### 🔬 Details (Phân)
The queue is described as a two-table pattern — a `tasks` table and a `task_attempts` table — with concurrent workers pulling work through the canonical Postgres `SELECT ... FOR UPDATE SKIP LOCKED` idiom, ordered by `priority DESC, created_at`. Attempts are lease-based so that if a worker crashes mid-run, an expiring lease returns the task to the pool without human intervention. Rate limiting is layered on top with three modes: concurrency caps, token-per-minute budgets, and a hybrid mode for workloads that are both wide and expensive. Observability is driven by Postgres `NOTIFY` events fanned out to a FastAPI Databricks App as Server-Sent Events, with a ten-second polling fallback.

The stack around the queue is deliberately Databricks-native: Lakeflow Jobs runs the actual document processing, Unity Catalog Volumes stores the PDFs, MLflow Tracing captures token usage per attempt, and `system.billing.usage` is joined in for per-application cost attribution. Because Lakebase inherits Unity Catalog identity, OAuth rotation, and instance branching from the platform, teams avoid running a separate identity plane for their agent infrastructure. Positioned against an external Redis-plus-Celery deployment, this trades a well-known scale-out story for a governance and cost-attribution story that a lakehouse-first shop is likely to prefer.

The migration cost is not zero. Teams that already have a mature Airflow-plus-Redis footprint will need to rewrite worker semantics against Postgres locking primitives, and Lakebase's autoscaling model — while positioned as an advantage — introduces a different tail-latency profile than a warmed Redis worker pool. The reference implementation is the useful starting point rather than a drop-in migration.

### 🎯 Takeaway (Hợp)
If your agent workloads already live inside Databricks, this pattern removes the strongest remaining argument for standing up a separate queue service. Read the reference code, benchmark `SKIP LOCKED` throughput against your current backlog width, and treat the MLflow-plus-billing join as the concrete win — that piece is genuinely awkward to reproduce outside the lakehouse.

### 💡 Example
```sql
-- The canonical dequeue pattern the reference architecture builds on
WITH next_task AS (
  SELECT id
  FROM tasks
  WHERE status = 'pending'
  ORDER BY priority DESC, created_at
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE tasks t
SET    status      = 'in_progress',
       lease_until = now() + interval '5 minutes',
       worker_id   = :worker_id
FROM   next_task
WHERE  t.id = next_task.id
RETURNING t.id, t.payload;
```

### 🔭 Overview (Tổng)
DuckDB shipped v1.5.5 as a bugfix release focused primarily on backporting out-of-bounds read fixes from the in-development 1.6 branch to the current LTS-track release. The release notes explicitly call out four distinct OOB read paths — JSON path key lookahead, string-to-struct casting, dictionary string decompression, and empty byte-array decimals — each of which could be triggered by adversarial input in files or queries. A `TemporaryMemoryManager` deadlock and a concurrent-ALTER/INSERT crash also land in the same release, both of which have a real chance of biting long-running production workloads.

### 🔬 Details (Phân)
The four security-relevant fixes were backported from PR #23100 and shipped via #23197, #23371, #23384, #23549, and #23567. None of them have public CVE or GHSA identifiers at the time of writing, and the DuckDB security advisories page still lists only the November 2025 encryption issue and two July 2024 items — so consumers relying on advisory feeds for triage should treat this release as effectively a silent security update. In practice, any deployment that ingests untrusted Parquet, JSON, or dictionary-compressed columnar data on 1.5.x should upgrade rather than wait for an advisory ID.

Beyond the OOB reads, the release resolves a memory deadlock in `TemporaryMemoryManager`, tightens Parquet `DATA_PAGE_V2` validation, fixes false RLE corruption errors, corrects window-function framing bugs in `FIRST_VALUE`, `CUME_DIST`, and `RANGE`, and prevents crashes when `ALTER` and `INSERT` run concurrently against the same table. A `DROP COLUMN` metadata-corruption fix and an external hash aggregate memory leak round out the stability work. Fifty-seven merged PRs land in this release, which is unusually broad for a patch.

For teams pinning to 1.5.x for LTS reasons, this is the release to move to — 1.5.4 (17 June 2026) is now demonstrably behind on both correctness and hardening. Users still on 1.4.x got a parallel bugfix (1.4.5) on the same 17 June date, but the July hardening work has not, as of this digest, been mirrored back to that branch.

### 🎯 Takeaway (Hợp)
Upgrade any DuckDB 1.5.x deployment to 1.5.5, especially if it handles JSON payloads, Parquet files, or concurrent DDL against live tables. Do not wait for CVE assignment — the changelog is the authoritative signal here, and the fix list is specific enough to justify a routine rollout this week.

### 🔭 Overview (Tổng)
Raspberry Pi released a 10-inch variant of the Touch Display 2 at USD 80, doubling the physical size of the earlier 7-inch model while lifting resolution to 1200×1920 and touch capability to ten simultaneous points. The panel drives kiosk, HMI, and home-automation form factors that the smaller display never comfortably covered. Support is officially limited to the four-lane DSI connector introduced on the Raspberry Pi 5 and the newer Compute Module IO boards.

### 🔬 Details (Phân)
The specification favours dashboards and control panels rather than handheld projects. A 1200×1920 portrait panel with an 85-degree viewing angle and capacitive ten-finger touch matches what off-the-shelf industrial HMI vendors ship at 3-5× the price. It is powered directly from the host Raspberry Pi over the same narrow, high-bandwidth ribbon cable as the 7-inch model, and driver support is enabled by default in Raspberry Pi OS with no manual calibration step. This mirrors the plug-and-go story that made the original 7-inch Touch Display popular for hobby signage builds.

The consequential caveat is compatibility. The four DSI data lanes required by this display are only exposed on Raspberry Pi 5 boards and Compute Module IO carriers designed for CM4 or CM5 with the newer connector. Raspberry Pi 4, earlier models, and the Pi Zero series cannot drive this panel. That excludes a large installed base and means the 10-inch model is functionally a companion product for the Pi 5 generation rather than a drop-in upgrade for existing 7-inch Touch Display 2 deployments.

Pricing continues the trend of Raspberry Pi treating first-party displays as loss-leader accessories. USD 80 for a 1200×1920 capacitive touch panel with official OS support is competitive against third-party HDMI-plus-USB touch panels once cables, drivers, and enclosure headaches are counted. The main alternative for makers on older Pis remains the 7-inch Touch Display 2 or a third-party HDMI monitor with a separate USB touch controller.

### 🎯 Takeaway (Hợp)
For any Pi 5 kiosk, home-automation dashboard, or benchtop control project that has been waiting for a first-party 10-inch touch option, this is the panel to design around. If your fleet is still on Pi 4 or Zero, plan around the 7-inch Touch Display 2 — the 10-inch model will not work no matter what adapters you try.

### 🔭 Overview (Tổng)
Arduino packaged its Qualcomm-Dragonwing-based UNO Q single-board computer into an Arcade bundle priced at USD 90.90, or EUR 96.36, with a 20% early-bird discount running through 10 September 2026. The bundle pairs the 4GB UNO Q with three Qwiic-connectable Modulino I2C input modules — a joystick, a button pad, and a six-axis motion sensor — and drives standard emulators through a Python bridge script that turns sensor data into `uinput` HID events on Debian. The pitch is a build-in-a-weekend retro console that also doubles as a teaching platform for the UNO Q hardware and I2C peripherals.

### 🔬 Details (Phân)
The core board is Arduino's UNO Q 4GB, built on the Qualcomm Dragonwing QRB2210 with onboard eMMC and running a Debian desktop. The three input modules chain over Qwiic connectors on the I2C bus, avoiding hand-wired GPIO and letting learners swap or add peripherals without a soldering iron. A Python script called `injector.py` reads I2C, translates gestures and button state into virtual keyboard and mouse events through the Linux `uinput` subsystem, and RetroArch — with mGBA, bsnes, and Nestopia cores — plus the Godot engine consume those events like any other HID device. The UNO Q itself needs an externally purchased USB-C hub and power supply to complete the setup.

Positioning-wise, the bundle competes less with a Steam Deck or a Raspberry Pi 5 games build and more with the Adafruit and Pimoroni educational hardware bundles. It is genuinely a learning kit — the Modulino ecosystem is exposed and documented, the emulation stack is off-the-shelf, and the injector script is a compact, readable teaching artefact. For classrooms already deploying UNO Q, the arcade bundle is an easy add-on that produces a visible weekend project.

The main friction is Arduino's own ecosystem gaps. Modulino I2C peripherals still have a smaller third-party accessory pool than Qwiic parts sourced through SparkFun or Adafruit, though they are electrically compatible. The USB-C hub requirement is minor but real — the bundle should not be positioned as a fully self-contained kit.

### 🎯 Takeaway (Hợp)
Consider the bundle when the goal is teaching, prototyping HID pipelines, or handing a class of students a project that produces a playable artefact by Friday. For a personal retro-gaming build with maximum performance per dollar, a used mini PC or a Pi 5 with an HDMI display is still the cheaper answer.

### 💡 Example
```python
# Sketch of the Modulino-to-uinput bridge used by the bundle's injector.py
from evdev import UInput, ecodes as e
from modulino import Buttons, Joystick

ui = UInput({e.EV_KEY: [e.KEY_LEFT, e.KEY_RIGHT, e.KEY_UP,
                        e.KEY_DOWN, e.KEY_ENTER, e.KEY_ESC]},
            name="modulino-arcade")

btns = Buttons()
stick = Joystick()

while True:
    x, y = stick.read()
    ui.write(e.EV_KEY, e.KEY_LEFT,  1 if x < -0.5 else 0)
    ui.write(e.EV_KEY, e.KEY_RIGHT, 1 if x >  0.5 else 0)
    ui.write(e.EV_KEY, e.KEY_UP,    1 if y < -0.5 else 0)
    ui.write(e.EV_KEY, e.KEY_DOWN,  1 if y >  0.5 else 0)
    ui.write(e.EV_KEY, e.KEY_ENTER, 1 if btns.a else 0)
    ui.write(e.EV_KEY, e.KEY_ESC,   1 if btns.b else 0)
    ui.syn()
```
