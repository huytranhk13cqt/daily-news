### 🔭 Overview (Tổng)
Databricks published a reference architecture for building document-processing AI-agent orchestration entirely on Databricks-native primitives, using Lakebase Postgres as the task queue, Databricks Apps as the FastAPI-based UI layer, Lakeflow Jobs as the agent runtime, MLflow Tracing for token and cost telemetry, and Unity Catalog Volumes for PDFs. The pitch is direct: no Kafka, no Redis, no Airflow, no Temporal. For teams already on Lakebase, this is the first Databricks-endorsed shape for the agent-orchestrator stack, and it explicitly frames a single-vendor alternative to the polyglot stacks that dominate the space today.

### 🔬 Details (Phân)
The queue is two tables — `tasks` and `task_attempts` — with four Postgres patterns doing the operational work. Concurrent priority dequeue uses `FOR UPDATE SKIP LOCKED` with an `ORDER BY priority DESC`, so many workers can safely pull the next-highest-priority row without blocking one another. Crash recovery is lease-based: each worker acquires a time-bounded lease, and expired leases get automatically re-enqueued, giving at-least-once semantics without a separate coordinator. Rate limiting is baked into the dequeue query in three modes — concurrency caps, token budgets, or a combination — which means governance sits in the queue rather than in per-worker code. Idempotent webhook handling ships as the fourth pattern to prevent duplicate task creation from retried inbound events.

The UI half streams task updates over Server-Sent Events driven by Postgres `LISTEN/NOTIFY` triggers, with a 10-second polling fallback for browsers that lose the SSE connection. Lakebase's specific capabilities lean in here: autoscaling compute with storage/compute separation lets the queue burst without a static provision, OAuth-rotated short-lived tokens auto-refresh through the connection pool, Unity Catalog identity integration means the queue inherits the same principal model as the rest of the platform, and native branching plus snapshot cloning allow full-fidelity dev environments off a production queue. A dashboard splits LLM token spend from MLflow Traces and serverless compute cost from Databricks Jobs into per-run breakdowns.

The stated production reference is CliftonLarsonAllen LLP, which the post credits with taking document extraction from hours to minutes on this stack. No latency, throughput, or cost benchmarks are published, and the piece does not compare against Temporal or Airflow directly — the argument is architectural, not performance-first. That is worth naming: teams choosing between this and a mature workflow engine still need to run their own load tests before committing.

### 🎯 Takeaway (Hợp)
For shops already deep on Databricks, this is the strongest single artefact yet on how to keep agent orchestration inside the platform. Steal the two-table schema and the `SKIP LOCKED` dequeue pattern for your own pilot, but hold off replacing an existing Temporal or Airflow deployment until you have measured throughput on Lakebase for your specific task shape.

### 💡 Example
```sql
-- Concurrent priority dequeue with lease-based crash recovery
WITH next_task AS (
    SELECT id
    FROM   tasks
    WHERE  status = 'pending'
       OR (status = 'running' AND lease_expires_at < now())
    ORDER  BY priority DESC, created_at ASC
    LIMIT  1
    FOR    UPDATE SKIP LOCKED
)
UPDATE tasks t
SET    status           = 'running',
       worker_id        = :worker_id,
       lease_expires_at = now() + interval '5 minutes',
       attempts         = attempts + 1
FROM   next_task n
WHERE  t.id = n.id
RETURNING t.*;

-- Publish updates to any FastAPI/SSE listener
CREATE TRIGGER tasks_notify
AFTER UPDATE ON tasks
FOR EACH ROW EXECUTE FUNCTION pg_notify('task_updates', row_to_json(NEW)::text);
```

### 🔭 Overview (Tổng)
DuckDB 1.5.5 is the sixth patch release in the 1.5 "Variegata" line, bundling roughly 70 pull requests from 27 contributors focused on bugfixes, targeted performance work, and backported security patches. The headline entry is a correctness fix for 128-bit DECIMAL columns where `RETURN_STATS` was swapping min and max values across multiple row groups — a class of bug that quietly poisons filter pushdown and query planning without ever throwing an error. Anyone on the 1.5 line running analytics over financial or currency data at HUGEINT precision should treat this release as mandatory.

### 🔬 Details (Phân)
The 128-bit DECIMAL fix is the item most likely to bite production users silently. `RETURN_STATS` is the metadata surface DuckDB uses to skip row groups during scans, so swapped min/max across groups means predicates can incorrectly include or exclude blocks — with no exception raised and no wrong-row-count signal. The rest of the crash-fix set is broad: min/max aggregate stats crashing when row groups are filtered, a `TemporaryMemoryManager` deadlock, a C API scalar-bind subquery crash, a segfault in the external hash aggregate, a race between concurrent ALTER and INSERT statements, unsafe iteration inside string cast operations, and additional guards around the DICT_FSST encoding path. There is also a false RLE-corruption error to stop scaring users off healthy data, Arrow-type extension fixes, an `ALTER TABLE ADD COLUMN IF NOT EXISTS` regression, `DROP COLUMN` metadata corruption, JSON rendering in duckbox, and a leak in the eviction node.

On the performance side the release enables ALP and ALP_RD compression for storage version 1.5.0+ with smaller block sizes, both codecs already in the codebase but now switched on by default. ADBC gains `duckdb://` URI-scheme support and the ADBC Statistics API, and `libduckdb` archives now bundle extension headers so downstream builds no longer need a separate include hunt. Security-wise, the release backports out-of-bounds fixes without disclosing specific CVE identifiers, so this is best treated as a defence-in-depth patch rather than a targeted CVE response.

For anyone tracking the wider release cadence, 1.5.5 is the maintenance line while 1.6.0 development continues in main — the pattern of monthly-ish patch drops on the current stable series has held all year. Extension authors should note the header change: rebuilding against 1.5.5 will pick up the bundled headers automatically.

### 🎯 Takeaway (Hợp)
Upgrade if you are on any 1.5.x, especially if your workload touches DECIMAL(38,x) columns — the min/max swap is exactly the kind of correctness bug that costs a quarter of reporting before anyone notices. Extension maintainers should rebuild against the new `libduckdb` to pick up the header changes and the ADBC surface.

## 5. ESPHome 2026.7 Turns On EN18031-Track Security: HMAC NVS Encryption, OTA Anti-Rollback, and an ESP-IDF Default Flip

| Field | Value |

| 📅 Date | 23/07/2026 |

### 🔭 Overview (Tổng)
ESPHome 2026.7 opened a coordinated wave of EN18031-track security features and flipped the default toolchain on ESP32 and nRF52 targets from PlatformIO to native ESP-IDF and nRF Connect SDK. Two follow-up patch releases (2026.7.1 on 21/07 and 2026.7.2 on 23/07) landed inside the last 48 hours, keeping the line current. The security move is the clearest signal yet that a major open-source IoT firmware stack is actively preparing for the EU Radio Equipment Directive's EN18031 consumer-device compliance standard, and the toolchain flip carries downstream implications for build caches, CI, and the long-term positioning of PlatformIO within the ESPHome ecosystem.

### 🔬 Details (Phân)
The security additions are opt-in but concrete. NVS encryption on ESP32 uses the built-in HMAC peripheral, is supported on ESP32-S2, S3, C3, C5, C6, H2, and P4, and derives keys at runtime from an eFuse HMAC key so it works without full flash encryption enabled. The docs warn plainly that burning the HMAC eFuse is permanent and irreversible, which is the kind of one-way door that deserves a checklist rather than a `--yes` flag in your CI script. OTA downgrade protection compares a staged image's version against the running version before switching the boot partition, and it applies across the native ESPHome OTA, HTTP request, and web server OTA sources. A new transport-agnostic provisioning component lets the API and ESP32 Improv register as sources and closes the provisioning window on timeout with a distinct `DISCONNECT_REASON_PROVISIONING_CLOSED` reason code.

The toolchain flip is the operational change most builds will notice. ESP32 configs without an explicit `toolchain:` key now build with ESP-IDF, and nRF52 configs now target nRF Connect SDK 2.9.2. PlatformIO remains available via `toolchain: platformio`, but the default is now native. ccache is enabled by default for ESP-IDF builds, with shared caches under `~/.cache/esphome/idf` and `~/.cache/esphome/sdk-nrf`, which should recover much of the build-time cost of the framework switch on any developer machine that compiles more than one project. The Modbus stack has been rewritten and split into `ModbusClientHub` and `ModbusServerHub`, adding `on_modbus_no_response()` and `on_modbus_not_sent()` callbacks with 2000 ms default `send_wait_time` and 600 ms `turnaround_time`. Networking gains Gigabit Ethernet on ESP32-S31 via new `type: GENERIC` and `type: YT8531` PHY components, and ESP-NOW v2 payloads now reach 1470 bytes on ESP-IDF ≥5.4 or Arduino ≥3.2. A single-precision-float sweep across roughly 50 components delivered measurable code-size wins — `hsv_to_rgb` fell from 108 to 69 bytes on ESP32, a 36% reduction.

Breaking changes are worth flagging before you upgrade. Python 3.11 support has been dropped and the tool now requires 3.12+. The bundled Tornado-based dashboard has been removed in favour of the external ESPHome Device Builder. The `packages: !include file.yaml` syntax must now be a list rather than a scalar. And web server v1 is deprecated with removal targeted at 2027.1.0, so any dashboard project still on v1 has roughly six months to migrate. The release notes do not cite specific CVEs, so treat the security work as defence-in-depth infrastructure rather than a response to a known exploit.

### 🎯 Takeaway (Hợp)
Upgrade a small slice of your fleet first, and turn the security features on deliberately — HMAC eFuse burn is one-way and OTA anti-rollback needs a coherent version-bumping discipline to avoid bricking legitimate downgrades. Anyone tracking EU compliance timelines should read the EN18031 alignment as the direction of travel; anyone still on the PlatformIO default should test their CI cache paths before the flip surprises them.
