### 🔭 Overview (Tổng)
Grab's engineering team published the first instalment of an agent-platform write-up on 24 July 2026, describing LLM-Kit — the internal FastAPI-and-LangGraph scaffolding that now underpins over 500 agent services and 50 registered MCP servers across the company, processing billions of tokens per month through a single GrabGPT gateway. The framing is unusually concrete: LLM-Kit is explicitly not a new agent abstraction, it is "a curated set of integrations and scaffolding" — pre-wired OIDC auth, Vault-backed secrets, OpenTelemetry-instrumented FastAPI + LangChain + MCP tracing, gRPC bidirectional contracts, ROUGE/BLEU/LLM-as-judge evals, and template-generated service diagrams. Anyone building an internal agent platform will find this a useful reference on where the actual complexity sits.

### 🔬 Details (Phân)
The technical spine is deliberate. LangGraph handles agent orchestration, FastAPI serves the HTTP layer, PostgreSQL with pgvector holds vector state, Protocol Buffers define gRPC service contracts with auto-generated SDKs, `uv` (upgraded from Poetry) manages Python dependencies, and OpenTelemetry auto-instruments FastAPI, HTTP, LangChain, and MCP calls so a single trace stitches together three otherwise siloed observability streams. Model access flows through GrabGPT Gateway — a single OpenAI-compatible API endpoint — so switching models is a config change rather than a code change, and every call inherits centralised rate limiting and audit. Secrets sit in Vault behind INI-file-shaped config. MCP servers are treated as remote runtime capability: adding a tool to an agent does not require redeploying the agent, because the MCP server registers separately and is discovered at runtime.

The evaluation story is the item most agent-platform posts skip. LLM-Kit ships an `/evals` endpoint on every scaffolded service on day one, with golden test cases wired to ROUGE, BLEU, and LLM-as-judge scorers. That means an agent has a regression signal before it has traffic, which is the reverse of the industry norm and closes the loop that usually turns "we upgraded the model" into a two-week production incident. The write-up also flags the practical compromises: services all start on `gpt-4.1` as the initial default, LangGraph diagrams are auto-exported to development environments to give reviewers a visual, and the scaffolding intentionally avoids introducing a new DSL — "the hard part of agent development isn't the reasoning loop itself, but everything around it".

The scale numbers put the pattern in perspective. Over 500 internal agent services in production, 50+ MCP servers on the shared remote framework, billions of tokens per month through one gateway. That is a working answer to the question a lot of platform teams are wrestling with now — one platform-team-plus-scaffolding vs many independent agent stacks — and the answer here is aggressive centralisation on integrations, thin coupling on business logic. Part 2 is trailed to cover MCP server operation and deployment mechanics.

### 🎯 Takeaway (Hợp)
Steal the shape rather than the code: a scaffolded FastAPI + LangGraph template with day-one `/evals`, a single OpenAI-compatible gateway for model access, and OpenTelemetry auto-instrumentation across FastAPI/LangChain/MCP is the highest-leverage design decision for a young agent platform. Skip building your own DSL; solve secrets, tracing, and eval scaffolding first.

### 💡 Example
```python
# Minimal shape of a Grab-style scaffolded agent service.
from fastapi import FastAPI
from langgraph.graph import StateGraph
from opentelemetry.instrumentation.fastapi import FastAPIInstrumentor
from myorg.llm_kit import gateway_client, load_secrets, eval_router

app = FastAPI()
FastAPIInstrumentor.instrument_app(app)
llm = gateway_client(model="gpt-4.1", api_base="https://grabgpt/v1")

graph = StateGraph(dict)
graph.add_node("plan",  lambda s: {"plan": llm.invoke(s["query"])})
graph.add_node("act",   lambda s: {"result": llm.invoke(s["plan"])})
graph.add_edge("plan", "act")
runnable = graph.compile()

@app.post("/run")
def run(payload: dict):
    return runnable.invoke({"query": payload["q"]})

app.include_router(eval_router)  # /evals ships on day one with golden cases
```

### 🔭 Overview (Tổng)
AWS Big Data published a walkthrough on 24 July 2026 for programmatically creating and updating Glue Data Catalog views that expose both ATHENA and SPARK dialects from a single API call, aimed at data-mesh setups where a central governance account owns databases and permissions while producer accounts manage the objects via CI/CD. The problem it solves is quietly common: a view created earlier with only the SPARK dialect cannot be queried from Athena, and until now backfilling the ATHENA dialect required manual console updates on every view. The `UpdateTable` API's new `ADD` and `REPLACE` view-update actions let a pipeline reach into an existing SPARK-only view and add the ATHENA dialect without touching the SPARK definition.

### 🔬 Details (Phân)
The `CreateTable` and `UpdateTable` Glue APIs now accept a `ViewDefinition` that carries multiple `Representations` — one per dialect. SPARK is dialect version 1.0 and unvalidated; ATHENA is dialect version 3 and asynchronously validated against the `VIEW_VALIDATION_ATHENA` Glue connection, which is a one-time prerequisite on the account. Adding an ATHENA representation therefore requires configuring an Athena workgroup and data source in the connection properties and giving the definer role `DESCRIBE` and `CREATE_TABLE` on the target database plus `SELECT` and `DESCRIBE` on the base tables. The `IsProtected: true` flag prevents accidental drop, and SPARK definitions must qualify tables as `<database>.<table>` even when the view is being created in that same database.

The cross-account model is the more interesting piece. In a governance-central data mesh — central account holds catalogs, producer accounts hold pipelines, consumer accounts hold BI — producer pipelines can now assume a definer role in the governance account and issue a single `CreateTable` call that ships both dialects simultaneously. Previously the choice was either create the view manually in the console (breaks CI/CD), create SPARK via SDK and add ATHENA manually later (breaks CI/CD but silently), or duplicate view logic into two API calls with drift risk. The `UpdateTable` `ADD` action solves the mid-life case for the backlog of SPARK-only views already in production.

The write-up is candid that this is an operational unlock, not a new capability. Athena and Spark querying the same view was possible before; automating the multi-dialect creation from a producer-account pipeline in a data mesh was not. That distinction matters for anyone standardising Glue as the central catalog for a large lakehouse — the missing surface for CI/CD-managed views is now closed, which removes one of the last reasons a mesh implementation reaches for a third-party catalog for cross-engine access.

### 🎯 Takeaway (Hợp)
If you own a Glue-central data mesh, add the `VIEW_VALIDATION_ATHENA` connection once per governance account, then update pipelines to emit both `SPARK` and `ATHENA` representations on every new view. For your existing SPARK-only backlog, script a batch `UpdateTable` with `ADD` to bring the ATHENA dialect online without touching consumers.

### 💡 Example
```python
import boto3
glue = boto3.client("glue")

glue.update_table(
    DatabaseName="risk_marts",
    TableInput={
        "Name": "top_customers_view",
        "TableType": "VIRTUAL_VIEW",
        "IsProtected": True,
        "ViewDefinition": {
            "IsProtected": True,
            "Definer": "arn:aws:iam::111122223333:role/definer_role",
            "SubObjects": ["risk_marts.orders"],
            "Representations": [
                {   # existing SPARK dialect stays untouched
                    "Dialect": "SPARK",
                    "DialectVersion": "1.0",
                    "ViewOriginalText":
                        "SELECT * FROM risk_marts.orders LIMIT 1000",
                    "ViewExpandedText":
                        "SELECT * FROM risk_marts.orders LIMIT 1000",
                },
                {   # ADD adds ATHENA alongside; REPLACE would swap it in
                    "Dialect": "ATHENA",
                    "DialectVersion": "3",
                    "ViewOriginalText":
                        "SELECT * FROM risk_marts.orders LIMIT 1000",
                    "ValidationConnection":
                        "glue-view-validation-connection",
                },
            ],
        },
    },
    ViewUpdateAction="ADD",
)
```

# Read 3 analog channels + drive an expander pin + issue an RS-485 query
# on the CirkitScape Top HAT using stock Python libraries.
import time
from smbus2 import SMBus
from gpiozero import DigitalOutputDevice
import serial

# ADS1015 default I2C address = 0x48; use adafruit-circuitpython-ads1x15 in practice
bus = SMBus(1)
for ch in range(3):
    bus.write_word_data(0x48, 0x01, 0xC000 | (ch << 12))
    time.sleep(0.01)
    print(f"ain{ch} raw = {bus.read_word_data(0x48, 0x00) >> 4}")

# MCP23017 at 0x20 -> flip GPA0 high as a relay-drive
bus.write_byte_data(0x20, 0x00, 0x00)     # IODIRA = all outputs
bus.write_byte_data(0x20, 0x14, 0x01)     # OLATA = 0x01

# MAX485 half-duplex query on /dev/ttyS0, RE/DE tied to a Pi GPIO
de = DigitalOutputDevice(17)
with serial.Serial('/dev/ttyS0', 9600, timeout=0.2) as bus485:
    de.on();  bus485.write(b'?VER\r'); bus485.flush(); de.off()
    print(bus485.readline())
