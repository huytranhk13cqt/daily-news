## 1. Espressif Ships Recovery Bootloader in ESP-IDF v5.5+: Second Bootloader Copy Plus eFuse Offset Lets ROM Fall Back After a Failed OTA on ESP32-C5, C61, P4 and S31

### 🔭 Overview (Tổng)
Espressif published a Recovery Bootloader design note on 27 July 2026, authored by embedded software engineer Konstantin Kondrashov, describing a mechanism that finally closes the long-standing brick risk in bootloader OTA. Application OTA already ships two slots and rolls back on failure, but the primary bootloader has historically lived at a single flash location — a corrupted write during an over-the-air bootloader update turns the device into a paperweight. Recovery Bootloader adds a second, known-good bootloader copy at a separate flash region and teaches the ROM to attempt it automatically when the primary one fails verification. Support requires ROM-level cooperation and is therefore limited to ESP32-C5, ESP32-C61 and ESP32-P4 (chip rev ≥ 3.0) on ESP-IDF v5.5+, plus ESP32-S31 on ESP-IDF v6.1+.

### 🔬 Details (Phân)
The developer contract is a menuconfig switch (`CONFIG_BOOTLOADER_RECOVERY_ENABLE`, under "Bootloader config → Recovery Bootloader and Rollback") and a flash offset (`CONFIG_BOOTLOADER_RECOVERY_OFFSET`) that gets burned into an eFuse. The offset-to-eFuse encoding is spelled out explicitly: divide the flash offset by 0x1000 to get the eFuse value, so 0x3F0000 becomes 0x3F0. Partition table gets one new entry of subtype `recovery` in the `bootloader` type, placed in a separate region from the primary. The ROM handles the fallback: on power-up it reads the eFuse pointer, tries the primary, and jumps to the recovery copy if verification fails, all without a running application to babysit the transition. Once booted, `esp_rom_get_bootloader_offset()` tells the application which copy was active so it can decide whether to re-flash the primary.

The OTA sequence itself is deliberately paranoid. Before pulling a new bootloader image, the application backs up the currently-running primary into the recovery partition (`esp_partition_copy(recovery_bootloader, 0, primary_bootloader, 0, primary_bootloader->size)`) and burns the eFuse pointer (`esp_efuse_set_recovery_bootloader_offset(...)`); only then does it write the new bootloader into the primary slot. If the write is truncated or corrupted, the next power-cycle triggers ROM fallback, the previously-good bootloader loads, the app reboots, and code that checks `esp_rom_get_bootloader_offset()` can re-copy from recovery back into the primary slot and try again. Optional monotonic anti-rollback (`CONFIG_BOOTLOADER_ANTI_ROLLBACK_ENABLE`) uses eFuse bit-count encoding to prevent downgrade to a vulnerable prior version — most chips allocate four bits, capping the total number of anti-rollback increments at four across the device lifetime.

There is one meaningful caveat: bootloader OTA cannot run alongside Secure Boot v1 (Secure Boot v2 is required, and even there the sequence needs care with signed images). For an established fleet that has been on ESP-ADF-era ESP32 or on older ESP32-C6/S3 silicon, the feature is not backported — the eligible target list is genuinely the frontier chips only. But for any product shipping today on P4, C5, C61 or S31, adding Recovery Bootloader to the base image before scaling is cheap insurance that removes the largest single risk of doing a fleet-wide bootloader push.

### 🎯 Takeaway (Hợp)
If you are shipping firmware on ESP32-C5, C61, P4 (rev ≥ 3.0) or S31, turn on Recovery Bootloader in your base BSP now, before the fleet grows and a bootloader-CVE forces the first OTA push under pressure. The runtime cost is one extra flash partition plus a menuconfig flag; the payoff is that a bad bootloader OTA becomes a self-healing reboot rather than a support ticket and an RMA truck-roll.

### 💡 Example
```kconfig
# menuconfig excerpt for a P4/C5/C61 project enabling Recovery Bootloader.
CONFIG_BOOTLOADER_RECOVERY_ENABLE=y
CONFIG_BOOTLOADER_RECOVERY_OFFSET=0x3F0000   # eFuse value = 0x3F0000 / 0x1000 = 0x3F0
CONFIG_BOOTLOADER_ANTI_ROLLBACK_ENABLE=y     # optional monotonic downgrade block
```
```
# partitions.csv — add a bootloader-type entry with subtype `recovery`
# Name,             Type,       SubType,   Offset,   Size,   Flags
nvs,                data,       nvs,       0x9000,   0x6000,
otadata,            data,       ota,       0xf000,   0x2000,
recovery_bloader,   bootloader, recovery,  ,         ,
ota_0,              app,        ota_0,     0x20000,  0x1E0000,
ota_1,              app,        ota_1,     ,         0x1E0000,
```
```c
// Bootloader OTA — paranoia-first order: pin recovery, back up primary,
// THEN write the new primary. If the new write is bad, ROM boots recovery.
esp_efuse_set_recovery_bootloader_offset(CONFIG_BOOTLOADER_RECOVERY_OFFSET);
esp_partition_copy(recovery_bootloader, 0,
                   primary_bootloader,  0,
                   primary_bootloader->size);
write_new_bootloader_into_primary_slot();   // if this dies, ROM falls back

// After boot: if recovery ran, restore the primary from the good copy.
if (esp_rom_get_bootloader_offset() != ESP_PRIMARY_BOOTLOADER_OFFSET) {
    esp_partition_copy(primary_bootloader, 0,
                       recovery_bootloader, 0,
                       recovery_bootloader->size);
}
```

### 🔭 Overview (Tổng)
The AWS Big Data blog on 27 July 2026 published a reference-architecture write-up by Amazon's Everyday Essentials team (Shraddha Anil Naik, Sergii Oborskyi, Walter Wong, Shawn Liu) walking through how they evolved a batch-only recommendation system into a hybrid batch-plus-real-time stack that serves "millions of customers" across global marketplaces at "tens of thousands of requests per second" with "sub-millisecond" ANN latency. The interesting bit for DE readers is not the recommendation ML itself but the choreography: how the same weekly MWAA pipeline that used to publish to DynamoDB now also publishes to MemoryDB (Valkey), and how the serving path splits "slow" and "fast" signals between them. It is a concrete, deployed example of the batch-plus-streaming pattern the field has been prescribing on whiteboards for years.

### 🔬 Details (Phân)
The batch pipeline runs weekly under MWAA and moves candidate sets through a fixed chain: Athena over Lake Formation to pull training data, AWS Glue (PySpark) to join/filter/aggregate, SageMaker Training Jobs on ml.g5 GPU instances to fit models, SageMaker Batch Transform to score, and SageMaker Processing Jobs running FAISS distributed via S3 sharding to build the ANN index over hundreds of thousands of candidate products per customer. Results land in DynamoDB for serving with TTL bounding staleness. The team encapsulates each compute pattern behind a custom Airflow operator (`GlueSQLOperator`, `ModelTrainingOperator`, `BatchInferenceOperator`, `VectorSearchOperator`, `GlueSparkOperator`, `DynamoDBPublishOperator`) which is now a rare piece of public prior art for teams designing their own MWAA operator layer — most published examples are one-off DAGs.

The real-time extension is where the architecture becomes interesting. Weekly freshness was not enough to capture what a shopper was doing right now, so the team added an Amazon MemoryDB (Valkey) cluster holding product vectors and a set of SageMaker real-time endpoints that generate on-demand embeddings for the current session. The batch pipeline gained a `MemoryDBPublishOperator` so the same weekly run keeps both stores in sync. The serving ECS Java service asks the SageMaker endpoint for a session embedding, queries MemoryDB for k-nearest-neighbours, and merges that with the DynamoDB batch candidates. Slow signals — purchase history, catalog relationships — flow on the batch path; fast signals — session activity, recent searches, cart adds — flow on the real-time path. The authors are explicit that "batch and real-time are not competing approaches" and note that a batch-generated candidate set stays "largely valid between runs" — what changes at serving time is relative ranking, which real-time re-ranking is cheap enough to do continuously.

The systems-design decisions worth stealing are the S3-as-universal-intermediate pattern (ephemeral Glue/SageMaker jobs pay only for active compute, and every operator hands off through S3 so failures resume mid-pipeline), regional isolation via TaskGroup-per-marketplace so a regional Airflow stall does not cascade globally, and TTL-bounded DynamoDB writes so a stuck pipeline naturally degrades rather than serving indefinitely stale results. Lake Formation with fine-grained cross-account access is the governance backbone; dedicated IAM execution roles per compute engine and VPC isolation across regions are the security backbone. None of these are novel individually — the value of the post is showing them assembled and running at Amazon.com scale.

### 🎯 Takeaway (Hợp)
If you are still batch-only on your recommendation or personalization surface, treat this write-up as the working blueprint for the incremental add: add a Valkey-compatible vector store (MemoryDB, or self-hosted Valkey), publish product vectors into it from the same batch DAG that already publishes to your online store, and put a real-time embedding endpoint in front of it for the current-session signal. You keep the batch investment intact and get the fast-signal loop without rebuilding the pipeline.

### 💡 Example
```python
# Simplified MWAA DAG — batch stages publish to BOTH DynamoDB and MemoryDB
# so the serving layer can merge slow (batch) and fast (real-time) signals.
from airflow.models.dag import DAG
from custom.operators import (
    GlueSQLOperator, ModelTrainingOperator, BatchInferenceOperator,
    VectorSearchOperator, DynamoDBPublishOperator, MemoryDBPublishOperator,
)

with DAG("reco_weekly", schedule="0 6 * * 1", catchup=False) as dag:
    for market in ["us", "eu", "jp"]:                # marketplace isolation
        pull   = GlueSQLOperator(task_id=f"pull_{market}",
                                 sql=f"training_data_{market}.sql")
        train  = ModelTrainingOperator(task_id=f"train_{market}",
                                       instance_type="ml.g5.4xlarge")
        infer  = BatchInferenceOperator(task_id=f"infer_{market}")
        ann    = VectorSearchOperator(task_id=f"faiss_{market}",
                                      shards=32)     # distributed via S3
        pub_dy = DynamoDBPublishOperator(task_id=f"to_dynamodb_{market}")
        pub_mb = MemoryDBPublishOperator(task_id=f"to_memorydb_{market}")

        pull >> train >> infer >> ann >> [pub_dy, pub_mb]
```

### 🔬 Details (Phân)
The stack is deliberately unglamorous: React front end, Python back end, deployed via Databricks Apps; Terraform underneath for cross-cloud infrastructure-as-code; a Lakebase database as the state store that tracks ownership, TTL and purpose per environment. Integration surfaces are Git Runners for the Terraform execution loop, Slack for expiry notifications, corporate identity for authorisation, and — the piece that dates the post to 2026 rather than 2022 — the Model Context Protocol (MCP) so agents can request environments the same way humans do. Engineers pick a template (or an agent asks for one via MCP), configure cloud provider and region, the app fetches the matching Terraform module, the Git Runner applies it, permissions get adjusted, and add-ons (Lakebase, notebooks, Unity Catalog Volumes) are provisioned on top. Default TTL for builder environments is 90 days, configurable for other environment types.

The systems-design lessons are the interesting bit for anyone building their own version. First, put the resource-ownership and lifecycle state in an actual database (Lakebase here) rather than in Terraform state — Terraform state is a description of "what exists", not "who owns it and when should it die". Second, the admin layer for global configuration, quota tuning and full audit is treated as a first-class surface, not a Cron job, because as the fleet grows into thousands of environments the platform team's ongoing operational work is exactly the shape of "which environments should not exist anymore". Third, the persistent catalog lifecycle is decoupled from the workspace lifecycle so that a workspace tear-down does not orphan cataloged data — an obvious-in-hindsight decision that a team building V1 usually misses. Fourth, the audit and attribution posture is treated as a product feature: every provisioning action is logged and attributed, which is what lets the platform team justify centralising the machinery in the first place.

The MCP integration deserves its own note. Making agents first-class clients — able to call the same provisioning API through the same authorisation policy that humans do — pre-empts the anti-pattern where agents get their own back-door provisioning path and the audit trail bifurcates. It also normalises the "who asked for this environment" question: whether the requestor was a human or an agent, the ownership record in Lakebase looks the same, and the TTL and Slack expiry loop behave the same. For any DE or platform team standing up an internal developer platform in 2026, wiring MCP in from day one is a lot cheaper than adding it later once the agent traffic arrives.

### 🎯 Takeaway (Hợp)
For any DE or platform team past the "central platform provisions everything" stage, this is a rare public reference for how to build a vending-machine layer that scales to thousands of environments without abandoning the audit trail. The pieces to lift are: Lakebase-style OLTP for ownership and TTL state, MCP wiring so agent and human requests share one authorisation policy, and treating admin controls as a product surface rather than an operational script.

```python
# FastAPI-shaped sketch of a vending-machine endpoint. The provisioning call is
# identical whether the caller is a human via React or an agent via MCP —
# authorisation, ownership recording and TTL all flow through the same path.
from fastapi import APIRouter, Depends

router = APIRouter()

@router.post("/environments")
def provision(req: ProvisionRequest, principal = Depends(authn)):
    # 1. Policy: same rules for humans and agents; principal.type in {"human","agent"}
    enforce_policy(principal, req.template, req.cloud, req.region)

    # 2. Record ownership + TTL in Lakebase BEFORE calling Terraform, so a
    #    crash mid-apply still leaves an audit trail to clean up later.
    env_id = lakebase.create_env(
        owner=principal.id, template=req.template,
        cloud=req.cloud, region=req.region,
        ttl_days=req.ttl_days or 90, purpose=req.purpose,
    )

    # 3. Hand off to the Git Runner that executes the matching Terraform module.
    git_runner.apply(module=req.template, env_id=env_id, vars=req.vars)

    # 4. Schedule the Slack expiry ping — expiration is a product surface,
    #    not a cron on the side.
    slack.schedule_expiry_ping(env_id, principal.id, days_before=[14, 3, 1])
    return {"env_id": env_id}
```
