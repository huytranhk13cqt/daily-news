### 🔭 Overview (Tổng)
The AWS Big Data blog published a step-by-step release write-up on 28 July 2026 (Bezuayehu Wate, Chuhan Liu, Keerthi Chadalavada, Prasad Nadig, Shubham Mehta, Karthik Prabhakar) for the AWS Spark Upgrade Agent, a Model Context Protocol server that plugs into an MCP-capable IDE — Kiro, VS Code with Cline, or another compatible client — and walks a Scala Spark codebase from Spark 3.x on EMR 6.x to Spark 4.0 on EMR 8.0.0. The team's earlier iteration already covered PySpark; this release closes the Scala gap that had blocked large industrial migrations. The interesting bit for DE readers is that the agent does not just transform source: it also updates the build files, spins up EMR Serverless to run validation against a live cluster, and iterates until the migrated job runs to completion, all inside the same MCP conversation.

### 🔬 Details (Phân)
The workflow decomposes into five phases the agent executes in order. It first generates an upgrade plan by reading the project, then updates build configuration files (`pom.xml`, `build.sbt`) to move Scala to 2.13 and Spark to 4.0, then validates the local environment, then applies targeted code transformations, then runs an end-to-end validation on remote EMR Serverless. Concrete transforms include the Scala 2.12→2.13 collection syntax change (`.to[Set]` becomes `.to(Set)`), Parquet configuration key renames, deprecated-import replacements, and ANSI-mode compliance where cast failures now throw rather than silently produce nulls — the agent rewrites the offending casts to `TRY_CAST` so the semantic behaviour is preserved on the new ANSI default. The demonstration migrates an ecommerce pipeline from Spark 3.3 / Scala 2.12 on EMR 6.9.0 to Spark 4.0 / Scala 2.13 on EMR 8.0.0, and the run finishes with the agent reporting a successful remote validation.

The MCP surface is what makes this different from the previous generation of "script that codemods your project". The agent runs under a scoped IAM role restricted to MCP calls and to an S3 staging bucket, with encryption in transit and CloudTrail auditing on every action. Because the agent is an MCP server, any MCP-capable IDE or agent client can drive it — the AWS write-up shows both Kiro and VS Code+Cline configurations — and the human review of the diffs stays in the IDE the developer already uses. AWS pitches the wall-clock saving as "months of manual work to hours", and while that figure is unaudited, the load-bearing change is that validation happens on the real EMR Serverless runtime instead of in a "compiles, ship it" workflow that pushes discovery of ANSI-mode regressions into production.

Two caveats are called out explicitly and worth budgeting for. EMR 8.0.0 requires Java 17, so any code path that still targets 8 or 11 needs a runtime upgrade in parallel. And ANSI-mode default is genuinely a behavioural change — silently-null-producing casts in Spark 3 will now throw, which is safer but changes downstream semantics; the `TRY_CAST` replacement preserves the null-producing behaviour where teams actually want that, but only where the agent can confidently identify the cast site. Codebases with dynamic SQL or heavy reflection will still need human review before merge.

### 🎯 Takeaway (Hợp)
If you carry any nontrivial fleet of Spark 3.x Scala jobs, this is the moment to trial the Upgrade Agent on one representative pipeline end-to-end — the win is not the code rewrite (existing codemods do most of that) but the free live validation on EMR Serverless before you touch the production cluster. Wire it into a branch build, let it upgrade the pom, apply the Scala 2.13 transforms and run the validation job, and use the diff plus the run log as the artefact your migration ticket links to.

### 🔭 Overview (Tổng)
Databricks posted the production-readiness release for AI Search on 28 July 2026 (Adam Gurary, Sheng Zhan, Ankit Vij, Vadim Antonov, Yu-Ju Huang, Dima Kotlyarov), turning what had been a prototype-friendly vector-search primitive into an autoscaling serving surface parametrised by a single `target_qps` value. The pitch is straightforward: developers stop hand-sizing replicas, provisioning load balancers or running load tests before each launch, and instead declare the target throughput they want the endpoint to sustain. Underneath, Databricks provisions and rebalances compute to hold that number. The change matters because vector-serving load tests have historically been the last unautomated step before a search feature goes to production, and getting it wrong shows up as tail-latency regressions long after the developer has moved on.

### 🔬 Details (Phân)
The `target_qps` parameter is set at endpoint create time or via update through the SDK, REST API or the endpoint UI. Endpoint state exposes a `scaling_info` field that transitions from `SCALING_CHANGE_IN_PROGRESS` to `SCALING_CHANGE_APPLIED`, so pipeline code can wait for the resize instead of guessing at a settle time. Delta Sync stays the recommended path for keeping the index fresh against the source table, and Unity Catalog governance applies as before, meaning the security envelope does not have to be re-planned when you flip a workspace from prototype to production. Observability surfaces requests per second, latency and endpoint-health metrics into the standard production monitors, so an SRE oncall can debug an endpoint the same way they would any other Databricks serving surface.

The load-bearing constraint — the one that is genuinely new for teams — is the authentication distinction. Traffic authenticated with a service principal is routed through what Databricks describes as "performance-optimized networks built for high-QPS production workloads" and can scale to thousands of QPS. Personal-access-token traffic runs on a lower-QPS path and is capped at "a few tens of QPS". This is not a soft recommendation: it changes how you have to wire the calling service. A backend calling AI Search from application code using a PAT will not scale, no matter what `target_qps` says. The migration is to move any real serving path onto a service principal with an appropriate token exchange, and reserve PATs for developer notebooks and one-off scripts.

There is one honest gap in the write-up: no benchmark numbers or explicit latency percentiles are published, and no code snippet is shown for the `target_qps` call itself. The implication is that the numbers depend on index shape, dimension count and query concurrency in ways that would not generalise. The right way to consume the release is to start a target-QPS-declared endpoint against your own index, run your own load pattern through a service principal, watch `scaling_info` reach `SCALING_CHANGE_APPLIED`, then read the P50/P99 out of the built-in monitor. That is now the sizing exercise instead of "provision N replicas by rule of thumb".

### 🎯 Takeaway (Hợp)
For any team currently running a hand-provisioned vector store behind a Databricks pipeline, the immediate action is to migrate the calling service to a service principal, then swap the index for an AI Search endpoint with `target_qps` set to the peak you actually see. Do the swap on the calling side first; the endpoint side is a one-parameter change but the auth-plane migration is where the day of engineering actually goes.

### 💡 Example
```python

# Do NOT call this from a service authenticated with a PAT — the request
# path caps at tens of QPS regardless of the value here.
from databricks.vector_search.client import VectorSearchClient

vsc = VectorSearchClient()
vsc.create_endpoint(
    name="reco_search_prod",
    endpoint_type="STANDARD",
    target_qps=3000,          # <-- new: sizing is now a declared property

# Poll scaling_info until the resize is applied before flipping traffic.

    if ep["scaling_info"]["state"] == "SCALING_CHANGE_APPLIED":
        break
```

### 🔭 Overview (Tổng)
The Zephyr Project blog on 28 July 2026 published a technical talk write-up by Dev Bhaveshbhai Joshi of Qualcomm Technologies (originally presented at Open Source Summit North America 2026) describing how Qualcomm's PMIC (power management IC) software team consolidated two divergent firmware codebases onto a single Zephyr v4.4.0 base. Pre-silicon work had been running on one platform with its own RTOS; production firmware ran on another; the two drifted, which turned pre-silicon validation results into evidence about a different program than the one that would eventually ship. The remedy is unusually clean: one Zephyr codebase, one OS-abstraction layer, two Devicetree targets, and a hardware-in-the-loop test rig built out of a Raspberry Pi Pico so that every pull request must pass on real silicon before it can merge.

### 🔬 Details (Phân)
The architecture is straightforward Zephyr-idiomatic. An OS abstraction layer isolates platform-specific APIs so that the application logic — PMIC control loops, USB-PD negotiation, charging state machines — is compiled unchanged against either target. Two Zephyr variants live in the tree: an upstream flavour for the pre-silicon emulator/FPGA path, and a downstream flavour with vendor-specific driver bindings for the production MCU. Each target owns its own set of Devicetree overlays and Kconfig fragments; the shared code path never has an `#ifdef PRE_SILICON` in it. The team calls out that this discipline is what actually kept the two paths converged — allowing platform-specific application code was where the previous split had started.

The hardware-in-the-loop rig is worth stealing. A Raspberry Pi Pico plays the role of the production MCU, wired over I²C and interrupt lines into a custom PMIC evaluation kit that carries actual silicon plus a USB-C switch for plug/unplug simulation. Zephyr's Twister test runner is driven by a Pytest harness that reads test specifications from YAML — the harness compiles firmware, flashes the Pico, cycles the USB-C switch, and asserts against the PMIC's I²C-visible state, including USB Power Delivery contract negotiation across plug-in/plug-out cycles. Test artefacts (compilation logs, register dumps, PD trace) are preserved in the CI run, so a developer investigating a failing PR does not need physical access to the lab. The Twister/Pytest combo here is a rare public example of a working HIL loop that a small team can actually replicate; most published HIL writeups describe six-figure benches.

The GitHub Actions integration turns the rig into a merge gate rather than a nightly report. A self-hosted runner has USB access to the Pico-plus-eval-kit, and PRs that fail the on-target validation cannot merge. The write-up notes that this discipline let the team do a simultaneous hardware transition (new PMIC silicon) and RTOS transition (from the previous OS to Zephyr) without slipping schedule, because a broken merge never reached the shared branch. Qualcomm has said upstream contributions are queued — USB Type-C Power Delivery drivers, fuel-gauge and charger drivers — so at least some of the enabling code is heading back to mainline Zephyr rather than staying vendor-forked.

### 🎯 Takeaway (Hợp)
For any embedded team maintaining separate pre-silicon and production firmware paths, this is a proof point that Zephyr plus a small HIL rig can collapse them cheaply — the Pi Pico is the load-bearing insight, since it means the emulator side of the split can be a $10 board rather than a bench-class instrument. The transferable pattern is: one Zephyr tree, OS-abstraction layer, per-target Devicetree overlays, Twister-driven Pytest against a HIL runner, and CI wired so merge fails if hardware fails.

```yaml
# Zephyr GitHub Actions runner picks up. The runner has USB access to a

      - CONFIG_USB_PD=y

        - tests/pmic/usb_pd/test_negotiation.py
```

## 4. Databricks Ships Unity AI Gateway Budgets: Dual-Budget Governance Model (Daily Self-Serve Raise via Slack, Monthly Tiered Approval with Auto-Revert) Enforced Once Across Claude, GPT and Gemini Coding-Agent Traffic

### 🔭 Overview (Tổng)
Databricks published an internal-experience write-up on 28 July 2026 (Rohit Agrawal, Shuyu Cao, Darming Zhao, Zack Siegel, Aaron Davidson) describing how they built and now operate Unity AI Gateway Budgets to govern the coding-agent spend of their own engineering organisation. The problem they name is one many enterprises are now seeing: with hundreds of engineers running Claude, GPT and Gemini coding agents against real repositories, a naive single-cap policy generates "hundreds of tickets, hundreds of interrupted work sessions" every month as engineers hit the limit and stall out. Their fix is a dual-budget model — one budget for runaway protection, one for legitimate large workloads — with different approval paths on each. It is the first widely published, opinionated recipe for governing agent spend inside a large company without either grinding engineers to a halt or losing cost control.

### 🔬 Details (Phân)
The dual model separates two failure modes that policy tends to conflate. The daily budget is the runaway-protection layer — its purpose is to catch accidental infinite loops, prompt-injection cost bombs and misconfigured tools before the bill grows over lunch. When an engineer hits 90% of daily, they get a Slack notification with an immediate one-click raise button; there is no approval queue, on the theory that the loop-detection function only needs to make the engineer look at the meter. The monthly budget is the extraordinary-spend layer — it governs "I am doing a legitimately expensive week of coding-agent work on migration X". Monthly raises move through fixed tiers (2×, 5×, unlimited) and go through a manager approval that is time-bounded to a specific project. When the project ends the raise auto-reverts, so exception budgets do not silently become baseline.

The plumbing that makes this uniform across tools is the AI Gateway itself. Because every coding agent — regardless of whether it is Claude, GPT, Gemini or a smaller model — routes through the same gateway endpoint, a single policy is enforced everywhere. The tool the developer picks does not change the budget rules, does not change the runaway protection, does not change how a raise is requested. This is the part worth taking seriously: many enterprises are trying to solve this per-vendor (one policy for Anthropic keys, another for OpenAI keys, another for a local Ollama), and end up with a matrix of budgets that no engineer can predict. Enforcing at the gateway collapses the matrix to one row per engineer per day.

There is a subtle design decision worth noting: daily and monthly are coupled through a fixed ratio, so a monthly raise increases the daily runaway-protection ceiling in step. Without that, raising a monthly budget would leave the daily cap intact and reintroduce the same "engineer hits the wall at lunch" problem the design set out to eliminate; without the coupling in the other direction, an engineer could keep hitting one-click daily raises indefinitely and produce a monthly overrun the manager never saw. The post does not publish the ratio, but the invariant matters: neither budget is meaningful in isolation. The article does not ship code — no policy DSL, no example config — which is the honest limitation to flag; readers wanting the pattern have to derive the policy shape from the description.

### 🎯 Takeaway (Hợp)
For any DE or platform team that has already routed multiple coding-agent providers through a single gateway (or is about to), the actionable takeaway is to design two budgets rather than one, and to give the daily one a self-serve Slack raise rather than a ticket. That single change removes the largest source of preventable engineer-hours-lost-to-cost-guardrails, without giving up the runaway-protection posture that a single monthly cap was trying to provide.

### 💡 Example
```yaml
# Sketch of a dual-budget policy shape at an AI-gateway-fronted org. Daily
# handles runaway protection with self-serve raise; monthly handles genuine
# extraordinary spend with manager approval and auto-revert.
principal: eng-jsmith
gateway:
  routes: [claude, gpt, gemini, local-ollama]   # one policy across all
budgets:
  daily:
    limit_usd: 50
    warn_at_pct: 90
    on_warn:
      notify: slack
      allow_self_serve_raise: true              # 1-click, no ticket
      raise_multiplier: 2
  monthly:
    limit_usd: 500
    tiers: [2x, 5x, unlimited]                  # manager-approved
    require_project_id: true
    auto_revert_on_project_end: true
coupling:
  # raising monthly proportionally lifts daily, so the runaway ceiling
  # stays calibrated during a project week rather than trapping the eng
  daily_from_monthly_ratio: 0.10
```
