## 1. AWS EMR Serverless Adds 32 vCPU / 244 GB Workers and 2 TB Shuffle-Optimized Disks: TPC-H at 1 TB Runs 38.5% Faster and 37.2% Cheaper Against the Previous 4 vCPU Cap

### 🔭 Overview (Tổng)
The AWS Big Data blog announced on 29 July 2026 (Karthik Prabhakar, Arun Maniyan, Neil Mukerje) that EMR Serverless now offers a "large" Spark worker profile up to 32 vCPU and 244 GB of memory, paired with an optional shuffle-optimized disk of up to 2,000 GB — an eight-fold jump on vCPU and a ten-fold jump on shuffle storage over the previous 4 vCPU / 30 GB / 200 GB ceiling. The post is packaged as a customer-facing release note but carries the load-bearing information data engineers actually need: benchmark numbers on TPC-DS and TPC-H, a runnable `spark-submit` snippet, and a plain-language rule for when the larger workers make sense. The change closes the gap that had made EMR Serverless awkward for shuffle-heavy workloads and pushed teams back to provisioned EMR-on-EC2 clusters when their joins fanned out.

### 🔬 Details (Phân)
The published benchmarks cover 126 queries across TPC-DS 3 TB (104 queries) and TPC-H 1 TB (22 queries). Averaged across the full 126-query set, execution ran 29% faster and query-attributed cost fell 29%. Broken out by suite, TPC-DS came in at 26.7% faster and 27.4% cheaper, TPC-H at 38.5% faster and 37.2% cheaper. The peaks matter more than the averages for planning: shuffle-heavy, multi-table joins landed in the 45–55% improvement range, which is where large-worker + shuffle-optimized disks earn their keep. AWS spells out the pricing arithmetic that keeps the cost curve down — the on-demand rate remains $0.052624 per vCPU-hour and $0.0057785 per GB-memory-hour, and shuffle-optimized storage bills at $0.000111 per GB-hour. Because shuffle-optimized disks scale IOPS and throughput with capacity, allocating more shuffle disk is a performance lever rather than a cost lever, and the improvements above hold even after the larger disk allocation is amortised.

The configuration surface is one job property and one disk type. `spark.executor.cores=32`, `spark.executor.memory=220g`, `spark.emr-serverless.executor.disk=2000G` and `spark.emr-serverless.executor.disk.type=SHUFFLE_OPTIMIZED` are the four lines an operator adds to a `spark-submit` invocation to move onto the new profile. Prior behaviour split each Spark stage across many small workers, which multiplied network shuffle between them; with a 32-core executor, more of the shuffle stays inside the process boundary, and the shuffle-optimized disk absorbs what does spill. AWS positions this as a first-class option rather than a preview, which means job templates in serverless application configurations can now request it directly.

Two caveats deserve budgeting for. Not every workload benefits: CPU-bound queries with narrow dependencies (map-only pipelines, small aggregations) will not move on wall clock and will pay for capacity they do not use, so the recommendation is to profile before promoting a job. And the larger workers do not remove the standard EMR Serverless application-level caps on maximum vCPU or memory — those still bound how many 32-core workers a job can hold in flight at once, so aggressive parallelism still needs an application quota increase. The blog is honest about scope: it demonstrates the perf/cost delta and the snippet, but does not publish the raw query traces or per-query latencies, so validation against your own workload remains the pattern.

### 🎯 Takeaway (Hợp)
If any Spark job on EMR Serverless has been slow because of shuffle spill — heavy joins, wide window functions, large `GROUP BY` cardinalities — the actionable move today is to duplicate the job configuration, add the four executor properties above, and rerun against the same input. The upside case shown in the benchmarks (38% faster / 37% cheaper on TPC-H) is large enough that the profiling exercise pays for itself on any job that survives the trial.

### 💡 Example
```bash
# Move an existing Spark job onto EMR Serverless "large" workers with
# a shuffle-optimized disk. The four executor properties are additive to
# the rest of the job's --conf set; nothing else in the job needs to change.
aws emr-serverless start-job-run \
  --application-id "${APPLICATION_ID}" \
  --execution-role-arn "${ROLE_ARN}" \
  --job-driver '{
    "sparkSubmit": {
      "entryPoint": "s3://my-bucket/jobs/etl_join.py",
      "sparkSubmitParameters": "
        --conf spark.executor.cores=32
        --conf spark.executor.instances=6
        --conf spark.executor.memory=220g
        --conf spark.emr-serverless.executor.disk=2000G
        --conf spark.emr-serverless.executor.disk.type=SHUFFLE_OPTIMIZED
      "
    }
  }'
```

### 🔭 Overview (Tổng)
Confluent published the release write-up for Confluent Platform 8.3 on 29 July 2026 (Julian Payne, Surabhi Singh, Anjan Kumar B R, Premika Srinivasan). The version bundle wraps Apache Kafka 4.3.0, Confluent Manager for Apache Flink (CMF) 2.4.0, Confluent for Kubernetes (CFK) 3.3.0 and USM Agent 1.2.0 into one platform drop. Three lines of work land at once: Flink SQL operations gets a materially more capable control surface (including an MCP server that AI agents can drive), the KRaft-migration path opens up for 2.5-datacenter (2.5DC) topologies that had previously been a blocker for ZooKeeper-only shops, and the Kubernetes operator lets teams change quorum size without rolling brokers. It is a broad release rather than a headline single feature, but each of the three pieces removes a real operator pain point.

### 🔬 Details (Phân)
The Flink piece is where the interesting engineering sits. CMF 2.4.0 ships a Model Context Protocol server that exposes what the release describes as over 16 read-only debugging tools and 20 write tools for managing Flink resources, so a coding agent like Claude Code can inspect jobs, apply DDL, and edit resources without the operator switching to a UI. Alongside the MCP surface, Flink SQL now supports Java UDFs registered directly in SQL workflows, an artifact-management model for storing and versioning SQL extensions across environments, and custom catalogs so Flink SQL can query non-Kafka sources such as Amazon S3 or blob storage. RBAC and authentication move into an embedded Metadata Service so the Flink control plane can enforce identity end-to-end, and periodic savepoints get scheduled and retained automatically. The Confluent Control Center integration for Flink is retired in favour of a dedicated CMF UI — worth flagging on the migration checklist because dashboards that pointed at the old integration will need rebuilding.

KRaft migration is the second thread. Two changes matter operationally: the migration path now supports 2.5-datacenter deployments with a lite-mode tiebreaker site, and a pre-check utility validates ZooKeeper metadata before a single-cluster migration begins. The 2.5DC support is the load-bearing addition — teams with an active-active pair plus a witness that had been waiting on KRaft-migration tooling can now schedule the cutover. On the Kubernetes side, CFK 3.3.0 supports dynamic quorum scaling without broker restarts, which turns "expanding the KRaft quorum" from a rolling operation into a live one. Monitoring gains a Kafka Streams UI for application discovery and health, and USM Agent 1.2.0 adds client-side observability that surfaces producer and consumer behaviour without needing to instrument the client. Governance-wise, schema IDs can now travel in Kafka headers rather than the message payload, which decouples schema-metadata evolution from producer/consumer code changes, and CPC Gateway Governance enters early access for centralised enforcement of encryption, schema validation and data-quality policies.

The honest limitation of the release note is that it stays at feature-description altitude and does not ship code snippets or migration scripts inside the post — screenshots of the new CMF UI substitute for the CLI walkthroughs an operator would want. The version compatibility matrix is the piece to lift straight out: CP 8.3 requires CFK 3.3.0 for the dynamic quorum-scaling capability, and CMF 2.4.0 requires either CP 7.6+ or Confluent Cloud on the metadata side. Environments running older CFK will get most of the CP 8.3 features but not the live quorum-resize path.

### 🎯 Takeaway (Hợp)
For teams already on Confluent Platform 8.x, the KRaft-migration additions plus CFK 3.3.0's live quorum-resize are the ops wins to schedule first — the Flink SQL operational upgrades are attractive but need CMF 2.4.0 in place. If you have not yet moved to KRaft because your topology was 2.5DC, this is the release that finally offers a supported path.

## 3. Arduino Core on Zephyr Hits 0.90.0 Stable: Nano RP2040 Connect Joins the Roster, SD Card Support Lands on Portenta H7/C33, PDM Digital Microphone Reaches the Nano 33 BLE, and IDE-Driven Loader Sync Retires the Manual mbedOS-to-Zephyr Switch

### 🔭 Overview (Tổng)
Arduino announced on 29 July 2026 that Arduino Core on Zephyr, the runtime that lets standard Arduino sketches execute on top of Zephyr RTOS while giving developers full RTOS capabilities underneath, is officially stable at 0.90.0 and out of beta. The framing matters: for the last year the Zephyr-backed core has been an opt-in path for developers who wanted preemptive scheduling, richer driver support and better vendor alignment on newer silicon, but the beta label kept it out of production plans. Version 0.90.0 flips that. The beta exit brings a new board (Nano RP2040 Connect), lifts limitations that had blocked practical projects on already-supported boards (SD card on Portenta H7 and C33, PDM microphone on Nano 33 BLE), and shifts the mbedOS-to-Zephyr transition from a manual procedure into an IDE-driven, per-board sync.

### 🔬 Details (Phân)
The supported-board list at 0.90.0 covers UNO Q, Portenta H7 and C33, Opta microPLC, GIGA R1 WiFi, Nano Matter, Nano 33 BLE, Nicla Sense ME and Nicla Vision, with Nano RP2040 Connect added in this release. Two hardware capability gaps also close in 0.90.0. Portenta H7 and C33 gain SD card support, which is the missing piece for local data logging on those two boards. Nano 33 BLE gains PDM library support — pulse-density-modulation microphone input at the driver level — enabling audio sampling, noise detection and edge-AI voice workloads that had previously required either a companion board or a fork of the core. Both additions are pragmatic; neither is glamorous release-note material, but both remove concrete blockers that had been keeping projects on the legacy core.

The IDE-side change is the one that most directly reduces friction for existing users. The 0.90.0 release introduces automatic loader-and-sketch synchronization, meaning a board that has been running an mbedOS-based sketch can be switched onto the Zephyr core and the Arduino IDE will handle the loader update as part of the next upload — no separate loader flash, no manual firmware juggling. For anyone who has been putting off the migration because the loader step was fiddly across a fleet of dev boards, this is the release where the switch becomes a one-click operation. Installation is unchanged: Board Manager, search for "zephyr", install 0.90.0, and the Zephyr-based variants appear in the board list.

The release notes do not explicitly enumerate remaining limitations, which is worth flagging: not every Arduino library ports cleanly across the RTOS boundary, and code paths that assumed cooperative scheduling on the previous core will behave differently under Zephyr's preemptive scheduler. The published migration guide covers the loader-flash step for existing hardware, but pattern-level guidance for adapting sketches that touched timing-sensitive interrupts is left to the developer. For teams evaluating adoption, the practical move is to take one representative sketch per target board, run it under 0.90.0 on hardware, and validate against the specific peripheral APIs (timers, interrupts, low-level GPIO) the project depends on.

### 🎯 Takeaway (Hợp)
For any Arduino project sitting on the mbedOS-based core specifically because Zephyr Core was still in beta, 0.90.0 is the release to plan the migration around — the loader sync alone changes what had been a per-board manual chore into an IDE upload. Teams building edge-AI on Nano 33 BLE or data-logging appliances on Portenta H7/C33 should treat the new PDM and SD paths as the moment those projects become natively feasible on the mainline Arduino toolchain.

### 💡 Example
```cpp
// Nano 33 BLE, Arduino Core on Zephyr 0.90.0.
// The PDM library now works natively — no companion board, no core fork.
// This sketch samples the on-board digital microphone into a buffer that
// downstream edge-AI code (e.g. TinyML voice detection) can consume.
#include <PDM.h>

static const int   channels        = 1;
static const int   frequency       = 16000;   // 16 kHz mono
static short       sampleBuffer[512];
static volatile int samplesRead    = 0;

void onPDMdata() {
  int bytesAvailable = PDM.available();
  PDM.read(sampleBuffer, bytesAvailable);
  samplesRead = bytesAvailable / 2;
}

void setup() {
  Serial.begin(115200);
  PDM.onReceive(onPDMdata);
  if (!PDM.begin(channels, frequency)) {
    Serial.println("Failed to start PDM");
    while (1) {}
  }
}

void loop() {
  if (samplesRead) {
    // Hand samples to the inference stage (out of scope for this snippet).
    samplesRead = 0;
  }
}
```
