### 🔭 Overview (Tổng)
The AWS Big Data blog announced on 30 July 2026 (Shakhi Hali, Mazrim Mehrtens, Huyam Hasan) that Amazon MSK Express brokers can now materialize any Kafka topic continuously into an Apache Iceberg table on Amazon S3 Tables, without any Kafka Connect deployment, custom consumer, or downstream Flink job. The path Kafka teams have spent the last two years wiring by hand — sink connector, exactly-once configuration, compaction service, catalog registration — collapses into a console workflow and an API call. The feature is framed as a first-class MSK capability rather than a preview, and it targets the specific gap that had kept many teams on self-managed sink connectors: the operational overhead of keeping streaming ingest, exactly-once, file sizing, and catalog registration coherent across a growing topic list.

### 🔬 Details (Phân)
Under the hood, MSK owns the write coordination and the file layout. The service handles exactly-once delivery from the Kafka log into Iceberg, performs inline compaction to produce query-optimised Parquet files, and registers each table in AWS Glue Data Catalog so query engines see it automatically. The claimed economics are two independent numbers: "up to 60% cost savings compared to self-managed alternatives" on the ingest path itself, and "up to 30% reduction in downstream query costs" attributed to the inline compaction producing files sized for the downstream engines rather than raw log-scale micro-batches. Throughput is documented as scaling automatically "to process gigabytes per second" per streaming table.

Setup is deliberately narrow. From the MSK console the operator picks a Kafka topic, configures schema handling through AWS Glue Schema Registry, and chooses either an S3 Tables destination (fully managed Iceberg) or a general-purpose S3 bucket. Programmatic control is exposed through the standard MSK API surface. AWS also ships a companion Agent Skill named `managing-amazon-msk` that lets a coding agent perform the same wiring conversationally — prompts like "create me a streaming table on my MSK cluster for my events topic" resolve into the same API calls, which is a meaningful shortcut for platform teams standardising on agent-driven ops.

Query-side coverage is broad from day one: Amazon Athena, Amazon Redshift, Amazon EMR (Spark) and Apache Flink can all read the resulting tables directly through the Glue catalog. The unsurprising caveat is that streaming tables are read-only from the query side — writes go through Kafka, and any late-arriving-data or backfill pattern that expects to `UPDATE` the table in place has to reroute through the topic. The blog does not spell out latency guarantees or schema-evolution handling for backwards-incompatible schema changes; both are worth verifying on your own workload before making streaming tables the default sink.

### 🎯 Takeaway (Hợp)
Any team currently running a Kafka Connect Iceberg sink, a Flink Table Store pipeline, or a custom Spark structured-streaming consumer purely to land topic data as Iceberg should benchmark this against the self-managed setup on one representative topic before adding the next one. The 60% ingest cost lever plus removal of a whole Connect cluster from the ops surface is the sort of change that pays for the migration itself once more than a handful of topics are involved.

### 💡 Example
```bash
# Enable streaming-tables materialization for an existing MSK Express topic.
# Once created, the Iceberg table is queryable via Athena/Redshift/EMR/Flink
# through the AWS Glue Data Catalog with no additional wiring.
aws kafka create-streaming-table \
  --cluster-arn "${MSK_CLUSTER_ARN}" \
  --topic-name "orders.v1" \
  --destination-type S3_TABLES \
  --s3-tables-bucket-arn "${S3_TABLES_BUCKET_ARN}" \
  --schema-registry-arn "${GLUE_SCHEMA_REGISTRY_ARN}" \
  --table-name "orders_stream"

# Query the freshly materialized table from Athena — no Connect cluster,
# no Flink job, no compaction cron. MSK owns exactly-once + file sizing.
aws athena start-query-execution \
  --query-string "SELECT order_id, total_cents, event_time
                  FROM iceberg.default.orders_stream
                  WHERE event_time > current_timestamp - interval '5' minute" \
  --result-configuration "OutputLocation=s3://my-athena-results/"
```

### 🔭 Overview (Tổng)
On 30 July 2026 the AWS Big Data blog published a technique guide by Navaneedha Krishnan Jagathesan on lowering AWS KMS Decrypt API costs for Spark jobs on Amazon EMR. The post targets a cost pattern that only becomes visible on the KMS invoice rather than on EMR itself: every Spark task that reads an encrypted S3 object triggers a KMS Decrypt call, and at scale those calls turn into an unbudgeted line item. The guide is specifically written for the constraint that makes the usual answer — enabling S3 Bucket Keys — off-limits, namely compliance requirements that need per-object key identifiers to appear in CloudTrail for audit.

### 🔬 Details (Phân)
The playbook recommends four levers that stack, and it does so with concrete Spark configuration rather than architectural sketches. The first is data aggregation via `coalesce()`, consolidating many small files into a smaller number of larger blocks before the write — the code sample uses `data.coalesce(10).write.mode("overwrite").parquet(...)`. Because each written S3 object is one Decrypt invocation on the way back in, cutting object count is the most direct KMS-call reduction available. The second lever is columnar format plus compression: converting CSV to Parquet with Snappy via `spark.conf.set("spark.sql.parquet.compression.codec", "snappy")` before the write reduces both the number of files and their footprint, and the post's charts show the Decrypt-call curve dropping sharply when moving from uncompressed CSV to compressed Parquet.

The third lever is Apache Iceberg. Iceberg's automatic file-layout optimisation and ZSTD-by-default compression produce fewer, better-sized objects than raw Spark writes; the guide positions it as the format to pick if you are also planning schema evolution, time travel, or partition evolution on the same dataset. The fourth is Glue Data Catalog partition indexes, which push partition filtering to the server side so Spark only lists (and thus only decrypts) the objects that actually match the query predicate — an entirely orthogonal reduction that stacks with the write-side levers above.

The one honest gap in the write-up is calibration: it shows the direction of impact on chart form but does not put a dollar figure on any of the four techniques, and the CloudTrail-auditability constraint (the whole reason the post exists) is not accompanied by a decision tree for when the audit requirement can actually be relaxed in favour of S3 Bucket Keys. Teams should treat the four techniques as a stacked recipe rather than an either/or, and measure the KMS spend before and after on their own workload rather than budget the improvement from the article.

### 🎯 Takeaway (Hợp)
If your EMR + KMS bill has crept up over the last quarter and S3 Bucket Keys are off the table for compliance reasons, this playbook is the shortest path from problem to concrete Spark config change. Batch a small proof: pick one high-frequency job, apply `coalesce()` + Snappy Parquet, then layer Iceberg or partition indexes if the format story allows — the delta on the KMS invoice will be visible inside a billing cycle.

### 💡 Example
```python
# The stacked recipe from the AWS post: fewer files (coalesce), smaller
# footprint (Snappy Parquet), and server-side pruning (Glue partition
# indexes). Each KMS Decrypt call maps 1:1 to an encrypted S3 object read,
# so cutting object count is a direct KMS bill reduction.
from pyspark.sql import SparkSession

spark = (
    SparkSession.builder
        .appName("kms-cost-aware-etl")
        .config("spark.sql.parquet.compression.codec", "snappy")
        .config("spark.sql.sources.partitionOverwriteMode", "dynamic")
        .getOrCreate()
)

df = spark.read.csv("s3://bucket/raw/events/", header=True, inferSchema=True)

(
    df.coalesce(10)                         # fewer output files → fewer Decrypts on next read
      .write.mode("overwrite")
      .partitionBy("event_date")            # aligns with Glue partition indexes
      .parquet("s3://bucket/optimized/events/")
)
```

### 🔭 Overview (Tổng)
Jonathan Brito announced on the Databricks blog on 30 July 2026 that Genie Code — Databricks' agentic coding surface — now drives the SQL-migration workflow on Lakebridge, converting proprietary SQL dialects into open ANSI SQL runnable on the lakehouse. The dialects covered in the initial release are T-SQL, Snowflake, Redshift, Oracle, BigQuery and Teradata, which is the practical superset of what migration engagements actually hit. The framing positions Genie Code as the successor to the manual, per-dialect conversion consulting engagement — Lakebridge has, per Databricks, been used by more than a thousand customers since its 2025 launch, and the addition of Genie Code turns that from a tool assisted by humans into a workflow assisted by parallel agents.

### 🔬 Details (Phân)
The engineering claim is that Genie Code "launches swarms of parallel agents that iteratively convert code, validating syntax and semantic intent" rather than acting as a single-pass translator. The parallelism matters because SQL migration is embarrassingly parallel at the file level but tightly coupled at the object-dependency level: a stored procedure references tables, views, functions and other procedures, and a translation that gets the syntax right but the semantic dependency wrong is a silent bug. Genie Code layers three practical features on top of the raw translation: complexity scoring that lets teams sequence the migration from easiest to hardest, automated lineage mapping across object dependencies so a rename in one file cascades correctly, and a custom-skill mechanism so organisation-specific naming conventions or stylistic rules can be baked into the agent.

The evidence in the post is a proof-of-concept walkthrough where 6 of 8 input files converted cleanly and end-to-end, and 2 required manual review. The failure mode on the two files is called out explicitly: Unity Catalog requires stored procedures to be addressed with three-part qualified names (`catalog.schema.object`), and the source files used single-part or two-part references that the agent chose not to rewrite without human confirmation. That is a concrete number engineering managers can plan against: expect roughly 75% clean conversion on realistic input, with the residue concentrated on catalog-naming rules the agent will not silently invent for you. Enterprise SQL features the post confirms are handled include multi-statement transactions, temporary tables and stored procedures.

The honest limitation is that a single walkthrough on 8 files is not a benchmark, and Databricks does not publish a broader accuracy table across the six dialects. Migration engagements will still need a review stage, and the value proposition is the reduction in reviewer effort rather than elimination of the reviewer role.

### 🎯 Takeaway (Hợp)
For teams evaluating a lakehouse move from Snowflake, Oracle or a legacy Teradata warehouse, the practical experiment is to run Genie Code over a bounded slice — 20 to 50 files covering the top three object types you use — and measure both the clean-conversion rate and the type of manual fix needed on the residue. If those manual fixes are catalog-naming rather than semantic, the tool is doing its job and the remaining work becomes a checklist rather than a translation project.

### 💡 Example
```sql
-- Before: T-SQL stored procedure with two-part naming, MERGE syntax and a
-- SQL Server-specific system function. Lakebridge + Genie Code rewrites
-- this into ANSI SQL that runs on the Databricks lakehouse; the two-part
-- reference is exactly the pattern that requires human review under
-- Unity Catalog's three-part naming rule (catalog.schema.object).
CREATE PROCEDURE sales.upsert_daily_totals AS
BEGIN
  MERGE INTO sales.daily_totals AS tgt
  USING (
    SELECT store_id, CAST(GETDATE() AS DATE) AS day, SUM(amount) AS total
    FROM sales.transactions
    WHERE tx_time >= CAST(GETDATE() AS DATE)
    GROUP BY store_id
  ) AS src
  ON tgt.store_id = src.store_id AND tgt.day = src.day
  WHEN MATCHED THEN UPDATE SET total = src.total
  WHEN NOT MATCHED THEN INSERT (store_id, day, total)
                       VALUES (src.store_id, src.day, src.total);
END;
```

### 🔭 Overview (Tổng)
The Zephyr Project cut v4.4.2-rc1 on 29 July 2026, a pre-release candidate for the 4.4 stabilisation branch that bundles more than 126 GitHub issues worth of fixes. The headline change is a fix for a thread-safety race in `net_buf_unref` (#106334) — a kernel-level synchronisation bug in the network buffer subsystem that any application using the Zephyr networking stack is exposed to. Even though the release is an RC and not the final 4.4.2, the concentration of security-relevant fixes across Bluetooth, networking, WireGuard and USB paths makes it worth reading now rather than after the final tag lands. No CVE identifiers are published in the release notes; fixes are referenced by GitHub issue numbers only.

### 🔬 Details (Phân)
Networking is where the most memory-safety-relevant fixes land. The WireGuard implementation gets patches for both replay handling and a linearization buffer overflow — either of which is exploitable in the traditional sense on any device exposing a WireGuard endpoint. ICMPv6 gains proper source-address validation to align with RFC 4443, closing a family of spoofing vectors that had been possible against Zephyr-based hosts on IPv6 links. Additional networking fixes cover DNS timeout handling and socket cleanup, IPv6 hop-limit decrement on forwarded packets, and a socket leak in the HTTP server that would otherwise strand file descriptors over time.

Bluetooth and audio receive a coordinated batch: BAP unicast client NULL-pointer paths, GATT notification and indication permission checks that were previously permissive, ISO stream SDU header validation, and general host qualification tightening. On the driver side, ESP32 and ESP32-S3 users get PSRAM and Wi-Fi heap mapping corrections that matter for any board using external PSRAM — the previous mapping could interact poorly with the Wi-Fi subsystem's heap allocations. STM32 flash and USB handling improves, and the I2C, SPI and UART async paths pick up fixes that have been landing on the main branch for a few weeks. In the kernel proper, userspace thread index allocation races are addressed alongside pipe and queue synchronisation improvements.

The scope of the release is worth naming: this is an RC, and the release notes reference GitHub issue numbers rather than CVE identifiers. That means detection tooling that maps installed Zephyr versions to CVEs will not flag anything specific here, and any downstream vendor SBOM will need to be updated by version comparison rather than CVE cross-reference. Teams shipping products on the 4.4 LTS branch should track the final v4.4.2 tag, but starting rc1 in QA is defensible now given the memory-safety density.

### 🎯 Takeaway (Hợp)
If your product is on Zephyr 4.4.0 or 4.4.1, treat v4.4.2-rc1 as the branch to promote through your CI and hardware regression rig this week — the networking fixes in particular are ones you do not want to defer until the next feature release. Bake the RC on the same hardware-in-the-loop bench you would use for the final tag, so promotion to v4.4.2 stable is a version bump rather than a fresh integration cycle.
