### 🔭 Overview (Tổng)
The AWS Big Data blog announced on 31 July 2026 (Amit Maindola, Bret Pontillo, Mukesh Punhani and Vishal Vyas) that Amazon EMR on EC2 has added an Advanced Managed Scaling mode with an explicit utilization-versus-performance slider. Until this release EMR customers had two positions: default Managed Scaling, which optimises performance first and cost second on a fixed policy, and custom autoscaling rules, which recover fine-grained control at the price of shuffle-data loss and Application Master termination when the rules scale in too aggressively. Advanced Scaling closes that gap by exposing a single knob, `UtilizationPerformanceIndex`, that lets operators declare their preference and lets EMR translate that intent into scaling decisions without giving up the safety guarantees Managed Scaling already provides.

### 🔬 Details (Phân)
The knob takes an integer from 1 to 100. An index of 1 (Utilization Optimized) scales conservatively, is suited to recurring spikes and cost-focused workloads, and errs toward keeping the cluster small. An index of 50 (Balanced) sits in the middle for steady workloads with mixed stage durations. An index of 100 (Performance Optimized) scales aggressively for SLA-sensitive jobs. Underneath the slider, EMR continuously evaluates pending Spark tasks, memory pressure and executor demand to decide when to add or remove nodes, and it inherits shuffle awareness and Application Master protection from the standard Managed Scaling code path, so aggressive scale-in still avoids the two failure modes that made custom rules fragile.

The blog attaches a 3TB TPC-DS benchmark on the same cluster shape to make the tradeoff concrete. At index 1 the run peaked at 50 nodes and finished in 840 seconds; at index 50 the run held to 48 peak nodes and finished in 780 seconds; at index 100 the run peaked at 50 nodes and finished in 660 seconds. Runtime dropped about 27 percent from cost-optimised to performance-optimised on this workload, with the intermediate Balanced setting recovering roughly two-thirds of the gain at essentially the same peak footprint as Utilization Optimized. The control surface is a `put-managed-scaling-policy` call with `ScalingStrategy: ADVANCED` and the chosen index; existing `ComputeLimits` (min and max capacity units) keep their meaning.

Operationally the release matters most for shops that already run recurring EMR jobs on a schedule and have been tuning custom autoscaling rules to squeeze cost. Those rules can be retired in favour of a single index expression, which is much easier to review, audit and change per environment. The obvious caveat is that Advanced Scaling is an EMR on EC2 feature — teams standardised on EMR Serverless get their scaling from a different code path — and the 27 percent number is TPC-DS on a specific dataset shape, not a universal ceiling; measure on a representative workload before promoting an index change into production policy.

### 🎯 Takeaway (Hợp)
If you maintain custom autoscaling policies on EMR on EC2 today, the shortest experiment is to reproduce one representative daily job under Advanced Scaling at indices 1, 50 and 100, capture runtime and cost against the current policy, and pick the point on the curve that matches the SLA you actually owe. Encoding cluster scaling policy as a single integer per environment is a meaningful simplification for the platform team and a policy change that runbook reviewers can reason about without re-deriving the rule set.

### 💡 Example
```bash

# is the only knob that changes when you re-tune the policy per env.

  --cluster-id "${EMR_CLUSTER_ID}" \
  --managed-scaling-policy '{
    "ComputeLimits": {
      "UnitType": "Instances",
      "MinimumCapacityUnits": 2,
      "MaximumCapacityUnits": 50
    },
    "ScalingStrategy": "ADVANCED",

  }'
```

## 2. DuckDB v2.0-dev Ships Asynchronous I/O for Parquet and CSV with a Work-Thread-Work Model: 22GB Single-File Parquet Reads 2.9x Faster, 80GB CSV Scans 19.4x Faster on r7i.16xlarge, and Concurrent-Query CPU Utilization Jumps from 5.9 to 48.1 Cores

| Field | Value |
|---|---|
| 📅 Date | 31/07/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `duckdb` · `async-io` · `parquet` |

### 🔭 Overview (Tổng)
DuckDB engineer Pedro Holanda published a deep dive on 31 July 2026 describing the asynchronous I/O implementation landing in the upcoming DuckDB v2.0 release, targeted for autumn 2026. The change is architectural rather than cosmetic: DuckDB has historically used blocking reads on the worker threads that also do compute, which meant that any query bound by remote object-store latency left CPU cores idle waiting for bytes to arrive. The new work-thread-work model separates fetch from compute across two thread pools and adds a read-ahead queue so that remote scans on Parquet and CSV are prefetched while the compute pool is still busy on the current row group or byte range.

### 🔬 Details (Phân)
The runtime keeps two pools. The REGULAR pool has one worker thread per CPU core and owns all computation. A new ASYNC pool defaults to four times the system thread count, capped at 256, and owns every operation that can block on I/O. Jobs are granular: one row group per Parquet job and a fixed byte range per CSV job. Instead of issuing a fetch only when a worker needs the data, DuckDB schedules fetch tasks for jobs that lie further ahead in the scan plan, with a shared countdown so the last fetch to complete flips the job into a state the compute pool can pick up. A single new configuration, `read_ahead_depth`, controls how many jobs can be in flight — `-1` (the default) lets the temporary memory manager bound the queue, a positive integer caps in-flight jobs, and `0` reverts to the old synchronous path.

The benchmark section is where the case becomes concrete. On an EC2 r7i.16xlarge (64 vCPUs) reading from S3, a single 22 GB Parquet file drops from 8.230 s on v1.5.5 to 2.844 s on v2.0-dev — roughly 2.9x faster — and tuned settings push it further to 2.227 s (about 3.7x). An 80.89 GB CSV scan collapses from 877.563 s to 45.264 s, a 19.4x improvement that reflects how badly the previous blocking path punished byte-range-oriented formats over the network. A partitioned dataset of 976 Parquet files goes from 9.344 s to 2.945 s (~3.2x). The clearest concurrency evidence comes from running four TPC-H queries at once: average CPU utilisation moves from 5.9 cores (roughly 90 percent idle) to 48.1 cores, network throughput saturates from 10.7 Gbit/s to 24.9 Gbit/s, and total runtime drops from 35.8 s to 15.6 s.

Local storage is a smaller but real win: cold reads on a MacBook Pro M4 Max drop from 1.321 s to 0.883 s (about 1.5x). Holanda calls out that DuckDB is still evaluating `io_uring` on Linux to further reduce syscall overhead, and that async support will extend beyond Parquet and CSV to JSON and the DuckDB native format in later releases. The most useful practical note is that data-lake users on Parquet and CSV get the benefit automatically once v2.0 ships — no query rewrites, no schema changes, just a version bump and, optionally, one line to tune `read_ahead_depth`.

### 🎯 Takeaway (Hợp)
If your DuckDB workload spends any meaningful fraction of wall clock reading Parquet or CSV from remote object storage, put v2.0-dev on the same benchmark you used to justify the current instance size and see whether you can drop a tier. The concurrent-query numbers matter more than the single-scan headline: workloads that fan several DuckDB queries at once against the same lake are the ones that will see the CPU-utilisation curve straighten out and the network pipe finally get saturated.

### 💡 Example
```sql
-- The knob is optional: -1 (default) lets the temp memory manager cap
-- in-flight I/O, a positive integer sets an explicit depth, 0 falls
-- back to the old blocking path if you need to A/B against v1.5.5.
SET read_ahead_depth = 5;

-- Same query as before — the async pool prefetches row groups while
-- the compute pool is still busy on the current one. On remote S3
-- scans this is where the 2.9x-19.4x speedups come from.
SELECT
  l_returnflag,
  l_linestatus,
  SUM(l_quantity)                                     AS sum_qty,
  SUM(l_extendedprice * (1 - l_discount))             AS sum_disc_price
FROM read_parquet('s3://my-lake/tpch/lineitem/*.parquet')
WHERE l_shipdate <= DATE '1998-09-01'
GROUP BY l_returnflag, l_linestatus
ORDER BY l_returnflag, l_linestatus;
```

### 🔭 Overview (Tổng)
Cameron Casher, Shanil Anushka Fernando and Kevin Hartman published part three of the Backstage-on-Lakebase series on the Databricks blog on 31 July 2026, subtitled "The one-query FinOps solution." Backstage is Spotify's developer portal, and the previous two posts covered running it on Lakebase — Databricks' PostgreSQL-compatible operational database — with per-workload compute isolation, one-second database branching for CI, and lakehouse-federated reads of analytical data. Part three closes the loop on cost visibility: the same Postgres catalog that already stores ownership and dependency data for every service in the developer portal can be joined directly against the Lakehouse billing tables, and a single SQL query returns the actual DBU spend broken out by team and branch, with no ETL pipeline between the operational and analytical planes.

### 🔬 Details (Phân)
The mechanism is Lakehouse Federation reading the live Postgres tables that Backstage populates as its catalog, joined against `system.billing.usage` in Unity Catalog. Because Lakebase surfaces a real Postgres endpoint and Unity Catalog federation understands the Postgres wire protocol, the join happens as a single SQL statement rather than a scheduled export. The post also puts numbers behind the compute-isolation claim from earlier parts: with a portal workload and an analytical query running against the same Lakebase, portal catalog queries measure at 55–65 ms end-to-end and search queries at 2–4 ms, i.e. the analytical join does not disturb the operational latency budget. The billing side benefits from Lakebase's per-branch accounting: test branch usage shows up as a discrete row (an example in the post is 0.0107 DBU for a short-lived branch) so CI cost and production cost can be separated without owning a cost-allocation tag scheme.

The one honest gap is authentication. Lakehouse Federation currently only supports static username-password credentials against the federated Postgres, not OAuth JWTs. Teams that authenticate humans to Lakebase over OAuth need a parallel identity for the federation path, and the post's recommended pattern is a native Postgres role using SCRAM-SHA-256, wired separately from the OAuth identity used by the application. That is a workaround rather than a supported end-state, and it is worth budgeting for the day federation grows a JWT flow — the credential rotation for a service account is a real operational responsibility until then. Endpoints on Lakebase scale to zero when idle, which keeps the workaround from becoming an always-on cost line.

The broader significance is that the "operational store versus analytical warehouse" split, which usually forces at least a CDC or scheduled ETL between the two, collapses when the operational store is Postgres-compatible and federatable. This series is the first practical, end-to-end write-up of that collapse for a real developer portal rather than a synthetic demo, and the FinOps use case is the sort of value-per-query metric that platform teams can lift verbatim.

### 🎯 Takeaway (Hợp)
If your platform team already runs a Backstage instance and pays Databricks bills separately from watching those bills, this walkthrough is the shortest bridge between the two. Even for teams that do not use Backstage, the pattern — federate the operational Postgres in read-only mode and join to `system.billing.usage` — is portable to any developer portal or service catalog, and the SCRAM-SHA-256 detour is a fair cost for shipping the report today rather than waiting for OAuth-JWT federation.

### 💡 Example
```sql
-- One-query FinOps: join Backstage's live Postgres catalog (federated
-- into Unity Catalog via Lakehouse Federation) against Databricks billing.
-- No ETL, no nightly export — the answer is as fresh as the catalog row.
SELECT
  bs.owner_team,
  bs.branch_name,
  SUM(bill.usage_quantity)              AS dbus,
  SUM(bill.usage_quantity * lp.price)   AS estimated_cost_usd
FROM  lakebase_pg.public.backstage_entities AS bs
JOIN  system.billing.usage               AS bill
  ON  bill.custom_tags.workload_id = bs.entity_id
JOIN  system.billing.list_prices         AS lp
  ON  lp.sku_name = bill.sku_name
 AND  bill.usage_start_time BETWEEN lp.price_start_time
                                AND COALESCE(lp.price_end_time, current_timestamp())
WHERE bill.usage_start_time >= current_date() - INTERVAL 7 DAY
GROUP BY bs.owner_team, bs.branch_name
ORDER BY estimated_cost_usd DESC;
```

Velxio is presented as CPU-accurate emulation rather than behavioural simulation, running unmodified `.hex`, `.uf2` and `.bin` binaries produced by the real `arduino-cli` and ESP-IDF toolchains. The pitch to embedded engineers is that the firmware you send to the simulator is the firmware you would flash to hardware, and the peripherals and network paths are close enough to real that the simulator is usable for regression testing and demo builds, not just for prototyping.

### 🔬 Details (Phân)
The emulation core is a QEMU fork that provides register-level Xtensa LX6 and LX7 peripherals for ESP32 boards and QEMU RISC-V (RV32IMC) system emulation for ESP32-C3. Other MCUs come in through purpose-built emulators — avr8js for Arduino AVR, rp2040js for the RP2040 — for a total of more than thirty boards across six CPU architectures, with ten variants in the ESP32 family alone. On the mixed-signal side, ngspice is compiled to WebAssembly and drives Modified Nodal Analysis so analog components behave with their real transfer characteristics rather than a lookup table. Peripheral coverage on ESP32 is broad: digital GPIO with a canvas wiring UI, multiple UARTs with auto-baud detection, 12-bit ADC reading the solved node voltages, I2C and SPI at protocol level, RMT with WS2812 timing accuracy for NeoPixel strips, hardware PWM/LEDC channels, and a camera module that can bridge a real webcam into the simulated ESP32-CAM path.

The networking story is what distinguishes Velxio from a pure MCU-in-a-tab. Multi-board simulations wire UART, I2C and SPI between different microcontroller types, so a distributed sensor mesh can be composed and debugged without touching hardware. The paid tier adds an AI agent that selects components, auto-routes wiring, writes multi-file firmware, compiles it with the real toolchain, and iterates by inspecting the serial monitor and pressing simulated buttons; the same agent behaviour is not required for basic use.

Velxio ships as a hosted instance at velxio.dev (free tier for public examples) and as a fully self-hostable Docker image published to GHCR. The reported install base at release is 15,000+ registered developers and more than 1,000 simulation runs per day, with ESP32 targets accounting for over half of those runs. The forward roadmap is browser-native emulators for ESP32, ESP32-S3, ESP32-C3 and ESP32-C6 (JavaScript-based, offline-capable) and revision-aware ESP32-P4 emulation. AGPLv3 is a notable licence choice for a service-oriented product; commercial deployments that modify the code and expose it as a network service will need to plan around the copyleft obligation.

Arduino Core on Zephyr keeps the familiar Arduino API surface — `setup()`, `loop()`, `pinMode`, `digitalWrite`, the standard library ecosystem — while replacing the runtime underneath with Zephyr RTOS. The practical benefit for embedded engineers is that Arduino sketches gain real RTOS capabilities (kernel-managed threads and synchronisation primitives, mature networking, driver reuse across the Zephyr ecosystem) without a rewrite, and vendor upgrades that ship on the Zephyr side land on Arduino boards through the same channel.

### 🔬 Details (Phân)

Arduino has not published a detailed compatibility matrix in the release note; teams with mbedOS-pinned firmware should evaluate on a per-project basis rather than assume a clean swap.

The broader story is Arduino continuing its multi-year alignment with Zephyr rather than maintaining a bespoke runtime per silicon family. That reduces the surface area of vendor-specific bring-up work, brings Arduino boards into the same driver update stream as the wider Zephyr ecosystem (including the security-relevant fixes that periodically land on the LTS branch), and makes Nano/Portenta/Nicla boards more attractive as targets for teams that already use Zephyr commercially.
