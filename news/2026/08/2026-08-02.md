### 🔭 Overview (Tổng)
Shakhi Hali, Mazrim Mehrtens and Huyam Hasan announced on the AWS Big Data blog on 30 July 2026 that Amazon MSK Express brokers can now deliver streaming data directly into Apache Iceberg streaming tables on Amazon S3 Tables. The feature removes the two components most teams still glue between a Kafka cluster and their lakehouse — a Kafka Connect fleet or a Flink job that reads the topic, and a separate compaction service that fights the small-file problem downstream. In the new model MSK itself is the writer: it continuously materialises the topic as an Iceberg table, registers it in the AWS Glue Data Catalog, and hands it off to query engines and AI agents as a first-class analytical asset.

### 🔬 Details (Phân)
The end-to-end pipeline goes producers → MSK Express brokers → intelligent inline compaction → optimised Iceberg tables in S3 Tables, with the resulting tables immediately queryable from Athena, Redshift, EMR and Spark through the standard Glue integration. AWS positions the built-in write path as exactly-once at the delivery layer, and it does the compaction on the fly rather than at a nightly cadence, which is the ingredient that makes the small-file problem go away without an out-of-band optimiser job. The headline economic claims are up to 60% lower cost versus a self-managed equivalent (a Kafka Connect cluster plus a compaction job plus the storage churn of un-compacted files) and roughly 30% lower downstream query cost, both attributed to the compaction discipline producing better-shaped Iceberg tables for scans.

Setup is a per-topic operation in the MSK console: choose the MSK Express cluster, enable delivery to streaming tables, point at the source Kafka topic, wire the schema through the AWS Glue Schema Registry, and pick either S3 Tables (the managed Iceberg storage) or a general-purpose S3 bucket as the destination. Programmatic setup goes through the MSK API and is described as scaling to gigabytes per second without operator intervention. The freshness bound is minute-level rather than second-level, which is the standard tradeoff for streaming into an Iceberg table where snapshots must be published as a coherent unit, and the coordination happens on the broker side rather than in application code.

Contextually this joins a broader industry pattern of pushing Iceberg down the stack into the systems that produce and store the bytes — S3 Tables at rest, MSK at the ingestion boundary — so that the analytical shape of the data is settled before any query engine touches it. The immediate consequence for platform teams is that a common ingestion topology (Kafka → Connect → Iceberg → compaction cron) collapses into a checkbox on the cluster, with the two managed pieces replacing a moving-parts pipeline that used to be a full-time operational surface. The caveat worth naming is that this is an MSK Express feature specifically; teams on self-managed Apache Kafka or on non-Express MSK clusters still take the connector path today.

### 🎯 Takeaway (Hợp)
If you already run MSK Express and pipe topics into a lakehouse via a Kafka Connect fleet plus a compaction job, this is a straight simplification: prototype a single topic on the new path, hold your producers constant, and compare 24 hours of Athena query cost and pipeline TCO against your current setup. The most defensible reason to pilot now is that the small-file problem — the one that quietly inflates every Iceberg-on-S3 query bill — is being solved by the writer rather than a downstream cron, and that is a shape of savings that compounds over topic count.

### 💡 Example
```bash
# Enable delivery from an MSK Express topic to an Iceberg streaming
# table on S3 Tables. Schema is resolved via the AWS Glue Schema
# Registry; the target Iceberg table is auto-registered in the Glue
# Data Catalog and immediately queryable from Athena/Redshift/EMR.
aws kafka create-streaming-table-delivery \
  --cluster-arn "${MSK_EXPRESS_CLUSTER_ARN}" \
  --topic-name  "orders.events" \
  --schema-registry '{
      "RegistryName": "orders-registry",
      "SchemaName":   "orders.events-value",
      "Compatibility": "BACKWARD"
    }' \
  --destination '{
      "S3Tables": {
        "TableBucketArn": "arn:aws:s3tables:us-east-1:123456789012:bucket/lakehouse",
        "Namespace":      "streaming",
        "TableName":      "orders_events"
      }
    }' \
  --delivery-semantics EXACTLY_ONCE
```

### 🔭 Overview (Tổng)
Navaneedha Krishnan Jagathesan published a FinOps-oriented walkthrough on the AWS Big Data blog on 30 July 2026 for teams running Spark on Amazon EMR against SSE-KMS-encrypted S3 data. The scaling problem is straightforward: every Spark task that opens an encrypted S3 object triggers its own `kms:Decrypt` API call, and for workloads that read hundreds of terabytes composed of millions of small objects, those calls become a visible line on the AWS bill. The post is aimed at the constrained case where S3 Bucket Keys — normally the correct first answer — cannot be used because compliance requires per-object key auditability, and it lays out three independent levers that stack.

### 🔬 Details (Phân)
Lever one is data aggregation: pushing many small files into fewer, larger ones so a single decrypt covers more compute work per call. The post's example is a plain `data.coalesce(10).write.parquet(...)` that lands a CSV dataset as ten Parquet files and, per CloudTrail counts, drops the decrypt-call fan-out meaningfully. Lever two is file format and compression: moving from uncompressed CSV to Parquet or ORC with a modern codec — Snappy is used in the example, and the article explicitly recommends ZSTD as the default — lowers the byte count that has to move over the wire and lets Spark's columnar readers skip whole objects, again cutting the decrypt call rate. Apache Iceberg is called out as the format-plus-catalog variant of the same lever, with the same `writeTo` API shape.

Lever three is Glue Data Catalog partition indexing. Without an index, Spark's planner has to enumerate partitions to decide which to read, which triggers a decrypt per object it touches during listing; with a partition index on high-selectivity columns (the example is year/month on an events table), Glue does the pruning server-side and the decrypt fan-out only fires on the surviving partitions. The three levers are additive rather than exclusive: aggregation shrinks the object count, columnar+compression shrinks the object footprint and enables reader-side skipping, and partition indexing constrains which objects the reader ever asks about.

The post is explicit about hierarchy: "S3 Bucket Keys is the most effective way to reduce AWS KMS `Decrypt` API calls" and everything above is a stack of secondary optimisations that also happen to be compliant when Bucket Keys are not on the table. That framing matters because it stops teams from treating these techniques as substitutes for the base setting when they aren't obligated to keep per-object key granularity. The measurements in the post are CloudTrail-based (call counts before and after) rather than dollar-denominated, so translating them into a saving requires each team to plug in their own request price and read profile.

### 🎯 Takeaway (Hợp)
Turn on S3 Bucket Keys if your compliance posture permits it — the article's own hierarchy puts that first — and layer aggregation, Parquet+ZSTD or Iceberg, and Glue partition indexes on top in that order. The tidy result is that a FinOps investigation into a mysteriously large KMS bill on an EMR/Spark workload now has a canonical checklist to walk through before opening a support case.

### 💡 Example
```python
# Layer 1 — coalesce many small CSVs into fewer Parquet objects so a
# single kms:Decrypt call covers more Spark task work.
consolidated = spark.read.csv("s3://amzn-s3-demo-bucket/raw-csv/")
consolidated.coalesce(10) \
    .write.mode("overwrite") \
    .parquet("s3://amzn-s3-demo-bucket/optimized-data/")

# Layer 2 — Parquet + ZSTD; article recommends ZSTD as default codec.
spark.conf.set("spark.sql.parquet.compression.codec", "zstd")

# Layer 3 — with a Glue partition index on (year, month), the planner
# prunes server-side; only surviving partitions trigger kms:Decrypt.
spark.sql("""
  SELECT COUNT(*)
  FROM   default.`kms-demoevents`
  WHERE  year = '2000' AND month = '04'
""").show()
```

## 3. Uber Engineering Retires the 2GB RoaringBitmap Ceiling for Exact COUNT(DISTINCT): Chunked Aggregation Buffer Uses xxHash64 to Route Into 65,536 Roaring64Bitmap Chunks, Raising Safe Cardinality From ~179M to ~11.7T and Cutting Quarterly Backfill 65%

### 🔭 Overview (Tổng)
Prakhar Agarwal, Avinash Varma Sagi, Abhay Singh Chauhan, Kranthi Reddy and Divya Rai published an engineering write-up on the Uber blog on 30 July 2026 describing how they scaled exact `COUNT(DISTINCT)` for non-rollup metrics — measures where daily totals do not compose into weekly or quarterly totals, because the underlying set of identifiers overlaps. Uber's quarterly MAU-shaped calculations had to reason over roughly 3.6 billion UUID identifiers simultaneously, and the standard tool for the job, RoaringBitmap on the JVM, was hitting a hard failure mode: Java's internal array indices are bounded at `Integer.MAX_VALUE`, so a single bitmap that grows past about 2 GB starts throwing `OutOfMemoryError` deterministically no matter how large the heap is.

### 🔬 Details (Phân)
The redesigned data structure is a Chunked Aggregation Buffer: instead of one bitmap, a `Map<Integer, Roaring64Bitmap>` keyed by chunk id. Every incoming identifier is hashed with xxHash64 (Hive's native hash function, so the same function that already lives on the ingest path is used), and the top 16 bits of the hash become the chunk id — `chunkId = (int)(hash >>> 48)` — producing 65,536 chunks. The write emphasises the arithmetic behind the choice of 16 bits: a Chernoff-bound analysis at 3.6 billion identifiers gives a negligible probability of any single chunk exceeding the 2 GB serialization ceiling, while 8 bits would leave chunks too coarse and 24 bits would multiply per-chunk overhead pointlessly. Each chunk is serialised independently, which bounds peak serialization memory to the size of the largest single chunk rather than to the total cardinality of the set.

The reduce path is where the constant-factor win becomes visible. Because the final answer a business dashboard needs is a cardinality — a single 8-byte long — the reducer sums per-chunk cardinalities and returns that number; it never has to reconstitute a bitmap that represents every distinct identifier at once. A magic-number prefix (`0xDEADBEEF`) tags partial results so the new format and the legacy monolithic-bitmap format can coexist in the same job during rollout, which meant Uber didn't need a stop-the-world backfill to migrate metric families onto the new code path. They compared explicitly against HyperLogLog, which would sidestep the memory issue at the cost of a 1–5% error, and rejected it because business-critical MAU-shaped metrics feed downstream financial reporting where that error is not tolerable.

The reported numbers are large enough to be worth quoting verbatim. Quarterly backfill duration on the affected pipelines went from 8.58 days to 2.96 days — a 65% reduction, with the highest-cardinality pipelines hitting up to a 94% improvement. Daily pipeline runtime dropped 23%. Monthly data preparation was cut in half, from 20 days to 10. The theoretical safe cardinality threshold — the point at which the previous design would begin to OOM — jumped from about 179 million to about 11.7 trillion, roughly a 65,000× headroom improvement. Post-deployment on 75 metric families, they report zero `OutOfMemoryError` failures. The write-up doesn't publish the exact reducer code, but it names the shape unambiguously enough that a competent JVM engineer can rebuild the pattern from the description.

### 🎯 Takeaway (Hợp)
Anyone maintaining an in-house exact `COUNT(DISTINCT)` implementation on the JVM that leans on a single monolithic bitmap should treat the ~2 GB ceiling as a scheduled failure rather than a hypothetical: shard the state by a stable hash prefix into 4- or 16-bit buckets, reduce on cardinality rather than on serialised bitmaps, and keep a magic-number-tagged wire format so the migration is incremental. It is the kind of small architectural change whose upside is measured in disappearing 3 a.m. pages, not in flashy demo numbers.

### 💡 Example
```java
// Sketch of the Chunked Aggregation Buffer pattern. Real Uber code
// is not published; this is the shape the writeup describes.
public final class ChunkedDistinctBuffer {
    private final Map<Integer, Roaring64Bitmap> chunks = new HashMap<>();

    /** xxHash64 → top 16 bits pick 1 of 65,536 chunks. */
    public void add(long id) {
        long h = XxHashFunction.hash(id);        // Hive's native xxHash64
        int  chunkId = (int) (h >>> 48);          // 16-bit shard key
        chunks.computeIfAbsent(chunkId, k -> new Roaring64Bitmap())
              .addLong(h);
    }

    /** Reduce returns cardinality only — never a full bitmap. */
    public long cardinality() {
        long total = 0L;
        for (Roaring64Bitmap b : chunks.values()) total += b.getLongCardinality();
        return total;
    }
}
```

### 🔭 Overview (Tổng)
The Espressif Developer Portal published a community post by Sylwester Sosnowski on 1 August 2026 introducing esparagus, a Rust-based ESP32 flasher whose design goal is machine consumption rather than human handholding. The premise is that flasher output has traditionally targeted a human reading a progress bar, and that both CI pipelines and LLM-based coding agents now sit downstream of that output and cannot reliably parse phrases like "A fatal error occurred" followed by a stack trace without fragile substring matching. esparagus keeps protocol parity with the canonical `esptool.py` — same SLIP-framed serial protocol, same stub loader, same reset paths — but wraps the operation in structured NDJSON events, stable numeric exit codes and machine-readable summary reports.

### 🔬 Details (Phân)
The flagship command is `flash-monitor`, which fuses image write, board reset and post-boot serial monitoring into a single call and returns an exit code that a shell script or agent can branch on without re-parsing text. Exit code 0 signals a clean flash-and-boot; 32 is the interesting one, signalling that the monitor detected a firmware-side crash (panic, watchdog reset, brownout or a reboot loop) even though the flash itself succeeded — a distinction that previously lived in log-scraping heuristics. Ranges 10–15 encode connection and chip-sync failures, 30–31 encode expect-pattern misses and timeouts, and the full table is small enough (nine codes) to fit in a documentation card. NDJSON output — enabled via `--json` and consumed one JSON object per line — carries timestamps, log levels and semantic event types (`chip_detected`, `stub_upload`, `write_progress`, `md5_verified`) with typed fields rather than free-form strings.

Automation goes further than exit codes. TOML-based expect scripts let boot flows be described declaratively with regex captures, branching and built-in crash detection, which is the shape of thing that ended up as ad-hoc shell in most factory-provisioning pipelines. Partition-name-addressed operations (read/write/erase by partition label instead of by hex offset) remove one of the most common sources of mistake in field service work. The tool also ships full-flash backup with compression, an NVS inspector (both a TUI viewer and a JSON export), YAML-based eFuse decoding, and an MCP server behind `esparagus mcp` that exposes 18 tools mirroring the CLI, streams events as MCP notifications, and spawns a fresh child process per `tools/call` so that serial-port ownership can be managed on demand rather than held persistently.

Chip coverage spans ESP32, ESP32-S2, ESP32-S3, ESP32-C2, ESP32-C3, ESP32-C5, ESP32-C6, ESP32-H2 and ESP32-P4, with end-to-end bench validation called out for ESP32-P4 (detect, stub handshake, compressed writes, full-flash backup, firmware reset) and detect-plus-backup for ESP32-C5; other families rely on the shared protocol code, with a matrix in `docs/STATUS.md`. Intentional omissions matter: `image_info`, `verify_flash`, `dump_mem`, `load_ram`, secure-boot signing, flash encryption, Secure Download Mode, UF2 generation and NVS writing are out of scope, so this is a flasher-for-automation rather than an all-in-one esptool replacement. The licence is GPL-2.0-or-later (derived from esptool's GPL codebase, with bundled stub binaries dual-licensed Apache-2.0/MIT), which is stricter than the MIT/Apache tone of most ESP32 tooling and worth reading before shipping esparagus inside a closed-source distribution.

### 🎯 Takeaway (Hợp)
Teams whose CI pipelines currently regex `esptool.py` stdout — or whose coding agents guess at the same output — should evaluate esparagus on a single production board, wire `flash-monitor` into a job, and treat the exit code and the NDJSON stream as the contract instead of the human-readable log. The GPL-2.0-or-later licence is the one thing worth reading upfront if the flasher is going to be embedded in a distributed product rather than only living on internal build agents.

```bash
cargo install --git https://github.com/DatanoiseTV/esparagus

```
