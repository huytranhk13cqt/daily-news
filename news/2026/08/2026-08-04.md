### 🔭 Overview (Tổng)
AWS extended its managed Apache Spark Troubleshooting Agent to cover Amazon EMR on EKS, which is the Kubernetes-hosted flavour of EMR that runs Spark workloads inside customer-owned EKS clusters. The agent is packaged as a fully managed single-tenant Model Context Protocol server so any MCP-compatible assistant — Claude Code and the Kiro CLI or IDE are the two AWS calls out — can drive it from a developer laptop. Its job is to pull the four log surfaces a Spark failure on EKS usually spreads across into one place and hand the correlated bundle to a Bedrock LLM with RAG that produces a written root-cause analysis plus PySpark code recommendations, so an engineer opens their assistant, asks "why did job X fail", and gets a specific answer rather than a grep session.

### 🔬 Details (Phân)
The mechanical work the agent does is correlation. Spark on EMR on EKS emits driver and executor logs to Amazon S3, container-level logs to CloudWatch Logs, and it exposes a Spark History Server through the EMR Persistent UI. Each surface tells part of the story: OOMs and Kubernetes exit-code exhaustion show up in the container logs, shuffle and skew problems live in the History Server's stage view, driver and executor logs carry the stack traces. The agent authenticates through IAM, calls `emr-containers:DescribeJobRun`, `emr-containers:DescribeVirtualCluster`, `elasticmapreduce:DescribePersistentAppUI`, `s3:GetObject`, `s3:ListBucket` and `logs:GetLogEvents`, is read-only by design and every call it makes is CloudTrail-audited. The failure taxonomy it covers is explicit: out-of-memory and Kubernetes exit-code exhaustion, data skew and shuffle issues, misconfiguration, and code-level defects — the four things that account for the bulk of production Spark incidents on EKS.

Once the correlated bundle is assembled, it is handed to an Amazon Bedrock LLM with a RAG index over Spark and EMR documentation, and the model produces a root-cause paragraph plus targeted PySpark rewrites. Nothing in the post is a new pricing tier: the agent itself carries no additional charge on top of existing EMR on EKS spend, and the model call plus the log pulls sit within the existing IAM boundary of the calling identity. Setup is short: Python 3.10 or later, the `uv` package manager, and an MCP-compatible assistant registered against the server; from there the assistant sees a normal MCP tool and calls it with a job run ID.

Context matters here. AWS shipped the same agent for EMR on EC2 earlier this year, so what changes on 3 August is coverage: EMR on EKS is the flavour teams choose specifically when they want Kubernetes-native scheduling and mixed workloads on shared clusters, and that shared substrate is exactly the environment where an engineer needs the four log surfaces stitched together automatically. The trade-off is that it is a Bedrock-hosted RAG agent rather than a local reasoner, so the standard concerns about handing production telemetry to a hosted model apply — read-only IAM and CloudTrail auditing exist so a security review can enumerate what was actually sent, but the review still needs to happen.

### 🎯 Takeaway (Hợp)
Any team running Spark on EMR on EKS should stand the agent up in a development account, point Claude Code or the Kiro CLI at it, and rerun the last three failed jobs through it to calibrate whether the root-cause paragraph matches what your on-call engineer already worked out. If it does, that becomes the first stop on the runbook and the CloudTrail trail becomes the audit story for compliance. ### 🔬 Details (Phân)
The operations skill's coverage of Express broker sizing is the piece worth calling out. Express is Amazon MSK's newer broker tier and its sizer trade-off is different from Standard — the skill runs a programmatic comparison across every instance type in both tiers, produces a cost breakdown that folds in cross-AZ transfer, replication overhead and per-broker partition limits, and returns a recommendation that a human can accept or override. Consumer-lag diagnosis and storage management follow the same shape: the agent pulls the CloudWatch and MSK API surface a human operator would consult, applies rules that match how AWS's own SAs walk through the same problems, and returns a prioritised action list rather than a raw metric dump.

The migration skill's three phases are ordered and distinct. Discovery inventories the source cluster — brokers, topics, partitions, consumer groups, ACLs, quotas, replication factor. Prerequisites are conservative: AWS CLI 2.35.0 or later, Python 3.12 or later on the operator machine, and one of the supported source Kafka versions on the other side. ### 🔭 Overview (Tổng)
ClickHouse published a playground on 3 August 2026 at `benchmark.clickhouse.com/playground` that lets anyone run queries against a 100 million row dataset preloaded into 110 different database systems, side by side, from a browser. There is a competition mode that fires the same query at every engine and shows the timings back in real time, and there is a single-engine mode for reading the plan and iterating a rewrite. The accompanying engineering post is the interesting artefact: it details how the ClickHouse team fits 110 heterogeneous database images on one host, cold-starts each engine in under five seconds, and keeps the shared host safe while an anonymous user runs arbitrary SQL against it.

### 🔬 Details (Phân)
The isolation story is Firecracker VMs on AWS bare-metal instances with nested virtualisation on, one VM per engine per query. Firecracker gives per-tenant kernel isolation with a sub-second launch, which is what the sub-five-second cold-start figure is really measuring: snapshot restore of the microVM plus the engine's own warm-up. The storage story is what makes the "all 110 engines on one host" claim credible: the team lays every engine's data directory down on a single BtrFS volume mounted with `compress-force=zstd:6`, and then uses reflink copies so each VM sees its own filesystem view without duplicating the underlying bytes. The end result is 7.5 TB of physical storage carrying the working set for every system in the field.

Memory is the second scarce resource on a shared host and the team's answer is to expose guest swap that is backed by the host's page cache rather than by disk, so a runaway query in one engine cannot pin RAM the next engine needs. A watchdog process kills queries that go over a CPU budget so one engine cannot starve the rest, and `vm.init_on_free = 1` is set at the host so freed pages are zeroed before they can be handed to a subsequent tenant. Network egress is locked to nothing during a query run: the host runs an SNI-inspecting proxy that allow-lists the specific hostnames that engines need for lookups at load time and denies the rest, so a hostile query cannot exfiltrate results or reach into another VM.

The reason this write-up is worth the time of a data engineer who is not planning to run their own benchmark hosting is that it is a full recipe for running many heterogeneous engines cheaply on shared infrastructure. Firecracker plus BtrFS plus SNI-proxying plus guest swap to page cache is a reusable pattern for anyone who wants to expose read-only query surfaces to untrusted callers — a customer-facing benchmark, an internal cost-comparison harness, a class of "prove out this engine on our shape of data before we commit" workflows. The specific numbers — 100 million rows across 110 engines, 7.5 TB compressed footprint, sub-five-second cold starts — set the sizing envelope for that pattern.

### 🎯 Takeaway (Hợp)
For evaluation work, the ClickBench Playground now removes the "spin up ten engines yourself" tax on a fair comparison — pick your query shape, run it across engines you were considering, read the plan on the loser. For anyone building shared query infrastructure of their own, the post is a concrete reference for the Firecracker plus BtrFS zstd:6 plus reflink pattern and worth cloning wholesale before writing your own containment story.

### 🔭 Overview (Tổng)
CNX Software wrote up on 3 August 2026 how developer Slava S., who publishes as slvDev on GitHub, has run a 28.9 million parameter transformer on a plain ESP32-S3 board that costs about eight US dollars. The model is trained on the TinyStories dataset and it sustains roughly nine tokens per second on the board's dual Xtensa LX7 cores, generating text into a small I2C display. The reason this matters is not the token rate — it is that the model is about a hundred times larger than what people were running on the same silicon in 2023, and the reason it fits is a specific architectural trick from Google called Per-Layer Embeddings.

### 🔬 Details (Phân)
The board has three storage tiers of very different sizes: 512 KB of on-chip SRAM, 8 MB of PSRAM over the OCTAL PSRAM interface, and 16 MB of flash. A conventional transformer would need the full weight tensor resident in the faster tiers, and a 28.9M parameter model at four-bit quantisation is 14.9 MB — too large for PSRAM alone if the embedding table is loaded into it. Per-Layer Embeddings works around this by moving the token embedding table to be layer-scoped and sized so that each token is a small independent record. In slvDev's port, the 25M-parameter embedding table (which is the vast majority of the model's weights) sits in flash and is streamed row by row as tokens are consumed, at roughly 450 bytes per token; the output head and working memory sit in PSRAM; and only the hot "thinking" tensors that a forward pass actually touches every step live in SRAM.

The measured throughput of about nine tokens per second is respectable for the class and is enabled by two things: the streaming embedding access is sequential and small enough that the ESP32-S3's flash bandwidth is not the bottleneck, and the working set that has to fit in SRAM is small enough that the LX7 cores do not stall on PSRAM latency during the forward pass. The 4-bit quantised on-flash file is 14.9 MB, well within the 16 MB flash budget, so the model ships as a single binary on the board with room to spare. Source lives at `github.com/slvDev/esp32-ai` and the writeup includes photos of the demo generating stories to a small I2C display.

The trend line is worth naming. In 2023 the state of the art on ESP32-class silicon was single-digit-million-parameter TinyML classifiers and the occasional 100-300k-parameter language model. In mid-2025 the frontier moved to sub-1M-parameter generative models on the ESP32-S3. Three months later slvDev's port is running a 28.9M-parameter transformer at usable tokens per second on the same board, and Per-Layer Embeddings is the architectural change that made that jump possible on a memory-constrained microcontroller. This is not a laptop LLM in a smaller box; it is a demonstration that the constraint on-device is no longer "how much RAM does the entire model need" but "how much of the model must be in the fastest tier every step".

### 🎯 Takeaway (Hợp)
For anyone building an embedded generative surface — an educational toy, a museum kiosk, a battery-powered narration device — the Per-Layer Embeddings pattern is the technique to look at first, because it is the reason a $8 board with 8 MB PSRAM can now host a model that would previously have required a Raspberry Pi. Clone the `slvDev/esp32-ai` repository, flash the demo firmware to any ESP32-S3 board with 8 MB PSRAM and 16 MB flash, and measure your own tokens per second before committing to any specific architecture.

### 🔭 Overview (Tổng)
Aliensense unveiled the NXS on 3 August 2026, a sensor hub aimed at autonomous robots built around an STM32G491 Cortex-M4F with 112 KB of SRAM and 512 KB of flash paired with a Maxim MAX96793 GMSL2/3 serializer. The whole thing sits in a 40 x 30 x 28 mm anodised-aluminium shell, takes power and video and sensor data over a single coax cable up to 15 metres (or roughly 40 metres over CAN-FD at a reduced rate), and exposes CAN-FD, Cyphal-over-serial and I2C register maps so it can slot into a distributed robotics topology without a custom carrier board. The "Vanguard Edition" kit is on pre-order at US$199 with shipping from 20 August 2026; the standard price after that is US$249.

### 🔬 Details (Phân)
The MAX96793 is the piece that makes the "one coax to the head" claim work. GMSL2 and GMSL3 are Maxim's serialiser-deserialiser standards for automotive-grade point-to-point links: a single 50-ohm coax carries the MIPI CSI-2 camera stream, back-channel control, and power-over-coax in one direction, and a paired deserialiser recovers the same signals at the host. At 15 metres this is longer than any practical MIPI ribbon run and it is the correct wiring pattern for a robot arm or a mobile base that needs sensor heads on the extremities. The STM32G491 handles the local intelligence — pre-processing, sensor fusion at the head, and the CAN-FD and Cyphal transport back to the compute stack — inside its 112 KB SRAM and 512 KB flash budget.

The mikroBUS socket is what opens the design up. Aliensense sell an add-on shuttle that exposes a standard mikroBUS pinout with I2C, SPI, UART, PWM, analog, interrupt and reset signals, which means the NXS can host any of the more than 2,000 MikroElektronika Click modules — accelerometers, magnetometers, ToF rangers, environmental sensors, gas sensors, temperature probes — without needing a custom PCB per sensor variant. Power input is 12 V nominal with a tolerant window from 4.7 V to 16 V, and the device is rated -40 °C to +85 °C so it survives outdoor and industrial deployments rather than being restricted to lab benches.

Positioning is against three obvious alternatives. Compared with rolling your own STM32 board plus a discrete GMSL serialiser, the NXS is a shorter path to a fielded system and the anodised shell plus the temperature rating are worth real money on any deployment past a prototype. Compared with a NVIDIA Jetson-based sensor head, the NXS is a much smaller compute envelope but a much smaller power envelope too, which matters on battery-powered mobile platforms. Compared with the growing family of USB-C sensor pucks that show up on Kickstarter, the NXS is the choice when the run is 15 metres long and the cabling constraint of a single coax matters more than the convenience of USB.

### 🎯 Takeaway (Hợp)
For a robotics team building an autonomous mobile platform or a large arm that needs sensor heads at the extremities, the NXS is worth costing into the design as a compact single-coax head; the US$199 pre-order price is low enough that ordering two Vanguard kits and prototyping against a representative Click module is a small commitment. If the deployment does not need the 15-metre coax run or the industrial temperature rating, the case for a plain USB or MIPI sensor stays intact.
