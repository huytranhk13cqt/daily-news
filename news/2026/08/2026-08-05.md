### 🔭 Overview (Tổng)
Databricks promoted the Variant data type to general availability on 3 August 2026 and shipped Variant Shredding as the piece that comes with GA. Variant is the semi-structured column type for JSON, XML and CSV that Databricks developed with the Delta and Spark communities and that has been standardised across both Parquet and Iceberg as an open format. The reason GA matters is the shredding: Predictive Optimization identifies the fields that queries actually touch, promotes them to real Parquet columns underneath the Variant, and collects statistics so the file skipper can prune. The current usage floor Databricks discloses is over 5,000 teams writing Variant across more than 500 million queries per month over 160 TB or more of data.

### 🔬 Details (Phân)
The performance numbers are the concrete substance. Variant Shredding delivers about four times faster reads than an unshredded Variant column and about thirty times faster reads than the same payload stored as a JSON string. The mechanism behind the four-times figure is standard columnar: once a nested field is promoted to its own Parquet column, the reader can skip pages by min-max statistics, can vectorise, and can hit a much smaller working set on disk. The mechanism behind the thirty-times figure is that JSON strings force the reader to re-parse every row on every scan, and Variant sidesteps that in one direction and shredding sidesteps it in the second direction as well. Storage-wise, Variant "stores common fields as columns in the underlying Parquet files" and the same table can be persisted in Delta or in Iceberg without changing the on-wire representation, which is what makes the standardisation claim meaningful outside the Databricks runtime.

The GA also closes the gap on the operating model. In pre-shredding Variant, an engineer had to know which fields were hot and either project them out into a maintained view or rewrite the pipeline to schematise. Predictive Optimization now automates the detection and the materialisation, so the pattern the announcement pushes — "land data first, refine the shape later" — is finally a defensible default rather than a debt-generating one. Auto Loader remains the incremental path for landing files from object storage, and Zerobus is the managed direct-write path for teams that do not want to build an ingest job at all.

Context sets the honest bounds. Snowflake VARIANT, Databricks Variant, DuckDB JSON with computed columns, and Iceberg's own emerging variant support are converging on the same shape of answer: an untyped column at rest, a columnar shredding pass under the covers, statistics that let the file skipper do work. Databricks's contribution here is a specific shredding implementation that ties into Predictive Optimization plus a claim that the Parquet-level representation is open enough that Delta and Iceberg both read it. The trade-off is honest too: Variant Shredding needs Predictive Optimization enabled on the table, so a team that has explicitly opted out of automatic optimisations for compliance reasons keeps the unshredded numbers.

### 🎯 Takeaway (Hợp)
Any team that stores JSON as a `STRING` column on Delta or Iceberg today should run one representative query against a Variant column with shredding on the same dataset before Q4 planning, because a thirty-times factor changes the shape of what queries are affordable to expose to product surfaces. For teams that already migrated to Variant in preview, the action is smaller — turn Predictive Optimization on for the tables where Variant fields are being queried repeatedly and re-measure — but the four-times factor is easy to leave on the table by accident.

### 💡 Example
```sql
-- Land raw event JSON into a Delta table as a Variant column; Auto Loader
-- handles the incremental read from object storage. Predictive Optimization
-- then shreds the frequently queried fields into real Parquet columns.
CREATE OR REFRESH STREAMING TABLE events_raw
TBLPROPERTIES ('delta.enablePredictiveOptimization' = 'true')
AS SELECT
     PARSE_JSON(value) AS payload   -- payload is a VARIANT column
   FROM STREAM read_files(
     '/Volumes/prod/events/*.json',
     format => 'json',
     schemaHints => 'value STRING'
   );

-- Query nested fields directly; the shredded columns are used transparently.
SELECT payload:user.id::STRING     AS user_id,
       payload:event.type::STRING  AS event_type,
       COUNT(*)                    AS n
  FROM events_raw
 WHERE payload:event.ts::TIMESTAMP > CURRENT_TIMESTAMP() - INTERVAL 1 DAY
 GROUP BY 1, 2;
```

### 🔭 Overview (Tổng)
Delivery Hero and AWS published a joint engineering write-up on 4 August 2026 covering the migration off self-managed Elasticsearch 7.x on GKE onto Amazon OpenSearch Service 3.x, and the piece worth extracting is the shape of the search stack rather than the migration diary. The system now runs parallel radial k-NN vector search and lexical BM25 in one request, backs it with Airflow-generated embeddings landed to S3 and streamed into OpenSearch by OpenSearch Ingestion (OSIS), and gets to a p95 baseline around 100 ms after roughly halving the previous latency. The OpenSearch 3.3 upgrade on top of that shaved another 18 percent off vector-query p95, and semantic-search p99 sits under 35 ms during peak.

### 🔬 Details (Phân)
Radial search is the piece that is worth defining out loud, because the terminology is not universal. Where standard k-NN returns a fixed count of nearest neighbours regardless of similarity, radial search inverts the ask: return every item at least this similar and stop, using a `min_score` cutoff. OpenSearch normalises cosine similarity as `(1 + cosine_similarity) / 2`, so a `min_score` of 0.95 corresponds to a raw cosine similarity of 0.9. For a food-ordering catalogue where the number of relevant products for a query is not fixed, this is the right shape — a query with three good matches returns three, a query with fifty good matches returns fifty, and the retriever does not spend budget on marginal neighbours.

The ingest side is worth reading for its own pattern. Airflow generates product embeddings daily from the current catalogue, writes them to S3, and OSIS pulls the deltas from S3 into OpenSearch. The index is force-merged nightly for query-side efficiency, and — the interesting choice — every document carries three parallel embedding variants at once so an A/B/C experiment against three model versions can be run at query time without re-indexing. Query-side shard routing is customised by geographic market, so a request tagged as Germany hits shards prefixed `FP_DE` and never fans out cross-market. The inference path runs the radial k-NN and BM25 lookups in parallel and blends them, and query embeddings for hot search terms are cached to keep the encoder off the critical path for the head of the distribution.

The numbers give the shape of the payoff. Before migration, p95 sat above 200 ms; after migration to OpenSearch Service, it steadied around 100 ms. The follow-on move from OpenSearch 2.17 to 3.3 gave a further 18 percent reduction on vector queries specifically, and semantic search p99 stayed under 35 ms during peak. The operational payoff — retiring the standalone Kubernetes deployment pipeline that used to babysit the Elasticsearch cluster, ingesting daily rather than continuously, deleting the self-managed cluster's control plane — is the piece that made the direct dollar case, but the latency figure is the one to quote to product engineers who are the customers of the search API.

### 🎯 Takeaway (Hợp)
For any team running self-managed Elasticsearch 7.x behind a product search surface, this is the reference architecture to read before pricing the next hardware refresh: parallel radial k-NN plus BM25 in one hit, OSIS from S3 for daily ingest, three embedding variants per document for cheap A/B/C, custom shard routing by market. If you are already on OpenSearch 2.x with vector search enabled, the 3.3 upgrade path is the fastest single move on the list — an 18 percent reduction on vector query p95 for a version bump is not a number to leave sitting.
