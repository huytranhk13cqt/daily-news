### 🔭 Overview (Tổng)
dbt Labs tagged `v2.0.0-beta.1` for dbt-core on 10 August 2026, the first beta on the road to a 2.0 series that rebuilds the open-source project on the same Rust runtime that ships in the proprietary dbt Fusion distribution. The alpha line has been out since 1 June, but the beta is the milestone at which teams are being invited to try the new engine against real projects — and the release notes carry a matching feature list rather than just parser plumbing. For any team running dbt in production, this is the release where the "Fusion under the hood" story stops being a promise and becomes something you can install from PyPI and point at your `dbt_project.yml`.

### 🔬 Details (Phân)
The runtime-level features are the ones that change how a project behaves rather than how it feels. Child nodes can now continue running when their parent errors — historically a dbt build stopped a subgraph at the first failure, which is safe by default but leaves later independent work on the table when the failing parent is a leaf test rather than a critical model. Redundant test optimization skips tests the engine can prove are unnecessary, which is the sort of change that quietly cuts wall-clock on projects with heavy generic-test coverage. `dbt State explain` lands as a Fusion-side feature that makes state-based selection decisions inspectable rather than opaque, and the new `DBT01` lint rule requires every `ref()` and `source()` call to be routed through a CTE import at the top of the model — a consistency guarantee that projects have been enforcing with shims for years.

Around those, several smaller pieces improve the day-to-day. Profile initialization now offers a default `profile.yml` selection during `dbt init` rather than a blank prompt, and overloaded UDFs are supported through function YAML configuration blocks so Snowflake and BigQuery user-defined functions can express the same argument variants they carry natively. Unit tests learn to reference pseudocolumns such as BigQuery's `_FILE_NAME`, and `dbt --format json --version` finally produces machine-readable output that CI systems can key off without parsing free-form text. On the fixes side, the DuckDB adapter's stale-schema cache no longer trips unit tests, FQN paths tolerate file-system reserved characters correctly, and Snowflake view staleness is treated more accurately when `dbt State` decides what to reuse.

The broader context is worth naming. The 2.0 line consolidates dbt-core and dbt Fusion onto one Rust engine, keeps the open-source code under Apache 2.0, and moves manifest artifacts to Parquet — the architectural bet that a fast, typed runtime is the base a semantic layer, cross-project references and richer state selection can grow from. Teams currently on 1.12 will get the same speed and feature set as Fusion users without a licence change, but adapter parity, plugin ecosystem behaviour and migration friction on very large projects are the pieces the beta cycle is meant to shake out. The engineering-hub docs already carry a 2.0 migration guide, and the release notes flag that provider adapters need re-testing against the new runtime rather than assumed-compatible.

### 🎯 Takeaway (Hợp)
For any team that has been watching Fusion from the sidelines because of the licence, `v2.0.0-beta.1` is the version to install in a scratch environment, point at a copy of a real project, and time against a comparable 1.12 run. Wire the `DBT01` lint rule into CI in warning mode first — cleaning up existing `ref()`/`source()` sites is where the visible migration cost lives, and doing it against a beta is cheaper than doing it against the GA. Expect provider adapters and dbt-core-experimental features to shift under you across the beta window, and pin versions in production until 2.0.0 final ships.

### 🔭 Overview (Tổng)
Snowflake promoted large-video support in the Cortex `AI_MULTI_EMBED` function to General Availability on 10 August 2026, extending the multimodal embedding function to files up to 6 GB backed by the TwelveLabs Marengo Embed 3.0 model. The function itself has been GA since May for shorter assets, but the practical ceiling had been a hard blocker for teams that wanted to index full-length recordings — meeting archives, broadcast clips, security footage — rather than short segments. The 10 August entry closes that gap and puts video into the same SQL surface that already covers text, images and audio embeddings inside the Snowflake AI Data Cloud.

### 🔬 Details (Phân)
`AI_MULTI_EMBED` produces 512-dimensional vectors that capture visual, audio and transcript semantics simultaneously, with separate embeddings emitted for each modality and for each segment of the source asset — so a single one-hour video becomes many rows in a table, each carrying its own vector and an offset into the media. That segmentation is what makes scene retrieval work at all: a query embedding hits the nearest segment, not the nearest whole file, so the answer to "when does the speaker mention Iceberg" is a timecode rather than a hit list. The Marengo Embed 3.0 model is the piece TwelveLabs contributes; Snowflake's role is the SQL entry point and the storage/serving path that keeps the vectors in the same table space as the rest of a warehouse's data.

The GA scope is the practical piece. Snowflake documents a 6 GB per-file maximum with `AI_MULTI_EMBED` in the GA release notes, which covers most feature-length recordings at typical bitrates and covers all of the short-form use cases at once. The function accepts video paths in an internal or external stage and returns an array-of-struct payload the caller can `LATERAL FLATTEN` into a table with one row per segment. From there the same vector-search primitives that already back retrieval over text embeddings apply — cosine similarity, `VECTOR_L2_DISTANCE`, hybrid keyword-plus-vector joins — with the only difference being that the "text" being searched is a scene, a spoken quote or a visual object rather than a token span.

The wider ecosystem context is that Snowflake is treating multimodal search as a first-class analytics surface rather than a separate application. AI_EMBED landed in July 2025 as the text/image entry point; `AI_MULTI_EMBED` in May 2026 added shorter video and audio; the 10 August GA push completes the shape by removing the file-size ceiling that pushed video workloads onto external services. For a data platform team, the operational consequence is that a video-search feature no longer needs a separate embedding service, a separate vector database and a separate synchronisation job — the extract-embed-store loop lives inside the warehouse, and the same governance, access controls and cost accounting apply.

### 🎯 Takeaway (Hợp)
For any team that has been running a bolt-on video search stack because Snowflake's function only covered short clips, the 10 August release is the moment to do the total-cost math again with a single-warehouse baseline. Start by measuring embedding wall-clock and cost against the current external service on a representative sample of long-form assets; the interesting variable is per-hour cost, not per-call latency, once the pipeline is nightly. If your governance story around video already lives on Snowflake stages, the migration is close to "swap the embedding call" — with the caveat that the segmentation output changes the downstream indexing shape, so plan a schema migration rather than a drop-in.

### 💡 Example
```sql
-- Embed a long-form video from an internal stage and store one row per
-- segment with its 512-dim vector. Uses AI_MULTI_EMBED (GA on 10/08/2026).
CREATE OR REPLACE TABLE video_segments AS
SELECT
    file_url,
    seg.value:modality::string      AS modality,   -- visual/audio/transcript
    seg.value:start_offset_ms::int  AS start_ms,
    seg.value:end_offset_ms::int    AS end_ms,
    seg.value:embedding             AS embedding
FROM (
    SELECT
        RELATIVE_PATH                AS file_url,
        AI_MULTI_EMBED(
            'twelvelabs.marengo-embed-3.0',
            TO_FILE('@video_stage', RELATIVE_PATH)
        )                            AS segments
    FROM DIRECTORY(@video_stage)
),
LATERAL FLATTEN(input => segments)   AS seg;
```

### 🔭 Overview (Tổng)
An unauthenticated SQL injection vulnerability in Metabase, tracked as GHSA-vwf4-m7j8-wcjf and scored CVSS 10.0, is being actively exploited in the wild against both self-hosted and cloud installations. Metabase disclosed the issue on 6 August 2026 after detecting attacks against its Cloud infrastructure that began around 3 August; laptop maker Framework and form-builder company Tally have since confirmed that customer data was stolen from their Metabase instances through the same chain. Coverage widened through 9–10 August as Help Net Security, BleepingComputer, Dark Reading and The Hacker News all published follow-ups. For any team running Metabase in front of an analytical database — the near-default shape on internal data platforms — this belongs on the same-day patch shortlist.

### 🔬 Details (Phân)
The vulnerability lives in `POST /api/session/reset_password`, an unauthenticated endpoint that reaches the application database with crafted input. A remote attacker with no credentials can inject arbitrary SQL and escalate to full administrator access on the Metabase instance, at which point every database connection Metabase holds becomes an exposure path. The Metabase security advisory pins the affected range at 0.58.0 through 0.63.x with equivalent 1.x releases, and the minimum patched versions are 0.58.24, 0.59.21, 0.60.17, 0.61.11, 0.62.9 and 0.63.5 — an unusually broad backport range that reflects both the severity and how many long-lived deployments are on older minors. Notably, no CVE identifier had been assigned at the time of the advisory, so scanners that consult only the NVD feed will not flag exposed instances; the GHSA reference is the current authoritative source.

The exploitation pattern is documented enough to write detection against. Defenders should look in application and ingress logs for a two-step sequence: a `POST /api/session/reset_password` returning HTTP 400, followed immediately by a `GET /api/user/current` returning HTTP 200. That combination is characteristic of a successful injection escalating to administrator context, and instances that show it in their history should be treated as compromised and escalated to incident response rather than merely patched. Rotating credentials for every database wired into the compromised Metabase instance is the next step — the tool's premise is that it holds live connection strings to the warehouses it visualises, and any attacker who reached administrator on the tool inherits that list.

The downstream disclosures are the piece that makes the scope concrete. Framework's Metabase environment was compromised in the same wave; the exposed data covers names, email addresses, phone numbers, physical addresses and login IP addresses for what the company describes as "all customers," though payment records and order-line data are stored elsewhere and were not affected. Tally reported to the Belgian Data Protection Authority that email addresses and password hashes were exfiltrated from its Metabase environment, with the form-response data itself sitting on a separate database that the attacker did not reach. Both disclosures point at the same lesson: an internal BI tool that holds credentials to the transactional systems is a first-class attack surface, and the classic "it's read-only, it's fine" framing does not survive an authentication-bypass class of bug.

### 🎯 Takeaway (Hợp)
Patch every Metabase instance to the relevant minimum-safe version this afternoon, then walk the logs for the two-step POST/GET signature — a clean version count is not the same as evidence of no compromise. For any hit, treat every database connection Metabase holds as compromised and rotate the credentials; the follow-up cost of assuming otherwise is exactly the shape of the Framework and Tally disclosures. Longer-term, this is the incident to point at when arguing for a network boundary between the internal BI tool and production databases, and for a periodic rotation cadence on the credentials it stores.

### 🔭 Overview (Tổng)
Adafruit surfaced an experimental MicroPython port for the Dabao — the evaluation board built around Bunnie Huang's Baochip-1x RISC-V microcontroller — in its 10 August 2026 Python on Microcontrollers newsletter. The Dabao is the first mostly-open-silicon target MicroPython has landed on, and the interesting piece is not the port itself but what it means to have a scripting environment running on top of a 22 nm RISC-V core whose RTL is publicly inspectable rather than a black box. For makers and educators who have been waiting for a chip that pairs open hardware with a Python-usable runtime, the appearance of this port shifts the Baochip-1x from "curiosity" into "you can start prototyping on it".

### 🔬 Details (Phân)
The Baochip-1x is a system-on-chip fabricated at TSMC on a 22 nm process, with a VexRiscv 32-bit CPU running at 350 MHz as the main core, 2 MB of on-die RAM, 4 MB of resistive RAM (RRAM) that serves the flash role for firmware storage, USB 2.0 High Speed, and a quad-core I/O accelerator based on the PicoRV32 clocking at 700 MHz. The differentiating architectural feature relative to comparable RISC-V hobby chips is a proper memory management unit on the main core — the MMU is what unlocks address-space isolation, larger runtime images and, in the MicroPython case, garbage-collected heaps that can grow past what a bare-metal MPU-only target can hold cleanly. The Dabao evaluation board is available through Crowd Supply and exposes the SoC's I/O to standard headers, so the port targets a hardware form factor that a maker can order today rather than a private dev kit.

The MicroPython port is flagged explicitly as experimental — the standard signal that the REPL comes up, `machine.Pin` and time primitives work, and the hardware-specific modules for USB, RRAM programming and the I/O accelerator are the pieces still being filled in. Historically that is roughly where a port sits between "toy" and "usable" for a few weeks before the hardware modules land, and the interesting variable is whether the Baochip's I/O accelerator ends up exposed as a MicroPython native module (fast, opaque) or as a userland driver (slow, inspectable). Either choice affects how a user builds against the chip, and the choice will land during this experimental phase.

The broader significance is worth naming. Open-silicon designs have been an aspiration for years; getting them to the point where a hobbyist can write Python against them turns them from academic exercises into things a classroom or a hackerspace can actually build against. The Dabao's cost, its Baochip-1x's open RTL, MicroPython's ergonomics and the MMU-plus-RRAM combination together give the same "cheap, hackable, scriptable" story that made the original ESP8266 and Raspberry Pi Pico moments — but with the added property that a curious builder can trace a bug through the silicon design as well as the compiler. That is a step change in what "open" means at the microcontroller layer, even if the chip's clock speed and memory footprint are modest by ESP32-class standards.

### 🎯 Takeaway (Hợp)
For makers curious about open silicon, this is the milestone that makes the Baochip-1x worth ordering — the Python-on-open-hardware combination lets you prototype at the same speed you would on an ESP32 while retaining the option to dig down into the RTL when a bug matters enough. For educators, the Dabao plus MicroPython is a candidate for a "how a computer really works" course that no other maker platform quite delivers, because every layer between the LED and the transistor is inspectable. Expect the hardware-module coverage to fill in over the next weeks; watch the port's repository for USB and I/O accelerator support before committing a bigger project.

### 🔭 Overview (Tổng)
Hackaday published a full teardown of the Oxford Nanopore MinION portable DNA sequencer on 10 August 2026, one of the rare cases where a bench-scale scientific instrument opens up cleanly enough to reason about its architecture end-to-end. The MinION pairs a durable USB-attached reader with a single-use consumable flow cell, and the teardown makes visible the engineering split between the two: a Xilinx Spartan 6 FPGA drives sampling and control on the reader side, while the disposable holds the microfluidic path and a bank of high-density-pitch ICs that translate ion currents through biological nanopores into digital reads. For an embedded engineer with no prior exposure to sequencing hardware, this is a rare walk-through of what "sensor at the edge" actually looks like for a molecular-scale signal.

### 🔬 Details (Phân)
The reader side sits around the Spartan 6 FPGA, which handles the real-time signal processing pipeline: the biological nanopores in the flow cell each generate a picoampere-scale ion current whose modulation encodes which nucleotide is passing, and the sampling rate needed to capture that at usable fidelity is far beyond what a general-purpose MCU can service. An FPGA is the natural fit — deterministic timing, wide parallel channels, and enough gates to run per-channel filters before the samples hit USB. The Spartan 6 is nearly a decade past its introduction now, and the teardown implicitly documents that the design was frozen against a mature part rather than chasing the newest silicon; a slim fan-based cooling loop indicates the device does dissipate enough power that passive cooling was not sufficient at duty cycle.

The consumable side is where the density is startling. Both faces of the flow cell PCB carry high-pitch ICs — dense enough that a teardown photograph rather than a schematic is the honest way to describe them — because each nanopore in the array needs its own front-end amplifier to lift a picoamp ion current above the substrate noise floor before it can be multiplexed to the FPGA. The microfluidics layer above the electronics guides the sample fluid across the nanopore array; the mechanical constraint is that the fluid path must be biocompatible, disposable and precisely aligned to the electrode grid underneath, which is why the flow cell is priced at roughly £690 per unit and treated as a limited-use consumable. The reader itself, at around USD 2,000, is much closer to hobbyist territory than laboratory instruments in the same category.

The wider engineering lesson is worth naming for any team building sensor edge devices. The MinION is not "IoT" in the smart-home sense, but the architectural pattern — reusable digital reader plus disposable analog front end, with per-channel amplification on the consumable and heavy DSP on the FPGA — recurs anywhere the signal is molecular, biological or single-photon. That model gives the sensor manufacturer control over the noise floor per unit (because the amplifiers ship with the consumable) at the cost of pushing more BOM into the disposable. The teardown also makes the case that scientific hardware and maker hardware share more silicon than the price tags suggest: the same Xilinx family that lands in enthusiast SDR builds is the piece doing the sequencing here, which is a small but useful demystification for anyone starting to reason about signal chains at the edge.

### 🎯 Takeaway (Hợp)
For embedded engineers with no prior exposure to biosensing, this teardown is a fast introduction to the "disposable analog front end plus reusable FPGA reader" pattern that recurs across many single-molecule and low-light sensor designs. For makers wondering what a Spartan 6 gets you in practice, the answer is a real-time signal chain fast enough to service hundreds of picoamp channels — the concrete number matters more than the marketing language. Read it side-by-side with any datasheet for a modern low-noise transimpedance amplifier if you want the full picture.
