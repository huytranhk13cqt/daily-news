### 🔭 Overview (Tổng)
Databricks announced the acquisition of Electric on 11 August 2026, folding the maker of PGlite — a Postgres build compiled to WebAssembly that runs inside a browser tab, an agent sandbox or an edge process — into the same organisation that ships Lakebase Postgres on the analytical side. The stated rationale is that agentic applications spawn many short-lived compute contexts that each need transactional state at millisecond latency, and reaching a central Postgres over the network is the wrong shape for that workload. Electric brings the local-first embedded database and the sync engine that keeps its rows aligned with a managed remote; Databricks brings the managed remote. For teams already building agent workflows on Lakebase or evaluating them, this is the announcement that turns "which local database do we ship inside the sandbox" from an integration question into a supported product line.

### 🔬 Details (Phân)
PGlite itself is the technical piece that gives the acquisition weight. It is a full Postgres server compiled with Emscripten to WebAssembly, small enough to run inside a browser or an isolate, and it exposes the same wire protocol and SQL surface as an ordinary Postgres server so an application can use existing drivers and ORMs against it unmodified. The Databricks blog notes that PGlite went from 1 million to 13 million weekly downloads over the past twelve months, a growth curve that mirrors the shift of agent runtimes toward per-session sandboxes where a network hop to a shared database is both a latency cost and an isolation risk. The second Electric asset is the ElectricSQL sync engine — a change-propagation layer that streams row-level changes between many PGlite instances and a central Postgres, so a fleet of agents can operate on local state while a single durable copy is maintained upstream.

The Databricks-side integration is Lakebase, the managed transactional Postgres surface that shipped alongside the Data Intelligence Platform in 2025. The acquisition folds Electric's sync engine into Lakebase so that a PGlite instance embedded in an agent's execution sandbox is treated as a first-class edge replica: local writes commit at in-memory latency and stream back to Lakebase, and Lakebase state fans out to sandboxes as they spin up. That closes an operational gap that agent builders have been feeling — every serious agent stack was already reaching for a small embedded database (SQLite in most cases) plus a bespoke synchronisation layer, and the collision between "give the agent a scratch database" and "keep the enterprise's system of record consistent" has been an open engineering problem for the past year.

The wider ecosystem context matters because the WASM-Postgres category is genuinely new. Before Electric, running an ACID relational database inside a WebAssembly execution context meant SQLite-on-WASM or self-hosted Postgres in a container, neither of which matches the "spawn an agent, give it its own database, tear it down in seconds" cadence that AI agent orchestration frameworks push. The acquisition also signals Databricks' willingness to spend on the runtime shape of agentic applications rather than just the model-serving surface — a strategic direction that had been implicit in Lakebase but now has a concrete artifact attached to it. Governance and cost accounting for these transient databases sit in the same Unity Catalog and object-storage plane as Lakebase itself, which is the piece that makes the story defensible against a self-hosted PGlite plus a hand-rolled sync layer.

### 🎯 Takeaway (Hợp)
For any team building AI agents that need transactional state on the fast path, the honest recommendation is to spend an afternoon running the current PGlite npm package inside an existing sandbox to feel the ergonomics before Lakebase's integration ships in preview. If your agent stack today uses SQLite plus a bespoke sync job to a central Postgres, this is the announcement that reframes the choice as "port the sync layer to ElectricSQL now, buy the managed version later"; if you were about to build that plumbing from scratch, don't. Watch for the Lakebase edge-sync preview from Databricks and the corresponding pricing surface, which will decide whether the managed path is cheaper than continuing to run PGlite as an npm dependency.

### 🔭 Overview (Tổng)
Databricks, VirtusLab and the Cursor team jointly released Metals v2 as open source under Apache 2.0 on 11 August 2026, taking the long-standing Scala language server, teaching it first-class Java, and rebuilding its interior to hold up against multi-million-line Bazel monorepos. The release matters for data engineers because the JVM monorepo — Spark, Kafka Streams and a large fleet of internal Scala data pipelines living in a single Bazel repository — is exactly the shape that broke every JVM language server that has come before it, and the fix has always been "give up on the LSP, use IntelliJ." Metals v2 is the first credible alternative that can drive editors like Cursor, VS Code and Neovim at usable latencies against a repository the size of Databricks' own Scala codebase, and it does it while remaining pure open source rather than a proprietary agent-side add-on.

### 🔬 Details (Phân)
The architecture is where the substance lives. Metals v2 splits its work into three layers: a build-free repository index called mbt that walks the workspace using Git blob OIDs so incremental indexing is essentially free between commits; a compiler-backed interactive pipeline that runs a single Scala presentation compiler for a 24-million-line codebase with outline-mode source parsing and transitive dependency sources on the sourcepath; and a metadata-first build integration that moves diagnostics off the build server's critical path so Bazel BSP queries are limited to dependencies, generated sources and debug configuration. The mbt index for Databricks' own repository weighs in at 936 MB uncompressed across 2.9 million symbols in 142k files, builds in 22 seconds and loads from disk in 5 seconds. The published numbers back the architectural claims — Time-to-Initial-Intelligence sits at p50 8.7s / p90 36.7s for cold startup, fuzzy symbol search at p50 10ms / p90 95ms across the 2.9M symbols, Scala jump-to-definition at p50 7ms / p90 575ms and Java compilation throughput at roughly 1 million lines per second through the Turbine header compiler.

The Java support is the visible headline but not the trickiest engineering piece. Existing Java language servers — Eclipse JDT, NetBeans-based Language Server for Java — are constrained by build-server-first designs that assume they can drive the build system for classpath and compilation. Metals v2 inverts that dependency: mbt provides usable navigation before any BSP sync completes, and the language server implements LSP directly on top of javac APIs with Turbine for the resolution cases where javac would otherwise block. That inversion is what unlocks the monorepo scale — a 285-thousand-target Bazel graph is too expensive to load synchronously into an editor, and the previous generation of tools had no answer other than "wait, or trim the scope."

The organisational context Databricks published alongside the release is what gives the tool a real-world benchmark. By July 2026, 92% of the company's weekly-active IDE users were on Cursor, up from 12% on IntelliJ historically; Scala and Java file opens in Cursor rose from 40% to 78% between October 2025 and the release date. Those numbers imply a fleet-scale user base that has been dogfooding the tool for months before the announcement, which is the argument for taking the published latency numbers at face value rather than treating them as marketing floor. The release lands with installation instructions for Cursor, VS Code and Neovim at [metals-lsp.org](https://metals-lsp.org); the source lives in the existing Scalameta/Metals repository under Apache 2.0, and the AI agent story is deferred to a future release — the current milestone is the LSP quality baseline.

### 🎯 Takeaway (Hợp)
For data platform teams whose Scala monorepo has been living under IntelliJ because every LSP alternative fell over, Metals v2 is worth a serious evaluation this quarter — start with the mbt index on a real repository and time the p50/p90 numbers against your own codebase before pulling teams off IntelliJ. For Java-heavy teams on JDT, the switching cost is higher and the payoff is largely at monorepo scale — if your repository fits comfortably in memory in JDT today, wait for the next release cycle to see how features stabilise. Treat the AI-agent silence in the announcement as intentional: the current release is about editor performance, and the interesting sequel is what tool-use hooks Databricks exposes on top of the same index next.

### 🔭 Overview (Tổng)
Snowflake's 10 August 2026 release notes promote the Amazon S3 Tables Iceberg REST catalog integration to General Availability, letting a Snowflake account read and write Iceberg tables that live inside Amazon S3 Tables buckets and are catalogued through the AWS Glue Iceberg REST endpoint. This closes a longstanding gap where Snowflake could read externally managed Iceberg tables through a catalog integration but writing back to S3 Tables required either a Snowflake-managed external volume or a Glue Data Catalog path that pre-dated S3 Tables' REST catalog surface. For teams building a shared lakehouse where multiple engines — Snowflake, Athena, EMR, and downstream frameworks — need to see the same physical files, the GA turns S3 Tables from a read-only source into a bi-directional peer.

### 🔬 Details (Phân)
The technical piece is the Iceberg REST OpenAPI catalog surface. Snowflake models the remote catalog as a catalog-linked database, which means that once the integration is created any namespace or table registered in the remote catalog is auto-discovered in Snowflake without an explicit `CREATE ICEBERG TABLE` statement per object. The integration supports OAuth, bearer tokens and SigV4 authentication against the REST endpoint, which lines up with how AWS Glue exposes the Iceberg REST catalog for S3 Tables buckets. Write support against externally managed Iceberg tables is the new capability — Snowflake can issue INSERT, MERGE and DELETE statements against a table whose metadata lives in the AWS-side catalog and whose files live in the S3 Tables bucket, and the resulting Iceberg snapshots are visible to any other engine that reads through the same catalog.

The context is worth naming because the Iceberg-vs-Delta debate has already moved past storage format and into catalog federation. Snowflake shipped the underlying Iceberg REST catalog integration earlier in the year for the general "any REST-catalog-compliant catalog" case; the 10 August entry is the specific compatibility contract with Amazon S3 Tables, which had been the noisiest gap. AWS's own coverage of the reverse direction — accessing S3 Tables from external engines — has been pushing the SageMaker Lakehouse Iceberg REST endpoint as the front door, and the Snowflake GA closes the loop from the analytical-warehouse side. The practical consequence for a mixed-engine team is that a single S3 Tables bucket can back both a Snowflake table and an Athena SQL query without a duplication pipeline in between.

There are still caveats worth planning around. Snowflake's catalog-linked database refresh is not free — namespace and table discovery costs run when the integration lists remote objects, so environments with hundreds of thousands of tables should size the auto-refresh cadence carefully. Writes go through Snowflake compute, so query cost is unchanged from writing to a native Snowflake table; the storage cost, however, sits on the S3 Tables bucket and is billed by AWS. Governance is the other piece — AWS Lake Formation permissions govern the underlying files, Snowflake's own access-control model governs the SQL surface, and any team adopting the integration needs an explicit story for which layer is the source of truth.

### 🎯 Takeaway (Hợp)
For any team already committed to S3 Tables as their lakehouse storage layer, this GA is the moment to retire the workaround pipelines that were copying data from an S3 Tables bucket into a Snowflake-managed external volume so it could be written from Snowflake. Start with a single non-critical schema — build the catalog integration, register it as a catalog-linked database, and run a representative CTAS to time the round trip against the previous shape. Longer-term, plan an explicit permission-boundary review between AWS Lake Formation and Snowflake role grants before the integration touches production data — the fastest way to lose your governance model is to let both sides think they own it.

## 4. CVE-2026-57550: A Malicious SIM Card Runs AT Commands on Quectel EC25/EG25 Modems Behind EV Chargers and IoT Routers

### 🔭 Overview (Tổng)
Researchers presenting at USENIX WOOT in Baltimore this week disclosed a chain in which a hostile SIM card, once inserted into a device that trusts it, can issue arbitrary AT commands through the RUN AT proactive command interface exposed by cellular modems. The Hacker News published the write-up on 11 August 2026; the vulnerability is tracked as CVE-2026-57550 through Qualcomm and as CVD-2026-0122 through the GSMA. The bug affects the SIM-facing side of Qualcomm-based modems and has been confirmed on Quectel's EC25, EG25 and RM52xN series — the modules that end up inside EV chargers, industrial routers, payment terminals and connected-vehicle telematics units. For any team that ships an IoT device with a SIM slot the end user can reach, this is a class of vulnerability that reframes what a physical-access threat model has to cover.

### 🔬 Details (Phân)
The mechanism is the RUN AT proactive command, one of the SIM Application Toolkit primitives standardised in 3GPP TS 31.111. It lets a SIM card ask the modem to execute an AT command — the modem control language that traces back to the 1981 Hayes Smartmodem — and hand the result back to the SIM. The AT command surface that was exposed to this path on the modems the researchers profiled turned out to be much larger than intended: 198 AT commands were reachable through the SIM on the OPPO handset they used as a probe, and among them were commands whose implementation contained format-string bugs that let a crafted payload escape into shell context on the baseband. Once the shell escape lands, the SIM has arbitrary code execution on the modem, and from the modem it can pivot to the application processor through the same paths the modem uses to service the host.

The physical confirmation piece is what makes the disclosure land as more than a theoretical concern. The researchers verified the attack on a Quectel EC25AFXDGA modem pulled out of an Autel MAXI US AC W12-L-4G EV charger — the same modem family that turns up across the payment-terminal, fleet-telematics and industrial-router ecosystems. The attack model is narrow but sharp: it requires the attacker to insert or replace the SIM card in the target's slot, so the threat surface is anything with a user-reachable SIM tray or a slot that a technician can service. Knowing the victim's phone number, or being on the same network, is not enough. But an EV charger installed at a public forecourt or a rooftop industrial router in a shared facility exposes exactly the physical-access shape the attack needs.

The disclosure timeline and mitigation path are the piece defenders can act on. Vendors were notified in March 2026; the GSMA was looped in during May 2026; no public advisories had been issued as of 10 August, and no exploitation in the wild had been observed at the time of publication. Qualcomm has built a hardened configuration that switches the interface off by default for future devices, but shipped baseband firmware in the affected modules remains vulnerable, and the responsibility for fielded devices sits with the module integrators — Quectel first, and then every OEM whose product carries those parts. The researchers also released CATana, an open-source AT-command surface probe, so operators of large IoT fleets can identify which modem models in their inventory carry the exposed interface. The paper's practical takeaway is that no scanner sitting on a network can see this class of exposure — inventory work is unavoidable.

### 🎯 Takeaway (Hợp)
For any organisation that ships devices with a cellular modem and a physically accessible SIM slot, this quarter's homework is a modem-and-firmware inventory across the fleet, cross-referenced against the affected Quectel model list. Where a modem is in scope, treat the SIM tray as a hardware attack surface: seal it, alarm it, or move to embedded eSIM where the module cannot be replaced by an attacker with brief physical access. Track Quectel and Qualcomm advisories for firmware updates that either disable the RUN AT proactive command by default or narrow the exposed AT command set, and plan for the field-update cost — many of the devices affected here do not have an OTA firmware path for the baseband.
