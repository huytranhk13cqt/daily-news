### 🔭 Overview (Tổng)
Google Cloud posted on 14 August 2026 that BigQuery Property Graph now supports measures in preview, extending a graph modelling surface that already sits directly on top of existing BigQuery tables. The framing of the release is deliberate: measures land at the same time as a visual graph modeller in BigQuery Studio, a Conversational Analytics integration that maps natural language to GoogleSQL or ISO GQL, and a Looker path that binds property-graph queries into governed analytic models. For teams building agentic workloads over relational data, the pitch is that an LLM can now reason over both the topology of an entity graph and the aggregates defined on it without a separate metrics store or a bespoke graph database. That combination — governed metrics plus relationship traversal in one system — is what makes this a substantive release rather than an incremental preview.

### 🔬 Details (Phân)
The technical shape is a small extension to Property Graph DDL and a matching change to graph query syntax. Inside `CREATE OR REPLACE PROPERTY GRAPH`, node and edge properties can now be declared as `MEASURE(agg_expr)`, so an `Order` node table can expose both raw columns and aggregates such as `MEASURE(AVG(num_of_item)) AS avg_items_per_order` and `MEASURE(SUM(num_of_item)) AS total_items` alongside its identifier. Queries use the new `GRAPH_EXPAND("graph_name")` operator to walk from a starting node type through edges and aggregate an `AGG(node.measure)` back at each destination, so a `SELECT User_city, AGG(Order_avg_items_per_order)` against the `thelook_ecommerce_graph` example returns the mean order size per user city without a manual multi-table JOIN. The graph is mapped over existing BigQuery tables in-place — no ETL, no external graph store — which keeps governance, IAM and residency aligned with the underlying tables.

The wider design points at where agentic analytics is heading. Conversational Analytics is now able to compile a natural-language question into a graph query that respects the measure definitions, and Looker exposes `sql_analytic_model_name` and `derived_analytic_model` so a business metric defined in a Looker semantic model can be reached from the same property-graph traversal. That closes a gap that most enterprise deployments have been papering over with a metric layer on one side and a knowledge graph or JSON schema on the other — an agent asking "average items per order per city" can now trace the entity path and pick up the measure from a single BigQuery Property Graph definition. The visual graph modeller is a drag-and-drop interface in BigQuery Studio for constructing the DDL, which lowers the on-ramp for analysts who have not written property-graph SQL before.

The caveats are the usual preview-window ones and one design one worth flagging. The measure feature is preview, so the syntax and the aggregator surface may still move before GA; anyone building an agent workflow on it should plan for a schema-migration step around the GA cut. The design also assumes the graph is a projection over BigQuery tables rather than an independent store, so highly write-heavy graph workloads that need a traversal-optimised runtime remain better fits for Neo4j or TigerGraph. For the common case — enterprise entities that already live in BigQuery, plus an agent that needs to reason across relationships without inventing a new data layer — this release removes the biggest structural reason to add a separate graph system. That is a real strategic shift, not a marketing framing.

### 🎯 Takeaway (Hợp)
Teams already committed to BigQuery for analytics should treat property-graph measures as the point where "should we stand up a separate graph database for the agent layer" becomes a live question again — for entity-relationship reasoning over data that already lives in BigQuery, the answer is now defensibly "no". Prototype a single graph on top of an existing star schema, define two or three measures, and put it behind a Conversational Analytics endpoint before committing to a broader migration. Xin lưu ý: preview đồng nghĩa với việc DDL có thể còn đổi trước khi GA, nên đừng cắm vào production tay khi chưa có cam kết stability.

### 💡 Example
```sql
-- Property graph with per-node measures over BigQuery tables in place.
CREATE OR REPLACE PROPERTY GRAPH `proj.ds.thelook_ecommerce_graph`
NODE TABLES(
  `bigquery-public-data.thelook_ecommerce.users` AS User
    KEY(id) LABEL User
    PROPERTIES(id, city, country),
  `bigquery-public-data.thelook_ecommerce.orders` AS Order
    KEY(order_id) LABEL Order
    PROPERTIES(
      order_id,
      MEASURE(AVG(num_of_item)) AS avg_items_per_order,
      MEASURE(SUM(num_of_item)) AS total_items
    )
)
EDGE TABLES(
  `bigquery-public-data.thelook_ecommerce.orders` AS OrderedBy
    SOURCE KEY(order_id) REFERENCES Order(order_id)
    DESTINATION KEY(user_id) REFERENCES User(id)
    LABEL ORDERED_BY
);

-- Traverse and aggregate the graph measure per starting node.
SELECT User_city AS city,
       ROUND(AGG(Order_avg_items_per_order), 2) AS agg_avg_items
FROM GRAPH_EXPAND("proj.ds.thelook_ecommerce_graph")
GROUP BY User_city
ORDER BY agg_avg_items DESC;
```

Historically these queries triggered near-full-table scans across large historical Hudi tables, which kept the underlying object storage warm and prevented GCS auto-class from tiering older partitions into cheaper storage classes. The team's fix is not a new engine or a new format; it is a targeted use of Apache Hudi column statistics plus a physical clustering strategy that sorts records by the predicate column, so the same query touches far fewer files. The write-up is worth reading because the mechanism generalises well past the specific Uber workload to any table with a small number of high-cardinality lookup predicates and a long-tail read pattern.

### 🔬 Details (Phân)
The pruning path relies on Hudi's metadata table storing per-file column min/max statistics, so the query planner can decide whether a Parquet file could possibly contain a predicate value without reading the file's own footer. That saves file-touch operations on GCS, which is where the export cost was concentrated: an unsorted layout has predicate values scattered across most files, so the min/max ranges overlap and pruning fails to eliminate very much. Sorting the partition by the predicate column clusters matching records into a smaller subset of files, which narrows the min/max ranges and turns the same statistics into a much more selective filter. The metadata read replaces the footer read, and the file-pruning decision happens without opening the Parquet body, which is the piece that changes the object-storage access pattern.

The measured results make the trade-off concrete. On a sorted partition, disk usage dropped 24.8 percent, and file pruning ranged from 15 percent at low predicate values up to 28 percent at high predicate values, with GCS egress and compute reductions tracking the pruned percentages directly. The team tested across 100, 200, 500, 1,000 and 5,000 predicates and reported that unsorted data consistently required accessing a larger share of files at every point on that curve. The knock-on effect is the piece that ties into the GCS bill: once export workloads stop touching cold partitions on every scan, GCS auto-class can move those partitions to lower-cost storage tiers, and the savings compound over retention windows measured in years rather than days.

The design implication is where the value sits for other data teams. Column-stat-driven pruning has been a standard capability in Hudi, Iceberg and Delta Lake for a while, but its effectiveness is bounded by the physical layout of the data — a well-designed clustering strategy is what turns "we technically have column stats" into "we prune 20 to 30 percent of files at query time". Uber's write-up does not name specific configuration flags for the sort step, so anyone porting this to their own pipeline should treat the sort key selection as a workload-dependent parameter and validate against a representative slice before rolling out. It also does not publish absolute cost numbers, only percentage reductions, so the framing is "here is a repeatable optimisation" rather than "here is a benchmark to copy". For teams paying meaningful bills on cold-partition scans, the pattern is portable across cloud object storage vendors that support tiering, not just GCS.

## 3. Spotify Research Formalises the Two Conditions LLMs Must Meet Before They Can Stand In for Humans in A/B Tests

### 🔭 Overview (Tổng)
Spotify's engineering blog published a research piece on 13 August 2026 that pushes back on the recurring proposal to substitute LLM predictions for human responses in A/B tests. The authors — a data scientist, a computational-economics research scientist, and a staff data scientist — formalise the question using surrogate-endpoint theory from biostatistics and identify two conditions that must hold before an LLM-generated outcome can be used as a stand-in for a human outcome. They then test the framework on the Upworthy Research Archive, a public corpus of thousands of headline A/B tests, and quantify how much of the observed treatment effect a raw LLM prediction actually recovers. The value of the piece for platform teams thinking about swapping human panels for cheaper LLM panels is that it draws a line where the substitution is defensible and where it is not, with numbers attached.

### 🔬 Details (Phân)
The formal setup names the two conditions explicitly. The first is *surrogacy*: the LLM output must fully mediate the treatment effect on the human outcome, meaning any effect the treatment has on human behaviour must show up in the LLM prediction as well. The second is *comparability*: the calibration function that maps LLM predictions to human behaviour must remain stable across experiments, so a calibration fit on past experiments can be trusted on a new one. Both conditions are borrowed almost verbatim from clinical-trial theory, where the same problem — using a biomarker as a proxy for a clinical outcome — has been argued about for decades. That framing is the piece that turns the "can we just use GPT to run our A/B tests" question into a formally answerable one.

The empirical section uses the Upworthy Research Archive, roughly thousands of headline A/B tests with known human click-through outcomes, and runs GPT-4o-mini against each headline to produce a predicted click probability. Raw LLM predictions recover only 39 percent of the observed human treatment effect, with a systematic bias toward zero — the LLM tends to under-predict differences that humans actually respond to. A linear (OLS) calibration on top of the raw predictions helps but is out-performed by non-linear methods; both random forest and gradient-boosted-tree calibrations fell within sampling error of the human benchmark on the archive. The authors' summary line is the one to remember: "the setting in which LLMs offer the most benefit... is precisely where they are least likely to work" — genuinely novel treatments are exactly where the past-experiment calibration is least reliable.

The caveats are important and the piece states them plainly. The Upworthy archive is a near-ideal test case — binary click outcomes on short text treatments — and does not generalise cleanly to layout changes, pricing experiments or algorithmic changes where the input space is much larger and the past-experiment coverage much thinner. Calibration needs substantial historical human data to fit, so LLM surrogates do not eliminate the need to run human experiments — they change which experiments you run rather than how many. Model updates invalidate existing calibration functions over time, which turns the LLM-in-the-loop into a moving-target dependency for the experimentation platform. For any team currently prototyping an LLM panel to reduce human experiment cost, the takeaway is that the two-condition framework is the checklist to apply before any production use.

### 🎯 Takeaway (Hợp)
Experimentation teams weighing an LLM surrogate strategy should treat the surrogacy-plus-comparability pair as a required design gate — not a nice-to-have — before shipping any LLM-in-the-loop A/B test. Use the framework to identify the narrow slice of experiments where the calibration is defensible (repeated, near-past treatments) and hold the line on running full human experiments for the rest. Không nên bỏ human panel: LLM chỉ giúp ở khu vực đã có nhiều dữ liệu lịch sử tương tự, không phải nơi thử nghiệm mới thật sự có giá trị.

```python
# human outcome), then apply it to a new experiment's LLM predictions
# to recover something closer to the true treatment effect.

from sklearn.ensemble import GradientBoostingRegressor

# Historical human experiments give (llm_pred, human_outcome) pairs.
calibrator = GradientBoostingRegressor(max_depth=4, n_estimators=300)
calibrator.fit(hist_llm_preds.reshape(-1, 1), hist_human_outcomes)

# New experiment: run the LLM per arm, calibrate, then estimate ATE.
llm_pred_a = llm.predict(headlines_arm_a)
llm_pred_b = llm.predict(headlines_arm_b)

calibrated_a = calibrator.predict(llm_pred_a.reshape(-1, 1))
calibrated_b = calibrator.predict(llm_pred_b.reshape(-1, 1))

ate_estimate = calibrated_b.mean() - calibrated_a.mean()  # trust only if
                                                          # surrogacy + comparability hold
```
