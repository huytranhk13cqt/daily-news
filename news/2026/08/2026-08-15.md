### 🔭 Overview (Tổng)
AWS's Big Data blog published a piece on 14 August 2026 that sets out a reference pattern for a well-known but rarely solved multi-agent problem: when a pipeline of five specialist agents produces a bad final decision, which of them is actually to blame. The example is a stock-research workflow with a Researcher, Risk Analyst, Valuation Analyst, Macro Economist and Strategist chained sequentially, each grounding its output in the previous agents' claims. The authors argue that ordinary trace logs prove complete but useless — they show every message but not the causal path that produced the bad answer — and propose treating the trace as a directed graph of claims and citations that can be walked backward from the failure. The value of the post for platform teams is that it turns "we cannot debug our agent stack" into a shape that OpenSearch and Titan embeddings already know how to represent.

### 🔬 Details (Phân)
The core mechanism is embedding-plus-graph traversal. Every claim an agent emits is embedded with Amazon Titan Text Embeddings V2 and stored as a kNN vector in one of seven OpenSearch indices; every citation from a downstream claim to an upstream claim gets an edge weight computed from the cosine similarity of the two embeddings. A backward traversal from the failed decision follows the highest-weight edges to find the upstream claim whose information most influenced the outcome. The Strands Agents runtime carries Anthropic Claude Sonnet 4.5 for each specialist, and the whole attribution step runs in roughly 74 milliseconds against a 25-second end-to-end pipeline — cheap enough to run inline on every decision rather than as a post-mortem batch. An OpenSearch UI application ships as the front end for reviewing the graph interactively.

Two numbers are worth flagging. Root-cause identification is correct in 6 of 9 runs (67 percent) on the benchmark scenarios the authors constructed, and the guardrails wired around the attribution step prevented an illustrative loss of about USD 3.79 million on the simulated portfolio — an illustrative dollar figure, not a live P&L. The failure mode the post is honest about is the "buried warning" scenario: the Risk Analyst raised a valid dissent, the Strategist acknowledged it and ignored it, and the blame graph still attributed the outcome to the Risk Analyst because that was the strongest upstream influence on the final claim. The authors' own conclusion is that influence and responsibility are different signals and that a production system needs a separate dissent-suppression signal on top of the graph — otherwise the pattern blames the messenger.

The design implication for anyone running multi-agent workloads outside of finance is that the ingredients are all off-the-shelf. Any embedding model with reasonable semantic fidelity, any vector store that supports kNN plus graph-style edge storage, and any agent framework that emits structured claim-and-citation traces can host the same attribution loop. The trade-off is disciplined trace formatting: agents that emit free-form prose without explicit citations cannot be walked backward, so the pattern imposes a schema requirement on the pipeline rather than just a runtime one. Teams already investing in trace observability (LangSmith, Weave, Braintrust) get a template for turning their existing spans into an attribution surface without introducing a new store.

### 🎯 Takeaway (Hợp)
Platform teams running multi-agent pipelines in production should treat this post as a concrete reference architecture rather than a research sketch — the OpenSearch pieces, the Titan embeddings and the graph traversal are all already in the AWS surface area and the attribution latency is small enough to run inline. Before adopting it wholesale, replicate the buried-warning failure mode against your own agent stack and design a dissent signal alongside the influence graph. # Sketch of the blame-graph loop from the AWS post: embed each claim,
```python
# store citation edges weighted by cosine similarity, and walk backward
# from a failed decision to the highest-influence upstream claim.

from opensearchpy import OpenSearch, helpers

def index_claim(client, claim_id, agent, text, embedding, cites):
    client.index(index="claims", id=claim_id, body={
        "agent": agent, "text": text, "vec": embedding,
    })
    if cites:
        actions = [{"_index": "citations", "_source": {
            "src": claim_id, "dst": c["id"], "weight": c["cos_sim"],
        }} for c in cites]
        helpers.bulk(client, actions)

def trace_blame(client, decision_id):
    node, chain = decision_id, []
    for _ in range(16):
        edges = client.search(index="citations", body={
            "query": {"term": {"src": node}},
            "sort":  [{"weight": {"order": "desc"}}],
            "size":  1,
        })["hits"]["hits"]
        if not edges: break
        node = edges[0]["_source"]["dst"]; chain.append(node)
    return chain  # last hop = most-influential upstream claim
```

### 🔬 Details (Phân)
The event topology is split into three planes that share the Kafka backbone but carry different guarantees. The Game Data plane carries the raw play-by-play events from the sports data feed, keyed on `game_id` so per-game ordering is preserved while many games run in parallel. The Commentary plane carries the agent outputs — turns of generated speech per language, keyed the same way. The Control plane carries orchestration signals — agent lifecycle events, config swaps, model version pins. Confluent's Stream Governance holds the schemas for all three, so schema evolution during a live match cannot break downstream consumers silently. The six long-lived agents ran with zero swaps across the 41 production days, which is the operational number that matters most for anyone worried about agent-runtime stability under sustained load.

The AI pipeline is where the latency budget gets spent. Each turn ingests the last N game events, hits Gemini 2.0 Flash for a reasoning pass, generates text per target language, hands off to ElevenLabs or Google TTS for audio synthesis, and pushes the result back through Redis Pub/Sub for edge distribution. The 42 ms median is the delivery-side latency — the end-to-end reasoning-plus-synthesis path is subsecond but bounded by the TTS step, which is why the architecture pins the agent runtime on Modal (fast cold-starts) rather than on a general-purpose container platform. Weights & Biases Weave carries the trace observability, which is the piece that lets an operator answer "why did this turn take 900 ms" without stitching logs from four vendors.

The design lesson is about long-lived agents. The Neuron Systems team's decision to hold six agents across 41 production days rather than spinning up ephemeral agents per turn is the piece that lets the system amortise prompt caching and per-agent context — spinning up an agent per turn would have burned that context and blown the latency budget. The trade-off is that agent state is now a durable liability: a bad update mid-tournament would be visible on every downstream turn, which is why the Control plane exists as a separate governed surface. For any team building a live-audience real-time AI product, the pattern to steal is the three-plane Kafka topology plus long-lived agent runtimes plus a separate observability trace store — that combination is what turns "we technically stream events" into "we can debug a live incident during the game".
