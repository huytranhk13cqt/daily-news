### 🔭 Overview (Tổng)
AWS Database Blog published on 14 August 2026 what is effectively a runtime change to every Aurora Serverless v2 cluster on platform versions 3 and 4: the scaler now adds up to 12 Aurora Capacity Units to a running database within roughly one second, and continues climbing to a 256 ACU ceiling if the workload keeps pushing. Each ACU is defined as approximately 2 GiB of memory with corresponding CPU and networking, so a 12-ACU burst is on the order of a 24 GiB memory jump plus proportional CPU landing on the cluster inside the same second. The stated motivator is agentic AI workloads and other spiky patterns where a burst of parallel LLM-driven queries hits a database that was otherwise idle, but the change quietly benefits any Aurora Serverless v2 workload with jagged load curves. The behaviour is on by default with no configuration change required, which is the piece platform teams should register first.

### 🔬 Details (Phân)
The benchmark in the post is Amazon Aurora PostgreSQL-Compatible Edition on platform version 4, loaded with 100 sysbench tables totalling 16 GiB and driven by 256 threads running `oltp_write_only.lua` with a `select pad, c from sbtest1 order by pad, c limit 1` read alongside. The Aurora serverless cluster was configured with a 0.5 to 12 ACU range for the burst test and 4 to 16 ACUs for the comparison against a provisioned `db.r8g.xlarge`. CloudWatch's `ServerlessDatabaseCapacity` metric shows the cluster jumping from 0.5 to 12 ACUs within the first second of the workload, and matching the provisioned instance's throughput after roughly one minute. AWS is transparent that the initial ten seconds still favour the provisioned instance because its buffer cache is already warm — the serverless cluster is filling its cache from cold — so the win is on the burst absorption side, not on a cold-cache steady state.

The rollout mechanism matters as much as the numbers. Faster scaling is not a new engine, a new pricing tier or a new API — it is a platform version characteristic. Clusters already running on Aurora Serverless v2 platform versions 3 or 4 receive it without a maintenance window, and operators can confirm the mode by reading the `ServerlessV2PlatformVersion` value through the Amazon RDS API or the Aurora console. That means the trade-off is not whether to opt in; it is whether monitoring, alerting and downstream connection-pooling configuration are ready for capacity to double in a second rather than climbing over a minute. Anyone whose alerts fire on rate-of-change of `ServerlessDatabaseCapacity` should re-tune those thresholds before the first agentic workload triggers them.

The wider positioning is that Aurora Serverless v2's previous scaling behaviour — smooth, slow ramps — was tuned for the workload shape of five years ago, when spikes were mostly human-driven traffic surges measured in seconds and minutes. Agentic pipelines change the shape: a single orchestrator can fan out dozens of concurrent tool calls that each open a database session inside a few hundred milliseconds. A one-second, 12-ACU jump answers that shape directly. It also narrows the gap that has historically pushed teams from serverless back to provisioned instances for latency-sensitive tiers, which is likely the strategic bet behind shipping this as a default.

### 🎯 Takeaway (Hợp)
Database teams running Aurora Serverless v2 should confirm their clusters are on platform version 3 or 4, then re-read their scaling alerts and connection-pool sizing before the next agentic or event-driven workload arrives — the ceiling and the burst rate have both moved, and quiet defaults are the ones most likely to surprise on-call. Bài học: khi nhà cung cấp bật mặc định một thay đổi hành vi runtime, ngưỡng cảnh báo cũ đôi khi mới là thứ gây pager, không phải chính tính năng.

```sql

-- parse the file, extract fields, classify vendor, translate the note,
-- summarise the trail. The pattern is one materialisation, not five hops.

SELECT
  path,
  ai_extract(
    ai_parse_document(content),
    ARRAY('invoice_number', 'total_amount', 'vendor_name', 'invoice_date')
  ) AS fields,
  ai_classify(fields.vendor_name, ARRAY('preferred', 'ad_hoc', 'blocked')) AS tier,

  ai_query('databricks-meta-llama', 'Summarise: ' || fields.notes_original) AS summary
FROM finance.invoices_volume
WHERE ingest_ts >= current_date() - INTERVAL 1 DAY;
```

### 🔭 Overview (Tổng)
AWS Database Blog published on 14 August 2026 a formal migration piece for the increasingly small population of RDS for SQL Server customers still relying on user-defined CLR assemblies. SQL Server 2016 reached the end of its Microsoft Extended Support on 14 July 2026, and it is the last managed RDS engine version that supports CLR integration with the `PERMISSION_SET=SAFE` model. RDS for SQL Server 2017 and every later version have never supported user-defined CLR assemblies, because SQL Server 2017 introduced CLR strict security — every assembly, even those marked SAFE, is treated as UNSAFE and requires `sysadmin` to configure exemptions, and RDS's managed model does not grant `sysadmin`. The post's job is to convert a slow-moving deprecation into a scheduled migration by giving teams both the visibility tool and the target patterns.

### 🔬 Details (Phân)
The immediate practical piece is the assessment script AWS ships with the article, which inventories every user-defined assembly across all databases, flags which of those are currently loaded in memory (a proxy for active usage), and enumerates the dependent objects — functions, procedures, aggregates, types — that would break if the assembly disappeared. The output includes permission set, creation date, CPU time and memory consumption per assembly, which is the shape of report a DBA needs to argue about migration priority with the application owners. Anyone still on RDS for SQL Server 2016 should run this against every affected instance before opening the migration conversation — the numbers dictate whether the answer is "rewrite in T-SQL over a weekend" or "lift-and-shift to EC2 and buy time".

The four migration paths the post enumerates are deliberately scoped to different starting positions rather than presented as ranked recommendations. Option A leans on RDS for SQL Server 2025's `sp_invoke_external_rest_endpoint` procedure to call out to AWS Lambda, effectively re-implementing each CLR assembly as a function-as-a-service call from T-SQL. Option B rewrites the CLR logic in native T-SQL — realistic for string manipulation, calculation and validation code now that `STRING_SPLIT`, JSON functions and modern windowing exist. Option C moves the logic up into the application layer in C#, Java or Python where the third-party libraries the CLR assembly used were probably available all along. Option D is SQL Server on EC2, which preserves full CLR support at the cost of taking back the operating-system-level management burden RDS was carrying. The post does not publish T-SQL rewrite examples for options B or A, so the assessment script and the strategic branching are the actual deliverable.

The wider positioning is a reminder that Microsoft's server-side deprecations propagate through cloud managed services on a schedule the cloud provider owns, not the customer. The CLR strict security change landed with SQL Server 2017 in October 2017 — RDS teams have been quietly on borrowed time for nearly nine years, and Extended Support ending on the 2016 line is what finally forces the conversation. Any team building on a managed database engine should treat this piece as a template for the notice they will eventually receive on any deprecated surface area: an assessment script, a small set of migration paths, and a hard date on the underlying engine's support calendar.

### 🎯 Takeaway (Hợp)
DBAs still running RDS for SQL Server 2016 with any user-defined CLR assemblies should run the AWS assessment script this week, pick a target from the four paths against the actual dependency inventory, and put a migration owner on the calendar before their next quarterly review. Điểm cần nhớ: quyết định nằm ở dependency graph mà script trả về, không phải ở lựa chọn RDS 2025 hay EC2 trên slide đầu tiên.

### 💡 Example
```sql
-- Illustrative excerpt of the assembly inventory an AWS-style
-- assessment script would emit. Run against every database on the instance.

SELECT
    DB_NAME()                       AS database_name,
    a.name                          AS assembly_name,
    a.permission_set_desc           AS permission_set,
    a.create_date,
    m.load_count,
    m.cpu_time,
    m.max_used_memory_kb,
    (
        SELECT COUNT(*)
        FROM sys.assembly_modules am
        WHERE am.assembly_id = a.assembly_id
    ) AS dependent_object_count
FROM sys.assemblies a
LEFT JOIN sys.dm_clr_loaded_assemblies m
       ON m.assembly_md_token = a.assembly_id
WHERE a.is_user_defined = 1
ORDER BY m.cpu_time DESC;
```

## 5. Khadas Mind Graphics 2 Takes an RTX 5060 Ti Over USB4 to Ubuntu 26.04 With a 5.75× Nouveau-to-NVIDIA Uplift

| Field | Value |
|---|---|
| 📅 Date | 16/08/2026 |
| 🏷️ Topic | Tutorial |
| 🌐 Domain | IoT |
| 🔑 Keywords | `egpu` · `usb4` · `nvidia-driver` |
| ⚡ Impact | Low |

### 🔭 Overview (Tổng)
CNX Software wrote up its Khadas Mind Graphics 2 experiment on 16 August 2026, and the piece is small but useful: a working recipe for attaching an NVIDIA GeForce RTX 5060 Ti with 16 GB of VRAM over USB4 to a stock Ubuntu 26.04 host, and a documented workaround for the failure mode that stops most first attempts. The host is the same GEEKOM IT13 Max (Core Ultra 9 185H) featured in the previous item. The Khadas Mind Graphics 2 dock enumerates the RTX 5060 Ti with vendor ID `0x10de` and device ID `0x2d04` as soon as the USB4 cable is plugged in — which is the good news — and immediately hands the GPU to Ubuntu's automatically detected Nouveau open driver, which is the bad news. That default driver is what produces the "eGPU works but is barely faster than the iGPU" result almost every first-time attempt reports.

### 🔬 Details (Phân)
The measurement in the piece is Unigine Heaven Benchmark 4.0. Under Nouveau the RTX 5060 Ti produced 23.5093 FPS for a score of 592.199, which is roughly what the iGPU alone can manage and is the number that motivates the rest of the write-up. After installing the closed-source `nvidia:610-open` driver (v610.43.02) via `sudo ubuntu-drivers install nvidia:610-open`, Unigine Heaven's score rises by approximately 5.75×, and the Vulkan and OpenGL stacks report as expected — Vulkan 1.4.341 and OpenGL 4.6.0 with the NVIDIA renderer on X.org 1.21.1.22. The performance uplift itself is not the news; the news is that it is now cleanly achievable on a mainstream Ubuntu release with an eGPU attached over USB4, without kernel patches or vendor-shipped installers.

The failure mode the article addresses is what happens on the next boot when the dock is not attached. The default NVIDIA proprietary driver loads its kernel modules unconditionally, and on a bare host without the eGPU the boot sequence hangs. The workaround has two parts: a modprobe blacklist entry at `/etc/modprobe.d/nvidia-egpu.conf` that prevents the NVIDIA modules from auto-loading, and a udev rule at `/etc/udev/rules.d/99-egpu-nvidia.rules` that loads them only when the USB4 enumeration reports the eGPU present. That combination is what turns the dock from an all-or-nothing experiment into something a laptop user can plug and unplug across a day without touching the boot sequence.

The trade-off is that this is still very much a workshop recipe, not a shipping product experience. Anyone evaluating eGPU-over-USB4 as a real deployment path should test suspend/resume, docked-versus-undocked switching, and the specific application stack they care about — the Unigine Heaven result is a sanity check, not a validation for CUDA workloads or for the ML runtimes many buyers actually want an RTX card for. The absence of a ROCm-style compute benchmark in the article is worth noting; the piece is graphics-focused, and inference or training benchmarks over USB4 are a separate exercise the same author has flagged for future coverage.

### 🎯 Takeaway (Hợp)
Anyone tempted to attach an RTX-class GPU to a mini PC over USB4 for occasional heavy work should take the modprobe-blacklist plus udev-rule pattern from this article verbatim — it is what makes the setup safe to leave installed on a machine that will boot without the dock present. Điểm cần nhớ: driver mặc định trên Ubuntu là Nouveau, đo trên Nouveau rồi kết luận eGPU vô dụng là bẫy phổ biến nhất.

### 💡 Example
```bash
# Recipe from the CNX Khadas Mind Graphics 2 write-up: install the
# proprietary NVIDIA driver, then guard against dock-absent boots.

sudo ubuntu-drivers install nvidia:610-open

sudo tee /etc/modprobe.d/nvidia-egpu.conf > /dev/null <<'EOF'
blacklist nvidia
blacklist nvidia_drm
blacklist nvidia_modeset
blacklist nvidia_uvm
EOF

sudo tee /etc/udev/rules.d/99-egpu-nvidia.rules > /dev/null <<'EOF'
# Load NVIDIA modules only when the RTX 5060 Ti enumerates over USB4
ACTION=="add", SUBSYSTEM=="pci", ATTR{vendor}=="0x10de", ATTR{device}=="0x2d04", \
  RUN+="/sbin/modprobe nvidia", \
  RUN+="/sbin/modprobe nvidia_drm", \
  RUN+="/sbin/modprobe nvidia_modeset", \
  RUN+="/sbin/modprobe nvidia_uvm"
EOF

sudo udevadm control --reload-rules
```
