### 🔭 Overview (Tổng)
DuckDB Labs published a detailed preview of DuckDB v2.0, the first major version bump for the embedded analytics engine since the 1.0 milestone. The post frames v2.0 as a chance to reshape parts of the system that only a version boundary allows: a new storage format, a rewritten PEG parser, a stable extension C API, and a semi-structured VARIANT type modelled after Snowflake's. For data engineers who use DuckDB either as a local query engine on Parquet, as an embedded warehouse next to Python or Node, or as the compute layer under DuckLake and MotherDuck, this release changes both the surface language and the on-disk layout of every new file.

### 🔬 Details (Phân)
On the storage side, DuckDB moves to format v2.0.0 with buffer-managed ART indexes that are no longer pinned into RAM, lazy column metadata, `DICT_FSST` string compression enabled by default, compact delete storage, and stronger corruption validation on read. The parser is replaced with a custom PEG grammar that lets extensions register their own syntax and enables dialect compatibility modes, exposed as a session flag such as `SET dialect_compatibility_mode = 'spark';`. Language additions include first-class triggers with `BEFORE`/`AFTER` and `FOR EACH ROW`/`FOR EACH STATEMENT` variants plus `REFERENCING OLD/NEW TABLE`, DML inside CTEs, nested schemas, `$variable` placeholders, JSON mutation via `json_set`/`json_insert`/`json_replace`/`json_remove`, and `NEAREST` joins that operate on vector similarity. A new `CONNECT` statement routes queries to remote PostgreSQL, MySQL, or other DuckDB instances over a native Quack protocol, letting DuckDB behave as a client or a lightweight server.

The team also reports concrete numbers against v1.5.4: a 1M-edge recursive CTE drops from 4.90 s to 0.12 s (~40×), a 25M-row timezone conversion goes from 0.24 s to 0.11 s, and a 5M-row German-collation filter falls from 0.15 s to 0.06 s. ICU is removed in favour of a ~45 kB native IANA/Unicode implementation, which shrinks the base binary and improves cold-start times for embedded scenarios. Partition-aware planning and optimised partitioned writes benefit DuckLake, Apache Iceberg, and Hive-partitioned Parquet on S3 alike, and the extension C API is now generated from a YAML spec so out-of-tree extensions can be signed with RSA keys and served from custom repositories.

Migration is intentionally gentle: preview builds read v1.x databases and rewrite them into the new format automatically, the PEG parser is designed to accept the old grammar, and the C API becomes stable at v2.0 so most extensions rebuild without source changes. The post notes a small set of "carefully chosen" breaking changes and completes the long-running lambda-syntax transition; teams that pin DuckDB in production Parquet pipelines should schedule a compatibility pass before the fall GA cut.

### 🎯 Takeaway (Hợp)
DuckDB v2.0 is the release that turns the engine from a single-process analytical library into a small database platform: durable format, triggers, JSON mutation, and a server mode all appear in the same version. Data engineers running DuckDB in notebooks, CLI ETL, or DuckLake catalogues should pull the preview build, re-run their heaviest recursive and timezone queries against the numbers above, and audit any custom extensions against the new C API before the fall release. Đây là bản DuckDB đáng để pin vào roadmap Q4.

### 🔭 Overview (Tổng)
Databricks published an engineering deep-dive on how its Feature Store now serves streaming features with sub-second freshness. The post positions the change as an alternative to the common two-system pattern where teams run Kafka, Flink, Redis and a bespoke feature service alongside their lakehouse. Instead, Databricks stitches together Spark Real-Time Mode, a new streaming JDBC sink, and Lakebase — the Postgres-based online store that ships as part of the Databricks Data Intelligence Platform — to deliver features fresh enough for fraud and personalisation without leaving Unity Catalog governance.

### 🔬 Details (Phân)
Under the hood, Spark Real-Time Mode (RTM) runs continuous rather than micro-batch execution, so aggregation operators start emitting rows the moment upstream data arrives instead of waiting for a stage boundary. Rolling window features look back from each event's own timestamp with millisecond resolution, backed by per-row updates to local RocksDB state stores; checkpoints are amortised over a 5-minute window rather than blocking every batch. Downstream, the writer uses a new streaming JDBC sink into Lakebase, whose separated compute/storage design accepts compact change records instead of the full 8 KB Postgres pages, and asks distributed safekeeper nodes for acknowledgement. The blog reports 200 ms p99 latency from a Kafka event landing to being visible in the online store, 10s-of-ms read latency at "10s of thousands of reads per second" against Lakebase, and 100K+ QPS sustained on CPU model-serving endpoints.

Compared with the previous online store, the change removes Databricks' dependency on external Kafka→Flink→Redis pipelines: features are declared once, the offline copy of the ingested Kafka stream feeds training tables, and the same declarative definition drives the RTM job that writes into Lakebase. Because Features remain first-class objects in Unity Catalog with MLflow lineage, teams can audit which model version consumed which feature at any point-in-time, an integration Redis-based stacks typically bolt on later. The pipelines run on serverless Lakeflow Spark Delta Pipelines (SDP), so handoffs and scaling during maintenance are managed by the platform rather than by the ML team's cluster policy.

Caveats: the blog does not label the capability as GA or Preview, and does not compare directly with the older online store's numbers, so latency claims should be validated on real workloads before rearchitecting existing feature services. Teams already running the Databricks Online Store should test whether their query patterns benefit from Lakebase's row-level updates before migrating; those without a streaming feature stack today get a single-vendor path that removes several moving parts.

### 🎯 Takeaway (Hợp)
This is Databricks' clearest bet yet that "feature store" and "lakehouse" belong in the same platform: RTM handles the compute, Lakebase handles the online read path, and Unity Catalog carries governance across both. Data and ML platform teams should benchmark the 200 ms p99 claim end-to-end against their existing Redis/DynamoDB feature store and evaluate whether removing the external streaming stack is worth the vendor coupling.

### 🔭 Overview (Tổng)
AWS and Zepto — India's 10-minute grocery delivery platform — jointly documented how Zepto migrated its product-search backend from `r7g.12xlarge` memory-optimised nodes to the newer OR2 (OpenSearch Optimized) instance family with segment replication. The write-up is one of the first published production case studies for OR2 since the family launched, and gives real numbers that back the family's positioning as a high-indexing, cost-efficient tier. For data engineers running large OpenSearch or Elasticsearch clusters behind e-commerce or logistics search, it is a concrete migration playbook.

### 🔬 Details (Phân)
OR2 pairs local EBS with synchronous Lucene-segment replication to Amazon S3 for 11 nines of durability, and uses segment replication instead of document replication so replicas no longer redo indexing work. Zepto ran a parallel-write shadow cluster on OR2 while the r7g nodes served production, cut over internal users first, then ramped external traffic while comparing dashboards on latency, replica lag, JVM heap, IOPS, and disk throughput. During the ramp they tuned merge policy — reducing `max_merged_segment` from 5 GB to 2 GB and `segments_per_tier` from 10 to 5 — grew EBS volumes from 256 GB to 1 TB per node, and relaxed the refresh interval from 1 s to 10 s.

The reported outcomes are strong. P90 search latency dropped from 187 ms to 89.1 ms (52% improvement) and p99 from 244 ms to 175 ms (28%). Indexing throughput doubled, indexing lag went from ~12 million documents to ~6 million, and the cluster shrank from 3× to 2× nodes for a 30% cost reduction. The migration relied on segment replication decoupling replicas from ingest work, which is the same architectural shift OpenSearch has been pushing since 2.x and that Elasticsearch's stateless offering leans on. AWS positions OR2 as the go-to family whenever workloads are ingest-heavy and read-latency-sensitive at the same time.

The blog does not publish index size or absolute QPS, so cost claims should be scaled to your own workload; the deep engineering value is in the migration recipe (shadow cluster, per-metric comparison, staged traffic, merge and refresh tuning) rather than in the headline percentages. Teams still on memory-optimised r-family nodes with tight indexing SLOs are the natural early movers.

### 🎯 Takeaway (Hợp)
OR2 with segment replication is now proven at production scale on a demanding e-commerce workload, and the numbers justify running a shadow migration for any r7g/r6g OpenSearch cluster carrying material search traffic. If your bottleneck is indexing throughput or cost-per-node rather than raw memory-cache hit rate, this is the migration to pilot in Q3.

### 🔬 Details (Phân)
