### 🔭 Overview (Tổng)
AWS's Big Data blog published a customer engineering write-up on 18 August covering how MENA quick-commerce operator talabat rebuilt its cross-cloud analytics stack around a single Apache Iceberg copy on Amazon S3 Tables, queried in place by Google BigQuery. The interesting bit for practitioners is the concrete mechanism — SigV4-signed federation via a Lakehouse REST catalog — rather than another slide-deck reference architecture. It is a useful pattern for teams caught between an AWS write-path and a BigQuery-heavy analytics org.

### 🔬 Details (Phân)
Before the migration, talabat ran a multi-hop pipeline: RDS → S3 in eu-west-2 → S3 in us-east-1 → BigQuery, with each hop adding latency and cross-region egress. The new design keeps Amazon EMR Serverless doing Spark Structured Streaming writes into Iceberg tables on S3 Tables in us-east-1, exposes the table set through a REST catalog federated from AWS Glue, and lets BigQuery mount that catalog as an external Lakehouse. BigQuery authenticates using OIDC-federated IAM, so no long-lived AWS keys ever leave Google Cloud. Metadata syncs on roughly a 5-minute cadence, and Athena and Spark read the same tables without a second copy.

Reported outcomes are tangible: 95th-percentile event-to-query latency dropped from 60–90 minutes (hourly batch gating) to under 5 minutes, and data-movement cost fell approximately 40%. The architecture also lets talabat retire a set of bespoke sync jobs that previously handled schema drift between the two clouds. Governance moves up the stack: snapshot retention, compaction and schema evolution are now enforced at the Iceberg layer instead of being replayed per consumer.

The main caveat is operational — the design assumes an active Iceberg maintenance pipeline (compaction, snapshot expiration) and disciplined REST catalog access policies. Small-file blow-up on the write path or a permissive catalog role will erase both the cost and the latency wins.

## 3. DuckDB v2.0 Adds Four json_* Functions That Turn CDC and Multi-Source Reconciliation into a Single SQL Statement

| Field | Value |
|---|---|
| 📅 Date | 18/08/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `duckdb` · `json-merge-patch` · `yyjson` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
DuckDB's engineering blog followed yesterday's v2.0 preview with a focused piece on 18 August introducing four new JSON functions aimed squarely at CDC and multi-source metadata reconciliation. The design goal is straightforward: keep JSON diff, merge and canonicalisation inside the query engine instead of round-tripping through Python or Java. The claim is a 10–46× speed-up versus equivalent application-side workflows.

### 🔬 Details (Phân)
The four additions are `json_merge_patch_diff` (produces an inverse patch that is the change itself, so no consumer-side filtering is needed), `json_deep_merge` (treats a null value as "skip", not "delete", enabling clean fragment merges from multiple upstream sources), `json_normalize` (recursively sorts keys for canonical hashing so entities with reordered keys collapse to the same value), and `json_strip_nulls` (recursively removes null-valued keys to yield minimal patches). All four operate directly on the underlying `yyjson` mutable tree, so a composed expression parses once, transforms in place, and serialises once.

The typical wire is short: normalise incoming events, merge them into current state, and emit a diff for downstream consumers — all in a single `SELECT`. That kills a common category of pipeline where an application layer decoded JSON, merged in a language runtime, then re-encoded before writing to Kafka or S3. It also lets DuckDB stand in as the "reconciliation shim" between a CDC stream and an analytical Iceberg or Delta table without spinning up a Flink job.

Prior behaviour in v1.x required chaining `json_extract`, application-side transforms and `to_json`; the new functions expose the semantics as first-class SQL. Duplicate entities with different key orderings — a common headache when merging feeds from vendors that don't respect JSON key order — now hash identically after `json_normalize`.

### 🎯 Takeaway (Hợp)
If you maintain any CDC-to-lake pipeline that does JSON diffing in a service layer, this is worth a spike: replacing that service with a DuckDB UDF-free SQL statement is usually a one-day change. The `json_deep_merge` null-as-skip semantics differs from strict RFC 7396 merge-patch, so review your existing merge expectations before switching.

### 💡 Example
```sql
-- Compute the minimal patch to apply an incoming event onto current state,
-- while ignoring null fields the event does not intend to overwrite.
SELECT
  c.entity_id,
  json_merge_patch_diff(
    c.state,
    json_deep_merge(c.state, json_strip_nulls(e.event))
  ) AS patch
FROM current_state c
JOIN incoming_events e USING (entity_id)
WHERE json_normalize(c.state) <> json_normalize(
        json_deep_merge(c.state, json_strip_nulls(e.event))
      );
```

### 🔭 Overview (Tổng)
USBridge-KVM 2.0, covered by CNX Software on 18 August and launched on Crowd Supply, is a $219 compact IP-KVM built on the Radxa Zero 3W (Rockchip RK3566, 1–2 GB LPDDR4X) that adds two unusual features to the growing PiKVM-alike category: BIOS access over a plain SSH terminal via on-device OCR, and an MCP endpoint so AI agents can drive the target machine directly. It is one of the first IP-KVMs to expose an agent-friendly API as a first-class control path.

### 🔬 Details (Phân)
The BIOS-in-Terminal feature uses offline OCR to convert the target machine's pre-boot screens into text streamed over SSH, so an operator on a low-bandwidth link can navigate BIOS menus without a browser or Moonlight session. Video capture is UVC at up to 1080p @ 45 FPS, with Moonlight streaming for interactive sessions quoted at 25–50 ms latency. A 240 × 240 IPS front display shows live status for rack-side techs, Wi-Fi 6 handles the network side, and Tailscale is natively supported for zero-config remote access. Storage uses Btrfs snapshots with a read-write overlay mode, so a config change can be rolled back cleanly.

The MCP integration exposes device control to Claude and other MCP-capable models, which turns the KVM into a controllable tool for an autonomous agent — installing an OS, walking a boot loop or capturing a screenshot on request. Hardware design files and documentation are published on GitHub, with the full schematic, PCB and firmware source released after the campaign closes. Funding goal is $33,000, with expected delivery in March 2027. One practical quirk called out in the write-up: the USB Type-C capture dongle behaves differently depending on cable orientation — flipping it 180° switches the negotiated speed between USB 2.0 (480 Mbps) and USB 3.0 (5 Gbps), and the article recommends the flipped orientation if capture feels laggy.

Compared to PiKVM v4 Mini and JetKVM, the differentiators are the OCR-over-SSH path and the MCP interface; hardware capture quality and streaming latency are broadly comparable.

### 🎯 Takeaway (Hợp)
If you manage a small fleet of bare-metal machines and already run Tailscale, this is worth backing for the SSH-only BIOS path alone — it survives on connections where a WebRTC session will not. For anyone building agentic ops tooling, the MCP endpoint is the more interesting long-term hook.

### 💡 Example
```bash
# Access the target machine's BIOS via the USBridge-KVM SSH bridge over Tailscale

    'usbridge bios --stream --ocr en --refresh 500ms'

# Delivers OCR-decoded BIOS text into your terminal at 2 Hz;
```
