## 1. Linux 7.2 Lands With Cache-Aware Scheduler, Fair GPU CFS and NR_CPUS Default Bumped to 256 for RISC-V

| ⚡ Impact | High |

### 🔭 Overview (Tổng)
CNX Software published a full architectural summary of the Linux 7.2 release on 21 August, several days after Linus Torvalds cut the tag on 16 August. The write-up matters for embedded and IoT engineers because the same mainline kernel underpins Yocto, Buildroot, OpenWrt, postmarketOS and most of the ARM- and RISC-V-based SBC distributions that ship inside industrial and consumer devices. Beyond routine driver churn, 7.2 introduces a cache-aware task scheduler, a CFS-style GPU scheduler, USB4 raw packet streaming and a phase change in swap accounting that meaningfully reshapes memory behaviour on large systems.

### 🔬 Details (Phân)
On the scheduler side, cache-aware task scheduling attempts to co-locate data-sharing threads inside the same Last Level Cache domain, cutting cross-LLC traffic on multi-die and hybrid parts. The new Fair GPU scheduler borrows CFS's approach for GPU workqueues, so interactive clients no longer starve behind a long compute batch — a change that most affects desktop and edge-AI boxes running Mesa. USB4STREAM adds a `/dev/tbstreamX` character device that speaks raw packets over USB4/Thunderbolt cables, opening the door to userspace transports for storage and networking that previously required kernel drivers. Swap table Phase IV unifies anonymous and shmem swap allocation and reclaims roughly 512 MB of kernel memory per 1 TB of mounted swap.

Architecture-specific work is heavier than usual on RISC-V. Support landed for the 80-core SpacemiT server SoC and Sophgo's 128-core Pisces part, and the default `NR_CPUS` ceiling was raised to 256 so distributions no longer need custom `CONFIG` fragments to boot those parts. kexec, ftrace and memory-mapping paths were reworked for the same class of hardware. ARM changes are broad but incremental — Rockchip RK3528 USB PHY support, Samsung thermal management improvements, Qualcomm Dragonwing IPQ9650 SoC enablement, plus routine work across Allwinner, Amlogic and MediaTek. MIPS receives only GPIO cleanups. Torvalds himself flagged that the release window closed with "a number of fairly late reverts", so a 7.2.1 stable is likely inside two weeks.

For fleet operators, the practical impact clusters around three items: the cache-aware scheduler benefits containerised workloads on Zen and hybrid Intel silicon without any userspace change, the swap accounting fix removes a real 512 MB tax on storage-heavy edge nodes, and the RISC-V CPU ceiling means distros can finally ship a single kernel for both dual-core dev boards and 128-core servers. Regression risk is concentrated in the newly reverted patches, so pinning to 7.1.y for a fortnight before rolling forward is a defensible posture.

### 🎯 Takeaway (Hợp)
Rebuild vendor kernels against 7.2 on any board where the scheduler or memory-pressure profile matters — many-core RISC-V, hybrid ARM big.LITTLE, and edge-AI boxes running headless Mesa. Trên các fleet đang chạy nhân LTS, đừng vội đưa 7.2 vào production trước khi 7.2.1 xử lý xong đợt revert cuối tuần.

### 💡 Example
```bash
# Enable the cache-aware scheduler on a hybrid or multi-die box.
# Value is a bitmask; 1 = co-locate data-sharing threads inside the same LLC.
echo 1 | sudo tee /sys/kernel/debug/sched/features/CACHE_AWARE

# Raise the runtime CPU ceiling on the new RISC-V default so a
# 128-core Sophgo Pisces boots without a kernel rebuild.

# Bind /dev/tbstream0 to a userspace tool that speaks USB4 raw packets.
sudo chgrp plugdev /dev/tbstream0 && sudo chmod g+rw /dev/tbstream0
```

## 2. DuckDB Replaces Its PostgreSQL-Derived YACC Parser With a PEG Parser Ahead of v2.0

| Field | Value |
|---|---|
| 📅 Date | 20/08/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `duckdb-v2` · `peg-parser` · `packrat-parsing` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
Daniël ten Wolde published a DuckDB blog post on 20 August walking through the v2.0 parser rewrite: the project has retired its PostgreSQL-inherited YACC/Bison grammar in favour of a Parsing Expression Grammar (PEG) parser. For DE teams building on DuckDB — either directly, through MotherDuck, or via extensions like ducklake, spatial, or fts — this is a foundational change that affects language evolution, error quality and third-party syntax extension. It also shortens the path for domain-specific SQL dialects to live inside DuckDB rather than as pre-processors upstream.

### 🔬 Details (Phân)
The old parser was a fork of PostgreSQL's YACC/Bison grammar, which was fine while DuckDB's SQL closely tracked PostgreSQL but grew painful as DuckSQL added its own extensions — friendly aliases, positional column references, pipe syntax, list comprehensions. Ten Wolde explains the trigger bluntly: in a YACC grammar "seemingly small additions… can interact with existing rules and introduce shift/reduce or reduce/reduce conflicts". A PEG parser evaluates ordered alternatives — when matching `SelectFrom`, the parser attempts `SelectFromClause` first, then `FromSelectClause` — so grammar authors reason locally rather than about the whole state machine.

Two concrete wins come out of the switch. Packrat parsing, which memoises intermediate matches, changes worst-case behaviour on malformed input dramatically: a query with 19 unmatched parentheses parses in 0.001 s under the new parser versus 10.640 s under the old one, an ~10,000× improvement that removes an entire class of client-side timeouts. Error messages also improve — instead of the historical Bison "syntax error at or near" line with a pointer to the manual, the PEG parser surfaces which alternative was being tried and where it failed. Backwards compatibility is preserved: only the parser implementation changes, and existing DuckSQL queries continue to work unchanged.

The strategic piece is runtime extensibility. Extensions can now register grammar rules directly with the parser, so an extension shipping pipe syntax or a domain-specific DDL does not need a fallback pre-processor. That is the mechanism that will let ducklake-style catalog syntax, geospatial-specific joins and application-specific extensions live natively in DuckSQL rather than as textual rewrites. The trade-off is minor: PEG parsers are typically 10–20% slower per character than a well-tuned LALR parser on happy-path input, though packrat memoisation swings that back on repeated sub-expressions.

### 🎯 Takeaway (Hợp)
Rebuild any custom DuckDB extension that ships its own SQL surface against the v2.0 preview branch now — the extension API for grammar registration is the piece to review first. For DE teams simply consuming DuckDB, the pragmatic win is timeout reduction on user-generated queries; nếu team đang ép timeout parser xuống dưới 1 giây để chống query malformed từ BI tool, có thể nới lỏng sau khi lên v2.0.

### 💡 Example
```sql
-- Pipe-style query enabled by an extension registering a new PEG rule
-- against DuckDB v2.0's parser. The same query compiles to the same
-- logical plan as the equivalent nested SELECT.
FROM read_parquet('s3://logs/2026/08/*.parquet')
|> WHERE status_code >= 500
|> AGGREGATE
     count(*)              AS errors,
     approx_count_distinct(session_id) AS sessions
   GROUP BY service, region
|> ORDER BY errors DESC
|> LIMIT 20;
```

### 🔭 Overview (Tổng)
The AWS Big Data blog on 20 August introduced Amazon Redshift's native integration with Amazon S3 Tables for long-term system-table retention. Historically, Redshift retained system-log data for only seven days inside the cluster; auditors and platform teams that needed longer retention had to build a UNLOAD-plus-Glue-crawler pipeline of their own. The new integration ships that pipeline as a first-party feature, writing over 25 system views into S3 Tables as Apache Iceberg tables with no additional export cost.

### 🔬 Details (Phân)
The integration is configured from the Amazon Redshift console under a new "System table integrations" page. An admin selects source warehouses, picks which system views to export (SYS_QUERY_HISTORY, SYS_CONNECTION_LOG, SYS_USERLOG and 20-plus others), chooses between per-warehouse or shared table deployments, and optionally attaches a KMS key. From that point forward, log rows land in an S3 Tables namespace as Iceberg tables that any Iceberg-aware engine — Athena, EMR Spark, Trino, Flink, DuckDB via the iceberg extension — can query directly. Delivery itself carries no additional cost; only S3 Tables storage, background maintenance and query engine usage are billed.

Architecturally, the interesting choice is that Iceberg is now AWS's preferred target for internal telemetry export. The same shape appeared this year for CloudTrail Lake, MSK Connect connector logs and DynamoDB point-in-time exports, and Redshift joining that list signals that Iceberg-on-S3 is the platform's standard cold-log substrate. Because the target tables are Iceberg, teams get schema evolution, time-travel and hidden partitioning for free — capabilities the old UNLOAD-to-Parquet pipeline had to reinvent. Querying from Redshift itself is straightforward: create an external schema against the AWS Glue Data Catalog resource link and read the tables like any other federated source.

The main caveat is operational: many DE teams already carry a Redshift audit-log pipeline of their own — sometimes into Snowflake, sometimes into a home-grown Iceberg lake. Deleting that pipeline and cutting over to the integration means aligning downstream dashboards to the new S3 Tables schema and confirming that governance controls (Lake Formation, Row-Level Security) still enforce what the internal pipeline enforced. For net-new deployments, though, there is no reason to build the pipeline by hand any more.

### 🎯 Takeaway (Hợp)
Retire any UNLOAD-plus-Glue pipeline that only exists to move SYS_QUERY_HISTORY out of Redshift for compliance — the integration replaces it end-to-end and keeps the data as Iceberg, so downstream engines don't need Redshift-specific loaders. Nếu team đã có Iceberg lake riêng, mapping schema Redshift SYS_* sang schema hiện tại là bước quan trọng trước khi bật integration ở production.

### 💡 Example
```sql
-- After enabling the console-side integration, query the exported
-- SYS_QUERY_HISTORY as an Iceberg table via an external schema.
CREATE EXTERNAL SCHEMA rs_sys
FROM DATA CATALOG
DATABASE 'rs_system_tables_link'
IAM_ROLE 'arn:aws:iam::123456789012:role/RedshiftS3TablesReader';

SELECT user_id,
       date_trunc('hour', start_time) AS hr,
       count(*) AS query_count,
       avg(elapsed_time)/1000.0 AS avg_seconds
FROM   rs_sys.sys_query_history
WHERE  start_time >= current_date - INTERVAL '30 days'
GROUP  BY 1, 2
ORDER  BY hr DESC, query_count DESC;
```

### 🔭 Overview (Tổng)
Espressif's developer blog on 20 August featured the ESP32 Bit Pirate — a scriptable, multi-protocol workbench built on the ESP32-S3 that folds twenty-plus wired and wireless protocol modes into one $20-class board. Written up by security engineer Andrei Vladescu, the project pulls the classic Bus Pirate concept forward: instead of a dedicated bench tool, an ESP32-S3 DevKit plus companion carrier gives firmware and hardware engineers I²C, SPI, UART, 1-Wire, JTAG, SWD, CAN, smartcard, USB and Ethernet on the wired side, and Wi-Fi, BLE, Sub-GHz, RFID, RF24 and IR on the wireless side.

### 🔬 Details (Phân)
The reference stack is three open-hardware pieces: the ESP32-S3 DevKit as the core, a Bit-Pirate-Dock carrier that provides selectable 1.8 V / 3.3 V / 5 V level translation for target buses, and an ESP32-C5 adapter that adds dual-band radio so 2.4 GHz and 5 GHz Wi-Fi both fit inside the same workflow. The firmware exposes three interchangeable UIs — a USB serial terminal, a web CLI served directly from the ESP32-S3, and a standalone mode for boards that carry their own screen and keyboard. That flexibility matters on a bench: a technician can attach with `screen /dev/ttyUSB0`, a remote SRE can open the web CLI over an SSH tunnel, and a field kit built around a T-Deck-class device can run offline.

Under the hood the modes include the tooling every embedded developer eventually reaches for: bus scanners, protocol sniffers, EEPROM and SPI-flash dumpers, and a logic capture path. Python scripting sits on top for automation, and the project ships a catalogue of "recipes" for common tasks. Licensing is explicit and permissive: firmware from geo-tp's ESP32 Bit Pirate repository, the dock hardware under CERN-OHL-W-2.0, and the documentation under CC BY 4.0 — a clean triple-licence stack that a corporate team can adopt without paperwork friction.

The context is important. Bus Pirate v5 and v6 are excellent but single-purpose, and the Flipper Zero addresses adjacent RF workflows but does not cover industrial buses. The Bit Pirate is the first bench-class tool on the ESP32 family that spans both worlds, which lines up with the hardware trend where a single MCU family now covers Wi-Fi 6, BLE 6, Sub-GHz and 802.15.4 in-package. For security engineers auditing IoT products, that convergence turns one $50 board into a very large fraction of the tools a lab needs.

### 🎯 Takeaway (Hợp)
Add an ESP32 Bit Pirate to any embedded lab that still relies on separate Bus Pirate, Flipper Zero and logic-analyser stations — the licence terms are permissive enough for internal-tool adoption without procurement review. Bên bảo mật IoT nên chú ý phần scripting Python: nó cho phép biến các recipe thành fuzzer bus-level chạy trong CI.

### 💡 Example
```python
# Bit Pirate scripting: scan an I2C bus at 400 kHz, then dump the
# EEPROM at 0x50. Runs over the ESP32-S3 serial CLI or web CLI.
import bitpirate as bp

bus = bp.i2c(mode="master", freq=400_000, pullup=True)
addrs = bus.scan()
print("Found devices:", [hex(a) for a in addrs])

if 0x50 in addrs:
    eeprom = bp.eeprom(bus, addr=0x50, size=32768)
    with open("/tmp/eeprom-0x50.bin", "wb") as fh:
        fh.write(eeprom.dump())
    print("Dumped 32K to /tmp/eeprom-0x50.bin")
```

### 🔭 Overview (Tổng)
StarFive announced the Dubhe-100 on 20 August as its highest-performance 64-bit RISC-V core to date, targeting servers, HPC, and inference-class workloads rather than the microcontroller and low-end SBC segments that dominate today's RISC-V shipments. For engineers watching the RISC-V roadmap, this matters because it is one of the first announced cores explicitly built to the RVA23 profile — the compliance target most Linux distributions and toolchains are now aligning against — and the first StarFive core positioned squarely at the AI-inference workload class.

### 🔬 Details (Phân)
The Dubhe-100 is a superscalar out-of-order core with a 15-stage pipeline and 6-wide issue, backed by 256-entry physical register files for both integer and floating-point/vector paths. Reported synthetic performance is 15 SPECint2006/GHz and 10.0 Dhrystone v2.2 DMIPS/MHz — figures that place it below Arm Neoverse V2 on integer throughput but above every previously announced RISC-V core, including SiFive P870 and Ventana Veyron V2. The ISA implementation is described as "RV64GCBVH" — general purpose, compressed, bit-manipulation, vector and hypervisor extensions — and the vector unit runs 8/16/32/64-bit integer and floating-point with `VLEN=2*DLEN=256`, which gives 512-bit vector state on 256-bit datapaths.

RVA23 compliance is the strategic piece. Distributions have been converging on RVA23 as the baseline profile that allows a single kernel and userspace to boot across future RISC-V hardware without the earlier per-vendor fragmentation, and Linux 7.2 (see item 1) explicitly raised its default CPU count to 256 for exactly this class of chip. The Dubhe-100 also carries the Vector Crypto extension, which lets AES, SHA-2/3 and SM4 flow through the vector pipeline instead of a fixed-function accelerator — the same design choice that Neoverse and Apple silicon made earlier.

StarFive lists LLM inference, AI agents, computer vision and infrastructure roles — SmartNIC controllers, distributed-storage controllers — as target applications. LECARC is publicly named as the first partner building an early server SoC around Dubhe-100. SDKs are not yet available for download; StarFive says they will land alongside the first commercial silicon. That is worth noting: JH8100 timelines slipped repeatedly, so IoT and edge-server planners should not build 2026 procurement around Dubhe-100 availability.

### 🎯 Takeaway (Hợp)
Any team scoping a RISC-V server or edge-inference deployment for 2027 should add Dubhe-100 to the shortlist alongside Ventana Veyron and SiFive P870, but treat announced timelines as directional until LECARC's first SoC tapes out. Với các ứng dụng IoT hạ tầng (SmartNIC, storage controller), sự kết hợp giữa RVA23 + Vector Crypto sẽ là chìa khoá để giảm phụ thuộc vào ARM Cortex-A trong 12–18 tháng tới.
