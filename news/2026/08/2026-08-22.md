## 1. DuckDB 1.5.3 Ships Chunked Query Results in the Java Driver to Skip JDBC Row-by-Row Overhead

| Field | Value |

| 🏷️ Topic | Release |

| 🔑 Keywords | `duckdb-jdbc` · `columnar-batch` · `arrow-interop` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
DuckDB's blog on 21 August, co-authored by Geertjan Wielenga and Alex Kasko, walks through the 1.5.3.0 Java driver release. The headline change is a new `DuckDBChunkedResult` API that exposes DuckDB's native columnar chunks — 2,048 rows of column vectors at a time — directly to Java callers, bypassing JDBC's row-cursor abstraction. For DE teams that use DuckDB from Spring, Trino, or their own JVM services, this closes a persistent gap where the engine held the data in columnar form only to have the driver unpack it into rows the caller would immediately repack.

### 🔬 Details (Phân)
Under the classic JDBC path, a Java caller iterates `ResultSet.next()` and pulls one cell at a time; the driver has to walk DuckDB's column vectors, materialise per-row values, and box them for the JVM. The new interface pivots that inside out. `DuckDBPreparedStatement.query()` returns a `DuckDBChunkedResult`, and callers iterate over chunks with `nextChunk()`, then read column vectors by index through `DuckDBReadableVector`. The chunks are lazily fetched and mirror DuckDB's C-API layout (zero-based column indices, native buffer views), so the driver hands the caller the same columnar layout the engine already holds.

That matters most when the eventual sink is columnar as well — an Arrow buffer, a Parquet writer, a Pandas-shaped ML matrix on the Python side of a gRPC bridge, or a Vector-friendly analytics engine. The prior path forced round-tripping through row objects even when both endpoints thought in columns, and the boxing/unboxing cost dominated wall-clock on wide analytical queries. Skipping it turns DuckDB-in-Java into a viable choice for the same class of embedded-analytics workloads where DuckDB Python already dominates. The Aug 18 JSON reconciliation post covered a separate 1.5.3 improvement in the type system; the two changes ship together.

The first release is deliberately narrow. Composite types — `LIST`, `STRUCT`, `MAP` — are not yet exposed through the chunked API, so any query returning nested rows still has to fall back to the classical `ResultSet`. A convenience string overload for `query()` is also missing, so callers must go through `PreparedStatement`. Both restrictions are called out as follow-ups, but a team planning a wholesale migration should audit their query surface for nested types before switching wholesale.

### 🎯 Takeaway (Hợp)
On any JVM service that already uses DuckDB as an embedded engine for parquet or CSV analytics, prototype the chunked path on the top three hot queries and measure end-to-end latency versus the JDBC row cursor — the win is largest when the downstream sink is Arrow, Parquet, or a columnar in-memory format. Nếu pipeline có nhiều truy vấn trả về `STRUCT` hoặc `LIST`, giữ nhánh `ResultSet` cho tới khi phiên bản kế tiếp bổ sung hỗ trợ nested type.

### 🔭 Overview (Tổng)
Databricks published a 20 August update extending Inbound Private Link support to account-level surfaces — account console, Genie One, Governance Hub, account-level APIs — and to disaster-recovery stable URLs and custom vanity domains like `acme.databricks.com`. The architectural change is that a single Private Link endpoint now covers every UI and API resource across regions, replacing the earlier model where enterprises had to stand up one endpoint per region or per workspace. For platform teams that carry a multi-region Databricks footprint behind private routing, this is a real reduction in endpoint sprawl.

### 🔬 Details (Phân)
The previous topology forced one PrivateLink endpoint per region and often one per workspace, and account-level surfaces sat outside that boundary entirely. That left teams either exposing the account console over the public internet with IP allowlists, or standing up bespoke reverse proxies. The new model routes account-level and workspace-level traffic through the same endpoint, and the endpoint is region-agnostic — a workspace in another region uses the same endpoint object. Custom-URL customers now also get PrivateLink instead of falling back to public routing, and the same endpoint carries the stable URL used by managed disaster-recovery failover.

Under the hood, the change is bound to a broader ingress policy model. Context-based ingress controls let an admin write a rule over three axes at once — identity (which user or principal), source (public IP or specific registered endpoint), and destination (which resource inside Databricks). That is meaningfully different from IP allowlists, where the only decision surface is "who is coming from what IP". A rule can, for example, allow the platform-eng SSO group to reach the Governance Hub only through the corporate PrivateLink endpoint, while allowing a specific automation principal to reach the account APIs from a designated egress IP.

The migration cost is real but bounded: enterprises with per-workspace endpoints do not have to rip everything out, but they can consolidate on the new endpoint model and retire redundant ones as workspaces are refreshed. The change also aligns with a broader trend across the hyperscalers of collapsing per-resource private endpoints in favour of a per-tenant one — AWS PrivateLink Interface endpoints and Azure Private Endpoint for storage account subresources have moved in the same direction over the past twelve months.

### 🎯 Takeaway (Hợp)
Any Databricks estate that today lists more than a handful of PrivateLink endpoints per region should draft a consolidation plan and pair it with a context-based ingress policy that separates human traffic from CI/automation traffic on the same endpoint. Với các workspace mới, mặc định dùng endpoint mới ngay từ đầu và bỏ qua topology "một endpoint mỗi region" — chi phí vận hành PrivateLink giảm rõ rệt khi consolidation.

### 💡 Example

  account_id = var.databricks_account_id

    private_link_endpoint = databricks_mws_vpc_endpoint.unified.id

### 🔭 Overview (Tổng)
Docker's engineering blog on 21 August introduced Docker Sandboxes as a first-class runtime for GitHub Agentic Workflows via a new `docker-sbx` value in the workflow schema. The point of the release is a security posture change: an AI agent invoked from a `.github/workflows/*.md` agentic workflow now runs inside a per-job microVM with its own kernel, filesystem, network stack, and private Docker daemon, rather than sharing the runner's Docker socket. For data-platform and MLOps teams that already run agents against their pipelines in CI, the release closes an isolation gap that has been the main reason infra teams hesitated to enable coding agents on shared runners.

### 🔬 Details (Phân)
The runtime binding is three YAML lines under `sandbox.agent`: setting `runtime: docker-sbx` swaps the default GitHub-hosted Ubuntu execution for a Docker-provided microVM. The workflow declares its network egress as an allowlist (`defaults`, `github`, `containers`, plus per-language buckets such as `java`) and its filesystem writes as an allowlist of paths (`allowed-files: src/**`) that constrain what the agent can push into a PR. Docker's example runs a Testcontainers-based Java 21 integration test suite that starts PostgreSQL inside the sandbox, detects a case-sensitivity bug, patches the source, and opens a draft PR — all with the agent holding root inside the sandbox but no privilege over the host runner.

The isolation design is the interesting bit. Because the sandbox runs a private Docker daemon rather than mounting the host's docker.sock, the agent can freely `docker run` databases, message brokers, or any tool it needs without opening a socket-mount escalation path — the classic footgun of running Docker-in-Docker on CI. The microVM boundary matches AWS Firecracker-class isolation rather than a shared-kernel container, so a compromise inside the sandbox does not spill into the runner or into other jobs. The example completes end-to-end in 11:16 on `ubuntu-24.04`, which puts the sandbox startup overhead in the low-tens-of-seconds range rather than minute-scale.

For DE workflows, the concrete opening is running lint/typing/regen agents against dbt, Airflow, and Dagster repos where the agent needs a real database or warehouse client to reason about generated SQL. That has been feasible only on a self-hosted runner or a bespoke Firecracker rig; `docker-sbx` gets the same posture on GitHub-hosted runners with a Markdown-authored workflow. Two operational notes: Docker credentials must be stored as `DOCKER_USERNAME` / `DOCKER_PAT` secrets, and the compiled `.lock.yml` is machine-generated — edits belong in the Markdown source, followed by `gh aw compile`.

### 🎯 Takeaway (Hợp)
For any repo where CI agents already have permission to run tests or open PRs, migrate the workflow to `runtime: docker-sbx` and pair it with a tight `network.allowed` list plus `allowed-files` under `safe-outputs.create-pull-request` — the security posture improves without giving up the ability to spin up real integration dependencies. Trước khi mở rộng cho toàn org, đo kỹ thời gian khởi tạo microVM để tránh bloat CI trên các job ngắn (< 3 phút).

### 💡 Example
```yaml
# .github/workflows/agent-test.md — an agentic workflow that runs the AI
# agent inside a Docker Sandbox microVM with its own Docker daemon.
---
name: "Agent: integration-test regen"
on: workflow_dispatch
runs-on: ubuntu-24.04

permissions:
  contents: read
  copilot-requests: write

engine: copilot

network:
  allowed:
    - defaults
    - github
    - containers
    - java

sandbox:
  agent:
    id: awf
    runtime: docker-sbx
    sudo: true

safe-outputs:
  create-pull-request:
    title-prefix: "[docker-sbx] "
    draft: true
    protected-files: blocked
    allowed-files:
      - "src/**"
      - "tests/**"
---
```

What makes the release worth flagging in an IoT digest is the combination of price point (under US$0.60 in volume for the MCXC151VFM) with features that entry-tier MCUs typically drop: ECC-protected data flash, an on-chip OpAmp, and a high-speed comparator with DAC. That mix targets industrial-sensing and motor-control designs that would otherwise require an external analog front-end.

### 🔬 Details (Phân)
On core specifications, the C16 clocks a Cortex-M23 at 72 MHz, the C15 at 48 MHz, and both hit 2.13 CoreMark/MHz (153 CoreMark on the C16). Memory tops out at 12 KB SRAM and 64 KB flash on the C16, 6 KB / 32 KB on the C15, plus a dedicated 16 KB data-flash bank with ECC — the ECC bit matters for retention-critical calibration and log tables that would otherwise ride on unprotected flash. Peripheral set includes a 16-bit SAR ADC, a high-speed comparator paired with a DAC, an internal OpAmp for signal conditioning, and FlexPWM outputs for BLDC and switched-mode power stages. GPIO count reaches 45, with the usual LPI²C, LPSPI and UART complement.

The positioning is against ST STM32C0, Renesas RA2, and GD32E23x in the same sub-dollar Cortex-M23 tier. STM32C0 and RA2 both undercut on price, but the NXP part gets differentiation from the on-chip OpAmp and ECC data flash — features usually only found one tier up. NXP is explicit about the migration play: existing LPC800 and Kinetis KE04 designs get a code-and-pin bridge onto MCX C via the shared MCUXpresso SDK, which lowers the switching cost for teams currently absorbing LPC and Kinetis end-of-life notices. The FRDM-MCXC162 dev board lists at US$15, so bring-up is cheap.

Two caveats live in the fine print. Announced lead time is 16 weeks — long for a Cortex-M23 in this class, and worth confirming against distributor stock before designing a part in. Second, the SRAM ceilings are tight enough (6-12 KB) that heavier RTOS stacks such as Zephyr with USB and TCP/IP will not fit comfortably; the target is bare-metal or FreeRTOS-with-lwIP-lite, and any team migrating from an LPC824-class device should audit their footprint against those numbers.

### 🎯 Takeaway (Hợp)
For a new industrial-sensing or brushless-motor design that would otherwise need an external OpAmp and unprotected calibration flash, price out the MCX C16 with its on-chip OpAmp and ECC data flash — the BOM saving typically outruns the incremental die cost. Với các team đang chạy LPC800/KE04 EOL, tận dụng MCUXpresso SDK để port firmware trong 1–2 sprint thay vì viết lại từ đầu.

For any project that expects to add a bespoke sensor board via I²C, this forces a solder-in fly-lead solution instead of a stackable design. ## 6. AWS Adds Custom-Tag Cost Attribution for SageMaker Unified Studio Projects via EventBridge, DynamoDB and CUR

### 🔭 Overview (Tổng)
The AWS Big Data blog on 20 August published a solution pattern that closes a real FinOps gap in Amazon SageMaker Unified Studio: dynamically-created project resources do not automatically inherit user-defined tags, so a CostCenter, Team, or Environment dimension attached to a project never made it into the AWS Cost and Usage Report (CUR). The blog post ships a reference architecture that captures the tags at project creation and joins them onto CUR line items after the fact — practical for organisations running ML, analytics, and generative-AI workloads on Unified Studio who need per-project chargeback.

### 🔬 Details (Phân)
The reference design has three moving parts and no bespoke agent. First, EventBridge subscribes to SageMaker Unified Studio project lifecycle events, and a Lambda writes a project-to-tag mapping into DynamoDB whenever a project is created or updated. Second, an AWS Glue ETL job runs on the CUR delivery cadence, joining CUR line items against the DynamoDB table on the project's resource identifier and appending custom tag columns. Third, QuickSight dashboards read the enriched CUR and let a FinOps analyst pivot cost by CostCenter, Team, Environment, or any custom dimension the organisation declared on the project.

The pattern matters because the alternative — trying to enforce tags at every downstream resource Unified Studio provisions on the user's behalf — is a losing arms race with the platform's automation. Every managed feature (managed notebooks, managed feature groups, managed vector stores) creates a class of resource where the user never sees the underlying ARNs, so tags cannot be applied directly. Doing the join in CUR post-processing avoids that problem entirely and keeps the source of truth at the project layer where the tags actually live. It also composes with existing CUR consumers: any BI tool that already reads CUR through Athena or a Redshift external schema keeps working, with new tag columns simply appearing in the schema.

The trade-off is operational surface area. The design introduces a stateful DynamoDB table that must be reconciled against Unified Studio if EventBridge misses an event, and a Glue job that runs on the CUR delivery schedule (typically daily). Teams that already own a tag-governance service will want to plug this into that service rather than run a parallel copy. And crucially, the enrichment is post-hoc: real-time cost dashboards will still show untagged rows for the first few hours after a project is created, until the next Glue run lands.

### 🎯 Takeaway (Hợp)
For any org already running Unified Studio for more than a handful of teams, deploy the reference architecture as a first pass and reconcile the DynamoDB tag map weekly against the Unified Studio API — the incremental cost of the pipeline is small compared with the chargeback disputes it prevents. Nếu team đã có tag-governance service, tách phần EventBridge/DynamoDB ra khỏi Lambda ví dụ và trỏ về store trung tâm để tránh drift giữa hai nguồn tag.
