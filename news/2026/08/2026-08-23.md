### 🔭 Overview (Tổng)
AWS announced the general availability of Glue 6.0 on 21 August, and the release is uncharacteristically wide for a Glue version bump. The runtime moves to Apache Spark 4.1, Python 3.13, and Scala 2.13, and is built on Iceberg 1.11.0 with full support for the Iceberg v3 table spec. Pricing drops 30% versus prior Glue versions on the same job class, which changes the per-DPU-hour arithmetic for teams currently running Glue at fleet scale. For any org running lakehouse ETL on Glue or considering it against Databricks Jobs or EMR Serverless, this release closes several of the gaps that made Glue a lagging option.

### 🔬 Details (Phân)
The Iceberg v3 support is the substantive change. Glue 6.0 exposes the new VARIANT type with shredding — semi-structured JSON, event, and log payloads stored in a columnar layout without pre-flattening the schema, which is the same shape Spark 4.1 handles natively. Native GEOMETRY and GEOGRAPHY types land alongside, giving spatial workloads a first-class column type in Iceberg tables rather than a WKB blob smuggled through a binary column. Nanosecond-precision timestamps address the long-standing IoT and high-frequency-finance ceiling where millisecond or microsecond precision lost information at the wire boundary. An "unknown" type gives schema-evolution consumers a safe way to represent columns whose type has not yet been resolved.

Spark 4.1 brings its own pull-forward: declarative pipelines that shorten ETL author-time boilerplate, Arrow-native Python UDFs and UDTFs that skip the pickle-serialise-copy path between the JVM and Python workers, and real-time streaming mode with single-digit-millisecond latency for Structured Streaming jobs. The Python 3.13 bump matters more than the number suggests — the free-threaded interpreter finally lets Arrow UDFs actually use multiple cores per Python worker on wide analytical queries. Scala 2.13 aligns Glue with the version most of the Iceberg ecosystem now compiles against, closing a source of dependency-resolution grief with third-party connectors.

The pricing move is the operational headline. Glue's per-DPU-hour rate — the meter that governs the vast majority of Glue spend — drops by 30% on Glue 6.0 jobs at the same job class, applied on second-granularity billing. For a team running a nightly warehouse-refresh job on 50 DPUs for two hours, the monthly saving is real money; for anyone running continuous streaming Glue jobs, the change reshapes the make-versus-buy calculus against EMR Serverless. Upgrade is via the `--glue-version` parameter or the Glue Studio Spark upgrade agent; the API surface does not change, so existing job definitions and IaC templates can be flipped in place after a compatibility pass. The one caveat is genuine: Spark 4.1 tightens several deprecations Spark 3.5 tolerated, so a full-fleet flip without a staged canary is not advisable on production paths.

### 🎯 Takeaway (Hợp)
For any Glue estate above a handful of jobs, stage the 6.0 upgrade behind a canary group and audit for deprecations Spark 3.5 tolerated but Spark 4.1 rejects — the 30% price cut alone typically pays for the migration effort within a quarter. Nếu roadmap đang chờ Iceberg v3 để chuẩn hóa các cột JSON dày và timestamp nanosecond, đây là cột mốc chính thức để bắt đầu chuyển các bảng warehouse sang v3 thay vì giữ v2.

""")

### 🔭 Overview (Tổng)
CNX Software reported on 22 August that Espressif has published a developer preview of an official Linux Board Support Package for the ESP32-S31, the dual-core RISC-V microprocessor Espressif announced in March 2026 and moved into mass production shortly before this release. The BSP is the first Linux port Espressif itself has stood up rather than the community; the ESP32-S31 is also the first Espressif chip with a memory-management unit, which is the architectural prerequisite that makes running a mainstream Linux kernel viable at all. For teams that have wanted an ESP-branded part they could target with a full Linux userland rather than FreeRTOS-plus-lwIP, this is the concrete opening.

### 🔬 Details (Phân)
The preview couples a Linux 6.18 kernel fork with Buildroot 2025.02 and packages the whole thing as a single 13.7 MB flash image (`s31_full_flash.bin`) that boots from NOR flash and drops a shell on the serial console at 115,200 baud. Tooling requires esptool 5.3.0 or later; the CNX writeup used 5.3.1. The kernel branch, the Buildroot external, and the BSP entrypoint all live under Espressif's GitHub organisation, with the primary artefacts at `github.com/espressif/esp-linux-bsp`, `github.com/espressif/esp-buildroot-external`, and `github.com/espressif/linux`. The reference hardware carries 16 MB of PSRAM, which is the practical floor for a minimal Linux userland on the part.

The chip specs frame the ambition. The ESP32-S31 pairs dual RISC-V cores with an MMU, Gigabit Ethernet, Wi-Fi, Bluetooth, and 802.15.4 — the connectivity profile of a Cortex-A gateway with the price and integration story of an Espressif MCU. Two community ports already existed against the same silicon: a GrieferPig branch on Linux 6.12 with experimental Wi-Fi and dual-core, and Marco's port on Linux 7.1 with OpenSBI 1.9 but with LCD, microSD, USB host, and WLAN not yet wired. Espressif's official BSP explicitly does not claim parity with either community fork on peripheral coverage; Wi-Fi status in particular is called out as undefined in the preview.

The preview label is doing real work here. Espressif is clear that updates will be irregular, that breaking changes will land without stability guarantees, and that bug fixes are best-effort — the BSP is for experimentation, not production. That aligns with the position an early Linux BSP usually holds against a hardened FreeRTOS SDK, but it is unusual for Espressif, who typically only publish once an SDK is production-ready. Teams looking to bring the ESP32-S31 into a Linux-first product line should track the BSP repository directly and pin to a known-good commit rather than assume main is stable across weeks.

### 🎯 Takeaway (Hợp)
For any gateway or edge design that has been stuck between "too big for FreeRTOS" and "too small for a Cortex-A SoM", pull the developer preview onto an ESP32-S31 reference board this week and measure the minimum image, boot time, and heap headroom under a representative workload — the answer decides whether the part slots into the next revision. Với các đội đang đánh giá RISC-V Linux cho một product line có Espressif ecosystem, chọn commit cố định của `esp-linux-bsp` chứ đừng bám main, vì preview sẽ vỡ backward compat trong nhiều tuần tới.

### 💡 Example

    write_flash 0x0 output/images/s31_full_flash.bin

### 🔭 Overview (Tổng)
Espressif's developer blog on 22 August published a reference implementation showing ESP-BIST — the LGPL-3.0 built-in self-test library it maintains — driving IEC 60730 Class B baseline coverage on an ESP32-P4 acting as the Modbus master for a motor drive HMI. The interesting piece is not the library, which has been in the ecosystem for months, but the architecture the article demonstrates: a low-power core is dedicated as a safety companion to the application core, and a boot gate refuses to bring up the display, Modbus stack, or motor control until self-tests pass. For engineers building appliance controllers, industrial drives, or any product that ships against IEC 60730-1 (2022), the reference shows how to structure a modern Espressif SoC as its own safety supervisor rather than pairing it with a discrete monitor chip.

### 🔬 Details (Phân)
ESP-BIST covers the domains IEC 60730 Table H.1 enumerates for Class B: CPU registers and CSRs, program counter execution flow, CPU stack integrity, RAM via March A / March X / Abraham algorithms, flash via CRC, clock source stability, watchdog liveness, and GPIO plus ADC plausibility. Testing runs in two phases — a heavy post-boot sweep (full RAM, flash CRC) and continuous lightweight background checks on a configurable period. The library claims 100% Table H.1 requirements coverage, with the honest caveat that implementation coverage is not a certification claim; it is a coverage-of-requirements assertion an integrator can build on.

The Host Diagnostics protocol is the design choice worth noting. On the dual-core RISC-V parts — ESP32-C5, ESP32-C6, and the ESP32-P4 used in this HMI — the low-power core runs the self-tests autonomously and issues timed cryptographic challenges to the main application core. The LP core owns the decision to force safe states, and the application cannot override it. That inversion mirrors the two-processor architecture regulated industries used to insist on with a discrete safety MCU beside the application MCU, but folds it onto one die. The reference boots an M5Stack Tab5 as the HMI paired with a second board simulating a motor drive over RS-485; the Modbus register map exposes coil (motor on/off), discrete input (overspeed alarm), holding registers (setpoint, critical speed), and input registers (measured speed, temperature).

Two design details land the safety posture concretely. The boot gate holds display init, LVGL, and the Modbus stack behind post-boot self-test completion — the touchscreen literally does not render its motor controls until BIST reports pass. On any runtime failure the code path is direct: command motor power off via Modbus, clear pending commands, then render a full-screen halt notification. There is no logging-only path or subtle UI-degradation path — a detected fault de-energises the actuator first and tells the operator second. The reference source is at `github.com/fdcavalcanti/esp-bist-hmi` with the library itself at `github.com/espressif/esp-bist`; the LGPL-3.0 licensing works for most product integrations but is worth confirming against firmware distribution constraints.

### 🎯 Takeaway (Hợp)
For any product that has to pass IEC 60730 conformity — white-goods controllers, thermal cutoffs, motor drives, safety-relevant HMIs — clone the reference and use it as a structural template: boot gate, LP-core companion, direct-to-actuator fault path. Việc đưa Class B lên chính ESP32-P4 cho phép bỏ safety supervisor MCU rời ra khỏi BOM, nhưng cần audit toolchain và giữ nguyên pattern "LP core owns safe state" thay vì để application layer quyết định.

### 💡 Example
```c
/* ESP32-P4 boot gate: hold LVGL, Modbus, and motor control behind an
 * ESP-BIST post-boot self-test executed on the LP core. */
#include "esp_bist.h"
#include "host_diag.h"

void app_main(void) {
    if (host_diag_wait_lp_post_boot(pdMS_TO_TICKS(2000)) != BIST_OK) {
        display_show_halt("BIST post-boot failed");
        return;                              /* refuse to init HMI */
    }

    lvgl_init();
    modbus_master_start(RS485_PORT, /*baud=*/19200);
    motor_controls_render();

    /* Runtime background tests: any failure de-energises the drive first. */
    host_diag_set_fault_cb([]() {
        modbus_write_coil(SLAVE_ID, REG_MOTOR_ON_OFF, 0);
        modbus_flush_pending();
        display_show_halt("BIST runtime fault");
    });
}
```

### 🔭 Overview (Tổng)
CNX Software carried AAEON's launch of the uCOM-Q6490 on 21 August, an 82×50 mm SMARC 2.1 system-on-module built around Qualcomm's Dragonwing QCS6490 for edge AI, robotics, and industrial display workloads. The module lands as a mid-tier alternative to the Tria SM2S-QCS6490 and Sagire Edge AI 600, with the differentiator being wide industrial-temperature range (-40 to +85°C on the extended variant) and MTBF quoted at ~3.05 million hours. For product teams building carrier boards for medical automation, robotics, or industrial HMIs against a Qualcomm edge stack, the release adds another SMARC option to a market where COM Express and SMARC choices are still narrower than the equivalent Intel/AMD tier.

### 🔬 Details (Phân)
The QCS6490 pairs an octa-core Kryo 670 CPU — one Gold Plus core at 2.7 GHz, three Gold cores at 2.4 GHz, four efficiency cores at 1.9 GHz — with an Adreno 643L GPU at 812 MHz and a Hexagon DSP with dual HVX rated at up to 12 TOPS of AI performance. That NPU tier sits comfortably above the 3–6 TOPS Cortex-A76-class MPUs and below the 40 TOPS Jetson Orin NX bracket, which is roughly the design centre for battery-friendly vision inference on small models. Memory tops out at 16 GB LPDDR5 with 64 GB UFS storage on-module, and the 314-pin MXM 3.0 SMARC connector carries DisplayPort 1.4 (2K@60Hz), dual 2.5 Gbps Ethernet PHYs, USB 3.1, four USB 2.0, SDIO 3.0, PCIe 3.0, dual UARTs, dual SPI, triple I²C, and GPIO. Spectra ISP handles up to 192 MP capture in non-ZSL mode, with 4K60 hardware decode across H.264, H.265, and VP9.

The design trade-off worth flagging is on the interface side. Where competing QCS6490 modules — Tria and Sagire — expose the Dragonwing MIPI camera and display lanes directly on the module connector, AAEON's uCOM-Q6490 leaves them off. That forces integrators to route camera and display through USB or DisplayPort rather than native MIPI, which raises latency and bandwidth ceilings for a machine-vision or high-refresh HMI carrier. In exchange, the module carries the widest industrial temperature envelope and MTBF in the class, which matters for medical-automation and rugged-industrial designs that would otherwise disqualify a consumer-tier module. Power draw is quoted at 33.12 W at 3–5.25 V input.

Software support is the caveat. AAEON ships QC Linux kernel 6.6.97 booting from the onboard UFS, with the ECB-960T-A18-0002 carrier board listed but with limited public documentation. There is no Yocto BSP or Ubuntu image announced, and the Dragonwing software stack — Qualcomm QAI Hub, AI Engine Direct — is not called out as pre-integrated. For a team building on this module today, that means budgeting BSP work to align the module against the Qualcomm reference software the QCS6490 target expects, or waiting for AAEON to publish a fuller software brief.

### 🎯 Takeaway (Hợp)
For a new robotics or industrial-HMI design that needs 8–12 TOPS on-module in a rugged-temperature envelope and does not depend on native MIPI camera/display, the uCOM-Q6490 is worth pricing against Tria and Sagire on the same board — the MTBF and temperature envelope justify the missing MIPI on the right use cases. Với dự án phụ thuộc MIPI CSI/DSI, chọn module Tria SM2S-QCS6490 hoặc Sagire Edge AI 600 để tránh routing camera qua USB.
