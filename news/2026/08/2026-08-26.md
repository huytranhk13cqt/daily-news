### 🔭 Overview (Tổng)
AWS published the first half of a two-part guide showing how a Google BigQuery user can query Amazon S3 Tables in place, without copying Iceberg data across cloud boundaries. The pattern relies on AWS Glue's Iceberg REST Catalog as the shared metadata surface and on Google's Cross-Cloud Lakehouse to consume it. For teams that already keep governed Iceberg data on AWS but have analytics and ML users standardised on BigQuery, this removes an entire class of replication jobs. It also signals that the Iceberg REST catalog specification has quietly become the interoperability layer that vendors are willing to build against.

### 🔬 Details (Phân)
The moving parts are narrow. S3 Tables sit behind the `s3tablescatalog` federated catalog in AWS Glue, which exposes them through an Iceberg REST endpoint; BigLake in BigQuery assumes an AWS IAM role using OpenID Connect with Google as the provider, then calls the Glue endpoint to enumerate namespaces, resolve snapshots and read data files directly from S3. Access flows entirely through IAM in this part of the series — the second part covers Lake Formation-based fine-grained control. Schema evolution is picked up automatically on the next Lakehouse refresh cycle (300 seconds in the walkthrough), and every catalog call is auditable in AWS CloudTrail.

Setup is scripted rather than click-through: `aws s3tables create-table-bucket`, `aws s3tables create-namespace`, `aws iam create-open-id-connect-provider` for `accounts.google.com`, then `gcloud alpha biglake iceberg catalogs create --federated-catalog-type=glue --glue-aws-role-arn=…` on the Google side. Traffic uses public internet by default but can be pinned to Cross-Cloud Interconnect for private egress; partition pruning is preserved because BigQuery reads Iceberg manifests directly rather than going through a proxy. There is no benchmark in the post, only a 10-row `orders` sample table demonstrating a two-cloud aggregation.

For platform teams the interesting question is authorship: who runs `MERGE` and `OPTIMIZE`? In this design AWS remains the writer and BigQuery is a read-mostly consumer, which keeps the compaction and snapshot-management responsibility on S3 Tables. That is a much cleaner boundary than the earlier "sync a copy into BigQuery-native storage" playbook, and it makes cross-cloud governance an exercise in IAM trust chains rather than data logistics.

### 🎯 Takeaway (Hợp)
If your Iceberg source of truth already lives in S3 Tables, treat this as production-ready plumbing for exposing it to BigQuery without duplication. Concrete next step: stand up a Glue federated catalog for one non-critical namespace, create the OIDC provider once per AWS account, and point BigLake at it before deciding whether the Lake Formation flow in part two fits your governance model. Đây thực sự là bước "khai tử" mô hình sync hai chiều S3 ↔ BigQuery cho các bảng Iceberg đã có.

### 💡 Example

### 🔭 Overview (Tổng)
AWS published a benchmark run of the RAPIDS Accelerator for Apache Spark on Amazon EMR using the new EC2 G7 instance family, which pairs modest x86 CPU counts with NVIDIA RTX PRO 4500 (Blackwell, 32 GB VRAM) accelerators. The headline is a 3.7x wall-clock speedup on the full TPC-DS 3 TB workload against three CPU-only comparators, delivered with no code changes to the Spark SQL under test. The second headline is that per-run cost also drops — the GPU cluster completes the benchmark for $2.06 versus $2.93–$3.18 on CPU nodes — because the shorter runtime more than compensates for the higher hourly rate.

### 🔬 Details (Phân)
The benchmark cluster ran EMR on EKS with a Spark configuration tuned for the RAPIDS plugin: `spark.executor.cores=14`, `spark.executor.memory=20G`, `spark.executor.memoryOverhead=30G`, and the `RapidsShuffleManager` enabled to avoid the classic GPU-Spark shuffle bottleneck. Against `m9gd.4xlarge` (Graviton), `m8id.4xlarge` (Intel) and `m8a.4xlarge` (AMD) — all 16 vCPU / 64 GB — the g7.4xlarge cluster finished TPC-DS in 281 seconds versus 1,010–1,043 seconds for the CPU sets. Of the 103 queries, 102 were faster on GPU; the biggest individual win was q93 at 11.4x, driven by heavy shuffle joins and aggregations that fit GPU execution models well.

Two points are worth underlining for capacity planners. First, the plugin turns Spark SQL into GPU kernels transparently — the same submitted job runs on either family — which means the migration cost is a cluster type and a config file rather than a rewrite. Second, the price-performance advantage comes from the "burn hot, finish fast" property of RTX PRO 4500 workloads: G7 hourly is higher, but the run ends before that matters. That inverts the usual assumption that GPUs are only for ML and helps to reopen the "why not batch analytics on GPUs?" argument that Databricks Photon and Velox-on-CPU had largely closed.

The caveats are the usual ones for RAPIDS: UDFs that fall back to CPU can wipe out the win, and any query dominated by narrow scans of small files will not benefit. But for shuffle-heavy ETL and warehouse-style aggregation, the benchmark is a strong signal.

### 🎯 Takeaway (Hợp)
Take one representative shuffle-heavy job from your EMR fleet, mirror it onto a small g7.4xlarge test cluster with the RAPIDS shuffle manager, and compare wall-clock and dollar cost against your current instance family before broader adoption. If you already run EMR on EKS, the migration path is almost purely configuration.

### 💡 Example

```yaml
spark.plugins: com.nvidia.spark.SQLPlugin
spark.executor.cores: 14
spark.executor.memory: 20G
spark.executor.memoryOverhead: 30G
spark.rapids.sql.enabled: true
spark.rapids.sql.concurrentGpuTasks: 2
spark.shuffle.manager: com.nvidia.spark.rapids.RapidsShuffleManager
spark.rapids.memory.pinnedPool.size: 4G
```

### 🔭 Overview (Tổng)
Snowflake made Snowpipe Streaming ingestion available for Snowflake-managed Iceberg tables, closing the loop between real-time row-by-row writes and open-format storage. The point of the release is to remove the previous friction test — building an S3 bucket, a Kafka topic and a Kubernetes cluster just to see whether streaming is the right pattern — by letting a small container inside Snowpark Container Services run a full end-to-end streaming loop against an Iceberg table. Snowflake claims sustained throughput of more than 1 million transactions per second through the SDK.

### 🔬 Details (Phân)
The Streaming SDK is exposed through Python, Java, Node.js and a REST interface; authentication uses short-lived OAuth tokens from SPCS rather than long-lived secrets, which is a real operational upgrade for anyone who has managed connector credentials in Kafka Connect. The reference architecture is a load generator running inside SPCS, calling `appendRows` on a channel that maps to a Snowflake-managed Iceberg table created with the Snowflake catalog. Best practices in the post are practical rather than aspirational: batch rows client-side before calling `appendRows`, keep channels long-lived (one per source partition), and set `TARGET_FILE_SIZE` at the table level to control the write-amplification profile.

The interesting forward-looking note is on metadata: the post flags that Iceberg v4's Adaptive Metadata Tree will address the write amplification pattern that high-frequency commits produce in v2/v3 today, which explains why Snowflake is willing to encourage very high commit rates now. Also worth reading between the lines — the release places Snowflake in a similar position to Confluent Tableflow and Databricks' streaming-to-Delta path: streaming writes are moving from a value-add on top of a warehouse to the default arrival mode for lakehouse tables.

For architects, the practical implication is that "stream into Kafka, then batch into Iceberg" pipelines can be collapsed into a single hop if the source already speaks HTTP or can host a small SDK client. That removes an entire tier from a lot of pipelines and simplifies exactly-once handling via the offset-token pattern the SDK exposes.

### 🎯 Takeaway (Hợp)
Prototype a Snowpipe Streaming channel per source partition and compare end-to-end latency and cost against your current Kafka-plus-Snowpipe-batch topology before committing. Where the source system can adopt the SDK, the operational simplification is meaningful; where Kafka is already a shared bus, Snowpipe Streaming from Kafka Connect remains the cleaner fit.

### 💡 Example
```python
from snowflake.ingest import StreamingIngestClient

client = StreamingIngestClient.builder("cc_stream") \
    .use_spcs_authorization() \
    .build()

channel = client.open_channel(
    database="RAW",
    schema="EVENTS",
    table="ORDERS_ICEBERG",
    channel_name="ingest-p0",
    offset_token="0",
)

for batch in produce_batches(source):
    channel.append_rows(batch.rows, offset_token=str(batch.offset))
```

### 🔭 Overview (Tổng)
Espressif released a Wi-Fi Aware component for ESP-IDF that lets an ESP device discover and talk to an iPhone directly, with no access point and no captive-portal provisioning dance. The release matters because iOS 26 is Apple's first release to expose Wi-Fi Aware to third-party apps, and pairing an ESP32-C5 with an iPhone 12 or later now works through a documented, cross-platform standard rather than through workarounds like SoftAP or Bluetooth-first bootstrapping. It is the concrete answer to the long-running "how do we onboard a headless IoT device from an iPhone without breaking the user's home Wi-Fi?" problem.

### 🔬 Details (Phân)
The component sits on top of the Wi-Fi Aware protocol (formerly NAN) and layers DNS-SD naming and discovery conventions on top, so services advertise and resolve by name rather than by MAC. Pairing uses a mandatory six-digit PIN with WPA3-PSK-equivalent security, which is the same threat model as modern Wi-Fi rather than "Bluetooth trust me". On the transport side, once paired both ends open an IPv6 socket and speak whatever application protocol they like — the blog uses Apple's Network framework on iOS to bind the socket and standard `lwip` calls on the ESP side. Target support is ESP32-C5 explicitly at launch, and the README enumerates the current chip list; requirements on the host side are iOS 26 or iPadOS 26 with iPhone 12 / iPad 10th-gen or newer, and Xcode 26 for the sample app.

The strategic significance is bigger than one API. Wi-Fi Aware crossing the Apple gate turns it into a genuine cross-platform standard — Android has supported it for years — and Espressif being first out with a maintained ESP-IDF component signals that the AP-less onboarding pattern is finally something a product team can build against without maintaining two provisioning paths. The concurrency point in the release notes is easy to miss but important: an ESP32-C5 can run Wi-Fi Aware and a normal STA connection at the same time, so a device does not have to drop from its regular Wi-Fi network to talk to a nearby phone.

Migration cost for existing SoftAP-based onboarding is not zero: the accessory-side pairing flow, the app-side entitlements and the six-digit PIN UX all have to be built. But the reward is a first-run experience much closer to AirPods-style pairing on a class of devices where that has never been possible.

### 🎯 Takeaway (Hợp)
If your product uses SoftAP onboarding today, prototype the Wi-Fi Aware path on ESP32-C5 with ESP-IDF v6.1 and a Xcode 26 sample app; the onboarding UX is a clear win where the customer's phone is an iPhone on iOS 26. Longer term, plan to keep both paths for a device generation while the iOS 26 install base grows.

### 💡 Example
```c
#include "esp_wifi_aware.h"

wifi_aware_publish_config_t pub_cfg = {
    .service_name = "esp-lamp",
    .publish_type = WIFI_AWARE_PUBLISH_TYPE_UNSOLICITED,
    .instance_id  = 1,
};
wifi_aware_session_handle_t session;

ESP_ERROR_CHECK(wifi_aware_init(NULL));
ESP_ERROR_CHECK(wifi_aware_advertise(&pub_cfg, &session));

/* On pairing request from the iPhone, accept with six-digit PIN */

```

### 🔬 Details (Phân)
The Genio 720 pairs two Cortex-A78 at 2.6 GHz with six Cortex-A55 at 2.0 GHz and a Mali-G57 MC2 at 1.1 GHz with a dual ISP; the Genio 520 has the same big-little split but caps the A78 at 2.2 GHz, halves GPU clock to 880 MHz and drops to a single ISP. Software support is Android 15 and Yocto Linux at launch, with Ubuntu on the roadmap; the AI stack is compatible with NVIDIA's TAO framework, which is a slightly unusual choice for a MediaTek target and signals Lantronix wants to sit inside customers' existing model-training pipelines rather than force them onto a MediaTek-specific toolchain. Availability is via Lantronix's wireless-samples site, and the standing dev-kit is priced at $1,300. Module unit pricing in the source is unusual — Open-M 720G listed at $286.21 and Open-M 520G at $436.09 — worth confirming with a Lantronix quote before assuming, since the lower-tier SKU appears more expensive.

Positioning-wise this is a direct competitor to i.MX 8M Plus and Rockchip RK3588 SoMs on the industrial-vision side, with the Genio 520's headline being lower power at 10 TOPS rather than the raw compute race. The Cortex-A78 pairing keeps single-thread performance solidly ahead of A55-only alternatives, which matters for the kind of mixed workload — some inference, some vision preprocessing, some control-loop code — that these modules actually run in the field.

### 🎯 Takeaway (Hợp)
Shortlist the Open-M 720G alongside i.MX 8M Plus and RK3588S SoMs for any new fanless Edge AI enclosure where board area is tight; the LGA footprint is the real design lever here.
