### 🔭 Overview (Tổng)
AWS published a hands-on walkthrough for the newly landed Iceberg v3 column types on Glue 6.0, which is now backed by Apache Spark 4.1. The post uses a fleet-telemetry pipeline to exercise four v3 additions in one table: native GEOMETRY and GEOGRAPHY spatial columns, semi-structured VARIANT with automatic shredding, nanosecond TIMESTAMP_NTZ(9), and declarative DEFAULT column values. For data-engineering teams still holding geospatial data in separate lat/lon columns or JSON-in-STRING, this closes long-standing schema gaps at the format level rather than through vendor-specific extensions.

### 🔬 Details (Phân)
The example schema declares a single Iceberg v3 table that mixes all four features and partitions on `days(event_time)` plus `vehicle_type`, with `format-version = '3'` and `write.delete.mode = 'merge-on-read'`. Geospatial columns are typed `GEOMETRY(4326)` and `GEOGRAPHY(4326)` (SRID 4326) and support the standard `ST_*` predicate family — the tutorial's geofence query calls `ST_Intersects(location, ST_SetSrid(ST_GeomFromWKB(X'{POLY}'), 4326))` for polygon containment. The VARIANT column stores heterogeneous per-vehicle sensor payloads and is queried through `variant_get(sensor_payload, '$.fuel_pct', 'DOUBLE')` with type coercion at extraction time, so different vehicle classes can share one column without the reader having to know the union schema up front. The only runtime toggle called out is `spark.sql.geospatial.enabled=true`; VARIANT, TIMESTAMP_NTZ(9) and DEFAULT need no extra flags on Glue 6.0.

The wider context matters. Iceberg v3 was ratified earlier in 2026 and the type additions were the headline items, but until now the reference engines exposing them were mostly Spark 4.x preview builds and Trino nightlies. Glue 6.0 promotes them to a first-party managed runtime with the Spark 4.1 base, which for AWS-heavy shops means the tables are readable from Athena and Redshift Spectrum without a self-hosted engine in the loop. The trade-off is version-lock: Iceberg v3 tables cannot be read by v2-only engines, so a table with any of these columns quietly excludes readers still on older Spark, Flink or Trino builds.

Adoption-wise, the practical migration is not schema-level but writer-level. Streaming writers based on Kafka Connect Iceberg sinks, Debezium Iceberg, or homegrown Glue jobs need their Iceberg library bumped to a v3-capable release before they can write these columns; a partial upgrade of writers to a v3 table will fail at commit rather than degrading silently.

### 🎯 Takeaway (Hợp)
Prototype an Iceberg v3 table with GEOMETRY plus VARIANT on a Glue 6.0 dev environment and read it from Athena and Redshift Spectrum to confirm your target consumers actually see the new types before you migrate a production table. Audit every writer that hits the table (Spark, Flink, Kafka Connect, custom Python) for Iceberg v3 support first — mixed writer versions on a v3 table is where the failure mode lives.

### 💡 Example
```sql
CREATE TABLE fleet_monitoring_db.vehicle_telemetry (
  event_id STRING,
  vehicle_id STRING,
  vehicle_type STRING DEFAULT 'UNKNOWN',
  event_time TIMESTAMP_NTZ(9),
  location GEOMETRY(4326),
  service_area GEOGRAPHY(4326),
  sensor_payload VARIANT,
  speed_kmh DOUBLE DEFAULT 0.0,
  region STRING DEFAULT 'EMEA'
) USING ICEBERG
TBLPROPERTIES (
  'format-version' = '3',
  'write.delete.mode' = 'merge-on-read'
)
PARTITIONED BY (days(event_time), vehicle_type);

SELECT event_id, vehicle_id,
       variant_get(sensor_payload, '$.fuel_pct', 'DOUBLE') AS fuel_pct
FROM fleet_monitoring_db.vehicle_telemetry
WHERE ST_Intersects(location,
        ST_SetSrid(ST_GeomFromWKB(X'{POLY}'), 4326));
```

### 🔭 Overview (Tổng)
Databricks published a deep dive on the storage architecture behind Lakebase Postgres, its managed OLTP layer for agentic workloads. The core inversion is that the write-ahead log becomes the durable source of truth, materialised asynchronously into pages on object storage, rather than the traditional Postgres model of mutable heap files on block storage. The article frames Lakebase as the OLTP complement to the Delta lakehouse — same object-store substrate, same time-travel primitives — repositioned for the agent-driven read/write patterns where transient branches and instant rollbacks are the common case.

### 🔬 Details (Phân)
The compute layer is unmodified Postgres — same MVCC, same lock manager, same query planner — but never reads directly from object storage. Instead, queries traverse a three-tier read path: RAM shared buffers, local NVMe cache, then the pageserver on a miss. The storage layer splits into three components: safekeepers replicate WAL records through a Paxos-based quorum, the pageserver replays WAL into pages and asynchronously materialises them into an immutable append-only history on object storage. Commit latency depends on safekeeper quorum acknowledgement, not on the object-store write, which is what keeps commit performance in a normal OLTP range despite the S3-shaped tail on the durability path.

The architectural payoff shows up in four agent-facing features. Branching creates a fresh database as a reference to a specific log sequence number rather than a physical copy, so an agent can spin up an isolated environment for schema experiments in seconds. Instant restore points the head reference at an earlier LSN with no data movement. Time-travel queries let an application inspect past table states directly rather than restoring a backup. And scale-to-zero suspends compute nodes after idle periods without losing state, because everything durable lives in the WAL and object-store layer. The post makes no direct concrete latency or throughput claim beyond the architectural description, so numbers still have to come from benchmarks.

The competitive framing is worth naming. This is the Neon architecture (Neon was acquired by Databricks in 2025) exposed as a first-class Databricks product. Aurora Postgres, Google AlloyDB and Azure Cosmos for PostgreSQL each have their own compute-storage separation stories, but none of them bake time-travel and LSN-based branching into the developer surface the same way. For teams that already run Delta and are looking for an OLTP tier that shares governance and lineage with the lakehouse, the pitch is that operational data and analytical data now sit on the same object-store fabric.

### 🎯 Takeaway (Hợp)
Read this article before your next OLTP-tier decision if you are running Databricks and evaluating Aurora, AlloyDB, or self-hosted Postgres alongside the lakehouse — the branching and scale-to-zero primitives are the actual differentiators, not the raw TPS number. Wait for third-party benchmarks before assuming Lakebase latency matches a standard Aurora deployment; the WAL-first path is sound in theory, but the numbers that matter for your workload are p99 commit and cold-start branch time, both of which need measurement.

### 💡 Example
```
Lakebase Postgres storage stack
  Compute      : unmodified Postgres (MVCC, locks, planner)
  Read path    : RAM shared buffers  ->  local NVMe cache  ->  pageserver
  Write path   : WAL  ->  safekeepers (Paxos quorum ack -> commit)
                       \-> pageserver  ->  object storage (async, immutable)

Agentic primitives (built on LSNs)
  Branch       : new DB = reference to LSN, no data copy
  Restore      : head -> earlier LSN, no data movement
  Time-travel  : SELECT ... AS OF LSN 'xxxxxxxx'
  Scale-to-0   : suspend compute; durability stays in WAL + object store
```

## 3. Picnic Fronts a Single Amazon MQ Broker With Two OAuth Providers

| Field | Value |

### 🔭 Overview (Tổng)
Picnic and AWS co-authored a tutorial covering a real-world gap in the Amazon MQ for RabbitMQ documentation: authenticating human operators through Keycloak and microservices through AWS IAM against the same broker. The stock docs walk through single-provider OAuth setup, but production estates typically have separate identity paths for people and services, and both should not have to go through the same identity provider. The post shows how RabbitMQ's multi-resource-server support handles this cleanly using audience claims on incoming tokens.

### 🔬 Details (Phân)
The trick is the RabbitMQ `resource_servers` config, which lets one broker bind multiple OAuth providers, each with its own signing keys, issuer, JWKS endpoint, and scope-mapping rules. Every incoming token is dispatched to a provider based on its `aud` claim: `rabbitmq-keycloak` for operator tokens, `rabbitmq-iam` for service tokens. The broker enables `auth_backends.1 = oauth2` and requires `auth_oauth2.verify_aud = true` so that a token that does not carry a recognised audience is rejected rather than falling through to the next backend. Keycloak groups map to RabbitMQ scopes through `scope_aliases`, and IAM roles are wired through the same alias mechanism with role ARNs on the left-hand side.

Two operational details are worth surfacing. First, Amazon MQ configuration for RabbitMQ is edited by uploading a base64-encoded `.conf` file through the AWS CLI or console — there is no live-reload equivalent for these fields — so a bad audience mapping means a rolling broker restart. Second, `verify_aud = true` is the single flag that turns the multi-provider pattern from "works" to "safe": without it, a token minted for a different service could be accepted with the wrong scope set, because JWKS validation alone does not enforce which provider was supposed to have issued the token for this broker.

Compared with the more common workarounds — running two brokers, or fronting one broker with an OAuth proxy that rewrites claims — the native multi-resource-server route keeps the number of moving parts down and preserves per-provider scope mapping. It does not solve authorisation-model differences: Keycloak groups and IAM role hierarchies still need a shared mental model on the RabbitMQ side.

### 🎯 Takeaway (Hợp)
Adopt the multi-resource-server pattern before considering a second broker if your Amazon MQ for RabbitMQ estate is authenticating both humans and services — it is materially simpler than the alternatives and needs no external proxy. Set `auth_oauth2.verify_aud = true` from the start; the multi-provider setup is not safe without it, and this is the single easiest security regression to leave in.

### 💡 Example
```ini
# Amazon MQ RabbitMQ configuration (uploaded as base64 .conf)
auth_backends.1 = oauth2
auth_oauth2.verify_aud = true

# Keycloak provider
auth_oauth2.resource_servers.rabbitmq-keycloak.id                = rabbitmq-keycloak
auth_oauth2.resource_servers.rabbitmq-keycloak.issuer            = https://keycloak.picnic.internal/realms/prod
auth_oauth2.resource_servers.rabbitmq-keycloak.jwks_uri          = https://keycloak.picnic.internal/realms/prod/protocol/openid-connect/certs
auth_oauth2.resource_servers.rabbitmq-keycloak.scope_aliases.op  = rabbitmq.configure:*/*  rabbitmq.write:*/*  rabbitmq.read:*/*

# AWS IAM provider
auth_oauth2.resource_servers.rabbitmq-iam.id                     = rabbitmq-iam
auth_oauth2.resource_servers.rabbitmq-iam.issuer                 = https://oidc.eu-west-1.amazonaws.com
auth_oauth2.resource_servers.rabbitmq-iam.jwks_uri               = https://oidc.eu-west-1.amazonaws.com/.well-known/jwks.json
auth_oauth2.resource_servers.rabbitmq-iam.scope_aliases.orders   = rabbitmq.write:%2F/orders.*   rabbitmq.read:%2F/orders.*
```

### 🔭 Overview (Tổng)
The Opener Initiative has released an Apache 2.0 reference implementation of DECT NR+ (formally DECT-2020 NR), covering the MAC layer and the upper protocol layers up to Application Profiles. It is written in C, targets Zephyr RTOS, and initially runs on Nordic Semiconductor's nRF91 series — the first commercially available radios with integrated DECT NR+ hardware. This is a meaningful step for the standard because the biggest blocker to DECT NR+ adoption so far has been the absence of a permissively licensed, production-usable stack outside of vendor SDKs.

### 🔬 Details (Phân)
DECT NR+ is designed for two workloads that are hard to serve well together: massive machine-type communications (up to one million devices per km²) and ultra-reliable low-latency links (sub-millisecond air-interface latency at 99.999% reliability targets). It operates in the license-exempt 1880–1930 MHz band, with an expansion to 3.8–4.2 GHz already agreed in Europe, and — unlike cellular NB-IoT or LTE-M — does not require centralised base-station infrastructure; devices negotiate roles dynamically and can form point-to-point, star or mesh topologies. Battery life targets are quoted in years for low-power sensor profiles.

Opener consists of two GitHub repositories, `opener` and `opener-samples`, hosted under the Opener Initiative organisation. Hardware support at launch centres on Nordic's nRF9151 DK and nRF9151 SMA DK, with third-party boards from Makerdiary, Norik Systems and Conexio, and Last Mile Semiconductor flagged as an incoming silicon vendor. Because the stack layers on top of Zephyr, integration with the standard Zephyr networking, device tree and Kconfig systems is direct rather than through a wrapper. The MAC layer is where most of the standard's cleverness lives — non-centralised scheduling, dynamic role assignment, hybrid ARQ — and having that in open source unlocks academic and industrial research that previously had to work through binary blobs.

Positioning versus other massive-IoT and low-latency standards is a useful sanity check. NB-IoT and LTE-M give you carrier-managed connectivity but centralised infrastructure and per-device SIM economics; LoRaWAN is unlicensed but not low-latency; Wi-Fi HaLow (802.11ah) is broadly comparable in ambition but has weaker mesh guarantees. DECT NR+ is the first standard combining unlicensed operation, massive-density support, and hard-real-time capability in one PHY, and Opener is the first Apache-licensed way to actually build on it.

### 🎯 Takeaway (Hợp)
Read the Opener samples and clone the repos onto an nRF9151 DK if your product roadmap includes ultra-dense sensor networks, industrial mesh telemetry, or asset tracking on unlicensed spectrum — this is the standard that unlocks those designs, and an Apache 2.0 stack is the missing piece. Track Last Mile Semiconductor and other second-source silicon; single-vendor availability is the current fragility, and a second radio option will decide whether DECT NR+ becomes a serious LoRaWAN alternative or stays a Nordic-only ecosystem.

The reason to look at this project is not the object itself but the pattern: a $10 BOM RISC-V MCU, a $3 round display, one Wi-Fi API, and an open-source repository is now enough to ship a category of ambient-data devices that used to require a Raspberry Pi. Use Deskradar as a reference build if you are prototyping a desktop ambient-data display on ESP32-C3 with a round GC9A01 — the two GitHub repos and the STL files short-cut the boring parts.
