### 🔬 Details (Phân)
The technical substance in the announcement is grounded in existing production use. Beyond QuickSight/Quick, DuckDB already reads Parquet, CSV and JSON directly from S3, runs in-process inside AWS Lambda, and is a common building block in serverless analytics stacks — the acquisition is framed as accelerating first-party integration across AWS analytics services rather than introducing a new proprietary fork.

The governance line is worth reading carefully. The DuckDB open-source project stays under the DuckDB Foundation, which is legally separate from DuckLabs the company; the DuckLabs team continues to steer the project but is now inside AWS. Historical precedent for that pattern is mixed: it has held for some hyperscaler-adjacent projects and drifted for others when commercial incentives changed. The post's specific commitment is to the MIT license and to the Foundation's oversight, not to feature parity between an eventual AWS-hosted DuckDB service and the community build.

The wider context is that this lands the same week the DuckDB core team published a v2.0 preview engineering post claiming a 42.6x speedup on recursive CTEs — the roadmap is clearly still moving in the open project and not stalled by the deal. Teams building on DuckDB should treat this as a stability signal for the open engine and a competitive signal for adjacent vendors (MotherDuck, Fivetran's SDF work, Snowflake's DuckDB-adjacent posture) rather than as a licensing risk today.

## 2. Amazon MSK Ships In-Place ZooKeeper-to-KRaft Upgrades Without Downtime

| Field | Value |
|---|---|
| 📅 Date | 26/08/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `amazon-msk` · `kraft-migration` · `kafka-3-9` |
| ⚡ Impact | High |

### 🔭 Overview (Tổng)
AWS enabled in-place ZooKeeper-to-KRaft migration on Amazon MSK, so existing clusters can shed ZooKeeper without provisioning a new cluster and copying data across. Apache Kafka has been on the KRaft path for years — ZooKeeper support was deprecated in 3.4, removed from KRaft-only mode in 4.0 — and until now MSK operators without an in-place path faced either dual-writing to a new cluster with Cluster Linking or a maintenance-window mirror. That option is closing, and this announcement removes it entirely for MSK provisioned clusters.

### 🔬 Details (Phân)
The migration runs as a five-phase state machine: (1) provision KRaft controllers alongside the existing ZooKeeper ensemble, (2) migrate metadata from ZooKeeper into the KRaft log, (3) roll brokers one AZ at a time while keeping the data plane available, (4) validate cluster health, and (5) decommission ZooKeeper. AWS explicitly states there is no expected downtime for produce/consume traffic when best practices are followed, and MSK monitors cluster health throughout; if it detects a condition that prevents completion, it automatically returns the cluster to its pre-migration state. That last line matters — the rollback removes the "no way back" fear that has kept several teams on ZooKeeper past the deprecation.

Prerequisites are specific and worth checking against your fleet: Kafka 3.9.x in ZooKeeper mode, standard brokers across three AZs, no under-replicated partitions, and clients on Apache Kafka library v3.0 or later. Anything that reaches into ZooKeeper directly — custom domain configuration through dynamic ZooKeeper settings, external tooling that reads ZK znodes, or applications still holding ZooKeeper connection strings — must be removed before initiation. The migration itself is triggered via the AWS console (a CLI equivalent through the standard `describe-cluster-operation` API is available for monitoring), which is a deliberately conservative interface.

The alternative — Cluster Linking to a fresh KRaft cluster — remains viable but expensive: double capacity during cutover, consumer offset reconciliation, and a longer maintenance calendar. For most MSK workloads the in-place path is now the default recommendation, provided the client-library and dependency preconditions are actually met, which is where the risk sits.

### 🎯 Takeaway (Hợp)
Audit client libraries and any code that reaches into ZooKeeper this week — the migration itself is well-instrumented, but the preconditions catch teams who assumed "we upgraded to 3.9 last year" was enough. If you are still on Kafka 3.7 or 3.8 on MSK, the sequenced plan is now: upgrade to 3.9, remove ZooKeeper dependencies, then run the in-place KRaft migration; skipping either preliminary is where the automatic rollback will bite.

### 💡 Example

  Kafka version         : 3.9.x, ZooKeeper mode
  Broker deployment     : Standard brokers, 3 AZs
  Client library        : Apache Kafka >= 3.0
  Partition health      : no under-replicated partitions
  ZooKeeper access      : disabled; no ZooKeeper connection strings in clients
  Custom domain config  : remove settings applied via dynamic ZK config

## 3. Iceberg v3 on AWS Glue 6.0 Adds Native Geospatial and VARIANT Types

### 🔭 Overview (Tổng)
AWS published a walkthrough of the Iceberg v3 types that Glue 6.0 now supports natively: GEOMETRY and GEOGRAPHY, nanosecond-precision `TIMESTAMP_NTZ(9)`, and the VARIANT type for semi-structured payloads. The example is a connected-vehicle telemetry pipeline, which is representative of the workload class where the previous workarounds — lat/lon columns with hand-rolled distance math, microsecond truncation of high-frequency sensor events, and separate tables per payload shape — have been most painful. Any Iceberg deployment that has been carrying those workarounds should read this release note before its next schema migration.

### 🔬 Details (Phân)
The geospatial types replace the pattern of storing latitude and longitude as two separate DOUBLE columns and computing intersections in Spark UDFs. With v3, spatial predicates land in the SQL layer as first-class functions — the walkthrough uses `ST_Intersects(location, ST_SetSrid(ST_GeomFromWKB(...), 4326))`, which the Iceberg planner can push down as a manifest-level filter rather than materialising every candidate row. Enabling the type requires a job-level configuration flag, `spark.sql.geospatial.enabled=true`, so it is opt-in per job rather than per table, which matters for shared Glue environments.

Nanosecond timestamps close a smaller but frequently-hit gap. Iceberg's earlier microsecond `TIMESTAMP_NTZ(6)` was fine for most business data but lost ordering on high-frequency sources — device telemetry, IoT event streams, and some observability pipelines — where two events genuinely land within a microsecond. The walkthrough uses `.123456789` versus `.123456790` as the concrete example: indistinguishable at microsecond precision, deterministically ordered at nanosecond precision. VARIANT is the type most people will use most: it stores JSON-shaped documents with per-row schema variation in a single column, avoiding the flatten-and-split refactor that heterogeneous payloads have forced up to now.

The trade-off with VARIANT is real. It buys schema flexibility at the cost of the query optimiser being able to reason about payload structure, so predicates against variant fields do not push down the same way as against typed columns. The right pattern is the same one that emerged with Snowflake VARIANT and Databricks OBJECT: land raw payloads in VARIANT, materialise the fields you actually query into typed columns via a downstream job, and keep VARIANT as an audit/replay surface. Iceberg v3 also brings `DEFAULT` values for columns, which quietly removes a long-standing awkwardness around backfills.

### 🎯 Takeaway (Hợp)
If you run a Glue pipeline that stores lat/lon as two columns and computes intersections in Python UDFs, that refactor is worth a sprint now — the manifest-level pushdown will show up in scan volume and cost, not just latency. Roll VARIANT out to the ingest layer and keep typed columns for the query layer; treating VARIANT as the query surface is the shape you will regret.

### 💡 Example
```sql
-- Iceberg v3 on Glue 6.0
SET spark.sql.geospatial.enabled=true;

CREATE TABLE telemetry.vehicles (
  vehicle_id    STRING,
  event_time    TIMESTAMP_NTZ(9),
  location      GEOMETRY,
  payload       VARIANT
) USING iceberg
  TBLPROPERTIES ('format-version'='3');

SELECT vehicle_id, event_time
FROM telemetry.vehicles
WHERE ST_Intersects(
        location,
        ST_SetSrid(ST_GeomFromWKB(X'...'), 4326)
      )
  AND event_time >= TIMESTAMP_NTZ '2026-08-30 00:00:00.000000000';
```

## 4. Databricks Explains Lakebase Postgres: WAL on Object Storage as Source of Truth

### 🔭 Overview (Tổng)
Databricks published a deep dive on the storage architecture of Lakebase Postgres, its serverless Postgres for the agentic-application tier. The core claim is that the Write-Ahead Log lives on object storage and is the durable source of truth; pages are a materialised view of the log, held in a hierarchy of RAM, local NVMe, and a pageserver that reconstructs them on demand. That inversion is what makes instant branching, point-in-time restore, and multi-second-idle suspend cheap enough to run for interactive agent workloads, and the post is worth reading as a piece of database internals regardless of whether you use Lakebase.

### 🔬 Details (Phân)
Commits acknowledge as soon as a quorum of safekeepers has fanned out the WAL record — the pageserver's materialisation is asynchronous, so write latency is decoupled from page-cache warmup. Reads walk a preference order: RAM, then local NVMe cache, then a page request over the network to the pageserver, then object storage as the last resort. The pageserver holds base images and delta layers in a log-structured tree; a Log Sequence Number is a lightweight pointer into that tree, which is how "read as of LSN" and "branch from LSN" reduce to pointer manipulation instead of physical copies. Branching a 2 TB database costs effectively nothing until either side actually diverges.

Compute suspends after five minutes of idle, and read replicas can activate from suspended state in a few hundred milliseconds. That combination is what unlocks the agent-per-user model: an idle Postgres for each agent session is not a fixed-cost server anymore. The Paxos-based safekeeper replication is the durability substrate; the write pipeline avoids the standard Postgres "double write" tax because pages are never authoritative — they are cache. Lakebase also transcodes materialised pages into open columnar formats to serve HTAP-style analytical queries from the same durable record, which is where the Lakehouse-side story reconnects.

Positioning is honest. Neon pioneered this shape and open-sourced the pageserver primitives; AlloyDB decoupled Postgres storage and compute more conservatively; Aurora keeps a purpose-built distributed log but retains classical page durability. Lakebase's contribution is the tighter integration with Unity Catalog governance and the open columnar transcode, at the cost of tying to the Databricks control plane. The post does not publish head-to-head benchmarks, which is the honest omission — the architectural claim is durable and specific enough to reason about without them.

### 🎯 Takeaway (Hợp)
If you are prototyping agent-per-user memory stores today and reaching for a hosted Postgres, benchmark Lakebase's cold-start-plus-first-query latency against your actual session distribution before locking in — the "hundreds of milliseconds" number is dominated by cache warmup on the read side, not just compute spin-up. Independent of vendor choice, the WAL-on-object-storage pattern is the reference architecture to learn from this month.

### 💡 Example
```
Lakebase read path (preference order)
  1. RAM (compute-local page cache)
  2. Local NVMe (persistent page cache on the compute node)
  3. Pageserver (rebuilds pages from WAL segments over the network)
  4. Object storage (append-only WAL + immutable image/delta layers)

Branch at LSN
  # Creating a branch does not copy pages;
  # it points a new compute at the same LSN in the log tree.
  # Storage cost accrues only for divergent writes after the branch point.

Commit
  ack when a quorum of safekeepers has the WAL record;
  pageserver materialisation is asynchronous.
```

### 🔭 Overview (Tổng)
Espressif walked through a working Wi-Fi Aware datapath between an ESP32-C5 and an iPhone 12 running iOS 26, using ESP-IDF v6.1. Wi-Fi Aware, also called NAN (Neighbor Awareness Networking), sets up a synchronised cluster of devices that advertise and discover services, optionally pair, and then open a direct high-bandwidth encrypted link without an access point or router in the middle. Apple's decision to expose it in iOS 26 is what makes this newly interesting — the standard has been around for years, but the mobile side has been the missing peer for embedded devices.

### 🔬 Details (Phân)
The stack requires iOS 26 or iPadOS 26 on an iPhone 12 or newer (iPad 10th gen or newer), ESP-IDF v6.1 or newer, and an ESP chip with Wi-Fi Aware support — the example uses the ESP32-C5. Service discovery follows DNS-SD naming conventions, so services declare themselves under familiar `_service._proto` labels; peers discover each other in-cluster, pair using a six-digit PIN with a WPA3-PSK equivalent security handshake, and then establish an IPv6 socket over the data path. The security model is not optional: iOS mandates PIN pairing on this path.

The concrete configuration is a small struct — `wa_dp_security_cfg_t` — with `mode = WA_SEC_PIN_PAIRING` and `caching_enabled` on the pairing block so subsequent connections skip the PIN dance. The post does not publish throughput or range numbers, which is a real omission for anyone sizing a firmware/media-transfer use case, and the honest answer is that both depend heavily on the pairing of chip and phone RF stack and are worth measuring on your target hardware before designing around them.

The competitive frame is worth naming. Direct-P2P options for embedded-to-phone have been fragmented: Bluetooth for pairing plus a Wi-Fi provisioning step, proprietary Wi-Fi Direct with poor iOS support, or falling back to cloud-mediated relay. Wi-Fi Aware with iOS 26 support is the first credible cross-platform standard for local high-bandwidth peer links between phones and embedded devices, and it fits the same shape that Matter has been pushing at the smart-home layer — an open standard with first-party OS support on both sides.

### 🎯 Takeaway (Hợp)
If your product pairs an ESP-class device with an iPhone today over a mix of BLE plus router-mediated Wi-Fi, prototype the Wi-Fi Aware path on an ESP32-C5 dev board this month — the six-digit PIN flow and DNS-SD service model map cleanly onto Matter-style commissioning UX. Measure your actual throughput and range on the target chip before locking down the product spec; the post does not, and neither should you assume.

## 6. AWS IoT Wires a Bedrock Agent Into Firmware Rollout Decisions

| Field | Value |

### 🔭 Overview (Tổng)
AWS IoT posted a reference architecture for driving firmware rollouts with an agentic loop on top of AWS IoT Jobs. The agent plans deployment waves against a device risk profile, respects production schedules, monitors per-wave health after each rollout, and decides whether to proceed, pause, or rollback based on explicit success-rate thresholds. The setup is a Step Functions orchestrator plus Bedrock (Anthropic Claude Haiku 4.5 as the reasoning model), IoT Jobs as the delivery mechanism, and DynamoDB as fleet state — familiar AWS building blocks assembled around a reasoning loop instead of a hand-coded state machine.

### 🔬 Details (Phân)
The agent exposes five tools to the model: `get_fleet_inventory`, `get_device_risk_profile`, `get_wave_health`, `create_deployment_wave`, and `rollback_wave`. After each wave the model evaluates the returned health JSON — success rate, failure count, failure-type breakdown — against fixed thresholds: proceed above 98%, pause between 95% and 98%, rollback below 95% or on boot-loop detection. That threshold arithmetic is not itself an LLM job; the post is honest that the reasoning value is in wave planning and root-cause classification, and the model calls a deterministic health function for the numbers.

The design pattern here is the interesting piece, independent of the specific AWS glue. Firmware rollouts have historically been either fully manual (an ops team stares at dashboards between waves) or fully policy-driven (rigid percentage step-ups that ignore device context). An agent with tool access sits in the middle: it plans waves by risk cohort, reacts to unexpected failure patterns rather than only to raw counts, and produces an auditable rationale for each pause or rollback. The failure-type breakdown (`boot_loop`, `network_disconnect`, etc.) is what lets the agent distinguish a bad firmware image from a bad AZ.

Caveats are worth naming. The auditable-rationale property depends on logging every tool call and model response into a durable store, which the post gestures at but does not spec in detail. Handing rollback authority to a reasoning model without a hard human-in-the-loop gate for large-blast-radius fleets is a policy call, not a technical one; the sample code lets a canary-failure scenario roll back autonomously. For regulated-device fleets (medical, automotive), a two-key pattern — model recommends, human approves — is likely the right adaptation before this ships to production.

### 🎯 Takeaway (Hợp)
The five-tool interface is the template to take away, even if you do not use Bedrock: expose `get_fleet_inventory`, `get_device_risk_profile`, `get_wave_health`, `create_deployment_wave`, `rollback_wave` from your own OTA system and any capable model can drive it. Keep numeric decisions in deterministic tools and let the model plan and classify; that split is where this design gets its reliability.
