## 1. Databricks Ships Distributed Checkpoint and Async Save for PyTorch on AI Runtime

| Field | Value |
|---|---|
| 📅 Date | 28/08/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |

### 🔭 Overview (Tổng)
Databricks published a technical walkthrough of the checkpoint and data-loading changes now shipping with PyTorch on AI Runtime, aimed squarely at the failure model of long multi-GPU training jobs. The post from Bruce Fontaine grounds the argument in reliability arithmetic: a 256-GPU job over 30 days carries roughly a 19% failure probability, and a 1,024-GPU job around 57%, so treating checkpointing as expensive-but-rare becomes untenable at that scale. The release re-tools two critical paths — checkpoint write and remote dataset read — around the assumption that both must be nearly free to run frequently enough to preserve goodput.

### 🔬 Details (Phân)
The checkpoint side moves off `torch.save` gathering all state to a single rank and onto PyTorch Distributed Checkpoint (DCP), in which every rank writes its own distinct shard alongside metadata. The published numbers are large: a 2.8B-parameter DDP model on 32 H100s drops from 66s to 36s per checkpoint, and a 20B-parameter FSDP model on the same hardware drops from 522s to 9s — the FSDP case is where centralised gather previously dominated wall clock. `UCVolumeWriter` and `UCVolumeReader` land those shards into Unity Catalog volumes, so lineage and governance stay attached rather than being lost in ad-hoc object-store paths.

Async checkpointing (`async_save`) decouples the training loop from upload latency by staging the checkpoint into a memory buffer and pushing it to storage in the background, overlapped with continued training. Frequency of checkpointing turns out to matter more than raw speed: the post quotes an internal example on the Delta H100 supercomputer, where failures on 608 GPUs come every 1.9 hours, and shows that moving from every-2-hour to every-30-minute checkpointing lifts goodput from 64% to 91%. The dataloader story is separate but complementary — `UCVolumeDataset` caches files locally on first access and prefetches upcoming batches, and image-classification benchmarks show throughput rising from 57.2 to 417 images/sec on epoch one and 371.6 to 6,590 images/sec on epoch two, with GPU utilisation moving from 12.6% to 53.3%.

The subtler recommendation is on data-pipeline state. Model weights alone are not enough to resume correctly: RNG seeds, shuffling state, and dataloader position must all be checkpointed together, or a resumed run silently re-uses samples the previous run already consumed. This is a general point about resumable training that the industry has under-served; the post treats it as a first-class API surface rather than an afterthought.

### 🎯 Takeaway (Hợp)
If you are running distributed PyTorch on Databricks against an FSDP model over more than a handful of GPUs, migrating to DCP with `async_save` this sprint is worth it before your next long run. Move the RNG and dataloader state into the same checkpoint object as the weights — the DCP call sites make that ergonomic — because the silent data-corruption failure mode from partial resumes is far harder to catch than a crash.

### 💡 Example
```python
import torch.distributed.checkpoint as dcp
from databricks.pytorch import UCVolumeWriter, UCVolumeReader

state = {
    "model": model.state_dict(),
    "optimizer": optimizer.state_dict(),
    "rng": torch.get_rng_state(),
    "dataloader": dataloader.state_dict(),
    "step": step,
}

# Non-blocking: stages to buffer, uploads in background.
future = dcp.async_save(
    state,
    storage_writer=UCVolumeWriter("/Volumes/main/train/ckpt-latest"),
)

# On resume: sharded load from the same UC volume path.
dcp.load(state, storage_reader=UCVolumeReader("/Volumes/main/train/ckpt-latest"))
```

### 🔭 Overview (Tổng)
Espressif released an ESP DALI master component that implements IEC 62386 on the RMT peripheral, with support spanning the ESP32, ESP32-S2, ESP32-S3, ESP32-C3, ESP32-C6, ESP32-H2 and ESP32-P4 on ESP-IDF v5.5 or newer. DALI is the dominant addressable lighting bus in commercial buildings — offices, hospitals, warehouses — and having a first-party master implementation on cheap Espressif silicon lowers the cost floor of DALI-native controllers significantly. The release is explicitly positioned for the class of gateway that reads DALI on one side and speaks Matter on the other, which is where the market is heading.

### 🔬 Details (Phân)
The component covers IEC 62386-102 control-gear commands, queries, DAPC (direct arc power control), scenes and configuration, plus Parts 103 (control devices), 209 (DT8 colour control), 303 and 304. Commissioning is automated: `dali_commission()` and `dali_103_commission()` walk the bus with a binary-search algorithm to discover and assign short addresses, which is the historically painful part of setting up a DALI installation and where a lot of the labour cost of DALI has sat. `dali_master_do_transaction()` is the single call site for commands, queries and DAPC, which keeps the API surface small. Colour control lands via `dali_master_set_color()` accepting CCT in Mirek, RGB, or RGBWAF triples — the last is what modern tunable-white plus RGB fixtures actually take.

The Matter integration is described but stops short of a production example. The architecture maps DALI capabilities to Matter endpoints — dimmable lights to `OnOff`+`LevelControl`, tunable-white fixtures to `ColorControl` with colour temperature, RGB fixtures to extended colour — with state caching and bi-directional sync between the DALI bus and the Matter fabric. Anyone building a commercial-lighting bridge will want that piece and it is not code-complete here; the post is honest about that, and the pattern is straightforward for anyone who has built a Matter bridge before.

The hardware note is the one thing worth double-underlining. DALI is a 16 V current-driven bus and physically incompatible with GPIO logic: "Never connect the DALI pair directly to the SoC" is in the post for a reason. A DALI-compliant interface IC — an isolated line driver plus receiver — sits between the ESP and the bus, and the reference designs Espressif points to use standard parts. The competitive alternative on Espressif hardware has been community components and closed-source vendor stacks; a maintained first-party implementation on the RMT peripheral removes both the ownership question and the CPU-cost concern of bit-banging.

### 🎯 Takeaway (Hợp)
If your product ships a Matter bridge for commercial lighting and has been carrying a community DALI stack, plan the migration to the first-party component this quarter — the RMT-backed timing is more predictable than software UART, and having Espressif as the maintainer removes a supply-chain risk. Design the DALI-side interface IC into your PCB before prototyping; it is not optional and every serious bug report on DIY DALI hardware traces back to skipping it.

### 💡 Example
```c
#include "esp_dali.h"

dali_master_handle_t dali;
dali_master_config_t dali_config = {
    .rx_gpio = GPIO_NUM_4,
    .tx_gpio = GPIO_NUM_5,
};
ESP_ERROR_CHECK(dali_master_new(&dali_config, &dali));

// Walk the bus, assign short addresses; safe to re-run.

// Set fixture 3 to 3000 K at 80% level.
dali_master_set_color(dali, 3, DALI_COLOR_CCT_MIREK, 333);
dali_master_do_transaction(dali, 3, DALI_CMD_DAPC, 204 /* 0..254 */);
```

## 4. Raspberry Pi Cuts LCA Embodied Carbon 30% by Swapping Weight Models for MicroGreen and ACT

### 🔭 Overview (Tổng)
Raspberry Pi partnered with academic groups at Cornell Tech and Columbia (with earlier work from Harvard and Meta) to publish a more accurate embodied-carbon model for its silicon, and reports that the revised methodology cut the total product-lifecycle embodied carbon by roughly 30% versus its previous weight-based inference. The post from Roger Thornton reframes the exercise from marketing to methodology: the drop is not because the boards changed, but because the previous model over-counted emissions that the physics does not actually justify. For any hardware team publishing LCA numbers or answering carbon-disclosure questionnaires, the tooling and the pattern here are directly reusable.

### 🔬 Details (Phân)
The weight-based approach — take grams of silicon, multiply by a generic emissions factor — treats silicon as if a chip's environmental cost scales with mass, which is close to nonsense at wafer scale. The replacement tools are MicroGreen (Cornell Tech and Columbia, credited to Udit Gupta, Ariel Goldner and Xuesi Chen) and ACT, the Architectural Carbon Modelling Tool from Harvard and Meta. Both take the parameters that actually drive fab emissions — die area, process technology node, manufacturing yield, and per-step energy intensity — and compose them into a per-chip figure rather than a per-gram one. The unit economics are different: a small die at a mature node uses far less energy per unit than either weight or wafer area alone would suggest.

The 30% headline number applies to the total product LCA — board plus chip plus packaging plus logistics — not just the silicon line item, so most of it comes from de-double-counting rather than under-counting. That distinction matters when the number goes into a customer disclosure: the LCA is now smaller and more defensible, but the delta is not an efficiency improvement. The post frames the collaboration with Cornell and Columbia as taking lab-developed tools to production scale, which is where the wider research value sits — models like MicroGreen only get good when they are calibrated against real fab data at real volumes, which is the piece academic groups cannot get on their own.

The broader IoT relevance is that a lot of edge-device carbon disclosure runs on the same weight-based shortcut Raspberry Pi has now moved off. For any embedded team publishing customer-facing carbon figures — Matter fabric hubs, industrial sensors, connected white goods — the same MicroGreen/ACT stack is available and the same directional correction is likely, meaning the numbers a lot of the industry has quoted are probably conservative-in-the-wrong-direction rather than aspirational.

### 🎯 Takeaway (Hợp)
Ask whoever produces your LCA numbers whether the silicon line is weight-based or model-based; if it is weight-based, an internal recalculation with MicroGreen or ACT is worth doing before your next customer disclosure cycle. The recalculated number should ship with a short methodology note — customers who take LCA seriously will want to know why the figure moved, and "we corrected a modelling artefact" is a stronger story than a silent revision.

### 💡 Example
```
Traditional embodied-carbon estimate for a silicon component
  emissions_kgCO2e ≈ mass_grams × factor_kgCO2e_per_gram

Model-based estimate (MicroGreen / ACT, illustrative shape)
  emissions_kgCO2e = f(
    die_area_mm2,
    process_node,          # e.g. 40nm, 16nm, 7nm
    manufacturing_yield,   # fraction of good dies per wafer
    step_energy_intensity, # kWh per wafer per step, by node/tool mix
    fab_grid_intensity     # kgCO2e per kWh at the fab's grid
  )

Raspberry Pi's reported outcome
  Total product LCA fell ~30% after switching methods,
  driven by de-double-counting rather than product changes.
```

## 5. Home Assistant 2026.9 Beta Adds Matter Network Map and Shared Modbus Connections

### 🔭 Overview (Tổng)
The 2026.9 beta from the Home Assistant team lands two changes that will show up in real installations: a Matter network map inside the core UI, and a shared Modbus connection layer that lets multiple integrations talk to the same physical bus without stepping on each other. Twelve integrations join the core, sonification is added to charts for accessibility, and a serial-port settings panel consolidates hardware management. The release notes read as an infrastructure round rather than a feature-showcase round, which is often the more interesting kind for a home-automation platform.

### 🔬 Details (Phân)
The Matter integration now renders network topology — Thread and Wi-Fi connections, device types, and signal strength — directly in the core Home Assistant UI. Previously this information lived only in the separate Matter Server interface, which is fine for the initial commissioning session but not what you reach for when a device drops off the network at 2 AM. Having Thread mesh visualisation in the same place as your automations means diagnostic loops close in one context rather than three. It is a small change with a large operational payoff for anyone running a nontrivial Matter fabric.

The shared Modbus connection is the technically-notable change. Multiple integrations — Fronius, Sofar, Flexit are the concrete first users — can now share a single Modbus RTU/TCP connection instead of each opening its own, which was the class of bug that produced "randomly one integration goes offline" reports on solar-plus-HVAC installations. The architectural change is a connection pool with per-integration slave-address routing, and the design is generic enough that any Modbus integration can adopt it. Alongside this, the Update entity permission model tightens (only privileged users can trigger firmware installs by default), Matter doorbells gain proper event support, and Z-Wave JS adds an access-control interface for device credentials.

The accessibility work deserves an explicit mention: charts are now keyboard-navigable and support sonification, in which data points produce tones that rise and fall with values. It is a real accessibility improvement, and the sonification pattern is generalisable to anyone building dashboarding tools. The release also includes backward-incompatible changes worth reading before upgrading a production install — Flexit fireplace mode is removed, KNX expose behaviour changes, and some update-entity behaviour changes for non-admin users — so this is a beta to try on a spare instance first, not a stable channel to roll onto your household hub.

### 🎯 Takeaway (Hợp)
If you run a Modbus solar/HVAC stack on Home Assistant and have been living with the "one integration steals the port" bug, this beta is worth trialling on a spare instance now and moving to the stable release when it drops in early September. For any Matter deployment beyond a handful of devices, the in-core network map alone justifies the upgrade — it will change how you triage the next dropped device.
