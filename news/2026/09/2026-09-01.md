## 1. BigQuery Graph Hits GA With GQL, Cross-Cloud Traversals, and Agent-Grounding Context Graphs

### 🔭 Overview (Tổng)
Google marked BigQuery Graph generally available today, promoting native graph analytics inside the warehouse from preview to production and folding it into the same engine that already runs SQL and BigQuery ML. The post from Bei Li and Candice Chen frames the release as "one engine, two jobs — large-scale graph analytics, and connected context for AI agents", and the second half of that sentence is doing most of the work: the GA lands alongside features that turn the graph layer into grounded memory for Gemini Enterprise via an MCP server. For a data team that has previously stood up a separate Neo4j or Neptune to answer traversal questions, the interesting question is now whether the extra hop is worth keeping.

### 🔬 Details (Phân)
The query surface is ISO-standard GQL sitting next to SQL, over property graphs defined as node and edge tables. The node/edge tables can reference native BigQuery tables, Iceberg tables on Cloud Storage, or Iceberg tables federated from Databricks Unity Catalog, AWS Glue Data Catalog, or Snowflake — Google calls this "borderless lakehouse" and it is the material differentiator from a standalone graph database, since a traversal like `(:Customer)-[:Bought]->(:Product)-[:Supplied_By]->(:Supplier)` can span three clouds without a data-movement step. Performance is quoted as 2x faster GQL execution and 100x faster undirected traversal since preview, and cycle detection under the `ACYCLIC` and `TRAIL` path modes is claimed as more resource-efficient than the earlier engine.

The agent-facing pieces are what make this GA more than a warehouse-catches-up release. Context graphs give an agent an auditable memory whose reasoning traces live in BigQuery Graph itself, so a downstream review can walk the exact node/edge path a model took. The Data Agent Kit — see item 5 — can now author and verify graph schemas end-to-end from a prompt in Antigravity, VS Code, or Claude Code, and Gemini Enterprise reaches the graph through a shipped MCP server, which is the same pattern Databricks Genie is using for its own AI-facing surfaces. Security inherits BigQuery's row- and column-level controls, so the graph does not open a new authorisation model.

Migration is the honest question. A production Neo4j or Neptune stack carries operational muscle memory that will not port cleanly; the GA is more compelling for teams standing up a new graph workload than for teams with a running one. Pricing was not disclosed in the post — the doc pointer is to BigQuery pricing generally, which usually means slot- and byte-scan billing applied to graph queries the same way as SQL, but that is worth confirming against your account before planning capacity.

### 🎯 Takeaway (Hợp)
If your team already runs BigQuery and a small dedicated graph store — fraud, identity resolution, customer 360 — schedule a two-week spike to port a representative traversal onto BigQuery Graph before renewing the graph-store contract; the borderless lakehouse angle is the reason. If you are grounding a Gemini agent on enterprise data and have not yet chosen a memory layer, the context-graphs pattern is worth reading before you commit to a vector-only design; retrieval and traversal answer different classes of question.

### 💡 Example
```sql
CREATE OR REPLACE PROPERTY GRAPH `my_project.retail.virtual_kg`
NODE TABLES (
  `my_project.gcs_lake.retail.customers`  AS Customer KEY (customer_id),
  `my_project.dbx_fed.retail.products`    AS Product  KEY (product_id),
  `my_project.dbx_fed.retail.suppliers`   AS Supplier KEY (supplier_id)
)
EDGE TABLES (
  `my_project.gcs_lake.retail.purchases`  AS Bought
    KEY (purchase_id)
    SOURCE      KEY (customer_id) REFERENCES Customer (customer_id)
    DESTINATION KEY (product_id)  REFERENCES Product  (product_id)
);

GRAPH `my_project.retail.virtual_kg`
MATCH (c:Customer {customer_id: 'C1'})-[:Bought]->(:Product)-[:Supplied_By]->(s:Supplier)
RETURN s.name AS supplier, s.country AS supplier_country;
```

## 2. Databricks Details the Lakebase Postgres Autoscaler: HyperLogLog Working-Set Plus CPU and Memory Signals

| Field | Value |
|---|---|
| 📅 Date | 31/08/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `lakebase-postgres` · `neonvm-autoscaler` · `hyperloglog` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
Carlota Soto's post walks through the autoscaler that sits underneath Lakebase Postgres, which Databricks says has scaled databases more than 32,000 times per month across the fleet. Where earlier Lakebase coverage focused on the storage-side architecture — WAL replication and pageservers on object storage — this piece is about the compute-side control loop that decides when to add or remove CPU and memory from a running VM. The design is unusual enough to be worth reading even for teams not on Lakebase: it combines the three signals engineers usually pick between, and gives downscaling the same weight as upscaling.

### 🔬 Details (Phân)
The autoscaler-agent computes three independent target sizes and takes the maximum. `cpuGoalCU` reads the VM's one-minute CPU load average every five seconds and targets ≤90% capacity. `memGoalCU` polls memory at two frequencies — five seconds at the VM level and 100 milliseconds inside Postgres itself — and targets 75% of allocated RAM; an earlier prototype used cgroup `memory.high` events but the team replaced it with polling because polling behaved "more predictable and stable" under load. `lfcGoalCU` is the interesting one: it estimates working-set size using a modified HyperLogLog that stores timestamps at register positions instead of bits, which lets the same sketch answer "how many distinct pages are hot in the last 1 to 60 minutes" over sliding windows. That structure detects sharp drops when an old workload ends and lets the agent shrink the cache instead of paying to keep dead pages resident.

The scaling mechanism sits inside NeonVM, which adds or removes CPU and memory from a running Postgres VM without dropping client connections; if the current node cannot grow in place, the system falls back to live migration. The blog's stance on downscaling — treated symmetrically with upscaling rather than being biased toward oversizing — is where the design departs from a lot of production autoscalers, which tend to grow aggressively and shrink conservatively. On a bursty analytics workload that is the safer default; on a spiky OLTP workload that pays real money for oversized nodes overnight, the symmetric policy is the point.

The competitive frame the post does not name explicitly is Aurora Serverless v2 and AlloyDB. Both operate on similar separation-of-compute-and-storage foundations, and the differentiator Databricks is pushing here is the working-set signal rather than pure CPU-and-memory reactive scaling. Whether that translates into a materially better goodput number in a bench-off is the missing piece; the post gives the algorithm but not a head-to-head.

### 🎯 Takeaway (Hợp)
If you are running Lakebase in preview and have been sizing compute defensively for peak, dial the autoscaling limits wider on a non-production instance this week and watch whether the working-set signal shrinks the average size — that is where the cost saving lands. If you are running Aurora Serverless v2 on a workload with a clear diurnal cache profile, the HyperLogLog-with-timestamps sketch is worth reading as a pattern; the same construction is generalisable to any cache-size autoscaler you write yourself.

### 💡 Example
```
Every 5 seconds:
  cpuGoalCU  = size such that projected_1min_load / capacity(size) <= 0.90
  memGoalCU  = size such that projected_rss     / ram(size)        <= 0.75
  lfcGoalCU  = size such that hot_page_count(window=15m) fits in shared_buffers(size)

  target = max(cpuGoalCU, memGoalCU, lfcGoalCU)
           # projected_* are forward projections, not last-tick values,
           # so capacity is added before pages evict.

  if target != current:
    if node_has_headroom(target):
      NeonVM.resize_in_place(target)      # no dropped connections
    else:
      NeonVM.live_migrate(target_node(target))
```

## 3. Kinesis Data Streams Ships Managed Iceberg Streaming Tables With Inline Compaction and 50% Lower Delivery Cost

| Field | Value |
|---|---|
| 📅 Date | 31/08/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `kinesis-streaming-tables` · `s3-tables` · `inline-compaction` |
| ⚡ Impact | High |

### 🔭 Overview (Tổng)
AWS turned on a managed capability inside Kinesis Data Streams that continuously delivers a stream directly into an Apache Iceberg table on S3 Tables, with no custom application, no self-managed compute, and no external ETL job in the middle. The post from Nikit Pednekar, Mazrim Mehrtens and Ren Liu quotes headline numbers of 50% lower delivery cost and up to 30% lower query cost compared with self-managed alternatives, and puts the pricing at $14 per TB delivered against $28 per TB for a stream-to-Iceberg pipeline built by hand. For any team currently gluing Kinesis to Iceberg via a Flink or Spark job, this is the AWS-native option the market has been asking for.

### 🔬 Details (Phân)
The mechanism doing the work is inline compaction: the service produces query-optimised Parquet files during ingestion rather than writing tiny files and running a separate compaction job later, which is where the "small file problem" cost normally shows up. Tables are automatically registered in the AWS Glue Data Catalog, so Athena, Redshift, EMR (Spark), and Apache Flink can read them the moment they land, without a discovery step. Setup is a few clicks in the console or a call through the Kinesis Data Streams APIs, and there is a Kinesis Data Streams Agent Skill in the AWS Agent Toolkit that lets an AI-assisted IDE wire it up from a prompt.

The competitive frame the post does not spell out is worth naming. Kinesis Data Firehose already ships records to S3 in Parquet, but Firehose has historically dropped raw Parquet files without the maintenance a proper Iceberg table needs — the small-file problem is exactly what this release addresses. MSK Connect with a Flink Iceberg sink is the other alternative, and it works, but its operational overhead is the reason the $14 vs $28 gap exists at all. The engineering tradeoff is that inline compaction constrains the write path — you get the schema and partitioning Kinesis picks for you, not an arbitrary Iceberg maintenance plan — but for the streams that would otherwise be flattened into S3 raw and re-ingested later, that constraint is almost always a net win.

Availability is across all AWS Regions where Kinesis Data Streams already runs, and the post reads as GA rather than preview. What it does not explicitly cover is Iceberg maintenance operations — compaction of older snapshots, expiration, orphan-file cleanup — so treat the managed piece as ingestion-plus-write-compaction and keep your existing Iceberg housekeeping running on the target table.

### 🎯 Takeaway (Hợp)
If you are running a bespoke Flink or Spark job to keep Kinesis in sync with an Iceberg table on S3, budget a spike this week to retarget it at streaming tables and measure the delivered per-TB cost against your current infra bill; the 50% headline is the ceiling, but even half of that pays for the migration. Do not skip the Iceberg-side housekeeping — snapshot expiration and orphan-file cleanup are still yours to run on the target table.

### 💡 Example
```
# Create a streaming table on S3 Tables that receives from a Kinesis stream.
# Illustrative CLI shape.

aws kinesis create-streaming-table-configuration \
    --stream-name my-events \
    --table-bucket-arn arn:aws:s3tables:us-east-1:123:bucket/analytics \
    --namespace prod \
    --table-name events \
    --iceberg-schema file://schema.json \
    --partitioning "day(event_time),region" \
    --inline-compaction ENABLED

# Query immediately via Athena — the table is auto-registered in Glue.
SELECT region, count(*) c
FROM   "s3tablescatalog/analytics"."prod"."events"
WHERE  event_time >= current_date - INTERVAL '1' DAY
GROUP  BY region;
```

## 4. AWS Glue 6.0 Adds Spark Real-Time Mode: Sub-Second Kafka Processing Without Micro-Batches

| Field | Value |
|---|---|
| 📅 Date | 31/08/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `spark-real-time-mode` · `aws-glue-6` · `iceberg-v3` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
The Glue 6.0 release cycle has already brought Iceberg v3 with geospatial and Variant types (covered earlier this week); today's post from Shoukat Ghouse and colleagues lands the second piece — Spark Real-Time Mode (RTM), which removes the micro-batch boundary from Structured Streaming and processes records as they arrive with sub-second latency. It is the same continuous-processing lineage as Apache Flink and the older Continuous Trigger, but reworked as a first-class mode inside Spark 4.1 and exposed on Glue with a one-line trigger change. For teams already running Structured Streaming jobs on Glue for feature detection or fraud scoring, this is the migration path Spark users have been waiting for since Continuous Trigger was left in experimental limbo.

### 🔬 Details (Phân)
The mode change is small on the surface — `Trigger.RealTime("1 minute")` instead of `Trigger.ProcessingTime(...)` — but the semantics underneath are different. Records flow through the pipeline continuously; the "1 minute" is a checkpointing cadence for recovery, not a batching interval. The blog demonstrates a Kafka-fed pipeline against Iceberg v3 tables using Variant columns for semi-structured payloads, `variant_get` for path-based field extraction at read time, Arrow-native UDFs for vectorised Python compute on `pyarrow.Array` inputs, and the new deletion vectors (Roaring Bitmaps) that replace positional delete files. The end-to-end path hit sub-second latency on the real-time branch, and the same pipeline can run the batch branch of the workload alongside without a second job.

The limits are worth reading before planning a migration. RTM in Glue 6.0 is Kafka-source only, stateless, Scala-only, and fixed-worker; it supports the update output mode but not append-with-watermarks or the wider stateful aggregation surface Structured Streaming has today. In practice that means feature extraction, event enrichment, filter-and-forward — the "lightweight per-record" workloads — are the right target, and anything joining a stream to a slowly-changing dimension or windowed aggregation should stay on micro-batches for now. The post does not explicitly stamp GA vs preview, but the constraint list reads as "production-ready but feature-limited" rather than tech preview.

Iceberg v3 is the quieter co-star. The Variant type replaces JSON columns with a schema-free binary representation that supports shredding — at write time the engine can extract known paths into typed Parquet columns while keeping the fallback for unknown fields — and the `write.parquet.shred-variants=true` table property turns that on. Deletion vectors on merge-on-read tables remove the join-with-delete-files cost at read time, which is where earlier Iceberg row-level updates paid a lot of latency.

### 🎯 Takeaway (Hợp)
If you have a Glue Structured Streaming job on Kafka that is stateless and Scala-friendly, port a single job to RTM against a test topic this week and measure end-to-end latency and cost against the micro-batch version; the sub-second path is worth confirming before you plan the migration. Turn `format-version=3` on for new Iceberg tables in the same pipeline — Variant shredding plus deletion vectors is the combination that pays for itself on write-heavy tables regardless of the streaming mode.

### 💡 Example
```scala
val df = spark.readStream
  .format("kafka")
  .option("kafka.bootstrap.servers", brokers)
  .option("subscribe", "trades")
  .load()

  .withColumn("v", from_json($"payload", tradeSchema))

  .format("iceberg")
  .outputMode("update")
  .option("path", "glue_catalog.market.flagged_trades")
  .option("checkpointLocation", checkpointDir)
  .trigger(Trigger.RealTime("1 minute"))   // continuous flow; 1m is checkpoint cadence
  .start()
```

## 5. Google Ships the Open-Source Data Agent Kit for YAML-Native Airflow Pipelines in the IDE

### 🔭 Overview (Tổng)
Google released the Data Agent Kit, an open-source collection of data-engineering tooling that plugs into VS Code, Claude Code, Codex and similar IDEs to let engineers author, deploy and debug production Apache Airflow DAGs from natural language. The kit sits on top of the Orchestration Pipelines framework the Google Cloud NEXT '26 announcements introduced, and its interesting contribution is the declarative YAML pipeline definition that decouples orchestration from underlying compute — the same pipeline file can compile down to Airflow on Cloud Composer or to Managed Service for Apache Airflow. Piotr Wieczorek and Alexandre Moueddene's post frames the "weeks to minutes" headline as an MLOps stack — extract, train, batch predict, evaluate — built end-to-end inside a conversation.

### 🔬 Details (Phân)
The YAML surface is where most of the value sits. A pipeline file declares actions of typed kinds — `sql`, `pyspark`, `ai`, `orchestrationPipeline` — with explicit `dependsOn` edges, and the framework compiles that to an Airflow DAG at deploy time. The example in the post wires a BigQuery SQL extract to a Dataproc Serverless PySpark training job, a Vertex batch prediction call, and a conditional retraining trigger, all in three short YAML files. The Data Engineering tab in the kit gives a dedicated view of pipelines, runs and their logs; the agentic skill uses that context to generate PySpark scripts, dbt configurations, and GitHub Actions CI/CD in the same session.

The strategic move is worth reading against the field. Snowflake Cortex, Databricks Genie One (item 2 in yesterday's digest), and now Google's Data Agent Kit are all pushing the same pattern: pull IDE-native AI coding into the data platform's front door, and give it enough platform context that generated pipelines actually land on the vendor's runtime. Google's twist is the YAML abstraction and the explicit multi-runtime story — pipelines written this way are not immediately locked to Cloud Composer — and the open-source posture, which lets the framework absorb custom action types from the community. What it does not do is replace dbt or a hand-authored DAG for the shops that already have one; the kit is aimed at teams building pipelines from scratch or standing up an MLOps stack quickly.

The post does not explicitly stamp GA or preview, but the documentation depth and the "Get Started Today" call to full production deployment reads as a shipped product rather than a preview. Governance is the piece to watch: an agentic pipeline author needs the same discipline about environment separation, secret handling, and pull-request review that human authors get, and it is easy to skip that review when the DAG appears in one prompt.

### 🎯 Takeaway (Hợp)
If you are standing up an MLOps or ELT stack fresh on Google Cloud, spend an afternoon walking the kit through a representative pipeline before you commit to raw Airflow; the YAML abstraction is genuinely easier to review in a pull request than a 300-line DAG file. Do not skip the CI/CD scaffolding the agent generates — a pipeline authored in a prompt still needs the same environment gating and secret handling you would insist on for a human-authored one.
