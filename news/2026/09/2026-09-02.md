## 1. Databricks Finds Seven MCP Tool Bugs Costing $1.2M/Year and Publishes a Design Rule for LLM Tools

### 🔭 Overview (Tổng)
Alkis Polyzotis published a post-mortem describing an hour of work that cut roughly $1.2M/year of Databricks' internal AI-agent waste — $499K in tokens plus 12,000 engineering hours of agent wait time — by fixing seven bugs in the MCP tool servers the agent was calling. The interesting part is not the dollar figure; it is the shape of the bugs. All seven were the tool disagreeing with the model about type coercion or missing-argument defaults, and none were bugs the tool authors would have called bugs in a human-facing API. The post lands right on top of yesterday's Databricks Genie Ontology piece and the wider industry push to hand agents production data tools, and it is the first piece in that stack that quantifies the tax when the tools underneath are unforgiving.

### 🔬 Details (Phân)
The diagnosis stack is Unity Gateway plus OpenTelemetry tracing for every MCP call, queried by Genie One in natural language — an eat-your-own-dogfood setup that made the "where is the money going" question a chat, not a JIRA ticket. The bug table is worth reading directly. A Jira tool that expected a comma-separated string for its `fields` parameter got a JSON array from the model and threw `KeyError`: 137 failures per day, $250K/year, 2,500 wasted engineering hours. A different Jira endpoint hit `list.split()` on the wrong shape 535 times per day for $87K. The Google Drive `drive_file_get` call failed on optional field selection in 49.6% of invocations for $46K, because the model reasonably assumed the parameter was optional. Each failure triggered an average of 12 retry turns before the agent gave up, which is where the token bill compounds.

The generalisation the post extracts is stated plainly: "Tools for agents should adapt to the way LLMs naturally call them — coerce the list into a string, default the omitted parameter, absorb the unexpected argument." Concretely that means a JSON array in a stringly-typed field should be joined instead of rejected; a missing optional field should get a sensible default instead of a 400; a spurious extra argument should be dropped instead of throwing. This is the opposite of the "strict inputs, permissive outputs" Postel-adjacent posture most human-facing APIs adopt, and it is the direction the Anthropic and OpenAI tool-use docs have been quietly pushing for a while without spelling out the failure mode this concretely.

The one honest gap in the write-up is the missing before/after numbers on token spend or wait time after the seven fixes shipped — the post commits to the extrapolation but does not show the follow-up chart. For a team weighing this pattern, the actionable read is the diagnosis loop: OpenTelemetry on every tool call, retention long enough to see 12-turn retry loops, and a query surface that lets a non-specialist ask "which tool is bleeding tokens today?" without writing a Spark job.

### 🎯 Takeaway (Hợp)
If you ship internal MCP tools that an agent calls at scale, wrap them behind a gateway that emits per-call spans this week and pull a "top 10 failing tools by retry count" query before you build anything else; the seven-bug pattern here is almost certainly present in your own stack. Then rewrite the input validators to coerce and default instead of reject — treat the LLM's most natural call as the contract, not the OpenAPI spec.

### 💡 Example
```python
# Before: strict validator throws on the LLM's most natural call shape.
def get_issues(fields: str) -> list[dict]:
    return jira.search(fields=fields.split(","))   # KeyError / list.split() when
                                                   # the model passes a JSON array.

# After: absorb the shape the model produces, keep the human-facing contract too.
def get_issues(fields: str | list[str] | None = None) -> list[dict]:
    if fields is None:
        fields = DEFAULT_FIELDS                    # missing optional → sensible default
    if isinstance(fields, list):
        fields = ",".join(fields)                  # JSON array → CSV, do not reject
    return jira.search(fields=fields.split(","))
```

## 2. AWS IoT Greengrass Component SDK for Rust Lands With a Sub-0.5 MB Runtime for Edge AI

| Field | Value |

### 🔭 Overview (Tổng)
AWS shipped a Rust flavour of the AWS IoT Greengrass Component SDK, and Dhananjay Karanjkar, Sandeep Gawande and Sanjay Chaudhari's launch post backs it with a full edge-AI reference architecture that runs quantised ONNX inference locally and only calls a Bedrock AgentCore agent for the anomalies it cannot classify on its own. The numbers matter: less than 0.5 MB SDK footprint, cold start under 100 ms, roughly 22 MB peak resident set with a sample model, versus about 30 MB for the Python SDK alone before you have loaded any weights. For anyone shipping to gateways with 256 MB of RAM shared between the OS, Greengrass nucleus, and SCADA processes, the difference is what decides whether an edge-AI story is viable at all on this hardware class.

### 🔬 Details (Phân)
The reference pipeline is a pump-monitoring scenario across 2,000 remote gateways over intermittent cellular. The local model is a tiny 1D CNN with squeeze-and-excitation attention, quantised to ~23 KB and served via the `ort` crate statically linked into the component; it consumes a 60-second sliding window of four sensor channels (240 points) and returns four-class softmax probabilities in "less than 50 ms on ARM Cortex-A53" against a 200 ms per-inference budget. IPC to other Greengrass components rides Unix domain sockets rather than TCP, and startup verifies the model file's SHA-256 before load, on top of the Greengrass digest check the deployment already does. Offline behaviour is explicit: a bounded FIFO queue of 1,000 messages with drop-oldest overflow keeps escalations for the cloud agent when the network is down, and drains on reconnect.

The escalation tier is where the design gets interesting. When the local classifier is uncertain, the component publishes to Bedrock AgentCore running the Strands Agents framework with Claude Haiku 4.5 as the reasoning model; the agent has two tools — `query_history` for a seven-day DynamoDB baseline lookup and `publish_response` for MQTT reply back through IoT Core. The response envelope is a structured `{severity, probable_cause, recommended_action, supporting_evidence, confidence}` object, which is what makes it actionable at the gateway. The post publishes a cost model too: about $0.004 per escalation, $10–15/month for 10 devices doing 8–12 escalations per day, and a worst-case "stuck sensor" scenario at roughly $345/month — the last number is the one that tells you whether local classifier accuracy matters more than raw model quality for fleet economics.

The strategic frame the post does not spell out is the Python-vs-Rust dividing line for edge AI on Greengrass. The comparison table gives ~30 MB for the Python SDK and ~70–110 MB for a full Python + ONNX stack, versus roughly 35 MB for the Rust equivalent, so this is not a rewrite for its own sake — it opens a device class Python could not fit into. The trade-off is the usual Rust one: cross-compilation to `aarch64-unknown-linux-gnu` and `tokio` async plumbing instead of `pip install`. Sample code is at `aws-samples/sample-greengrass-rust-edge-ai-agent`, with a CDK stack for the cloud side.

### 🎯 Takeaway (Hợp)
If you have a fleet on 256 MB gateways where a Python Greengrass component would eat the memory budget before the model even loads, port your smallest AI component to the Rust SDK this sprint and measure resident set against the current Python component; the sub-0.5 MB runtime is the reason to bother. Do not skip the escalation cost model in the post — the worst-case stuck-sensor number is what should decide your local-versus-cloud threshold, not the average.

### 💡 Example
```rust
// Sketch of the edge classifier + escalation loop.
let model = OrtModel::load("model.onnx")?;                 // statically linked ort crate
let socket = GreengrassIpc::connect().await?;              // Unix domain socket IPC
let mut queue: BoundedQueue<Escalation> = BoundedQueue::new(1000);

loop {
    let window = sensor_window(Duration::from_secs(60)).await?;     // 240 points, 4 chans
    let scores = model.infer(&window)?;                             // < 50 ms on Cortex-A53
    let (label, conf) = argmax_with_confidence(&scores);

    publish_local_classification(&socket, label, conf).await?;

    if conf < ESCALATE_THRESHOLD {
        let msg = Escalation::new(label, conf, window.summary());
        match iot_publish("edge/pump/escalate", &msg).await {
            Ok(_)  => {},                                           // sent
            Err(_) => { queue.push_drop_oldest(msg); }              // offline: buffer
        }
    }
    if network_up().await { drain(&mut queue).await?; }             // drain on reconnect
}
```

### 🔭 Overview (Tổng)
Srujan Alase and Richard Tomlinson walked through how Databricks recommends actually operationalising Genie Ontology in a customer's stack, a piece that reads as the missing manual for the ontology work Databricks announced earlier this year. The framing sentence is "model the 'head' and let Genie Ontology infer the 'tail'" — deliberately curate the definitions that carry authority, then let the system pick up the long tail from tables, queries, dashboards and notebooks, ranked by Unity Catalog permissions and authority signals. For anyone weighing a semantic-layer investment on top of a lakehouse against a standalone tool like Cube or dbt Semantic Layer, this is Databricks' most explicit statement to date of what its opinionated path looks like.

### 🔬 Details (Phân)
The blueprint is six layers stacked. Layer 0 is a gold layer modelled around business processes with entity resolution collapsing duplicates into single golden records; the post is unusually direct that this is the layer without which nothing above works. Layer 1 is metadata enrichment — Unity Catalog table descriptions, column comments, PII and PHI tags, business-function tags — and the post points at the `dbxmetagen` accelerator to bootstrap the first pass instead of writing it by hand. Layer 2 is the semantic layer proper: explicit primary and foreign keys, Metric Views for governed measures and dimensions, and agent-facing metadata such as display names, synonyms and format patterns, organised into Domains and Pages. Layer 3 certifies trusted assets and deprecates stale ones so the ranking layer above can tell the two apart. Layer 4 wires in Unity Catalog access controls plus row-level security, column masking, attribute-based access and — new in the piece — Unity AI Gateway for model access controls, rate limits and safety guardrails. Layer 5 is a continuous evaluation loop with Genie Agent Benchmarks plus citation-driven feedback back into the appropriate layer.

The Genie Code capabilities the post highlights are the practical part. Metric Views can be created and maintained by natural-language instructions, Tableau or Power BI semantic models can be imported into Genie, and Pages can be drafted in bulk from the imported model rather than typed. External access is via MCP — the same protocol the day's other three items use — so a downstream agent authored in Claude Code, Copilot or Cursor can ground on the same ontology without a separate integration. The recommended adoption path is unusually restrained for a vendor post: pick one high-friction workflow such as a forecast call or a planning cycle, prove the ontology on that domain, then expand.

The honest caveat is that the piece is a design guide, not a bench-off. There are no comparative metrics against dbt Semantic Layer, LookML or Cube, and no numbers on how much of the "tail" Genie actually infers correctly for a representative shop. Treat the six layers as a checklist to reason against, not a promise.

### 🎯 Takeaway (Hợp)
If you are already on Unity Catalog and running Genie in preview, spend a day walking one recurring reconciliation workflow through the six layers before adding scope; the "one high-value domain" advice is where teams that skip it end up with a semantic layer that nobody trusts. If you are evaluating a semantic layer more broadly, read this as Databricks' committed shape — Metric Views plus Unity Catalog plus MCP is the whole answer, and the alternative is stitching those three from separate vendors.

### 💡 Example
```sql
-- Layer 2: a Metric View is the governed unit Genie grounds on.
CREATE OR REPLACE METRIC VIEW retail.gross_margin
  OVER retail.sales_gold
  DIMENSIONS (
    region                          AS "Region",
    date_trunc('month', order_date) AS "Month",
    product_category                AS "Category"
  )
  MEASURES (
    sum(revenue)              AS revenue      COMMENT 'Booked revenue, tax-exclusive',
    sum(revenue - cogs)       AS gross_margin COMMENT 'Revenue minus COGS',
    sum(revenue - cogs) / nullif(sum(revenue), 0) AS margin_pct
      COMMENT 'Gross margin ratio; expressed as a fraction'
  )
  WITH TAGS ('domain'='retail', 'certified'='true', 'owner'='finance-analytics');

-- Layer 4: grant Genie read access only through the governed view.
GRANT SELECT ON METRIC VIEW retail.gross_margin TO `genie-agent-svc`;
```

### 🔭 Overview (Tổng)
Alongside the Rust SDK release, NagaBharathi Challa, Graham Boone and Robert Schumann's post lays out a second Greengrass edge-AI pattern: deploy an MCP server as a Greengrass component so that a small language model can drive network diagnostics — ping, traceroute, SNMP walks, CLI commands — entirely at the edge, even while the site is disconnected from the cloud. The framing problem is the operational one: "engineers must be physically or remotely available to troubleshoot, creating delays when connectivity is unreliable", and the pattern replaces the on-call round trip with a local agent that already has the diagnostic playbook.

### 🔬 Details (Phân)
The architecture is three Greengrass components. An MCP server exposes the diagnostic toolset over the stdio transport as local, standardised tool calls. An edge ML component receives the intent, picks the right tool sequence, and interprets responses. An orchestration component — built on the Strands Agents SDK, the same framework the Rust-SDK post uses for its cloud tier — coordinates the workflow, holds context and persists results locally. Diagnostic results buffer through the Greengrass stream manager with a 256 MB default per-stream cap, and sync back to the cloud automatically when connectivity returns; unresolved sessions log to DynamoDB for follow-up. The post's headline claim — "you gain autonomous diagnostic capabilities that operate independently during disconnected periods" — is the differentiator against a cloud-only MCP setup where every tool call needs a round trip.

The pattern is more general than the network use case the post walks through. Any operator playbook that runs a scripted sequence of read-only diagnostics before escalating to a human — HVAC controller health, cellular modem signal profiling, PLC status sweeps — fits the same architecture, and the MCP standard means the tools written for one deployment are reusable across sites without rewriting the agent. What the post does not explicitly cover is which small language model runs at the edge, and there is no size or latency benchmark for the on-device inference; that is the piece to nail down before you commit to a hardware class. It also does not benchmark against the alternative of shipping a hand-written diagnostic script — the sales pitch is flexibility of tool composition, not raw performance.

Read the two AWS IoT posts together and the picture is clear: MCP-as-transport is now the intended way to hand tools to on-device AI on Greengrass, whether the runtime is Python-based (this piece) or Rust-based (item 2). The pattern is the same as Databricks and Google are pushing on the DE side of today's digest, just landed on a device that has a router next to it instead of a warehouse under it.

### 🎯 Takeaway (Hợp)
If you own a fleet with a diagnostic playbook engineers run repeatedly and connectivity is anything less than always-on, spend an afternoon translating one playbook into MCP tools and wire up this pattern on a test gateway; the offline diagnostic capability is the piece that pays for itself the first time a site is down. Pin down the on-device model choice before piloting broadly — the post is silent on it, and it will dominate your BOM and your latency numbers.

### 🔭 Overview (Tổng)
Kalyan Janaki and Aneesh Varghese's post lands the Apache Spark Troubleshooting Agent for Amazon EMR, which registers as an MCP server inside an AWS DevOps Agent space so the agent can reach into artifacts the standard AWS APIs cannot — the Spark History Server event log, executor Python worker memory, the line of code that allocated too much. For teams that already respond to `FailedJobs` CloudWatch alarms by SSHing into a driver to unpack a stack trace, this is the pattern that closes the loop between the alarm and the root cause without a human context-switch.

### 🔬 Details (Phân)
Setup is standard AWS DevOps Agent plumbing: create an agent space in region (us-east-1 in the walkthrough), stand up a PrivateLink connection into the VPC where the MCP endpoint lives at `sagemaker-unified-studio-mcp.us-east-1.api.aws`, and connect the `spark-troubleshooting` server so the agent gains two tools — `analyze_spark_workload` and `analyze_spark_history_server_endpoint`. Traffic is a SigV4-signed MCP call over PrivateLink, so it never leaves AWS's network. A CloudWatch alarm on the `AWS/EMRServerless` namespace `FailedJobs` metric fires the agent, which pulls alarm context via native APIs, then invokes the MCP tools to walk the event log and executor state.

The worked example is worth reading because it shows what an agent produces on a real failure. For a deliberately broken PySpark job, the agent surfaced three compounding causes: an `expand_event` function on line 23 that amplified each input row 11×, a `repartition(1)` that funnelled the amplified data into a single partition on one executor, and a `collect()` on line 31 that pulled the whole thing back to the driver. That is not just a stack trace — it is the interaction between three lines a human debugger would normally chase across three tabs. The pattern generalises to any framework where the failure mode lives across multiple runtime views (Spark, Flink, Ray), provided the MCP server exposes enough of the runtime state.

The competitive frame is Datadog's LLM-observability plus its Spark integration, which does similar surfacing but as a monitoring surface rather than an agent tool. This release positions the MCP surface as the more general answer — the same agent space can carry a network-diagnostics MCP server, a Spark server, an OpenSearch server (see the sibling post today on Agent Health) and rehearse a whole runbook without switching consoles. The scaffolding is at `aws-samples/sample-aws-data-processing-and-analytics`, including the demo failing job.

### 🎯 Takeaway (Hợp)
If you run EMR Serverless with a `FailedJobs` alarm that already pages a human, wire this MCP server in behind the alarm this week and let the agent produce the first-pass root cause before the engineer opens the ticket; the three-cause example is the kind of triage that saves ten minutes every time it lands. Do not skip the PrivateLink piece — the security review is easier when the trace flow never leaves your VPC.

### 💡 Example
```
# Illustrative CLI: register the Spark troubleshooting MCP server in your agent space.
aws devops-agent register-mcp-server \
    --agent-space-name prod-spark-space \
    --server-name spark-troubleshooting \
    --endpoint-url https://sagemaker-unified-studio-mcp.us-east-1.api.aws \
    --tools analyze_spark_workload,analyze_spark_history_server_endpoint \
    --connection-type private-link \
    --vpc-endpoint-id vpce-0abc123def456

# CloudWatch alarm target: agent invocation on FailedJobs > 0
aws cloudwatch put-metric-alarm \
    --alarm-name emr-failed-jobs \
    --namespace AWS/EMRServerless --metric-name FailedJobs \
    --statistic Sum --period 60 --evaluation-periods 1 --threshold 0 \
    --comparison-operator GreaterThanThreshold \
    --alarm-actions arn:aws:devops-agent:...:agent-space/prod-spark-space
```
