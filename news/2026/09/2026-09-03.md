### 🔭 Overview (Tổng)
The DuckDB team cut the v2.0-cyanoptera branch off main, declared feature freeze, and asked the community to start hammering the alpha before a projected release in the second half of October. The headline change under the hood is a jump of the Quack wire protocol from 0.x to 1.0, which the team frames as higher throughput in both directions between server and client plus improved compatibility across language bindings. For a project whose install base has spread across notebooks, edge devices and embedded pipelines faster than most database projects manage in a decade, a major-version bump is the moment shops that care about long-term ABI stability need to pay attention.

### 🔬 Details (Phân)
The announcement is deliberately thin on new-feature marketing and heavy on installation and validation instructions. On Linux and macOS the alpha is one line — `curl https://install.duckdb.org | DUCKDB_VERSION=alpha bash` — followed by `~/.duckdb/cli/latest/duckdb -c "SELECT version() AS version;"` to confirm the current CLI at `v2.0.0-alpha39998`. Python users can pull it with `pip install duckdb --pre --upgrade`, which currently resolves to `1.6.0.dev379`. The four core extensions — `httpfs`, `ducklake`, `iceberg` and `spatial` — have alpha builds available on the same channel; the team explicitly wants extension authors to test their code against the new ABI before the tag ships.

The interesting piece is the Quack 1.0 bump. Quack is DuckDB's client-server protocol, used by the Python client, JDBC driver, and increasingly by third-party tools that want to talk to a DuckDB server without going through the C API. Moving to 1.0 is the team's signal that the wire format is now a supported surface rather than an implementation detail, which matters for anyone building on top of `duckdb-jdbc`, `duckdb-node`, or the Rust client — and for shops that expose DuckDB behind a network endpoint via the community httpserver extension. The announcement is quiet on breaking API changes, deprecations, or migration steps, so treat the alpha the way the team is asking you to: as a test target, not a preview of the change log.

The context is the DuckLabs-to-AWS deal announced a week earlier, which keeps the project open source but changes the sponsorship shape. The cyanoptera release is the first tag pinned to that new arrangement and, taken with the Quack protocol move, reads like the team stabilising the interface surface just as the corporate perimeter changes. Extension maintainers and driver authors — Motherduck, dbt-duckdb, `sqlmesh`, the Rust `duckdb-rs` crate — are the audience most exposed to the ABI, and the six-to-eight-week alpha window is the whole runway they get.

### 🎯 Takeaway (Hợp)
If you ship anything that links DuckDB as a library or speaks Quack over the wire, install the alpha this week and run your test suite plus a smoke test of your largest analytical query against it — the six-week window is short and the team is explicitly asking for regressions, not opinions. If you only use DuckDB inside Python notebooks, wait for a later alpha; the interesting-for-you features will land in the CHANGELOG closer to the tag.

## 2. Trino 475 on Amazon EMR 7.11 Reads S3 Tables Through the Iceberg REST Catalog With SigV4

| Field | Value |
|---|---|
| 📅 Date | 02/09/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `trino-emr` · `s3-tables` · `iceberg-rest` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
AWS documented a path for Trino running on EMR to read and write Amazon S3 Tables directly through the S3 Tables Iceberg REST endpoint, without a Glue Data Catalog intermediary. The requirement matrix is specific: Trino 475 or newer, bundled inside EMR 7.11 or newer, connected to `https://s3tables.<region>.amazonaws.com/iceberg` with SigV4 signing. For teams that adopted S3 Tables when it launched but had been forced to route Trino queries through Glue as an Iceberg catalogue, this closes the last leg — the REST protocol is now the shared surface for both Trino and Spark against the same physical warehouse.

### 🔬 Details (Phân)
The whole integration lives in one file at `/etc/trino/conf/catalog/s3tables_irc.properties` and a matching IAM trust policy. Five settings must be exact for it to work: `iceberg.rest-catalog.sigv4-enabled=true`, `iceberg.rest-catalog.signing-name=s3tables`, `iceberg.rest-catalog.view-endpoints-enabled=false`, `fs.hadoop.enabled=false`, and `fs.native-s3.enabled=true`. The Iceberg REST warehouse is the S3 Tables bucket ARN, not an S3 path, and the catalogue URL is region-scoped. The EMR service role gets an assume-role trust from both the EMR service principal and the EC2 instance profile so that Trino workers can obtain S3 Tables credentials without a per-user token.

The functional consequence is that `trino-cli --catalog s3tables_irc` gives standard SQL over the table — `CREATE NAMESPACE`, `CREATE TABLE ... USING iceberg PARTITIONED BY (...)`, `INSERT`, `MERGE`, `SELECT`, `SHOW TABLES`. Table maintenance — compaction, snapshot expiration, orphan file cleanup — stays inside S3 Tables' managed layer, so Trino does not have to run its own housekeeping jobs against these buckets. That is the actual reason to bother with this configuration over a Glue-backed Iceberg catalogue: the operations that historically had teams writing their own periodic maintenance Spark jobs are handled at the storage tier.

The strategic frame is that the S3 Tables REST endpoint is quietly becoming a first-class Iceberg catalogue peer, on the same footing as Nessie or Polaris. Trino 475 is doing the same job here that Iceberg-native Spark 3.5 did a year ago; the pattern will land in Flink 2.3 and in the SageMaker Lakehouse materialized-view piece below through the same door. The version pinning is the part that catches teams out — EMR 7.10 shipped Trino 471, which does not carry the SigV4 catalog signer, and there is no supported backport. Plan the EMR bump before writing the catalog properties file.

### 🎯 Takeaway (Hợp)
If you already have S3 Tables and were routing Trino through Glue as an Iceberg catalogue, promote one workload to the REST endpoint on a new EMR 7.11 cluster this sprint and compare query planning time and maintenance-job cost against the old path; the operational lift, not the query performance, is where this pays back. Do not skip the SigV4 settings — the connector will silently fall back to unauthenticated requests and every table access will 403, which is the failure mode that eats an afternoon.

### 💡 Example
```properties
# /etc/trino/conf/catalog/s3tables_irc.properties  --  Trino 475 on EMR 7.11+
connector.name=iceberg
iceberg.catalog.type=rest
iceberg.rest-catalog.uri=https://s3tables.us-east-1.amazonaws.com/iceberg
iceberg.rest-catalog.warehouse=arn:aws:s3tables:us-east-1:123456789012:bucket/analytics
iceberg.rest-catalog.sigv4-enabled=true
iceberg.rest-catalog.signing-name=s3tables
iceberg.rest-catalog.view-endpoints-enabled=false
fs.hadoop.enabled=false
fs.native-s3.enabled=true
s3.region=us-east-1
s3.iam-role=arn:aws:iam::123456789012:role/service-role/EMR_S3Tables_Role
```

## 3. Iceberg Materialized Views on SageMaker Lakehouse Collapse the Medallion Stack Into SQL

| Field | Value |
|---|---|
| 📅 Date | 02/09/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `iceberg-mv` · `sagemaker-lakehouse` · `incremental-refresh` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
AWS added Iceberg materialized views as a first-class construct across Athena Spark, AWS Glue 5.1 and Amazon EMR 7.12, and a companion tutorial reframes the medallion architecture as three SQL definitions on top of one bronze table rather than three ETL jobs and an orchestrator. Each layer — silver, gold, and gold-on-gold — is a `CREATE MATERIALIZED VIEW … SCHEDULE REFRESH EVERY 1 HOUR AS SELECT …` statement whose incremental refresh reads Iceberg position-delete and equality-delete files to touch only the rows that changed since the last snapshot. For teams currently gluing together dbt models, Airflow DAGs and CDC watermarks to keep a warehouse fresh, this collapses several moving parts into one.

### 🔬 Details (Phân)
The SQL surface is small and explicit. A silver view over a bronze trips table looks like `CREATE MATERIALIZED VIEW mv_trips_silver COMMENT '…' SCHEDULE REFRESH EVERY 1 DAY AS SELECT trip_id, driver_id, CAST(trip_start_time AS TIMESTAMP) AS ts, CASE WHEN distance_miles > 0 THEN total_amount / distance_miles ELSE 0 END AS revenue_per_mile FROM trips_bronze WHERE trip_id IS NOT NULL`. Gold views select from the silver view directly and refresh on their own schedule, so `mv_city_daily_metrics` and `mv_vehicle_performance` can hang off the same silver definition and each pull only their own delta. The mechanism the AWS Glue runtime uses is Iceberg's own change-tracking — position-delete and equality-delete files identify the rows that moved since the last successful refresh, and only those rows re-enter the view. A `REFRESH MATERIALIZED VIEW <name>` action forces an immediate refresh, and `REFRESH … FULL` is required whenever the underlying table has deleted rows, because incremental refresh cannot see removals.

The limits are worth reading before adopting this in earnest. Minimum refresh cadence is one hour, so this is not a substitute for streaming when latency-sensitive dashboards need sub-minute freshness. Cascading refresh is not automatic — a change in the silver view does not trigger the gold view; each layer runs on its own schedule and reads whatever snapshot is current when it wakes. Schema evolution needs a view recreate; a new column added upstream will not appear until you drop and re-`CREATE` the view. Not every SQL construct is supported — UDFs and some advanced expressions are excluded — and this is an AWS extension that will not carry over to an open-source Iceberg deployment on a different runtime. Refresh cost is billed as managed Spark at USD $0.44 per DPU-hour with a one-minute minimum, which is meaningful when you have hundreds of small hourly views.

The comparison to hold in mind is `dbt-core` running on a Databricks or Snowflake warehouse. That path already gives you incremental models keyed on a watermark and a DAG-driven ordering. The Iceberg MV path trades the DAG orchestrator for cadence-based refresh and the incremental key for Iceberg's delete-file bookkeeping, and it keeps the tables as open Iceberg tables that Trino or Spark elsewhere can read. That is the reason the SageMaker-Lakehouse framing appears alongside the Trino piece above: the S3 Tables REST catalog plus incremental MVs plus a Trino query engine is the same warehouse from two different query surfaces.

### 🎯 Takeaway (Hợp)
If your medallion stack today is dbt plus Airflow plus a CDC watermark column, port one silver-gold pair onto Iceberg MVs on a copy of the data and compare refresh time, DPU-hour cost and freshness against the current pipeline; the interesting question is not whether it works, but whether the DPU-hour bill for cadence-based refresh beats the DAG-based path at your table count. Do not use this where the SLA is sub-hourly — the one-hour floor is a hard constraint, not a limitation the team will lift soon.

### 💡 Example
```sql
-- Silver: incremental hourly view over the bronze table.
CREATE MATERIALIZED VIEW analytics.mv_trips_silver
COMMENT 'Cleaned trip data with typed timestamps and derived columns'
SCHEDULE REFRESH EVERY 1 HOUR
AS
SELECT
  trip_id, driver_id, city, vehicle_type,
  CAST(trip_start_time AS TIMESTAMP) AS trip_start_ts,
  CASE WHEN distance_miles > 0 THEN total_amount / distance_miles ELSE 0 END
    AS revenue_per_mile
FROM analytics.trips_bronze
WHERE trip_id IS NOT NULL;

-- Gold: aggregate on top of the silver view; own schedule, own delta.
CREATE MATERIALIZED VIEW analytics.mv_city_daily_metrics
SCHEDULE REFRESH EVERY 1 DAY
AS
SELECT city, date_trunc('day', trip_start_ts) AS d,
       count(*) AS trips, avg(revenue_per_mile) AS avg_rpm
FROM analytics.mv_trips_silver
GROUP BY city, date_trunc('day', trip_start_ts);

-- Deletes upstream: incremental refresh cannot see removals; force a FULL.
REFRESH MATERIALIZED VIEW analytics.mv_trips_silver FULL;
```

### 🔭 Overview (Tổng)
Home Assistant 2026.9 replaces the ageing Modbus foundation with a new `modbus-connection` library built on top of the modern typed `tmodbus` package, so integrations for Fronius, Sofar Inverter Modbus and Flexit can be added from the UI by picking the device instead of writing register maps by hand. The other headline is a Soniox-powered speech-to-text engine on Home Assistant Cloud, explicitly targeting accents, background noise and non-English recognition without logging or training on user audio. For an IoT platform where Modbus solar inverters and voice control are two of the most-installed integrations, both changes touch the paths users hit every day.

### 🔬 Details (Phân)
The Modbus modernisation is the load-bearing change. The old Modbus integration in Home Assistant required each user to build YAML register maps by hand, with function codes, byte order and scaling factors all typed out per device; a wrong register meant a silent zero. With `modbus-connection` under the hood, the vendor-specific integrations own that map and expose only the device selection in the UI. Fronius, Sofar Inverter Modbus and Flexit are the first three to migrate; the shape of the library — typed data classes on top of `tmodbus` — is the pattern subsequent Modbus integrations will follow. The Soniox integration lands as a Labs feature for Home Assistant Cloud subscribers; the STT service runs in Nabu Casa's cloud with the privacy contract that audio is not stored or used for training.

Two Matter-side changes matter for anyone running a mixed-transport smart home. A "Show map" button on the Matter integration renders the Matter Server's network topology inside Home Assistant, showing Thread versus Wi-Fi transport, border router status and signal strength direction — the first time this level of visibility has been exposed without dropping into `chip-tool`. The Security dashboard picked up active alerts (configurable Alert or Warning severity) and favourite pinning as first-class UI concepts, and the Activity/History view gained a unified Sources panel that filters by floor, area, device, entity, or domain and shows the full causality chain for a state change with a link to the underlying trace.

The breaking-change list is longer than usual and hits automations directly. LLM tool names are now domain-prefixed as `homeassistant__GetLiveContext`, so any custom prompt or automation referring to the old bare tool name will break; KNX exposes no longer transmit initial values unless the integration is configured with `send_on_init: true`; persistent notification updates now fire `update_type: updated` instead of the previous `added`, which will silently break any automation that keyed on `added` to detect edits; the VLC integration is removed; the Vacuum `battery_level` property is gone (moved to the sensor entity); update install/skip actions and Z-Wave JS lock management now require administrator accounts; and UniFi Protect now requires the controller at 7.2.105 or newer. Thirteen new integrations arrived — Besen EV chargers over BLE, Hot Spring spa control, ISEO Argo BLE locks, LibreNMS, Samsung TV over RS-232 via ExLink among them — and Midea gained sixteen virtual brand stubs to consolidate the fragmented white-label device landscape.

### 🎯 Takeaway (Hợp)
If you run Home Assistant with hand-built Modbus YAML for a Fronius, Sofar or Flexit device, migrate to the vendor integration this weekend and delete the YAML; the UI path is the one the project will maintain going forward, and future Modbus additions will land there first. Read the breaking-changes list before upgrading — the LLM tool-name prefix and the persistent-notification event-type shift are the two that quietly break automations without any log line pointing at the release.

### 🔭 Overview (Tổng)
Arduino published a case study in which Forgis, an industrial-automation partner, runs a multimodal foundation model entirely on-device on the new Arduino UNO Q to translate spoken operator commands into control signals for a robotic arm, with a claimed end-to-end latency of 20 ms. The model consumes camera feed from the arm, the robot's CAD model and the PLC's I/O signals in one context and emits structured motion instructions. For anyone watching the "edge AI on a microcontroller-class board" line move over the last two years, this is the first Arduino post that puts a foundation model rather than a small CNN inside the control loop of a physical actuator.

### 🔬 Details (Phân)
The hardware anchor is the Arduino UNO Q, positioned by Arduino as a Pro-class board capable of running foundation-model inference locally rather than shipping frames to a cloud endpoint. In this deployment the UNO Q sits between a USB-connected camera watching the arm's workspace and the arm's own controller; the 20 ms figure is the round trip from voice input through inference to motion command, which is inside the reaction budget for hand-guided pick-and-place tasks. Forgis's model is described as multimodal — text prompts, video frames, CAD geometry and PLC I/O values — and continually learns from production runs, which the post frames as the differentiator against a fixed-vocabulary industrial voice-control HMI.

The strategic frame is where the piece is honest by omission. The parameter count, quantisation regime, inference framework (whether it is ONNX Runtime, ExecuTorch or something bespoke), and the memory footprint on the UNO Q are all absent from the announcement. So is any benchmark against the traditional PLC-plus-HMI baseline, which is the comparison operators actually make when they weigh replacing a proven touchscreen with a voice interface. What the post does establish is a template: an edge-class Arduino board running a foundation model as the reasoning layer, taking sensor inputs the traditional PLC already emits, and outputting motion commands the arm's existing motion planner accepts. That template is deployable on top of any brownfield PLC installation without ripping out the automation controller.

The wider industry read is that Arduino is positioning UNO Q as the entry-price rung of the same edge-agent ladder AWS is climbing with the Rust Greengrass SDK announced two days ago and Espressif is climbing with its ESP-IDF work on the ESP32-S31. Three vendors, three microcontroller classes, one converging pattern: a small on-device model that handles the common case, escalates the unusual case, and stays inside a millisecond-scale control loop. The safety and certification questions — how a voice-driven agent gets past a factory-floor risk assessment when the operator is inside the robot's working envelope — are the ones the post does not answer, and they will decide whether the pattern generalises past demos.

### 🎯 Takeaway (Hợp)
If you are prototyping edge inference for an industrial control loop, put an Arduino UNO Q against the ESP32-S31 and a Raspberry Pi 5 on the same workload — inference latency, watts, and BOM cost — before committing to a hardware class; the announcement is a demo, not a benchmark, and the platform choice will lock in for the product's lifetime. Be sceptical of the 20 ms round-trip until you can reproduce it with your own workload — the number is quoted without hardware configuration or measurement methodology.
