### 🔭 Overview (Tổng)
Arduino tagged ArduinoCore-Zephyr 1.0.0, the first non-beta release of the project it started 18 months ago to move its board catalogue off the legacy AVR core and mbed OS onto Zephyr as a shared RTOS foundation. The 1.0.0 tag pulls the base kernel up to Zephyr 4.4.1, adds first-class support for the newly launched VENTUNO Q board with its STM32H5 real-time coprocessor, and turns on the camera stack for Nicla Vision so on-device image classification and object detection sketches run without an external toolchain. For anyone building embedded firmware on Arduino Pro boards, this is the release that makes Zephyr — not the classic Arduino core — the supported path forward.

### 🔬 Details (Phân)
The supported hardware matrix is now twelve boards: Arduino UNO Q, VENTUNO Q, Portenta H7, Portenta C33, Opta microPLC, GIGA R1 WiFi, Nano Matter, Nano RP2040 Connect, Nano 33 BLE, Nicla Sense ME, Nicla Vision, and the Nano Matter announced earlier in the year. VENTUNO Q is the notable addition: the Qualcomm Dragonwing IQ-8275 handles high-level AI compute while the STM32H5F5 sits on the same board as a deterministic real-time controller, and the Zephyr port targets that STM32 side. Nicla Vision's camera driver moves from an out-of-tree patch into the mainline core, so the standard Arduino IDE workflow now produces a sketch that can grab a frame with `Camera.grabFrame()` and hand it to a TFLite Micro or ExecuTorch model without a vendor SDK detour.

Under the hood the changelog reads more like a maintenance release than a headline one — CI improvements, serial pin remaps, loader fixes, sketch-size calculation corrections, expanded PDM and PWM support, and OTA update file generation across variants. That is by design: the 0.90.0 release six weeks ago was already tagged as stable, and 1.0.0 is Arduino's signal that the ABI and folder layout will not shift under third-party libraries any more. Migration from a 0.9x sketch is a rebuild, not a rewrite; the breaking risk is concentrated in libraries that reach into Zephyr internals directly, which will now compile against the 4.4.1 headers instead of the older 4.3.x base.

The strategic frame is that Arduino has quietly finished the transition from a small-8-bit-MCU story to a Zephyr-based Pro-class portfolio. VENTUNO Q at USD 299 with a Dragonwing IQ-8275 is priced against a Raspberry Pi 5 plus a companion MCU rather than against a classic Nano, and running Zephyr on the STM32 side gives it the same real-time API surface as the Opta microPLC on a factory bench. For firmware teams that have been juggling one toolchain per Arduino product line — mbed for Portenta, Nordic SDK for Nano BLE, ESP-IDF for Nano ESP32 — the 1.0.0 release is the invitation to consolidate on Zephyr west workspaces, one HAL, one CI pipeline.

### 🎯 Takeaway (Hợp)
If you ship an Arduino Pro board in production, plan a 1.0.0 rebuild this sprint against your existing sketch and library stack — the ABI is now the one Arduino will maintain, and staying on 0.9x deprives you of the Nicla Vision camera path and any future VENTUNO Q integration work. Nếu bạn đang cân nhắc VENTUNO Q cho một dự án physical AI, 1.0.0 chính là mốc để bắt đầu; trước đó firmware side chưa có Zephyr chính thống.

## 2. Next-Generation Amazon OpenSearch Serverless Replaces Route 53 Profiles With PrivateLink DNS

| Field | Value |
|---|---|

### 🔭 Overview (Tổng)
AWS documented the connectivity model for the next-generation Amazon OpenSearch Serverless, which drops the previous Route 53 Profile arrangement in favour of standard AWS PrivateLink interface endpoints with native private DNS. The service now exposes two endpoint shapes — a per-collection hostname `<collectionId>.aoss.<region>.on.aws` and a per-account regional hostname `<accountId>.aoss.<region>.on.aws` — reachable through the interface endpoint service `com.amazonaws.<region>.aoss-data`. The post catalogues nine concrete network patterns, from a single VPC through cross-account hubs to three cross-Region strategies, and is the reference platform teams will point at when the security review asks how the collection reaches its callers.

### 🔬 Details (Phân)
The mechanical change is that a consumer VPC now creates one PrivateLink interface endpoint with `--private-dns-enabled` and the AOSS-region hostname resolves locally on that VPC, with no custom hosted zone required. Every collection's hostname carries its region identifier as a suffix, so a workload in `us-east-1` and a workload in `eu-west-1` resolve to the correct endpoint independently without a central Route 53 fabric. Network policies gate which VPC endpoints can reach a collection; data-access policies still govern which IAM principal can query it. The two policy families continue to work in tandem and both must permit the caller.

The nine patterns walk from a single VPC private access at the trivial end through multi-VPC same-account, on-premises via Transit Gateway or Direct Connect, cross-account with an endpoint per consumer, a centralised shared endpoint via Route 53 Profiles for accounts that want a single point of DNS control, a distributed multi-business-unit spoke design, a multi-business-unit variant with on-premises reach, and three cross-Region shapes — application-level dual-write, an OpenSearch Ingestion pipeline that registers endpoints automatically, and S3 cross-region replication combined with re-ingestion. Pattern 5 is the only one that still requires the operator to run a Route 53 Profile; the other eight resolve inside the VPC with no additional DNS infrastructure.

The strategic frame is that the previous generation's DNS complexity was a source of quiet operational cost — every consumer VPC needed an endpoint plus a manually built private hosted zone, and adding a new business unit meant a Route 53 Profile migration. By moving to standard PrivateLink DNS, OpenSearch Serverless has aligned with the way the rest of the AWS estate — S3 Interface, Kinesis, Lambda — has exposed connectivity for years. The trade-off is that customers on the previous model do not get an automatic migration; the launch is limited to new next-generation collections, and existing serverless collections continue to require the Route 53 Profile design until the team publishes a migration path.

### 🎯 Takeaway (Hợp)
If you are provisioning a new OpenSearch Serverless collection this month, take the next-generation path and skip the Route 53 Profile setup — the interface-endpoint DNS is one CloudFormation resource, not a private hosted zone plus a profile plus an association. If you already run classic serverless collections, wait for the migration guidance rather than trying to retrofit the new hostname shape onto an existing collection.

### 💡 Example
```bash
# Provision the PrivateLink interface endpoint that fronts an AOSS-region hostname.
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-abc123 \
  --service-name com.amazonaws.us-east-1.aoss-data \
  --vpc-endpoint-type Interface \
  --subnet-ids subnet-111 subnet-222 \
  --security-group-ids sg-xxx \
  --private-dns-enabled

# From an EC2 in that VPC, resolve the per-collection hostname locally.
dig +short abc123def.aoss.us-east-1.on.aws
# 10.0.12.34
# 10.0.13.56
```

## 3. Moovit Cuts 33% of Analytics Cost by Splitting Redshift Across a Multi-Engine Lakehouse

### 🔭 Overview (Tổng)
Moovit published, through the AWS Big Data blog, a walkthrough of a multi-quarter migration from a single Amazon Redshift cluster to a multi-engine lakehouse: BI serving stays on provisioned Redshift, ad-hoc and data-science exploration moves to Redshift Serverless, and heavy aggregation ETL is offloaded to Amazon EMR with Spark SQL. The headline numbers are a 33% overall analytics cost reduction and a 50% cut in provisioned Redshift capacity, with the flagship aggregation job dropping from four hours to about ten minutes on EMR. It is one of the more concrete case studies out this quarter of the pattern the industry has been describing for two years — that mixed engines against one storage layer, with workload isolation, beats a monolithic warehouse for both cost and elasticity.

### 🔬 Details (Phân)
The methodology has three explicit phases. First, measurement: Moovit built an automated query classifier that tagged each query by workload type, tracking CPU time, execution duration and queue metrics per class so the migration decisions were driven by workload evidence rather than intuition. Second, cleanup: obsolete processes were removed before any migration, which alone accounted for a 7% unnecessary CPU load and reset the baseline against which the migration was measured. Third, migration: heavy aggregation pipelines moved to EMR only after a proof-of-concept that had to hit three explicit success criteria — 40% runtime reduction on the transformation workload, more than 30% Redshift cost reduction, and exact data-parity between the Redshift and Spark implementations.

The engineering details are the interesting part. The team quotes 100 executors dropped to under 50 through executor tuning; excessive data shuffles were eliminated by query rewrites; SQL-dialect differences between Redshift and Spark were resolved case by case. Validation was defensive: row counts, distinct-entity checks, metric parity, time-series consistency and row-level spot checks all had to line up before production cutover. Redshift Serverless carries the ad-hoc and data-science layer, so bursty user-driven queries no longer contend with the aggregation workload for cluster capacity, which is where the 50% provisioned-cluster reduction comes from.

The pattern this case study demonstrates is neither novel nor Moovit-specific: it is what Databricks calls a lakehouse, what AWS calls the Iceberg-on-S3-plus-many-engines model, and what Google Cloud is now shipping as BigLake plus BigQuery Serverless. The value in this write-up is the numeric baseline and the honesty about the tuning cost — dropping executors, rewriting SQL for shuffle behaviour, and running weeks of parity checks are the actual bill of work. Any team pointing at this post as justification for their own migration should budget the same engineering-quarter of comparison and tuning, not just the platform-side spend delta.

### 🎯 Takeaway (Hợp)
If your Redshift bill is dominated by a small number of long aggregation jobs while your interactive query load is bursty, port the largest aggregation onto EMR Spark SQL against the same source tables on a copy of the data, and require the same three-criterion POC gate — runtime, cost, data parity — before committing. The 33% figure is a plausible target for a similar workload shape; if your workload mix skews interactive rather than batch, the payback is smaller and the migration risk is larger.

### 💡 Example
```python
# EMR Spark SQL: the aggregation pattern Moovit offloaded from Redshift.
# Focus on eliminating shuffle by pre-aggregating, then joining, and by tuning executors.

spark.conf.set("spark.sql.shuffle.partitions", "400")
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")

df_trips_daily = spark.sql("""
  SELECT city_id, date_trunc('day', trip_start_ts) AS d,
         count(*)          AS trips,
         sum(distance_km)  AS km,
         sum(fare_amount)  AS revenue
  FROM   analytics.trips_bronze
  WHERE  trip_start_ts >= current_date - INTERVAL 1 DAY
  GROUP  BY city_id, date_trunc('day', trip_start_ts)
""")
df_trips_daily.write.mode("overwrite").saveAsTable("analytics.trips_daily")
```

### 🔭 Overview (Tổng)
Databricks expanded Genie Agents along four axes: an Agent Mode with multi-step reasoning, a public API that streams responses over Server-Sent Events, unstructured-data analysis that reads PDFs, slide decks, documents and images from Unity Catalog volumes, and shared chats that stay dynamically linked to the underlying agent. Genie Code, the authoring surface for these agents, picked up automated baseline generation, failure diagnosis and production management tooling. For teams that had been evaluating Genie as a natural-language-to-SQL front end, the update turns it into a broader agent runtime whose scope now overlaps with what a bespoke LangChain or LlamaIndex stack would provide.

### 🔬 Details (Phân)
Agent Mode is the load-bearing change. Where the earlier Genie surface answered a single question with a single SQL query, Agent Mode plans multi-step tasks — reason about the user question, pull structured facts from the warehouse, cross-reference against attached PDFs or slide decks, and compose an answer with citations. Each Genie Agent can now have up to ten Unity Catalog volumes attached; the search index over those volumes uses content-based retrieval, and permissions inherit from Unity Catalog so users only see files they already have access to. The API surface streams intermediate reasoning and results over SSE, which matches how contemporary agent frameworks expect to consume tokens and tool calls; a companion endpoint retrieves the full conversation object for audit.

The Chat Sharing behaviour is different from a static chat export. A shared conversation stays live: when the underlying data changes or the agent is updated, the shared chat reflects the current view rather than the snapshot the sharer saw. That has both operational and governance consequences — a shared chat cannot be treated as a snapshot for compliance, and any downstream automation that relies on the exact numbers a chat contained must re-query. The example prompts Databricks published — "Which regions have the most churned customers, and what are the main themes in their exit surveys?", "Compare the differences between these two SOWs", "What's the deadline to submit gym reimbursements?" — deliberately mix structured warehouse data, unstructured documents and internal policy content, which is the workload Genie Agents are being repositioned to serve.

The competitive frame is Snowflake Cortex Agents and Google's Gemini for BigQuery. All three vendors are converging on the same shape: an agent runtime on top of the warehouse that can reason across tables and files, exposes a streaming API, and inherits enterprise ACLs from the storage layer. Genie's specific advantages here are the tight Unity Catalog binding — the same object permissions govern SQL access and file retrieval — and the up-to-ten-volumes ceiling, which is realistic for a departmental agent but low for an enterprise-wide knowledge base. The trade-off is that Genie Agents remain a Databricks-workspace construct; you cannot host the same agent runtime outside Databricks the way you can host a LangChain graph anywhere.

### 🎯 Takeaway (Hợp)
If you have a Databricks workspace with Unity Catalog and were previously evaluating a separate RAG stack for internal document Q&A, run a two-week POC with a Genie Agent against one representative volume of PDFs plus one warehouse fact table, and measure answer quality and end-to-end latency against your incumbent option. If your document corpus needs to span more than ten volumes or if you must expose the agent outside Databricks, treat Genie Agents as a workspace-scoped complement rather than a replacement.

            evt = json.loads(line[6:])
            if evt.get("type") == "reasoning":
                print("...", evt["step"])
            elif evt.get("type") == "answer":
                print(evt["text"])

## 5. Arduino UNO R4 Minima Drives an MLX90640 Handheld Thermal Camera at 32x24

### 🔭 Overview (Tổng)
Arduino published a walk-through of a DIY handheld thermal camera built around an Arduino UNO R4 Minima, a Seeed Studio MLX90640 IR array, and a DFRobot Fermion capacitive-touch TFT, packaged in a FreeCAD-designed 3D-printed enclosure. The article is a project post rather than a release, but the choice of components is the interesting content — the MLX90640 delivers a 32x24 raw thermal grid over I2C at up to 32 Hz, and pairing it with the R4 Minima's Renesas RA4M1 gives enough RAM to interpolate the frame to a display-friendly resolution without a companion Pi. It is a useful reference build for anyone considering a factory-floor HVAC or insulation-diagnostic sensor at hobbyist BOM cost.

### 🔬 Details (Phân)
The wiring is I2C-only: the MLX90640 connects on the R4's SDA/SCL pins with 4.7 kΩ pull-ups, the DFRobot TFT sits on SPI plus the R4's capacitive-touch controller, and a pair of physical buttons handle mode switching. The MLX90640 sensor itself is a well-characterised part — Melexis publishes the calibration and driver code, and Adafruit and Seeed both ship the same die on carrier boards — so the electrical build risk is low. The R4 Minima was chosen over the classic UNO because the classic AVR does not have the SRAM to hold both the raw 768-pixel `float` frame and an interpolated display buffer; the RA4M1 with 32 KB SRAM does the work comfortably at interactive frame rates.

The article is quiet on firmware detail — no code snippet, no interpolation algorithm named, and no on-screen colour-mapping approach — which limits its use as a copy-and-adapt reference. What it does provide is the confirmed hardware BOM and the enclosure design workflow in FreeCAD, both of which are the two lifts that stop hobbyists from moving from a breadboard demo to a portable instrument. For a workshop that already has a 3D printer and standard Arduino toolchain access, this is a weekend build, and the resulting device is comparable in raw thermal capability to entry-level commercial thermal cameras from Seek or FLIR at roughly a fifth the cost.

The limits worth flagging are three. First, 32x24 is genuinely low — commercial handheld thermal cameras today start at 160x120 and go up to 384x288, so the interpolated output is visually smoother than the underlying data. Second, the MLX90640 is not radiometric in the sense of a calibrated commercial camera; absolute temperature accuracy depends on emissivity assumptions and ambient temperature compensation the user has to configure. Third, the R4 Minima has no built-in Wi-Fi, so any cloud-side pipeline for storing thermal frames needs an external radio or a wired dump to a host.

### 🎯 Takeaway (Hợp)
If you need occasional thermal inspection at HVAC-diagnostic cost and are comfortable with I2C wiring and a FreeCAD-plus-printer workflow, this is a viable weekend project — treat it as a hobbyist tool, not a calibrated instrument. If your use case is quantitative (energy audit, industrial hotspot detection at known emissivity), spend the extra on a radiometric commercial camera instead of trying to characterise the MLX90640 yourself.

### 💡 Example
```cpp
// Minimal MLX90640 read loop on an Arduino UNO R4 Minima using Adafruit_MLX90640.
#include <Wire.h>
#include <Adafruit_MLX90640.h>

Adafruit_MLX90640 mlx;
float frame[32 * 24];

void setup() {
  Serial.begin(115200);
  Wire.begin();
  Wire.setClock(400000);
  if (!mlx.begin(MLX90640_I2CADDR_DEFAULT, &Wire)) {
    Serial.println("MLX90640 not found");
    while (1) delay(10);
  }
  mlx.setMode(MLX90640_CHESS);
  mlx.setResolution(MLX90640_ADC_18BIT);
  mlx.setRefreshRate(MLX90640_8_HZ);
}

void loop() {
  if (mlx.getFrame(frame) == 0) {
    Serial.print(frame[0]); Serial.print(" C  hotspot=");
    float hot = frame[0];
    for (int i = 1; i < 32 * 24; i++) if (frame[i] > hot) hot = frame[i];
    Serial.println(hot);
  }
}
```
