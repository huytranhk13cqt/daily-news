## 1. Arduino Core on Zephyr 1.0.0 Lands With 11 Boards and a Dragonwing-Plus-STM32H5 Flagship

### 🔭 Overview (Tổng)
Arduino announced the first stable release of ArduinoCore-Zephyr, tagged 1.0.0, after roughly a year in the 0.9x beta line. The core rides on Zephyr 4.4.1 upstream and now targets eleven Arduino boards spanning the whole Portenta / Nicla / Nano / Opta / GIGA line, with a brand-new VENTUNO Q joining as an AI-plus-real-time flagship that pairs a Qualcomm Dragonwing IQ-8275 SoC with an STM32H5F5 microcontroller in a single package. The significance is that Arduino has now stapled its familiar `setup()` / `loop()` sketch surface onto a real preemptive RTOS with drivers, power management, and networking that Arduino did not have to write, closing a gap that Zephyr-first ecosystems like Nordic's nRF Connect had been widening for years.

### 🔬 Details (Phân)
The 1.0.0 release lifts the upstream Zephyr version to 4.4.1 — the same LTS-adjacent branch the Zephyr Project cut security fixes into last month — and inherits its Bluetooth, USB, filesystem, and driver improvements without any Arduino-side patching. Camera capture now works on the Nicla Vision through the Zephyr `video` subsystem, which is the first time Arduino IDE users get a proper streaming camera API on that board rather than a vendor-specific blob. Bug-fix work touches the whole core: the changelog notes a substantial round of cleanup, and the underlying architecture is a Zephyr application that exposes Arduino APIs as a compatibility shim, so a sketch continues to compile but sits on top of a real thread scheduler, work-queue, and device-tree-driven driver model.

The VENTUNO Q is the interesting hardware story around the release. The Dragonwing IQ-8275 is a Qualcomm application-class SoC with an NPU aimed at on-device AI, and pairing it with a Cortex-M33 STM32H5F5 in the same board gives a single Arduino platform both AI compute and hard real-time control loops — the split most industrial edge stacks currently build by wiring two boards together. Existing boards keep their places: UNO Q, Portenta H7, Portenta C33, Opta microPLC, GIGA R1 WiFi, Nano Matter, Nano RP2040 Connect, Nano 33 BLE, Nicla Sense ME, and Nicla Vision are all in the supported set. Installation is through Arduino IDE's Board Manager by searching "zephyr" and selecting 1.0.0; the package installs the correct Zephyr toolchain in the background so end users do not see west, CMake, or a Python virtual environment at all.

Where this sits in the ecosystem is worth reading carefully. Zephyr already covers most of these SoCs directly through its own `boards/arduino_*` ports, so the win of ArduinoCore-Zephyr 1.0.0 is not new silicon — it is that a sketch author can move from AVR-era Arduino IDE workflows to a modern RTOS without learning `prj.conf`, device-tree overlays, or Kconfig. The trade-off, and the reason to treat this as a bridge rather than a replacement, is that anything beyond the Arduino API surface (threads, work-queues, RTOS mutexes, Zephyr-native subsystems like Bluetooth Mesh or LwM2M) still needs Zephyr-native code, which the compatibility shim exposes but does not translate to Arduino idioms.

### 🎯 Takeaway (Hợp)
If you have a Portenta, Nicla, or GIGA board sitting on the classic Arduino Core, this is the version to migrate to before starting new work — Zephyr 4.4.1 underneath gives you real threading, deterministic scheduling, and a modern driver model without touching the sketch code. The VENTUNO Q is the board to watch if your edge AI stack has been two boards taped together; consolidating onto Dragonwing + STM32H5 is exactly the pattern this release is built for.

### 💡 Example
```cpp
// A Nicla Vision sketch on ArduinoCore-Zephyr 1.0.0: capture one frame
// through the Zephyr video subsystem and stream it over USB CDC.

#include <Arduino.h>
#include <Camera.h>          // Arduino wrapper over Zephyr video
#include <USBCDC.h>

CameraClass cam;
uint8_t     buf[320 * 240 * 2];  // RGB565 QVGA

void setup() {
  Serial.begin(115200);
  while (!Serial) delay(10);
  cam.begin(CAMERA_R320x240, CAMERA_RGB565, 15);
}

void loop() {
  if (cam.grab(buf, sizeof(buf)) == 0) {
    Serial.write((const char *)"FRAME\n", 6);
    Serial.write(buf, sizeof(buf));
  }
  delay(66);  // ~15 fps
}
```

### 🔭 Overview (Tổng)
Home Assistant 2026.9 shipped with a rework of Modbus support that removes the long-standing pattern of pasting hundreds of register maps into `configuration.yaml` and replaces it with a shared `modbus-connection` library built on `tmodbus`, so device integrations describe how their hardware talks and share one TCP or RTU connection instead of each opening its own. Three new integrations — Fronius (SunSpec Modbus TCP for per-string solar), Sofar Inverter Modbus, and Flexit ventilation — ship on this new stack and are configured through the UI rather than YAML. Alongside the Modbus rework, the release opens a Home Assistant Cloud beta for a Soniox-backed speech-to-text engine, extends the security dashboard with active-alerts and favourites cards, and adds thirteen new integrations covering spa systems, Samsung TV RS-232 control, Specialized turbo e-bikes, ISEO Argo BLE armored-door locks, and Besen EV chargers.

### 🔬 Details (Phân)
The Modbus modernisation is the release's load-bearing change. Historically a Home Assistant Modbus setup meant per-device YAML blocks that declared each holding-register address, data type, scale factor, and unit, and the built-in `modbus:` integration held one connection per bus. The new architecture inverts that: the `modbus-connection` shim (a HA-specific wrapper over the `tmodbus` async library) owns the connection lifecycle, and per-vendor integrations declare their register maps in Python once and are configured through the UI as regular integrations. That means adding a Fronius inverter is now a "Add Integration → pick the model → point at IP" flow rather than a copy-paste-and-restart operation. It also unlocks per-string solar data on Fronius via SunSpec, automatic model detection on Sofar, and shared-bus operation when multiple devices sit on the same RS-485 segment.

The Cloud voice work is a change of provider for Nabu Casa subscribers rather than a change of architecture. The new speech-to-text engine is powered by Soniox and is opt-in through Settings → System → Labs; Home Assistant states there is no logging, storage, or training on subscriber audio, and Soniox's headline gains are accent robustness, noisy-room performance, and non-English coverage — the three complaint categories that have dominated the STT feedback threads for the last year. Alongside it, the security dashboard now has an "Active Alerts" card that renders only when doors are open, smoke alarms are triggered, or another user-marked severity fires, and a "Favourites" card that pins frequently-checked entities to the top, both of which were community-designed and use the same editor workflow as regular Lovelace cards.

The thirteen new integrations lean local-first: Hot Spring spa control is fully local network, Samsung TV via ExLink uses the panel's RS-232 port for models that stopped responding to the network API years ago, ISEO Argo BLE ships encrypted access logs from Italian-market armoured doors, and Besen EV chargers arrive on BLE rather than Wi-Fi. The Matter network map is now shown as an actual topology diagram with Thread routing and RSSI, and tile cards can now expose light effects, vacuum fan speed, and humidity setpoints without opening a more-info dialog — small quality-of-life work that adds up across a large dashboard.

### 🎯 Takeaway (Hợp)
If your Home Assistant install has a large `modbus:` block, this is the release to plan a migration against — moving to UI-configured, per-vendor Modbus integrations gets you shared-bus concurrency and stops the YAML from being your single point of failure at every restart. Voice UX teams that had shelved Cloud STT because of accent errors should re-test on the Soniox beta before deciding whether to keep local Whisper as the default.

## 4. AWS Wires Trino 475 on EMR Into S3 Tables via the Iceberg REST Endpoint

| Field | Value |

| 🔑 Keywords | `s3-tables` · `iceberg-rest` · `trino-emr` |

### 🔭 Overview (Tổng)
AWS Big Data published a walkthrough showing how to point Trino 475 (or later) running on EMR 7.11+ at Amazon S3 Tables using the Iceberg REST Catalog interface with AWS Signature Version 4 authentication. The pattern replaces the earlier, S3-Tables-specific catalog wiring with the same REST catalog interface any Iceberg-compatible engine already knows, which means the same catalog wiring works for Spark, Flink, Trino, Snowflake, and third-party engines with only a URL and warehouse ARN change per engine. Practically it collapses one of the more awkward integration points in the AWS lakehouse stack — Trino wanting a real REST catalog, S3 Tables wanting SigV4 — into a single properties file that ships with EMR.

### 🔬 Details (Phân)
The configuration lives in a single Trino catalog properties file at `/etc/trino/conf/catalog/s3tables_irc.properties` on the EMR nodes. Four settings do the load-bearing work: `iceberg.rest-catalog.uri=https://s3tables.<REGION>.amazonaws.com/iceberg` points at the S3 Tables REST endpoint, `iceberg.rest-catalog.warehouse` names the S3 Tables bucket by ARN, `iceberg.rest-catalog.sigv4-enabled=true` with `iceberg.rest-catalog.signing-name=s3tables` turns on SigV4 signing against the S3 Tables service (rather than plain `s3`), and `iceberg.rest-catalog.view-endpoints-enabled=false` disables the view catalog surface that S3 Tables does not implement today. The filesystem side is `fs.hadoop.enabled=false` with `fs.native-s3.enabled=true`, which switches Trino to the native S3 file system rather than the Hadoop S3A adapter — the native path is required for the Trino-S3 Tables happy path and skips the S3A quirks around consistent listing.

Version pinning is not optional. Trino 475 is the first release where the Iceberg connector's REST catalog handles SigV4 signing with a custom signing name; earlier Trino releases have the REST catalog but assume the endpoint is signed as `execute-api`, which fails against S3 Tables. EMR 7.11 is the earliest AWS-published EMR image that ships Trino 475, and it also updates the IAM role wiring — `s3.iam-role=arn:aws:iam::<ACCOUNT-ID>:role/service-role/<ROLE-NAME>` — so the Trino worker's SigV4 signer picks up the EMR instance profile rather than a static access key.

What this pattern replaces is the AWS-Glue-Data-Catalog-with-S3-Tables-adapter approach that had been the recommended EMR integration until now. Glue-mediated access works but adds a hop and requires every S3 Tables table to be registered as a Glue table; the REST catalog path skips Glue entirely, so query planning goes Trino → S3 Tables → object storage without a metadata cache in between. The trade-off is governance: teams that centralised policy on Glue's Lake Formation grants have to move those to S3 Tables permissions, and Athena / Redshift Spectrum consumers of the same tables still speak the Glue path today, so a hybrid deployment sits on both catalog surfaces during the transition.

### 🎯 Takeaway (Hợp)
If you run Trino on EMR against S3 Tables and had wired it through the Glue catalog to work around REST-catalog limitations, upgrade to EMR 7.11 with Trino 475 and cut over to the direct Iceberg REST path — the config is one properties file and it removes the Glue hop from your query plan. Nếu Redshift Spectrum hoặc Athena vẫn còn đọc trên cùng tập bảng, giữ song song hai catalog trong giai đoạn chuyển tiếp cho tới khi các engine đó cũng nói REST catalog trực tiếp.

### 💡 Example
```properties

# with Trino 475+. Replace REGION, ACCOUNT-ID, BUCKET-NAME, ROLE-NAME.

connector.name=iceberg
iceberg.catalog.type=rest
iceberg.rest-catalog.uri=https://s3tables.us-east-1.amazonaws.com/iceberg
iceberg.rest-catalog.warehouse=arn:aws:s3tables:us-east-1:111122223333:bucket/prod-lake
iceberg.rest-catalog.sigv4-enabled=true
iceberg.rest-catalog.signing-name=s3tables
iceberg.rest-catalog.view-endpoints-enabled=false

fs.hadoop.enabled=false
fs.native-s3.enabled=true
s3.region=us-east-1
s3.iam-role=arn:aws:iam::111122223333:role/service-role/EMR_EC2_Trino_Role
```

## 5. Databricks Turns Genie Agents Into a Multi-Step Reasoning Product With APIs and UC Volumes

### 🔭 Overview (Tổng)
Databricks expanded Genie Agents from a chat-style structured-data assistant into a multi-step agentic product: every Genie Agent now has an Agent Mode that plans, iterates, and produces a report with visualisations and citations; a REST API with Server-Sent Events streams the agent's steps to a caller; and each agent can attach up to ten Unity Catalog Volumes so PDFs, slide decks, and images become first-class context alongside SQL tables. A companion tool called Genie Code auto-generates baseline agents from a purpose statement and example questions, and diagnoses failing conversations by surfacing the top failure themes from user feedback. The release makes Genie the first Databricks-native agent surface with both federated data access and a documented external API — the same shape enterprise agent teams have been building by hand.

### 🔬 Details (Phân)
Agent Mode is the substantive change. Where the previous Genie surface answered a single natural-language question with a single SQL query and a chart, Agent Mode runs an agentic loop that plans a research task, executes several iterative queries across the same Unity Catalog data set, and returns a written report with findings, plots, and citations back to the underlying rows. The API is REST with SSE streaming, meaning a caller receives incremental tokens, tool-call events, and rendered visualisations as the agent works rather than a single blocking response; conversation management (thread state, follow-ups, edits to a rendered chart) is exposed through the same endpoints. The visualisation-via-API pathway is the piece most caught the eye — dashboards and analyst tooling can now embed a Genie-authored chart without the user opening the Databricks UI.

The unstructured-data integration is where Genie starts stepping outside its "SQL assistant" origin. Attaching a Unity Catalog Volume — the same governed object-storage abstraction Databricks uses for MLflow models and DLT source files — makes the files inside it retrievable by the agent, and enabling content-search indexing on a Volume gives the agent higher-quality retrieval when the Volume holds thousands of documents rather than a handful. The examples Databricks published lean into the mixed pattern the release is aimed at: "Which regions have the most churned customers, and what are the main themes in their exit surveys?" is a query that hits both structured churn tables and an exit-survey Volume in one agent turn.

Genie Code is the meta-tool for the release. Given a natural-language purpose description and a list of example user questions, it emits a baseline agent — instruction, sample queries, seeded documents — and then, once the agent has conversation history, it diagnoses the failure patterns by summarising the top question topics and the top feedback trends. Where this fits in the broader agent-tooling market is against LangGraph, LlamaIndex, and the AWS AgentCore reference architecture that AWS Big Data posted last week: Databricks is not selling an agent framework, it is selling a fully-managed agent that is native to Unity Catalog and can be pointed at customer data without a build step. The trade-off is Unity Catalog lock-in — Genie Agents are useful precisely because they are governed by UC lineage and ACLs, but that ties the agent's data surface to the Databricks stack.

### 🎯 Takeaway (Hợp)
If you have already stood up Unity Catalog and had been planning to hand-roll an agent over your governed tables and PDFs, evaluate Genie Agents with Agent Mode before writing a line of LangGraph — a UC-native agent with an SSE-streamed API is exactly the surface most enterprise stacks were building by hand. Nếu bạn cần cắm agent này vào tooling ngoài Databricks, REST + SSE là đường cửa chính; đừng chờ SDK.

### 💡 Example
```python
# Minimal SSE client for Genie Agent's Agent Mode. Streams incremental
# tool calls and visualisation frames back as they are produced.

import requests, json

url = "https://<workspace>.cloud.databricks.com/api/2.0/genie/agents/<agent-id>/converse"
headers = {
    "Authorization": f"Bearer {TOKEN}",
    "Accept": "text/event-stream",
}
body = {
    "message": (
        "Which regions have the most churned customers this quarter, "
        "and what are the main themes in their exit surveys?"
    ),
    "mode": "agent",
    "attachments": ["uc://catalog/schema/exit_surveys_volume"],
}
with requests.post(url, headers=headers, json=body, stream=True) as r:
    for raw in r.iter_lines():
        if not raw or not raw.startswith(b"data: "):
            continue
        event = json.loads(raw[len(b"data: "):])
        print(event["type"], event.get("payload", {}).get("summary", ""))
```
