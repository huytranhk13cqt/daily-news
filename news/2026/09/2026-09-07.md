### 🔭 Overview (Tổng)
dbt Labs cut `v2.0.0-rc.1` of dbt-core, the first release candidate of the 2.0 line, and the changelog is unusually load-bearing: a Phase 1 Exasol adapter, automatic query-tag metadata on Databricks, ClickHouse work that finally aligns SQL and Python adapter semantics, a new set of parse-safe graph views, and a call-provenance tracker that powers a new DBT05 lint rule against hard-coded references. The OSS CLI binary is also renamed from `dbt-sa-cli` back to `dbt`, signalling the end of the branding split introduced during the fusion transition. This is the first RC of the 2.0 branch and the piece downstream users (adapter maintainers, dbt-cloud teams, lint-rule authors) will build parity against before the general release.

### 🔬 Details (Phân)
The Exasol adapter is the biggest surface-area addition. Phase 1 covers a working connection layer with TLS and connection-timeout options, all four core materializations (table, view, incremental with the usual `merge` / `delete+insert` / `append` strategies), snapshots, dbt model contracts (column-level constraints), plus the cross-database utilities in `dbt_utils` that adapters have to implement one by one. That is the same "everything a real user needs on day one" scope as when the BigQuery and Databricks adapters landed, and it puts Exasol on the same footing as Snowflake/BigQuery/Databricks/Redshift for orchestrator wiring.

On the Databricks adapter, query tags now include automatic dbt metadata (project name, model unique_id, invocation id, run reason) with configuration at both the profile and the model level, so a DBA looking at the Databricks query history no longer has to grep for a `-- dbt` comment to attribute a query. The Fusion environment variant of the adapter accepts a Python environment key and a dependencies list for serverless job submission, closing a gap that had been blocking Python-model users on Databricks Serverless. ClickHouse gains configurable `DEFINER`, `SQL SECURITY`, and `INSERT ONLY` modes, and model settings now render into DDL with version-gated support so a project targeting older ClickHouse servers does not silently emit unsupported clauses; incremental strategies now match the Python adapter's behaviour and `on_schema_change` co-operates with codec-aware `ALTER` statements.

The two changes that touch every user regardless of adapter are parse-safe graph views and provenance tracking. `dbt.models`, `dbt.seeds`, `dbt.tests`, and the rest of the graph node views now surface at parse time without exposing compile-only columns, so a Jinja macro that reads the graph no longer has to guard against runtime-only fields. Reference tracking records each `ref()`, `source()`, and `this` call as it renders, which is the machinery the new DBT05 lint rule uses to flag hard-coded table references (`FROM my_db.my_schema.my_table` inside a model body) that a project author almost always meant to write with `ref()`. On the security side, the release fixes symlink/hard-link traversal during tarball extraction and updates the `sqlparse` pin to cover CVE-2026-54284, CVE-2026-59893, CVE-2026-59894, and CVE-2026-71491.

### 🎯 Takeaway (Hợp)
If you run dbt-core against Databricks, ClickHouse, or Exasol, install the RC in a scratch project and re-run your DAG before the general release: query-tag defaults change how Databricks history looks, ClickHouse DDL now emits new clauses, and DBT05 will start flagging hard-coded refs your existing suppressions do not cover. Nếu bạn đang quản lý repo dbt-utils tuỳ biến, kiểm tra sớm parse-safe views trước khi 2.0 GA để tránh phải patch macro sau này.

### 🔭 Overview (Tổng)
MotherDuck published a two-week analytics study of its own platform comparing queries issued through its UI (human) with queries issued through its MCP server (agent), and the numbers are more lopsided than most warehouse teams have been modelling. Agents ran 29 times more queries than humans over the measurement window, up from 6x and 16x in the previous two months, meaning the agent-to-human ratio has doubled month-over-month. Organisations already carry twice as many agent users as human users on average, with one customer at a 7:1 ratio. The post is a rare public data point on how agentic workloads actually hit an analytical warehouse, and its recommendations (context layer, hybrid local caching, elastic burst capacity) map cleanly onto changes several other DE vendors have started shipping.

### 🔬 Details (Phân)
The behaviour differs from human traffic on three concrete axes and the MotherDuck engineering team has quantified each. Query cadence is far tighter: the median gap between agent queries is 4 seconds, versus 60 seconds for humans, which makes agent workloads bursty and concurrency-limited rather than throughput-limited. Query shape is also inverted — the median agent query scans 7,000 rows, against 200,000 for a human query — because agents spend most of their time probing schema, sampling small windows, and iterating on error messages before they commit to a scan-heavy final query. And the sheer volume gap is not shrinking: the piece cites 6x, 16x, and 29x agent-to-human ratios across three consecutive months, and calls out one customer at 7:1 agent-to-human user counts.

The recommended architectural response is three-part. First, invest in a context layer — a curated set of table descriptions, column semantics, and example queries — because agents that hit the warehouse without one either waste tokens on trial-and-error or produce wrong answers; MotherDuck cites 55% token savings once its own context layer is on. Second, run hybrid execution so that the small, exploratory queries can hit local cache (the DuckDB-side of MotherDuck's dual-engine model) rather than always round-tripping to the cloud warehouse. Third, design the warehouse capacity model for burst — 4-second inter-arrival intervals mean the peak-to-average concurrency ratio is materially higher than a human-only estimate would suggest.

The wider ecosystem context here is that Databricks (Genie Agents, seen in yesterday's digest), Snowflake (Cortex Agents), and Google Cloud (Data Agent Kit) have all launched agent surfaces on top of governed warehouses in the last quarter, and the MotherDuck numbers are the first published field data on what those surfaces then generate downstream. If the ratios hold across other warehouses, capacity planning that assumes an "agent counts as one user" model is off by roughly an order of magnitude.

### 🎯 Takeaway (Hợp)
Before your next warehouse capacity review, pull your own agent-vs-human query counts for the last three months and check whether the ratio doubled — if it did, size for burst concurrency, not average throughput, and stand up a context layer before the next agent surface goes live. Nếu bạn chưa có MCP server hoặc agent surface trên warehouse, đây là bằng chứng đầu tiên cho thấy chi phí truy vấn có thể tăng bậc thang khi chuyển sang.

### 🔭 Overview (Tổng)
OpenTrailPaper is a new open-source firmware project that turns the LILYGO T5 E-Paper S3 Pro devkit into a self-contained bike computer with offline maps, GPS tracking, and Bluetooth sensor pairing. The board pairs an ESP32-S3N16R (dual-core, 240 MHz, 8 MB PSRAM, 16 MB flash) with a 4.7-inch 960×540 capacitive-touch e-paper panel, a u-blox MIA-M10Q or Quectel L76K GNSS module, an SX1262 LoRa radio, a PCF8563 RTC, and a 1,500 mAh battery. Firmware source and companion iOS/Android apps are on GitHub. The interesting part for an IoT engineer is that it is a full ESP-IDF application against a devkit that is already sold as a bundle, not a bespoke board — so the whole stack from GNSS handling to LoRa peer beacons to FIT logging is a working reference for the same hardware sitting in a lot of drawers.

### 🔬 Details (Phân)
The firmware is written against ESP-IDF and drives the e-ink panel through the on-board display controller, with a 16-grey-level render pipeline that the map tiles are pre-quantised into so the panel refreshes stay under a second on the "partial update" path. Rides are logged in FIT — the same binary format Garmin devices produce — so an export drops into Strava, TrainingPeaks, or Zwift without conversion; structured workouts are read from `.erg` and `.mrc` files on the microSD card, which is also where the offline tiles live. The GNSS is a standard NMEA/UBX pipeline hanging off UART, and Bluetooth-Low-Energy pairing follows the GATT profiles for heart rate, cycling power, and cadence so any standards-compliant sensor works without a vendor-specific driver.

The mapping story is worth calling out because it is the one part usually blocked on commercial licences. OpenTrailPaper generates its own offline tiles from OpenStreetMap using either a Python tool, a browser workflow, or a companion phone app, and renders them at 16 grey levels tuned for e-ink; climbing data is derived from tile elevation instead of a barometric sensor, so the board itself does not need a BMP280 or similar. LoRa on the SX1262 is used for peer-to-peer beacons between OpenTrailPaper devices — the classic mesh-of-cyclists use case — not for uplink to a gateway, so the LoRaWAN stack is optional.

Battery life is honest — under 8 hours on the 1,500 mAh cell — because the ESP32-S3 stays partly awake to service GNSS and BLE; a serious touring build would swap in a higher-capacity pack or duty-cycle the radios more aggressively. The project README credits Claude as a coding assistant "with human supervision", which is worth noting alongside the Spotify Portal item below on how AI-assisted development is now visible in embedded project READMEs the same way in web-app READMEs.

### 🎯 Takeaway (Hợp)
If you already own the LILYGO T5 E-Paper S3 Pro devkit (or you are looking for a reference project on ESP32-S3 + SX1262 + GNSS + e-ink), flash OpenTrailPaper and treat it as a working starting point rather than a hobby build — the tile-generation pipeline and the FIT-logger alone save a couple of weeks of integration work. Nếu bạn muốn dùng LoRa cho beacon giữa các thiết bị, đây là ví dụ tối giản có sẵn.

### 🔭 Overview (Tổng)
The Zephyr Project published a write-up of two lightning talks from the Open Source Summit India 2026 track that sketch out where Zephyr's video subsystem is heading for AI camera workloads. The two proposals are narrow but concrete: attach per-frame metadata and ISP statistics to video buffers so inference results stay aligned with the frame they were computed from, and add runtime power management plus buffer status flags so drivers can suspend the sensor when the stream stops and applications can tell whether a returned frame is intact. Both talks explicitly frame Zephyr against Linux V4L2 and Media Controller — the goal is to add just enough surface for real AI camera pipelines without carrying V4L2's complexity onto microcontroller-class devices. Nothing has landed yet; the value of the post is that it names the specific gaps the maintainers are working from.

### 🔬 Details (Phân)
Rutvij Trivedi's talk framed a modern camera as a "real-time data pipeline" that needs zero-copy buffer sharing, frame-level metadata synchronisation, and predictable streaming states — three things Zephyr's current video framework does not fully provide. The concrete gap is that a `struct video_buffer` today has no place to hang metadata (timestamp, exposure, gain, ISP histogram, or per-frame ML tensor), so the callback that produces an ML result cannot cheaply prove which frame it came from. Trivedi proposed extending the buffer to carry metadata and ISP statistics plus adding per-buffer callbacks so a pipeline stage transition does not require waking the CPU on every frame; on a battery-powered camera doing 15–30 fps that is directly a power-consumption win.

Elgin Perumbilly and Ankit Siddhapura's talk compared Zephyr's camera framework with Linux V4L2 and Media Controller and identified two smaller but load-bearing improvements. First, runtime power management for camera drivers so that when the application stops the stream, the sensor and its regulator drop out — today many Zephyr camera drivers keep the sensor powered whenever the driver is bound. Second, status flags on video buffers so an application can tell whether a returned frame is valid, dropped, or corrupted (a torn frame after a sensor reset, for example), which Linux gets via the V4L2 `V4L2_BUF_FLAG_ERROR` and friends. The framing throughout is that Zephyr should not replicate the whole V4L2 stack — the point is deterministic behaviour on microcontrollers — but the two proposals are the minimum viable delta.

Where this sits relative to yesterday's ArduinoCore-Zephyr 1.0.0 story matters: the Nicla Vision camera path is going through this same Zephyr video subsystem, so the eventual outcome of these proposals lands under Arduino sketches too, without any Arduino-side change. It also sets an interoperability point for Espressif's ESP32-P4 image-pipeline work (already using the Zephyr video framework upstream) and for silicon vendors that ship Zephyr drivers rather than Linux V4L2 shims for their camera SoCs.

### 🎯 Takeaway (Hợp)
If you are building an on-device vision pipeline on Zephyr, subscribe to the video subsystem RFC threads now — per-frame metadata and runtime PM are the two changes that will affect your driver, your inference callback, and your battery budget. Nếu bạn đang tạm bỏ Zephyr vì thiếu metadata per-frame, đây là cửa sổ hợp lý để đóng góp use case của bạn trước khi API được cố định.

 * struct video_buffer. Consumers would read buf->metadata
 * alongside buf->buffer to keep ML results aligned with the
 * exact frame they were computed on. Draft, not upstream yet.

    uint32_t                     size;

## 5. Spotify Open-Sources the Portal Shunt Plugin, Claims 90% Claude Code Token Cut by Splitting I/O From Reasoning

### 🔭 Overview (Tổng)
Spotify Engineering published the internals of Portal — an internal platform for "AiKA Modes", declarative agents running on ephemeral compute — and open-sourced the piece of it that plugs into Claude Code: a marketplace plugin called `shunt` that routes routine file-reading and boilerplate generation to a cheaper model, leaving only actual reasoning steps for the frontier model. The team reports a 90% reduction in Claude Code token usage on their own workloads. The observation driving it is that "most of what an AI coding agent does for me isn't thinking. It's I/O." — a claim that generalises past Spotify's setup to any team running Claude Code at production scale, and one worth reading whether or not you adopt Portal itself.

### 🔬 Details (Phân)
The technical architecture is a three-layer routing system built on Claude Code's hooks, subprocess wrappers, and skills. The first layer is a Claude Code hook that intercepts file reads longer than 350 lines (the threshold is configurable) and redirects them to a `bulk-reader` mode. The second layer is a pair of bash wrappers — `bulk-read` and `code-write` — that invoke the Portal CLI, hand it the file list or the code-generation prompt, and return only the distilled result to the caller. The third layer is a set of Claude Code skills (Markdown files) that teach the frontier model when to delegate: "if you need to read more than three files, call bulk-read; if you need to produce boilerplate that matches an existing pattern, call code-write".

Portal itself runs the two modes as short-lived, declarative agents. `bulk-reader` is configured against Gemini 2.5 Flash with `temperature: 0.2` and an instruction to "output structured bullets only", which is why the token count on the return path stays low. `code-writer` matches existing patterns from the file it is generating alongside and is instructed to "output only the code" so the frontier model does not have to re-parse a chatty response. The whole configuration is a YAML file per mode and lives alongside the plugin, which means an outside team can adapt the modes without touching Portal source.

The `shunt` plugin is public in the `spotify/portal-ai-plugins` marketplace on GitHub, installable through Claude Code's plugin surface. Where this fits the DE picture is on cost engineering for agent-backed data workflows: MotherDuck's post above quantifies the volume-side (agents run 29x more queries than humans), and the Portal write-up quantifies the read-side — most of the tokens an agent spends in a warehouse or codebase are I/O, and pushing that I/O to a cheaper model has an order-of-magnitude impact on cost without touching the reasoning quality. The trade-off is model-diversity risk: the cheap-model results have to be summarised without dropping the detail the frontier model still needs.

### 🎯 Takeaway (Hợp)
If you run Claude Code (or another agentic dev tool) at team scale, spend an afternoon on `shunt` with your own workload before renewing your model spend; the 350-line hook threshold is a good first knob to turn. Nếu bạn quản lý agent trong pipeline dữ liệu, cùng ý tưởng — tách I/O sang mô hình rẻ — sẽ áp dụng được ngay cho retrieval và schema exploration.

### 💡 Example
```yaml
# portal-ai-plugins/shunt/modes/bulk-reader.yaml
name: bulk-reader
model: gemini-2.5-flash
temperature: 0.2
system: |
  You are a file reader. For each file the caller lists, produce a
  compact structured summary as bullet points. Include only:
    - file path
    - top-level symbols (functions, classes, exports)
    - external imports
    - notable constants
  Do not include any prose beyond the bullets. Do not restate the input.

# .claude/hooks/before-read.sh (installed by the shunt plugin)
#   Intercept oversized file reads and route them to bulk-reader.
if [ "$(wc -l < "$1")" -gt 350 ]; then
  exec portal run bulk-reader --file "$1"
fi
```
