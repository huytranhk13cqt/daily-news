### 🔭 Overview (Tổng)
AWS published "AWS and DuckLabs: Building the future of analytics together" on 8 September 2026 to mark the closing of its acquisition of DuckLabs, the roughly thirty-person Amsterdam team behind the DuckDB in-process analytical database. The definitive agreement was announced on 26 August 2026 and closed just under two weeks later; the AWS Big Data blog post is the first substantive statement of what changes for existing DuckDB users. Hannes Mühleisen and Mark Raasveldt stay on to lead the team inside AWS, the DuckDB open-source project itself continues to live under the independent DuckDB Foundation on the MIT license, and AWS commits to keep contributing there rather than fork. For any data engineering team that has adopted DuckDB as the small-query engine sitting next to their warehouse — Parquet-on-S3 exploration, notebook analytics, embedded product analytics — the acquisition sets the tone for the next twelve months of integration work.

### 🔬 Details (Phân)
The post confirms three governance points that had been left ambiguous when the deal was announced in August. First, DuckDB core intellectual property continues to be owned and governed by the DuckDB Foundation, a Netherlands-based non-profit, and the MIT-licensed codebase is not moving into AWS control; the acquisition is of DuckLabs the company (commercial support, cloud service, engineering headcount) rather than of DuckDB itself. Second, Mühleisen and Raasveldt remain the technical leads, which is the signal existing contributors and DuckDB extension authors were waiting for. Third, AWS explicitly commits to keeping DuckDB "an open, community-driven project" and to continue investing in it from inside — the same posture AWS took with OpenSearch after the Elastic fork, with rather different mechanics because DuckDB is community-governed to start with.

The technical roadmap is where the post is most concrete. AWS is positioning DuckDB as an engine that will show up across its analytics surface — Redshift, Athena, EMR, Glue — for the class of queries where the "warehouse" answer is over-provisioned: single-user notebook work, dashboard-tile queries that hit sub-terabyte datasets, product-embedded analytics, and pipeline steps that today spin up a Spark cluster to filter a Parquet file. Amazon Quick already leverages DuckDB inside its dashboarding stack — the post cites 2.5 billion queries processed since October 2025 and a 30% average query-latency reduction — and Allen Institute is cited as a customer whose exploratory queries dropped from minutes to under a second. The prior collaboration path — DuckDB support in Amazon S3 Tables and Amazon SageMaker Lakehouse, added through early 2025 — is the template for what the deeper integration looks like.

For engineering teams, the practical consequence is that the "DuckDB or Redshift?" framing collapses into "DuckDB in front of Redshift, both from AWS." The extension ecosystem (httpfs, iceberg, delta, postgres, spatial) is unchanged, DuckDB v2.0 alpha remains on the DuckDB Foundation's own release train, and MotherDuck (the commercial DuckDB cloud built by other early team members) continues as an independent competitor. The item to watch is pricing: AWS has not yet said whether DuckDB will show up as its own line item on the bill, be bundled inside existing analytics services, or both.

### 🎯 Takeaway (Hợp)
If your stack already leans on DuckDB for notebook or embedded analytics, keep your dependency on the DuckDB Foundation release channel, not on any AWS-branded distribution — the acquisition changes ownership of the company, not the project's licence. Nếu bạn còn đang chọn giữa DuckDB và Redshift Serverless cho lớp query nhỏ, kỳ vọng sáu tháng tới sẽ thấy hai công cụ hội tụ về một control plane duy nhất trên AWS.

## 2. Databricks Unity Catalog Gains ABAC DENY Policies and a New time_bucket SQL Function

| Field | Value |

### 🔭 Overview (Tổng)
Databricks pushed two release-notes entries on 8 September 2026: ABAC DENY policies in Unity Catalog reached beta, and a new `time_bucket` SQL function reached general availability. The DENY entry is the more consequential of the pair — it plugs the last policy-model gap where a Unity Catalog admin could not, before now, subtract a privilege from an owner without changing ownership. The `time_bucket` function is smaller in scope but eliminates the boilerplate every data engineer has written at least once to align event timestamps to non-calendar windows like 15-minute or 3-month buckets. Together the release is Databricks tightening the two ends of Unity Catalog: governance policy and query ergonomics.

### 🔬 Details (Phân)
ABAC DENY policies (beta) let an admin explicitly deny the `MANAGE ACCESS CONTROL` privilege to a named set of principals — and the release notes are clear that "they always take precedence over any grant," so an object owner who would otherwise inherit the privilege loses it once a matching DENY is in place. Prior to this feature Unity Catalog's ABAC layer could only add attribute-conditioned grants; a deny had to be modelled by not granting, which failed at exactly the point admins actually cared about, namely rescinding privileges an owner had by virtue of ownership. The beta is scoped to `MANAGE ACCESS CONTROL` specifically, not a general "deny anything" primitive, which lines up with the same conservative design SQL Server and Postgres use for their DENY equivalents.

The `time_bucket` SQL function is a small ergonomics win with a real footprint in ETL code. It returns the start of the fixed-width interval a timestamp falls into, aligned to a caller-supplied origin, so a 15-minute bucket that begins at 07:07 aligns to 07:00, 07:15, 07:30, etc.; a 3-month bucket aligned to February 1 aligns quarters to Feb–Apr–Aug rather than Jan–Apr–Jul. It is a strict superset of `date_trunc` for cases where the bucket size does not fit a named calendar unit; anyone who has written a subquery with `dateadd(minute, floor(datediff(minute, origin, ts)/15)*15, origin)` will delete a modelling helper this week. Nothing about it is novel across the industry — PostgreSQL 17 has `date_bin`, TimescaleDB has `time_bucket`, Snowflake has `TIME_SLICE` — but the pattern-match to those functions matters for portability.

The pair sits inside a wider Databricks September batch that includes Zerobus Ingest into default storage (see item 5), OpenAI GPT-6 Astra on Unity Gateway (covered yesterday), and expanded Genie One capabilities. The `MANAGE ACCESS CONTROL` DENY specifically is the piece to review against your least-privilege posture before the next Databricks security review — it is now the mechanism for revoking access-management authority from a schema owner without having to reassign ownership through a service principal.

### 🎯 Takeaway (Hợp)
Pilot `MANAGE ACCESS CONTROL` DENY policies against your most-privileged owners this sprint — it is the shortest path to closing the "owner can always regrant" gap in Unity Catalog. Nếu ETL của bạn có hàm helper để chia phút hoặc chia tháng lẻ, `time_bucket` là dịp xoá bớt một lớp abstraction không còn cần thiết.

### 💡 Example
```sql
-- ABAC DENY policy: prevent all members of `data_stewards` group from ever
-- running access-management operations on `analytics.sales`, even if they
-- own the schema. The DENY takes precedence over the ownership grant.

CREATE POLICY sales_deny_manage_access ON SCHEMA analytics.sales
  DENY MANAGE ACCESS CONTROL
  TO GROUP data_stewards;

-- time_bucket: align event timestamps to 15-minute windows starting at
-- 00:00:00 local. Buckets that do not fit a calendar unit are what the
-- function replaces; date_trunc still wins for exact hour/day/month.

SELECT
  time_bucket(INTERVAL 15 MINUTE, event_ts, TIMESTAMP '2026-01-01 00:00:00')
    AS bucket_start,
  count(*) AS events
FROM analytics.sales.raw_events
GROUP BY bucket_start
ORDER BY bucket_start;
```

### 🔭 Overview (Tổng)
Arm launched Compute Subsystems (CSS) for Mobile 2 on 8 September 2026, an AI-native reference platform built around new C2-Ultra and C2-Pro CPU cores with SME2 matrix units and a Mali G2-Ultra NX GPU that adds dedicated neural accelerators alongside the traditional shader cores. CSS is Arm's ready-integrated IP package aimed at flagship-tier mobile SoC customers — Qualcomm, MediaTek, Samsung, Google — and the "AI-native" framing means the whole subsystem is co-designed for on-device inference rather than treating a separate NPU as a bolt-on. For IoT and embedded teams, the reason to pay attention is that CSS-tier IP typically trickles down into the automotive-grade and industrial-grade Cortex-A parts inside twelve to eighteen months, and SME2 in particular will change what an edge-class Arm chip can do without an accelerator.

### 🔬 Details (Phân)
The C2-Ultra core moves to Armv9.3-A with Armv9.4-A extensions and adds both SME2 and SVE2. Arm publishes an out-of-order superscalar pipeline with up to 14 cores per cluster, 64 KB L1 I-cache, 128 KB L1 D-cache, 2-3 MB L2 options, and an optional 256 KB-32 MB L3, all inside a 40-bit physical address space with TrustZone and Secure-EL2 available. Relative to a same-process C1 cluster, Arm's own numbers put the C2 cluster at 1.7× throughput on AI models, 15% higher single-thread performance, 12% faster app launch and multi-thread work, and 15% faster browsing. The C2-Pro variant is the mid-cluster complement; documentation was not public at time of announcement.

The Mali G2-Ultra NX is where the "AI-native" language earns its keep. The GPU supports 10-24 shader cores and pairs them with dedicated neural accelerators used for tasks Arm calls out explicitly — frame-rate upscaling and super-sampling in-engine, and general on-device model inference from the same buffer the graphics pipeline is writing to. Relative to G1-Ultra, Arm claims 24% higher benchmark performance overall, 14% better non-AI gaming, and — this is the interesting number for a mobile power budget — a 70% reduction in DRAM traffic. Less DRAM traffic per rendered frame is where mobile SoCs actually get thermal and battery headroom, so the win is systemic rather than a peak-throughput headline.

The trickle-down for IoT is the point. CSS-tier IP configurations reach automotive and industrial parts on a ~12-18 month lag, and SME2 (Scalable Matrix Extension 2) shipping in a Cortex-A78AE-class successor means an edge gateway can run a mid-size transformer directly on the CPU without depending on a vendor NPU with a proprietary compiler chain. The 70% DRAM traffic drop on the GPU side matters twice: once for battery-powered devices, and once for headless embedded SoCs that reuse the GPU for compute. If you are designing a device that will fabricate in 2028, this is the IP generation to model against — not the current C1 / G1 pair.

### 🎯 Takeaway (Hợp)
Put SME2 on your "we can rely on this" list for edge-inference workloads shipping in 2028 hardware, and start benchmarking your model against publicly available SME2 simulators rather than assuming a dedicated NPU will remain the only route. Nếu bạn đang cân nhắc SoC cho thế hệ sản phẩm sau, CSS for Mobile 2 là mốc IP đầu tiên đáng chép vào bảng so sánh cho 2027-2028.

__arm_new("za")

### 🔭 Overview (Tổng)
Seeed Studio released two refreshes of its thumbnail-sized XIAO line on 7 September 2026: the XIAO SAMD21 Plus at US$5.90 and the XIAO RP2040 Plus at US$4.90. Both keep the roughly 21 × 18 mm footprint of the original XIAO series but move to USB Type-C, add roughly fifteen extra GPIO pins as castellated SMD pads on the underside, and integrate a Li-ion power management IC so the boards can be soldered onto a carrier and driven directly off a single-cell Li-ion pack without external charge and boost circuitry. For any project that has been using the original XIAO on breadboards and then hit the ceiling on I/O count or battery integration, the Plus revisions are a drop-in replacement that removes those two limits without changing the mechanical envelope.

### 🔬 Details (Phân)
The XIAO SAMD21 Plus uses the same Microchip SAMD21G18 Cortex-M0+ at 48 MHz with 256 KB flash and 32 KB SRAM as the original, in a 23.5 × 17.5 mm footprint. Beyond the seven pins on the two long edges, the Plus adds sixteen SMD castellations on the underside for I2C, SPI, PWM, analog, and extra digital I/O, and the on-board PMIC handles Li-ion charge, protection, and boost. USB-C replaces micro-USB for programming and power, and the industrial temperature range of -40°C to 85°C is preserved.

The XIAO RP2040 Plus uses a Raspberry Pi RP2040 at 133 MHz with 264 KB SRAM and 2 MB SPI flash in a 21 × 17.8 mm footprint, adds fifteen SMD castellations for the extra I/O, and includes the same PMIC arrangement. The temperature range is the narrower consumer band of -20°C to 70°C. Both boards support Arduino, MicroPython, CircuitPython, Rust, and Zephyr, so the toolchain story is unchanged. The RP2040 Plus in particular is aimed at the wearable and small-battery segment where the XIAO RP2040 has been the go-to reference but where designers historically added a TP4056 charge module and an MCP73831 or MP2617 as external parts.

The wider read is that the "Pico footprint Linux SBC" thread from earlier this week (YuzukiNeko yesterday) and this XIAO Plus release are two sides of the same trend: the thumb-sized microcontroller footprint is being pushed both up (adding a real Linux capability inside the same slot) and out (giving the existing MCU a full battery and I/O story), so the design space between the classic Pico module and a fully custom carrier is shrinking. For a fielded product on the original XIAO, the Plus is a bill-of-materials simplification rather than a redesign.

### 🎯 Takeaway (Hợp)
If you ship a XIAO-based product with an external Li-ion charger IC, spec the Plus revision into the next PCB rev — the PMIC integration alone typically removes two-to-three passives and a whole subcircuit. Nếu bạn cần thêm chân IO nhưng vẫn muốn giữ nguyên footprint XIAO, đây là bản Plus tối thiểu để nâng cấp mà không đụng đến layout.

## 5. Databricks Turns On Zerobus Ingest Into Default Storage in Public Preview

| Field | Value |

### 🔭 Overview (Tổng)
Databricks moved Zerobus Ingest into default storage to public preview on 7 September 2026, which is the piece that had been missing from the wider Zerobus Ingest rollout: an event producer can now write directly into a Unity-Catalog-managed table backed by default (Databricks-managed) storage, rather than only into a table backed by a customer-managed external location. Zerobus Ingest is Databricks' streaming-append surface in Lakeflow Connect — a serverless HTTP endpoint that accepts row-oriented events, batches them in the platform, and commits Delta files without the producer having to run any compute or hold any state. The default-storage preview closes the last "why does this need a special external location?" question and makes the surface usable from the same governed catalog as everything else.

### 🔬 Details (Phân)
Zerobus Ingest itself has been generally available since earlier in 2026 as a Lakeflow Connect endpoint. The producer speaks the Zerobus wire protocol — Apache Arrow reached general availability on the endpoint on 4 September (see the September release notes) — and Databricks handles buffering, ordering, exactly-once semantics, and the Delta commits. Until now the target table had to sit in a customer-managed external location — an S3, ADLS Gen2, or GCS path registered under Unity Catalog — because default storage did not yet accept the low-latency small-file writes Zerobus generates before compaction. The 7 September preview extends the target set to include tables backed by default storage, which is where new Unity-Catalog-first workspaces put everything unless the team has explicitly configured otherwise.

The mechanical benefit is that the same governance surface that already covers table ACLs, column masks, and row filters now covers the entire path from `POST /zerobus/rows` to the Delta table without an out-of-band bucket policy step. For a data-engineering team standing up ingestion for a new domain, this collapses "provision a bucket, register it as an external location, grant on the location, grant on the table" to just "create the table, grant on the table." The preview status means the standard Databricks preview caveats apply — no production SLA, feature flags may change — but the write path is the same as the GA endpoint, so a preview target can be lifted to GA storage once the feature reaches general availability without changing the producer code.

The wider positioning is that Databricks is closing the gap with Snowflake's Snowpipe Streaming and Confluent's direct-into-Iceberg path on the low-latency-append surface. Snowpipe Streaming is engine-native and default-storage from day one; Confluent's Tableflow lands into Iceberg tables in customer-managed storage; Zerobus Ingest is the Databricks equivalent and, with default-storage support in preview, now matches Snowpipe on that dimension.

### 🎯 Takeaway (Hợp)
If you have been avoiding Zerobus Ingest because you did not want to stand up an external location for streaming rows, revisit it this sprint — the preview lets you target default storage and cuts the setup to a single CREATE TABLE. Nếu pipeline hiện tại đang gõ trực tiếp vào Delta bằng Structured Streaming từ EKS, Zerobus là điểm tựa serverless đáng benchmark lại chi phí.

### 💡 Example
```python

# default storage (public preview since 07/09/2026). No compute required
# on the producer side; Databricks handles buffering and Delta commits.

import requests, os

ENDPOINT = os.environ["ZEROBUS_URL"]        # per-workspace HTTPS URL
TOKEN    = os.environ["DATABRICKS_TOKEN"]

payload = {
  "table": "main.events.clicks",             # default-storage-backed table
  "rows":  [
    {"user_id": "u_129", "event": "page_view", "ts": "2026-09-09T07:20:00Z"},
    {"user_id": "u_130", "event": "add_cart",  "ts": "2026-09-09T07:20:01Z"},
  ],
}
r = requests.post(
    f"{ENDPOINT}/zerobus/rows",
    headers={"Authorization": f"Bearer {TOKEN}"},
    json=payload,
    timeout=5,
)
r.raise_for_status()
print(r.json())    # -> {"committed": 2, "sequence": 8123421}
```
