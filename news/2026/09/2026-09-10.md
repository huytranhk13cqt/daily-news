### 🔭 Overview (Tổng)
Waveshare unveiled the ESP32-C5-Pico on 9 September 2026, a development board that takes Espressif's dual-band ESP32-C5 SoC — the first RISC-V part with 2.4/5 GHz Wi-Fi 6, Bluetooth 5 LE and 802.15.4 for Zigbee, Thread and Matter — and drops it into the same 51 × 21 mm outline the Raspberry Pi Pico established. Four variants ship at US$8.99 to US$11.33 depending on antenna choice (PCB or U.FL) and pre-soldering. For anyone with an existing Pico-shaped carrier board, this is the first single-package way to get a full three-radio stack — dual-band Wi-Fi 6, BLE and 802.15.4 — without redoing the mechanical layout.

### 🔬 Details (Phân)
The board carries an ESP32-C5HF4 single-core 32-bit RISC-V running at 240 MHz with a secondary low-power RISC-V core at 48 MHz, 384 KB SRAM, 320 KB ROM and 4 MB SPI flash. Two 20-pin headers expose 26 GPIO with the expected I2C, SPI, UART, SDIO, PWM and JTAG signals, and USB Type-C handles both programming and power. Power management is more integrated than the classic Pico: an MP1605GTF-Z buck converter runs off USB or a 3.7 V single-cell Li-ion input, and an ETA6098 handles battery charging on-board. The physical footprint is 56.85 × 21 mm for the PCB-antenna variant and 51 × 21 mm for the external-antenna variant — the latter matching the original RP2040 Pico exactly.

Toolchain support is the standard Arduino IDE plus ESP-IDF, and Waveshare publishes documentation at docs.waveshare.com/ESP32-C5-Pico with a GitHub repository at github.com/waveshareteam/ESP32-C5-Pico that includes sample code for the on-board RGB LED, an I/O expander, Wi-Fi and UART, an LCD touchscreen carrier and a CAN transceiver. Two SKUs ship unsoldered (Pico and Pico-U at US$8.99 / US$9.99) and two ship with headers pre-soldered (Pico-M and Pico-UM at US$9.99 / US$10.99); the Waveshare store lists them today. The context is that Espressif's ESP32-C5 entered mass production in April 2025 but until now the mainstream carriers were either the DevKitC-1 form factor or Seeed's XIAO ESP32-C5 in a much smaller thumb layout — the Waveshare board fills the "Pico slot" that Raspberry Pi's own RP2040 defined.

For anyone maintaining a Pico-based product, the ESP32-C5-Pico is a like-for-like footprint upgrade with three practical consequences. Wi-Fi 6 on 5 GHz avoids the crowded 2.4 GHz band; 802.15.4 support means the same board can act as a Thread border router or a Matter accessory without a companion chip; and the on-board Li-ion PMIC eliminates a chunk of external charge circuitry that Pico designs typically added on the carrier. The trade-off is the ESP32-C5's single application core, which is a step down from the RP2350 dual Cortex-M33 in raw MCU throughput, so anything that needed both cores of the newer Pico 2 is not a drop-in swap.

### 🎯 Takeaway (Hợp)
Add the ESP32-C5-Pico to your parts list if you have a Pico-shaped product that wants Wi-Fi 6, Thread or Matter without a companion radio. Nếu carrier PCB đã sẵn footprint Pico, đây là cách rẻ nhất để có ba radio và Li-ion charger tích hợp chỉ với một lần thay module.

Contributor `@ash2shukla` is credited on the commit. There is no CVE number in the release notes at time of writing, but the pattern (server-controlled input reaching filesystem write path) puts this in "patch now" territory for anyone whose dbt CI pulls community packages.

On the pre-release track, 2.0.0-rc.2 lands ClickHouse unit-test support with better SQL statement splitting for backslash escapes, expands ClickHouse table, materialized view and projection handling, and improves how Databricks views handle full refresh flows. Snowflake operators should note the separate dbt-snowflake advisory attached to the September release: Snowflake plans to increase default string and binary column sizes to 128 MB / 64 MB later this month, and dbt-snowflake versions below v1.10.6 may fail incremental builds when it activates.

### 🔭 Overview (Tổng)
Databricks flipped the `generate_citations` option on the `ai_search` SQL function to Beta on 8 September 2026, letting a caller ask the function to return not just an answer but also the specific retrieved chunks the underlying model used to support it. For engineering teams that have been putting `ai_search` into governed queries and dashboards, this is the piece needed to close a real audit loop: every generated answer can now be tied back to source rows in the same query result, without a second orchestration step. It sits on the same September Databricks release train as ABAC DENY policies and `time_bucket` covered yesterday.

### 🔬 Details (Phân)
`ai_search` is Databricks' SQL surface for retrieval-augmented generation over a Unity Catalog vector or hybrid index: it accepts a natural-language question, executes retrieval against the index, and returns a synthesised answer. Until now the answer came back as an opaque string and any team wanting citations had to run the retrieval and the LLM call separately, then join them by document ID. The new `generate_citations` option asks the same function to emit both the generated answer and, for each chunk it used, an identifier and offset — so the same SQL that produced the answer produces the evidence. Databricks documents the flag alongside the `ai_search` reference and the AI Search sibling release the same day, which added struct/map column indexing and filter-only queries.

The design point that matters is that this is a SQL-level option, not a separate API. A caller can turn citations on in a dashboard tile, a materialised view, or an inline `SELECT` — governance follows the query. That maps neatly onto the same audit posture that Unity Catalog's ABAC DENY policies now enforce: an admin can prove which rows produced a given answer and which principals could have queried them. The current Beta scope is `ai_search`; the same idea across other `ai_*` SQL functions (`ai_query`, `ai_generate_text`) is not yet in the release notes.

For most data engineering teams the practical consequence is that `ai_search` becomes viable in downstream products where compliance or product design needs "why did the model say that." The trade-off is response size: each citation adds rows or JSON to the return, so a dashboard hitting `ai_search` at high fanout should measure the extra tokens against its cost model. Beta status also means the schema of the citation payload may shift before GA, so wrap it in a view rather than reading it directly from application code.

### 🎯 Takeaway (Hợp)
Turn `generate_citations` on in one non-production `ai_search` dashboard this sprint and audit the citations against known-good documents — it is the fastest way to see whether retrieval quality has been silently drifting. Nếu bạn phục vụ khách hàng nội bộ cần "vì sao câu trả lời như vậy", đây là mảnh ghép đầu tiên đáng đưa vào review chuẩn.

### 💡 Example
```sql
-- ai_search with citations turned on. Same call shape as before, but the
-- return now carries chunk-level provenance for every answer.

SELECT
  question,
  answer,
  citations                             -- new: array<struct<chunk_id,offset>>
FROM (
  SELECT
    q.question,
    ai_search(
      index      => 'main.support.kb_index',
      query      => q.question,
      num_results => 5,
      options    => named_struct(
        'generate_citations', true      -- Beta flag, off by default
      )
    ).*
  FROM support.recent_questions q
  WHERE q.ingested_at >= current_date() - INTERVAL 1 DAY
);
```

### 🔭 Overview (Tổng)

The remap is a direct response to the summer's consolidation — IBM closed its acquisition of Confluent in March 2026 and has since retired its own Kafka products, CoreWeave absorbed Bufstream into its AI platform, and Decodable merged into Redis. For any team building on Kafka, the landscape is now the reference for who owns which slice of the streaming market this quarter.

### 🔬 Details (Phân)
The workload / deployment quadrant places Confluent, Amazon MSK, Azure Event Hubs (Kafka surface), Google Managed Kafka, WarpStream and Aiven in the operational / fully-managed corner; Apache Kafka itself, Redpanda, Cloudera, StreamNative and Strimzi in operational / self-managed; Databricks and — new to the landscape this quarter — Snowflake in analytical / fully-managed; and Apache Fluss, Spark, Materialize and RisingWave in analytical / self-managed. Waehner counts more than 150,000 organisations running Kafka in 2026, and calls Apache Kafka "the de facto standard." Snowflake's promotion into the analytical quadrant follows its Datastream launch at Snowflake Summit 2026 in June — a Kafka-compatible ingest surface that lets existing Kafka producers write into Snowflake tables without an extra service.

The consolidation picture is the reason the axes changed. IBM's ownership of Confluent means the "IBM Event Streams" and Confluent Platform stories collapse into one; StreamNative reversing its historic anti-Kafka stance and shipping its own Kafka product signals that the market has forced convergence on the Kafka protocol, even for vendors who started elsewhere. The "deployment control" axis captures a new pressure — data sovereignty rules pushed by EU, APAC and government-adjacent customers make "fully managed by a US hyperscaler" no longer a default; air-gapped and BYO-cloud deployments matter enough now to earn their own axis rather than a footnote.

For a data engineering team, the useful output is a scoring rubric: for a given topic, if the downstream is a warehouse table, the analytical quadrant (Databricks, Snowflake, Fluss, Materialize, RisingWave) is where to shop; if it is a microservice, the operational quadrant applies, and the deployment axis then decides between the hyperscaler-managed corner and the on-prem / air-gapped edge. This is a substantive change from the 2025 landscape, which treated deployment as a footnote to workload; the 2026 view acknowledges that sovereignty is now driving vendor selection at least as much as feature parity.
