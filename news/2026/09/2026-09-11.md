## 1. Apache Iceberg Advances Read Restrictions and Catalog Labels as Cross-Engine Governance Primitives

| Field | Value |
|---|---|
| 📅 Date | 10/09/2026 |
| 🏷️ Topic | Standards |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `apache-iceberg` · `read-restrictions` · `catalog-labels` |
| ⚡ Impact | High |

### 🔭 Overview (Tổng)
Databricks used a 10 September 2026 blog post to describe two Apache Iceberg specifications that have now been advanced and adopted by the Iceberg community: Read Restrictions and Catalog Labels. Together they attempt to answer a question that has dogged multi-engine lakehouses for two years: how does a governed table stay governed when Trino, Spark, DuckDB and Snowflake all read it through a REST catalog rather than a single query engine. Read Restrictions describes how a catalog returns per-request row-filter and column-projection instructions that a trusted engine must apply; Catalog Labels describes how governance metadata travels between federated catalogs as opaque key/value pairs. For any team standardising on Unity Catalog, AWS Lake Formation, Google Knowledge Catalog, Snowflake Horizon or a Polaris/REST implementation, this is the first version of a common wire-level protocol for enforcement instead of every catalog inventing its own.

### 🔬 Details (Phân)
Read Restrictions is deliberately bounded rather than expressive. The spec defines nine predefined column-projection actions — the write-up calls them column-level rewrites such as drop, mask, hash and null — together with a standardised row-filter expression grammar the catalog returns alongside metadata. A trusted engine reads the response, applies the mask or filter locally, then reads the underlying data files. The bounded vocabulary is the point: it is small enough for Spark, Trino, DuckDB and warehouse-adjacent engines to implement uniformly, and it explicitly cannot express subqueries, lookup joins or custom UDFs. The scenario it fits is direct engine-to-catalog with a runtime the catalog trusts to obey the instruction — Databricks calls out "securely configured Trino" as the canonical example.

Catalog Labels goes the other direction: it lets one catalog publish governance metadata that another catalog can consume without needing a synchronous permission callback per request. Labels are opaque key-value pairs attached to tables and columns and exchanged over Iceberg's Open APIs; the consuming catalog maps them to its own classification and evaluates access locally. There is no standardised label semantics — a `pii=email` label is only meaningful to a consumer that has been configured to recognise it — but that trade-off is what makes it federate: Unity Catalog, Snowflake Horizon, Lake Formation and Google Cloud's Knowledge Catalog can each apply their own rules once they read the label. This is fundamentally different from an ABAC policy sync in that no cross-catalog RPC is needed at query time.

The wider read is that the Iceberg community is quietly turning the REST catalog into a control plane rather than a metadata store. Read Restrictions closes the loophole where a foreign engine reads Parquet files directly and bypasses the catalog's row filters; Catalog Labels closes the loophole where federated catalogs disagree about which columns are sensitive. Both are additive changes to the existing Iceberg REST spec — no format-level change to v3 tables — so vendor implementation timelines will vary and early adopters should expect Unity Catalog and Snowflake to move faster than the open-source Iceberg REST reference. There is no mention of when this lands in Iceberg 1.12 or a later minor release.

### 🎯 Takeaway (Hợp)
If your architecture has more than one query engine reading the same Iceberg tables, put Read Restrictions and Catalog Labels on the platform roadmap this quarter — they are the first cross-vendor path to consistent enforcement. Nếu bạn đang phải viết Ranger hoặc OPA policy song song cho Trino và Spark, đây là spec đáng theo dõi để bỏ bớt một trong hai.

### 🔭 Overview (Tổng)
Databricks Field Engineering open-sourced Consort on 9 September 2026, an agentic development framework that runs test-driven development against real Lakebase Postgres branches instead of mocks. The design treats database migrations as versioned artifacts that ship with application code, assigns dedicated LLM agents to product-owner, architect, DBA and test-strategist roles, and coordinates them with a deterministic state-machine conductor. It is community-supported rather than a Databricks platform feature, and works on top of Lakebase — available in the Databricks Free Edition — plus Java, Python or Node stacks running on Claude.

### 🔬 Details (Phân)
The core mechanic is Lakebase's copy-on-write database branching: creating an isolated database instance is constant-time regardless of data size, so a pull request can spin up its own branch, run schema migrations via Alembic, Flyway or Knex, execute the full test suite, and tear the branch down. That collapses the traditional gap between "unit tests with a mocked DB" and "integration tests in staging" into a single inner-loop step where every red/green/refactor cycle sees a fresh branch. Consort exposes this via a VS Code plugin that displays paired Git and Lakebase branches with unified code/schema diffs, and an observability dashboard that shows each workflow step live including prompts and artifacts.

Role separation is the second design choice worth reading carefully. The agent that writes production code cannot modify tests, and the agent that writes tests cannot modify implementation — the framework treats the boundary as a contract enforced by the conductor rather than by prompt hygiene. Workflows split into a spec-first design lane, where requirements are agreed and frozen before coding begins, and a build lane that runs the red/green/refactor loop against live database branches. Human approval gates are built into the conductor rather than left to convention, and the write-up describes scoped context packages that prevent agents from drifting by giving each one only the requirements it needs.

The wider read is that Databricks is using Consort as a demonstration of what Lakebase branching enables rather than shipping it as a platform product. The onboarding is deliberately lightweight — three commands starting with a StockFlow example project — and there is no SLA. For teams already on Lakebase, this is a low-risk way to try branching in an actual development loop; for everyone else it is a design pattern worth reading before writing your own agent framework on top of copy-on-write databases. The write-up also references an internals paper on arXiv but positions the framework itself as open to codeowner contributions.

### 🎯 Takeaway (Hợp)
If you already run Lakebase, clone the Consort StockFlow example this sprint and put one migration through the agentic loop against a live branch — the point is to feel the branching latency, not to adopt the framework wholesale. Nếu team bạn còn dùng mock DB cho unit test, đây là mô hình đáng đọc trước khi tự viết framework tương tự trên Postgres copy-on-write.


## 3. Lakebase Postgres Swaps LFC for 75 Percent Shared Buffers and Huge Pages, Reports up to 2x Throughput

| Field | Value |
|---|---|
| 📅 Date | 10/09/2026 |
| 🏷️ Topic | Research |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `lakebase-postgres` · `shared-buffers` · `huge-pages` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
Databricks detailed on 10 September 2026 how it lifted Lakebase Postgres shared buffers from a conservative 1 GB cap to 75% of DRAM on fixed-size compute nodes at 80 CU and above, retired the Local File Cache (LFC) intermediate layer, and enabled 2 MB HugeTLB pages across the virtualised infrastructure. Three production endpoints saw 1.3× to 2× throughput improvements, one saw storage GetPage reads drop 5× from ~8K to ~1.5K per second, and huge pages alone shaved tail read latency by up to 40% and CPU by up to 30%. The change is live now on fixed 80 CU+ Lakebase computes; dynamic shared buffers for autoscaling computes are the follow-up in progress.

### 🔬 Details (Phân)
Historically Lakebase Postgres was capped at a conservative 1 GB `shared_buffers` and leaned on the OS page cache plus a Local File Cache tier on local NVMe. That combination double-buffered every hot page — once in shared buffers, once in the kernel — and paid translation cost on every random access. The rewrite sizes shared buffers to 75% of DRAM on a fixed-size compute, drops the OS-page-cache dependency so the memory is used exactly once, and enables 2 MB HugeTLB pages across the virtualised host so the CPU's TLB stops thrashing on hot working sets. Users can confirm the new setting with `SHOW shared_buffers` and expect `20971520` (in 8 KB pages, i.e. ~160 GB) on an 80 CU node.

The production numbers are the interesting part because Databricks published them per-endpoint. Endpoint 1 hit roughly 2× throughput and cut storage GetPage reads 5× — from about 8K to 1.5K per second — because the resident working set now stays in RAM. Endpoint 2 saw 1.3× throughput at near-100% cache hit rates, i.e. the working set already fit but huge pages and single-buffering removed translation and copy overhead. Endpoint 3 is the most striking: the customer cut compute from 20 to 4 cores while still gaining 2× throughput, a 5× CPU efficiency win driven by huge pages plus the removal of double buffering. Databricks calls out that huge pages alone (holding cache size constant) reduced tail read latency up to ~40% and CPU up to ~30%.

The wider read is that Lakebase is quietly closing the "managed Postgres" gap against RDS/Aurora on cache tuning, where the hyperscalers still tend to ship conservative defaults. The trade-offs are real: 75% shared buffers assumes a workload that benefits from a large cache, and huge pages exchange finer memory granularity for TLB efficiency, both of which can hurt small OLTP hot paths that need many small allocations. Databricks flags dynamic shared buffers on autoscaling computes as still in development and promises a follow-up post; teams on autoscaled Lakebase should time their migration to that release, not this one.

### 🎯 Takeaway (Hợp)
If you run Lakebase on an 80 CU or larger fixed compute, run `SHOW shared_buffers` this week to confirm the new value and re-baseline latency dashboards — the change is silent from the SQL side. Nếu workload của bạn là read-heavy với working set lớn, đây là cải thiện gần như "free" xứng đáng kiểm chứng ngay.

### 💡 Example
```sql
-- Quickly verify the new shared_buffers value on an 80 CU+ Lakebase compute.
-- Expect roughly 20971520 (in 8 KB pages, i.e. ~160 GB), not 131072 (1 GB).

SHOW shared_buffers;   -- e.g. 20971520

-- Confirm huge pages are in play. huge_pages should read 'on'
-- (not 'try') on the new configuration.
SHOW huge_pages;

-- Re-baseline the cache-hit rate for your hot tables. GetPage/s
-- against distributed storage should drop after the switch.
SELECT relname,
       heap_blks_read,
       heap_blks_hit,
       heap_blks_hit::float
         / NULLIF(heap_blks_hit + heap_blks_read, 0) AS hit_ratio
FROM pg_statio_user_tables
ORDER BY heap_blks_read DESC
LIMIT 10;
```

### 🔭 Overview (Tổng)
Espressif published a compliance walkthrough on 9 September 2026 covering the EU Cyber Resilience Act's vulnerability reporting obligations, which take effect on 11 September 2026 — today in Perth time. From that date, any manufacturer placing a connected product on the EU market is required to notify their national CSIRT and ENISA within 24 hours of confirming an actively exploited vulnerability, with a follow-up within 14 days of a fix. The rules apply retroactively to products already on shelves, and the "manufacturer" is whoever puts a product on market under their own brand — which pulls white-label and rebranded IoT into the same net.

### 🔬 Details (Phân)
The Article 14 timeline the post spells out has two firing dates. From 11 September 2026 the reporting duty applies to all in-scope products already on the EU market, regardless of when they were sold. From 11 December 2027 the full CRA applies — essential cybersecurity requirements, conformity assessment and CE marking on new units. What must be reported today is narrow: actively exploited vulnerabilities where there is evidence of malicious use, and severe incidents that affect product security through data harm or malicious code introduction. Good-faith security research findings and published proof-of-concept code without evidence of real exploitation are explicitly excluded per Recital 68 — the 24-hour clock does not start on a Twitter PoC.

Mechanically, all notifications go through the ENISA Single Reporting Platform via a registered Assigned Representative with an EU Login account and two-factor authentication; API access is deferred beyond the initial launch, so the near-term flow is a web form and coordinator CSIRT distribution to affected Member States. Espressif's own support structure is the interesting bit for anyone shipping ESP32 designs: per-product security advisories you can subscribe to, an ESP-IDF Security Dashboard that maps CVEs to specific ESP-IDF releases daily and covers bundled components as well as Espressif's own code, and the `esp-idf-sbom` tool that generates SPDX bills of materials and cross-checks them against NVD data. Espressif also flags a dedicated Vulnerability Reporting Portal launching at the end of September to automate tracking.

The post is emphatic that CRA compliance is a property of the finished product, not a chip or an SDK. Espressif is responsible for the ESP32 hardware, ESP-IDF and its bundled components; the product manufacturer owns the application, cloud services and companion app; other component vendors — secure elements, cellular modules — own theirs. That layered model is important because it means the manufacturer cannot outsource the reporting duty to Espressif for the parts of the stack Espressif owns. Under the CRA, one entity must file to ENISA per product, and that entity is the brand on the label. IoT teams should treat the ESP-IDF Security Dashboard and `esp-idf-sbom` as inputs to their own SBOM and reporting pipeline, not as substitutes for it.

### 🎯 Takeaway (Hợp)
If you ship any Wi-Fi or BLE product into the EU, this week is the deadline to designate an Assigned Representative, register with the ENISA SRP, and stand up an SBOM pipeline that combines your own code with Espressif's dashboard output. Nếu bạn chưa bao giờ dựng SBOM cho firmware, `esp-idf-sbom` cùng với danh sách advisory theo sản phẩm là điểm khởi đầu tối thiểu.

### 💡 Example
```bash

# against NVD. Combined with per-product advisories, this is the
# minimum viable input to a CRA reporting workflow.

# 1. Configure the project as usual.
idf.py set-target esp32c5
idf.py reconfigure

# 2. Generate an SPDX SBOM covering Espressif code and bundled
#    components (mbedTLS, lwIP, wolfSSL, etc).
esp-idf-sbom create --format spdx-json \
                    --output   sbom.spdx.json \
                    build/project.map

# 3. Check the SBOM against the NVD for known CVEs. Feed the
#    results into your CSIRT/ENISA reporting pipeline.
esp-idf-sbom check --input sbom.spdx.json \
                   --db nvd \
                   --exit-code-on-vulnerability
```
