## 1. Iceberg Materialized Views Go GA on Amazon EMR, Glue and Athena with Automatic Query Rewrite

| Field | Value |

### 🔭 Overview (Tổng)
AWS declared Iceberg materialized views generally available for Spark on 10 September 2026, across Amazon EMR 7.12.0+, AWS Glue 5.1+ and Amazon Athena's optimized Spark runtime, together with an automatic-query-rewrite optimizer that transparently substitutes materialized-view scans for matching subtrees of the query plan. The rewrite path is opt-in via a single Spark configuration flag and does not require SQL changes on the application side, which puts a real answer behind a question that has hung over the Spark-on-Iceberg stack since 2024: how do multi-TB dashboards get sub-second responses without a Trino or Snowflake sidecar. Base-table freshness is tracked through Iceberg snapshot IDs, so a stale MV is skipped rather than served, and refresh is scheduled through the AWS Glue Data Catalog. The benchmark numbers are prescriptive rather than illustrative — AWS ran TPC-DS 3TB and published per-design speedups.

### 🔬 Details (Phân)
The optimizer applies two rewrite strategies. Structural rewrite handles queries dominated by aggregations and inner joins by rolling up the pre-computed aggregate stored in the MV and applying residual filter predicates against the base table; the write-up puts this design at ~5× speedup for a single-table aggregate MV sized at 0.07% of source, and ~10× for a pre-joined and pre-filtered MV at 0.04% of source. Exact-match rewrite is the second strategy: it canonicalises the MV body and matches it against the shape of the incoming query plan, which lets it kick in for window functions and other patterns structural rewrite cannot decompose. The exact-match case hits 20× or more speedup for a query whose result set is effectively cached in an MV of ~100 rows — the number is unremarkable in isolation but proves the rewrite catches shapes the classic aggregate-only path misses.

Turning it on is a single Spark conf: `spark.sql.optimizer.answerQueriesWithMVs.enabled=true`, plus two additional flags — `spark.sql.materializedView.v1SourceTables.enabled` and `spark.sql.materializedView.v1ETagVersioning.enabled` — for Parquet base tables that are not yet Iceberg. That last knob matters for teams mid-migration: it lets you build an Iceberg MV on top of a Parquet source table and still enjoy automatic rewrite while the base is being converted. Refresh runs on a schedule the catalog manages; snapshot-id checks are how the optimizer decides whether the MV is fresh enough to substitute.

The wider read is that this closes the last big performance gap between Spark-on-Iceberg and the warehouse engines that ship MVs natively — Snowflake, BigQuery and Databricks Photon among them. It also raises the value of storing curated marts as Iceberg tables rather than as engine-specific structures, because the rewrite is now defined at the table format layer rather than at the engine layer. The caveats worth watching are the usual MV traps: refresh cost during batch loads, plan-cache invalidation when an MV is added, and the fact that structural rewrite does not currently handle outer joins or non-additive aggregates, so a materialised outer-join view still requires exact match to be rewritten.

### 🎯 Takeaway (Hợp)
If you already run Spark on Iceberg at EMR 7.12+ or Glue 5.1+, benchmark one heavy dashboard query with an MV this sprint — the config flag is the whole opt-in, and the 5–20× speedup range is testable in a single afternoon. Nếu team đang dùng Redshift hoặc Trino cho lớp BI phía trên Iceberg, đây là lý do đầu tiên đáng cân nhắc rút phần đó về Spark.

### 💡 Example
```sql
-- Enable automatic query rewrite for Iceberg materialized views
-- on EMR 7.12.0+/Glue 5.1+/Athena Spark runtime.
SET spark.sql.optimizer.answerQueriesWithMVs.enabled = true;

-- For Parquet base tables during Iceberg migration, opt in explicitly.
SET spark.sql.materializedView.v1SourceTables.enabled = true;
SET spark.sql.materializedView.v1ETagVersioning.enabled = true;

-- Create a pre-aggregated, pre-filtered MV on an Iceberg table.
CREATE MATERIALIZED VIEW sales_daily_us
AS
SELECT   order_date, product_id, SUM(net_amount) AS revenue
FROM     glue_catalog.sales.orders_iceberg
WHERE    country = 'US'
GROUP BY order_date, product_id;

-- The user query is unchanged; the optimizer rewrites the plan
-- to scan sales_daily_us and skip the raw orders table.
SELECT product_id, SUM(revenue)
FROM   glue_catalog.sales.orders_iceberg
WHERE  country = 'US' AND order_date >= DATE '2026-09-01'
GROUP  BY product_id
ORDER  BY 2 DESC
LIMIT  10;
```

### 🔭 Overview (Tổng)
Confluent published a design write-up on 10 September 2026 describing an agentic security operations centre built on top of Apache Kafka, Confluent Cloud for Apache Flink and its Real-Time Context Engine. The architecture treats security alerts as a continuous stream: a central triage coordinator routes them, a set of specialised evidence agents (endpoint forensics, cloud audit trails, and a network domain) collect the artefacts a human analyst would normally pull manually, and an adversarial evaluator agent challenges each conclusion before it is escalated. Over a 30-day production window the pipeline processed 4,700 alerts with roughly 5% escalation rate and identified more than 250 true positives, of which only about 3% ended up on the on-call queue.

### 🔬 Details (Phân)
The mechanical core is Flink used as a deterministic router rather than a policy engine. High-volume, low-context filtering — duplicate suppression, correlation with prior alerts, first-pass severity — lives in Flink SQL because it must run at line rate on every event; the LLM-shaped work sits behind that fan-in, driven by the Real-Time Context Engine which enriches each surviving alert with live telemetry and historical case knowledge before the triage coordinator dispatches it. That split matters: the Flink layer keeps the p99 latency of the pipeline bounded, and the agent layer never touches events the deterministic side has already resolved. The self-learning knowledge base is a hybrid vector-plus-keyword store built over past investigations, and both retrievals are performed inside the agent step rather than as a pre-processing pass.

The adversarial evaluator is the design choice worth studying. Rather than let the triage coordinator alone decide whether an alert escalates, a separate agent is instructed to argue against the coordinator's classification using the same evidence, and the escalation decision is taken only when the challenge fails. This is a concrete instantiation of the "verifier is easier than solver" pattern applied to alert routing, and it is the reason the 3% on-call rate is credible rather than optimistic — the failure mode of a single-agent SOC is confident false positives, which is exactly what an adversarial reader is set up to catch. The write-up is careful to note that no reference architecture or open-source code is being released; the value is in the mechanism, not a template.

The wider read is that streaming security is quietly becoming the second flagship workload for Kafka + Flink after real-time analytics, and the shape of an agentic SOC — deterministic router, specialist collectors, adversarial verifier — is stabilising across vendors. The trade-offs are familiar: institutional-knowledge quality dictates whether the knowledge base is a moat or a liability, and the adversarial agent is easy to under-prompt into agreement bias. For teams building on Confluent Cloud, the useful new capability is the Real-Time Context Engine's ability to serve live telemetry to the agents, which was the missing link between Kafka-as-transport and LLM-as-analyst designs.

### 🎯 Takeaway (Hợp)
If you run Kafka for security telemetry today, this design is worth reading before you commit to another year of a rules-only Sigma pipeline — the Flink triage layer plus an adversarial evaluator is a small change that materially lowers analyst load. Nếu team bạn đang cân nhắc LangGraph hoặc Autogen cho SOC, hãy đặt câu hỏi cụ thể: verifier có tách khỏi solver hay không.

### 💡 Example
```sql
-- Sketch of the deterministic Flink layer that fronts an agentic SOC.
-- Duplicate suppression and severity boosting run at line rate on Kafka;
-- only the surviving alerts reach the LLM triage agent downstream.

CREATE TEMPORARY VIEW hot_alerts AS
SELECT alert_id,
       tenant_id,
       source,
       severity,
       fingerprint,           -- stable hash of subject+kind+entity
       event_ts
FROM   TABLE(
         TUMBLE(TABLE raw_alerts, DESCRIPTOR(event_ts), INTERVAL '1' MINUTE)
       )
WHERE  severity >= 3;

-- Suppress duplicates within a 15-minute window, boost severity when
-- the same fingerprint fires 5+ times, drop the rest.
INSERT INTO triage_queue
SELECT window_start,
       fingerprint,
       ANY_VALUE(alert_id)                       AS lead_alert_id,
       COUNT(*)                                  AS burst,
       MAX(severity) + IF(COUNT(*) >= 5, 1, 0)   AS boosted_severity
FROM   TABLE(
         HOP(TABLE hot_alerts, DESCRIPTOR(event_ts),
             INTERVAL '1' MINUTE, INTERVAL '15' MINUTE)
       )
GROUP  BY window_start, fingerprint;
```

### 🔭 Overview (Tổng)
Espressif shipped ESP-IDF v5.2.8 on 11 September 2026 as the final bugfix release of the v5.2 branch, closing it out at end-of-life and rolling in four upstream NimBLE CVEs (CVE-2026-45811, CVE-2026-45815, CVE-2026-45816 and CVE-2026-46452) together with a decision that changes the trust model on three chips: ECDSA Secure Boot V2 is now disabled by default on ESP32-H2, ESP32-C5 and ESP32-P4 because of a vulnerability in the ECDSA-based Secure Boot flow documented in the chip errata. The recommended migration target is ESP-IDF v6.0.3, and the release itself is available via the ESP-IDF Installation Manager, git, and packaged archives. For a team that has been sitting on v5.2 to avoid the churn of the v5.3/v5.4/v6 chain, this release is the last stop.

### 🔬 Details (Phân)
The NimBLE CVEs come from upstream Apache NimBLE and land as a single sync of the bundled Bluetooth stack; Espressif's write-up positions them as covering both classic BLE and the new NimBLE-based mesh path. Beyond the four numbered advisories, v5.2.8 also rolls in the routine set of stability fixes that a terminal bugfix release usually carries. The more consequential change is the Secure Boot V2 update. ECDSA-signed Secure Boot on ESP32-H2, ESP32-C5 and ESP32-P4 is now disabled unless a project explicitly opts back in through Kconfig, and the chip errata that motivates the change is public. Existing devices in the field that provisioned ECDSA keys are not silently bricked — the enforcement change is a build-time default, not a hardware fuse flip — but new firmware images should be rebuilt with RSA-3072 or the recommended alternative before shipping.

The branch context matters. Espressif's ESP-IDF support policy runs each release train for roughly 2.5 years, and v5.2 was released in early 2024, so this EOL is on schedule rather than a surprise; the practical implication is that any CVE that appears against ESP-IDF v5.2 after today has no fix and forces an upgrade. Users on the v5.5 branch continue to receive fixes (the most recent v5.5.5 landed 17 July 2026), and the v6.0.3 branch is the modern default carrying the DMA2D colour-conversion driver and ISP-from-memory support. The intermediate v5.3 and v5.4 branches are already EOL, so the practical migration path for anyone stuck on v5.2 today is either forward to v5.5 (minimum churn) or to v6.0.3 (best long-term support).

The wider read is that Espressif is tightening its Secure Boot story ahead of the EU CRA CE-marking deadline in December 2027, and the ECDSA disable is consistent with that direction: RSA-3072 is what the CRA-aligned production advice defaults to, and the ECDSA errata was the last technical reason to keep it on. For anyone shipping a product using an ESP32-H2, ESP32-C5 or ESP32-P4 into the EU, this release week is the natural moment to re-run the Secure Boot provisioning path and confirm the production firmware is not still pinned to ECDSA in the build configuration.

### 🎯 Takeaway (Hợp)
If you have a fleet on ESP-IDF v5.2, plan the jump to v5.5 or v6.0.3 this quarter, and audit any ESP32-H2, C5 or P4 device for an ECDSA Secure Boot V2 configuration before your next firmware build. Nếu bạn chưa từng review Kconfig Secure Boot, đây là dịp bắt buộc phải làm cùng với việc cập nhật NimBLE.

### 🔭 Overview (Tổng)
Amlogic unveiled the A123X and C305X2 on 11 September 2026, becoming the first silicon vendor to ship Cortex-A320 SoCs to sampling. Both parts are built on TSMC 6 nm and target AIoT — the A123X is a quad-core industrial-vision chip for dashcams, robots and access control; the C305X2 is a dual-core, battery-optimised part for solar doorbells, hunting cameras and IP cameras. Cortex-A320 is Arm's Armv9.2-A profile core designed for edge AI, adding SVE2 vector extensions on top of the Armv8-A Cortex-A55 baseline and, in Arm's own numbers, delivering a 34% SPECint2007 uplift over Cortex-A35 and a 10× ML uplift over its predecessor. Both parts are sampling now with production scheduled for Q4 2026.

### 🔬 Details (Phân)
The A123X pairs its quad-core CPU with a two-tier NPU: 4 TOPS ADLA2 for AI-ISP work plus 8 TOPS ADLA3 that is explicitly transformer-capable, and it drives H.264/H.265 video at 4K@60fps encode and 4K@30fps decode with a low-light HDR AI-ISP at 4K@30fps. Memory is a 32-bit LPDDR4/4X/5 interface running up to 6400 Mbps, and I/O covers Gigabit Ethernet, USB 3.0 OTG, USB 2.0 host, two 4-lane MIPI CSI, an 8-lane Sub-LVDS interface, and 2× CAN FD — the sub-LVDS lane count in particular signals that the target is machine-vision cameras with wide sensors, not phones. The C305X2 halves the CPU to dual-core, drops the sub-LVDS to save package pins, and slows the memory to LPDDR4/4X/5 at 4266 Mbps, but keeps the 8 TOPS ADLA3; it also introduces an always-on video path plus pre-roll modes and a neural SED (smart event detection) engine for the battery-camera use case where the SoC needs to wake, classify and record without ever hitting the LPDDR full-power state.

Cortex-A320 as a core is the interesting piece. Arm markets it as the smallest Armv9.2-A design point, and the SVE2 vector extensions are what unlock the 10× ML uplift over Cortex-A55: quantised int8 tensor kernels compile into much wider SIMD than NEON allowed, which reduces the pressure on the paired NPU for small models and lets the CPU handle inference bursts without lighting up the AI subsystem. Combined with MTE (memory tagging) and pointer authentication, it is also the first mainstream edge core where a modern security posture — Rust in userspace, MTE-checked memory in production — is compilable out of the box. On 6 nm rather than 12 nm, the process node is what makes the low-power side of the C305X2 credible; Amlogic's earlier A311D2 was 12 nm and had a very different battery-life story.

The wider read is that the Amlogic parts land into a market that was, until this month, dominated by Rockchip's RK3588 family (Cortex-A76/A55, 8 nm) at the top and RK3576/RK3568 in the middle. Cortex-A320 skips the A76 and goes straight to the Armv9.2-A profile at the low end, which is the same architectural jump the phone market made two years ago. Software support is described as Linux with reference designs and pre-validated OS stacks; MediaTek, Rockchip and Qualcomm have not yet announced Cortex-A320 parts, so Amlogic has a real first-mover window from sampling to Q4 production, and OEM designs that value MTE plus ADLA3 for on-device transformer inference will find the A123X the earliest concrete option.

### 🎯 Takeaway (Hợp)
Track the A123X for any AIoT design that needs 4K@60fps H.265 encode plus an on-die transformer NPU under 5 W, and the C305X2 for a battery-camera reference; both are worth the design-in evaluation ahead of RK3576's on-shelf inventory. Nếu team đang gắn với Cortex-A55, đây là điểm chuyển sang Armv9.2-A đầu tiên đáng thử.

// Sketch of a quantised int8 MobileNet kernel enabled for
// Cortex-A320's SVE2 path via ACLE. On the A123X's quad core,
// SVE2 gives the CPU a real role for small-batch inference
// instead of always offloading to the 8 TOPS ADLA3 NPU.
//
// Build:  clang -march=armv9.2-a+sve2 -O3 -o mn mn.c

#include <arm_sve.h>
#include <stdint.h>

void mm_int8_sve2(const int8_t *a, const int8_t *b,
                  int32_t *c, int m, int n, int k) {
    for (int i = 0; i < m; i++) {
        for (int j = 0; j < n; j += svcntb()) {
            svbool_t pg = svwhilelt_b8(j, n);
