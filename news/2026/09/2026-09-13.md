### 🔭 Overview (Tổng)
AWS released AWS Glue 6.0 on 9 September 2026 with Spark Declarative Pipelines (SDP) as the headline feature — Spark's native declarative pipeline framework, brought to Glue with automatic dependency resolution, dry-run validation, and selective refresh scopes. The runtime is Apache Spark 4.1, and AWS is pricing Glue 6.0 at 30% below Glue 5.1 on the same worker type. That combination — a declarative authoring model plus a materially cheaper runtime — is what makes 6.0 more than an incremental release: it is the first Glue major version that lets a team describe an ETL DAG in Python or SQL and hand refresh sequencing to Glue rather than orchestrating steps in Airflow or Step Functions.

### 🔬 Details (Phân)
A pipeline is authored as a set of dataset functions decorated with `@dp.table`, `@dp.materialized_view` or `@dp.temporary_view`, and Glue derives the DAG from the reads and writes inside each function. Dependency resolution is automatic and does not require an explicit `depends_on` graph, which is the change that removes most of the boilerplate compared with a hand-orchestrated Glue 5.1 workflow. Two job arguments turn the mode on: `--enable-spark-declarative-pipeline` and `--enable-glue-datacatalog`. Execution mode is `VALIDATE` for a dry run that resolves the DAG and type-checks SQL without materialising data, or the default `RUN`. Selective refresh is exposed as three flags: `--refresh` for an incremental default, `--full-refresh` for one table and its dependents, and `--full-refresh-all` for a rebuild of every managed table in the pipeline.

The pricing change is the second lever. AWS lists Glue 6.0 at 30% below Glue 5.1 on the same G.1X worker (2 DPUs is the reference in the blog), which puts the effective cost of a declarative Glue pipeline below the equivalent Spark-on-EMR job in the tens-of-minutes duration band Glue is designed for. Spark 4.1 as the runtime brings the current Iceberg 1.11 connector on by default and the recent Spark ANSI-SQL semantics that landed in 4.0, so migration from a 5.1 pipeline is not only a version bump for teams that were already on ANSI mode.

The wider read is that declarative ETL as a runtime feature has moved from a Delta-Live-Tables-only story into the open Spark stack, and Glue 6.0 is the first serverless carrier of it at AWS scale. Migration itself is a version pin, but the value only unlocks when jobs are refactored into `@dp.table` functions — an operator-first mental model still needs some Glue plumbing (IAM, catalog binding) around it.

### 🎯 Takeaway (Hợp)
If your team runs Glue 5.1 for periodic ETL today, refactor one pipeline into SDP this sprint to feel the authoring difference; the 30% price drop alone is enough to re-open the migration budget conversation. Nếu team đang cân nhắc DLT hoặc Airflow-only orchestration, đây là dịp phải đặt lại câu hỏi lựa chọn.

### 💡 Example
```python
# Declare a Spark Declarative Pipeline for AWS Glue 6.0.
# Submit the job with:
#   --enable-spark-declarative-pipeline
#   --enable-glue-datacatalog
#   --execution VALIDATE      # dry-run, no data written
#   --refresh                 # incremental refresh (default)
import glue.declarative as dp

@dp.materialized_view
def clean_orders():
    return (spark.readStream
                 .table("bronze.orders")
                 .filter("status IN ('paid','shipped')"))

@dp.table
def daily_revenue():
    return (dp.read("clean_orders")
              .groupBy("order_date")
              .agg({"net_amount": "sum"}))
```

## 2. Databricks Rebuilds the Lakebase Postgres Cache Around Huge Pages and 75% Shared Buffers

### 🔭 Overview (Tổng)
Databricks published a deep write-up on Lakebase — its serverless Postgres offering — on 10 September 2026 that details a rework of the compute-layer caching stack. Two mechanical changes underpin the numbers in the post: `shared_buffers` is now sized to roughly 75% of the endpoint's DRAM on any fixed compute of 80 CU or larger, and 2 MB huge pages replace the default 4 KB pages fleet-wide. Reported gains include roughly 2× throughput and 5× fewer reads from Databricks' shared page store on one large customer endpoint, 1.3× throughput on a second, and 5× lower CPU with 2× higher throughput on a third; the huge-page change on its own cuts tail read latency by up to ~40% and drops CPU utilisation by up to ~30%.

### 🔬 Details (Phân)
The prior architecture used a two-tier cache: an in-memory `shared_buffers` pool sized conservatively at the historical Postgres rule of thumb of ~25% of RAM, plus a Local File Cache (LFC) on NVMe that acted as an L2 in front of the shared page store. That design assumes cheap NVMe and expensive RAM, which is upside-down for a serverless Postgres running on modern instance types where tens of GB of DRAM is cheaper per operation than a block-storage round-trip. The rework flips both knobs at once: `shared_buffers` climbs to ~75% of DRAM (an 80 CU fixed-compute endpoint reports `shared_buffers = 15278640` in 8 KB pages, roughly 117 GB), and `huge_pages` is forced on so the TLB miss rate on the enlarged buffer pool does not undo the win. LFC is being deprecated because the raised `shared_buffers` absorbs the working set for essentially every observed customer profile.

The post is direct about the trade. A small endpoint below 80 CU does not receive the 75% resize because Postgres backend overheads at low CU make that fraction too aggressive; Databricks tunes those brackets separately. The huge-page config is orthogonal — it applies across the fleet and can be inspected in a live session with `SHOW huge_pages` and `SHOW shared_buffers`. Storage-side, GetPage/s dropped from about 8,000/s to about 1,500/s on the large-endpoint benchmark, which is what makes the throughput and latency numbers explainable rather than heroic: fewer storage round-trips mean the endpoint spends more of its CPU budget on query execution instead of on page faults.

The wider read is that Lakebase is being tuned like a purpose-built OLTP-plus-analytics runtime rather than as a lift-and-shift Postgres, and the choices — bigger buffer pool, huge pages, LFC removal — track what large Postgres shops (Aurora, Cloud SQL, AlloyDB) have converged on over the last three years. For teams that adopted Lakebase in the last quarter, the practical implication is that reserved-compute sizing should be re-costed: the cache is now sized to the endpoint automatically, which changes the "what CU should I pick" question, and any manual `shared_buffers` override from a v1 setup should be removed.

### 🎯 Takeaway (Hợp)
If you run a Lakebase endpoint at 80 CU or above, check `SHOW huge_pages` and `SHOW shared_buffers` after the next maintenance window and drop any manual buffer-pool overrides — the defaults now do the right thing. Nếu bạn đang dựa vào LFC làm L2, đó là dấu hiệu phải re-benchmark trước khi nghĩ đến việc tăng CU.

## 3. Databricks and the Iceberg Community Propose Read Restrictions and Catalog Labels for Cross-Catalog Governance

### 🔭 Overview (Tổng)
On 10 September 2026, Databricks published a governance write-up proposing two additions to the Apache Iceberg specification: Read Restrictions, a contract that lets a catalog delegate enforcement of column projections and row filters to a trusted engine, and Catalog Labels, a lightweight key-value metadata exchange between catalogs at the table and column level. The two pieces address different failures of the current model — Read Restrictions solves the "engine has to re-derive policy" problem, while Catalog Labels solves the "each catalog re-classifies the same column" problem — and together they line up Iceberg to be the neutral interoperability layer between Unity Catalog, Snowflake, AWS Lake Formation and Google Cloud Knowledge Catalog rather than a table format that each catalog wraps in its own governance layer.

### 🔬 Details (Phân)
Read Restrictions is a specification-level change. A catalog issuing a table-load response returns, alongside the usual snapshot metadata, a set of column-projection actions (mask this column with a hash, drop this column) and row-filter expressions in a canonical form the engine must evaluate before returning rows to the user. Spark, DuckDB and Trino are the named reference engines. The point is that enforcement happens once, at the engine, and the catalog does not have to sit in the data path for every query. The failure mode this closes is well-known: engines that "trust the catalog" today are running with best-effort policy translation, which is why cross-engine governance answers today are usually a Trino-plus-Ranger sidecar or an Immuta layer rather than a native Iceberg contract.

Catalog Labels is the second piece and does not touch the data path. A source catalog exposes labels as `{name, value}` pairs at table and column level; a consuming catalog reads those labels and maps them into its own tag or classification model. In practical terms, a Unity Catalog table exposed through Iceberg can carry its `pii = true` classification into a Snowflake tag-based masking policy without a synchronisation job, and a Lake Formation permission grant can enrich a Google Cloud Knowledge Catalog view. The write-up is careful to frame Catalog Labels as a metadata exchange rather than an enforcement contract — labels are read once by the consuming catalog and translated, not evaluated per query — so the two proposals compose without stepping on each other's semantics.

The wider read is that the pattern of the last twelve months has been every warehouse vendor claiming "Iceberg-first" and then re-implementing governance in its own catalog. Read Restrictions and Catalog Labels are Databricks making the case that the interop layer should live in Iceberg itself, at a moment when Snowflake Polaris, AWS Lake Formation and Unity Catalog are all shipping REST-catalog implementations. Adoption is not automatic — the specs need to land through the ASF's normal process — but the technical shape is small enough that Trino and DuckDB implementations are plausible in-tree by end of 2026. The blast radius for teams already federating Iceberg across two catalogs is meaningful: cross-catalog tag sync jobs become spec-defined behaviour rather than glue code.

### 🎯 Takeaway (Hợp)
If your stack already federates Iceberg across two catalogs (say Unity Catalog plus Snowflake, or Lake Formation plus Polaris), track the Iceberg PRs for Read Restrictions and Catalog Labels this month — the proposal shape decides whether cross-catalog governance stops being a synchronisation problem. Nếu team đang viết ETL đồng bộ tag giữa các catalog, hãy tạm hoãn cho tới khi thấy PR chính thức hạ cánh vào spec.

```yaml
#    The engine must apply these before returning rows to the user.

    - column: email
      action: mask_hash         # engine hashes the column before return
    - column: ssn
      action: drop
  row_filter:
    dialect: iceberg-sql
    expression: "region = current_user_region()"

# 2. Catalog Labels attached at table and column level.
#    A consuming catalog reads these once and maps them into
#    its native tag/classification model.
labels:
  table:
    - {name: pii,       value: "true"}
    - {name: retention, value: "P365D"}
  columns:
    email:
      - {name: pii,     value: "true"}
      - {name: masking, value: "hash"}
```

### 🔭 Overview (Tổng)
On 11 September 2026 the mandatory reporting obligations of Article 14 of the EU Cyber Resilience Act took effect for manufacturers of connected products placed on the EU market, and Raspberry Pi published a walkthrough of the resulting timelines the same day. Two categories now trigger notification to ENISA: actively-exploited vulnerabilities and severe incidents. Each carries a three-step cascade of deadlines, the first of which is a 24-hour early warning. The full CRA — CE marking of connected products, essential-requirements documentation, secure-by-default configuration — has its compliance date on 11 December 2027; Article 14 was pulled forward so the incident-reporting rail is operational well before the CE marking sweep.

### 🔬 Details (Phân)
For an actively-exploited vulnerability, a manufacturer must issue an early warning to ENISA within 24 hours of becoming aware; a follow-up notification within 72 hours giving the nature of the exploit and mitigation status; and a final report within 14 days assessing severity and detailing corrective measures. For a severe incident affecting the security of the product, the deadlines shift to a 24-hour early warning stating whether the incident is suspected to result from unlawful or malicious acts, a 72-hour follow-up with detail on the incident, and a final report within one month. The two workflows are logically distinct — a vulnerability is a defect discovered before or after exploitation; an incident is a compromise event — and a single occurrence can generate both notifications on parallel clocks.

Practically, the 24-hour window is what changes the operations posture. Vulnerability triage that today runs on a weekly cadence at most IoT vendors has to move to a permanent on-call rota with a documented ENISA contact and a filing template that can be produced in under a day, in the two working languages the vendor commits to. Raspberry Pi's post is written for its component-integrator customers and points them at the company's Product Information Portal for firmware advisories and security contacts, but the shape of the obligation applies equally to any manufacturer shipping an ESP32-, STM32- or i.MX-based product into the EU. The white paper referenced from the post covers the mapping between existing PSIRT workflows and the ENISA notification format.

The wider read is that this is the point at which CRA becomes operational for engineering teams rather than a regulation described in slides. Vendors have 15 months from today to reach full CRA conformity, but the reporting rail is live from now, and the first product-level ENISA notifications will define how strictly the deadlines are enforced in practice. Alignment with the EU CSIRT network is the missing piece for smaller vendors — the notification path is not a webform, it is a coordinated disclosure with the national CSIRT of the member state of first placement plus ENISA, and that plumbing is what most small IoT teams have never built.

### 🎯 Takeaway (Hợp)
If your product ships into the EU and includes a network interface, spin up an ENISA notification runbook this week and identify who can sign a 24-hour warning at 3 am AWST. Nếu team chưa có PSIRT, đây là dịp bắt buộc phải chuẩn hoá kênh liên hệ với CSIRT quốc gia trước 11/12/2027.
