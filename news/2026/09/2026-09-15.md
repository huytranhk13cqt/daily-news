## 1. Databricks Ships On-Demand State Repartitioning for Structured Streaming Without Losing Checkpoints

| Field | Value |
|---|---|
| 📅 Date | 14/09/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `structured-streaming` · `rocksdb-state-store` · `checkpoint` |
| ⚡ Impact | High |

### 🔭 Overview (Tổng)
Databricks has announced Public Preview of on-demand state repartitioning for Apache Spark Structured Streaming, letting operators change the number of state-store partitions on a long-running stateful query without discarding the checkpoint. Until now, the partition count of a stateful query was frozen at the moment the checkpoint was created because keys hash into RocksDB shards by that count; any change silently corrupted state, so teams either lived with the original number forever or accepted full replays. The feature ships in Databricks Runtime 18 and is targeted at streaming jobs whose traffic grew or shrank enough that the original shard sizing is no longer efficient.

### 🔬 Details (Phân)
The mechanism introduces a dedicated Spark configuration, `spark.sql.streaming.stateStore.partitions`, which takes precedence over the general `spark.sql.shuffle.partitions` setting for stateful operators. The workflow is: stop the query, set the new partition count, restart with the same checkpoint. On restart the driver drains any pending microbatch, then performs a one-time physical redistribution of state data across the new partition count, re-hashing keys into their correct new RocksDB instances. Progress is reported through the standard `StreamingQueryProgress` event under a `controlBatch.REPARTITION` field that emits the repartition duration in milliseconds.

Prerequisites are DBR 18 or later and the RocksDB state-store provider, which has been the default since DBR 17.3, so most Databricks customers already meet the runtime baseline. Because the operation reshuffles state on disk, its cost scales with total state size rather than throughput, so shrinking a state store from a hundred million keys to fewer partitions is dominated by I/O, not compute. Databricks positions the feature against three concrete scenarios: right-sizing after growth or shrinkage, running backfills at higher partition counts before scaling down for steady state, and evaluating latency-versus-cost trade-offs against live production checkpoints instead of synthetic benchmarks.

Coveo, cited in the announcement as an early adopter, reported cutting related Amazon S3 API costs by 40% after adopting the feature, attributing the saving to no longer having to over-provision shards to hedge against future growth. The feature has no direct open-source equivalent in vanilla Apache Spark today, so it is a Databricks-only capability at launch; teams running Structured Streaming on EMR, HDInsight or self-managed clusters will need to keep to the traditional replay path for now.

### 🎯 Takeaway (Hợp)
For any team running long-lived stateful streams on Databricks, this closes one of the most painful operational gaps left in Structured Streaming; audit your current jobs, note where the partition count was chosen before a traffic shift, and plan a DBR 18 upgrade so you can repartition rather than replay. Nếu bạn đang stuck với 200 partition từ hồi 2023, đây là lần đầu bạn có thể đổi số đó mà không phải nhả state store.

### 💡 Example
```python
# Original stateful query pinned at 200 partitions when the checkpoint was created
df = spark.readStream.format("kafka").load()
(
    df.groupBy(window("timestamp", "10s"), "id").count()
      .writeStream
      .option("checkpointLocation", "/mnt/checkpoints/orders")
      .toTable("silver.orders_by_id")
)

# Months later: traffic tripled, state store ballooned, RocksDB compactions hurt.
# 1) Stop the query.
# 2) Repartition state on-demand at restart — checkpoint is reused.
spark.conf.set("spark.sql.streaming.stateStore.partitions", "400")

# 3) Start again with the same checkpoint; Spark performs a one-time repartition
#    before resuming. Watch the controlBatch.REPARTITION field in progress logs.
```

## 2. AWS Kinesis Data Streams On-Demand Advantage Adds Warm-Throughput Scale-Down to Cut Consumer Costs

| Field | Value |
|---|---|
| 📅 Date | 14/09/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `kinesis-data-streams` · `on-demand-advantage` · `warm-throughput` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
AWS has extended the warm-throughput controls on Amazon Kinesis Data Streams so that streams running in On-demand Advantage (ODA) mode can now be scaled down after a transient traffic spike, not just scaled up in anticipation of one. Under the older behaviour a spike would cause Kinesis to split shards automatically, and the elevated shard count persisted long after the burst had subsided, forcing consumers to keep paying for parallelism they no longer needed. The feature has no additional charge on top of ODA pricing.

### 🔬 Details (Phân)
The scale-down is triggered by calling `update-stream-mode` with a lower `--warm-throughput-in-mb` value. AWS applies a safeguard that the resulting capacity is the greater of the requested value and the peak ingest observed in the last hour, so the API cannot under-provision a stream that is still hot. Monitoring uses the standard Kinesis CloudWatch namespace — `IncomingBytes` and `IncomingRecords` for traffic shape, `WriteProvisionedThroughputExceeded` for post-scale-down throttling — plus polling `DescribeStreamSummary` for the open shard count, which is not published as a metric.

The consumer-side pain that motivates the feature is concrete and easy to under-count in a Lambda-heavy shop. When a stream splits from 100 to 150 shards to absorb a burst, a Lambda consumer configured with a parallelization factor of 2 goes from 200 to 300 concurrent invocations; those extra 100 invocations bill for compute for as long as the shards remain open. The same effect hits KCL consumers via more DynamoDB lease-management traffic and higher iterator-age noise. AWS positions warm-throughput scale-down as the missing complement to the July 2026 scale-up feature so ODA behaves symmetrically around a moving baseline.

Best practice from the post is to look at 24 hours of `IncomingBytes` before setting a new warm-throughput target, keep the target well above observed steady-state peaks, and then watch `WriteProvisionedThroughputExceeded` for at least a couple of hours after each reduction. The scale-down is available through the AWS CLI and the Kinesis console today; SDKs pick up the new field via the standard model updates.

### 🎯 Takeaway (Hợp)
If your Kinesis stream sits on ODA and downstream Lambda or KCL bills are noisier than your producer bill, this is a free lever — script scale-down after your known burst windows (batch loads, marketing sends, cron-driven producers) rather than leaving shards open until the next natural split. Verify the one-hour safeguard so an automation script does not repeatedly issue no-op reductions.

### 💡 Example
```bash
# 1. Inspect the current warm-throughput setting and open shard count.
aws kinesis describe-stream-summary \
  --stream-name orders-events \
  --query 'StreamDescriptionSummary.{Shards:OpenShardCount,Warm:StreamModeDetails}'

# 2. After a confirmed transient burst, request a lower warm throughput.
#    AWS applies max(requested, last-hour-peak) as the safeguard.
aws kinesis update-stream-mode \
  --stream-arn arn:aws:kinesis:ap-southeast-2:111122223333:stream/orders-events \
  --warm-throughput-in-mb 50

# 3. Watch throttling for the next hour to confirm the downstream capacity is enough.
aws cloudwatch get-metric-statistics \
  --namespace AWS/Kinesis \
  --metric-name WriteProvisionedThroughputExceeded \
  --dimensions Name=StreamName,Value=orders-events \
  --start-time  $(date -u -d '1 hour ago' +%FT%TZ) \
  --end-time    $(date -u +%FT%TZ) \
  --period 60 --statistics Sum
```

### 🔬 Details (Phân)
Pause/Resume replaces the old all-or-nothing retry model for batch jobs. A pipeline that fails after eighteen hours no longer has to restart from source; it can be resumed from a checkpoint automatically on failure, or paused manually to free accelerated compute for a higher-priority workload — a common pattern in shops that share GPU quota between feature engineering and inference. Google documents the manual path through the console and the `gcloud dataflow` CLI, with a job entering a Paused state that can be Resumed against the same checkpoint.

The RTX PRO 6000 support gives Dataflow workers 96 GB of vGPU memory and 1.6 TB/s of memory bandwidth per accelerator, enough to run 70B-parameter models in a single worker rather than sharding across cards. The GPUs plug into Dataflow's existing `RunInference` transform, Right Fitting auto-sizing and GPU-enabled autoscaling, so pipelines that already run on L4 workers pick up the new machine family by changing the worker-type flag rather than rewriting graph. That preserves the operational model — one Dataflow job, one autoscaling policy — while lifting the ceiling on model size a single worker can host.

The competitive frame is Databricks Model Serving on the DE side and Vertex AI Prediction on the AI side; Dataflow's angle is that the ingest, transform and inference stages live in one pipeline, so features and predictions ship over the same graph without a separate serving endpoint. Batch teams also benefit from Pause/Resume even when no GPU is involved, because Dataflow batch pricing bills per worker-hour and a full restart on hour 20 of a 24-hour job doubles that bill.

### 🎯 Takeaway (Hợp)

### 🔭 Overview (Tổng)
JetKVM has introduced the JetKVM Mini and Mini W, a cost-optimised redesign of the original JetKVM that swaps a Rockchip RV1106G3 Linux SoC for Espressif's ESP32-P4X microcontroller. The change drops the required external DDR and eMMC, brings the bill of materials down enough to sell the unit at USD 39 (or 42 for the wireless model), and moves the video-encoding path from a userspace pipeline to the ESP32-P4X's hardware VPU. It targets homelab and small-fleet operators who want out-of-band console access without paying for an enterprise IPMI card.

### 🔬 Details (Phân)
The Mini carries a dual-core RISC-V HP cluster at 400 MHz with an LP MCU sidecar at 40 MHz, 768 KB of L2 SRAM plus 32 MB of PSRAM, 16 MB of flash, a microSD slot and a 240×240 IPS status display. HDMI capture is 720p60 or 1080p30 native, with 4K delivery when a host-side JetKVM OS Services helper offloads the extra pipeline work; H.264 encoding is done on-chip by the VPU and streamed to the browser over WebRTC. USB is served by two Type-C ports — one 480 Mbps for control, one 12 Mbps HID emulation — and power draw is 5 V at 500 mA. The wired Mini has a 100 Mbps RJ45; the Mini W drops the RJ45 in favour of Wi-Fi 6, Bluetooth and 802.15.4 delivered by an on-board ESP32-C5 companion module.

The interesting part is not the specs but the SoC choice. Previous ESP32-P4 KVM prototypes had to convert colour spaces in software because the VPU input path did not match HDMI capture natively, adding latency and heat; JetKVM says the Mini avoids that by feeding the VPU directly, which is what makes 1080p30 usable on a microcontroller without a heatsink. Compared with the Linux-based original — same JetKVM cloud remote-access model, same web UI — the Mini gives up general-purpose scripting on the device itself (there is no shell), but keeps the WebRTC latency envelope and adds a status display.

Firmware is FreeRTOS-based on ESP-IDF, and JetKVM has committed to open-source the sources via its GitHub organisation at launch. Both models ship on 26 October 2026, with a three-pack bundle bringing per-unit price to USD 33 (Mini) or USD 36 (Mini W). Aluminium enclosure is 42×42×23 mm, which is small enough to velcro to the back of most 1U servers.

### 🎯 Takeaway (Hợp)
For homelab and small-fleet operators, the Mini is now the cheapest credible IP KVM with WebRTC and either wired or wireless management; buy the three-pack if you run more than a couple of hosts and wait for the firmware to hit GitHub before betting on custom automation. Verify HDMI EDID compatibility with your target hosts — capture-side EDID quirks are the failure mode that trips up microcontroller-class KVMs.

Software support is where HaLow deployment historically bogs down and where the release explicitly speaks to the pain: Windows and macOS are covered by shipping drivers, but Linux users need to either compile against a patched kernel with S1G (sub-1 GHz) support or run Morse Micro's OpenWrt fork with the `morse_driver` and vendor firmware from the company's GitHub. The external SMA connector and included antenna make the adapter usable straight out of the bag without matching-network work.

Positioning against the rest of the HaLow ecosystem — Silex, Newracom, Alfa — the MM8108-based product line has been the volume leader since Morse Micro's Series C, and this SKU closes the "how do I test HaLow on my laptop" gap that competitors have not filled. For teams already running the HaLowLink 2 access point, the adapter becomes the natural client evaluation kit for coverage and interference surveys before committing to embedded modules in production hardware.

## 6. Espressif Publishes EN 18031 Assessment for ESP32-C5 and ESP RainMaker Ahead of CRA Reporting Deadline

### 🔭 Overview (Tổng)
Espressif has published a formal EN 18031 case study covering an ESP32-C5-DevKitC-1 running the ESP RainMaker device-to-cloud stack. The document walks through both Part 1 (cybersecurity) and Part 2 (privacy) of the harmonised standard that gives European Radio Equipment Directive 2014/53/EU compliance a concrete technical yardstick, and it lands three days after the 11 September 2026 CRA vulnerability-reporting deadline came into force. Espressif also notes the same architecture applies to ESP32-C3 and ESP32-C6 devices, extending the reach beyond the C5 evaluation board.

### 🔬 Details (Phân)
EN 18031 splits into three parts: Part 1 for internet-connected radio equipment, Part 2 for equipment that processes personal data, and Part 3 for equipment involved in financial transactions. Espressif's document maps ESP RainMaker and the ESP32-C5 hardware feature set against the assessment methods in Parts 1 and 2. Secure Update maps to Secure Boot on-device plus signed OTA with rollback protection over HTTPS in the cloud; Secure Communication uses mutual TLS with X.509 certificates and per-device key material; Secure Storage relies on eFUSE plus Flash Encryption on the MCU and NVS Encryption for cloud credentials; Data Deletion is implemented as an account-wipe flow with OTP verification; Logging is delivered through ESP Insights for remote diagnostics.

The practical value of the paper is that it removes an ambiguity a lot of small IoT vendors have been sitting on since the mandatory-compliance date of 1 August 2025: whether the "generic MCU + custom cloud + our own OTA" story is good enough for CE marking under the RED. Espressif is effectively saying that if you ship on ESP32-C3, C5 or C6 with ESP RainMaker, the platform already implements the technical requirements listed in Part 1 and Part 2, and the remaining work is documentation, risk assessment and choosing between self-assessment and a notified body for the conformity route. That is a materially cheaper path than assembling an equivalent set of features on a bare-metal design.

Manufacturers still have to determine which parts of EN 18031 apply to their product, run a risk assessment, and produce technical documentation and a Declaration of Conformity. The CRA layer adds vulnerability reporting — actively exploited vulnerabilities within 24 hours to ENISA — on top of the RED baseline, which is where the 11 September date matters even for products already CE-marked under earlier regimes. The document does not include code samples; it is written as a compliance-mapping reference, not a hardening guide.

### 🎯 Takeaway (Hợp)
IoT vendors selling into the EU on ESP32-C3, C5 or C6 should treat this case study as a checklist template — map each row to your own implementation before your next audit rather than after. If you are on a non-ESP MCU, the same table is still useful as a gap analysis against what a compliant reference architecture actually looks like.
