## 1. Espressif Ships Zephyr Support for ESP32 in QEMU for Boardless Firmware Development

| Field | Value |
|---|---|
| 📅 Date | 15/09/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | IoT |
| 🔑 Keywords | `zephyr` · `qemu` · `esp32` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
Espressif has documented a first-party path for running Zephyr firmware on emulated ESP32 devices using the company's QEMU fork, covering ESP32, ESP32-S3, ESP32-C3 and ESP32-C6 without any physical board attached. The emulator supports both the Xtensa cores of the ESP32 and ESP32-S3 through `qemu-system-xtensa` and the RISC-V cores of the ESP32-C3 and ESP32-C6 through `qemu-system-riscv32`, so a single laptop can host CI or interactive development for every current ESP32 variant that Zephyr targets. Upstream QEMU still lacks the ESP32 SoC models, so this fork is the practical option for anyone who wants to run tests on ESP32 targets in headless containers or during pull-request checks.

### 🔬 Details (Phân)
The workflow builds on a normal Zephyr west workspace and the Zephyr SDK, plus an architecture-specific QEMU binary shipped as a pre-built tarball on the espressif/qemu GitHub releases page. After extracting the archive into `~/opt` and prepending its `qemu/bin` directory to `PATH`, `qemu-system-xtensa -machine help | grep esp32` verifies the SoC models are visible. There are two equivalent build paths: passing `-DCONFIG_ESPRESSIF_QEMU=y` to a standard `west build` against the hardware board such as `esp32_devkitc/esp32/procpu`, or using the dedicated board variant `esp32_devkitc/esp32/procpu/qemu` for a cleaner invocation. Either path ends with `west build -d <builddir> -t run`, and CTRL-A X exits QEMU cleanly.

For debug workflows the emulator supports `west build -t debugserver`, which halts the emulated CPU and opens GDB port 1234 on the host; developers then attach the architecture-specific GDB — `xtensa-espressif_esp32_zephyr-elf-gdb` for ESP32 and ESP32-S3, `riscv64-zephyr-elf-gdb` for ESP32-C3 and ESP32-C6 — with the usual `target remote :1234`, `tb main`, `c` sequence. MCUboot flows work through Zephyr sysbuild via `--sysbuild --pristine` with an explicit `--domain hello_world` selector on the run target, so signed-boot smoke tests do not need a real flash chip.

The functional envelope is deliberately narrow. Espressif calls out working coverage for `hello_world`, crypto drivers, watchdog, memory-layout tests, clock control, retained memory and interrupt handling, and explicit non-coverage for Wi-Fi, Bluetooth, the external 32 kHz XT WDT callback path and any peripheral not yet modelled. Flash images have to be padded to one of 2/4/8/16 MB, which is a common trip-up for anyone converting an existing partitioned firmware into a QEMU boot image. Compared with the alternatives — Renode's ESP32 model, which lacks Zephyr integration, and vanilla QEMU, which lacks the SoC entirely — this is now the shortest path from `zephyr/samples/hello_world` to a `west build -t run` on ESP32 targets.

### 🎯 Takeaway (Hợp)
Teams that already run Zephyr on ESP32 hardware should add a QEMU-backed CI lane for the core-and-driver subset this fork supports; the wins are deterministic runs and no hardware queue for pull-request checks. Bạn không thay được board thật khi cần Wi-Fi hoặc BLE, nhưng phần logic bên trên có thể chạy hết trong container CI.

### 💡 Example
```bash
# 1. Install the Espressif QEMU fork (Linux x86_64, Xtensa variant).
mkdir -p ~/opt && cd ~/Downloads
wget https://github.com/espressif/qemu/releases/download/esp-develop-9.2.2-20260417/qemu-xtensa-softmmu-esp_develop_9.2.2_20260417-x86_64-linux-gnu.tar.xz
tar -xf qemu-xtensa-softmmu-*.tar.xz -C ~/opt --one-top-level=qemu-xtensa-softmmu
export PATH="$HOME/opt/qemu-xtensa-softmmu/qemu/bin:$PATH"
qemu-system-xtensa -machine help | grep esp32   # sanity-check SoC list

# 2. Build hello_world for the QEMU board variant and run it, no hardware required.
west build -b esp32_devkitc/esp32/procpu/qemu zephyr/samples/hello_world \
  -d build-qemu-esp32 --no-sysbuild --pristine
west build -d build-qemu-esp32 -t run
# CTRL+A, X exits QEMU
```

### 🔭 Overview (Tổng)
Aiven, Confluent, Redpanda, StreamNative and Ververica have announced the Streamhouse Working Group, a vendor-neutral consortium formed to define an open streaming data architecture and shared vocabulary for real-time systems that feed both operational applications and AI agents. The group frames Streamhouse around three attributes: real-time updates, production-grade reliability, and decentralised deployment across databases, applications and cloud services. Governance runs through a public GitHub repository, and a Trademark Commitment lets anyone use the name Streamhouse without permission or fees, which is a deliberate contrast with the vendor-controlled Lakehouse trademarks that have complicated similar categories.

### 🔬 Details (Phân)
Streamhouse is scoped explicitly around five technology areas — change data capture, event streams, stream processing, open table formats and low-latency serving — that today live in separate ecosystems with mismatched semantics for time, keys, exactly-once delivery and schema evolution. The working group's stated goal is to produce a written definition of the architecture and its interface points rather than a new codebase; the initial announcement contains no protocol specification, timeline for a 1.0 definition, or reference implementation. Membership at launch covers the two commercial Apache Kafka forks (Confluent and Aiven), the C++ Kafka-protocol reimplementation (Redpanda), the commercial Apache Pulsar leader (StreamNative), and the commercial Apache Flink leader (Ververica), which together cover most large-scale streaming production estates outside AWS-managed services and Google Cloud Pub/Sub.

The competitive frame is Databricks' Lakehouse and Snowflake's data-cloud positioning: both use table-format-first architectures with streaming bolted on. Streamhouse instead treats the stream as the primary substrate and the table as a materialisation. That distinction matters for AI agents, where feature freshness measured in seconds — not the tens of minutes typical for Iceberg or Delta tables refreshed via batch — is the operational constraint. Absent from the announcement are guarantees about which existing standards will be absorbed (Iceberg for tables, Arrow for wire format, OpenLineage for lineage), so the working group's early output will effectively decide whether Streamhouse becomes a superset of existing open formats or a parallel category.

Adoption implications for platform teams depend on the group's first written artifact. If the initial definition merely names components already deployed — Kafka Connect for CDC, Kafka or Pulsar for event transport, Flink for processing, Iceberg for tables — the value is largely branding and interoperability testing. If it defines the semantics between those components (for example, how to represent a Flink processing job as a first-class object with a versioned schema and known upgrade rules), it becomes a serious operational reference. Either way, the working group's presence puts pressure on Databricks, Snowflake and the two major hyperscaler streaming services to declare compatibility or explicit divergence within the next quarter.

### 🎯 Takeaway (Hợp)
Data platform leads should track the Streamhouse GitHub repository for the first written definition and align internal vocabulary early — a shared term set is cheap to adopt now and expensive to retrofit after the fact. If your streaming stack already spans two of the five member vendors, the group's proposed interfaces are the ones worth vetting against your existing schemas.

## 3. Snowflake Data Connectivity Proxy Brings Openflow to Private Data Behind Deny-All-Inbound Firewalls

| Field | Value |
|---|---|
| 📅 Date | 14/09/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `snowflake-openflow` · `data-connectivity-proxy` · `mtls` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
Snowflake has released Data Connectivity Proxy (DCP), a reverse-tunnel agent that lets Snowflake Openflow ingest from private data sources — on-premises Oracle, SQL Server, PostgreSQL and MySQL, private Kafka brokers, and cross-cloud sources — without opening any inbound firewall rule in the customer network. The agent runs as a lightweight Docker container on a Linux host, opens a single outbound TLS session on port 443 to Snowflake, and receives ingest work over that tunnel. DCP is generally available on AWS, Azure and GCP for Snowflake Standard, Enterprise and Business-Critical editions.

### 🔬 Details (Phân)
The architecture inverts the classic ETL-agent model: rather than Snowflake reaching into the customer network, the agent reaches out. Bootstrap uses a one-time JWT token generated with `SYSTEM$GENERATE_DATA_CONNECTIVITY_PROXY_BOOTSTRAP_TOKEN`, valid for a configurable window (seven days in the documented example). After first use, authentication switches to mutual TLS with automated certificate rotation, so the operator never manages long-lived credentials on the agent host. Source-system credentials themselves remain in Snowflake and are never resident on the agent, and the tunnel is TCP-level pass-through with no data inspection or storage on the proxy path.

Compared with the two existing patterns for private-source connectivity — customer-managed PrivateLink for cloud-native sources, and a VPN or SSH tunnel plus a self-hosted connector for on-prem sources — DCP eliminates the network-engineering step for the on-prem path entirely. Access control lives on the Snowflake side through network rules that allowlist destinations, and revocation is a matter of disabling the DCP object, which invalidates the agent's certificate on the next handshake. That control-plane-first model is the same shape as Databricks' Serverless SQL Warehouse egress and Google Cloud's Private Service Connect, but with the operational advantage that on-prem sources need no changes at all beyond running the container.

For teams that currently pay for a commercial CDC vendor to bridge on-prem Oracle or SQL Server into a cloud warehouse, DCP is a materially cheaper substrate because it collapses the connector, the network path and the credential store into one Snowflake-native object. The trade-off is that the tunnel is Snowflake-only: the same agent cannot back a Fivetran or Airbyte connector without duplicate infrastructure, so mixed-vendor pipelines still need their own network story. Deployment is one `docker run` invocation with a credentials-file mount and the DCP client name; `DESCRIBE DATA CONNECTIVITY PROXY` on the Snowflake side reports last-heartbeat and certificate expiry for monitoring.

### 🎯 Takeaway (Hợp)
Snowflake shops with private Oracle, SQL Server or PostgreSQL sources should pilot DCP for their highest-throughput pipeline first and measure round-trip latency plus TLS overhead against the current tunnel; the savings in network-engineering time alone often pay for the pilot. Nếu bạn đang trả tiền cho một sản phẩm CDC bên thứ ba chỉ để cầu nối tunnel, đây là lúc so sánh lại tổng chi phí.

### 💡 Example
```sql
-- Create the DCP object and mint a one-week bootstrap token on the Snowflake side.
CREATE DATA CONNECTIVITY PROXY my_dcp_client;
SELECT SYSTEM$GENERATE_DATA_CONNECTIVITY_PROXY_BOOTSTRAP_TOKEN('my_dcp_client', 7);
```
```bash

docker run -d \
  --name dcp-agent \
  --restart unless-stopped \
  -v /etc/dcp/credentials:/credentials:ro \
  snowflake/dcp-agent:latest \
  --dcp-client-name my_dcp_client \
  --credentials-file /credentials \
  --snowflake-account my-account
```
```sql
-- Verify heartbeat, certificate expiry, and connection status.
DESCRIBE DATA CONNECTIVITY PROXY my_dcp_client;
```

### 🔭 Overview (Tổng)
Alif Semiconductor has released two development kits — the Balletto B1 StartKit and the Ensemble E1C StartKit — built around microcontrollers that pair a 160 MHz Arm Cortex-M55 core with Helium vector extensions and an Arm Ethos-U55 NPU delivering 128 MACs per cycle. Both boards ship with 2 MB of SRAM and roughly 1.8–1.9 MB of on-chip non-volatile memory, and both expose a 20-pin Arducam camera header, dual PDM microphones and a mikroBUS Click socket for expansion. The Balletto B1 adds an integrated Bluetooth LE 5.3 and 802.15.4 radio; the Ensemble E1C is the wireless-free variant. Pricing sits at roughly USD 50 per kit through Mouser and DigiKey, with stock expected on 22 October 2026.

### 🔬 Details (Phân)
The Cortex-M55 plus Ethos-U55 combination is Arm's reference pairing for entry-level edge AI, targeting keyword spotting, always-on wake-word detection, small vision classifiers and pose estimation on always-on power budgets. Helium's M-Profile Vector Extension lets the Cortex-M55 execute signal-processing and INT8 inference kernels efficiently even before delegating to the NPU, so latency-sensitive workloads can stay on the CPU when the NPU is busy. The 128-MACs-per-cycle Ethos-U55 is the smallest member of the Ethos-U line and is dimensioned for models in the 100 KB–1 MB int8 range, which is enough for most audio and simple-vision use cases but rules out anything approaching a full ImageNet backbone.

The physical layout — 86.37 mm × 71.09 mm, dual USB Type-C (one for the SoC, one for the on-board Segger J-Link debugger), and standard headers — makes the boards easy to drop into a Zephyr, ArmDS or Visual Studio Code toolchain. Alif ships CMSIS Device Family Packs for both parts, and the Balletto B1 has a Zephyr-based BLE example flow that includes native iOS and Android companion apps for testing. Compared with the older Ensemble E7 development boards, which used a much larger multi-core SoC and priced well above USD 100, the E1C StartKit is a deliberate step down in silicon and price aimed at hobbyists and audio-first products, while the Balletto B1 stakes a similar price point against Nordic's nRF54H20 kits with the addition of on-chip NPU acceleration.

The main caveat is stock and toolchain maturity. Alif's TensorFlow Lite for Microcontrollers delegate for Ethos-U55 has been stable for two years, but full Zephyr integration for both boards is still evolving, and camera-first workloads will need custom drivers for anything beyond the reference OV5647-class module implied by the Arducam header. Firmware in the Balletto B1 case must budget for the radio's coexistence with the NPU when both are active, since both draw from the same on-chip PMIC.

### 🎯 Takeaway (Hợp)
Teams evaluating edge-AI microcontrollers for audio wake-word, low-resolution vision or Matter-over-Thread applications should treat the Balletto B1 as a serious first-look at USD 50, and reserve the Ensemble E1C for battery-first designs that will never ship a radio. Order before stock lands on 22 October if you plan a Q4 prototype cycle.

## 5. Confluent Open-Sources KCP to Orchestrate Amazon MSK to Confluent Cloud Migrations

| Field | Value |
|---|---|
| 📅 Date | 14/09/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `apache-kafka` · `kcp` · `cluster-linking` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
Confluent has released KCP — short for Kafka Copy Paste — an open-source command-line tool that automates the four-step migration from Amazon Managed Streaming for Apache Kafka to Confluent Cloud. KCP handles discovery, infrastructure provisioning, data replication and client cutover behind a single state file, and lives on GitHub under the confluentinc organisation. Support for self-managed source clusters is on the near-term roadmap. The tool is aimed at teams that have historically punted MSK-to-Confluent-Cloud migrations because inventory discovery and Terraform generation across topics, ACLs, schemas, connectors and clients were manual and error-prone.

### 🔬 Details (Phân)
Step one is discovery: KCP scans the source AWS account across regions and inventories topics, ACLs, Schema Registry entries, MSK Connect connectors and known clients, producing a machine-readable snapshot in a `kcp-state.json` file that serves as the migration source of truth for every subsequent step. Step two generates Terraform templates for the target Confluent Cloud environment including networking configuration for public endpoints, AWS PrivateLink or VPC peering, so the target cluster and its network path can be provisioned from CI rather than click-ops. Step three handles the actual data movement using Confluent's Cluster Linking feature for byte-for-byte replication of topics, ACLs, schemas and connectors, and preserves consumer group offsets so downstream consumers do not replay data after cutover. Step four — client migration — is currently manual, with an integration into Confluent's Gateway product flagged for H1 2026.

The mechanism that matters most operationally is Cluster Linking with offset preservation. In the historical hand-rolled migration, the two hardest problems were replicating the exact offsets that consumers had committed and keeping schemas in sync across two schema registries with different subject-naming conventions; KCP's approach of driving both through Cluster Linking removes both issues without asking the operator to author bespoke MirrorMaker 2 configurations. That eliminates the classic cutover risk of consumers restarting at the earliest offset after moving to the target cluster. The Terraform templates it emits use the confluentinc/confluent provider, so an existing Confluent-Cloud-on-Terraform shop can drop the generated files into its own module tree.

The competitive frame is Amazon's own MSK-to-MSK migration guidance, which does not exist for MSK-to-Confluent-Cloud, plus the third-party Kafka replication tools (Cloudera Streams Replication Manager, Kafka Connect MirrorMaker 2 wrappers). Those alternatives are more general — they can migrate in either direction between arbitrary Kafka clusters — but they do not automate the discovery-and-provisioning steps or the state-file bookkeeping. KCP is deliberately opinionated in the direction of "MSK source, Confluent Cloud target, byte-for-byte replication", and the payoff is that a migration that used to take weeks of coordinated planning can be scripted end-to-end.

### 🎯 Takeaway (Hợp)
If a MSK-to-Confluent-Cloud migration is on your roadmap, prototype KCP against a non-production cluster this week to size the state file and confirm the Terraform output matches your IaC conventions; the tool eliminates most of the historically manual inventory work. Wait for the H1 2026 client-migration integration before automating the final cutover step in production.

### 💡 Example
```bash
# Install KCP from the Confluent GitHub release page or via go install.
go install github.com/confluentinc/kcp/cmd/kcp@latest

# 1) Discovery — scan every AWS region and inventory the source MSK estate.
kcp discover \
  --aws-profile prod-msk \
  --regions ap-southeast-2,us-east-1 \
  --state-file ./kcp-state.json

# 2) Infrastructure — emit Terraform for the target Confluent Cloud environment.
kcp plan-infra \
  --state-file ./kcp-state.json \
  --networking private-link \
  --output ./terraform

# 3) Data migration — set up Cluster Linking with offset preservation.
kcp migrate-data \
  --state-file ./kcp-state.json \
  --preserve-offsets

# 4) Client migration (currently manual; Gateway integration coming H1 2026).
kcp report --state-file ./kcp-state.json > migration-runbook.md
```
