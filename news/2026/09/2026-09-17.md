## 1. Databricks Ships MATCH_RECOGNIZE for Row Pattern Detection in Lakehouse Real-Time

| Field | Value |

### 🔭 Overview (Tổng)
Databricks has moved MATCH_RECOGNIZE — the SQL:2016 row-pattern-matching operator — into Public Preview across its Lakehouse compute surface, including Lakehouse Real-Time streaming pipelines. The feature applies a regex-like grammar directly to ordered rows: analysts DEFINE named states, describe the sequence in PATTERN using operators such as `+`, `*`, `?` and `|`, and pick which matched rows to emit through MEASURES. That collapses the long-standing "gaps and islands" pattern — a genre of SQL problem that has historically required window functions, LAG/LEAD arithmetic and manual island numbering — into a single declarative block against the source table.

### 🔬 Details (Phân)
The operator sits inside a standard FROM clause and slots into any table or view, so it works over both batch Delta tables and Structured Streaming sources without a separate engine. State variables in DEFINE evaluate arbitrary Boolean expressions on the current row, and MATCH_RECOGNIZE exposes navigation helpers — PREV and NEXT for LAG/LEAD-style access, FIRST() and LAST() for anchoring inside a match, and the `$` anchor for end-of-partition detection — so the pattern language is powerful enough for the awkward cases (a match that only completes on the last row of a partition, or one whose window is dynamically anchored to the first qualifying event rather than a fixed time). Databricks lists four canonical use cases: credential-stuffing detection where a burst of failed logins is followed by a success, V-shaped stock trend detection without manual island carving, checkout-abandonment tracking with idle timeouts, and predictive-maintenance patterns such as a slow temperature climb followed by a vibration spike.

Context matters here because MATCH_RECOGNIZE has existed for years in Oracle, Snowflake, Trino and Flink SQL, but Databricks' arrival at Public Preview brings the operator to a compute surface that mixes batch and continuous execution against the same tables. Combined with Lakehouse Real-Time, the pattern query is not a periodic scan but a streaming operator that emits matches as the underlying source progresses. Compared with hand-rolled Structured Streaming stateful operators, MATCH_RECOGNIZE removes the need to author `flatMapGroupsWithState` in Scala or Python, keep manual keyed state, and reason about watermark timing; the engine owns partitioning, ordering and match emission, and Genie Code offers AI-assisted migration for existing gaps-and-islands SQL.

The trade-off during Preview is coverage: the release currently targets Databricks compute (both classic clusters and Serverless SQL), and multi-workload access patterns — for example, replaying a pattern from a Snowflake or BigQuery table via federated query — remain scoped to what those engines expose. Teams that already run Structured Streaming stateful jobs should benchmark the operator against their existing state-store footprint before consolidating; teams that today ship analyst-authored gaps-and-islands SQL are the clearer wins.

### 🎯 Takeaway (Hợp)
Analytics teams with recurring sequence-detection SQL — anomaly cascades, abandonment funnels, financial trend reversals — should port one hand-tuned window-function query onto MATCH_RECOGNIZE on Databricks this sprint and compare readability plus runtime side by side. Nếu bạn đang duy trì `flatMapGroupsWithState` chỉ để phát hiện chuỗi sự kiện, đây là lúc cân nhắc thay bằng SQL pattern-matching.

### 💡 Example
```sql
-- Detect credential stuffing: 5+ failed logins within 60 seconds followed by a success.
SELECT *
FROM login_events
MATCH_RECOGNIZE (
  PARTITION BY user_id
  ORDER BY event_time
  MEASURES
    FIRST(FAIL.event_time)  AS attack_start,
    LAST(FAIL.event_time)   AS last_failure,
    SUCCESS.event_time      AS breach_time,
    COUNT(FAIL.event_time)  AS failed_count
  ONE ROW PER MATCH
  AFTER MATCH SKIP PAST LAST ROW
  PATTERN (FAIL{5,} SUCCESS)
  DEFINE
    FAIL    AS event_type = 'FAILED_LOGIN'
            AND event_time <= FIRST(FAIL.event_time) + INTERVAL 60 SECONDS,
    SUCCESS AS event_type = 'LOGIN_SUCCESS'
);
```

### 🔭 Overview (Tổng)
DuckDB has released duckdb-skills, an official Claude Code plugin that redirects data-manipulation tasks through the DuckDB CLI instead of ad-hoc Python. Installed from the Claude Code plugin marketplace, the plugin exposes a set of named skills — reading a wide range of formats (CSV, JSON, Parquet, Avro, Excel, spatial, SQLite, Jupyter), exploring remote storage on S3, GCS, Azure and HTTPS without downloading, running spatial joins against Overture Maps data, and searching DuckDB and DuckLake documentation — that the agent can invoke either by natural language or with an explicit `/duckdb-skills:*` command. The pattern replaces the common "generate pandas code, run it, hope the schema matches" loop with a SQL-first exchange between the model and the database.

### 🔬 Details (Phân)
The plugin ships as a marketplace-installable bundle: `/plugin marketplace add duckdb/duckdb-skills` followed by `/plugin install duckdb-skills@duckdb-skills` registers the skills into a Claude Code project, and the DuckDB CLI is the only external prerequisite. Under the hood the plugin implements a dual-conversation pattern — the model talks to the user in natural language, and separately talks to DuckDB in SQL — with an auto-repair loop that reads DuckDB error messages, corrects column names or syntax and retries without going back to the user. That closed loop matters because it turns the notorious "hallucinated column" failure mode into a self-recovered retry, and it keeps the model out of Python interpreter start-up costs on every step.

The skill inventory reflects DuckDB's actual strengths rather than a generic SQL veneer: remote-file exploration uses DuckDB's HTTPFS and secret manager so a session can hit `s3://bucket/prefix` and enumerate schemas without a full download, geospatial workflows use the `spatial` extension and can join Overture Maps layers for distance and nearest-neighbour queries, and the extension-management skill lets Claude install or upgrade community extensions when a task needs one. Compared with an equivalent Python-first agent, the DuckDB path avoids two categories of failure — schema mismatch bugs that only surface at read time, and I/O overhead from re-materialising remote data — because the query executes inside the same process that reads the file.

The competitive frame is Snowflake's Cortex, Databricks' Genie and Google's Data Agent Kit, all of which route agentic analytics through their vendor-native SQL engine and governance surface. duckdb-skills instead makes the local, embeddable DuckDB the analytical substrate and treats remote object storage as first-class rather than through a warehouse import step, which fits use cases like ad-hoc log exploration, cross-cloud data joins during migrations, and preview-scale analytics on lake data without provisioning a cluster. The caveat is that anything requiring governance controls — row filters, masking policies, audit trails — remains outside the plugin's scope; DuckDB provides no equivalent to Unity Catalog or Snowflake network rules, so shared production data lakes still need a mediating layer.

### 🎯 Takeaway (Hợp)
Teams already using Claude Code for data engineering scratch work should install duckdb-skills today, point it at a Parquet-heavy S3 prefix and measure the reduction in Python-side iteration. Trên môi trường có DuckLake hoặc Iceberg local, plugin này biến DuckDB CLI thành lớp truy cập chính của agent, giảm được khá nhiều vòng lặp `df = pd.read_parquet(...)` không cần thiết.

## 3. United Airlines Uses AWS Glue Data Catalog Federation to Query Databricks Unity Catalog From Redshift Serverless

### 🔭 Overview (Tổng)
AWS has published a technical case study describing how United Airlines lets Amazon Redshift Serverless query Databricks-managed Delta Lake tables directly, without ETL, through a federation chain of Databricks Unity Catalog, the Iceberg REST protocol, AWS Glue Data Catalog and AWS Lake Formation. The airline reports approximately US$30,000 per month in cost reduction from eliminating redundant ingest pipelines, plus faster access for about 100 analysts who no longer wait for sync jobs. The pattern is significant because it collapses the multi-catalog problem — Redshift needs Glue, Databricks uses Unity Catalog — into a single query-time credential vending flow.

### 🔬 Details (Phân)
The architecture strings four layers together: Unity Catalog exposes tables via the Iceberg REST API with Delta UniForm enabled to generate Iceberg-compatible metadata; AWS Glue Data Catalog creates a federated catalog (`databricks-federated-catalog`) that calls that REST endpoint at query time; a resource-link database in the default Glue catalog acts as a pointer without copying metadata; and Redshift Serverless references the resource link through an external schema. On query execution the resolver walks the chain — Redshift consults the external schema, Glue calls the Iceberg REST endpoint for table metadata, the Redshift namespace's IAM role invokes `lakeformation:GetDataAccess`, Lake Formation evaluates its permission grants and vends temporary S3 credentials, and Redshift reads the Iceberg data files directly from S3. No data leaves Delta storage.

The security model is deliberately layered. Lake Formation grants split into two distinct permissions: `DESCRIBE` on the resource-link database and `SELECT`+`DESCRIBE` on the tables in the federated catalog via "Grant on Target". Getting that split wrong — for example granting `SELECT` on the resource link — is the failure mode that shows tables in `SVV_EXTERNAL_TABLES` but returns access-denied on read. IAM policy for the Redshift namespace role is limited to Glue catalog metadata operations and `lakeformation:GetDataAccess`, and short-lived credentials are re-vended per query rather than issued long-term. The blog also documents JDBC connection strings for SAML users, letting enterprise identity providers front the whole flow without local credentials on analyst laptops.

Compared with the alternatives — a full ETL replication into Redshift-managed storage, a Redshift Spectrum external table over customer-owned Iceberg, or a Databricks-side view exposed via Delta Sharing — this federation path avoids duplicating storage, keeps a single source of truth in Delta, and does not require exporting to a separate Iceberg-only copy. The trade-off is coupling to two vendors' catalog fidelity: Delta tables must run UniForm to be readable as Iceberg, well-partitioned and regularly compacted for good performance, and any Unity Catalog features not surfaced through Iceberg REST (row filters, column masks) will not apply on the Redshift side.

### 🎯 Takeaway (Hợp)
Data teams whose warehouses live on Redshift but whose upstream ETL runs on Databricks should try this federation pattern before scoping a new sync pipeline; the storage and pipeline savings compound quickly at any non-trivial data volume. Kiểm tra kỹ hai lớp Lake Formation grant khi triển khai — sai chỗ này thì query báo access-denied dù bảng đã hiện trong catalog.

### 💡 Example
```sql
-- 1. On the Redshift side, expose the federated database as an external schema.
CREATE EXTERNAL SCHEMA databricks_schema
FROM DATA CATALOG
DATABASE 'databricks_federated_db_link'
IAM_ROLE 'arn:aws:iam::111122223333:role/RedshiftServerlessNamespaceRole'
REGION 'ap-southeast-2';

-- 2. Verify the tables are visible through the federation chain.
SELECT schemaname, tablename
FROM SVV_EXTERNAL_TABLES
WHERE schemaname = 'databricks_schema';

-- 3. Query a Databricks-managed Delta table by name; Redshift reads Iceberg from S3.
SELECT event_id, event_type, event_ts
FROM databricks_schema.interaction_events
LIMIT 10;
```

### 🔭 Overview (Tổng)
Developer Paulneja has published version 0.8 of a project that boots mainline Linux 6.11 natively on Espressif's ESP32-S3, using one of the chip's dual Xtensa LX7 cores at 240 MHz plus its 8 MB octal PSRAM. The image is single-flashable to a 16 MB flash / 8 MB PSRAM ESP32-S3 board, exposes working Wi-Fi in STA mode by handing radio duties to the second core still running the ESP-IDF stack, and routes the chip's hardware RSA accelerator into the Linux Crypto API. Hackaday, Hackster and daily.dev covered the release simultaneously. This is not a demonstration of Zephyr or a homebrew RTOS — it is the mainline kernel, patched only where the platform genuinely lacks upstream support.

### 🔬 Details (Phân)
The core technical concession is NOMMU. The ESP32-S3 has no memory management unit, so the build uses the Linux NOMMU configuration and ships a custom `fork()` implementation because virtual memory copy-on-write is unavailable; that is the same class of workaround previously used on Cortex-M-class targets and on early Blackfin and RH850 ports. Only one of the two Xtensa LX7 cores runs Linux at 240 MHz; the second remains under FreeRTOS with the ESP-IDF Wi-Fi stack, and Linux talks to it over a bespoke bridge to expose radio operations. Available RAM after boot has climbed from an unstable footprint in v0.7 to a workable 3.7 MB in v0.8, enough to host busybox userspace and light network services.

Peripheral coverage tells the story of where the port stands: Wi-Fi in station mode works, the RSA accelerator is bridged into the kernel's crypto framework so operations that would take seconds on a soft Xtensa implementation drop to hardware speeds, and the flash and PSRAM are usable. Missing pieces are equally illustrative — no upstream Xtensa NOMMU support means the tree is a fork rather than an upstreamable series, no Bluetooth is bridged through, and the second core's FreeRTOS remains the wireless owner rather than Linux itself. Compared with Espressif's own Zephyr-in-QEMU workflow — a separate story from the 16 September digest — this is the opposite trade: real hardware, real Wi-Fi, but a research-grade kernel fork rather than a supported RTOS path.

The interesting practical envelope is a small always-on Linux box: a network router or gateway that needs BusyBox userspace, iptables and lightweight scripting on an ESP32-S3 already in the BOM. That fits a category of hobby and research hardware that currently reaches for a Raspberry Pi Zero 2 W but wants a cheaper, single-chip alternative with integrated radio. For anyone shipping a commercial product, though, the NOMMU-plus-fork combination is a maintenance liability; kernel upgrades will need to carry the same patches, and mainline Xtensa Linux is not currently trending toward absorbing them.

### 🎯 Takeaway (Hợp)
Firmware engineers curious about the mainline-kernel envelope of the ESP32-S3 should build v0.8 against a 16 MB/8 MB dev board and measure the RSA-accelerated TLS handshake; the result gives concrete data on whether a Linux-on-ESP32 product is even feasible. Đừng dùng cho sản phẩm thương mại — đây là nhánh nghiên cứu, mainline upstream chưa có Xtensa NOMMU support.

### 💡 Example
```bash
# 1. Fetch the release and flash a single image to a 16 MB / 8 MB ESP32-S3 board.
git clone https://github.com/paulneja/Linux-on-esp32-S3
cd Linux-on-esp32-S3
git checkout v0.8

# 2. Build the flashable image (kernel + bootloader + rootfs).
./build.sh                    # honours the pinned toolchain in Makefile

# 3. Flash to a ESP32-S3-DevKitC-N16R8 (16 MB flash, 8 MB octal PSRAM).
esptool.py --chip esp32s3 --port /dev/ttyUSB0 --baud 921600 write_flash \
  0x0 build/linux-esp32s3.bin

# 4. Attach a UART console and watch the kernel come up on the LX7 core.
#    Expect ~3.7 MB free after login; RSA acceleration exposed via /dev/crypto.
picocom -b 115200 /dev/ttyUSB0
```

## 5. OpenMANET Ships an 802.11ah Wi-Fi HaLow Mesh Alternative to Meshtastic on Raspberry Pi

| Field | Value |

| 🔑 Keywords | `wifi-halow` · `mesh-networking` · `raspberry-pi` |

### 🔭 Overview (Tổng)
OpenMANET has launched an open-source mesh-networking stack built on 802.11ah Wi-Fi HaLow radios from Morse Micro, aimed at delivering higher bandwidth than Meshtastic's LoRa-based network while keeping the same off-grid, long-range topology. The project runs on OpenWrt with a Go-based mesh daemon called OpenMANETd, uses the IEEE 802.11s mesh standard plus batman-adv for routing, and supports a range of boards including Raspberry Pi Zero 2 W, Raspberry Pi 3 Model B, Gateworks Venice, HaLowLink 2 and Heltec HT-HD01 V2 — with a Raspberry Pi 4 kit recommended for the full feature set. Because the medium is IP over Wi-Fi HaLow rather than a proprietary LoRa payload format, OpenMANET nodes deliver 1–15 Mbps depending on the country's HaLow regulatory allocation.

### 🔬 Details (Phân)
The stack layers cleanly. OpenWrt provides the base firmware and Wi-Fi HaLow driver, IEEE 802.11s handles the layer-2 mesh membership, batman-adv provides layer-2 routing that survives topology churn, and OpenMANETd manages higher-level operations — push-to-talk voice, GPS position sharing, camera and video streaming, and ATAK (Android Team Awareness Kit) integration for tactical mapping. A single node in the mesh can act as a "mesh gate", bridging traffic to the internet through Starlink or cellular, so a small deployment gets a shared uplink without every node needing its own WAN link. That gate model is what makes OpenMANET a plausible drop-in for search-and-rescue and disaster-response deployments where Meshtastic's low-bandwidth text-only medium is not enough for camera and video traffic.

The trade-offs against Meshtastic are explicit. Meshtastic wins on ultra-low power draw and cost per node — a sub-USD 30 LoRa module can run for weeks on a small battery, whereas an OpenMANET node needs a Raspberry Pi with its accompanying HaLow radio, active thermal envelope and non-trivial power. In return, OpenMANET offers a full IP substrate: any protocol that runs over Wi-Fi runs over the mesh, including standard RTP streams for video and TCP for file transfers. Compared with commercial tactical mesh radios that occupy the same use cases at four-figure prices, the project is deliberately positioned as an open-source alternative that lets teams build their own kit around commodity Raspberry Pi hardware and Morse Micro's chipsets.

Practical caveats are the usual ones for HaLow: allocated bandwidth and channel plans vary sharply by country (the US S1G plan differs from Australia's, and both differ from the European CEPT allocation), transmit power limits shape achievable range, and antenna selection has more effect on link budget than at 2.4 GHz. The project ships reference configurations for common regulatory domains, but any real deployment needs an RF check for the operating country. Because the media is licence-exempt sub-GHz Wi-Fi rather than a proprietary Meshtastic frame, spectrum coexistence with existing S1G devices should also be planned in high-density events.

### 🎯 Takeaway (Hợp)
Teams evaluating open long-range mesh options for camera or ATAK-backed workflows should trial an OpenMANET kit against their existing Meshtastic deployment and measure both throughput and power envelope; the fit depends on whether the mission needs kilobits or megabits. Với các đội cần voice PTT hoặc streaming video off-grid, đây là hướng đáng thử trước khi mua radio thương mại.

### 💡 Example
```yaml
# Minimal OpenMANET node profile — Raspberry Pi 4 with a HaLowLink 2 radio,
# joining an existing mesh and offering itself as a gate if a WAN uplink is up.

  role: gate            # 'gate' bridges to WAN when available, otherwise 'client'
  hostname: rescue-01

  protocol: batman-adv

  gps_beacon: true      # periodic position beacons
  atak: true            # forward CoT XML messages
uplink:
  interface: eth0       # Starlink or cellular
  advertise_gate: true
```
