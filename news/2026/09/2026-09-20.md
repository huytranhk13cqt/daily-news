## 1. DuckDB-Wasm Adds opfs Persistent Databases and Retires the IndexedDB Serialize Dance

| Field | Value |
|---|---|
| 📅 Date | 18/09/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `duckdb-wasm` · `opfs` · `browser-analytics` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
DuckDB-Wasm can now open a database at an `opfs://` path and have it survive page reloads and browser restarts, folding the same write-ahead log and checkpoint model DuckDB uses natively into the browser. The feature builds on the Origin Private File System (OPFS), a per-origin sandboxed file store with random-access reads and writes that every modern browser has shipped since March 2023. For teams that already treat DuckDB-Wasm as the in-tab analytics engine, this is the release that removes a specific piece of scaffolding: serializing tables to Parquet, stuffing bytes into IndexedDB, and re-registering them on every load.

### 🔬 Details (Phân)
Opening a persistent database is a one-liner change to the existing bootstrap: pass `path: 'opfs://analytics.duckdb'` with `DuckDBAccessMode.READ_WRITE`, and DuckDB-Wasm writes both the main file and its `.wal` sidecar into OPFS. Durability follows the native model — committed transactions land in the WAL, `CHECKPOINT` promotes them into the database file. Because a browser tab can close at any moment, the release notes are explicit that user-driven writes should be followed by a checkpoint, either explicitly after each edit batch or by setting `checkpoint_threshold = '0KB'` for aggressive fsync-like semantics. Remote datasets loaded once via HTTP range requests are cached in place, so a subsequent `CREATE TABLE IF NOT EXISTS orders AS SELECT * FROM 'https://.../orders.parquet'` skips the network entirely.

Two file-handling modes exist: `fileHandling: 'auto'` scans each SQL statement for `'opfs://...'` literals and registers the file transparently, while the default manual mode expects `registerOPFSFileName()` / `dropFile()` calls and is documented as cheaper for high-query workloads. There is one operational sharp edge: only one handle per file can be open at a time, and DuckDB-Wasm cannot yet copy files into or out of OPFS from SQL, so import/export goes through the browser's own `navigator.storage.getDirectory()` API or a `COPY ... TO 'parquet'` step. The release notes also flag a versioning trap: npm's `latest` build (1.33.1-dev57.0) does not persist correctly, so shops should pin to 1.32.0 or track the `@next` tag (1.33.1-dev64.0+).

Positioning matters. OPFS is still per-origin and is treated by browsers as evictable cache under storage pressure, so the guidance is to keep authoritative data in DuckLake, object storage, or a server-side warehouse and use OPFS as a fast local materialisation. That is a narrower contract than a native `.duckdb` file, but a much cleaner one than the IndexedDB round-trip most Wasm apps built themselves.

### 🎯 Takeaway (Hợp)
For any team already shipping DuckDB-Wasm in a data app, this release is the moment to delete the custom Parquet-to-IndexedDB glue. Nếu app đang cần "state" giữa lần mở tab, cứ chuyển sang `opfs://` với `CHECKPOINT` sau mỗi batch — nhưng nhớ pin version đúng và coi OPFS là cache có thể bị evict, không phải kho dữ liệu chính.

### 💡 Example
```javascript
// Open a persistent DuckDB database inside OPFS
await db.open({
  path: 'opfs://analytics.duckdb',
  accessMode: duckdb.DuckDBAccessMode.READ_WRITE,
});

const conn = await db.connect();

// Load a remote Parquet once; OPFS caches it for later sessions
await conn.query(`
  CREATE TABLE IF NOT EXISTS orders AS
  SELECT * FROM 'https://shell.duckdb.org/data/tpch/0_01/parquet/orders.parquet';
`);

// Fold the WAL into the main file after a batch of user edits
await conn.query('CHECKPOINT;');
```

## 2. Apache Airflow 3.3.2 Closes Backfill Enumeration Leak and Reorders Bearer vs Session Auth

### 🔭 Overview (Tổng)
Airflow 3.3.2 is a patch release aimed squarely at the 3.3 line's REST API and authentication surface. Two changes stand out for anyone running Airflow behind a shared authentication layer: backfill endpoints stop leaking which backfill IDs exist across DAGs, and an explicit `Authorization: Bearer` credential now wins over a coexisting session cookie. The release also lands over eighty scheduler, database, and UI fixes accumulated since 3.3.1 in August. For teams on Airflow 3.3.x — especially those exposing the REST API to service accounts or a fronting API gateway — this is a mandatory upgrade rather than an optional patch.

### 🔬 Details (Phân)
The security-relevant behaviour changes are precise. Requesting a backfill on a DAG the caller cannot read now returns `404 Backfill not found` instead of `403 Forbidden`, which prevents an attacker with partial access from probing which backfill IDs exist behind DAGs they cannot see. The `/assets/events` listing has been scoped to the DAGs the caller may read, and the partitioned DAG-runs listing no longer surfaces DAG existence to unauthorised callers. On the authentication side, a request carrying both a `_token` cookie and an `Authorization: Bearer` header is now resolved as the bearer token's principal; invalid explicit credentials are rejected with `401`/`403` even when a valid session cookie is present, and the logout endpoint revokes every credential presented to it, not just the session cookie. Neither change ships with a CVE number, but the release notes describe the pre-3.3.2 behaviour as a real disclosure risk.

Beyond security, the fix list is dense with operational relief. Task-instance lookup drops a redundant `dag_run` join for a measurable win on large histories; `airflow db clean` finally purges the `callback` table; an XCom-corruption regression during the bytea-to-JSONB migration is fixed, so long-running upgrades do not silently mangle JSON-parseable values. Two race-condition classes get proper fixes as well: `DeadlockImminentError` when a connection is resolved inside an async task, and a DAG-processor crash when an orphaned processor is killed. The changelog also mentions UI timezone awareness and calendar-view performance, both of which have been recurring 3.3 complaints.

There are no schema migrations flagged by this release, which is unusual for a security-adjacent Airflow patch and welcome for shops on managed Airflow variants. Anyone whose middleware or reverse proxy was relying on the old "cookie wins over bearer" ordering — a pattern that shows up in some legacy SSO integrations — should audit their auth flow before upgrading, since the new precedence is not toggleable.

### 🎯 Takeaway (Hợp)
Treat 3.3.2 as a security patch and pull it into the next maintenance window, not the next quarterly refresh. Trước khi upgrade, review lại bất kỳ integration nào cho bearer token và session cookie cùng tồn tại, vì thứ tự ưu tiên đã đảo và sẽ thay đổi principal của request đang chạy.

## 3. Arduino Core for ESP32 3.3.12 Lands USB Host, IPv6 OTA and Optional SHA-Verified Firmware Sidecars

| 🔑 Keywords | `arduino-esp32` · `usb-host` · `secure-ota` |

### 🔭 Overview (Tổng)
Arduino Core for ESP32 3.3.12 is the point release that finally ships a real USB Host stack for Arduino sketches — HID, MSC and CDC-serial classes — alongside a set of network and security fixes that matter well beyond hobby projects. It rebases on ESP-IDF v5.5.5, extends OTA to IPv6, adds optional SHA-256 / SHA-512 sidecar verification for incoming firmware, and folds in support for a wider range of Waveshare and third-party boards. For anyone shipping an ESP32-based product on the Arduino API, this is the release that closes a small pile of long-standing web-server and BLE-pairing rough edges at the same time.

### 🔬 Details (Phân)
The USB Host addition is the largest new capability. The library exposes host-mode HID (keyboard, mouse, gamepad), MSC (mass storage — read/write to USB drives from a sketch) and CDC-serial (talk to USB serial devices) via classes analogous to the existing device-mode APIs, which brings the Arduino side closer to what ESP-IDF developers have had in `esp_usb_host` for a while. On the network side, OTA now speaks IPv6 — a small change with real consequences for fleets on IPv6-only networks — and the HTTP client fixes socket reuse for HTTP/1.0 servers, which are still stubbornly common inside industrial LANs. WiFiProv now guarantees BLE allocation before provisioning starts, closing a class of "provisioning worked once, then never" bugs.

The security posture also tightens meaningfully. The web server is described as "hardened," addressing both hang conditions and unspecified vulnerabilities. Optional SHA-256 or SHA-512 checksum validation can be enabled for OTA updates via a configurable sidecar URL, giving fleets a low-cost integrity check without requiring code signing infrastructure. BLE pairing failures are now reported instead of silently succeeding — arguably the most important safety change in the release, since a silent success can look like a working device until an encrypted characteristic is written and everything falls apart. Matter 1.5 gets improved binary-sensor and light-colour-control support with node-identity features, and OpenThread gains SRP/DNS-SD APIs for on-mesh service discovery.

Board support widens noticeably: Waveshare's ESP32-C5-Zero (the first mainline board built on Espressif's Wi-Fi 6 / 802.11ax-ready C5 SoC in this release stream), several ESP32-S3 Touch-LCD variants, an ESP32-S3 RGB Matrix and a Raiden S01 ESP32-S3 devkit all land as first-class targets. The release also fixes CPU frequency calculations for ESP32-H2 and -C6 variants and eliminates a memory leak in `getSupportedCpuFrequencyMhz()`. There are no explicit breaking API changes, though products relying on the previous silent-success BLE pairing behaviour will surface latent bugs after upgrading.

### 🎯 Takeaway (Hợp)
For any ESP32 product on the Arduino API, 3.3.12 is worth pulling in for the webserver hardening and BLE pairing fix alone; the USB Host additions expand what a single-chip design can do without a companion microcontroller. Nếu đang chuẩn bị lô hàng mới, bật thêm SHA-verified OTA sidecar để có thêm một lớp integrity check cho firmware download qua HTTPS.

### 💡 Example
```cpp
// Enable IPv6 + SHA-256 verified OTA on Arduino Core for ESP32 3.3.12
#include <WiFi.h>
#include <HTTPUpdate.h>

void setup() {
  WiFi.enableIPv6(true);
  WiFi.begin(SSID, PASSWORD);
  while (WiFi.status() != WL_CONNECTED) delay(200);

  WiFiClient client;
  httpUpdate.setChecksumURL(
    "https://fw.example.com/prod/firmware.bin.sha256"  // sidecar checksum
  );
  httpUpdate.setChecksumAlgorithm(HTTP_UPDATE_SHA256);

  t_httpUpdate_return ret =
    httpUpdate.update(client, "https://fw.example.com/prod/firmware.bin");
  if (ret == HTTP_UPDATE_FAILED) {
    log_e("OTA failed: %s", httpUpdate.getLastErrorString().c_str());
  }
}
```

## 4. ESPHome 2026.9.0 Parallelises PlatformIO Installs and Ships Noise-Encrypted OTA to Every Board

| Field | Value |
|---|---|
| 📅 Date | 16/09/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | IoT |
| 🔑 Keywords | `esphome` · `noise-protocol` · `esp8266` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
ESPHome 2026.9.0 is a chunky monthly release that tackles two long-standing complaints at once: builds are noticeably faster, and OTA updates finally travel over a Noise-encrypted channel by default when both sides speak it. Alongside that, the release lays groundwork for a native ESP8266 toolchain that bypasses PlatformIO, and squeezes tens of kilobytes of flash and hundreds of bytes of RAM out of the smaller targets. For Home Assistant users maintaining fleets of dozens of ESPHome nodes — the modal Home Assistant deployment — this is the release that meaningfully improves both the day-to-day compile loop and the security story on firmware distribution.

### 🔬 Details (Phân)
The build-time work is measurable. PlatformIO package extraction now uses one worker per available CPU core, and CI benchmarks report the package phase dropping from 17.1 s to 10.3 s on ESP8266-Arduino configurations (36 % of build time down to 25 %). Registry libraries and tool archives download concurrently behind a single progress bar, and the Docker image preinstall step drops from roughly 100 s to 46 s across architectures. The eight-PR ESP8266 native-toolchain scaffolding — a shared registry layer, a linker-script processor and a SHA256-verified installer for Arduino ESP8266 core 3.1.2 and xtensa-gcc 10.3 — ships dormant, with the full replacement planned for 2026.10.0. Two things worth flagging as still-in-progress: encrypted OTA is opt-in unless both firmware versions ship the release, and the ESP8266 toolchain work does not change behaviour until 10.0.

The Noise-encrypted OTA path is the security headline. ESPHome reuses the ChaCha20-Poly1305 handshake from its native API, so the same API key gates both control and firmware channels; an `encryption:` block can be added to force encryption and reject fallback. Backward compatibility is preserved — older firmwares still receive unencrypted updates — and the release ships an optimised cryptographic library that dramatically reduces both flash and RAM on constrained devices. Numbers speak louder than adjectives: on an ESP8266 D1 mini, the crypto flash footprint drops from 80.9 KB to 41.9 KB and static RAM from 1376 B to 48 B; the Noise handshake itself falls from ~580 ms to ~300 ms. Similar gains apply to ESP32 (IDF) and Pico W (RP2040) targets. A codebase-wide sweep also moved 211 conditional log literals across 60 files from RAM into flash on ESP8266, and swapped a base64 alphabet table for arithmetic to recover another 64 bytes of RAM.

The release does carry breaking changes. Modbus Controller configurations must rename `custom_command` to `custom_pdu` and revisit `register_count`, `force_new_range` and `skip_updates`. ESP32 devices with an eFuse-burned custom MAC now apply that MAC to every interface — Ethernet, Bluetooth, 802.15.4 — which will change on-wire addresses and force DHCP and bonding updates. Nine previously permissive UART components (`mhz19`, `daly_bms`, `teleinfo` and others) now enforce baud rate and parity at configuration time, so misconfigured YAML fails the compile instead of failing silently at runtime. ESPHome also now rejects ESP8266 Arduino framework below 3.0.0, and ESP32 Hosted requires ESP-IDF 5.3 or newer.

### 🎯 Takeaway (Hợp)
For a Home Assistant fleet the security upgrade alone justifies the release; the compile-time speedups are a bonus that will pay back on every subsequent flash. Nên đọc kỹ phần breaking changes cho Modbus Controller, custom MAC trên ESP32 và các UART sensor trước khi bấm upgrade, vì một số cấu hình cũ sẽ không compile ngay lần đầu tiên.

### 💡 Example
```yaml
# Enforce Noise-encrypted OTA on ESPHome 2026.9.0+
api:
  encryption:
    key: "<base64 32-byte key>"        # reused for OTA on 2026.9.0+

ota:
  - platform: esphome
    password: !secret ota_password
    encryption:
      required: true                    # refuse fallback to plaintext OTA
```
