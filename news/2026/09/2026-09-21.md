## 1. Apache Arrow Rust 60.0.0 Ships the First Production Parquet Reader With ALP Float Encoding

| Field | Value |

### 🔭 Overview (Tổng)
Apache Arrow Rust 60.0.0 is the first shipping Parquet implementation in any language to carry an Adaptive Lossless floating-Point (ALP) encoder and decoder end-to-end. ALP has been in the Parquet Format 2.14.0 specification since 11 September, but Rust is the language that hits `cargo publish` with a working reader-writer pair; C++ and Java implementations remain in flight. For any team writing wide floating-point columns — sensor telemetry, market ticks, ML feature stores — this is the release that starts folding compression ratios closer to lossless columnar formats designed for floats, without touching the query API.

### 🔬 Details (Phân)
The changelog lists ALP encoder-decoder support explicitly as a breaking change in the `parquet` crate, meaning the writer negotiates the new encoding when both sides advertise Parquet Format 2.14.0 and falls back to `PLAIN` or `BYTE_STREAM_SPLIT` otherwise. Alongside encoding work the release rewrites the metadata surface: column metadata moves from `HashMap<String, String>` to an ordered `Metadata` struct, which preserves insertion order across round-trips and unblocks a class of catalog-integration bugs. Two FFI functions — including `FFI_ArrowSchema::with_metadata` — are now `unsafe` to reflect their real invariants, so downstream crates that wrapped them without care will need audit passes. The `rand` dependency jumps to `0.10`, which propagates a `SeedableRng` API change into any codebase pinning specific RNGs.

There are 67-plus contributors on this release, and the operational surface expands with MapArray fixes, additional `Utf8View`/`BinaryView` kernels and buffer-management fixes that reduce a class of validation-failure panics on truncated files. The ALP work builds on cross-language coordination: an ALP reference implementation exists in DuckDB and in the ClickHouse fork of the format, but until now no Parquet writer in the Apache tree could produce ALP-encoded columns at all. Uploading old files remains fully compatible — ALP is per-column encoding metadata, not a file-format break — so a mixed-cluster upgrade is safe as long as older readers can advertise the format version.

Downstream, DataFusion 55.1.0 (also released this week) pulls the new arrow-rs release through, which means the ALP path is now reachable from SQL query plans that spill Parquet. Iceberg-Rust 0.11.0 is still in RC because of unrelated encryption issues, so ALP arrival in Iceberg Java tables is gated on Java 1.12.0. The practical implication is that anyone using DataFusion or a direct arrow-rs pipeline to write floating-point Parquet today can experiment with ALP immediately; downstream consumers on older arrow-rs will simply read the file with the fallback path.

### 🎯 Takeaway (Hợp)
Pin `parquet = "60.0"` and `arrow = "60.0"` on new float-heavy pipelines and benchmark ALP against your current encoding before rolling to Iceberg. Nếu hạ tầng đang dùng `HashMap` cho column metadata trong FFI, chuẩn bị migrate qua struct mới vì đây là breaking change duy nhất có thể làm gãy code sẵn có.

### 💡 Example
```rust
// Write a Parquet file with the new ALP encoder in arrow-rs 60.0.0
use arrow::array::{ArrayRef, Float64Array};
use arrow::record_batch::RecordBatch;
use parquet::arrow::ArrowWriter;
use parquet::basic::Encoding;
use parquet::file::properties::WriterProperties;
use std::sync::Arc;

let temps: ArrayRef = Arc::new(Float64Array::from(vec![21.5, 21.51, 21.49, 21.52]));
let batch = RecordBatch::try_from_iter([("temp_c", temps)])?;

let props = WriterProperties::builder()
    .set_column_encoding("temp_c".into(), Encoding::ALP)
    .build();

let file = std::fs::File::create("telemetry.parquet")?;
let mut writer = ArrowWriter::try_new(file, batch.schema(), Some(props))?;
writer.write(&batch)?;
writer.close()?;
```

## 2. Sedona Measures GeoParquet Data-Skipping and Confirms Row Order Is the Index

| Field | Value |

### 🔭 Overview (Tổng)
Jia Yu, Apache Sedona's PMC chair, ran a quiet but consequential benchmark on 3.82 million Washington-state buildings stored as GeoParquet and turned the result into a single sentence: the row order is the index. The post compares three real-world sort strategies — geometry-sorted, name-sorted and randomly shuffled — for a small downtown Seattle bounding-box query, and then shows how a Bloom-filtered S2 cell column recovers most of the pruning that a bad sort loses. It is one of the few recent posts that puts hard MB and millisecond numbers on GeoParquet layout decisions.

### 🔬 Details (Phân)
The three layouts, all written with 50 000-row row groups, produce very different metadata footprints. A geometry-sorted layout using S2 space-filling-curve coordinates yields a median bounding box per row group of 0.15 square degrees; a name-sorted layout (the realistic production case where files come from CDC or ETL that groups by city or county) yields 5.3 square degrees; and a shuffled layout balloons to 26.6 square degrees — effectively the whole state per row group. A 1 × 1.5 km window over downtown Seattle then reads 4 of 77 row groups (20 MB, 40 ms) on the sorted file, 54 of 77 row groups (253 MB, 105 ms) on the name-sorted file, and all 77 row groups (373 MB) on the shuffled file, with the shuffled case slow enough that the post drops the millisecond number entirely.

The recovery mechanism is the interesting half. Adding a Bloom-filtered S2 cell column at level 12 costs only 1.3 MB in a 591 MB file, and rescues the name-sorted case: Seattle drops from 54 to 8 row groups (253 MB → 43 MB), and Leavenworth drops from 41 to 3. The post is honest about limits: single-cell-per-row cannot handle skew (cell populations from 1 to 13 267 buildings), cannot handle geometry crossing cell boundaries without duplicates, degrades on wide queries, and requires manual level tuning. Yu closes by pointing to the Hippo algorithm (VLDB 2016) as a template for a future adaptive multi-index in Parquet — a genuine research direction rather than a shipped feature.

For teams operating Iceberg or DuckLake tables on top of Parquet, the operational implication is direct. A sort key that already exists in your write path (city, region, tenant) is not free from a query-cost perspective, and a small pre-computed cell column with a Bloom filter is a cheap retrofit that avoids a full table rewrite. The pattern is not GeoParquet-specific either: any high-selectivity column with a natural bucketing (S2 for spatial, geohash, or business-domain hashes) benefits from the same Bloom-plus-cell trick when the natural sort order and the query predicate disagree.

### 🎯 Takeaway (Hợp)
Before rewriting your lakehouse to a geometry-sorted layout, try adding a Bloom-filtered cell column and re-measuring — the post's numbers say you may recover most of the skipping at 0.2 % storage overhead. Cách này không thay thế được sort đúng, nhưng đủ để mua thời gian cho các bảng CDC đã tồn tại.

### 💡 Example
```python
import sedona.spark as sd

# Write three layouts of the same GeoParquet file with 50k-row row groups
for name, key in {"geo": "s2", "name": "place", "random": "rnd"}.items():
    sd.sql("SELECT * FROM buildings").to_parquet(
        f"layout_{name}.parquet",
        sort_by=[key],
        single_file_output=True,
        max_row_group_size=50_000,
        geoparquet_version="1.1",
        options={"bloom_filter_enabled::cell": True},
    )

# Query cost: 4/77 row groups vs 54/77 vs 77/77
sd.sql("""
    SELECT COUNT(*) FROM buildings
    WHERE ST_Intersects(geom, ST_MakeEnvelope(-122.34, 47.60, -122.32, 47.62))
""").show()
```

### 🔭 Overview (Tổng)
ESP-IDF v5.3.6 is a security-heavy point release for the still-supported v5.3 line, and it does two things that matter beyond a normal maintenance drop: it fixes at least five CVE-class memory-safety bugs across HTTP Server, Protocomm, Bluetooth (Bluedroid), LWIP DHCP and the JPEG decoder, and it disables ECDSA Secure Boot V2 on production ESP32-H2, ESP32-C5 and ESP32-P4 devices — plus preview silicon H4, S31 and H21 — after a vulnerability was found in the ECDSA verification flow. For any team shipping firmware on those SoCs, this is not a cosmetic patch: an ECDSA-signed image will no longer boot until the project moves to RSA Secure Boot V2 keys.

### 🔬 Details (Phân)
The memory-safety patches are precisely scoped. `esp_http_server` and its websocket handler get a null-pointer-dereference fix that could be crashed from crafted client headers; `protocomm` fixes username-length validation and additional null-pointer paths hit during Wi-Fi provisioning; Bluedroid gains out-of-boundary read hardening in AVRCP vendor-command parsing plus L2CAP length checks; the LWIP DHCP server rejects specially crafted packets that previously caused OOB reads; and the JPEG decoder ships stricter picture-parse checks under advisory GHSA-v6r2-f6p2-88cj. None of these are theoretical — they are the kind of issues a Wi-Fi provisioning session or a BLE probe from a hostile peer can reach today.

The bigger, more disruptive change is the ECDSA Secure Boot V2 disable. Espressif's release note calls the vulnerability out explicitly as a flaw in the ECDSA-based Secure Boot flow and turns the feature off in the code path for H2, C5, P4 production silicon plus H4, S31 and H21 preview parts. RSA Secure Boot V2 remains supported and is now the mandatory path forward on those chips; any project that had committed to ECDSA keys during pilots must regenerate an RSA keypair, re-sign firmware images and update the `bootloader_signing_key.pem` reference before the next OTA. Devices already deployed with ECDSA-signed firmware keep booting the image they were flashed with, but a new signed image will not verify.

The v5.3 line as a whole remains active, but two adjacent facts are worth noting. ESP-IDF v5.2 shipped its last bugfix (v5.2.8) on 11 September and is now end-of-life, with users pointed at v6.0.3 or newer. v5.3 is therefore the current oldest supported branch, and 5.3.6 is the release that shops on 5.3 must land. The changelog also refactors small pieces of the security-boundary code without changing user-facing APIs, so the upgrade should be a rebuild and reflash rather than a sketch rewrite — the sharp edge is the signing-key work above.

### 🎯 Takeaway (Hợp)
Anyone with H2, C5 or P4 in the fleet — including preview boards — should upgrade to v5.3.6, regenerate RSA Secure Boot keys and cut a new signed OTA before their next production ship. Với các CVE trong HTTP/BLE/JPEG, chỉ cần rebuild là đủ; phần Secure Boot mới là chỗ phải sửa toolchain và pipeline ký firmware.

## 4. Uber Ships Claimed-Error Retry Ownership and Cuts Storm Radius From 25 Hops to 3

| Field | Value |
|---|---|
| 📅 Date | 17/09/2026 |
| 🏷️ Topic | Research |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `retry-storm` · `service-mesh` · `error-ownership` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
Uber's engineering team has published the design behind an in-mesh retry-storm guardrail that has been running in production for months and, during a November 2025 outage on their Core Entity service, blocked 9.5 million spurious requests inside a single degradation window. The core idea is small and general: propagate a header that says which service originally caused an error, and let callers upstream refuse to retry unless they see that claim. The post lays out the math for retry amplification, the header semantics, and the deployment shape — all of which apply to any distributed system with a retry policy, from Airflow-triggered service calls to inference gateways.

### 🔬 Details (Phân)
The amplification math is the anchor. Without controls, request volume at each node in a call chain follows `R^d × N`, where R is the retry count, d is depth and N is baseline load; a single retry across three hops multiplies traffic at the deepest node by 8×. A uniform per-service retry budget B reduces that to `(1+B)^d × N`, so a 10 % budget across six hops caps amplification at 1.33× regardless of where the failing node sits. Retry budgets alone still let callers fight over the "cause" of an error, though — an outage two hops down looks like an internal error two hops up, and each layer independently decides to retry.

The claimed-error mechanism resolves that. A service claims ownership only when no downstream calls failed inside the same request, meaning it is the actual cause; otherwise it forwards the error unclaimed. The claim rides on an `x-uber-error-claim` header with three states — Claimed, Unclaimed, Missing — and callers retry only on claimed errors. The rule that makes it work is simple: if edges A → B and B → C are fail-close, and C returns a claimed internal error, B retries C; if C returns an unclaimed error (because C's own downstream failed), B does not amplify. During the November 2025 Core Entity outage — five hops deep — this stopped 9.5 M spurious requests, and internal metrics show the maximum retry-storm radius dropping from 25 hops to 3 and average depth from 20 to 2.

There is a supporting piece that keeps the design honest. Uber's service dependency analysis correlates inbound failure timestamps with outbound failure timestamps, so a claim can be validated against actual downstream state rather than the caller's word. The team classes about 2 % of edges with more than 100 failures per minute as coincidental noise, distinguishing them from correlated failure fronts. The pattern is language- and framework-agnostic; the concrete implementation uses YARPC middleware, but a bare gRPC or HTTP fleet can adopt the same header contract with a small interceptor on each side.

### 🎯 Takeaway (Hợp)
Any team running multi-hop pipelines — Airflow calling internal services, agent frameworks calling a chain of tools, or an event-driven microservice mesh — can steal the header protocol without adopting YARPC. Đặt retry budget + claimed-error header trước khi thêm queue-based smoothing, vì đây là fix căn nguyên chứ không phải bù đắp downstream.

### 💡 Example
```go
// Sketch: middleware that only retries when the callee has "claimed" the error.
func retryIfClaimed(next Caller) Caller {
    return CallerFunc(func(ctx context.Context, req Request) (Response, error) {
        resp, err := next.Call(ctx, req)
        if err == nil {
            return resp, nil
        }
        claim := resp.Header.Get("x-uber-error-claim") // Claimed | Unclaimed | Missing
        if claim != "Claimed" {
            // Downstream forwarded a symptom; do not amplify the storm.
            return resp, err
        }
        // Retry only the true cause, and within the caller's budget.
        return next.Call(ctx, req)
    })
}
```
