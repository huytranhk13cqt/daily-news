### 🔭 Overview (Tổng)
Databricks announced general availability of the Genie One Model Context Protocol server, a managed endpoint that lets any external agent — Claude, ChatGPT, Cursor, or a bespoke framework — pull the same governed business context that Databricks users already reach through Genie. The MCP lives inside Unity Gateway, which handles authentication, audit logging and centralised policy so that connecting a new agent no longer means re-implementing entitlements. For data teams that have been building their own retrieval endpoints on top of the Genie API, this is a signal to consider retiring bespoke shims in favour of a maintained protocol surface.

### 🔬 Details (Phân)
The MCP exposes a small set of tools an agent can call to query Genie One for insights, retrieve structured and unstructured result sets, poll incremental query progress, and steer response behaviour. Grounding happens against the Genie Ontology, so cross-agent answers reference the same metric definitions and dimensional joins rather than the fragmented ones an agent might otherwise infer from raw schemas. An accompanying MCP App renders interactive visualisations and citations inside the calling application, which reduces the "answer without provenance" failure mode common to agent-plus-warehouse setups.

The GA lands in a market where MCP has become the connective tissue for enterprise agents — Snowflake, AWS IoT Greengrass and others have all published MCP servers in the last quarter — but Genie One MCP is differentiated by binding directly to Unity Catalog governance rather than to a lower-level SQL surface. Prior to this release, teams typically wrote a thin FastAPI wrapper that translated agent tool calls into Databricks SQL statements; that pattern loses row-level filters, semantic metric definitions, and audit fidelity.

Adoption cost is low for shops already on Unity Catalog: the MCP is a managed endpoint enabled at the workspace level, and existing entitlements carry over. Teams that have not consolidated on the Genie Ontology, however, will need to invest in curating shared metric and dimension definitions before external agents produce consistent answers.

### 🎯 Takeaway (Hợp)
If a team already runs Genie against Unity Catalog, the migration from a hand-rolled Genie proxy to the managed MCP is largely a configuration change. Điểm cần chú ý là chất lượng ontology quyết định chất lượng câu trả lời cross-agent — nên đầu tư vào metric definitions trước khi mở endpoint cho các agent bên ngoài.

### 💡 Example
```yaml
mcp:
  name: genie-one
  transport: http
  endpoint: https://<workspace>.cloud.databricks.com/api/2.0/mcp/genie
  auth:
    type: oauth2
    scope: "genie.read genie.query"
  tools:
    - query_genie
    - fetch_result
    - poll_progress
    - shape_response
```

## 3. AWS Big Data Publishes a Metadata-Size Formula for Scaling Amazon MSK Consumer Groups Past 500 Members

| Field | Value |
|---|---|
| 📅 Date | 22/09/2026 |
| 🏷️ Topic | Tutorial |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `amazon-msk` · `consumer-groups` · `kip-848` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
AWS Big Data published operational guidance for teams whose Amazon MSK consumer groups have grown into the thousand-member range, where the default 1 MB record limit on the internal `__consumer_offsets` topic starts to reject group-metadata commits. The post gives an explicit sizing formula, a set of breakpoints tied to member count, and a walkthrough of raising both the topic-level `max.message.bytes` and the broker-level `replica.fetch.max.bytes` in lockstep. For anyone running Kafka-Streams-style deployments or MirrorMaker clusters on MSK, it is a compact reference for the exact knobs that get missed in most first-time scale exercises.

### 🔬 Details (Phân)
The core mechanic is that Kafka encodes group-membership metadata into a single record on `__consumer_offsets`; when the group grows, that record grows past the 1 MB default and the group can no longer rebalance. AWS gives the estimator `member_count × (3 × avg_topic_name_bytes + 2 × client_id_bytes + ~200 bytes overhead)`, which puts a 1,000-member group with 50-byte topic names and 40-byte client IDs at roughly 430 KB — comfortably under 1 MB, but a shorter naming convention or larger group can flip that in a hurry. The recommendation curve is 1 MB below 500 members, 2 MB in the 500-1,000 range, 2-5 MB from 1,000-2,000, and group splitting above that.

A critical pairing that the post calls out is `replica.fetch.max.bytes ≥ max.message.bytes`, otherwise followers cannot replicate the enlarged offset record and the cluster becomes silently under-replicated. Broker sizing guidance shifts to `kafka.m5.xlarge` or larger for groups over 500 members. The article also frames the forward path: Apache Kafka 4.0's KIP-848 server-side assignor moves group state off `__consumer_offsets` entirely and removes this class of failure, so teams on the roadmap for Kafka 4.0 upgrades can treat the 5 MB ceiling as a bridge rather than a permanent target.

### 🎯 Takeaway (Hợp)
Audit your `__consumer_offsets` topic config today, apply the formula to your largest group, and confirm `replica.fetch.max.bytes` is at least equal — this is one of the cheapest hardening steps on a Kafka cluster. Với các cluster đã có consumer group vượt vài nghìn members, kế hoạch nâng cấp lên Kafka 4.0 (KIP-848) đáng đưa vào roadmap ngay.

### 💡 Example
```bash
# Raise the internal offsets topic to 2 MB
kafka-configs.sh --bootstrap-server "$BOOTSTRAP" \
  --entity-type topics \
  --entity-name __consumer_offsets \
  --alter \
  --add-config max.message.bytes=2097152

# Match the broker replica fetch limit (rolling restart required)
kafka-configs.sh --bootstrap-server "$BOOTSTRAP" \
  --entity-type brokers --entity-default \
  --alter \
  --add-config replica.fetch.max.bytes=2097152
```

### 🔭 Overview (Tổng)
Cactus Compute released Needle 2, a 14 MB open-source language model published on Hugging Face under Apache 2.0 that is designed to run entirely on the Raspberry Pi 5's CPU — no AI HAT, no GPU, no cloud round-trip. Unlike a general chatbot, Needle 2 is trained to pick a Python function from a supplied toolset and fill in its arguments, which makes it a fit for turning natural-language commands into local actions on IoT hardware. Raspberry Pi's own newsroom featured the model, and the packaging as a `pip`-installable `cactus-needle` library lowers the barrier for hobbyists and integrators considering an on-device NLU layer.

### 🔬 Details (Phân)
The model weighs 14 MB on disk and about 28 MB per native session, and the published benchmarks on a Raspberry Pi 5 (8 GB) sit between 76 ms and 149 ms end-to-end per task, with prefill throughput of roughly 461-488 tokens per second. Those numbers put it in the range where a voice or text trigger can produce a tool call inside a single frame of a physical UI loop, which is the qualitative threshold that separates "usable local automation" from "cloud-latency assistant". Weights and inference code live at `github.com/cactus-compute/needle` and the Hugging Face repo `Cactus-Compute/needle2`.

Positioning-wise, Needle 2 is closer to Meta's Llama-Guard-Prompt-Guard family or Google's Gemma-nano tool-use variants than to a general SLM — its output surface is a constrained function-call schema rather than free-form text. That makes it complementary to the ESP32 and Arduino ecosystems, where the Pi 5 typically acts as the gateway node, and it aligns with the broader shift, visible across Espressif, Arduino UNO Q and AWS IoT Greengrass releases this month, toward pushing at least the intent-recognition layer down to the edge. Adoption cost is low: an `@needle.tool` decorator over an existing Python function is enough to expose it, and the license permits commercial use without royalty.

### 🎯 Takeaway (Hợp)
For Pi-based home automation, edge control panels or field diagnostics kits, Needle 2 is worth a prototype this week — it collapses a category of code that used to require either a cloud API or a full local LLM stack. Với các dự án cần latency thấp và tính riêng tư, đây là một lựa chọn đáng thử ngay trên phần cứng đã có sẵn.

### 💡 Example
```python
import needle

@needle.tool
def save_note(text: str):
    """Append a note to a local text file."""
    with open("notes.txt", "a") as f:
        f.write(text + "\n")

agent = needle.Needle(tools=[save_note])
agent.run("Save a note that says the cooler is working.")
```

### 🔭 Overview (Tổng)
AWS Big Data documented how Moeve reduced dbt-on-Athena project onboarding from days to about 15 minutes by pushing pipeline plumbing behind a shared launcher contract and running the actual transformations in AWS Fargate against a per-team data lake account. The architecture is worth studying because it captures a common pattern — many small dbt projects sharing one execution engine — without regressing on governance or team isolation. Their CI feedback loop also dropped from 8-10 minutes to under 2 minutes by validating models locally against DuckDB before hitting Athena.

### 🔬 Details (Phân)
The runtime is a Step Functions state machine that orchestrates dbt runs on a Fargate task, with Athena as the compute engine, DynamoDB as the configuration store for per-project parameters, and EventBridge for publishing completion events that downstream jobs subscribe to. Cross-account roles let each business team keep transformations in its own data lake account while inheriting the shared launcher; because DynamoDB holds the parameters, ops changes such as swapping a warehouse or adjusting concurrency require no code deploy. Runs are idempotent, which erases the operational distinction between the daily incremental and a historical reprocess.

The two design boundaries Moeve identifies are worth adopting even outside AWS: a launcher contract of "parameters in, events out" and a strict separation between "run a dbt project" and "orchestrate many dbt projects". Locally, developers use DuckDB as a fast dbt adapter for CI, catching most modelling regressions before they consume Athena scan budget. This mirrors the pattern the DuckDB team documented earlier in the year and echoes what teams building lakehouse CI on GitHub Actions have adopted.

Migration cost is real but bounded — a new project only needs to write its dbt models and register a DynamoDB config row — which is what unlocks the day-to-minutes onboarding number.

### 🎯 Takeaway (Hợp)
Teams operating more than a handful of dbt projects on Athena, Redshift or BigQuery should copy the launcher-contract-plus-event-bus split; even without Step Functions, the pattern maps cleanly onto Airflow, Dagster or Argo. Đặc biệt, ý tưởng dùng DuckDB làm CI local cho dbt Athena models là điểm đáng thử ngay tuần này.

```json
  "athena_workgroup": "data-platform-prod",

  "notify_topic": "arn:aws:events:eu-west-1:123456789012:bus/data-platform"
```

### 🔭 Overview (Tổng)
Arduino published a project write-up for Nuvi, an under-30-cm desktop companion built on the recently launched Arduino UNO Q board that pairs a Linux processor with a real-time microcontroller in a single package. The interesting part is not the puppet-inspired form factor but the concrete distribution of work between the UNO Q's two brains — servo timing and touch sensing on the MCU side, voice and reasoning on the Linux side — running Gemini for understanding, Piper for on-device text-to-speech, and optional web search and smart-home integrations on top. It doubles as a reference for what the UNO Q architecture actually enables outside of Arduino's marketing.

### 🔬 Details (Phân)
The build uses four hobby servos for arms and ears, two serial servos for a two-axis neck, a small display, capacitive touch inputs and a microphone; the MCU handles servo PWM and touch debouncing so the Linux side can be interrupted or updated without visible motion glitches. The Linux side runs Piper for local speech synthesis and calls out to Gemini for the reasoning loop, with smart-home control layered on via standard Arduino Cloud integrations. Piper is significant here because it keeps voice generation on-device even when the reasoning call goes to the cloud, which shrinks the perceived latency of every reply and eliminates one class of privacy exposure.

Positioning-wise, this fills the same slot that hobbyists filled last year with a Raspberry Pi plus an ATmega co-processor, but as one board with a maintained SDK, tighter power budget and shared Arduino tooling. Project files and full walkthroughs live on the Arduino Project Hub, and the UNO Q is sold through the official Arduino Store and authorised distributors.

### 🎯 Takeaway (Hợp)
For makers evaluating the UNO Q, Nuvi is the first substantive third-party reference build showing where the Linux/MCU split lands in practice, and it's a useful template for anyone building an always-on voice interface on hobby-scale hardware. Điểm mạnh nằm ở việc Piper chạy local giữ được độ trễ và quyền riêng tư khi reasoning vẫn dùng cloud.

### 💡 Example

```yaml
      - name: gemini-agent

        tools: [smart_home, web_search]
    audio:
      capture: alsa:hw:1,0
      playback: alsa:hw:0,0
```
