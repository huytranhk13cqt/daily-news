## 1. AWS Announces Spark Connect on Amazon EMR on EC2 With 1,000 Concurrent Sessions per Cluster

### 🔭 Overview (Tổng)
AWS announced Spark Connect on Amazon EMR on EC2, letting data engineers develop and debug PySpark interactively from Amazon SageMaker Unified Studio Data Notebooks or a local IDE while the engine executes on a shared long-lived cluster. The release removes the historic requirement to install Spark locally or spin up a personal cluster per developer, and instead treats the cluster as a multi-tenant service reached over gRPC/TLS. For teams that have been running one EMR cluster per developer, or paying for a separate serverless SKU for interactive work, this is a concrete consolidation lever.

### 🔬 Details (Phân)
Under the hood, Spark Connect on EMR runs on a client-server model. When a session starts, EMR launches a Spark Connect Server as a YARN application on the target cluster and issues a session endpoint plus authentication credentials; the lightweight PySpark client then ships DataFrame and SQL operations to that server over an encrypted connection and streams results back. A single cluster supports up to 1,000 concurrent sessions with isolated permissions, each carrying its own IAM execution role and lifecycle, which is what makes shared infrastructure viable across a whole team without cross-tenant leakage. Because interactive sessions run on the same cluster with the same configuration as production batch jobs, the version-mismatch and dependency-drift bugs common to laptop-based Spark development largely disappear.

The requirements are specific: EMR clusters must run `emr-spark-8.0.0` or later with `SessionEnabled` in the cluster config, Python 3.9+ locally with `pyspark[connect]` installed, and IAM policies granting `elasticmapreduce:StartSession` plus `iam:PassRole`. Notable limitations to plan around include a mandatory client-server Spark version match, no RDD API support (DataFrame and SQL only), one-hour token expiry on the auth token, and a 60-minute default idle session timeout — so debugging workflows that leave a session parked overnight need explicit reconnection logic. IDE integration follows the standard PySpark experience: breakpoints, step-through, and variable inspection in VS Code, PyCharm or Jupyter work against the remote engine.

Positioning-wise, this narrows the practical gap between EMR on EC2 and EMR Serverless / Databricks Connect for interactive development while keeping EMR's cost model. Teams that have adopted per-user Databricks or per-user EMR clusters as a workaround for interactivity can now share one long-lived cluster and rely on IAM session isolation instead of infrastructure isolation.

### 🎯 Takeaway (Hợp)
Any team already on EMR on EC2 should stand up an `emr-spark-8.0.0` cluster with `SessionEnabled` and try attaching from a SageMaker Unified Studio Data Notebook or VS Code — the setup is a config flag plus a client pip install rather than a re-platforming exercise. Đây là bước hoàn thiện quan trọng để EMR on EC2 phục vụ luôn cả interactive workload thay vì buộc phải mở EMR Serverless bên cạnh.

### 💡 Example
```python
from pyspark.sql import SparkSession

# host, session_id, auth_token returned when EMR starts the Spark Connect Server
url = (
    f"sc://{host}:443/"
    f";use_ssl=true"
    f";x-aws-proxy-auth={auth_token}"
    f";authorization={session_id}"
)
spark = SparkSession.builder.remote(url).getOrCreate()
spark.sql("SELECT 'Hello from EMR on EC2' AS message").show()
```

### 🔭 Overview (Tổng)
Databricks published a case study describing how Concurrence, a healthcare AI company, funnels both its clinical inference workload and its developer coding-agent traffic through Unity Gateway. The published numbers are unusually concrete: 100.8 billion input tokens and 11.2 million LLM calls per 30-day window, an annualized run rate near 1.2 trillion input tokens, and 61 billion cumulative input tokens across roughly 360,000 coding-agent requests since July 2026. For teams still deciding whether an AI gateway is worth the operational overhead, the piece is a rare look at what governance and cost accounting look like once volume is real.

### 🔬 Details (Phân)
The architecture stitches Lakebase for operational agent and conversation state, Unity Catalog for data and AI asset governance, Delta tables for immutable patient events, Zerobus Ingest for the roughly 2.7 million world-model events processed monthly, and Apache Spark Declarative Pipelines for the clinical derivations built on top. Agent traces stream into Delta tables where scheduled `ai_query` jobs score interactions for quality and safety before writing the results back to governed storage. Concurrence explicitly records new patient facts as immutable events rather than overwriting rows — a "world model" pattern — so that agents can be tested against a preserved history without contaminating live records, and the ratio of simulation and evaluation traffic to production traffic runs about 7 to 1.

Coding-agent governance is the second half of the story. All coding-agent model and MCP tool traffic is routed through Unity Gateway's coding CLI, so every request is attributed to the requesting engineer, tool access is managed centrally through group permissions, and usage is queryable via `system.ai_gateway.usage`. In July, fourteen individual users generated 35.85 billion input tokens through this path, with 95.37% served from cache — a data point that reframes what an AI gateway is doing for cost as much as governance. Compliance drives the routing logic: Concurrence maintains HIPAA, GDPR and SOC 2 with HITRUST and ISO 27001/42001 in progress, and the router prevents protected health information from reaching non-BAA-covered models. Batch workloads run `ai_query` on Databricks-hosted Claude under a business associate agreement, and each customer organization gets an isolated schema and service principal.

For readers running a homegrown proxy in front of LLM providers, the notable design boundary is treating coding-agent traffic and production inference as one governance surface rather than two. That collapses the "who used what model and for which patient" question into a single query.

### 🎯 Takeaway (Hợp)
If your organization is stitching together per-team OpenAI/Anthropic keys and separate observability plans, this case study is a useful counter-benchmark: a single gateway can pay for itself in cache-hit economics alone at seven-figure-plus request volumes. Điểm đáng học là mô hình dùng chung một gateway cho cả coding agent lẫn production inference — quan trọng nhất là chuyện attribution per-user và cost allocation theo team.

### 💡 Example
```sql
-- Per-user attribution over the last 30 days through Unity Gateway
SELECT
  request_identity,
  COUNT(*)                                  AS calls,
  SUM(input_tokens)                         AS input_tokens,
  SUM(cache_read_input_tokens)              AS cache_reads,
  ROUND(100.0 * SUM(cache_read_input_tokens)
        / NULLIF(SUM(input_tokens), 0), 2)  AS cache_hit_pct
FROM system.ai_gateway.usage
WHERE request_time >= current_timestamp() - INTERVAL 30 DAYS
GROUP BY request_identity
ORDER BY input_tokens DESC;
```

### 💡 Example
```python

bedrock = boto3.client("bedrock-runtime")

    "Which age groups had the highest rates of emergency department "
    "visits for tooth disorders? Use only the enriched dental dataset."
)

    modelId="anthropic.claude-3-5-sonnet-20241022-v2:0",

    }),
)
print(json.loads(resp["body"].read())["content"][0]["text"])
```

### 🔭 Overview (Tổng)
An independent developer using the handle Haris published KryonOS, an open-source operating environment for ESP32 boards that bundles a GUI layer, a graphics library and a JavaScript runtime with SD card filesystem access and a hardware API. Hackaday covered the project on 23 September, framing it against the historical parallel of MicroPython's improbable path to becoming a mainstream embedded language. The immediate audience is hobbyists on ESP32 display boards — the popular "Cheap Yellow Display" module is called out explicitly — but the more interesting signal is that JavaScript is quietly following the same route.

### 🔬 Details (Phân)
Beyond the runtime itself, KryonOS ships a small app-store concept for installable software on the device, conceptually similar to the Badge.Team ecosystem that grew up around DEF CON and Hacker Hotel hardware badges. The stack is designed for ESP32 boards equipped with a display, and the JavaScript layer sits on top of the graphics and hardware APIs so that a web developer can write a functional on-device application without touching C/C++, Arduino sketches or ESP-IDF component boilerplate. Weights and code live at `github.com/Haris16-code/KryonOS` and the project is single-maintainer at this stage, which affects how much production weight it can currently carry.

Positioning-wise, KryonOS is not competing with ESP-IDF for firmware developers; it competes with the "throw MicroPython on the board and see how far it gets" pattern for makers who want a higher-level environment on constrained hardware. That is a real audience — the same audience that made MicroPython viable — and JavaScript's familiarity to web developers is a genuinely different funnel than Python's familiarity to scientific and scripting audiences. Practical caveats apply: RAM and flash on a typical ESP32 constrain the size of the running interpreter and the complexity of on-device apps, and there is no formal LTS story yet.

For anyone using an ESP32 with a display as an internal tool platform, KryonOS is worth a look as a lower-friction alternative to writing yet another custom UI in LVGL and C.

### 🎯 Takeaway (Hợp)
Treat KryonOS as an interesting datapoint about JavaScript reaching microcontroller-class devices rather than a production stack, and try it on a spare Cheap Yellow Display if you already have one lying around. Với các dự án nội bộ dùng ESP32 có màn hình, đây là một lựa chọn đáng thử để giảm thời gian dựng UI so với LVGL truyền thống.

### 💡 Example
```javascript
// Minimal KryonOS app: draw a label and print an ADC read on tap

const label = ui.label({ x: 10, y: 10, text: "Tap to read ADC" });

  const mv = hw.adc.readMillivolts(34);
  label.setText(`ADC(34) = ${mv} mV`);
});
```
