### 🔭 Overview (Tổng)
Databricks announced the Unity Gateway CLI, a centralized tool that lets administrators approve models, tools, MCP servers, skills and spending policies for coding agents from a single Govern surface, and lets developers launch those approved agents with commands as terse as `ug claude` or `ug codex`. The release turns the AI-gateway story that yesterday's Concurrence case study described at the architecture level into a concrete package a platform team can hand a developer on day one. Where individual engineers currently paste API keys into `.zshrc`, this shifts the surface to one governed CLI that carries policy with it.

### 🔬 Details (Phân)
The CLI is anchored in Unity Gateway's Agent Configuration console under Govern, where admins pin the list of allowed frontier models, approved MCP tool servers, skills and per-team spending policies. `ug` then acts as the developer entrypoint: `ug claude` launches an approved Claude coding session, `ug codex` launches an approved Codex session, and `ug usage` returns per-user consumption drawn from the same trace and cost tables Unity Gateway populates for production inference. Traces from every tool call and skill invocation write to a unified trace table on the lakehouse, so a platform team can query `system.ai_gateway.usage` for coding-agent spend on the same schema as their model-serving spend, closing the historical gap between engineering-tool budgets and product AI budgets.

Two features do more than the CLI itself. Smart Routing chooses a model per request based on task complexity — Databricks reports "35% cost savings on our internal coding benchmark" — and Budget-Aware Defaults automatically fall back to a cheaper model as a group approaches its spending cap, so overspend fails soft rather than hard. Databricks also cites its own operational win from the same tracing surface: seven MCP tool bug fixes surfaced through Unity Gateway traces and Genie One removed roughly $1.2 million per year in wasted AI spend inside Databricks itself, and Concurrence's 61 billion input tokens across roughly 360,000 coding-agent requests are quoted as the customer-scale reference point.

Positioning-wise, the CLI closes the last gap in Databricks' AI-gateway story. Yesterday's Concurrence write-up showed the read-side value — one query for "who used what model on which patient" — but did not describe how a coding agent actually gets onto an engineer's laptop; the CLI is that piece.

### 🎯 Takeaway (Hợp)
Platform teams already routing production model traffic through Unity Gateway should pilot `ug claude` or `ug codex` with a single squad, wire Smart Routing on for that squad, and compare the resulting `system.ai_gateway.usage` numbers against their current per-user API key spend. Về mặt vận hành, đây là bước tự nhiên để attribution per-user không còn dừng ở production inference mà kéo được cả traffic của coding agent vào cùng một mặt bằng governance.

### 💡 Example

```bash
# Inspect this month's coding-agent spend attributed to the current user
```

### 🔭 Overview (Tổng)
Databricks staff engineer Angel De Leon published a walk-through of an in-house security-review pipeline built entirely on Databricks primitives. The system uses seven focused agents rather than one general-purpose reviewer, and it stores every standard, request, piece of evidence and decision as governed data in Unity Catalog. The framing throughout is deliberately conservative: automation completes routine, low-risk requests in minutes, and higher-risk items get routed to humans with the evidence pre-assembled.

### 🔬 Details (Phân)
The seven agents split the workflow into single-responsibility roles: an intake agent that runs the conversational request UI, a risk-assessment agent that assigns a tier with cited evidence, a requirements agent that maps applicable security standards to the proposed architecture, a set of specialized review agents keyed to request type, a validation agent that builds a checklist for higher-risk items, a workflow agent that drives follow-ups and escalations, and a learning agent that surfaces prompt improvements from reviewer feedback. Each agent runs against Databricks-hosted foundation models — Claude Haiku, Sonnet and Opus are named — with model choice varying by task complexity, and the orchestration itself runs on Lakeflow Jobs on serverless compute. Databricks Apps hosts both the intake conversation and the executive-facing dashboards that report on volume, risk distribution, automation rate and estimated time saved.

The design boundary that separates this from an off-the-shelf "AI security reviewer" is that policy, evidence and outcomes are governed artifacts in Unity Catalog rather than opaque state inside an agent. Standards are versioned tables; requests, evidence and decisions land in Delta so downstream audits and metrics use the same schema as any other data product. The post is explicit that the learning agent proposes prompt changes but does not deploy them: humans stay in the loop on prompt updates, exceptions and consequential decisions.

For teams considering a similar build, the piece is unusual in showing the metric surface — automation rate by risk tier, throughput, estimated time savings — rather than only the architecture picture, and in resisting the temptation to unify the seven agents into one super-agent.

### 🎯 Takeaway (Hợp)
If your organization already owns Unity Catalog and Lakeflow Jobs, this is a credible reference design for turning an operational review process into a governed, measurable agent workflow without leaving the platform. Điểm đáng chú ý là mô hình tách nhỏ bảy agent theo trách nhiệm rõ ràng thay vì gom vào một agent tổng hợp — dễ debug và dễ đo hiệu quả hơn.

### 💡 Example
```python
# Lakeflow Jobs task that runs the risk-assessment agent against a governed request
from databricks.sdk.runtime import spark

req = spark.read.table("secreview.requests").where("status = 'intake_complete'")

# ai_query invokes the Databricks-hosted foundation model for tier assignment
tiered = spark.sql("""
  SELECT
    request_id,
    ai_query(
      'databricks-claude-3-5-sonnet',
      concat('Classify this security-review request into tier low/medium/high. ',
             'Cite evidence from the request text. Return JSON.\n\n',
             request_text)
    ) AS tier_json
  FROM secreview.requests
  WHERE status = 'intake_complete'
""")

tiered.write.mode("append").saveAsTable("secreview.tier_assignments")
```

## 3. SageMaker Unified Studio Adds Domain-Level VPC Networking to Enforce One Network Per Domain

### 🔭 Overview (Tổng)
AWS added domain-level VPC networking to Amazon SageMaker Unified Studio, letting administrators pin one VPC configuration to a domain and have every new project inside that domain inherit it automatically. Where per-project networking created a familiar enterprise problem — inconsistent subnet choices, missing VPC endpoints and hard-to-triage connectivity failures — the domain scope collapses configuration into a single place. For a platform team that has been chasing per-project tickets from data engineering, analytics and ML users, this is a straightforward operational win.

### 🔬 Details (Phân)
The prerequisites are concrete rather than aspirational: a VPC with DNS hostnames and DNS support turned on, at least two private subnets across different Availability Zones, and AWS's own baseline of "at least five available IP addresses per expected Amazon SageMaker Unified Studio project", with a `/24` or larger subnet recommended for production domains. Eleven VPC endpoints are required in total: S3 as a gateway endpoint plus interface endpoints for Glue, SageMaker API, SageMaker Runtime, CloudWatch Logs, CloudWatch Monitoring, STS, DataZone, ECR API, ECR Docker Registry and KMS. Configuration itself is a small flow in Domain Management → Settings → Add VPC: pick the VPC, choose at least two private subnets in different AZs, optionally supply a security group, and wait for the state to flip to Ready.

Two limits are worth planning around. First, updating a domain's VPC does not retroactively rewire already-provisioned resources: projects that never had a VPC can adopt the domain-level configuration in place, but projects that already carry their own VPC must be recreated to take the new settings, so a migration playbook needs to schedule that work. Second, everything downstream — analytics, ML, data engineering — sits behind the same VPC endpoints, so incident response and Flow Logs / CloudTrail auditing get simpler at the cost of losing the freedom to give one project a different network. The blog also ships a Python validation script (Python 3.8+, Boto3 1.26+) that probes S3, Glue and STS via the endpoints, resolves service DNS names against private IPs, and prints an explicit `[PASS] All services accessible via private VPC endpoints` when the configuration is healthy.

Positioning-wise, this brings SageMaker Unified Studio closer to how mature enterprises already run Amazon EMR and Amazon Redshift: one network per environment, not one per team.

### 🎯 Takeaway (Hợp)
If SageMaker Unified Studio is on the roadmap, define the domain VPC before the first project is created — retrofitting is possible but requires re-creating any project that already carries its own VPC. Với các domain đang có sẵn, hãy dự trù ngân sách thời gian để migrate cẩn thận thay vì bật thẳng cấu hình domain lên.

### 💡 Example

```python
ec2 = boto3.client("ec2")
sts = boto3.client("sts")
glue = boto3.client("glue")

```

### 🔭 Overview (Tổng)
Hackaday covered LakeShark, an open-source handheld multi-mode radio scanner built on a LilyGO T-Display P4 board — an ESP32-P4 microcontroller paired with a 4.1-inch AMOLED touchscreen — with an onboard Semtech SX1262 LoRa radio, GPS and a nine-axis IMU, and an external RTL-SDR Blog V3 or V4 dongle for the wider SDR workload. The project shows what the ESP32-P4 class of chip is now capable of when paired with a real host-scale display and an off-board SDR, and it is a useful reference implementation for anyone building a portable multi-protocol receiver on Espressif silicon. It is a maker project rather than a shipping product, but the codebase is public.

### 🔬 Details (Phân)
On the modes side, LakeShark decodes P25 Phase 1 trunking transmissions, ADS-B, POCSAG and legacy FM broadcast, and it exposes both a waterfall analysis view and a nearby-device detection mode that flags nRF24 traffic. The on-board SX1262 covers LoRa specifically, while the RTL-SDR does the general-purpose SDR heavy lifting; GPS provides both position and a time reference, and the IMU underpins orientation and gesture inputs on the touchscreen. Everything runs from the ESP32-P4 host with the AMOLED as the primary UI, and the code lives at `github.com/SAMS0N1TE/LakeShark` under an open-source license.

Positioning-wise, LakeShark occupies the space that used to require pairing an SDR dongle with a full laptop or a Raspberry Pi with a screen. The ESP32-P4's larger memory footprint and higher clock, together with an AMOLED that can actually render a waterfall at usable resolution, are what make a truly handheld form factor tractable — this is the same class of hardware the ESP32-DJ project on the same day and Arduino's VENTUNO Q board earlier this week both lean on for perception-heavy workloads. Practical caveats apply: it is a single-maintainer hobby project without an LTS story, RTL-SDR quality varies by dongle revision, and P25 trunking regulations differ by jurisdiction, so anyone building on top of it should treat the codebase as a starting point rather than a shipping stack.

For makers looking at ESP32-P4 as more than a "bigger ESP32-S3", LakeShark is a useful concrete demonstration that the chip can drive a genuinely portable, multi-radio, multi-mode receiver from a battery-powered board.

### 🎯 Takeaway (Hợp)
Treat LakeShark as an interesting datapoint that ESP32-P4 plus an AMOLED plus an RTL-SDR is now a viable handheld SDR class, and clone the repo on a LilyGO T-Display P4 if you already have one lying around. Về dài hạn, đây là tín hiệu rằng dòng ESP32-P4 sẽ tiếp tục lấn sang các use case portable trước đây phải cần một chiếc laptop hoặc Raspberry Pi.

### 🔭 Overview (Tổng)
Hackaday featured a final-year university project by an engineer called Zoe Skyforest that runs YOLOv8 Nano on a 4 GB Raspberry Pi 5 to count cars, trucks, buses and motorcycles at a roadside deployment, powered end-to-end by a 12 V lead-acid battery topped up from a single 100 W solar panel through a basic charge controller. The interest for an IoT audience is less the ML model and more the power-engineering discipline: what does it actually take to run a Pi 5 headlessly on solar for a real vision workload? The project is documented publicly at `mch170.com/projects/traffic_monitoring`.

### 🔬 Details (Phân)
The hardware pairs a Pi 5 with a 720 p USB webcam and cloud storage for the resulting counts, and the vision pipeline uses YOLOv8 Nano with a lightweight de-duplication algorithm to avoid counting the same vehicle multiple times as it crosses the camera's field of view. The interesting part is the power budget. To sit inside the solar envelope, the developer disables Bluetooth, PCIe, audio and HDMI outright at the firmware level; underclocks both CPU and GPU below their default profiles; and runs the whole stack headless with no attached monitor. Together those cuts pull the sustained load low enough that a 100 W panel plus a 12 V lead-acid battery is enough to keep the workload running through the night and cloudier days.

Positioning-wise, this fills the same edge-inference niche as commercial traffic counters from vendors such as Miovision and TrafficVision, but at a fraction of the parts cost — the entire stack is a Pi 5, a webcam, a solar panel and a battery. That does not make it a plug-and-play production replacement (weatherproofing, on-site theft, cellular backhaul and per-jurisdiction data-retention rules are all left as exercises), but it is a credible starting point for a municipality prototyping counting at a low-traffic intersection or for a research group running a study without capital budget. It is also a useful counter-example to the "you must go to a Jetson or a Coral" reflex for edge vision — on the Pi 5, YOLOv8 Nano gets close enough on classic 30 fps camera streams that a solar-only site is plausible.

The write-up is refreshingly explicit about the trade-offs, which is what makes it worth flagging rather than yet another "AI on Pi" demo.

### 🎯 Takeaway (Hợp)
For teams evaluating solar-powered edge vision on the Raspberry Pi 5, this project is a good baseline for the power-engineering steps that actually make it work — headless boot, disabled subsystems, underclocked CPU/GPU. Với các nhóm nghiên cứu giao thông ở địa phương, đây là một cách rẻ tiền và có thể tự dựng lại để chạy pilot mà không phải chờ vendor gateway thương mại.

### 💡 Example
```bash
# /boot/firmware/config.txt tweaks used to fit YOLOv8 Nano in a solar power budget
dtoverlay=disable-bt
dtoverlay=disable-wifi     # keep BT/Wifi off unless required for backhaul

hdmi_blanking=2
dtparam=pciex1_gen=0        # PCIe off; Pi 5 runs off SD/USB only

# Underclock CPU and GPU; run headless
arm_freq=1800
gpu_freq=400
disable_splash=1
```
