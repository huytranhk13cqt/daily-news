### 🔭 Overview (Tổng)
Databricks published a joint write-up with S&P Global Energy that describes how a multi-commodity structured data estate — spanning LNG, Chemicals, Crude Oil, Refined Products and Gas & Power — has been turned into a conversational surface without hand-built SQL pipelines or bespoke APIs per use case. The interesting design choice is that S&P puts subject-matter experts in charge of curating one Genie Agent per dataset group, then leans on Databricks' new managed MCP endpoints to expose those agents to any MCP-aware client with no additional glue code. For a data platform team that already lives inside Unity Catalog, this is a concrete template for shipping conversational access as a governed product rather than a research prototype.

### 🔬 Details (Phân)
Architecturally, the pattern is three-layer. Domain SMEs curate focused Genie Agents on a per-dataset-group basis — for LNG this means separate agents for assets, cargoes, tenders, outages, supply/demand, netbacks and prices — without writing agent code. Each Genie Agent then auto-exposes as a managed MCP server at `https://<workspace-hostname>/api/2.0/mcp/genie/{genie_space_id}` with two core tools (query submission and response polling), so any MCP client can call it as a first-class tool. A FastMCP proxy layer composes multiple group-level agents into commodity-level bundles with namespaced tools, which is what makes cross-domain questions such as "compare LNG spot with Refined Products margins" tractable through a single client connection.

The governance story is what separates this from a demo. Every generated query still runs through Unity Catalog permissions on native or federated tables, so row-level and column-level policies attach to the conversational surface automatically, and Lakehouse Federation brings non-Databricks sources in without ETL and inherits the same governance. The blog does not publish specific latency, precision or adoption percentages; it does report that development cycles "collapsed" to days for new dataset groups, and that S&P tracks the rate at which SMEs agree with generated SQL during curation as a leading adoption indicator rather than as a post-hoc quality metric.

Positioning-wise, this is the first customer case study that leans heavily on the managed MCP surface — Databricks' broader agent story so far has centred on Unity Gateway for coding agents; here it is Genie Agents and managed MCP for read-side analytics on production data.

### 🎯 Takeaway (Hợp)
Teams already using Unity Catalog and Genie should treat this as a reference for scoping — one Genie Agent per dataset group, not one per business unit — and for exposing agents through managed MCP so downstream clients (BI tools, agent frameworks, IDEs) reuse the same governed endpoint. Về mặt tổ chức, phần đắt giá không phải là MCP mà là kỷ luật để SME làm chủ curation thay vì để đội data platform gánh hết.

### 🔭 Overview (Tổng)
AWS Big Data Blog walked through how Delivery Hero rebuilt its ad measurement stack on Amazon Managed Service for Apache Flink, replacing an hourly batch pipeline that averaged a 61-minute event-to-record gap with a streaming pipeline that reports a 1.2-second average end-to-end delay. The migration cut monthly operational cost by about 57 percent and drove missing-data rates on core fields to near zero. For any team measuring ad performance, billing, or attribution on top of Kinesis today, this is a rare public write-up that pairs concrete before/after numbers with a full architecture and the specific data-quality lifts the streaming design produced.

### 🔬 Details (Phân)
The Flink job runs a five-stage pipeline — decompress/decrypt, deduplicate, enrich, attribute, aggregate — over two Amazon Kinesis Data Streams (user actions and orders) that fan in from Amazon SNS/SQS ingestion via Amazon EventBridge Pipes. Reference data such as campaign and product metadata is served from Amazon DynamoDB and decryption keys from AWS Secrets Manager, while sinks split three ways: billing events land on Apache Kafka, event logs write to Amazon S3 in Avro (also used for checkpoints), and aggregated metrics go to a reporting database. Amazon Managed Service for Apache Flink handles operational plumbing — checkpointing, scaling and recovery — so the Delivery Hero team could focus on the pipeline logic. At peak the job sustains 20,000 messages/second without back-pressure.

The data-quality lift is where the case study is most concrete. Missing session rate dropped from 30–40 percent to 0, missing customer IDs from 5 percent to 0.8 percent, and missing impression timestamps from 91 percent to 0.2 percent. Those are not incidental improvements: the previous hourly job could not always join related events landing across boundary windows, and the streaming model — with per-key state and a proper deduplication stage — closes the join windows that the batch design lost. Cost drops of the reported magnitude on such a stack usually come from removing spiky orchestration overhead and idle-compute time between hourly runs rather than from cheaper per-record compute, and the write-up is consistent with that.

For teams already on Kinesis but still batching downstream, the piece is a useful reference for both cost and quality: it is not just a latency-only success story.

### 🎯 Takeaway (Hợp)
If you own an ad-measurement, telemetry or billing pipeline that still batches on top of Kinesis, use this as an internal proposal template: quantify current missing-field rates, model the batch-orchestration overhead you would remove, and pilot a Managed Flink job on one Kinesis stream before committing to a full cut-over. Điều đáng học nhất là cách team này công bố cả latency lẫn tỉ lệ dữ liệu thiếu — hai chỉ số hay bị giấu khi nói về streaming.

// Sketch of the two-stream keyed join Delivery Hero uses as stage 3 (enrich).

    .keyBy(Action::getUserId)
    .connect(orders.keyBy(Order::getUserId))
    .process(new KeyedCoProcessFunction<>() {

        @Override public void processElement1(Action a, Context ctx, Collector<EnrichedEvent> out) {
            Order o = pendingOrder.value();
            if (o != null) out.collect(EnrichedEvent.of(a, o));
        }
    });

## 3. DuckDB Adds Native hf:// Protocol for Querying Hugging Face Datasets In Place

### 🔭 Overview (Tổng)
DuckDB shipped a native `hf://` protocol handler that lets any DuckDB client query datasets hosted on Hugging Face directly, without a prior download step. The team's framing is deliberately minimal: "DuckDB can read them directly, exactly where they are and without downloading anything, over the DuckDB `hf://` protocol." For ML and data teams already using DuckDB for lightweight local analysis, this collapses the usual staging step and makes the tens of thousands of datasets on the Hub queryable with the same SQL syntax you use for local files. For dataset publishers, it also means the standard Hub browse experience is now backed by a real query engine rather than a preview widget.

### 🔬 Details (Phân)
The protocol works transparently against CSV, JSONL and Parquet — the three most common formats on the Hub — and understands glob patterns and the Hub's revision syntax. A basic call is a plain `SELECT * FROM 'hf://datasets/datasets-examples/doc-formats-csv-1/data.csv'`; a partitioned dataset is a single-line glob such as `SELECT count(*) FROM 'hf://datasets/cais/mmlu/astronomy/*.parquet'`; and pinning to a specific revision uses the Hub's `@<ref>` suffix, e.g. `@~parquet` for the auto-converted Parquet mirror of a dataset. Because DuckDB pushes predicates and column projections into the Parquet reader over HTTP range requests, common "just answer this one question" workloads scan only the byte ranges they need rather than pulling the whole file.

Authentication for private or gated datasets goes through DuckDB's Secrets Manager, either as a direct token or by letting DuckDB pick up the token cached at `~/.cache/huggingface/token` — meaning that an engineer already logged in via the `huggingface-cli` gets zero-configuration access. There are no published latency or throughput numbers in the blog, and reads still pay the Hub's public egress path, so this is not a replacement for cloning a dataset when a training loop needs every byte many times; it is a replacement for the "download, unzip, inspect, delete" ritual that dominates the first hour with any new dataset.

Positioning-wise, the `hf://` protocol slots alongside DuckDB's earlier `s3://`, `azure://` and `gs://` handlers, so any tool that speaks DuckDB — including notebooks, dbt-duckdb and the recent dbt v2 integration — gets Hub access for free.

### 🎯 Takeaway (Hợp)
Add DuckDB's Hugging Face integration to the standard dataset onboarding path: query the Parquet mirror in place with a projection and a `WHERE` first, and only clone the dataset once you have decided it is worth the disk. Với các đội đang dùng DuckDB làm sandbox trước Snowflake/BigQuery, đây là cách nhanh nhất để đưa dataset public vào chung một mặt bằng SQL.

### 💡 Example
```sql
-- Query a Hub dataset directly, no download, with predicate pushdown to Parquet
SELECT subject, count(*) AS n
FROM 'hf://datasets/cais/mmlu/*/**/*.parquet'
WHERE answer = 'A'
GROUP BY 1
ORDER BY n DESC
LIMIT 10;

-- Private/gated dataset: create a secret once, then read normally
CREATE SECRET hf_token (TYPE HUGGINGFACE, TOKEN 'hf_xxx');
SELECT * FROM 'hf://datasets/your-org/your-private-dataset@main/data.parquet'
LIMIT 5;
```

### 🔭 Overview (Tổng)
Hackaday covered "Pocket Pico" by btech, an open project that resurrects the classic Heathkit HK-21 packet radio TNC on a Raspberry Pi Pico by running a full Z80 emulator on the RP2040 and executing the original HK-21 firmware unmodified. The unusual technical claim is that the Pico also handles Bell 202 modulation and demodulation in software at 1200 baud, so the entire packet-radio pipeline — Z80 CPU, AX.25 framing, modem — sits inside one $4 microcontroller with no dedicated modem chip. For amateur-radio and embedded audiences it is a compact demonstration of how much of a 1980s hardware bill of materials the current RP2040 class can subsume in software.

### 🔬 Details (Phân)
The stack is: an RP2040 core running a Z80 emulator, that emulator running the original HK-21 ROM binaries, an in-firmware Personal Bulletin Board System for station-to-station messaging, and a software Bell 202 modem that turns audio-frequency-shift-keyed tones into demodulated AX.25 Level 2 frames at 1200 baud. Hackaday quotes the project as "it literally runs the same firmware as the real HK-21" and highlights that the Pico "do[es] the work of modulating and demodulating Bell 202 audio tones at 1200 baud" without a dedicated modem IC. That last detail is what separates this from a straight retro-computing emulator: doing FSK demodulation in real time on the RP2040 is a non-trivial signal-processing budget, and it means the project stands in for a real physical-layer TNC on-air rather than only reproducing the user-facing behaviour.

Positioning-wise, this is another datapoint in a pattern the digest has flagged before — that low-cost Cortex-M0+ class hardware is increasingly able to replace fixed-function embedded devices from an era when radio, CPU and modem each demanded their own silicon. It is a maker project and does not compete with modern software-defined-radio stacks such as Direwolf on a Raspberry Pi 5, and the amateur-radio regulatory framing (licensing, band plans) still applies to anything transmitted from it. But as a reference build for anyone who wants a compact packet-radio TNC without hunting for surplus Kantronics or MFJ hardware, the entire recipe now fits on a single Pico plus an audio interface.

The write-up links to the project's home page at `n7wdz.com/projects.html#pocket-pico-tnc`; a public source drop was not linked from the Hackaday article at time of writing.

### 🎯 Takeaway (Hợp)
Amateur-radio experimenters who need an inexpensive TNC for AX.25 or APRS should look at Pocket Pico as an alternative to hunting down vintage Kantronics hardware, especially where a $4 Pico plus a passive audio interface is all the parts list needed. Về mặt embedded, đây là ví dụ thực tế cho thấy demod FSK 1200 baud giờ đã hoàn toàn nằm trong ngân sách CPU của RP2040 mà không cần DSP rời.

### 💡 Example
```python
# Minimal MicroPython sketch of the Pocket Pico audio hook: read PWM/ADC samples
# from the audio interface at ~19.2 kHz and hand them to the Bell 202 demodulator.
from machine import ADC, Timer
import array

SAMPLE_HZ = 19200
BUF = array.array("H", [0] * 256)
adc = ADC(26)  # audio-in

def on_sample(_):
    for i in range(len(BUF)):
        BUF[i] = adc.read_u16()
    bell202_demod(BUF)  # AFSK1200 -> bits -> AX.25 framer -> Z80 emulator I/O

Timer().init(freq=SAMPLE_HZ, mode=Timer.PERIODIC, callback=on_sample)
```
