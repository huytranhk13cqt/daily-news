### 🔭 Overview (Tổng)
Amazon has signed a definitive agreement to acquire DuckLabs, the Amsterdam-based company behind the open-source analytical database DuckDB. The post is published on the AWS Big Data Blog and paired with a commitment that DuckDB itself remains open-source under the independent DuckDB Foundation on the MIT licence, with Hannes Mühleisen and Mark Raasveldt continuing to lead the team and the project. For a data engineering audience this is the single largest ownership change in the local-first analytics space this year — DuckDB is the engine behind an unusually broad range of tools (dbt-duckdb, pandas/Polars interop, DuckDB-Wasm, the new dbt v2 Fusion runtime, the recent `hf://` Hugging Face integration) — so the reasonable question is what "AWS-native, still open-source" means in practice.

### 🔬 Details (Phân)
The AWS post frames the acquisition around the observation that most SQL workloads are small: the write-up cites DuckLabs' own figure that DuckDB "optimizes for the 90%+ of SQL queries processing 1 terabyte or less" and highlights the engine's vectorized execution, in-process embedding and direct scanning of Parquet, CSV and JSON on Amazon S3 without a separate compute cluster. Two customer quotes anchor the case: the Allen Institute's Executive Director says "queries that took minutes now come back in less than a second, enabling completely new ways of interacting with data," and Amazon Quick reports that DuckDB integrations reduced average query latency by 30% after processing over 2.5 billion queries. AWS states that it plans to integrate DuckDB with its data services (Redshift, Athena, EMR, Glue ETL and SageMaker) and optimize the engine for AWS infrastructure — the phrasing is deliberately open-ended, which is normal for a signed-but-not-closed deal.

The open-source commitment is the sentence the ecosystem will parse hardest. DuckDB's code has always lived under the DuckDB Foundation, and the Foundation model — separating the engine's licence and governance from the commercial company that employs most contributors — is the safety mechanism that lets AWS make a credible "still MIT, still Foundation" promise without needing to hand the licence back after the fact. What it does not guarantee is contributor time balance: commercial extensions previously built inside DuckLabs (the S3 secret store, the Motherduck-integration paths, the recent `hf://` protocol) will now be prioritised against AWS's own product roadmap rather than against DuckLabs' commercial pipeline.

Positioning-wise, the acquisition follows a familiar pattern of hyperscalers absorbing the teams behind widely embedded engines — Google around Iceberg contributors, Databricks around Tabular in 2024 — but is unusually visible on the client side because DuckDB is embedded, not run as a service. The transaction is expected to close "shortly"; regulatory review timelines are not disclosed in the blog, and DuckLabs' recent product moves (DuckDB v2.0-alpha on 2 September, DuckDB in dbt v2 on 22 September, `hf://` on 25 September) continue in the meantime under the existing team.

### 🎯 Takeaway (Hợp)
If your stack embeds DuckDB — dbt-duckdb, notebooks, DuckDB-Wasm, edge/CLI tools — no immediate action is required, but track two signals over the next quarter: whether the AWS-branded extensions (S3, Redshift, Athena readers) start landing upstream on the same cadence as before, and whether non-AWS cloud extensions (Azure, GCS) keep pace. Về mặt sinh thái, DuckDB Foundation là bảo hiểm chính; nhưng đội nào đang xây thương mại trên DuckDB đều nên đọc kỹ điều khoản Foundation trước khi giả định "vẫn open-source" là bất biến.

### 🔭 Overview (Tổng)
CedarDB engineer Lukas Vogel published a technical write-up describing a port of the original 1993 id Software Doom to run inside a SQL engine, with game logic and the frame renderer both implemented as database queries; the post was amplified across the community after Hackaday covered it on 25 September. Only the front-end plumbing — keyboard polling, timing at 35 Hz, and blitting a 320×200 bitmap — stays in Python; everything else, from monster AI to visplane rendering, sits in SQL tables and CTEs against CedarDB's own engine. For a data engineering audience this is not a toy in the usual sense: it is one of the more disciplined exercises in "what does a real modern SQL engine give up, and what does it not, when you stretch its execution model," and the write-up is unusually specific about the timings.

### 🔬 Details (Phân)
The renderer is a single query around 1,300 lines long, built from 89 CTEs. It replaces Doom's recursive BSP traversal with a lexicographic sort over BSP node coordinates, expands wall columns with `generate_series()`, computes visplanes (floor and ceiling spans) with window functions, and resolves per-pixel depth via bitpacked sort keys. Game logic — monster AI, physics, pickups, damage — takes about 5,900 more SQL lines and uses an entity-component-system pattern mapped to relational tables, with `UPDATE ... WHERE` playing the role of per-tick state changes and recursive CTEs standing in for state-machine loops. Multiplayer is ACID by construction: transactions serialise concurrent player writes and PostgreSQL-style roles gate access, which is unusual for a game engine but plausible for a demonstration of the underlying database.

The performance numbers are what turn this from a curiosity into a data-engineering artefact. Game ticks run in 2–10 ms against a 35 Hz budget of 28.6 ms; the full frame renders in 16–30 ms, with a comfortable 60 FPS achievable on modern hardware. The most expensive individual passes are visplane rendering (about 3 ms) and depth resolution (about 8.2 ms). CedarDB compiles SQL to LLVM IR, which is what makes those numbers possible; the write-up notes explicitly that a general-purpose PostgreSQL would not clear the frame budget, and that the exercise says as much about JIT'd analytical engines as it does about Doom.

Ecosystem-wise this is a rare piece of engineering-marketing that ships a working artefact — a public demo runs on CedarDB Cloud, source is on GitHub — rather than a benchmark deck, and it is a useful counterweight to the "SQL cannot express X" reflex that shows up whenever a new agent framework or ETL DSL launches. For engineers writing genuinely large queries against JIT'd databases (CedarDB, DuckDB, DataFusion, Snowflake), the patterns for BSP-as-sort and visplane-as-window-function are transferable.

### 🎯 Takeaway (Hợp)
Use the Doom write-up as a reference for how far a JIT'd SQL engine can be pushed with window functions, recursive CTEs and materialised sort keys before you reach for an imperative UDF or a client-side loop — the trade-off point is much later than most teams assume. Về mặt truyền thông kỹ thuật, đây là ví dụ nên học cho các DBaaS: một artefact chạy được nói nhiều hơn một trang so sánh benchmark.

### 💡 Example
```sql
-- Sketch: BSP front-to-back ordering via lexicographic sort instead of recursive descent.
WITH RECURSIVE bsp AS (
    SELECT node_id, parent_id, split_axis, split_value,
           /* build a fixed-width sort key that puts the near side first */
           encode_bsp_key(player_x, player_y, split_axis, split_value) AS k
    FROM bsp_nodes
),
walk AS (
    SELECT node_id, k FROM bsp WHERE parent_id IS NULL
    UNION ALL
    SELECT c.node_id, c.k FROM bsp c JOIN walk p ON c.parent_id = p.node_id
)
SELECT node_id
FROM walk
ORDER BY k;   -- traversal order = sort order
```

### 🔭 Overview (Tổng)
Kigen announced that its automotive eSIM is the first to achieve GSMA eSA (eUICC Security Assurance) certification against SGP.32 v1.3, the latest IoT variant of the GSMA remote SIM provisioning specification. The eSIM runs on Infineon's TEGRION SLI22 automotive-grade secure element, and Kigen is shipping a coordinated portfolio across the TEGRION SLx22 family: automotive (SLI22, SGP.32 v1.3), consumer (SLC22, SGP.22 v2.7) and industrial IoT (SLM22, SGP.32 v1.3). For any IoT team that has been tracking the SGP.32 story — the IoT-focused successor to consumer SGP.22 that introduces the IPA (IoT Profile Assistant) architecture — this is the first commercial silicon plus stack combination certified against the current 1.3 revision.

### 🔬 Details (Phân)
The technical envelope in the announcement matters. SGP.32 v1.3 adds direct and indirect profile downloads (device-initiated and server-initiated), digital activation codes as a replacement for the paper QR path used in consumer SGP.22, an emergency profile handling flow, and hybrid post-quantum cryptography compatibility for signalling paths that are expected to outlive the classical PKI baseline. The GSMA eSA scheme itself validates the eSIM operating system and the underlying secure element together, so certifying the OS on a specific silicon (Kigen OS on TEGRION SLI22) is what the certificate anchors to; ports to other silicon require their own eSA re-certification. Sampling in the ETSI MFF2 package is scheduled for October 2026, with GSMA-run interoperability testing in the same month.

Positioning against the market is the useful frame. The consumer eSIM roadmap (SGP.22) is already dominant on smartphones, but the automotive and industrial paths have lagged because their provisioning flows and security expectations differ: cars are shipped years before their SIM profiles are configured, they cross borders under different operator agreements, and their profile lifecycle can exceed 15 years — comparable to the field-life story Canonical is telling around Zephyr LTS. Kigen's press positioning also highlights China Mobile International as a deployment partner, which matters because CMI is one of the operators that has been running SGP.32 interop tests since v1.2.

For product teams the practical implication is narrow but concrete. If you are designing a connected-vehicle telematics unit or an industrial cellular gateway that needs to be shippable to multiple operators without pre-provisioned SIM cards, SGP.32 v1.3 is the specification you will target for the next generation of hardware, and a v1.3-certified secure element with a certified eSIM OS on top removes a significant chunk of security audit work.

### 🎯 Takeaway (Hợp)
For automotive T-Box, telematics and industrial gateway designs, treat this as the go-ahead to pin SGP.32 v1.3 on your next bill of materials rather than staying on v1.2 or SGP.22 — the eSA-certified stack now exists, and October sampling means design-in windows for 2027 shipments are open. Về mặt tuân thủ, đây là mảnh vá cuối để đơn giản hoá audit an ninh cho các sản phẩm connected car dùng chung một silicon cho nhiều thị trường.

## 5. Breaking Taps Fabricates a Custom Transport-Triggered SoC via wafer.space

### 🔭 Overview (Tổng)
Hackaday covered a project by hardware YouTuber Breaking Taps that walks through the full custom-silicon workflow — design in the Spade HDL, tape-out through wafer.space, packaging under clear epoxy, and bring-up on a breadboard — to build a working transport-triggered architecture microprocessor with integrated memory and peripherals. For an IoT audience that has watched the Tiny Tapeout movement grow over the last three years, this is the first widely visible datapoint that the "one designer, one full chip, one shuttle run" path is now practical outside a research group, and it foreshadows a class of tiny, purpose-built silicon for edge sensors that neither Cortex-M nor RISC-V IP quite fits.

### 🔬 Details (Phân)
The chip is a transport-triggered architecture (TTA) SoC — a design style where the ISA exposes an interconnect between functional units and every instruction is a data move, so control flow emerges from where data goes rather than from a fixed opcode set. Breaking Taps writes the design in Spade, an emerging Rust-adjacent HDL that targets modern silicon flows without the SystemVerilog boilerplate, and fabricates it through wafer.space, a service that packages MPW-style shuttle runs for individual designers. The result is one chip rather than a Tiny-Tapeout tile, so the entire design — CPU, memory and peripherals — is a single die visible under the clear epoxy package on-camera, in contrast to the modular per-designer tiles of Tiny Tapeout.

The trade-offs are worth flagging. wafer.space runs on older process nodes than commercial IoT SoCs, so the die is physically larger than a comparable STMicro or Espressif MCU and the on-chip memory density is nowhere near a mass-market part; the write-up describes the service as "premium" today with an expectation of getting cheaper as MPW capacity grows. On the other hand, the workflow Breaking Taps demonstrates is the actual professional flow — design capture, synthesis, tape-out, packaging, board bring-up — compressed to the scale of one person, and the successful execution of a small program on breadboard hardware validates every step end-to-end. There is no comparable published run-through at this scope from a single hobbyist.

For embedded engineers this changes the "should I bother designing a custom part?" calculation for niche edge devices. TTA is a genuinely good fit for sensor-front-end silicon where a handful of very specific dataflows (ADC → filter → threshold → radio) dominate, and the ability to iterate a wafer-space design in weeks rather than the year-scale of a foundry engagement means small companies can now credibly consider it for products that ship in the thousands rather than the tens of millions.

### 🎯 Takeaway (Hợp)
Add wafer.space + Spade to your list of "how tiny does an edge device have to be before I stop reaching for an ESP32" tools; for a sensor-front-end product with tight dataflow and low unit-count, a small TTA design now competes with an off-the-shelf MCU on the design side of the ledger even if the wafer cost is still higher. Về dài hạn, đây là dấu hiệu MPW service dần dịch chuyển từ hoạt động học thuật sang một kênh sản xuất khả thi cho các sản phẩm embedded nhỏ.

### 💡 Example
```systemverilog
// Illustrative sketch of a transport-triggered move:
// data flows between functional units; the "opcode" is where the move lands.
// (Real design is written in Spade; SystemVerilog shown here as familiar reference.)
module tta_bus (
    input  logic        clk,
    input  logic [15:0] src_data,     // e.g. output of ADC unit
    input  logic [ 3:0] dst_sel,      // which functional unit consumes it
    output logic [15:0] alu_add_a,
    output logic [15:0] alu_add_b,
    output logic [15:0] cmp_lhs
);
    always_ff @(posedge clk) begin
        case (dst_sel)
            4'd0: alu_add_a <= src_data;
            4'd1: alu_add_b <= src_data;
            4'd2: cmp_lhs   <= src_data;
            default: /* no side effect */ ;
        endcase
    end
endmodule
```
