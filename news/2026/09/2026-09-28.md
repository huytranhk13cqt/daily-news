## 1. ESA's Galileo Signal Authentication Service Holds Lock Through Jammertest 2026 Spoofing Attacks

### 🔭 Overview (Tổng)
Hackaday's 27 September write-up documents the first widely reported field validation of the Galileo Signal Authentication Service (SAS), the encrypted successor and companion to the existing OSNMA scheme. During the Jammertest GNSS testing event held in Andøya, Norway, in early September the European Space Agency used five Galileo satellites transmitting SAS-secured pilot codes on the E6-C signal, and a receiver held a stable position lock while the range was under active jamming, delayed-retransmission and spoofing attacks. For an IoT audience that ships anything with a GNSS front-end — logistics tracking, drones, connected vehicles, precision agriculture, timing references for utility or industrial gateways — this is the first strong signal that civil-grade authenticated positioning is moving from spec to something that can be built into shipping receivers.

### 🔬 Details (Phân)
SAS operates on top of the E6-C pilot channel of Galileo satellites and treats spreading codes themselves as the secret. Ground stations pre-select the codes, encrypt them with keys that rotate on a schedule, and publish the encrypted blocks so receivers can pre-fetch and store them. Each satellite then transmits a message block on E6-C, followed by the decryption key on a separate, timed release, at which point receivers can recover the spreading codes retroactively and correlate them against the raw samples they have already captured to reconstruct valid pseudoranges. This "correlate against a secret you did not have at reception time" pattern is what defeats replay and meaconing: an attacker cannot fabricate a valid signal without the current key, and by the time the key ships the observation window on the receiver has already closed.

The Jammertest 2026 results are the substantive piece. ESA reports stable lock across five satellites under simultaneous jamming, retransmission delay attacks, and spoofing attempts — the three classes that break existing civil GNSS in different ways. That triad matters because the low-cost commodity spoofing kits shown at DEF CON 33 and in recent trade press each target one of them at a time; SAS's threat model is explicitly the composite case. The article also notes that the underlying primitive is portable in principle: pre-shared encrypted spreading codes plus a delayed-key release does not require Galileo-specific infrastructure and could be extended to GPS or other constellations on future satellite generations, though nothing operational has been announced.

The trade-offs are real. SAS is not a drop-in for OSNMA: it needs the E6 receiver chain, adds a code-pre-fetch dependency (a receiver that has not stored the current block cannot authenticate), and consumes more ground infrastructure than OSNMA's per-frame HMAC approach. For product teams the question is which receiver families will expose SAS in firmware. Chip-side support is not yet broad, but the field test is the point at which chipset vendors and module makers start committing to roadmaps, and the certification story around eSIM-connected trackers with authenticated GNSS becomes plausible for shipments in 2027-2028.

### 🎯 Takeaway (Hợp)
If your IoT roadmap depends on GNSS integrity — asset tracking that gets stolen, timing that anchors billing, autonomous positioning — treat this as the trigger to ask your GNSS module vendor when SAS on E6-C will land in their receivers and to budget for a slightly larger BOM (E6-capable RF front-end) on next-generation designs. Về mặt tấn công, đây là lần đầu civil GNSS có bằng chứng thực nghiệm chống được combo jam-delay-spoof, đủ để nâng bar đánh giá rủi ro cho các sản phẩm phụ thuộc định vị.

```text
#
# Pre-flight (background, over IP link to SAS distribution service):
#   1. Pull encrypted spreading-code block for epoch T = current + delta
#   2. Store block indexed by (satellite_id, epoch T)
#

#   3. Sample raw E6-C signal from each visible Galileo SV, buffer ~N chips
#   4. Wait for delayed key release (K_T) from Galileo signal-in-space

```

## 2. Nordic nRF54LM20 Debugging Trap: J-Link's Default Memory Cache Feeds Stale Values to GDB

| Field | Value |
|---|---|
| 📅 Date | 27/09/2026 |
| 🏷️ Topic | Coding |
| 🌐 Domain | IoT |
| 🔑 Keywords | `nrf54lm20` · `jlink-cache` · `cortex-m33-debug` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
Nordic Semiconductor's newly sampling nRF54LM20, an ARM Cortex-M33-class multi-radio SoC, has already produced its first well-documented debugging landmine. Daniel Mangum published a detailed diagnosis, picked up by Hackaday on 27 September, of a case where GDB read commands over the standard J-Link toolchain returned values that were minutes stale, hiding the actual live state of the chip. The root cause is not silicon or the Cortex-M33 debug architecture; it is that Segger's `JLinkArm.dll` ships with an internal memory cache enabled by default, which the GDB remote protocol path does not invalidate on the reads embedded engineers assume are "direct" AP accesses. For anyone bringing up new Nordic hardware this quarter it is worth reading once and pinning to the team wiki.

### 🔬 Details (Phân)
The mechanics are worth walking through because the symptom is easy to misdiagnose as a peripheral bug. `JLinkGDBServer` translates GDB Remote Serial Protocol (RSP) memory reads into `JLinkArm.dll` calls, and the DLL keeps a small memory-region cache that assumes contents do not change between reads. On a live target where the CPU or a DMA engine is updating a register the cache never sees the change, so `p *addr` returns whatever was there on the first hit. The write-up traces the exact code path and documents two workarounds: disabling the cache globally with `(gdb) monitor exec SetEnableMemCache = 0`, or using the explicit `ReadMemAP` command with an access-port index and address to bypass caching for a single read. Both work; the first is what you want for interactive sessions, the second for scripted checks.

Segger's own docs describe the `SetEnableMemCache` command but do not surface it in the default `.gdbinit` templates, which is why the issue lay dormant on older Cortex-M4/M33 parts as well and only surfaced now on the nRF54LM20 because Mangum was doing tight state-machine debugging. The nRF54LM20 itself is Nordic's next-generation multi-radio device (Cortex-M33 with TrustZone, Bluetooth LE + 802.15.4 + the new 802.15.4z UWB radio, currently sampling to select customers); its debug interface is stock ARM CoreSight, so the same trap can bite any Cortex-M part driven through J-Link, but the higher clock rates and DMA density on this class of SoC make it more likely to observe.

The competing debug stacks handle this differently. OpenOCD by default does not cache AP reads and reads directly through the DAP on every access, at the cost of slower stepping. Segger's cache is a defensible engineering choice for the register-inspect workloads most users hit, but the failure mode — silent staleness rather than an error — is bad enough that many teams will now pin `SetEnableMemCache = 0` into their default GDB init file for anything with DMA, an RTOS scheduler tick, or a live radio.

### 🎯 Takeaway (Hợp)
Add `monitor exec SetEnableMemCache = 0` to your project's `.gdbinit` (or the equivalent in your IDE's J-Link config) for any nRF54, nRF53 or other Cortex-M33 bring-up work, and prefer `ReadMemAP` in scripted diagnostics; the interactive-step performance hit is minor compared to the hours a stale-value hunt costs. Về công cụ, đây là ví dụ tại sao cache mặc định trong tool chuỗi debug là một loại "silent failure" đắt tiền — cần gán default off cho các dự án có DMA hoặc RTOS.

### 💡 Example
```gdb
# .gdbinit fragment for Nordic nRF54LM20 (or any live Cortex-M33 target).
# Attach GDB, then disable J-Link's internal memory cache before anything else.

target remote localhost:2331

# Disable memory caching in JLinkArm.dll to see true live values.
monitor exec SetEnableMemCache = 0

# Optional: read a specific register through the explicit AP path.
# monitor exec ReadMemAP 0 0x40000000

# Now interactive reads (e.g. `p/x *(uint32_t*)0x40000000`) reflect the
# current hardware state, at the cost of every read going over the wire.
```

### 🔭 Overview (Tổng)
The AWS Big Data Blog published a detailed engineering case study on 24 September describing how Delivery Hero rebuilt its retail-media ad measurement pipeline on Amazon Managed Service for Apache Flink, moving from a batch pipeline with a 61-minute average end-to-end latency to a streaming pipeline with a 1.2-second average end-to-end latency and a 57% monthly cost reduction. For data engineers weighing "how much simpler is a first-party Flink service really" against self-hosting on Kubernetes, this is one of the better public write-ups of the last quarter: it names the state size, the operators, the failure modes fixed, and the specific KPI deltas rather than the usual generic latency-graph.

### 🔬 Details (Phân)
The pipeline is a five-stage streaming job. Stage one decompresses and decrypts ad-event tokens using keys pulled from AWS Secrets Manager. Stage two deduplicates against a 30-hour RocksDB keyed-state window sized at roughly 20 GB, using event-time watermarks. Stage three uses Flink's Async I/O to enrich each event from Amazon DynamoDB, which the article calls out as the fix for a synchronous bottleneck in the previous architecture. Stage four does a multi-day interval join for attribution and sits on approximately 100 GB of keyed state. Stage five aggregates and upserts to the reporting database in 5-minute microbatches. Events come in via Amazon Kinesis Data Streams, land as Avro in Amazon S3 for replay, and billing outputs go to Apache Kafka topics; state checkpoints ride to S3. The job sustains a peak of 20,000 messages per second and holds exactly-once billing semantics via at-least-once delivery plus deduplication.

The metric table is what makes this notable. Missing-session rate dropped from 30–40% to 0%, missing customer-ID rate from 5% to 0.8%, missing impression-timestamp rate from 91% to 0.2%, and processing latency from a 61-minute mean to 1.2 seconds. The 57% monthly cost reduction is credited to the elimination of an EMR-based batch layer plus better utilisation on the managed Flink service. AWS does not disclose the Flink minor version, but the operator patterns (Async I/O with DynamoDB, interval join with large state on RocksDB, S3 checkpoints) map cleanly to the 1.19/1.20 line the service currently exposes.

Positioning-wise, the piece sits in a growing set of managed-Flink case studies (Grab in June, Autodesk in July, now Delivery Hero) that collectively make the case that the pain points of self-hosted Flink on Kubernetes — checkpointing to durable storage, RocksDB tuning at ~100 GB state, restart storms, Kubernetes operator upgrades — are the parts the managed service actually removes. It is not a like-for-like comparison for teams that already run Flink on EKS with a working operator, but it is a strong reference for teams still on hourly Spark batch pipelines who are asked to justify moving to streaming.

### 🎯 Takeaway (Hợp)
Use this as the reference architecture when a stakeholder asks why real-time attribution can be worth the migration cost: the 61-minute-to-1.2-second and 91%-to-0.2%-missing-timestamps deltas are the concrete kind of numbers you can attach to a business case. Về kỹ thuật, kết hợp Async I/O với DynamoDB cho enrichment plus interval join cho attribution là một mẫu áp dụng lại được cho gần như mọi retail-media pipeline.

### 💡 Example

```java
// Sketch: enrichment via Async I/O against DynamoDB, then interval join
// for attribution — the two operators that carry most of the latency win.
DataStream<AdEvent> events = kinesis
    .map(new DecryptAndDecompress())
    .keyBy(AdEvent::userId)
    .process(new DedupOverEventTime(Duration.ofHours(30)));   // 20 GB state

DataStream<EnrichedEvent> enriched = AsyncDataStream.unorderedWait(
    events,
    new DynamoDbEnrichmentFn(),                                // non-blocking
    /* timeout */ 5, TimeUnit.SECONDS,
    /* capacity */ 200);

DataStream<Attribution> attributed = enriched
    .keyBy(EnrichedEvent::sessionId)
    .intervalJoin(clicks.keyBy(Click::sessionId))
    .between(Time.days(-2), Time.days(0))                      // ~100 GB state
    .process(new AttributeConversion());

attributed
    .keyBy(Attribution::campaignId)
    .window(TumblingEventTimeWindows.of(Time.minutes(5)))
    .aggregate(new BillingAggregate())
    .addSink(new KafkaBillingSink());
```

### 🔭 Overview (Tổng)
ClickHouse shipped 26.9 on 23 September with 56 new features, 135 performance optimisations and 464 bug fixes. The headline items — conditional `LIMIT` boundaries, incremental refresh for append-only materialized views, disk spilling for `DISTINCT`, time-limited access tokens and column-statistics-only answers for `min`/`max`/`count` — are unusually well-aligned with lakehouse workloads, and specifically with the Iceberg-as-sink pattern that has been growing across the ClickHouse install base since 26.7. For data engineers who use ClickHouse as either the front-end analytical store or as the streaming aggregator upstream of an Iceberg table, this is a release worth pulling into a staging environment now rather than waiting for the next LTS drop.

### 🔬 Details (Phân)
Conditional `LIMIT` introduces `AFTER` and `UNTIL` clauses that start and stop output based on values in the ordered result stream — for log or event tables that is the difference between fetching the entire day and asking "give me everything from the first ERROR until the next successful checkpoint." An `ALL` modifier reapplies the same window logic repeatedly through the stream. Incremental refreshable materialized views add `APPEND INCREMENTAL` syntax that processes only rows committed since the last refresh instead of scanning the source table end to end; the blog frames the target case as append-only replication into an Iceberg data lake, which is the current cheapest path from ClickHouse into a shared cross-engine lakehouse.

Disk spilling for `DISTINCT` is the quality-of-life fix for a class of high-cardinality aggregations that previously OOM'd. The new `max_bytes_before_external_distinct` setting flips the hash set to disk on threshold, matching the pattern ClickHouse already has for `GROUP BY` and joins; production teams running observability workloads have been asking for this for two release cycles. Time-limited access tokens via `CREATE TOKEN` produce scoped credentials with expiry (default 30 minutes if not specified), which fits the workload-identity model that most cloud deployments now enforce and is easier to slot into a Vault or IAM Roles Anywhere setup than static long-lived keys.

Two smaller but useful items round out the release. `min()`, `max()` and `count()` can now be answered from column statistics without reading the underlying column data — a significant win for dashboarding queries that repeatedly ask for a table's most recent event or highest ID. And bracket syntax for JSON subcolumns removes a syntactic wart when addressing nested paths in the JSON type; combined with expanded PromQL support, this makes the observability-native positioning of ClickHouse more concrete.

### 🎯 Takeaway (Hợp)
Two changes are worth adopting first: switch high-cardinality `DISTINCT` queries to lean on `max_bytes_before_external_distinct`, and replace hand-rolled Airflow rebuild jobs against source tables with `APPEND INCREMENTAL` refreshable views if your sink is Iceberg or a similar append-only table. Về vận hành, `CREATE TOKEN` là con đường ngắn nhất để nghỉ hẳn với các API key dài hạn trong stack ClickHouse.

### 💡 Example
```sql
-- Incremental append-only refresh into an Iceberg-backed table,
-- replacing the daily "rescan-and-rewrite" job.
CREATE MATERIALIZED VIEW ad_events_daily_iceberg
REFRESH EVERY 5 MINUTE
APPEND INCREMENTAL
TO iceberg.analytics.ad_events_daily
AS
SELECT toDate(event_time) AS event_date,
       campaign_id,
       count()            AS impressions,
       uniqExact(user_id) AS unique_users
FROM raw.ad_events
GROUP BY event_date, campaign_id;

-- Scoped 30-minute token for a downstream reporting service.
CREATE TOKEN reporting_bi
  EXPIRES 30 MINUTE
  GRANT SELECT ON analytics.*;
```
