### 🔭 Overview (Tổng)
DuckDB 1.5.6 shipped on 28 September as the last planned patch on the 1.5 line before the 2.0 development tree stabilises. It is the sort of release that reads short in the changelog and matters a lot in production: the 12 correctness fixes touch query paths that most analytical pipelines exercise every day (LIMIT/OFFSET pushdown, filter pushdown through aggregates, UNNEST, Top-N window elimination), and the accompanying API work stabilises every v1 C symbol so that extensions and language bindings can commit to a stable ABI. For teams running DuckDB as their in-process warehouse, as the query engine behind a data app, or as the compute in a lakehouse setup, this patch should be treated as urgent rather than optional.

### 🔬 Details (Phân)
The correctness list is the substantive part. DuckDB fixed a LIMIT pushdown bug that produced wrong rows when combined with volatile projections and OFFSET; a filter pushdown that incorrectly moved predicates through aggregates whose GROUP BY expressions were volatile; UNNEST pushdown returning incorrect cardinalities; Top-N window elimination that mis-handled nullable expressions; common subplan elimination emitting wrong results inside UNION ALL branches; and — the one most likely to have bitten users silently — long integer literals being truncated to HUGEINT without a warning. Parquet reads got fixes for TIME_NS values and for VARIANT shredding, plus four stability fixes covering a Top-N crash on `LIMIT 0`, a `url_decode` segfault on dictionary-encoded columns, checkpoint marker recovery, and a WAL handle leak during recovery.

On the API side, the release unifies C API symbol versioning across client and extension surfaces and stabilises every v1 API, which is the step vendors of language bindings (duckdb-node, duckdb-rs, JDBC, ADBC) have been waiting for. Two smaller items pay their weight: temporary file read hardening (defense against a malicious spill file replaced under the running process) and UTF-8 validation in `printf`'s `%c` conversion. The new `enable_optimistic_write` setting is the first hint at the write-path work landing in the 2.0 dev tree, letting the engine assume no concurrent writer for a workload where the operator can guarantee it.

Positioning-wise, this release closes the 1.5 line in exactly the way DuckDB has been closing lines since 1.0: with a batch of pushdown correctness fixes discovered by fuzzing and by users hitting them in production, and with an API stabilisation pass that lowers the cost of the next major-version transition. Extension authors targeting v1 C API symbols now have a firm contract; that in turn is what will let the community DuckDB extensions ecosystem move forward without breaking on every patch.

### 🎯 Takeaway (Hợp)
Upgrade any 1.5.x DuckDB dependency to 1.5.6 this week — the LIMIT/OFFSET, filter-through-aggregate, and integer-truncation fixes each have the profile of a bug that returns silently wrong answers rather than an error, which is the worst kind of correctness regression to leave in a warehouse. Về API, đây là mốc thích hợp để bindings/extensions pin lên v1 stable rồi mới cân nhắc đường lên 2.0.

For teams that were already comfortable using Iceberg reads from Redshift Spectrum but hesitated to commit their write path, this closes the last major functional gap.

### 🔬 Details (Phân)
The schema-evolution section walks through `ALTER TABLE` operations that Iceberg guarantees will not rewrite existing data: adding a new column that reads as NULL for old rows, dropping a column, renaming a column, and widening a numeric type (for example `DECIMAL(10,2)` → `DECIMAL(18,2)`). It also covers changing table properties such as compression codec (switching to `zstd` for future writes only), which is a common lever for cost-tuning as data volume grows. Every operation is executed through standard Redshift SQL against a table catalogued under AWS Glue, which is the operational win: no separate Spark job or Iceberg CLI is needed for schema changes.

The partition-evolution section is where Iceberg genuinely differs from Hive. The post shows adding a `bucket(user_id, 32)` partition alongside an existing date partition without rewriting the historical files; replacing a partition transform atomically (moving from `days(event_time)` to `months(event_time)`) so that new writes use the new spec while old files remain queryable under the old spec; layering multi-level composite specs progressively; and removing partition fields altogether. Iceberg's read planner uses the file-level partition-spec ID to route pruning per file, which is what makes this work without a compaction pass. The article also flags the cross-engine surface: with Lake Formation resource links published into an S3 Tables catalog entry, the same tables become queryable from Athena and other engines under a single governance boundary.

Positioning matters here as much as content. Redshift's Iceberg story lagged Snowflake's through 2025, and Part 3 finishes the parity story on writes — the remaining differentiators are ergonomics and cost, not capability. For lakehouse architects standardising on Iceberg as the shared table format, the practical result is that any of the three major managed warehouses (Redshift, Snowflake, Databricks) can now sit on the same set of Iceberg tables and each can drive schema and partition evolution independently. That is closer to the original lakehouse thesis than the state a year ago.

## 3. Databricks Ships Lakebase Search: BM25 and RaBitQ-Compressed Vectors Inside Postgres

| Field | Value |
|---|---|
| 📅 Date | 28/09/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `lakebase` · `pgvector-alternative` · `rabitq-quantization` |
| ⚡ Impact | High |

### 🔭 Overview (Tổng)
Databricks announced Lakebase Search on 28 September, adding two Postgres extensions — `lakebase_vector` for ANN vector search and `lakebase_text` for full-text search — that are generally available on AWS and Azure inside the Lakebase managed Postgres offering. Neither is an incremental improvement to the existing pgvector or tsvector paths. `lakebase_vector` uses hierarchical IVF clustering plus RaBitQ binary quantization to compress 768-dimensional embeddings to roughly one bit per dimension; `lakebase_text` implements a native BM25 index with global IDF and block-max pruning. The benchmark numbers in the announcement are the reason to notice: 97% recall at 71 ms P99 on VectorDBBench's 100M LAION dataset, twice the throughput and about 4× the cost efficiency of cloud Postgres with pgvector.

### 🔬 Details (Phân)
The `lakebase_vector` architecture is the more novel of the two. Vectors are clustered hierarchically and grouped into contiguous storage blocks. At query time the engine scores cluster centroids in memory, then reads only blocks whose centroids are close to the query — the classic IVF pattern, but with RaBitQ's binary quantization the resident memory footprint drops by roughly 32× compared to float32 vectors. Databricks reports that a single compute unit can serve 100M vectors this way, and cold-start after scale-to-zero is 1.13 seconds at P90. The comparison the post makes to pgvector is pointed: pgvector needs approximately 330 GB of RAM to hold a 100M × 768-dimensional HNSW index for millisecond latency; index spills cause 10–50× regression; and initial index build on standard cloud instances is quoted at "almost 50 hours." Whether you accept the exact numbers or not, the underlying architectural claim — separate storage from compute, compress vectors aggressively, page from object storage — is what makes serverless pricing plausible for large ANN workloads.

`lakebase_text` targets the second half of retrieval pipelines. Native BM25 with global IDF gives corpus-wide relevance weighting that Postgres's built-in tsvector cannot express (tsvector's `ts_rank_cd` is document-local). The engine evaluates score upper-bounds during posting-list traversal and skips blocks that cannot reach the top-K threshold — the standard block-max WAND family of optimisations that competitive text engines like Tantivy and Lucene use, but inside a Postgres extension. In practice this is the ingredient that lets a hybrid search (BM25 + dense) run entirely inside the database, without shipping documents out to a separate search cluster.

Positioning is straightforward. This is Databricks slotting a full retrieval stack into Lakebase — the operational Postgres offering that pairs with the Databricks lakehouse — so that RAG applications, agent memory, and product search can be built as ordinary Postgres queries with joins across relational, vector, and text columns. It is a competitive move against pgvector-plus-Elastic architectures and against Snowflake's separate Cortex Search product. The trade-offs are the usual ones: quantization loses some recall vs full-precision HNSW at the smallest scales, block-max BM25 is a young code path relative to Lucene, and the extensions are locked to the Lakebase managed environment rather than shipping as open-source Postgres extensions.

### 🎯 Takeaway (Hợp)
If your retrieval workload today rides pgvector plus a separate text index, benchmark Lakebase Search on your own dataset before renewing the search-cluster contract — the RaBitQ quantization is the primary lever, and either your recall target survives it or it does not. Về mặt kiến trúc, đây là bước tiến để hybrid (BM25 + dense) chạy chung trong một transactional Postgres, giảm mạnh operational surface cho RAG stack.

### 💡 Example
```sql
-- Hybrid retrieval query using both extensions inside Lakebase Postgres.
CREATE EXTENSION lakebase_vector;
CREATE EXTENSION lakebase_text;

CREATE INDEX idx_docs_embed ON docs
    USING lakebase_vector (embedding vector_cosine_ops)
    WITH (quantization = 'rabitq', lists = 4096);

CREATE INDEX idx_docs_body ON docs
    USING lakebase_text (body);

WITH dense AS (
    SELECT doc_id, embedding <=> query_vec($1) AS score
    FROM docs
    ORDER BY embedding <=> query_vec($1)
    LIMIT 200
),
sparse AS (
    SELECT doc_id, bm25(body, $2) AS score
    FROM docs
    WHERE body @@ websearch_to_tsquery($2)
    ORDER BY score DESC
    LIMIT 200
)
SELECT doc_id, sum(1.0 / (60 + row_number() OVER (ORDER BY score))) AS rrf
FROM (SELECT * FROM dense UNION ALL SELECT * FROM sparse) t
GROUP BY doc_id
ORDER BY rrf DESC
LIMIT 20;
```

### 🔭 Overview (Tổng)
Henrik Forstén — the engineer behind previous well-documented bike-mounted and budget SAR builds — published a next-generation drone-borne synthetic aperture radar that finally solves the two problems that limited hobbyist SAR imaging: coarse platform position and a single-pass elevation ambiguity. Hackaday's 28 September writeup summarises the build. RTK and PPK GPS bring platform position from metre-class to centimetre-class, which lets a much stronger autofocus algorithm converge; and flying the same track twice at different altitudes turns the radar into an interferometric imager that recovers per-pixel elevation from the phase difference between passes. The result is a working IoT-class instrument that produces the class of imagery previously locked to satellite or crewed-aircraft platforms.

### 🔬 Details (Phân)
The positioning stack is the enabling piece. Standard GPS on a hobbyist drone gives roughly 1-metre resolution, which is fatal for SAR because platform position error is a phase error in the correlator that broadens the point-spread function. RTK carrier-phase corrections from a ground base station bring instantaneous accuracy to a few centimetres; PPK does the same by matching the drone's recorded observations against a base-station log after the flight. With centimetre-accurate positions in hand, Forstén's rewritten autofocus algorithm can converge on residual motion errors rather than fighting the position noise, and image cleanliness improves visibly in the published examples. On the RF side, a stabilised phase-locked loop drives a cleaner frequency sweep, and a fast on-the-fly compression scheme keeps the recording path within the FPGA's SD-card interface bandwidth.

Interferometric imaging is what turns the build from an imaging instrument into a mapping instrument. In classical single-pass SAR the assumption is that all scatterers lie on a constant-elevation reference surface, which is why tall objects appear to lean toward the sensor. Forstén flies the same path twice at slightly different altitudes and combines the two complex-valued images pixel by pixel: the phase of the ratio between them encodes the height difference of each scatterer above the reference surface. With careful phase unwrapping this yields a digital elevation model of the imaged patch. The hardware carrier is a small plastic box mounted under the drone containing two patch antennas, a camera for ground-truth reference, and the GPS antenna, connected to the FPGA-and-radar boards.

Positioning-wise, this is the second consumer-scale SAR project this month (after ESA's Jammertest 2026 SAS demonstration), but it comes from a different angle: not defensive positioning against jamming, but active imaging as a low-cost geospatial primitive. For the IoT audience the takeaway is that the hard parts of SAR — precise platform state, phase-coherent RF, correlator throughput — are all now buildable on hobby-level hardware once you accept the RTK/PPK infrastructure requirement. That opens practical applications in agriculture (soil-moisture indicators), construction (change detection over a site), and disaster response (rapid post-event elevation change).

### 🎯 Takeaway (Hợp)
If you have been circling SAR as a "someday" IoT project, the two shifts to steal from this build are the RTK/PPK positioning stack (it is the enabler for everything else) and the two-pass interferometric flight pattern (it is what promotes the instrument from imaging to mapping). Về mặt hệ sinh thái, đây là ví dụ tốt cho việc phần cứng đo lường khoa học đang chuyển dần vào tầm với của một team IoT nhỏ.

### 💡 Example
```text
# Interferometric SAR (InSAR) processing sketch — two-pass altitude difference.
#
# Inputs:
#   pass_A: complex SAR image, altitude h_A, RTK/PPK track T_A
#   pass_B: complex SAR image, altitude h_B, RTK/PPK track T_B
#
# 1. Co-register pass_B onto pass_A's pixel grid using the precise tracks.
# 2. Form the interferogram: I(x,y) = pass_A(x,y) * conj(pass_B(x,y))
#    -> phase(I) encodes 2 * pi * (delta_range / lambda) per pixel.
# 3. Estimate and subtract the flat-earth phase from the geometry alone.
# 4. Phase-unwrap the residual (e.g. Goldstein-Werner branch-cut).
# 5. Convert unwrapped phase to per-pixel height:
#       delta_h(x,y) = -lambda * phase_unwrapped(x,y) * range / (4 * pi * B_perp)
#    where B_perp is the perpendicular baseline derived from (h_A - h_B).
# 6. Add height back to the reference DEM to yield the final elevation map.
```

### 🔭 Overview (Tổng)
Michael Biggins (PhonicUK) released a Jet-engine port of the well-known N64 megatextures demo that runs on a stock ESP32-S3 with 16 MB of PSRAM, and Hackaday covered it on 28 September. The interesting engineering is not the 3D rendering per se — plenty of hobbyist engines run on the ESP32 line — but the memory strategy: the original N64 demo used 40 MB of texture data out of a 64 MB cartridge, and Biggins gets the same scene into 5.01 MB by re-encoding textures as 8-bit palette indices plus using mipmaps as a level-of-detail scheme. The result is a real-world case study in fitting console-era graphics onto a $5 microcontroller through data-format compression rather than algorithmic tricks.

### 🔬 Details (Phân)
The compression strategy is straightforward but effective. The original megatextures were 32-bit RGBA; Biggins re-encodes them as 8-bit palette-indexed textures per material, dropping storage by roughly 4× before other optimisations. Mipmapping — precomputed downsampled copies of each texture at successively lower resolutions — is used both to reduce texture bandwidth during rendering and, more importantly here, to serve as an explicit level-of-detail mechanism: the engine chooses the mip level appropriate to the on-screen texel footprint, so far-away geometry costs almost no memory-bandwidth in the fetch loop. Between the two techniques the 40 MB working set compresses to 5.01 MB, which fits comfortably inside the ESP32-S3's 16 MB PSRAM and leaves headroom for the frame buffer and scratch memory.

The chip itself deserves attention because the ESP32-S3 is not a 3D accelerator. It is a dual-core Xtensa LX7 running at 240 MHz with SIMD instructions and no dedicated GPU; all triangle rasterisation and texture sampling happens on the CPU cores. The article notes that with careful code this class of MCU can trade blows with mid-1990s consoles, and the megatextures demo is the concrete artefact behind the claim. Source is on GitHub (`CubeCoders/JetMegatexturesDemo`), which is the useful piece for embedded engineers: the pattern of palette-index textures plus mipmapping-as-LOD generalises to any resource-constrained device that needs to display richly textured 3D content, from AR/VR wearables to industrial HMI panels.

Positioning-wise this is a low-impact but useful data point. It does not shift any product roadmap, but it does reset the mental model of what an ESP32-S3 can do when someone commits to the data-format work. For teams building consumer IoT devices with a graphical UI (thermostats with animated dashboards, kiosk-style controllers), it is worth reading before defaulting to a more expensive SoC. The trade-off is the human cost of the texture pipeline: 8-bit palette encoding is not a runtime step, it is an offline asset-conditioning stage that must be built into whatever content pipeline the product uses.

### 🎯 Takeaway (Hợp)
If your device roadmap tops out at "we need decent graphics on a cheap MCU," treat this as evidence that palette-indexed textures plus mipmap-as-LOD is still the right first knob to turn before jumping to a more expensive SoC. Về tổng thể, tin này ít impact ngành nhưng là ví dụ rất tốt để review team về design pattern nén tài nguyên trong embedded.

### 💡 Example
```c
// Rough sketch of the palette-index + mipmap sampling loop.
// Textures are stored as an array of mip levels; each level is a
// uint8_t[] of palette indices plus a 256-entry uint32_t palette.
typedef struct {
    uint16_t width, height;
    const uint8_t *indices;   // width * height bytes
} MipLevel;

typedef struct {
    uint8_t levels;
    const uint32_t *palette;  // 256 * uint32_t RGBA
    const MipLevel *mips;     // mips[0] is largest
} Texture;

static inline uint32_t sample_tex(const Texture *t, float u, float v, int lod)
{
    if (lod >= t->levels) lod = t->levels - 1;
    const MipLevel *m = &t->mips[lod];
    int x = ((int)(u * m->width))  & (m->width  - 1);
    int y = ((int)(v * m->height)) & (m->height - 1);
    return t->palette[m->indices[y * m->width + x]];
}
```
