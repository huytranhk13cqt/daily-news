## 1. Databricks Ships `ai_decide`, a Native SQL Decision Function for Governed Data

### 🔭 Overview (Tổng)
Databricks announced `ai_decide` in Beta on 30 September, a native AI Function that takes an unstructured input and returns a structured decision — a category label, an ordered score, or a probability — rather than free-form generated text. It is callable both from SQL for batch scans across governed tables and from a REST API endpoint for real-time integration into applications and agents. The pattern is the same one landing across the analytics stack this month — a small structured judgement embedded inside a query or a request path — but the delivery is deliberately vendor-native: `ai_decide` runs inside Databricks, respects Unity Catalog governance, and executes without a caller-managed model deployment.

### 🔬 Details (Phân)
The function returns three shapes of answer. It can pick one label from a fixed set of options with an associated probability, giving callers a category and its confidence in one call. It can return an ordered score on a rubric so results are directly comparable against a threshold or usable as an `ORDER BY` key. And it can return a probability alone, effectively answering yes/no with calibrated confidence — the same shape that makes classification-inside-`WHERE` viable in analytics. The blog frames four production patterns for it: tagging customer reviews with the primary issue and its likelihood, routing prompts to different downstream models by reasoning-difficulty score, judging AI-generated answers against a governance policy, and driving real-time application logic — the post's Snake-game demo uses `ai_decide` as the movement policy over a REST call each frame.

Positioning-wise this closes a gap Databricks had against Snowflake Cortex, which has offered its own `AI_CLASSIFY` and `AI_FILTER` primitives since earlier this year, and against community efforts such as Jev + DuckDB covered in this digest a day ago. `ai_decide` is optimised specifically for decision workloads rather than text generation, so the pricing/latency profile is meant to make row-by-row evaluation on real tables affordable rather than a research demo. Access matches the rest of the Databricks AI Functions family — call it inside a SQL statement over a Unity-catalogued table and every input, every prediction, and the governance chain around it stays within the workspace's audit surface.

The trade-off is the usual vendor-native one. `ai_decide` is bound to the Databricks control plane and its billing meter, so cost-per-row still has to be modelled before turning it loose across a billion-row scan; and the API is currently Beta, so schemas and pricing may still move. But for teams already living inside Databricks with governed tables, the ergonomic gap between "call an external LLM classifier" and "write it as a column in your SQL query" collapses to nothing with this release.

### 🎯 Takeaway (Hợp)
If your organisation is already on Databricks and you have been reaching for LLM classification through Python jobs or an external endpoint, prototype `ai_decide` this week against a bounded input set — the SQL binding is the fastest way to see whether decision quality holds on your data before you cost-model a scan. Về mặt kiến trúc, chú ý rằng đây là chức năng platform-locked chứ không phải một extension như `jev` — quyết định "dùng ai_decide hay dùng LLM tự host" nên dựa trên governance yêu cầu và pattern chi phí, không phải trên khả năng chạy được.

### 💡 Example
```sql
-- Tag customer reviews with the primary issue and confidence,
-- then filter to the ones about billing or payments.
SELECT
    review_id,
    review_text,
    decision:label AS primary_issue,
    decision:score AS confidence
FROM (
    SELECT
        review_id,
        review_text,
        ai_decide(
            review_text,
            options => array('billing', 'delivery', 'quality', 'support', 'other')
        ) AS decision
    FROM catalog.crm.customer_reviews
    WHERE review_date >= current_date() - INTERVAL 7 DAYS
)
WHERE decision:label IN ('billing')
  AND decision:score >= 0.7
ORDER BY decision:score DESC;
```

## 2. A Concrete Cost-Optimization Playbook for Lakebase Postgres With Percentage Deltas

### 🔭 Overview (Tổng)
Databricks published a cost-optimization guide for Lakebase Postgres on 30 September, authored by Benjamin Nwokeleme, Firas Farah, and Jen Darrouzet. Lakebase is the managed Postgres service that shares storage with the Databricks Lakehouse and separates compute from storage — the guide walks through the architectural knobs that make cost efficiency possible and, unusually for a vendor blog, gives concrete percentage deltas rather than qualitative claims. The audience is anyone already running Lakebase or evaluating it against RDS/Aurora as a serving layer next to a lakehouse.

### 🔬 Details (Phân)
The architectural substance is the separation of storage and compute so branches, read replicas, and high-availability replicas all share one storage layer instead of duplicating pages. On top of that sits serverless autoscaling with scale-to-zero, and the guide states cache warm-up "in a few hundred milliseconds" after a scale-to-zero wake — the number that decides whether a bursty workload should keep a warm instance or accept the cold-path penalty. Compute defaults to an 8–16 Capacity Unit autoscaling range and the connection pooler is documented as supporting up to 10,000 concurrent client connections, which is the right ceiling to plan around for high-fanout web services.

Storage tuning is where the concrete numbers live. Snapshot storage is quoted at approximately 74% cheaper than regular branch storage, and Point-in-Time Restore storage at approximately 42% cheaper than standard branch storage — meaning the naive "keep 30 days of PITR on every branch" strategy is often the wrong default, and a scheduled-snapshot plus shorter PITR window is materially cheaper. Synced Tables — the managed pipeline that pulls Lakehouse data into Lakebase — supports three modes (Snapshot, Triggered, Continuous), and the guide sets a rule of thumb: Snapshot when >10% of the source changes each run, Triggered for scheduled updates, Continuous only for genuine real-time needs. Right-sizing is expressed as "working set fits in 75% of RAM", which is the cache-hit-ratio target most Postgres operators already use but which the guide restates against Lakebase's autoscaling behaviour.

The trade-off worth flagging is that many of these knobs are workload-shape dependent rather than one-time settings. Continuous sync is convenient but costs more than the same data on a Triggered schedule; a big PITR window feels safe but is quietly the biggest storage line item; scale-to-zero saves money on quiet periods but adds cold-start latency on the first request. The guide's contribution is putting the numbers next to each choice so those trade-offs stop being blind.

### 🎯 Takeaway (Hợp)
If you are running Lakebase Postgres today, audit two things this week: your PITR window (default is often longer than needed, and 42% cheaper storage per day quietly adds up) and your Synced Tables mode mix (Continuous should be the exception, not the default). Về ops, giữ working set trong 75% RAM là quy tắc đơn giản nhưng khớp với behaviour autoscaling của Lakebase — nó là điểm bắt đầu tốt hơn là chọn CU dựa trên đỉnh CPU.

### 💡 Example
```yaml
# Sketch of a Lakebase Postgres configuration aligned with the guide.

instance:
  autoscaling:
    min_cu: 8
    max_cu: 16              # default range; raise only if working set exceeds 75% RAM
  scale_to_zero: true       # accept ~few-hundred-ms warm-up on the first request

backup:
  pitr_window_days: 7       # shorter window uses PITR storage priced ~42% below branch storage
  scheduled_snapshots:
    frequency: daily        # snapshot storage priced ~74% below branch storage
    retention_days: 30

synced_tables:
  - name: dim_customer
    mode: snapshot          # >10% of rows change per refresh window
  - name: fact_orders
    mode: triggered         # refreshed on a schedule aligned with downstream SLAs
  - name: session_events
    mode: continuous        # kept for the case that genuinely needs sub-minute freshness

connections:
  pooler:
    max_client_connections: 10000
```

## 3. Aurora PostgreSQL Gets Zero-ETL Into a Glue Managed Iceberg Catalog for SageMaker

### 🔭 Overview (Tổng)
AWS published a walkthrough on 29 September announcing zero-ETL integration from Amazon Aurora PostgreSQL directly into an AWS Glue managed catalog, with the target tables materialised as Apache Iceberg on Amazon Redshift managed storage. Authored by Apurwa Pawar and Sarika Subramaniam, the post is both a launch note and an end-to-end setup guide: point Aurora at a Glue catalog, let AWS replicate the write-ahead log continuously, and query the result from Athena, Redshift, or Amazon SageMaker AI without owning any ETL code. The interesting substance is the delivery mechanism — enhanced logical replication over the WAL, DDL included — and the resource shape it lands as (Iceberg tables in a managed catalog, not S3-first Parquet).

### 🔬 Details (Phân)
Enabling the integration is a cluster-parameter change plus a resource wiring exercise. Two Aurora cluster parameters must flip: `rds.logical_replication=1` and `aurora.enhanced_logical_replication=1`, both applied via a custom parameter group and a cluster reboot. From there the setup is IAM- and Lake-Formation-heavy: create a `GlueDataCatalogDataTransferRole` with permissions for `kms:GenerateDataKey`, `kms:Decrypt`, `glue:GetDatabase`, and `glue:GetCatalog`; register the Glue managed catalog as a zero-ETL target backed by Redshift managed storage; and attach a resource policy authorising inbound integrations from the source cluster ARN. The integration itself is a single `aws rds create-integration` call that names the source cluster, target catalog, and a data filter (for example `include: *.*` to pick up every schema).

Once active, "enhanced logical replication continuously monitors the database transaction log and streams every insert, update, and delete to a downstream target in near real time", and it also automatically propagates DDL — a materially different guarantee than most CDC-to-lake pipelines, where schema changes trigger manual regeneration. The target is an Iceberg table in the Glue managed catalog, so downstream engines see the change through the standard Iceberg reader path: Athena, Redshift, and Amazon SageMaker AI all pick up the update without extra wiring, and the guide's verification step uses the Redshift Data API to run a `SELECT ... LIMIT 10` against the replicated table.

Ecosystem-wise this pulls Aurora PostgreSQL into the same shape AWS already offers for DynamoDB, RDS for MySQL, and Aurora MySQL — analytical replicas landed as Iceberg without a customer-managed pipeline. What is new here is the target format (Iceberg-first, not S3 Parquet only) and the DDL propagation guarantee. The trade-offs to weigh remain the usual zero-ETL ones: replication lag is "near real time" but is not zero; the managed catalog storage lives on Redshift managed storage rather than the customer's bucket, which changes both the cost model and where governance policies must be authored; and the CDC pipeline still charges by row and by change.

### 🎯 Takeaway (Hợp)
If you are running Aurora PostgreSQL as an OLTP store and have been standing up a Debezium-to-Iceberg pipeline for analytics, this integration is worth prototyping first — the DDL-propagation guarantee alone removes an entire class of on-call incidents. Về governance, tables landing như Iceberg trong Glue managed catalog nghĩa là Lake Formation là surface bạn phải authorise chứ không phải bucket policy — plan phần đó trước khi bật integration lên production.

### 💡 Example
```bash
# End-to-end: turn on enhanced logical replication and create the zero-ETL integration.

# 1. Custom parameter group enabling enhanced logical replication.
aws rds create-db-cluster-parameter-group \
    --db-cluster-parameter-group-name aurora-pgsql-zetl-cluster-pg \
    --db-parameter-group-family aurora-postgresql16

aws rds modify-db-cluster-parameter-group \
    --db-cluster-parameter-group-name aurora-pgsql-zetl-cluster-pg \
    --parameters \
        ParameterName=rds.logical_replication,ParameterValue=1,ApplyMethod=pending-reboot \
        ParameterName=aurora.enhanced_logical_replication,ParameterValue=1,ApplyMethod=pending-reboot

# 2. Create the integration (Aurora cluster -> Glue managed catalog).
aws rds create-integration \
    --source-arn "$AURORA_CLUSTER_ARN" \
    --target-arn "$GLUE_CATALOG_ARN" \
    --integration-name zetl-aurora-to-glue \
    --data-filter "include: *.*"

# 3. Verify from Redshift Data API once the integration reaches "active".
aws redshift-data execute-statement \
    --workgroup-name analytics \
    --database dev \
    --sql 'SELECT * FROM "catalog"."public"."orders" LIMIT 10;'
```

### 🔭 Overview (Tổng)
Espressif published a long postmortem on 30 September from team XLC–WYLDFYRE, who built two autonomous soccer robots for RoboCup Junior 2026 and finished 11th of 24 at the world final in Incheon in July. The technical arc is the one most embedded teams face at some point: an Arduino Mega hit its performance and memory ceiling, so the team ported the whole stack to the ESP32-S3-DevKitC-1 and reworked the control loop around the S3's 240 MHz dual-core Xtensa with hardware floating point. What makes the write-up worth studying is the honesty about the pin-budget squeeze, the sensor-scanning rate they were able to reach, and the concrete role that ESP-NOW plays in a competitive robotics context.

### 🔬 Details (Phân)
The compute story is straightforward: the ESP32-S3's dual cores at 240 MHz with hardware floating point are enough to run trigonometry-heavy behaviour code at 333 Hz across 32 line sensors while a 5 Hz radio loop and a video pipeline off two Pixy2 cameras run alongside. The Arduino Mega could not hold that combination — its 16 MHz AVR without an FPU chokes on sine/cosine at the required rate, and 8 KB of RAM ran out before the sensor state fitted. The team notes 16,000 ADC samples/second alongside all other processing, which is a useful concrete number when planning an ESP32-S3 project around line-following or reflectance sensing.

The pin-budget squeeze is the operational lesson. The team pushed the ESP32-S3 well past its "polite" GPIO map: `"All four strapping pins became our multiplexer address bus"` — GPIO0, 3, 45 and 46 were repurposed to address a 48-way phototransistor multiplexer; `"Disabling PSRAM gave us three more pins"` — GPIO35, 36, 37 were recovered by trading external PSRAM the workload did not need; native USB pins (GPIO19/20) became buttons; and JTAG pins (GPIO39–42) became status LEDs and sensor inputs. Each of those is a legitimate move on the S3 but any of them can brick the board if done thoughtlessly, so the retrospective doubles as a checklist of which pins are safe to reclaim.

ESP-NOW is the other worth-copying idea. The robots use ESP-NOW at 5 Hz to swap roles — attacker/defender — mid-match without any field-side transmitter, and to pass ball position and heading between units. Because ESP-NOW is peer-to-peer over the Wi-Fi radio without an AP, it works in the RF-hostile RoboCup arena where a normal Wi-Fi network would not; ESP-NOW makes that swap practical. The failure log is also useful: two PM8834 gate driver outputs were merged in parallel per the datasheet's stated permission and multiple boards died in testing — `"datasheet permission is not a test result"` is now a rule on their bench.

### 🎯 Takeaway (Hợp)
Two portable ideas: reclaim strapping/JTAG/USB pins on the ESP32-S3 only after checking each one's boot-strap and reset behaviour, and treat ESP-NOW as a first-class coordination channel between microcontrollers rather than a curiosity — it is the right tool for many-node robotics and swarm-style IoT deployments. Về performance, S3 chạy hardware FP đủ để làm trig ở 333 Hz cho 32 sensor, số này là baseline hữu ích khi bạn định dùng board này cho reflectance line-following hay hexapod control.

### 🔭 Overview (Tổng)
Arduino published a positioning piece on 30 September pushing back on the emerging pattern of using rack-mounted Mac minis as the runtime for autonomous AI agents. The article argues that the right deployment target for an agent that needs to see, sense, and act in the physical world is a small Linux-capable board with an NPU and a real-time microcontroller — Arduino's own VENTUNO Q, or a distributed mesh of UNO Q nodes — rather than a general-purpose desktop machine. The interesting piece for an IoT reader is not the marketing but the hardware shape it is arguing for: a converged compute platform where the Linux side runs the agent loop and the MCU side owns the deterministic sensor/actuator path.

### 🔬 Details (Phân)
The technical substance is thin — no benchmarks, no code — but the pitch is coherent. VENTUNO Q pairs a Linux-capable application processor with an NPU for on-device inference and a real-time microcontroller on the same board, so an agent can perform inference locally and drive real-time I/O without the round-trip to a cloud endpoint that dominates latency for anything moving in physical space. UNO Q is positioned as the lower-cost remote node in a distributed deployment — an agent spread across multiple UNO Q units at different sensor locations, coordinated through a VENTUNO Q. Cost anchor: a Mac mini configuration Arduino cites starts at around $900; the equivalent Arduino stack is quoted as "significantly less", though the post does not print a per-node BOM.

The community exhibit the article leans on is David Groom's OpenClaw framework, an agent runtime that has been demonstrated interacting with multiple Arduino boards simultaneously — sensors, actuators, and camera modules operated by a common agent loop rather than a hand-rolled control script. That is the missing piece that makes the argument concrete: with an off-the-shelf framework, an agent can treat a mesh of Arduino boards as its body without the developer writing bespoke serial protocols per project. The wider point the post makes is that low deployment cost enables broader distribution — more agents on more sensor sites, more feedback loops, more exposure to real-world edge cases than a simulated software agent can see from a data centre.

Positioning-wise this is Arduino staking a claim in the "agents in the physical world" narrative that OpenAI, Anthropic, and Physical Intelligence have been driving with software or robot-scale demos. The trade-off is honesty: a Mac mini is orders of magnitude more capable than any Arduino board for hosting a large frontier model. The Arduino argument only works if you agree that the agent-in-the-world case does not need a frontier-class model at every step and that a small local model plus authoritative I/O is often enough. That is a live open question in the ecosystem right now, not a settled one.

### 🎯 Takeaway (Hợp)
Treat this piece as a signal about hardware direction rather than a benchmarked recommendation — the interesting datapoint is that a mainstream MCU vendor is now shipping a Linux-plus-NPU-plus-MCU converged board specifically aimed at agent workloads. Về thực dụng, nếu bạn đang có prototype agent chạy trên máy dev, thử port một task đơn giản (image-classify + servo actuation) sang VENTUNO Q hoặc mesh UNO Q trước khi cam kết kiến trúc.
