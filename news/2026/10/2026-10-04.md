## 1. DuckDB Ships a Dimension-Table Pattern for Faster String Aggregations

| Field | Value |
|---|---|
| 📅 Date | 02/10/2026 |
| 🏷️ Topic | Tutorial |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `duckdb` · `dimension-tables` · `hash-aggregation` |

### 🔭 Overview (Tổng)
The DuckDB team published a technique post on 2 October titled "Faster String Aggregations with Dimension Tables" that walks through a concrete pattern for cutting the cost of `GROUP BY` queries over repeated string columns. The target reader is a working analyst or data engineer whose columns look like station names, product SKUs, or event types — low-cardinality text that repeats millions of times — and whose aggregation queries sit on the critical path of a dashboard. The post is not announcing a new engine feature; it is codifying a schema pattern users can apply by hand today, which makes it immediately useful on any current DuckDB build.

### 🔬 Details (Phân)
The pattern is a classic star-schema move translated into a step-by-step DuckDB recipe. Pull the distinct string values into a small dimension table, assign each one a sorted narrow integer surrogate key, replace the string column in the fact table with the key, then do the heavy aggregation on the integer and join the string back only at the very end. The post explains why this helps: narrow integers let DuckDB use perfect hash aggregation, hash-table memory shrinks because keys are two bytes instead of variable-length strings, and comparison cost drops to a few CPU instructions where the string version "grows with the length". The worked example uses a 380,959-row Dutch railway dataset where "Amsterdam Centraal" appears 7,591 times as an 18-byte string, with 537 distinct station names fitting comfortably in `USMALLINT` and 15 distinct service types fitting in `UTINYINT`.

The post is deliberately honest about what it does not provide. There are no end-to-end speedup numbers quoted for the train-services dataset; the author recommends readers "compare both versions" for their own data because the win depends on string length, cardinality, and the specific aggregation. The pattern competes with the engine's own dictionary encoding of VARCHAR columns, which handles the common case automatically, so the technique is positioned for cases where the dictionary either does not fit comfortably in the compression unit or where the same low-cardinality column is reused across many fact tables and should be normalised once. For a star-schema warehouse built on DuckDB this is also the shape conformed dimensions want.

The migration cost is small in both directions. The dimension table is built with a single `CREATE TABLE AS SELECT`, the fact table rewrite is a join plus a cast, and queries over the normalised schema add exactly one `LEFT JOIN` at the end. There is no new storage format, no new file, no backwards-incompatible flag. The caveat worth noting is that any downstream tool that reads the fact table expecting raw strings now needs the join, which is a one-line migration in SQL and a view-wrapper fix in BI tools.

### 🎯 Takeaway (Hợp)
If you have a DuckDB table where a text column appears millions of times with only a few hundred distinct values and `GROUP BY` on that column is hot, try this pattern on a copy and measure — the win on hash-aggregation memory and CPU is architectural, not incremental. Về cách dùng, viết sẵn một view join lại dimension table để các dashboard query không phải tự biết schema đã normalise; đây là cách giữ compatibility mà vẫn hưởng benefit về memory và speed.

### 💡 Example
```sql
-- Build the dimension table with narrow sorted keys (537 distinct values → USMALLINT).
CREATE OR REPLACE TABLE stations AS
    SELECT station_name,
           (row_number() OVER (ORDER BY station_name))::USMALLINT AS station_id
    FROM (SELECT DISTINCT station_name FROM train_services WHERE station_name IS NOT NULL);

-- Rewrite the fact table so the hot column is a 2-byte key, not a variable-length string.
CREATE OR REPLACE TABLE train_services_encoded AS
    SELECT ts.* REPLACE (s.station_id AS station_name)
    FROM train_services ts
    LEFT JOIN stations s USING (station_name);

-- Aggregate on the integer key, join the human-readable string back at the very end.
WITH rollup AS (
    SELECT station_id, count(*) AS calls
    FROM train_services_encoded
    GROUP BY station_id
)
SELECT s.station_name, rollup.calls
FROM rollup LEFT JOIN stations s USING (station_id)
ORDER BY rollup.calls DESC;
```

## 2. ClickHouse Managed Postgres Switches Backups to Direct I/O to Protect the Page Cache

| Field | Value |
|---|---|

| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `clickhouse` · `direct-io` · `wal-g` |

### 🔭 Overview (Tổng)
Kaushik Iska, Director of Engineering for ClickHouse Postgres, published a backup-path engineering post on 2 October explaining why the team switched the read path of their WAL-G-based Postgres backups to `O_DIRECT`, and what that change actually bought in production. The problem described is universal to any managed database running on local NVMe: a backup pass reads the entire database through the kernel page cache, evicts the hot pages the running Postgres instance was serving from memory, and tail latencies spike. The fix is a well-known filesystem primitive, but the post is unusually honest about the follow-on problem it creates — losing kernel readahead on striped drives — and shows the sizing math that recovers the lost throughput.

### 🔬 Details (Phân)
The default buffered backup, measured on an `i8ge.12xlarge` with 48 vCPUs, 384 GB RAM, four instance-store NVMe drives, and a 467 GB pgbench database, "evicted the entire 40 GiB idle warm table within 20 seconds" of starting. During that eviction window, p99 query latency jumped from a 0.04 ms baseline to 0.33 ms — 4.7× the undisturbed number — and recovered slowly as Postgres re-paged the working set back in. Switching WAL-G to direct reads with `WALG_DIRECT_IO=true` kept the warm table in the page cache at zero eviction, and brought p99 latency during the backup down to 0.06 ms, 1.5× baseline. The post frames direct I/O not as a performance optimisation but as a page-cache isolation primitive: the backup should not be allowed to share the cache that the serving instance depends on.

The non-obvious follow-on is that bypassing the page cache also bypasses kernel readahead, so naïve direct reads at the default 128 KiB size leave the striped NVMe array under-utilised. The team's fix is to size each direct read to span the full RAID0 stripe: `WALG_DIRECT_IO_BLOCK_COUNT = drive_count × 256`, which on a four-drive array gives 1024 × 4 KiB = 4 MiB reads where "a 4 MiB read covers two full stripes, so every drive serves part of every request". Reader concurrency is tuned to the hardware class — `WALG_UPLOAD_DISK_CONCURRENCY = 48` on dense NVMe boxes and the full vCPU count, half the vCPU count on everything else — because the goal is to saturate the devices without starving Postgres of CPU. With 4 MiB reads at 48 readers, backup duration dropped from 96 seconds (default 128 KiB direct) to 71 seconds, and CPU usage during the backup fell 14% versus the buffered path.

The caveats are stated plainly. Direct I/O requires the file size to be a multiple of the device logical-block size, which WAL-G handles transparently but constrains how the code reads partial blocks at the tail. The approach is specific to the backup read path on local NVMe arrays; it does not generalise to object-storage-backed primary data or to EBS, where the stripe formula does not apply. And the stripe math is per hardware class, not per database — a different instance type with a different NVMe layout wants a different `BLOCK_COUNT`.

### 🎯 Takeaway (Hợp)
If you run Postgres on local NVMe and your backup window has visible query-latency symptoms, this is the pattern to copy — enable `WALG_DIRECT_IO`, size reads to the stripe width using `drive_count × 256`, and scale readers to the hardware class. Về đo lường, hãy thử baseline với `pgbench` trước và sau khi bật flag để xác nhận page-cache được bảo toàn và p99 trong backup window không tăng quá 1.5–2× — nếu con số còn cao, nhiều khả năng là `BLOCK_COUNT` chưa match stripe width hoặc concurrency đang bóp CPU của Postgres.

### 💡 Example
```sh
# WAL-G direct I/O knobs that ClickHouse Managed Postgres uses in production.
# For a 4-drive NVMe RAID0 on an i8ge.12xlarge (48 vCPU, 384 GB RAM).

export WALG_DIRECT_IO=true
export WALG_DIRECT_IO_BLOCK_COUNT=1024    # 4 drives × 256 blocks × 4 KiB = 4 MiB per read
export WALG_UPLOAD_DISK_CONCURRENCY=48    # dense NVMe rule: use the full vCPU count
export WALG_COMPRESSION_METHOD=lz4

# Trigger the backup; the direct-I/O read path keeps Postgres' hot pages in the
# page cache instead of evicting them.
wal-g backup-push "$PGDATA"
```

### 🔭 Overview (Tổng)
AWS's Big Data blog published a walkthrough on 1 October by Yashika Jain, Kalyan Janaki, and Vinayaka Gangadhar on enabling KIP-848, the Next Generation Consumer Rebalance Protocol, on Amazon MSK clusters running Apache Kafka 4.x. The protocol itself is upstream, shipped with Kafka 4.0, but the post matters because MSK Standard and Express brokers on 4.x now carry the server-side support and the client-side opt-in is a one-line configuration change. For teams running large consumer groups where rebalance pauses are visible on their dashboards, this is the fix that was promised when 4.0 shipped and is now a drop-in on managed Kafka.

### 🔬 Details (Phân)
The architectural change moved by KIP-848 is specific. The classic rebalance protocol was client-driven and used a global synchronization barrier — every consumer in the group paused processing at the same time, synced with the group coordinator, received a new assignment, and resumed, regardless of whether its particular partition assignment had changed. The new protocol is "fully server-driven" with "incremental, async reconciliation": the broker owns the assignment logic and sends targeted updates, so "only affected partitions move during a rebalance, and consumers with unchanged assignments continue processing uninterrupted". For a 100-consumer group where a single consumer joins or leaves, that is the difference between a 100-way pause and a one-way handoff.

Enabling the new protocol on MSK is deliberately conservative. The server side is on when the cluster runs any 4.x Apache Kafka version on either MSK Standard or Express brokers; the client side is opt-in. "The protocol is not enabled by default", so an application has to set `group.protocol=consumer` explicitly on its consumer config — otherwise it stays on `classic`. The post covers both Python and Java consumer configs, with a working `confluent-kafka-python 2.12.0+` example for Python and a note that Java has been GA since Apache Kafka 4.0. It also walks through static membership via `group.instance.id`, which pairs well with the new protocol for container restarts: with static membership, a planned restart does not trigger a rebalance at all, and when a rebalance does happen only the affected partitions move.

The post includes a diagnostic section for when the new protocol does not deliver the expected latency improvement, which is the honest content you want from a tutorial. Common failure modes called out are: the client library predates `group.protocol` support (older `confluent-kafka-python` or Java clients will silently fall back to classic); the cluster is still on 3.x so the broker rejects the new protocol; and partition-assignment strategies configured on the client are ignored because assignment is now broker-side. A graceful-shutdown pattern using signal handlers to trigger an "immediate leave-group" is included to avoid stale assignments during pod rotation.

### 🎯 Takeaway (Hợp)
If you run Amazon MSK on 4.x and have consumer groups with more than a handful of members, flip `group.protocol=consumer` on the clients and measure rebalance latency on a planned deploy — the broker is ready, the only thing in the way is the client config. Về rollout, bắt đầu bằng một consumer group non-critical, kiểm tra end-to-end latency không bị regress, rồi mới mở rộng; cũng nên verify client library version để tránh silent fallback về classic protocol.

### 💡 Example
```python
# Opt in to KIP-848 Next Generation Consumer Rebalance Protocol on Amazon MSK 4.x.
# Requires confluent-kafka-python >= 2.12.0; the broker side ships with any 4.x cluster.

from confluent_kafka import Consumer
import signal, sys

config = {
    'bootstrap.servers': bootstrap_servers,
    'group.id': 'orders-processor',
    'group.protocol': 'consumer',          # required; defaults to 'classic'
    'group.instance.id': 'orders-pod-01',  # static membership — restarts don't rebalance
    'auto.offset.reset': 'earliest',
    'enable.auto.commit': False,
}

consumer = Consumer(config)
consumer.subscribe(['orders'])

def shutdown(signum, frame):
    consumer.close()   # triggers an immediate leave-group so stale assignment doesn't linger
    sys.exit(0)

signal.signal(signal.SIGTERM, shutdown)

while True:
    msg = consumer.poll(1.0)
    if msg is None or msg.error():
        continue
    process(msg)
    consumer.commit(msg)
```

### 🔭 Overview (Tổng)
Monogoto's engineering team published a comparison on IoT For All on 2 October titled "GEO vs. LEO vs. Direct-to-Device: Satellite IoT Options Compared" that lays out the three satellite-connectivity architectures an IoT engineer actually has to choose between in late 2026. The piece names the operators that are commercially live versus still ramping, cites the 3GPP Release 17 NTN band identifiers each tier uses, and gives concrete latency numbers rather than vague "high" or "low". It is useful not because any single fact is new but because the three categories are usually conflated in product marketing, and the post draws the distinctions in a way that maps cleanly to a build-vs-buy decision.

### 🔬 Details (Phân)
The three categories are physically different. GEO at 35,786 km altitude needs as few as three satellites for near-global coverage but carries 480–600 ms round-trip latency. The commercially-live NB-IoT NTN service today "runs mostly over GEO, in L-band, through Skylo", using 3GPP Release 17 band n255 (1525–1559 MHz downlink, 1626.5–1660.5 MHz uplink). The fit is asset tracking, container telemetry, pipeline monitoring — workloads that send a few bytes every few minutes and do not care that the round trip is half a second. LEO at 500–1,200 km altitude cuts latency to 20–40 ms but requires hundreds to thousands of satellites; named NB-IoT/LTE-M NTN operators here include Iridium, OQ Technology, and Satelliot, with coverage still ramping and S-band band n256 (2170–2200 MHz down, 1980–2010 MHz up) in active use. Starlink Direct to Cell and AST SpaceMobile also sit in LEO but target a different radio layer entirely.

Direct-to-Device is the category that gets most confused in press coverage. It is not a different orbital tier but a different radio model: the satellite transmits on terrestrial mobile spectrum, so an unmodified smartphone can connect without special hardware. Starlink's partnership with T-Mobile and AST SpaceMobile's partnerships with AT&T, Verizon, and Vodafone are the named deployments. Shared capacity is roughly 2–4 Mbps per cell today, oriented toward consumer SOS, texting, and voice; broadband voice/video/data is pushed to 2027+. For narrowband sensor IoT, the post is explicit that D2D is the wrong tool — "unsuitable for battery-constrained sensor deployments requiring efficient narrowband communication" — because the terrestrial-spectrum design does not carry the NB-IoT power-save behaviour that extends battery life to multi-year operation.

The practical consequence is that the three tiers are "not interchangeable, and they're not competitors either" but layers of the same connectivity stack. A real deployment might use GEO NB-IoT NTN as the always-on fallback for coverage gaps, LEO NB-IoT NTN as it matures for lower-latency telemetry, and consumer D2D on the smartphone the field technician carries — three different radio paths serving three different roles in the same product. The post names Release 18 extensions and a Keysight/Samsung S-band n252 demonstration from January 2026 as the direction of travel.

### 🎯 Takeaway (Hợp)
If you are scoping a satellite-IoT product for a late-2026 deployment, pick the tier by workload shape — GEO L-band NB-IoT NTN via Skylo for commercially-available asset tracking today, LEO as the roadmap bet, and D2D only if your device is actually a phone. Về band selection, bắt buộc confirm chipset trong module đã certify n255 (hoặc n256 nếu đi LEO) trước khi order; vendor datasheet thường claim "NTN-capable" nhưng không phải band nào cũng supported qua firmware hiện tại.
