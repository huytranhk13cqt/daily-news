## 1. Databricks NEAREST BY Pushes Vector Search Into the SQL Join Plan

| Field | Value |
|---|---|

| 🏷️ Topic | News |
| 🌐 Domain | Data Engineering |

### 🔭 Overview (Tổng)
Zero Qu, Alexis Schlomer, Akash Nayar, Yingyi Bu and Sergei Tsarev published a Databricks engineering post on 5 October titled "NEAREST BY Join: Scaling Vector Search in Databricks Runtime" that promotes vector search from a client-side detour to a first-class SQL join operator. The piece positions NEAREST BY as the mechanism that lets an analytics engine do batch k-nearest-neighbour lookup inside the query plan — "for every query row, find the k nearest rows by vector similarity or distance — exact or approximate" — rather than exporting both sides to a dedicated vector store. The framing matters because the operational premise of a lakehouse falls over the moment someone has to run and sync a separate vector service, and this is the first time Databricks has tried to collapse that split with a native join rather than a bolt-on function.

### 🔬 Details (Phân)
The surface API is a single new join form. A query reads `SELECT * FROM queries NEAREST BY SIMILARITY TO (SELECT vector FROM base) ORDER BY similarity LIMIT k` and the planner recognises it as a bulk vector-to-vector match with configurable APPROX or EXACT mode and either BY SIMILARITY or BY DISTANCE semantics. Underneath, the piece names three cooperating pieces that make the operator viable at scale: a fused Photon operator that collapses cross join plus distance scoring plus a partial top-k into one custom GEMM kernel whose arithmetic intensity scales with batch size and "crosses the roofline ridge point at batch sizes of 64 or more queries"; native SIMD vector functions including `vector_inner_product`, `vector_cosine_similarity`, `vector_l2_distance`, `vector_norm`, `vector_sum` and `vector_avg`; and a bounded heap-based top-k aggregate with O(k) memory that supports k up to 100,000 and is distributable through the usual partial/merge contract.

The indexing side is the piece that explains why the authors can quote billion-vector corpora. Rather than invent a new index container, the engineering team maps an IVF (inverted-file) index onto a liquid-clustered Delta table — each centroid becomes a cluster key, each vector lands in the partition for its nearest centroid, and the probe step reduces to normal Delta partition pruning. The post states "no separate vector store, no sync pipeline to keep consistent, no second system to operate" and claims probe queries touch "less than 0.1% of a billion-scale corpus" when nprobe is modest. Because the index is just a Delta table, it inherits time travel, Unity Catalog grants, OPTIMIZE compaction and liquid clustering tunability for free.

The caveats the post is careful to flag are version and mode discipline. The article does not pin a specific Databricks Runtime version where the operator GA'd, and the Photon fused kernel is the piece that delivers the big numbers — pure Spark execution does not currently fuse the operator, so a workspace stuck on a non-Photon warehouse will see a much weaker win. APPROX mode trades recall for latency along the usual IVF axis (nprobe) and is the right choice for interactive serving; EXACT is still useful for golden-set evaluation and small corpora. There is no mention of HNSW as an index variant, so teams that depend on HNSW recall curves need to validate IVF plus Delta clustering gives acceptable recall on their data distribution before migrating off a dedicated vector service.

### 🎯 Takeaway (Hợp)
If you already pay for Photon warehouses and were about to stand up or renew a dedicated vector database for RAG, agent memory, or similarity recommendation, re-run the sizing exercise against NEAREST BY first — the Delta IVF path makes the question whether a second system is still worth operating. Về triển khai, bắt đầu bằng corpus 10M-100M vector trên Photon warehouse, test APPROX ở nprobe thấp để đo recall vs latency, và chỉ migrate production khi đã kiểm tra kỹ Databricks Runtime hiện tại có fused operator; EXACT mode nên dành cho offline evaluation.

### 💡 Example
```sql
-- NEAREST BY join on Databricks (post dated 05/10/2026).
-- Pattern: a batch of query embeddings against a billion-vector base table.

SELECT q.query_id,
       b.doc_id,
       vector_cosine_similarity(q.embedding, b.embedding) AS similarity
FROM   query_batch AS q
NEAREST BY SIMILARITY TO (
  SELECT doc_id, embedding
  FROM   docs_base
) AS b
ORDER BY similarity DESC
LIMIT 10;                       -- top-10 per query row; k up to 100,000

-- APPROX mode with nprobe tuning for the Delta-backed IVF index:
SET spark.databricks.vector.search.mode = 'APPROX';
SET spark.databricks.vector.ivf.nprobe = 8;
```

## 2. DuckDB Java Table Functions Beat JDBC and Appender for Streaming MongoDB Loads

### 🔭 Overview (Tổng)
DuckDB's blog on 5 October carried a guest post by Geertjan Wielenga and Alex Kasko titled "Importing Data using Java Table Functions" that documents a feature often missing from the Java-side DuckDB conversation: user-defined table functions written directly in Java. The post walks through what the Java API looks like, where it slots into the DuckDB execution model, and — the headline — benchmarks it against the usual JVM ingest paths on a real 485,168-record MongoDB extract. For teams whose production warehouse of record is DuckDB but whose source systems are JVM-native, this closes a gap that has pushed people to CSV staging or JDBC bridges.

### 🔬 Details (Phân)
The programming model is a parameterised interface `DuckDBTableFunction<BindData, GlobalData, LocalData>` with three lifecycle hooks: `bind` populates `DuckDBTableFunctionBindInfo` to declare the output schema; `init` receives a `DuckDBTableFunctionInitInfo` to open shared resources and set max parallelism via `info.setMaxThreads(8)`; and `apply` is invoked per thread with a `DuckDBTableFunctionCallInfo`, which hands back a `DuckDBDataChunkWriter` into which the implementation writes up to 2,048 rows per chunk using column vectors (`output.vector(0).setString(row, ...)`). Parallel execution requires `SET preserve_insertion_order = FALSE` because the writer threads interleave chunks and ordering is not preserved by design.

The benchmark is where the post earns its substance. On a 485,168-record MongoDB dataset the four JVM-side paths rank as: the native DuckDB MongoDB Extension at 55 seconds (the baseline the post is trying to match without taking an extension dependency), JDBC batch inserts at 3 minutes 37 seconds (dominated by per-row overhead), the DuckDB Appender interface at 2 minutes 2 seconds (true batching but single-threaded), and the Java Table Function at 1 minute 27 seconds (parallel apply, day-sized batches). The post notes the Java Table Function matches the MongoDB extension on larger production data, which is the real argument for the pattern: comparable throughput without inheriting another extension's version pins or network dependencies.

The use cases demonstrated are concrete and recognisable. The first is analytics acceleration — pulling a year of vulnerability-scanner records out of MongoDB into DuckDB so that scoped filter queries drop from multi-second to sub-second response times. The second is parallel ingest from a slow-but-partitionable source where day-sized shards fan out across the eight worker threads. The third is Excel export acceleration, where a 2–3 minute export for 50,000 rows collapses to under 10 seconds once DuckDB sits between the source and the writer. The honest limitation the post implies but does not say outright is that the pattern binds the data pipeline to the JVM — teams on Python-only stacks get no benefit, and `preserve_insertion_order = FALSE` means downstream SQL cannot assume source order.

### 🎯 Takeaway (Hợp)
If your source-of-truth is a JVM database or document store and you have been building fragile CSV staging or JDBC passthrough just to feed DuckDB, this is the pattern to try next — the API surface is small, parallelism is a single flag, and the published benchmarks beat JDBC by a factor of two or three. Về triển khai, start with a prototype table function that returns a bounded sample, verify output chunk sizes match your downstream consumers (DuckDB default 2048 rows per chunk is a sensible floor), then enable `setMaxThreads` and `preserve_insertion_order = FALSE` only after confirming no downstream query depends on insertion order.

### 💡 Example
```java
// DuckDB Java Table Function skeleton (duckdb.org, 05/10/2026).
// Implements a MongoDB -> DuckDB parallel loader.

public class MongoLoadTF implements DuckDBTableFunction<Bind, Global, Local> {
  @Override public void bind(DuckDBTableFunctionBindInfo info) {
    info.addColumn("ts",   DuckDBType.TIMESTAMP);
    info.addColumn("key",  DuckDBType.VARCHAR);
    info.addColumn("body", DuckDBType.JSON);
  }

  @Override public void init(DuckDBTableFunctionInitInfo info, Global g) {
    g.mongo = MongoClients.create(uri);         // one connection per global
    info.setMaxThreads(8);                      // enable parallel apply()
  }

  @Override public void apply(DuckDBTableFunctionCallInfo info, Local l) {
    DuckDBDataChunkWriter out = info.writer();  // chunks of up to 2048 rows
    for (Doc d : l.cursor.nextBatch(2048)) {
      int r = out.appendRow();
      out.vector(0).setTimestamp(r, d.ts);
      out.vector(1).setString(r, d.key);
      out.vector(2).setString(r, d.body.toJson());
    }
  }
}

-- SQL side:
SET preserve_insertion_order = FALSE;           -- required for parallel apply
CREATE TABLE events AS SELECT * FROM mongo_load_tf('mongodb://...');
```

### 🔬 Details (Phân)
The hardware stack is specific. The accelerator is the DEEPX DX-M1M, available now at 25 TOPS; a 13 TOPS variant is scheduled for late 2026. The ecosystem reading is that this is the first mainstream Pi HAT in the field that competes directly with the Hailo-8L and NVIDIA Jetson Orin Nano on edge-AI benchmarks while staying inside the Pi 5 power envelope. For deployments that have been pushed to Jetson Orin or an x86 edge gateway purely because the Pi 5 lacked an NPU with real memory bandwidth, this is now an evaluable alternative. The honest caveats are that pricing is not stated in the post, the quoted FPS numbers are vendor-provided ModelZoo exports (so recall and accuracy on a custom-trained model may be lower), and sustained 3 W is a typical rather than worst-case figure — thermally constrained enclosures should budget for the Pi 5's own power ceiling on top.

### 🔭 Overview (Tổng)
Al Williams's "The FPGA Chronicles: Open Source It" on Hackaday, published 5 October, is the sequel instalment in a running series on learning FPGA development on cheap boards; this entry replaces the vendor GOWIN toolchain with APIO, the open-source aggregator that bundles Yosys, nextpnr, GTKWave and openFPGALoader behind a single CLI and VS Code extension. The target board is the Sipeed Tang Nano 20K — a sub-$30 GOWIN FPGA development board that has become a common entry point for homebrew FPGA work — and the post's useful contribution is a concrete, working `apio.ini` and simulation recipe that avoids the proprietary GOWIN installer entirely.

### 🔬 Details (Phân)
The configuration surface is deliberately minimal. APIO reads an `apio.ini` at the project root that pins board, toolchain, and simulator; from there, `apio build`, `apio sim`, and `apio upload` cover the three usual phases. The post includes the specific clock-programming invocation `pll_clk O0=27M -s` wired to FPGA pin 10 — the Tang Nano 20K's on-board 27 MHz oscillator feeds a GOWIN PLL and APIO's generator script emits the correct bitstream for it. For simulation, the post uses GTKWave over a Verilator-driven testbench and notes a practical gotcha: at full clock rates the VCD trace files balloon rapidly, so the testbench clocks the DUT at a reduced rate to keep file sizes manageable while still catching timing-order bugs.

The piece's non-tutorial contribution is a comparative read on open-source versus vendor FPGA tools. APIO abstracts the toolchain so the same CLI drives iCE40, ECP5 and GOWIN flows, which matters for a hobbyist who may own more than one FPGA family. Williams also calls out a library-conflict workaround — renaming the system `libreadline.so.8` where it collides with the APIO-provided copy — the kind of friction that reads as unremarkable in a tutorial but is the exact failure mode that burns a Saturday afternoon on an unfamiliar board. VS Code integration via the APIO extension is explicitly supported, which lowers the barrier for engineers who do not want to live in a dedicated terminal.

The ecosystem reading is modest. For professional ASIC/FPGA teams on commercial support contracts, this changes nothing. For the much larger audience of embedded engineers who touch an FPGA occasionally and would rather not babysit a vendor installer, APIO plus the Tang Nano 20K is now a credible all-open-source story — which is also a credible all-reproducible-build story for CI, since the toolchain pins into a project's `apio.ini` rather than depending on a developer's machine. The caveat Williams implies is that GOWIN's own simulator still has features APIO's open path does not match on every corner case; teams validating against the vendor flow should spot-check timing closure before committing to the open toolchain on a production project.

### 🎯 Takeaway (Hợp)
If you have a Tang Nano 20K on the bench and have been avoiding it because the GOWIN installer is painful, this is the week to try APIO — the `apio.ini` pattern is small enough to live in a repo, VS Code integration is already supported, and the clock-programming recipe is the piece that usually blocks a first bitstream. Về use case, APIO phù hợp cho hobby, education, và CI; cho production thiết kế cần vendor timing analyzer thì vẫn nên giữ GOWIN cạnh bên để spot-check cho tới khi tin tưởng được open-source P&R trên board cụ thể của bạn.

### 🔭 Overview (Tổng)
Aaron Beckendorf covered a project by builder opsobot on Hackaday on 5 October titled "Building A Cheap, Dexterous Robot Hand" that documents the Yeah Hand (formerly Rebelia) — a mostly 3D-printed, cable-driven, five-finger robotic hand with both a research-robot variant and an experimental prosthetic variant. The design is unusual for a hobby build in that the published numbers are not demonstration-grade: the hand lifted 8 kg and sustained 800 open-close cycles without overheating. Source and a ROS driver are available, which means the project is directly usable as a reference rather than only inspiration.

### 🔬 Details (Phân)
The actuation design puts all five servos outside the finger assemblies and runs fishing-line tendons through PTFE Bowden tubes down to each fingertip, with silicone grips on the inner finger surfaces and sculpted thumbnails for small-object pinch. "No actuators within the fingers themselves" is the design choice that produces the project's unusual thermal budget — motor losses dissipate at the forearm manifold rather than inside the finger assemblies, and the PTFE guides keep friction low enough that the 800-cycle endurance run completed without the motors approaching their thermal limit. Grasping force peaks at about 5 kg while the full-arm lift carries 8 kg; the discrepancy is the usual cable-driven split between static holding force and dynamic lift.

The software and ecosystem story is where the project earns a mention outside the usual Hackaday project writeup. The ROS driver sits at `github.com/opsobot/yeah_hand_ros` and exposes the hand as a conventional ROS actuator so a user can target it from MoveIt, from a URDF-based simulation, or from a flex-sensor glove — the demonstration input device the builder uses to mirror a human operator's finger positions in real time. The project page is Hackaday.io project 204373. The prosthetic variant uses the same base mechanism with grip-geometry changes rather than a different drive mechanism, which keeps the parts list and the ROS driver shared between the research and the medical use cases.

The ecosystem reading is pragmatic. Low-cost, high-force, ROS-ready end effectors have historically been the hardest part of a research manipulator; most hobby hands either lift under 1 kg or depend on a bespoke, undocumented serial protocol. A reproducible BOM, a ROS driver, and credible force and endurance numbers mean the Yeah Hand is now a reasonable starting point for a university lab or a prosthesis research group that would otherwise have had to build the actuator stack from scratch. The caveats are the usual: this is a solo builder's project, the long-term maintenance commitment is unknown, and the 800-cycle endurance claim is a single run rather than a lifetime rating.

### 🎯 Takeaway (Hợp)
If your lab or hobby project needs a sub-$1k dexterous end effector that already speaks ROS, pull the Yeah Hand repo and the Hackaday.io BOM before you start a from-scratch design — the externalised-actuator plus Bowden-tendon pattern is the piece that explains the force and thermal numbers. Về sản phẩm, vẫn nên treat đây như một reference design cộng đồng: in thử một prototype, chạy stress test riêng cho use case cụ thể, và chuẩn bị sẵn fallback nếu các dung sai in 3D của bạn khác với builder gốc.
