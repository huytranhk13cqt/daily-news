## 1. IFCO Cuts a dbt Job From 7 Hours to 2h20 on Databricks With Liquid Clustering and Per-Model Tasks

### 🔭 Overview (Tổng)
Fernando Muñoz, Ludwig Brummer and Maxim Hammer at Databricks published a guest piece on 6 October titled "Scaling and Operating a Large dbt Project on Databricks: IFCO's Data Team on Performance, Visibility, and Debugging" that documents how IFCO tuned the warehouse behind its global reusable-crate pooling service. IFCO tracks hundreds of millions of crates across more than fifty countries, so its daily transformation processes billions of tracking events into cycle-time, loss and breakage KPIs. The write-up matters because it is one of the rare long-form customer case studies that quotes concrete runtime numbers and names the specific Delta Lake and dbt mechanisms behind them, rather than pointing vaguely at platform features.

### 🔬 Details (Phân)
The headline numbers are substantial. Core job runtime fell from about seven hours to two hours and twenty minutes, a sixty-six percent reduction; the consolidation model scans seventy-five percent fewer rows; daily compute cost dropped fifty-eight percent; and the share of assets recomputed on each run fell from close to one hundred percent to between three and five percent. The authors are careful to attribute these gains to a short list of specific Delta Lake tunings rather than a single magic flag: liquid clustering on the asset and event-date columns to make file pruning effective, a MERGE strategy with equi-join predicates that enables dynamic file pruning at the physical plan level, row-hash guards that stop rewrites of rows whose payload has not changed, and time-bounded write windows that keep each run focused on recent data.

The debugging methodology is the part worth quoting back at a reviewer who asks why their incremental model is slow. The piece insists on reading the executed query plan stage by stage from query history, not the compiled SQL, and the consolidation model's slow path turned out to be three distinct problems: upstream timestamps regenerated on every run so every row looked changed to the merge, unbounded window functions scanning the full asset history, and dead columns and forward-looking windows pulling scan volume up for no downstream reader. Fixing these produced the row-scan reduction more than any infrastructure change.

The operational architecture is where the article hands readers a reusable artefact. IFCO replaced a single dbt task with a per-model task graph driven by `databricks-dbt-factory`, an MIT-licensed open-source project that reads a dbt manifest and emits a Databricks job with one notebook task per model. Pre-built base environments bake `dbt-databricks` into the image so cold-start cost is capped, and manifest injection skips re-parsing on every run. On top of this they layer `dbt-bouncer` and `sqlfluff` in CI, uniqueness tests at error severity on primary keys, unit tests on complex logic, and contract enforcement on the layer that external consumers read. The caveats the authors are honest about are that this is a batch architecture — Change Data Feed, Auto Loader and Lakeflow Connect are listed as future work for near-real-time — and that the gains assume Delta Lake plus Photon; the same dbt code on a non-Photon runtime will not see the same curve.

### 🎯 Takeaway (Hợp)
If your dbt-on-Databricks job runs for hours and nothing you have tried in the model SQL has moved the needle, work the checklist in this order: read the actual query plan from query history, add liquid clustering on the real join grain, stop upstream models from regenerating timestamps, bound your incremental merge to a time window, and only then split the dbt graph into per-model Databricks tasks. Về công cụ, `databricks-dbt-factory` là open-source MIT nên có thể copy pattern vào project nội bộ mà không phụ thuộc vendor; nhưng vẫn validate rằng Photon đã bật trước khi expect toàn bộ speedup trong bài.

```yaml
# Pattern from IFCO's dbt-on-Databricks tuning (Databricks blog, 06/10/2026).
# Combines liquid clustering, dynamic file pruning, row-hash guard, and a
# time-bounded merge window on an event-grain consolidation model.

models:
  consolidation:
    materialized: incremental
    incremental_strategy: merge
    unique_key: ['asset_id', 'event_date_time']
    on_schema_change: append_new_columns
    merge_update_columns:
      - status
      - last_seen_ts
    cluster_by:                 # liquid clustering keys = query grain
      - asset_id
      - event_date_time
    partition_by: null          # intentional: let liquid clustering own it

    pre_hook: |
      SET spark.databricks.delta.dynamicFilePruning = true;

    config:
      incremental_predicates:
        - "DBT_INTERNAL_DEST.event_date_time
             >= (current_timestamp() - interval 3 days)"   -- bounded window
      row_hash_guard: md5(concat_ws('||', status, qty, last_seen_ts))
```

## 2. Iceberg REST Catalogs Get REGISTER and UNREGISTER APIs For Zero-Copy Table Handoff

| Field | Value |
|---|---|

### 🔭 Overview (Tổng)
Ryan Blue and Marco Kroll published "Unlocking Data Portability: Preventing Catalog Lock-in with REGISTER and UNREGISTER APIs" on the Databricks blog on 5 October. The piece introduces two complementary HTTP endpoints for the Apache Iceberg REST Catalog (IRC) specification that let an operator move a table between catalogs — Unity Catalog, Nessie, Polaris, Hive, a self-hosted IRC — without copying metadata.json, parquet files, or anything else at the storage layer. The lineage here is important: Ryan Blue is the Iceberg co-creator, so this is the kind of change the Iceberg community has standardised on rather than a Databricks-specific extension.

### 🔬 Details (Phân)
The surface area is deliberately narrow. REGISTER accepts a POST that pairs a desired table name in the target catalog with the URI of an existing metadata.json; the catalog writes exactly one record associating the two and returns. No data files are copied, moved or rewritten; no metadata is regenerated. UNREGISTER, by symmetry, removes a table entry from the managing catalog without deleting the underlying metadata or data, and returns the latest metadata location pointer so the caller can hand it off. The authors frame the pair as the fix for the long-standing hazard that `DROP TABLE` deletes both the catalog entry and the backing data, which previously made clean migrations impossible without manual filesystem copies.

The design invariant the article hammers on is that "the table has exactly one managing catalog at all times." The three-step handoff is UNREGISTER on the source, read the returned metadata location, then REGISTER on the target — a workflow that is safe to pause between steps because at no point do two catalogs claim ownership. The piece explicitly calls out that this eliminates the split-brain scenario of parallel writers from two catalogs racing on the same table, which has been the dominant counter-argument against open table formats in multi-vendor shops. The REST path for Unity Catalog is given concretely as `POST <uc-iceberg-rest-base>/v1/{prefix}/namespaces/{namespace}/tables/{table}/unregister`, matching the pattern used in the upstream IRC spec.

The ecosystem reading is that this is the piece Iceberg was missing to be an actually portable table format rather than a format whose portability depended on which catalog you started in. Teams that have been pinned to a single vendor's catalog because the switching cost was effectively a full data copy now have a cheap exit path; conversely, teams that have been reluctant to adopt an open table format out of lock-in concerns lose one of the stronger objections. The caveats are version discipline — any IRC server implementation has to add both endpoints before the pattern is useful, so interoperability depends on how fast Nessie, Polaris and self-hosted servers ship the matching code — and storage permissions, since the target catalog still needs read access to the metadata URI it is being asked to register.

### 🎯 Takeaway (Hợp)
If you run Iceberg across more than one catalog, or have been holding off adopting Iceberg because catalog migration was a blocker, this is the week to prototype a REGISTER/UNREGISTER rehearsal on a non-production table. Về chiến lược, pattern này biến catalog từ một silo thành một pointer thin layer; nên viết sẵn runbook ba bước (UNREGISTER → fetch metadata location → REGISTER) và test disaster recovery từ catalog A sang catalog B trước khi cần dùng thật.

### 💡 Example
```bash
# Zero-copy table handoff across Iceberg REST catalogs
# (Databricks blog, 05/10/2026). No parquet or metadata.json is moved.

# 1) Remove the table from its current managing catalog.
curl -sS -X POST \
  -H "Authorization: Bearer $SRC_TOKEN" \
  "$SRC_IRC_BASE/v1/prod/namespaces/sales/tables/orders/unregister" \
  | tee /tmp/handoff.json
#   Response includes: {"metadata-location": "s3://warehouse/.../v37.metadata.json"}

META_URI=$(jq -r '."metadata-location"' /tmp/handoff.json)

# 2) Attach the exact same metadata.json to a new catalog as a new table name.
curl -sS -X POST \
  -H "Authorization: Bearer $DST_TOKEN" \
  -H "Content-Type: application/json" \
  -d "{\"name\":\"orders\",\"metadata-location\":\"$META_URI\"}" \
  "$DST_IRC_BASE/v1/prod/namespaces/sales/tables/register"

# Invariant preserved across the sequence:
#   exactly one managing catalog claims the table at any moment.
```

### 🔬 Details (Phân)
The 5 October piece names six concrete workloads it is prepared to document: an agentic-AI development loop where a coding agent like OpenCode runs on the board, writes a sketch, flashes it to the microcontroller side via the on-device RPC bridge and observes the physical outcome before iterating; a local Home Assistant install handling scheduling, historical data, dashboards and integrations with no cloud subscription; a self-hosted n8n automation node that wires APIs, databases and local devices without round-tripping through a cloud workflow service; a Pi-hole DNS-level filter that uses the microcontroller side to drive a physical status display and panic button; a Frigate NVR instance performing real-time object detection on local camera streams; and a Samba-exposed network-attached storage share using an external USB drive. The architectural claim the posts keep returning to is that the microcontroller side keeps hard-real-time control deterministic while the Linux side runs the services and ML inference that cannot be constrained to a 1 kHz loop. The RPC bridge between the two is what makes the dual role usable from a single codebase: a Linux-side service receives a webhook or an AI tool call, decides what should happen in the physical world, and dispatches to the microcontroller side where a Zephyr task closes the control loop. This is the piece most hobby-grade "add AI to Arduino" projects skip and the reason they tend to stutter on real workloads. The articles concede the honest trade-off that no single platform is optimal across embedded sensing, autonomous robotics and video serving, and advise picking the right tool rather than treating the UNO Q as a universal fit.

Distribution is global — Arduino Store, DigiKey, Mouser, RS Components and authorised resellers — but the posts avoid headline pricing, which is the piece a buyer still needs from the product page before costing a fleet. The 6 October piece is explicitly a design-philosophy post rather than a product announcement, so it is best read as context for the 5 October list of concrete workloads.

### 🎯 Takeaway (Hợp)
If you were about to build an edge gateway from a Raspberry Pi plus an external microcontroller, or buy a commercial smart-home hub plus a separate RTOS board, pull the UNO Q onto the eval shortlist — the Linux side is already set up to run Home Assistant, n8n, Pi-hole and Frigate, and the Zephyr-on-STM32H5 side gives you deterministic control under the same roof. ## 4. EDG C++ Compiler Frontend Enters Open Source Under the C++ Alliance

### 🔭 Overview (Tổng)
Maya Posch wrote on Hackaday on 6 October that Edison Design Group — the Boston-area firm that has quietly licensed its C++ frontend to Intel C++, Microsoft Visual C++ and NVIDIA's CUDA compiler since 1988 — is winding the company down and transitioning its frontend to open source under the C++ Alliance, a nonprofit. The code is now on GitHub under the EDGCPP account. For embedded teams this is bigger than it sounds: EDG is the third industrial-grade C++ parser outside GCC and LLVM/Clang, and vendor toolchains for several microcontroller families have historically been built on top of it rather than on either of the open two.

### 🔬 Details (Phân)
The practical significance comes from how C++ is parsed. Posch's piece underlines that "parsing C/C++ correctly is a famously impossible problem if you aren't already one of the big two" — GCC and Clang have spent decades absorbing standard quirks, compiler-specific extensions and ABI edge cases that are not fully written down anywhere. EDG is one of the very few organisations to have shipped a competitive implementation; the frontend's extensive internal test matrix has in the past surfaced conformance bugs in both GCC and Clang. Having that implementation in public source, under a nonprofit stewardship model rather than a per-seat commercial licence, lowers the barrier for new compiler projects, static analysers, IDE tools and embedded toolchains that need a C++ parser without the multi-year investment of writing one.

The stewardship story is the next thing to pay attention to. The C++ Alliance is positioned as the long-term maintainer and will drive the governance, release cadence and standard-tracking work that EDG's small commercial team used to do. Public open-sourcing does not automatically mean active maintenance, and the Alliance's bandwidth to keep pace with C++26 and C++29 feature work will determine whether this ends up as a living project or a snapshot in a repository. The GitHub repository is already live and reviewable; the article does not pin a specific licence identifier, which is the first detail an embedded vendor evaluating integration should confirm before writing it into a product roadmap.

The ecosystem reading is cautious. Commenters on the Hackaday thread raised whether specific microcontroller architectures that currently depend on EDG-based commercial toolchains will see smoother upgrades or whether vendors will quietly migrate those chains to Clang over the next cycles. The honest answer is that both are plausible: a vendor already paying EDG royalties has an incentive to adopt the open fork and keep its existing patches; a vendor already moving to LLVM infrastructure for other reasons has less reason to invest in a parallel frontend. For a working embedded engineer the immediate effect is probably minimal, but the long-term shape of C++ toolchains for proprietary silicon just changed.

### 🎯 Takeaway (Hợp)
If your product depends on a commercial C++ toolchain for a specific microcontroller, read your vendor's release notes over the next quarter — the EDG open-sourcing creates both an opportunity for cheaper upgrades and a risk that the vendor migrates to Clang on a timeline you cannot control. Về công cụ cá nhân, không có việc gì phải làm ngay nhưng đáng bookmark repo EDGCPP trên GitHub và theo dõi hoạt động của C++ Alliance trong 2–3 release tới trước khi coi đây là một compiler frontend sẵn sàng production ngoài các vendor-based use case hiện có.

### 🔭 Overview (Tổng)
Simon Long at Raspberry Pi published "Raspberry Pi Desktop now available for PC and Mac" on 6 October, announcing the first major update to the project's x86 desktop image since the Bullseye-based build. The new image is based on Debian Trixie and ships as a live USB with optional persistence or a permanent install via the Calamares installer. For embedded engineers the practical reason to care is that this is now a Pi-flavoured desktop that boots on existing hardware and includes the Raspberry Pi Connect client out of the box, which means a workstation can act as a remote-access endpoint for a fleet of Pi devices without a separate setup.

### 🔬 Details (Phân)
The architecture detail driving the system-requirements story is that the new build is sixty-four-bit only; Debian itself dropped mainline thirty-two-bit PC support, and Raspberry Pi has followed. The practical consequence is that most PCs manufactured within the last fifteen years boot the image, but a thirty-two-bit-only machine does not. Apple Silicon is unsupported, since Debian's ARM64 support on M-series silicon is still experimental, so the Mac side of the release targets Intel Macs — a shrinking but real population of lab, workshop and refurbished-fleet machines. Long is explicit in the post that "unfortunately those of you with the latest and greatest shiny fruit products will not be able to run this."

The in-box desktop story is a visible refresh rather than a redesign. The release ships with an updated Control Centre and a new dock, which brings the x86 image closer to the look and feel of a current Raspberry Pi OS install. The bundled Raspberry Pi Connect client is the more consequential change: Connect gives screen-sharing and remote-access access between desktops and Pis without manually configuring SSH tunnels, VPNs or third-party remote-desktop stacks, and having it preinstalled on the PC/Mac side removes a step that previously had to be done per machine. Live-USB persistence is the install mode most useful for support engineers who need to drop into customer sites with a sanitised OS on a USB stick and still carry their own tooling between visits.

The honest ecosystem reading is that this is not an engineering release so much as an availability one. There is no new kernel feature, no new boot-time pipeline and no changed drivers worth calling out for an embedded project. What has changed is that the Pi project now actively publishes a current Debian-based desktop for the two most common non-Pi developer-workstation platforms, which keeps the Pi ecosystem's x86 presence from drifting into the "last touched in 2022" bucket. For a team already running a Raspberry Pi fleet in production, the Connect preinstall is a small ergonomic win.

### 🎯 Takeaway (Hợp)
If you support or deploy Raspberry Pi fleets and currently use a Windows or macOS workstation, drop the Trixie-based Pi Desktop image onto a sixteen-gigabyte USB stick and keep it in your bag — the preinstalled Pi Connect client makes it a drop-in remote-access workstation on any Intel laptop you can borrow. Về mặt kỹ thuật, không có breaking change đáng kể để lên kế hoạch migration, nhưng cần biết trước là Apple Silicon chưa support, nên các team all-M-series phải tiếp tục dùng Pi Imager và Pi Connect từ macOS ARM thay vì chạy image này native.
