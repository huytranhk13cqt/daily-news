## 1. Databricks Opens Workday Data Connect Federation in Unity Catalog via Iceberg REST

### 🔭 Overview (Tổng)
Dan Zuckerberg, John Spencer, Kosta Bizetic and Katie Cummiskey at Databricks published "Announcing Workday Data Connect federation in Unity Catalog" on 8 October, opening the connector to public beta. The feature registers Workday HR and finance tables that a Workday administrator has published through Workday Data Cloud as a foreign catalog in Unity Catalog, and lets Databricks compute read them in place as Apache Iceberg tables through Workday's Iceberg REST catalog. For teams that have been running nightly extracts out of Workday to answer basic headcount, compensation and cost-centre questions, this is the alternative that lets the warehouse read from the system of record without an ingestion pipeline.

### 🔬 Details (Phân)
The handshake is deliberately narrow. On the Workday side an administrator shares the approved tables through Workday Data Cloud, registers an API client that uses a JWT Bearer Grant, uploads a public key and grants a Workday Integration System User (ISU) read access to the shared surface. On the Databricks side an admin creates a single OAuth connection and a foreign catalog in Unity Catalog; Databricks then performs the OAuth token exchange against Workday's Iceberg REST catalog itself, so analysts never touch a Workday token endpoint. Unity Catalog resolves the foreign catalog's metadata and Databricks compute reads the backing files directly from Workday's managed object storage, with table-level access controls applied through Unity Catalog on top. Query paths are standard SQL plus natural language through Genie. The runtime prerequisites are a Unity Catalog-enabled workspace, Databricks Runtime 19 or later, and a workspace admin enabling the connector from the Previews page while it is in beta.

The piece places the feature on the same ladder as two existing paths. Lakeflow Connect for Workday Reports, Workday HCM and Workday Activity Logs is the managed, incremental ingestion option that lands Delta tables in Unity Catalog and preserves history with SCD2 — the right choice when a team needs a durable copy with its own retention. A JDBC Live Data Query connection is the on-demand option that fetches rows at query time without putting metadata into Unity Catalog. Federation sits between the two: metadata lives in Unity Catalog, data stays in Workday, no rows are copied, and no incremental state has to be reconciled. The read-only constraint and the fact that Workday remains the system of record make it unsuitable for scenarios that want to mutate HR data from Databricks, which is a non-feature by design rather than a limitation.

The ecosystem reading is that this is another concrete use case for the Iceberg REST catalog spec outside of the data-platform vendors themselves. Workday exposing its managed data as an Iceberg REST endpoint, and Databricks federating over it, is the pattern several SaaS vendors have signalled they want to adopt; the caveats are the usual public-beta ones — Databricks lists this as public beta, not GA, so production commitments should wait, and the connector depends on how often Workday refreshes the Iceberg metadata, which is not pinned to a specific SLA in the post.

### 🎯 Takeaway (Hợp)
If your organisation already pays for Workday Data Cloud and runs Unity Catalog, prototype this against a non-production ISU and compare it against your current Workday extract pipeline on three axes: freshness, cost of the compute that reads the federated catalog, and effort to replicate the row filters and column masks you have today. Về mặt kiến trúc, pattern này cho phép giữ Workday là system of record đồng thời đưa dữ liệu HR vào context của Genie và các mô hình xuôi dòng mà không phải vận hành thêm pipeline ingestion — nhưng vì đang public beta, hãy giới hạn phạm vi ở các truy vấn analytics đọc, chưa commit workload sản xuất.

### 💡 Example
```sql
-- Pattern from Databricks' Workday Data Connect federation announcement
-- (08/10/2026). Metadata lives in Unity Catalog, data stays in Workday.

-- 1) Workspace admin creates the OAuth connection to Workday (one time).
CREATE CONNECTION workday_prod TYPE workday
OPTIONS (
  host           '<tenant>.workday.com',
  client_id      '<workday_oauth_client_id>',
  jwt_key_id     '<kid of uploaded public key>',
  isu_user       'databricks_svc_reader'
);

-- 2) Register the foreign catalog that fronts Workday's Iceberg REST catalog.
CREATE FOREIGN CATALOG workday_hcm
USING CONNECTION workday_prod
OPTIONS (catalog_name 'hcm_shared');

-- 3) Query the shared tables in place. No ingestion, no copy.
SELECT cost_center, SUM(fte) AS fte_total
FROM   workday_hcm.people.employees
WHERE  employment_status = 'Active'
GROUP  BY cost_center
ORDER  BY fte_total DESC;
```

### 🔭 Overview (Tổng)
Franck Nijhof published "2026.10: You are here" on the Home Assistant blog on 7 October, cutting the project's October release. The release lands five visible UX changes — a trigger-ID picker inside the condition editor, a Modbus connections panel under Settings → Connectivity, a vector OpenStreetMap renderer that replaces the raster map tiles, a one-click Model Context Protocol server in the AI page, and a reorganised profile page with per-user name and picture editing — alongside fifteen new integrations and a tightly scoped set of breaking changes. For a running Home Assistant install it is a routine monthly bump; for a fleet, several of the breaking changes need read-first attention before pulling the update.

### 🔬 Details (Phân)
The trigger-ID UI is the change the automations editor has been waiting for. A new "Triggered by" condition reads the current automation's triggers, lets the author pick one by name, and assigns the underlying ID automatically; existing hand-written YAML IDs continue to work. The editor flags conditions that point to triggers that no longer exist and warns on duplicate IDs with a one-click Fix action, which closes off the most common silent-failure mode of trigger-ID conditions. The vector map change is more consequential than it looks: the browser used to request raster tiles directly from the tile server for every pan, which both leaked a user's lat/long to that server and failed if the Home Assistant instance was off the public internet. The new Map tiles integration caches tiles through the Home Assistant instance itself, so the browser only talks to the local instance; older devices automatically fall back to the raster map. The Modbus panel enumerates every configured Modbus connection, the devices behind it and the integrations consuming it, which is the discovery piece Modbus has needed since it stopped being just an inverter protocol and started showing up under solar, HVAC and meter integrations.

The AI page gets a Model Context Protocol server card: toggle it on and copy the exposed URLs into an MCP-capable client, which brings Home Assistant into the same bucket of local MCP endpoints users are already running for personal AI setups. The profile page is now split into Appearance, Localization, This browser / This mobile app and Security sections, and every user — not just admins — can edit their own name and avatar through an Edit profile button. Fifteen new integrations ship this month: Axle Energy, Bitvis Power Hub, Gree Infrared, INDI Allsky, KACO Modbus, my-PV, OSRAM Infrared, Persang Infrared, SolarEdge Modbus, Sunsynk, Theben Conexa Smart Meter Gateway, Threema, Vitesy, Willow and Zonneplan — a lean energy-heavy slate that fits the European market the project has been expanding into.

The breaking changes are concentrated enough to list before upgrade. The legacy authentication provider mode is gone and usernames are normalised, which can surface case-mismatched duplicates in older installs. MQTT `publish` and `dump` and Synology DSM reboot and shutdown now require an administrator account when invoked by a non-admin user. Linode and Tank Utility integrations are disabled this release. Telegram `download_file` now requires `directory_path` to be in `allowlist_external_dirs`, which will silently break any automation that writes outside those directories. UpCloud polls every sixty seconds unconditionally, so interval overrides now mean more API calls, not fewer. Sofar inverters without an energy meter stop producing six energy sensors. Proxmox VE uptime sensors return a start timestamp instead of elapsed seconds, which breaks any template that assumed the old units. The Xbox Game Pass binary sensor is removed outright, and several easyEnergy and EnergyZero sensors are renamed and no longer use "h" as a unit — a template layer refresh is in order.

### 🎯 Takeaway (Hợp)
Pull 2026.10 on a test instance before rolling it to a fleet: the trigger-ID UI and the vector map are quality-of-life wins that compound, but the Telegram allowlist, the MQTT and Synology admin requirement, and the Proxmox uptime unit change will each break at least one automation in a non-trivial install. Về chiến lược, giữ nguyên script upgrade cũ nhưng chèn thêm bước kiểm tra `allowlist_external_dirs`, template unit "h" của EnergyZero/easyEnergy và chủ sở hữu account của mọi script dùng MQTT `publish` trước khi production upgrade.

## 3. Databricks Apps On-Behalf-Of-User Authorization Reaches GA With Scoped API Permissions

| Field | Value |
|---|---|
| 📅 Date | 07/10/2026 |
| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `databricks-apps` · `on-behalf-of-user` · `oauth-scopes` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
Aakrati Talati, Cynthya Peranandam, Tushar Madan, Evan Pandya and Theo Fernandez announced on 7 October that on-behalf-of-user (OBO) authorization for Databricks Apps is now generally available. OBO lets a Databricks App act with the signed-in user's identity against Unity Catalog, Genie and Unity Gateway, so Unity Catalog's row filters, column masks and table grants apply to each request without the app re-implementing them. The service principal pattern still exists for app-owned work such as reading shared configuration or writing metrics; the change is that user-scoped reads can now be routed through the user's own token rather than an over-privileged app identity.

### 🔬 Details (Phân)
The surface is a small set of OAuth scopes rather than a new API. The recommended read scope is `sql:restricted-query`, which is deliberately narrower than the broader `sql` scope the article contrasts it with. Scopes `genie` and `ai-gateway` cover Genie and Unity Gateway calls respectively. The article advises against requesting `files`, `model-serving` or `vector-search` unless an app actually uses them — a least-privilege nudge that matters because, once a user consents, those scopes travel with every request. Configuration is done either in the Databricks UI or in a Declarative Automation Bundle; users are prompted to consent on first access. The runtime wiring is straightforward: Databricks forwards the user's token in the `x-forwarded-access-token` header, and the app hands it to the Databricks SQL Connector via its `access_token` parameter. The post is explicit that the token is short-lived and must be read per request and never stored.

Governance uses a two-level allowlist. The workspace allowlist, under Settings → Development → Apps, is the admin's scope ceiling for every app in that workspace — the default is all supported APIs, and admins can either narrow it to a selected list or set it to None. Account admins can add scopes outside a workspace's allowlist. When a scope is removed from the allowlist after an app is already using it, the running app keeps serving traffic but cannot be started, deployed or updated until the scope is removed from its manifest — a soft-fail path that keeps a tightening change from bringing production down but still forces the fix on the next deploy. The example app in the article uses Flask and the Databricks SQL Connector for Python with functions named `query_as_user` and `require_user_token`; the full code is linked rather than inlined.

The migration implications are mostly discipline, not refactor. Keep app-owned and user-owned clients separate in code — the app's service principal is still the right identity for metrics, cache priming and shared config. Fail closed when the forwarded token is missing rather than quietly falling back to the service principal, which is the specific regression the post warns about most pointedly because it defeats OBO's whole point. Create the user-scoped client inside request-time handlers for agents, not at process startup, since otherwise all users share the first request's token. And retest end-to-end user access after any Unity Catalog policy change, because row filters and column masks now reach into app paths they used to bypass.

### 🎯 Takeaway (Hợp)
If you have a Databricks App that reads tables on behalf of users through a service principal, the GA badge removes the preview-only excuse for not fixing it — change the SQL client wiring to use `x-forwarded-access-token`, request the narrowest scope set your handlers actually need, and add a startup self-check that fails if the token header is absent. Về mặt vận hành, nhớ phân biệt rõ "app owns" vs "user owns" trong code, và xem workspace allowlist như một dạng policy chứ không phải default.

### 💡 Example
```python
# Databricks Apps on-behalf-of-user wiring (GA 07/10/2026).
# Request-time, not startup; fail closed when the token is missing.

from flask import Flask, request, g, abort
from databricks import sql

app = Flask(__name__)
WORKSPACE_HOST = "example-workspace.cloud.databricks.com"
WAREHOUSE_PATH = "/sql/1.0/warehouses/abc123"

def require_user_token() -> str:
    tok = request.headers.get("x-forwarded-access-token")
    if not tok:
        abort(401, "missing on-behalf-of-user token")
    return tok

@app.before_request
def bind_user_token() -> None:
    g.user_tok = require_user_token()

@app.get("/kpi/<cost_center>")
def kpi(cost_center: str):
    with sql.connect(
        server_hostname=WORKSPACE_HOST,
        http_path=WAREHOUSE_PATH,
        access_token=g.user_tok,          # scoped sql:restricted-query
    ) as con, con.cursor() as cur:
        cur.execute(
            "SELECT SUM(amount) FROM finance.gl.actuals WHERE cc = %s",
            [cost_center],
        )
        return {"actuals": cur.fetchone()[0]}
```

## 4. DuckDB Publishes a Pattern for Catalog Files That Hold Views Over Remote Parquet, Not Data

| Field | Value |
|---|---|
| 📅 Date | 07/10/2026 |
| 🏷️ Topic | Tutorial |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `duckdb` · `httpfs` · `semantic-layer` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
The DuckDB team published "A DuckDB Database with No Data in It" on 7 October, documenting a pattern where a `.duckdb` file holds nothing but `CREATE VIEW` definitions that point at remote Parquet files over HTTPS or S3. The authors note that a catalog of this shape stays "a few hundred kilobytes" regardless of how much data the views describe, because the data never lives inside the file. The result is a sharable, versionable semantic layer whose distribution unit is a URL to a tiny file, with consumers running `ATTACH ... (READ_ONLY)` to use it exactly as if the tables were local.

### 🔬 Details (Phân)
The mechanics are built on three ingredients DuckDB already shipped. The `httpfs` extension — installed once with `INSTALL httpfs;` — gives DuckDB read access to Parquet files over HTTPS and S3. A view can wrap `read_parquet(...)` with a glob (for example, one file per year) or project the raw columns with aliases and `* EXCLUDE (station)` so a renamed source column keeps the old name downstream. Consumers attach the catalog with `ATTACH 'https://example.com/rail_catalog.duckdb' AS rail (READ_ONLY);` and query it as `rail.services`; the post benchmarks against a 380,959-row train services Parquet file to show the pattern working end to end. The crucial property is that `CREATE OR REPLACE VIEW` can swap the underlying `read_parquet()` target without changing a column's name or type, so the publisher can repartition, move or re-materialise the data lake and consumers' queries keep working.

The pattern lands in the space between "ship a .parquet URL" and "stand up a REST catalog". Shipping a Parquet URL leaves naming, column selection and partition logic in every consumer's query; standing up a REST catalog is the right answer for multi-tenant governance but a heavy lift for a small team or a public dataset. A view-only `.duckdb` file sits in the middle: it is a single artefact that encodes names, projections and joins, costs nothing to host (any static file server will do) and version-controls cleanly because it is bytes-stable. The authors are honest about the limits — consumers need network access to both the catalog file and every referenced Parquet source, HTTPS and S3 attachments are read-only so updating views means editing a local copy and re-uploading, and performance tracks the network path to the backing files rather than the catalog's local disk.

The ecosystem reading is quietly interesting. For a working data team the pattern is the lightest-weight way to publish a semantic layer over an existing lake without introducing a catalog service, and for an open-data publisher it is the lightest-weight way to publish a dataset with named, versioned views instead of a bare file dump. It does not replace Iceberg, Delta or Hudi, but it is a useful intermediate step for projects whose data is already in Parquet and whose consumer surface is DuckDB-shaped — which, since DuckDB is embedded in a growing set of client tools, now includes a lot of projects that did not look like candidates a year ago.

### 🎯 Takeaway (Hợp)
If you already publish Parquet to a static URL and your downstream consumers run DuckDB — in a notebook, a web app, or any WASM-embedded client — build the view catalog once, host the few-hundred-KB file next to the data, and hand out the catalog URL instead of a list of file paths. Về mặt vận hành, giữ catalog file trong git để có đổi tên cột và glob mới ở commit nào; consumer chỉ cần cập nhật URL hoặc kéo lại file, không phải sửa query.

### 💡 Example
```sql
-- "View-only" DuckDB catalog pattern (DuckDB blog, 07/10/2026).
-- Catalog file holds no data, only CREATE VIEW over remote Parquet.

-- PUBLISHER: build the catalog once, then upload rail_catalog.duckdb
INSTALL httpfs;
LOAD    httpfs;

CREATE OR REPLACE VIEW services AS
SELECT * EXCLUDE (station) RENAME (stop AS station)
FROM read_parquet(
  's3://open-rail/trains/year=*/services.parquet',
  hive_partitioning = true
);

-- CONSUMER: attach the catalog read-only and query views as tables.
ATTACH 'https://data.example.com/rail_catalog.duckdb'
AS rail (READ_ONLY);

SELECT station, count(*) AS calls
FROM   rail.services
GROUP  BY station
ORDER  BY calls DESC
LIMIT  3;
```

## 5. ESP-Hosted Turns an ESP32-C6 Into a 40–50 Mbps Wi-Fi and Bluetooth Co-processor for the Raspberry Pi

| Field | Value |
|---|---|
| 📅 Date | 07/10/2026 |
| 🏷️ Topic | Tutorial |
| 🌐 Domain | IoT |
| 🔑 Keywords | `esp-hosted` · `sdio` · `raspberry-pi` |
| ⚡ Impact | Medium |

### 🔭 Overview (Tổng)
Arya Voronova wrote on Hackaday on 7 October about using Espressif's `esp-hosted` stack to drive an ESP32 as a wireless co-processor for a Linux single-board computer, in this case a Raspberry Pi. The project splits into three repos — the parent `esp-hosted`, the microcontroller-side `esp-hosted-mcu` (formerly `esp-hosted-fg`) and the Linux-side `esp-hosted-linux` (formerly `esp-hosted-ng`) — and exposes the ESP32's Wi-Fi and Bluetooth to the host over SDIO or SPI. Supported chips span the ESP32-S2, S3, C2, C3, C5 and C6/C61; the article's build uses an ESP32-C6 and recommends the C5 for new designs because of its 5 GHz support.

### 🔬 Details (Phân)
The physical interface is where the write-up is most useful. SDIO is the recommended path for speed, carrying CMD, CLK and either D0–D3 or D0 alone, with Bluetooth passed through on the same bus rather than tying up a UART; the Pi's UART console comes back once the Bluetooth overlay is disabled. The signal integrity caveats are concrete and easy to miss on a quick breadboard build: series and pull-up resistors on the SDIO lines per the ESP-Hosted docs, trace length matched to within about 1 mm, kept short, with a continuous ground return. The EN pin is optional; passing `resetpin=-1` to the driver skips EN control, which simplifies wiring for prototypes. Power draw is 300–400 mA at 3.3 V, so the host needs an input rail that can carry the Pi plus the ESP32 under worst-case Wi-Fi transmit, and the article suggests a 4-pin JST-SH connector with a QWIIC-like pinout for the flashing header.

The software path has two sharp edges worth flagging. Firmware and driver must come from the same `esp-hosted` git commit — a mismatched pair makes the driver refuse to load, which is the first bug most people hit. The `rpi_init.sh` build script defaults to `make -j8`, which exhausts memory on Pi models with 512 MB or less; the article recommends dropping to `-j2` or `-j1`, and Pi Zero users should cross-compile the firmware on a desktop because `cmake` can lock up the Zero. Installation is standard out-of-tree module work: `sudo cp esp_sdio.ko /lib/modules/$(uname -r)/kernel/drivers`, `sudo depmod -a`, `sudo modprobe esp_sdio`, and an entry in `/etc/modules` to autoload. The `config.txt` edits remap the SDIO pins and disable the Pi's built-in Bluetooth so the ESP32's stack can own that path, and the article suggests `dmesg -Hw` as the live debugging surface. The `poll_once=off` SDIO overlay parameter is called out as probably unnecessary and a source of `dmesg` noise.

The performance headline is honest: about 40–50 Mbps throughput at the default SDIO frequency, with higher speeds available by tuning per the porting guide. No latency figures are given, which is the number a time-sensitive application would care about more than raw bandwidth; the ecosystem context the article points at — including prior Hackaday coverage from 2024 and the 38C3 2024 talk on ESP32 Wi-Fi blob reverse engineering — explains why some teams prefer an ESP-based path to the proprietary blobs that ship with mainstream Wi-Fi silicon. The caveat is that this is a tutorial, not a production reference design; a shipping product would want enclosure thermal validation, EMC pre-compliance for the SDIO bus and a wake-up strategy that neither repo documents end to end yet.

### 🎯 Takeaway (Hợp)
If you are building a custom SBC and want to avoid shipping a closed Wi-Fi firmware blob — or if you already have an ESP32 on your board and want to expose its radios to a Linux host rather than running a second RTOS — `esp-hosted` is now the right starting point. Về mặt kỹ thuật, lock firmware và driver vào cùng một git commit từ ngày đầu, chọn SDIO 4-bit cho throughput tốt nhất, chuẩn hoá wiring theo mẫu trong porting guide, và chấp nhận trần ~50 Mbps cho đến khi đủ thời gian tune.

### 💡 Example
```bash
# Minimal Raspberry Pi bring-up of ESP32-C6 as a wireless co-processor
# over SDIO using esp-hosted (Hackaday, 07/10/2026).

# 1) Pi: remap SDIO pins and disable the built-in Bluetooth.
sudo tee -a /boot/firmware/config.txt <<'EOF'
dtoverlay=sdio,bus_width=4
dtoverlay=disable-bt
EOF

# 2) Clone + build driver from the SAME commit as the firmware.
git clone https://github.com/espressif/esp-hosted-linux.git
cd esp-hosted-linux/host/linux/host_driver/esp32

# On a 512 MB Pi, drop parallelism before the kernel OOMs.
sed -i 's/make -j8/make -j2/' ../../../../rpi_init.sh
../../../../rpi_init.sh

# 3) Install the module and load it (resetpin=-1 skips EN wiring).
sudo cp esp_sdio.ko /lib/modules/$(uname -r)/kernel/drivers/
sudo depmod -a
sudo modprobe esp_sdio resetpin=-1
echo esp_sdio | sudo tee -a /etc/modules

# 4) Watch the handshake. Expect ~40-50 Mbps at default SDIO clock.
dmesg -Hw | grep -i esp
```
