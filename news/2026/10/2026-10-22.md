## 1. DuckDB 2.0.0 LTS "Cinnamon Teal" Ships Quack Client-Server, VARIANT Type and a New PEG Parser

### 🔭 Overview (Tổng)
On 21 October 2026 the DuckDB team announced DuckDB 2.0.0 LTS, codenamed "Cinnamon Teal", the project's largest feature release so far and the next long-term-support line, supported until at least October 2027. The post describes close to 20,000 commits since 1.5 and ships four changes that reshape how DuckDB is deployed: a client-server mode built on the new Quack protocol, a shredded VARIANT type for semi-structured data, asynchronous I/O for Parquet/CSV/native storage, and a PEG-based SQL parser that replaces the old YACC/Bison LALR(1) parser as the default. The release also keeps 1.4 LTS supported until late November 2026 and extends 1.5 to March 2027, so teams have a defined window to migrate.

### 🔬 Details (Phân)
Client-server is the headline shift. The `quack` extension exposes `CALL quack_serve(...)` and the CLI gains `-serve` and `-connect` flags; by default the server listens only on `localhost`. A new `CONNECT` statement attaches and switches to a remote database in one step and works against PostgreSQL and MySQL as well as Quack, which keeps the familiar embedded workflow available while adding a persistent service process. On the storage side, asynchronous I/O keeps multiple requests in flight for Parquet, CSV and the native format — directly aimed at remote reads against S3 and compatible object stores. The VARIANT type ships with `variant_type`, `variant_keys` and related functions, and the engine "shreds" semi-structured data into columnar form when a common structure is detected, with shredded Parquet reading and writing. SQL surface additions include `CREATE TRIGGER` with BEFORE/AFTER, row and statement level and transition tables, data-modifying CTEs, `NEAREST` joins, nested schemas, JSON mutation functions, `FETCH FIRST`, `UNNEST` in `GROUP BY`, and well-defined `MERGE`/`UPDATE ... FROM` semantics when multiple rows match the target.

The post positions 2.0 against the way DuckDB is already used inside pipelines. Agent mode is a new CLI default that detects coding agents and switches to compact Markdown output, reports truncation, stops runaway queries and emits errors as JSON; a TPC-H experiment in the post shows the model-visible output falling by 59%. Core extensions bundled with the release — DuckLake 1.1, additional Iceberg REST catalog options and Delta `CREATE TABLE` — point to the same direction, keeping DuckDB a first-class reader against external catalogs rather than a silo. A new C API v2 and extension repositories let organisations publish signed internal extensions pinned by RSA keys, though the post flags the syntax as still subject to change.

The migration cost is non-trivial. Database files written by 2.0 cannot be opened by older versions, so the recommended path is a shadow system that double-writes until confidence is built; 2.0 can still read and write 1.x files, which stay readable by their original engine. The build toolchain now requires a C++17 compiler and Clang is the default for release builds on Linux and macOS. Single-arrow lambdas are disabled by default and the `lambda_syntax` flag plus the single-arrow form are scheduled for removal in 2.1, so projects should move to the Python-style `lambda x: ...` form now. Amalgamation builds and macOS x86_64 community extension builds are deprecated with removal planned in 2.1 as well. ICU has been removed from core: timezones, calendars and collations now live in the `icu` extension, with IANA data compressed to roughly 45 kB.

### 🎯 Takeaway (Hợp)
If you ship DuckDB inside an analyst or ETL product, read the breaking-changes section before upgrading: the shadow-write pattern against the new storage format and the lambda syntax deadline for 2.1 are the two cheap-to-prepare, expensive-to-forget items. Về kiến trúc, Quack cùng VARIANT type và async I/O đưa DuckDB rời khỏi vị trí "chỉ embedded" — đáng dành một spike để đo lợi ích khi gom nhiều Python workers về một process DuckDB chung thay vì mỗi worker mở file riêng. Expect the first patch release in November, per the post.

## 3. Databricks Contributes UNREGISTER to the Iceberg REST Catalog Spec and Opens Private Preview in Unity Catalog

### 🔭 Overview (Tổng)
Elizabeth Bowman's 19 October 2026 Databricks post, "What makes a catalog open?", pins down three criteria for an open catalog — storage you own, advanced features that work on tables in that storage, and the freedom to move a table between catalogs without copying data — and reports two concrete steps toward the third criterion. Unity Catalog is now, per the post, the first catalog to support both REGISTER and UNREGISTER from the Apache Iceberg REST catalog spec, with Databricks contributing UNREGISTER to the spec itself. Both operations are in Private Preview and require contacting a Databricks account team to enable.

### 🔬 Details (Phân)
The mechanics are straightforward. `REGISTER` attaches a table's existing metadata location to a new catalog, creating the name-to-metadata binding without moving files, and `UNREGISTER` removes a table from Unity Catalog and returns the latest metadata location so the next catalog can pick up commits where this one left off. Foreign Iceberg tables remain read-only in Databricks because a different catalog owns the commits, and a planned `SET MANAGED IN PLACE` is on the roadmap to convert foreign or external tables into Unity Catalog managed tables while keeping the storage path untouched. The spec contribution matters because without a symmetric UNREGISTER, "openness" is one-directional — any catalog can let data in, but only some can let it out — and that is what the handover between vendors has lacked.

The post places this on the same ladder as other recent Unity Catalog work: Predictive Optimization running `OPTIMIZE`, `VACUUM` and statistics collection on managed Delta and Iceberg tables in customer-owned storage, time-travel and drop-and-restore windows of up to 30 days against the user's own object store, and the claim that 99% of Unity Catalog managed tables sit in customer-owned storage rather than provider storage. A Zepto quote cites over USD 1 million per year in storage cost savings from the automatic optimisations. Readers should treat the inter-vendor comparisons in the post as vendor claims — they are useful as a map of the pitch, not as evidence — but the UNREGISTER contribution is verifiable in the Iceberg REST spec itself, and the preview availability is a concrete gate on exercising the capability today.

### 🎯 Takeaway (Hợp)
If your team runs Unity Catalog alongside another Iceberg REST catalog, request the Private Preview and plan a dry run of a REGISTER/UNREGISTER round-trip against a non-production table before you need it in anger. Về mặt chiến lược, có UNREGISTER làm chuẩn chung giảm chi phí "bị khoá" trong một catalog, nên đây là tính năng đáng đưa vào vendor-risk checklist dù hiện mới ở Private Preview. Watch for the `SET MANAGED IN PLACE` roadmap item — that is the step that lets a foreign table become managed without data movement.

### 💡 Example
```sql
-- Unity Catalog + Iceberg REST round-trip (REGISTER / UNREGISTER)
-- as described in the 19/10/2026 Databricks post. Both operations
-- are Private Preview; enablement is via your Databricks account team.

-- 1) Bring an Iceberg table managed elsewhere into Unity Catalog by
--    pointing at its current metadata location.
CALL system.catalog.register_iceberg_table(
  target_name     => 'main.lake.orders',
  metadata_location => 's3://acme-lakehouse/orders/metadata/v12345.metadata.json'
);

-- 2) Hand ownership back out. UNREGISTER returns the final metadata
--    location so the next catalog can keep committing.
CALL system.catalog.unregister_iceberg_table(
  table_name => 'main.lake.orders'
);
-- Returns: s3://acme-lakehouse/orders/metadata/v12346.metadata.json
```

### 🔭 Overview (Tổng)
Hackaday's Zoe Skyforest wrote up a desktop internet radio build on 21 October 2026 that uses an ESP32-S3 as the host and a conventional small-electronics bill of materials — OLED display, rotary encoder for station selection and volume, I2S audio amplifier for output. The piece is interesting less for novelty than for being a clean reference pattern: a Wi-Fi-connected, screenful embedded appliance that an engineer can clone in a weekend without any specialist chip, and that stresses most of the ESP32-S3's practical features at once.

### 🔬 Details (Phân)
The hardware chain is Wi-Fi radio and TCP streaming on the ESP32-S3, decoding of MP3 or AAC from the station URL, I2S output into a Class-D amplifier, and user interface over a monochrome I²C OLED with a rotary encoder for input. The build pattern makes two technical points worth noting. First, the ESP32-S3 has enough SRAM and PSRAM headroom to run both the networking stack and an audio decoder without external memory beyond the module's own PSRAM, which is why the design can skip a dedicated decoder IC that older ESP8266-era radios needed. Second, the use of I2S rather than DAC-plus-amp keeps clocking clean enough for audible-quality streams without a crystal oscillator PCB redesign.

The pattern is also useful as a template for other always-on IoT appliances — a weather clock, a smart-home status display, a small kiosk — because almost every subsystem (Wi-Fi, screen, input device, audio or haptic feedback) is already wired up and only the "what does it do" layer changes. A reader can expect to spend most of the time on robustness: handling station URL redirects, surviving Wi-Fi reconnects, debouncing the encoder reliably, and gracefully failing when audio buffers underrun. None of that is novel in isolation, but having a known-good reference wiring makes those issues the next step rather than the first.

### 🎯 Takeaway (Hợp)
If you have a drawer of ESP32-S3 modules, this is a weekend reference project that doubles as a template for later always-on dashboards and clocks. Lưu lại pattern "ESP32-S3 + OLED + rotary encoder + I2S" như một bộ scaffolding chuẩn, sau này đổi payload là xong. Just plan time for the quiet-day work: reconnect logic, buffer underruns and encoder debounce decide whether it feels like a product or a demo.

### 💡 Example

```c
// Illustrative audio-task scaffolding for an ESP32-S3 internet radio.
// Pattern described in Hackaday's 21/10/2026 build writeup.
#include "driver/i2s_std.h"

static i2s_chan_handle_t tx_handle;

void audio_task(void *arg) {
  int16_t buf[1024];
  while (1) {
    int n = stream_decode_fill(buf, sizeof(buf)); // MP3/AAC decode
    if (n > 0) {
      size_t written;
      i2s_channel_write(tx_handle, buf, n, &written, portMAX_DELAY);
    } else {
      ui_show_underrun();
      stream_reconnect();
    }
  }
}
```
