## 1. BigQuery ObjectRef Reaches GA, Bringing Multimodal Files Into SQL With Versioned GCS References

### 🔭 Overview (Tổng)
On 21 October 2026, Gaurav Soni's Google Cloud blog post announced the general availability of BigQuery ObjectRef, a built-in STRUCT type that lets a standard BigQuery row point at an object in Cloud Storage without copying its bytes. The release moves the "unstructured data in SQL" workflow out of preview on all BigQuery editions and on-demand tiers, and the post pairs it with the AI function family (`AI.CLASSIFY`, `AI.IF`, `AI.GENERATE`, `AI.AGG`) that uses ObjectRef as its input. For a data engineer who has been bolting on an extra pipeline every time an image or audio file enters the warehouse, this is a direct swap: a reference lives next to the relational columns, versioned by GCS generation number, and the same IAM policies that gate the row gate the file.

### 🔬 Details (Phân)
The STRUCT itself is small — `uri`, `authorizer`, `version`, and a `details` JSON that carries GCS metadata — but the surrounding affordances are what make it usable. `OBJ.MAKE_REF(uri)` creates a reference from a raw string, with format auto-detection, so an existing table of string URIs can be upgraded in place. ObjectRefs can now be stored in arrays, which lights up multi-file reasoning: the post's phishing-detection example passes `[OBJ.MAKE_REF(trusted_ui_uri), OBJ.MAKE_REF(suspect_ui_uri)]` to `AI.GENERATE` with a typed `output_schema`, so a single call compares two screenshots and returns a structured boolean plus a reason string. GA also adds End User Credentials, which lets ad-hoc analysts query ObjectRefs under their own IAM identity instead of a shared service account connection, while production pipelines are expected to stay on explicit BigQuery connections. Metadata sources can be object tables, Cloud Storage insights datasets, or plain string columns, and ObjectRefs can be passed into Python UDFs so libraries like OpenCV run on the data in place.

Positioning-wise, this is the GCP answer to the Snowflake FILE/`SNOWFLAKE.AI_CLASSIFY` surface and the Databricks Unity Catalog Volumes + `ai_classify`/`ai_query` surface — a warehouse-native way to keep governance uniform across structured columns and the files they describe, without a second copy and without exporting the data to a notebook. The versioning story matters here: because the ObjectRef carries a GCS generation number, a query will see the exact file version that existed when the row was written, which is the piece raw string URIs cannot guarantee. The release notes that AI functions default to Optimized Mode, which reduces token consumption; the post does not publish per-unit rates and defers to the pricing documentation, so cost estimates still require a dry run against a representative shard.

Migration cost is low on the schema side — a nullable ObjectRef column plus a backfill of `OBJ.MAKE_REF(uri)` on existing URI strings — but higher on the policy side. Teams that run two IAM stories today (one for the warehouse, one for the bucket) will need to collapse them, because the "unified governance" claim only holds if the authorizer on the ObjectRef is actually honoured in both places. The documented tutorial uses synthetic image data and product categories, which is the right place to start to measure token spend before running `AI.GENERATE` across an existing media library.

### 🎯 Takeaway (Hợp)
If your BigQuery warehouse already indexes GCS by URI strings, pilot the backfill into ObjectRef on a non-production table and benchmark one `AI.CLASSIFY` call per thousand rows to size the token budget before pointing it at the full fleet. Trước khi ký cost sheet, tracker token của Optimized Mode cần được audit cùng team FinOps vì AI function tính tiền tách khỏi slot. Watch for ObjectRef support in External Tables and in Dataform — those are the two surfaces where the GCS-first teams will feel the gap first.

```sql
SELECT
  customer_id,
  call_date,
  OBJ.MAKE_REF(audio_uri) AS ref,
  AI.CLASSIFY(
    OBJ.MAKE_REF(audio_uri),
    ["Lost or stolen card", "Declined card payment",
     "Activate my card", "Order physical card",
     "Cancel transfer", "Password or pin forgotten",
     "Virtual card not working", "Card swallowed by ATM",
     "Balance not updated after bank transfer",
     "Transfer fee charged"]
  ) AS customer_issue_type
FROM call_center.raw_call_logs;
```

The post is paired with a Databricks Research write-up on MemCurrent, the design the product implements, so the release has two faces — a product for engineers to call from Agent Bricks and a published architecture that gives platform teams a model to compare against their own agent stack. The claim at the top of the post is unusual for a memory feature: in internal benchmarks, agents with memory passed about three times as many enterprise tasks and used 31% fewer tokens, and one example dropped a follow-up question from 11 tool calls over nearly six minutes to 2 tool calls in 41 seconds.

### 🔬 Details (Phân)
Three components make up the surface. Managed sessions store an ordered conversation history — messages, tool calls and results — in each framework's native format, which keeps the raw record addressable without a translation layer. Managed memory holds profile data, preferences, domain knowledge and workflows, with an index the agent loads at session start and queries during a session through hybrid keyword and semantic search. Memory pipelines run in the background, on demand or on a schedule, to extract durable facts, remove duplicates, and replace facts that newer conversations contradict. The two-layer split — raw event record below, continuously distilled store above — is the MemCurrent idea in production form, and the research post describes the pipeline as the piece that converts logged conversations into a store the agent can read quickly next time.

Control stays with the customer. Sessions and memories live in the customer's Lakebase project, developers can read, export and delete per-user entries, and pipeline instructions let a team say what should be retained and what should be dropped. The post names Unity Gateway for models, the Agent Bricks CLI for deployment, and the existing Agent Bricks tracing and evaluation plumbing as the integration points; it does not mention Unity Catalog directly, which is a gap worth flagging for teams that expect their governance posture to carry across. API surfaces, pricing, limits and a GA timeline are not stated — the post links to a quickstart, an existing-agent tutorial, and the stateful-agents documentation for the operational detail.

For teams already running agents in production, the useful comparison is not against "no memory" but against a hand-rolled memory layer. The internal 3× task-pass number is directional until replicated on an external benchmark, but the 31% token saving is the one most teams can verify quickly on their own traffic, because it only requires swapping the memory layer and holding everything else constant. Lakebase as the backing store matters for cost accounting too — this is Postgres-compatible, so a team that already operates it will inherit the backup, PITR and read-replica story without adding a new system of record.

### 🎯 Takeaway (Hợp)

## 5. A PCB-Only Open-Source Linear Capacitive Encoder Reads to 40 µm on an STM32

### 🔭 Overview (Tổng)
On 22 October 2026 Hackaday's Zoe Skyforest wrote up `open-linear-scale`, a PCB-only linear position encoder built from two boards and an STM32, that reaches 40 µm accuracy — the same measurement technique that sits inside cheap digital calipers, but with the hardware and firmware exposed instead of hidden behind a sealed plastic shell. The project is interesting less because capacitive sensing is new and more because the design is small enough to drop into a hobby machine (3D printer axis, pen plotter, small lathe) without buying a commercial scale, and because the source files are published and reusable.

### 🔬 Details (Phân)
The sensor PCB carries eight transmitting antennas etched into the copper and one larger receiving antenna above them. The reflector PCB sits opposite, fixed. As the sensor moves, the transmitters pulse a pattern, the pulses bounce off the reflector, and the capacitive coupling — modulated by position — changes the pulse strength reaching the receiver. An STM32 reads the received pulses and converts them into a displacement number. The project page lists "40µm/16thou" in its title; the Hackaday post explains the 40 µm figure as the achieved accuracy and leaves the 16-thou unit as the imperial equivalent for readers who work in that system. The reported accuracy puts the design in the same order of magnitude as inexpensive calipers but above hobby-grade optical encoder modules at a similar bill of materials.

The novelty here is in the openness, not in the physics. Calipers already use this technique, and the Hackaday post links to a separate teardown of a cheap digital caliper that explains the coupling mechanism. What `open-linear-scale` adds is a reproducible PCB layout, an STM32 firmware pass that converts the pulse readings into position, and a GitHub repository — meaning the design can be forked, lengthened for larger axes, or reshaped around a specific machine without reverse engineering a sealed sensor. The project page lives on Hackaday.io and the source files are on GitHub, with the article pointing readers there for license and build instructions, which the news item itself does not list.

As a reference pattern, the useful lesson is for anyone building a motion stage or a cost-sensitive gantry. The absence of a magnet, a lead screw count-based estimate, or an optical linear encoder removes several meaningful failure modes (dust on optical scales, slip on friction wheels, drift on inductive sensors), and the two-PCB packaging keeps the mechanical assembly thin. The limits are the same limits that affect any capacitive sensor: sensitivity to environmental humidity, proximity of grounded objects, and PCB tolerance stacking across the pulse pattern.

### 🎯 Takeaway (Hợp)
If you are building a small-footprint motion stage or a cost-controlled hobby CNC, fork `open-linear-scale`, print the PCBs on a cheap fab run, and benchmark the 40 µm accuracy claim against the exact axis length you need before you design the mechanics around it. Với các dự án điều khiển sản xuất nhỏ, pattern "PCB antenna array + reflector + STM32" là một build block hợp lý để tích hợp vào custom hardware mà không phải mua scale thương mại. Treat environmental conditioning as part of the test — humidity and nearby grounded metal will dominate the error budget once the core design is right.

### 💡 Example
```c
// Illustrative STM32 reading loop for a capacitive linear encoder.
// Scaffolding only, written from the 22/10/2026 Hackaday writeup;
// see the open-linear-scale repository for the actual firmware.
#include "stm32xxxx_hal.h"

static int32_t position_um;

void encoder_tick(void) {
  uint16_t rx[8];
  for (int tx = 0; tx < 8; tx++) {
    pulse_transmit(tx);           // energise one TX antenna
    rx[tx] = adc_read_rx();       // read the single RX antenna
  }
  int32_t phase = decode_phase(rx);          // modulo one pitch
  position_um = unwrap_position(phase);      // across the full scale
}
```
