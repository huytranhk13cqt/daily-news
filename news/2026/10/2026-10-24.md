### 🔭 Overview (Tổng)
On 21 October 2026 the DuckDB team announced DuckDB 2.0.0, codenamed "Cinnamon Teal", the project's second long-term support line, supported until at least October 2027. The release is the first in which the on-disk format changes: a file written by 2.0 cannot be opened by any 1.x build, although 2.0 can still read and write 1.x files, which means the migration is one-way at the file level even if the engine remains backwards compatible on reads. Alongside the format change, 2.0 ships a new default SQL parser, a client-server protocol called Quack, asynchronous I/O for Parquet, CSV and the native format, a columnar VARIANT type, triggers, agent mode in the CLI, and a C API v2.

### 🔬 Details (Phân)
The parser swap is the detail most likely to catch an existing codebase. The PostgreSQL-derived YACC/Bison parser is replaced by a PEG grammar that accepts extensions adding SQL syntax and reports error locations more precisely; the team describes it as compatible with the old grammar apart from a listed exceptions table. The single-arrow lambda form is now disabled by default — code that reads `list_transform(xs, x -> x + 1)` must switch to `lambda x: x + 1` or opt back in with `SET lambda_syntax = 'enable_single_arrow';`, with both forms removed in 2.1. If the new parser rejects a dialect the application depends on, installing the `legacy_parser` extension and setting `enable_legacy_parser = true` restores the old behaviour as an escape hatch rather than a permanent setting.

Quack is the second surface change worth planning for. A session can call `CALL quack_serve(token = 'my_token');` to expose its databases, and a remote client runs `ATTACH 'quack:localhost' AS qk (TOKEN 'my_token'); CONNECT qk;` to switch into them; the CLI exposes the same functionality through `-serve` and `-connect` flags. The protocol is implemented as the `quack` extension rather than being wired into the core engine, so an operator opts in explicitly. Asynchronous I/O sits below this: the team cites network throughput charts in the companion post but does not publish a single speedup figure, so a concrete benchmark on the target object store is still the right way to size the gain. VARIANT stores semi-structured data columnar-style with automatic shredding and is paired with a `variant_*` function family; triggers and C API v2 round out the SQL-side additions, and the agent mode in the CLI reduced the volume of model-read output by 59% in the team's own TPC-H experiments.

Migration cost is low on the engine side and higher on the operations side. A C++17 compiler is now required, Clang is the default for release builds on Linux and macOS, ICU moves out of core into the `icu` extension, the amalgamation build is deprecated, and macOS x86_64 is on a stated end-of-life path with support dropped in 2.1. The team recommends keeping production on 1.x until a first patch planned for November, and running a shadow deployment of 2.0 against representative workloads before the switch; the migration guide at `duckdb.org/docs/2.0/operations_manual/migration.html` lists the exact deprecation and compatibility items. Versions 1.4 and 1.5 are supported through November 2026 and March 2027 respectively, giving a two-track window.

### 🎯 Takeaway (Hợp)
If you run DuckDB in a server or ETL role, pin production to 1.5 until the November 2.0 patch and start a parallel 2.0 cluster now to profile asynchronous Parquet reads from your object store — that single number is the easiest way to decide whether the format break is worth it this quarter. Khi tận dụng Quack server mode, nhớ wrap token trong secret manager và không hard-code trong attach string, vì nó là bề mặt auth duy nhất của protocol này. Watch the lambda arrow deprecation closely: codebases that generate SQL at runtime will break silently without the compatibility shim, so grep for `->` in generated queries before cutting over.

### 🔭 Overview (Tổng)
On 23 October 2026 Lisa Cao and Sudhanva Huruli published a Databricks engineering post that measures Spark Declarative Pipelines (SDP) against procedural PySpark on an agent-authored workload: 22 data engineering tasks, each written twelve times against messy input datasets, for a total of 528 builds across the two approaches, all generated by Opus 4.8. The headline numbers are easy to read: SDP caught 55 of 264 builds at a pre-run dry-run before any cluster time was spent, cut total executor-seconds from 596 to 17, and shortened median lines of code from 131 to 64, at the cost of about 2.3x LLM tokens per build. The benchmark repository is published on GitHub, which is the piece that lets a reader verify these numbers rather than take them on trust.

### 🔬 Details (Phân)
The SDP execution model is the central lever. In SDP the author defines each dataset and the query that produces it; Spark decides execution order and materialises the result. Before any job runs, SDP performs a dry run that validates column references against the source dataset's schema, dataset dependencies against producers in the graph, and the completeness of the ordering, so an agent typo in a column name or a missing upstream table surfaces as an authoring error rather than a mid-run crash. In the benchmark, this dry-run gate stopped 55 of 264 declarative builds before output, while the procedural runs surfaced many of those same errors inside Spark at execution time, and the same gap drives the cluster-time delta: Spark spent 596 executor-seconds across 264 procedural builds against 17 across 264 declarative builds. The declarative approach is also more consistent in that 19 procedural builds used an in-memory row-by-row shortcut that would not survive production data volumes, versus zero declarative builds — a function of SDP's materialised-view decorator steering generation toward set-based code.

The caveat the post is honest about is silent errors. Both approaches shipped roughly a quarter of builds that produced wrong output without failing: 27.7% procedural versus 32.2% declarative, slightly worse on the declarative side. The dry-run only validates structure, not semantics, and a correctly typed join on the wrong keys will pass. Token cost moves the other way — about $0.26 per procedural build versus about $0.50 per declarative build at the authors' prices — because the agent writes more context when the structure is enforced. The authors frame this as a trade-off that scales favourably with data volume: a fixed up-front token premium against compute cost that grows with the size of each production run.

Positioning-wise the post sits with the recent "agent-as-author" wave at Databricks that already covers Agent Bricks and Agent Memory, but it is unusual in that it publishes a side-by-side benchmark instead of a single scenario, and in that it reports both wins and losses for its own system. Review workload drops with 51% fewer lines, which is a direct cost reduction for human reviewers. For teams that already stand up PySpark jobs through an agent — whether their own harness or a tool like Agent Bricks — the actionable detail is the materialised-view decorator pattern and the dry-run step: both can be adopted inside an existing project without a full rewrite, by moving the derived tables one at a time behind `@dp.materialized_view(...)`.

### 🎯 Takeaway (Hợp)
If your agent generates PySpark today, run the published benchmark against your own agent harness and compare the structural-error rate before accepting Databricks' numbers — the dry-run gate is replicable, so this is a measurement, not a vendor claim. Khi chuyển một bảng derived sang SDP, chọn bảng có schema source hay thay đổi để lợi ích dry-run nổi lên rõ nhất và bù lại chi phí token tăng. Pair SDP with explicit output-value tests even after adoption; the 32.2% silent-error figure is high enough that structural validation alone is not a review substitute.

### 🔭 Overview (Tổng)
On 23 October 2026 Mike Kershaw's Hackaday "This Week in Security" column highlighted a flaw in Broadcom WPS code — "the oldest vuln" — that is present on affected routers back to at least 2010 and allows a WiFi-adjacent attacker to open a root shell without the network password, without a completed WPS pairing, and without any route to the Internet. Broadcom's 2018 patch was incomplete, Broadcom is its own CVE Numbering Authority and declined to assign a CVE, and the eCos-based chipsets at the heart of the issue are unlikely to see a general fix. The researcher's estimate, cited by Kershaw, puts the vulnerable gateway population at over 1.5 million in Belgium alone — a usable floor for scoping the exposure in any country whose carriers deployed the same Broadcom reference designs.

### 🔬 Details (Phân)
Operationally the flaw is as bad as a WiFi-adjacent vulnerability can be, because the pre-authentication primitive is in the WPS implementation itself rather than in a service that WPS enables. An attacker in RF range sends the WPS probe exchange, the firmware falls into the bug, and the attacker gets a root shell on the gateway over the air; the carrier does not have to expose the device publicly, the owner does not have to know WPS is on, and the Internet does not have to be reachable. The chipsets are eCos-based, which means they do not have a modern Linux-style update story, and Broadcom's refusal to issue a CVE blocks the usual coordinated path through NVD and vendor advisories. Browsers and operating systems have no mitigation to apply, because the fault is not in a protocol stack above the WiFi driver — it is in the firmware under it.

The practical mitigation list is short. Where the gateway's web UI exposes a WPS toggle, disabling WPS removes the primitive, so this is the first thing to check in any audit; where the toggle is absent or disabled by firmware, the only safe path is to put the carrier-supplied gateway into bridge or passthrough mode and run WiFi through an access point that still receives updates. For enterprises operating fleets of consumer-grade gateways — small branches, retail sites, remote worker rigs — the ask is a once-off asset-inventory sweep of gateway chipsets and WPS states, followed by a vendor conversation with carriers that supply the hardware. Kershaw's column lands this on the same week as two CVSS 9.0 Linux kernel ksmbd bugs disclosed by mistake to the LKML (home NAS exposure), three NGINX CVSS 9.2 issues on worker processes (NGINX-based appliances and the Kubernetes Ingress Controller), the Trezor hardware wallet implant story, and the eMudhra CA key compromise that leaves embedded devices trusting bad intermediates until a firmware root-bundle update ships — so the broader IoT lesson is that this is a bad week for anything with a radio.

The eMudhra and Trezor items are the two most useful to pair with the Broadcom story in a team briefing. The eMudhra piece shows the long tail of embedded roots-of-trust: browsers blocked the compromised intermediates quickly, but non-browser devices that do not check revocation stay exposed until the root bundle on each device updates, which many IoT devices never do. The Trezor piece shows a different attack class — microcontrollers physically swapped in supply chain to generate predictable recovery phrases — but reinforces the same posture: an IoT device's threat model has to include the hardware's own origin, not just its network.

### 🎯 Takeaway (Hợp)
If your estate includes carrier-supplied gateways, inventory Broadcom chipsets and WPS states this week, and open a ticket with each carrier asking for either a confirmed patch path or an alternative device — the eCos reality means waiting out a vendor patch is not a strategy. Với các team quản lý fleet remote worker, chuyển gateway sang bridge mode và deploy AP có update cadence rõ ràng là cách duy nhất đảm bảo kiểm soát được bề mặt WPS này. Treat the eMudhra and ksmbd items as a parallel sweep: the IoT devices that fetch firmware or configuration over HTTPS, and the home NAS boxes with SMB on, deserve the same inventory pass.

### 🔭 Overview (Tổng)
On 23 October 2026 Espressif's He Xinlin published Chip Comparator Portable, a technical-evaluation web app that puts a single ESP chip's details, side-by-side differences against other chips, requirement-based filters, application scenarios and matching Espressif development boards onto one page. The post positions it alongside — not replacing — the existing ESP Product Selector, which handles part numbers, commercial status and lifecycle data; the Comparator is scoped specifically to the technical evaluation step that sits between "I need WiFi + BLE + a camera" and "here is the dev board I will prototype on". Coverage spans ESP8266 and the ESP32 S, C, H, P and E series, which includes most of the parts actively specified in new designs.

### 🔬 Details (Phân)
The tool is organised around five tabs. Single-chip details shows a Technical Reference view with a core capability summary, a specification matrix with per-feature explanations and notes, and links to official datasheets, so an engineer can lift a chip's actual numbers rather than approximations. Multi-chip comparison selects two or more chips and renders a side-by-side specification table with differences highlighted, exportable to Excel for inclusion in design review documents. Chip filtering narrows the catalogue by requirements: core and memory bands, wireless modes, digital/multimedia/analog peripherals, specific interfaces such as I2C and UART, and USB capability granularity down to HS versus FS — the kind of filter set that previously required reading several datasheets in parallel. Application Scenarios and Dev Board Selection tabs round out the flow by linking a chip choice to Espressif's own demos and showcases, then to official boards narrowed by display, voice, or vision function and by hardware conditions such as screen size and interface.

The engineering value for a developer is in two places. First, the explicit split between technical selection (this tool) and commercial selection (Product Selector) acknowledges that most selection mistakes happen inside the technical tab — picking a chip that lacks a peripheral or an interface mode after the firmware is already underway — so the Comparator reduces one of the common cost tails on ESP projects. Second, the per-feature notes column is where ESP32 variants differ in ways that catch firmware teams late, such as which parts actually support USB HS, which chips keep hardware floating point, or which peripherals share bus arbitration with WiFi. Reading these notes before board selection avoids a familiar failure mode: a dev board arrives that matches a filter on paper but misses the exact peripheral mode the application needs.

The tool is a static web app hosted under esp-techpedia at `docs.espressif.com/projects/esp-techpedia/en/latest/chip-comparator-web/ESP32_Chip_Comparator_Portable.html`, which means it is free, works offline once cached, and is not gated by an Espressif account. The limitation worth flagging is that the Dev Board Selection database covers Espressif's official boards, not the third-party module ecosystem; teams designing around a Seeed, Olimex or custom module still need the datasheet pass alongside the Comparator's output. The post does not state an update cadence, so engineering teams relying on it for sourcing decisions should re-run selections after each ESP-IDF or chip announcement.

### 🎯 Takeaway (Hợp)
Before committing to a new ESP target this quarter, run the Chip Comparator over the top three candidates and export the differences table into the design review — that single artefact is often the piece missing between a firmware spike and a board bring-up ticket.
