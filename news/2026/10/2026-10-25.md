## 1. Cloudflare's Pingora Cache Removes the Range-Size Tunable and Halves R2 p99 Time to First Byte

### 🔭 Overview (Tổng)
On 23 October 2026 Cloudflare published Origin Range Requests, a change to the Pingora-based cache that removes the per-zone range-size tunable and reorganises how byte-range requests reach the origin. The write-up is light on authors but structured as a launch rather than a roadmap post: the feature is on all plans today, exposed through a Cache Rule, with the headline number that p99 time-to-first-byte on R2 range workloads has roughly halved on both cache hits and misses. For teams that serve large files out of R2 — video, data lake Parquet partitions, scientific datasets — this collapses one of the longer-standing operational tunables into a single on/off decision.

### 🔬 Details (Phân)
The old architecture, inherited from the earlier nginx-based cache, split origin fetches into fixed-size ranges whose size was a zone-level knob and part of the cache key, so changing it invalidated every cached entry. The two failure modes it created are easy to describe. A small range size pushed many short origin requests that each held memory while in flight, which hurt tail latency; a large range size downloaded far more bytes than the client ever asked for, which the post illustrates with a 64 MiB range in which a tiny read crossing an alignment boundary cost 128 MiB of inter-DC transfer. Origin Range Requests keeps the aligned-chunk model on disk but drives origin fetches from Pingora's existing fixed-size on-disk chunks, so the chunk size stops being a zone knob and only the client's requested bytes are returned to the client.

The piece that makes this safe is the coordinator. Each response is assembled from three pools of bytes: already-cached chunks, in-flight downloads that a concurrent request can attach to instead of starting its own origin fetch, and new origin data. Before combining them the coordinator checks that every piece belongs to the same representation using size, ETag, and the If-Range header, falling back to serving the entire response when ranging is not safe — the example given is content being decompressed in flight. A separate, later change in the same post combines on-disk and upstream bytes into a single response and is credited with roughly a 6% week-over-week drop in tiered cache traffic for R2 and similar workloads.

Operationally the implication is that cache topology changes that used to be hazardous — raising the range size to cut request count, lowering it to reduce wasted transfer — are no longer needed. For data engineering teams the specific win is on R2-backed data lakes, where a query engine like DuckDB or Trino issues small aligned range reads for Parquet row groups and footer metadata: previously those reads either paid the inter-DC overfetch penalty or forced an unusually small range size whose cost showed up elsewhere. Cloudflare does not publish p50 numbers or absolute millisecond figures, so sizing against a specific workload still requires a test, but the direction of the change is clear enough to run as a Cache Rule and measure.

### 🎯 Takeaway (Hợp)
If your data platform reads Parquet or similar formats from R2, enable Origin Range Requests on the serving zone through a Cache Rule and compare p99 TTFB on representative range sizes before changing anything else — the halving claim is specific enough to validate in a single afternoon. Với các zone đang gồng tham số range-size vì lý do lịch sử, chuyển sang Origin Range Requests giúp xóa luôn một dòng cấu hình dễ bị quên khi tune cache. Treat the 6% tiered-cache traffic reduction as a quieter secondary benefit for cost rather than latency; it only shows up at the Cloudflare fleet level and will not appear on a single zone's bill in isolation.

### 🔭 Overview (Tổng)
On 23 October 2026 Maneesh Sharma, Laura Reith, Sri Pooja Ravipati and Songzhi Liu opened a three-part AWS Big Data series on cross-Region Trusted Identity Propagation (TIP) for Lake Formation. The headline capability is that IAM Identity Center now replicates identity objects to Regions you choose, so a query service in one Region can see the same user identity as a producer account in another Region, and Lake Formation can authorise each row-level request against that user and log it in CloudTrail. Part 1 walks the Amazon S3 and Amazon Redshift paths, with Amazon QuickSight and Amazon EMR coming in later parts; the practical outcome is that identity-aware queries no longer require every participant to sit in the same Region.

### 🔬 Details (Phân)
The topology in the walkthrough is specific. A producer account in Asia Pacific (Sydney, `ap-southeast-2`) owns S3-governed and Redshift-governed data under Lake Formation, a consumer account in South America (São Paulo, `sa-east-1`) queries that data through Amazon SageMaker Unified Studio (Amazon Athena) and Redshift Serverless, and the IAM Identity Center organization instance lives in `us-east-1`. Both accounts must sit in the same AWS Organization and share one IAM Identity Center organization instance, with identity objects replicated to Sydney and São Paulo through the new TIP control plane. Access to the underlying resources is bridged with AWS Resource Access Manager shares and AWS Glue resource links, where the consumer side grants only `glue:DescribeResourceLink` on the local link — a tighter grant than the whole-database model many teams default to.

Two IAM details are worth lifting into a review document before adoption. On S3, the producer registers the bucket location using a custom IAM role whose trust policy includes `sts:SetContext`, because the Lake Formation service-linked role does not carry that action and TIP needs it to re-establish the user context inside the governed path. On Redshift, data moves through a datashare that is registered to the Glue Data Catalog, so the Redshift path reuses the Catalog as the central resource graph rather than a separate Redshift-only grant model; the post is explicit that permissions are granted both to the consumer account and to the IAM Identity Center users and groups themselves, which is where row- and column-level control actually lands.

The architectural implication is one less reason to co-locate query engines with the data they govern. Teams that previously replicated catalogues, maintained parallel Lake Formation grant trees, or ran per-Region access gateways to keep identity consistent now have a managed path that keeps a single grant graph. The caveat the post is upfront about is scope: TIP replicates identity objects to selected Regions, not every Region, and quota and latency numbers for that replication are not given. The series' later parts are the ones to watch for QuickSight dashboards and EMR Spark jobs — both of which have historically been the hardest surfaces to keep in step with Lake Formation grants across accounts.

### 🎯 Takeaway (Hợp)
If your data platform already uses IAM Identity Center plus Lake Formation and you have been running a per-Region copy of the catalogue to keep latency acceptable, model the cross-Region TIP path against your query mix before committing to the replication — the Sydney/São Paulo topology in the post is directly reproducible. Với team hay deploy một IAM role trung gian cho mỗi cross-account access, chú ý thêm `sts:SetContext` vào trust policy của role đăng ký bucket, vì đây là điểm khác biệt dễ bỏ sót so với mẫu service-linked role cũ. Keep Part 1 open as a reference for the S3 and Redshift paths and wait for Parts 2 and 3 before expanding the pattern to QuickSight and EMR, where the identity contract is slightly different.

### 🔭 Overview (Tổng)
On 23 October 2026 Philip O'Toole published a retrospective on twelve years of distributed SQLite, tracing rqlite from its September 2014 launch to the current v8.0 line and placing it alongside dqlite and Litestream. The post is useful precisely because it describes the design decisions rqlite got right and the ones it reversed — most notably its 2016 move away from goraft to HashiCorp's Raft library, which is still in use today. It made the Hacker News front page on 24 October, which is reason enough to read it as a vocabulary document for anyone who has to pick a Raft implementation or decide between consensus and WAL streaming for a durable SQLite deployment.

### 🔬 Details (Phân)
Rqlite's architecture is a CP system in the CAP sense. Writes are serialised through a leader, acknowledged by a majority quorum of nodes, and refused by a partitioned minority rather than accepted and reconciled later; reads can trade consistency for speed by picking a weaker read level. The 2016 switch to HashiCorp Raft is the lever behind most of the post's engineering lessons: goraft had been built as a learning exercise, HashiCorp's library had a production operator community around it, and inheriting that community's bug fixes was cheaper than maintaining a bespoke consensus implementation. The decision also sets a usable rule for other teams — pick the Raft library with the biggest paying operator population, not the one most adjacent to your codebase.

The piece places rqlite inside a broader distributed-SQLite ecosystem. Dqlite, open-sourced by Canonical in 2017, is an embeddable C library that still runs its own Raft implementation, which is one way to run distributed SQLite without introducing a separate daemon in the hot path. Litestream, released in 2021, took the opposite architectural turn by streaming the SQLite WAL to S3 for disaster recovery without a consensus layer at all; rqlite v8.0 later borrowed the Litestream-style WAL handling to simplify its own on-disk model while keeping the Raft log for ordering. The piece is honest about what it does not benchmark: no throughput figures, no latency distributions, only the design shape and the read-consistency levels, which keeps the comparison on the architectural plane where it actually belongs.

For a data engineer the practical lift is in the vocabulary. The post normalises the vocabulary of "CP SQLite" versus "WAL-streaming SQLite" as separate categories with separate operational trade-offs, instead of lumping both under "replicated SQLite". It also makes explicit the pragmatic lesson that long-lived open source projects rebuild their foundations more than once — rqlite replaced its consensus library, then its WAL layer, both without changing its external API, which is a workable template for any infrastructure component that has to survive upstream churn.

### 🎯 Takeaway (Hợp)
If you are evaluating distributed SQLite for a product tier, read this post before cutting a prototype against any one project — it draws the "CP with Raft" versus "WAL-streaming" line sharper than any vendor documentation does. Với các team đang maintain fork Raft nhỏ cho riêng mình, câu chuyện goraft → HashiCorp Raft là lý do thực tế để migrate nếu bug backlog đang tăng. Treat the lack of benchmarks as a signal, not a gap: the post deliberately stays on architecture because the right numbers depend on your workload, and the right next step is a short local run against both an rqlite cluster and a Litestream pair.

```bash
# Node 2

  -join http://node1:4001 data/n2

# Node 3

  -join http://node1:4001 data/n3

# Write (strong consistency), then read with weak and strong levels for a quick side-by-side.
curl -XPOST 'http://node1:4001/db/execute' -H 'Content-Type: application/json' \
  -d '[["CREATE TABLE t (id INTEGER PRIMARY KEY, v TEXT)"], ["INSERT INTO t(v) VALUES(?)", "hello"]]'
curl 'http://node1:4001/db/query?level=weak' --data-urlencode 'q=SELECT * FROM t'
curl 'http://node1:4001/db/query?level=strong' --data-urlencode 'q=SELECT * FROM t'
```

### 🔭 Overview (Tổng)
On 24 October 2026 Hackaday's 2026 Retrocomputing Challenge coverage flagged Meatloaf, an ESP32-based device that implements the Commodore IEC serial protocol in firmware and presents remote files to a Commodore machine as if they were on a period-correct floppy drive. The post names the plain ESP32, but a reader comment on the same article corrects it to an ESP32-S3, which matches the source repository's hardware configuration. For an IoT engineer the value is less nostalgia and more the IEC implementation itself: a workable example of using an ESP32-S3 to bit-bang a slow, timing-sensitive serial bus while keeping a WiFi stack and an HTTP client alive on the other core.

### 🔬 Details (Phân)
The device plugs into a Commodore's IEC serial port and does all configuration from the Commodore side, which means the firmware exposes a user-space command surface over the same wire as the data. Files can live either in local flash or at an arbitrary URL, and archive files are unpacked on the fly so their contents appear to the Commodore as discrete floppies rather than as a .zip the operating system would not understand. The practical result is that a vintage BASIC program can load from a GitHub-hosted archive without any changes on the client side, which puts the complexity on the microcontroller: it has to synthesise disk-like responses while meeting the IEC bus timing, including the handshake-heavy sequences that fail at even small jitter.

The source lives at `github.com/idolpx/meatloaf` and the design is a reasonable reference for anyone building an ESP32-S3 bridge between a modern transport (WiFi, HTTP, flash) and a legacy serial bus with real-time constraints. Two patterns worth lifting are the IEC pin bit-banging — gated by the ESP32-S3's hardware timers so WiFi activity on the other core cannot stall it — and the archive-unpack-on-serve approach, which keeps the controller's write-amplification bounded even when the underlying "disk" is a 100 MB zip. Those patterns generalise to industrial retrofits where a modern gateway has to look like an older PLC or sensor over RS-485 or similar.

Where this fits in a 2026 IoT week is mostly as a reminder that the ESP32-S3 is a credible platform for software-defined device emulation, not only sensor polling. The low ratings on the "serious" scale are deliberate: it is not a security advisory, not a chip release, and not a protocol standard, but it is a published open-source implementation of a non-trivial on-the-wire protocol, which puts it ahead of most hobby posts. Teams running real retrofits or sensor-bridge products can save several weeks by starting from Meatloaf rather than reimplementing the timing-sensitive handshake from scratch.

### 🎯 Takeaway (Hợp)
If you are prototyping an ESP32-S3 bridge between WiFi and a slow, timing-strict serial bus — Commodore IEC, RS-485, LIN — read Meatloaf's IEC driver before writing one yourself; the handshake and pin-timing code is the piece most hobby projects get wrong first. Với team làm retrofit industrial, lưu ý mô hình "unpack-archive-on-serve" là một cách giảm ảnh hưởng flash wear khi phải phục vụ volume lớn từ ESP32-S3. Treat the Hackaday article's "ESP32" wording as a copy error against the repository: build for S3 if you are reproducing it.
