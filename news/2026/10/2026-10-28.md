### 🔭 Overview (Tổng)
On 26 October 2026 Michelle Chen published a Cloudflare blog post coordinated with the SGLang RadixArk team disclosing a cross-request KV cache exposure in GLM-5.3 served under `@cf/zai-org/glm-5.3` on Workers AI. The post matters for a data engineering audience because the leak lived at the inference-stack level, not in a Workers application: between 27 August and 9 September 2026, 155 responses to prompts longer than 681,280 tokens returned content built on KV pages still holding other customers' request state. The report was filed by Gadi Evron of Knostic on 8 September through HackerOne, Cloudflare declared an incident on 9 September at 13:22 UTC and reproduced the leak inside 25 minutes, the model was set to private at 14:00 and restored at 19:40 the same day, and the postmortem names two root causes, a Mooncake-over-RDMA transfer path, and a concrete SGLang fix line.

### 🔬 Details (Phân)
The two root causes compound. The GLM-5.3 deployment advertised a 1,048,576-token context window, but the KV cache pool on the prefill GPUs held only 681,280 tokens, and the pool size was computed at startup from remaining GPU memory after weights loaded while the context length was a separate config value — nothing enforced agreement. The team expected SGLang to error on oversized prompts, and long-context tests returned HTTP 200 with no error frames, so the mismatch stayed invisible until the researcher's report. Inside SGLang's disaggregated prefill/decode path, when a prompt exceeded the pool the engine replaced it with a one-token placeholder and marked the request rejected, but the admission queues checked whether a request was finished rather than whether it was rejected. The router then told decode the original prompt length, decode reserved 8 KV pages, prefill ran one forward pass on the placeholder and wrote a single page, prefill signalled transfer complete, decode accepted the handoff and attended across all 8 pages — the 7 unwritten pages still held stale data from earlier requests, and the client got HTTP 200 with coherent output and an inflated `prompt_tokens` count. The upstream bug was first reported as SGLang issue #30233 on 6 July 2026, before Workers AI hit it in production.

The remediation lands in two layers. On configuration, Cloudflare resized the GLM-5.3 prefill KV pool to about 2.04M tokens — roughly twice the context length — so valid requests never reach the rejection path on this model. On the engine, rejected requests are now retired at the disaggregation admission queue with their original error, before any bootstrap, page allocation, or KV transfer, in SGLang #36988 (v0.5.20) and #38935 (v0.5.21), and decode verifies that transferred token counts match its reservation in draft #38704. The post also lists a block of adjacent hardening work that is more useful to operators than the specific fix: deferred KV release on both roles covering all failure types, bounded Mooncake transfer batches so a timed-out call cannot leave unbounded in-flight writes, a load balancer that holds connections to the first token instead of aborting mid-transfer, per-transfer KV checksums behind `--disaggregation-enable-kv-checksum` (#39500), the KV Canary (#38596, #40642), and new metrics for deferred release (#41128). A page-level tag prototype — tags reset on reallocation and checked at read time, with under 1% throughput and tail-latency cost in tests — was built but disabled on GLM 5.2 in mid-August for reliability reasons; Cloudflare says a formal verification pass over its SGLang-plus-Mooncake RDMA setup is the longer-term direction.

For a team running inference on SGLang or any disaggregated engine, the actionable surface is the three-line gap between pool size, context length, and admission state. The practical risk is not SGLang-specific — any engine that splits prefill and decode across a KV page pool and signals handoff before verifying bytes transferred has the same shape of exposure, and the Cloudflare write-up is the clearest public anchor to compare an in-house stack against. The researcher's reproduction script and Cloudflare's canary-marker tests were used to validate the fix before restoring the model, so the pattern for operators is to re-run both against any production endpoint after a weights, quantization, parallelism, or memory setting change.

### 🎯 Takeaway (Hợp)
On every prefill and decode node, compare the KV pool size printed at SGLang startup against the context length and refuse to roll out any configuration where the pool is smaller than context; add a canary-marker test to the deploy pipeline that intentionally sends prompts near context length and watches for cross-request content. Nâng engine lên tối thiểu SGLang v0.5.22 để fix admission landing và bật `--disaggregation-enable-kv-checksum` nếu model hỗ trợ, không coi "flake-free HTTP 200" là bằng chứng pool đủ. Treat Cloudflare's postmortem as the reference template for any team self-hosting disaggregated inference — the three-line config/admission/transfer invariant is the one that leaked here and the one your own validator should encode.

  - name:    kv_transfer_integrity

### 🔬 Details (Phân)
The one-prompt flow is deliberately shaped as a decision tree rather than a black box. The user names a path (`s3://my-bucket/clickstream/` is the article's example), CoCo asks where the data should land and which of four setup options to use — temporary access on Amazon S3, Terraform for the full pipeline, existing cloud access, or Snowflake objects plus cloud setup files — then detects the format, proposes column names and types, reuses compatible storage integrations, stages, and file formats, and flags any existing pipes that would double-load the same files. The default workflow shows SQL and asks for approval before changing Snowflake objects. CoCo can backfill the last seven days immediately, run a one-time load for older files, and turn on schema evolution. After setup it checks pipe status, notification delivery, and load history, and reports errors. Supported storage covers Amazon S3, Azure Blob Storage, and Google Cloud Storage, and supported formats are CSV, JSON, Parquet, Avro, ORC, and XML. The user interface is Snowsight, CoCo Desktop, or CoCo CLI.

The AWS specifics are the most important part of the GA line because they decide whether the automation is usable inside an enterprise security review. CoCo uses AWS IAM temporary delegation: the user approves one time-limited request in the AWS Management Console, and Snowflake creates the storage role, trust policy, and bucket notifications without AWS access keys. A permissions boundary limits the role and AWS CloudTrail logs the setup actions. For teams that must self-manage infrastructure, CoCo can emit Terraform covering both Snowflake objects and cloud resources on AWS, Azure, and Google Cloud, or CloudFormation, or ARM templates. On Iceberg, the automation sets up a Snowflake-managed Iceberg table and a pipe where Snowpipe writes Parquet, converts non-Parquet source formats on load, and Snowflake maintains Iceberg metadata and table upkeep — the first-class support for Iceberg means an ingest built this way can be read from Apache Spark or any other Iceberg-compatible engine without a second materialisation step.

The honest limits are on the GA edges rather than the core flow. AWS IAM temporary delegation is not available in AWS GovCloud (US) or China regions, so those customers stay on static-credential or Terraform paths. Setup time is affected by cloud approval and permission-propagation latency, which the post does not quantify. The announcement names no regions or benchmark numbers beyond the GovCloud/China exclusion and refers to CoCo and Snowpipe cost documentation for pricing — Snowpipe is still billed as serverless usage. Nothing in the post describes performance of the generated pipeline (load latency on new files, throughput ceilings per pipe, cost per million rows), which is appropriate for a setup-tool GA post but means the operational properties still have to come from the existing Snowpipe documentation.

### 🔬 Details (Phân)
The new architecture rests on compute/storage separation. Data is written to Amazon S3 at ingestion and served through a fast storage layer, so stateless OCUs can be added within seconds as demand rises and taken away when load drops. Minimum and maximum OCU settings are configurable per role, with ingest OCUs set separately from search OCUs, and when minimum OCUs is set to zero the collection scales fully to zero after ten minutes of inactivity. Collection groups let several collections share compute while continuing to use separate AWS KMS keys, which is the mechanism the post names for per-collection encryption at scale. The post claims terabytes-per-day ingestion is in scope but does not publish a benchmark number against the prior generation beyond the "up to 20x faster" autoscaling claim.

The configuration surface is where migration cost will live. Index-level `index.warm.after` controls the hot-to-warm transition (`"7d"` in the post's example, which moves data to the warm tier after seven days while data continues to live in S3 throughout). The default timestamp field remains `@timestamp`, but it can now be overridden with `index.timestamp_field: "event_time"`, with documents whose timestamps are missing, null, or invalid rejected individually — in a `_bulk` call the overall request still succeeds, and failures surface in the `errors` block. Retention has moved onto index templates through `index.data.retention`, which the post pairs with a seven-day hot tier for a thirty-day example — the printed snippet is slightly malformed in the article (a missing closing quote), so operators should check the official docs before copying. The next-generation OpenSearch UI, announced in November 2024 but newly relevant here, carries an Observability workspace with alerting, anomaly detection, visualisations, and PPL support, and the article positions it as the migration path from provisioned clusters.

What the piece leaves open is the shape of the warm tier under real load. The post is explicit that warm-tier queries have higher latency because they read directly from S3, but gives no numbers on query latency at the warm boundary, on how the fast storage layer scales when a backfill lands on the ingest OCUs, or on cost of a warm-tier reindex. There is also no regional availability or pricing in the post. For a daily digest the practical reading is that the architectural line is firm and the operational numbers are not — enough to commit to a design but not enough to commit to a migration SLA without a staging run.

### 🎯 Takeaway (Hợp)
If your observability data is already in OpenSearch provisioned or classic serverless and the peak-to-trough ratio is wide, the new scale-to-zero plus separable ingest and search OCU knobs are the right primitives to try — set minimum OCUs to zero on a staging collection first and confirm the ten-minute idle behaviour against your access pattern. Với team đang mô hình chi phí observability, bỏ phần hot và warm paying together là điểm thay đổi về mặt billing, nhưng warm-tier latency chưa có benchmark công khai nên vẫn phải đo trên data thực. Keep retention off external lifecycle policies and move it onto `index.data.retention` on the index template to stay on the supported configuration surface.

### 🔭 Overview (Tổng)
On 27 October 2026 Kristen Drexinger and Seshendranath Balla from Databricks published an engineering post titled "From spot fixes to measured gains: improving document extraction accuracy with `ai_extract` and MLflow Prompt Registry". The post earns a daily-digest slot because it is a worked case study with concrete numbers on a problem most data engineering teams building LLM-backed extraction run into — a spot fix helps one field and quietly hurts the pipeline. It describes a methodology (which lever to pull, how to version prompts and schemas, how to measure against fixed ground truth, how to assign a verdict), and it lands on an architecture that pairs the `ai_extract` AI Function with the MLflow Prompt Registry so prompt and schema versions can be promoted or rolled back without re-deploying the pipeline.

### 🔬 Details (Phân)
The levers come first and matter the most, because the post's whole thesis is that extraction regressions start from putting a rule in the wrong place. Field-specific rules such as preserving leading zeros or excluding status terms belong in the schema. Document-level logic such as source priority or cross-field consistency belongs in the global prompt. Formatting belongs in downstream SQL or code. Precision mode is the lever for structural problems like repeated line items, and citations plus confidence scores are the lever for telling extraction errors apart from labeling disagreements. The MLflow Prompt Registry versions prompts and schemas separately from pipeline code, with aliases such as `@prod` and `@candidate` pointing to approved versions — the article names `mlflow.genai.set_prompt_alias` as the move-alias API — so a promotion or rollback is a one-call operation rather than a redeploy. The pipeline under study extracts about forty fields from partner order documents across dozens of PDF layouts, with an evaluation cohort of several hundred PDFs.

The numbers in the piece are what give the methodology shape. A schema-only change on the `revision` field cut revision errors by 49% but raised total errors by 9%, so it was not shipped. A restructured prompt-and-schema pair cut revision errors by 57% and total errors by 16%, with the prompt coming out at under half its original length. Turning on precision mode alone cut total errors by 24% and revision errors by 10%. Combining precision mode with the restructured prompt and schema cut total errors by 32% and revision errors by 64%. The piece also surfaces a measurement gotcha — scoring only non-blank cases understated the revision fix (under three points of apparent gain); including blank-answer errors in the baseline showed revision errors roughly halving. For run-to-run variance, the article prescribes running the production baseline three to five times to estimate noise, and treats gains inside roughly two sigma of baseline as inconclusive.

The verdict schema is the piece operators are most likely to adopt verbatim because it is small and portable: candidates get labelled BETTER, SUSPECT (accuracy up but coverage down), UNSTABLE, INCONCLUSIVE, or WORSE, and an owner makes the final promotion decision with an override logged and a reason attached. The piece also promotes Databricks' Genie Code as the automation layer for the measure-improve-re-evaluate loop, but the methodology stands independent of that product — the schema labels, the two-sigma significance bar, and the fixed ground-truth coverage requirement are repo-independent and can be bolted onto any `ai_extract`, Snowflake Cortex, or in-house extraction stack.

### 🎯 Takeaway (Hợp)
If you run any LLM-backed extraction over documents, adopt the verdict schema (BETTER / SUSPECT / UNSTABLE / INCONCLUSIVE / WORSE) and the two-sigma noise bar before you ship another "fix", and move prompt plus schema versioning off pipeline code into the MLflow Prompt Registry so a rollback is an alias move rather than a deploy. Với team đang chạy extraction production, bài này ép bạn tính luôn blank-answer errors trong baseline — nhiều fix tốt bị đánh giá thiếu vì cột blank-answer bị tách ra. Carry the four levers forward verbatim (schema for field rules, prompt for document rules, SQL for formatting, precision mode for structure) and treat an improvement on one field at the cost of system totals as a non-ship, not a trade-off.

### 💡 Example
```python
# ai_extract + MLflow Prompt Registry promotion loop,
# per Databricks engineering post (27/10/2026).

import mlflow

# 1. Fixed ground truth: scored every run, includes blank-answer errors.
GOLD = load_gold("partner_orders_eval.jsonl")   # several hundred PDFs

# 2. Baseline noise: 3-5 runs of @prod, compute sigma.
baseline = [score(ai_extract(doc, prompt="@prod", schema="@prod"), GOLD)
            for _ in range(5)
            for doc in GOLD]
sigma = stdev(baseline)                          # ~2*sigma is the "noise band"

# 3. Candidate: schema change OR prompt change OR precision mode.
cand = [score(ai_extract(doc, prompt="@candidate",
                         schema="@candidate",
                         mode="precision"), GOLD) for doc in GOLD]

# 4. Verdict (concrete numbers from the article):
#    schema-only revision fix     : revision -49%, total +9%  -> WORSE
#    prompt+schema restructure    : revision -57%, total -16% -> BETTER
#    precision mode alone         : revision -10%, total -24% -> BETTER
#    combined                     : revision -64%, total -32% -> BETTER
verdict = classify(cand, baseline, sigma)   # BETTER / SUSPECT / UNSTABLE / ...

# 5. Promote by alias; no pipeline redeploy.
if verdict == "BETTER":
    mlflow.genai.set_prompt_alias(name="partner_orders",
                                  alias="prod",
                                  version=cand_version)
```

### 🔬 Details (Phân)
Three ISA limitations shape the implementation. First, the Xtensa LX7 SIMD unit only compares signed 8-bit values, and reinterpreting unsigned pixel data as signed breaks ordering for values 128–255, so the author shifts every loaded unsigned byte from `[0, 255]` into `[-128, 127]` before comparing. Second, SIMD arithmetic on the ESP32-S3 is saturating, so the straightforward way to apply that shift — subtract 128 — does not round-trip across the boundary; the author uses the identity `x − 128 = x XOR 0x80` instead, which flips the most significant bit without touching the saturating path. Third, the ISA cannot read misaligned data directly, so for the FAST pre-test, which samples pixels in the four cardinal directions around a candidate, the center block is assumed aligned and the east and west blocks are built by loading the aligned neighbouring blocks and extracting the needed byte slice from two concatenated 128-bit registers. A 128-bit vector register holds sixteen 8-bit pixels, so sixteen candidates are processed per vector by loading four chunks per direction.

The engineering around the compute is as interesting as the compute itself. The author wrote a small register allocator called `basm` to manage the SIMD register file, which is the kind of overhead that typically explains why hand-written SIMD on embedded Xtensa stops at proof-of-concept — once the register pressure crosses what a human can bookkeep, a mini-allocator is the lever that lets the pipeline grow. The write-up includes a minimal function skeleton with the Xtensa prolog/epilog shape (`.section .text`, `.global`, `entry sp, 48`, register aliases `r_a = a2`, `r_b = a3`, body, `retw.n`) which is enough for a reader to clone the project and extend it without recovering the ABI from scratch. A SIMD scoring function was also written for the full FAST pass but the post does not detail it, so the open piece is how the corner score — the part of FAST most sensitive to vectorisation — fits inside the same pre-test harness.

The numbers earn the digest slot because they are measured and reproducible. The ESP32-S3 at 240 MHz processes a QVGA frame in about 6 ms, giving headroom to run a 30 FPS VGA (640×480) stream. The throughput improvement is reported as "about 220%" — 5.1 MP/s to 11.2 MP/s — which the author translates as roughly 2.2x, though the "220%" wording in the post is ambiguous between a 2.2x ratio and a 2.2x increase on top of baseline; the raw MP/s figures resolve it as a 2.2x ratio or roughly 120% increase. No cycle counts are given, which is the one gap worth noting for anyone estimating headroom for a wider pipeline. License is not stated in either post, so the repository on GitHub is the authoritative place to check before any derivative work.

### 🎯 Takeaway (Hợp)
For any team doing vision on an ESP32-S3 without an application processor behind it, the three ISA workarounds in this project — XOR 0x80 to shift unsigned into signed around the saturating subtract, concatenate-and-extract for misaligned slices, align-the-center-block for pre-test sampling — are a transferable template, not just a corner-detector trick. Với team đang build pipeline nhận dạng feature embedded, con số 11.2 MP/s / 2.2x cho FAST pre-test là mốc đáng tin cậy để so sánh với các cách tiếp cận ESP-DL hoặc QEMU-trên-server, và `basm` register allocator là dấu hiệu rằng SIMD assembly đã đến ngưỡng cần tooling riêng.
