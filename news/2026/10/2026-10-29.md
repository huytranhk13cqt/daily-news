### 🔭 Overview (Tổng)
On 26 October 2026 Gábor Szárnyas and Geertjan Wielenga published "Gems of DuckDB 2.0.0" on the DuckDB blog, a follow-up to the 21 October announcement of DuckDB 2.0.0 LTS "Cyanoptera". The post is worth a daily-digest slot because the headline 2.0.0 announcement focused on bigger-ticket items, so the smaller changes with the highest leverage for day-to-day data engineering — a first-class Python appender, a security-oriented view type, custom partition subdirectory paths, and GeoJSON write support — were only lightly covered. The gems post lays those out with runnable snippets, calls out behavioural changes in the CLI, and documents how community extensions are now version-and-platform matrixed. For teams planning the upgrade to 2.0.0 LTS, this is the piece that identifies the quietly actionable surface changes.

### 🔬 Details (Phân)
The clearest ergonomic win is the Python appender. `con.appender("duckdb_releases")` returns a context-managed object that buffers rows and commits them in one operation, replacing the executemany/transaction patterns most ingestion scripts carry. The appender takes `append_row` for a single tuple and `append_rows` for a list of tuples, and the post uses the DuckDB release names themselves as sample data. On the SQL surface, `CREATE SECURE VIEW` is a new view kind designed to limit metadata leakage from predicate pushdown and error messages — the post's example masks the `all_users` table so that only rows where `access_level = 'standard'` are visible. `SHOW <setting>` is a new keyword alongside the existing `SELECT current_setting(...)` and `pragma`, with a new `show_behavior` session setting controlling output verbosity; `regexp_extract` gains an options-taking overload; and `setval()` is added for setting sequence values. Prepared statements can also fall back to session variables of the same name as named parameters, which collapses two steps of parameter plumbing in scripts.

Partitioned writes get two useful knobs. `COPY ... (FORMAT parquet, PARTITION_BY (year), PARTITION_PATH <expr>)` lets the subdirectory layout be a SQL expression rather than the default `col=value` pattern, so an archive layout like `archive/2015/`, `recent/2024/` is now expressible without a post-write rename pass. `ORDER_BY` as a COPY option sorts rows inside each partition, which matters for predicate pruning on columnar formats downstream. Geo support also lands on the write side: `COPY ... (FORMAT GEOJSON)` and `FORMAT GEOJSONL` write GeoJSON and newline-delimited GeoJSON respectively, closing the output half of the geospatial loop. The CLI defaults are the one area to re-check during an upgrade: `.schema` now pretty-prints by default and takes `--no-indent` to restore the single-line form that many scripts and tests parse. `.manual` shows function documentation, `.history` prints the shell history, and `shell_history()` exposes that history as a SQL table function.

For extension authors and operators, the compatibility matrix is the most useful operational change. Community extensions now carry a per-version, per-platform matrix on the directory, so a team pinning an environment can read which combinations are tested rather than discover a gap at install time. Extensions can also define window functions through the C++ API, lifting a long-standing boundary where custom aggregates were supported but windowed semantics required a core change. Offline documentation ships as Markdown and PDF bundles — roughly 5 MB and 10 MB for the docs, and 3 MB and 35 MB for the blog — which is a small but real win for air-gapped environments where the usual answer is to mirror the whole site.

### 🎯 Takeaway (Hợp)
If you are planning the move to DuckDB 2.0.0 LTS, read the gems post before the announcement: the Python appender replaces a lot of hand-rolled ingestion code, `CREATE SECURE VIEW` is the right primitive for shared BI databases that need predicate-safe row filtering, and `PARTITION_PATH` lets you adopt a human-readable Parquet layout without a rename pass. Chú ý rằng `.schema` giờ pretty-print mặc định — nếu CI của bạn đang grep output `.schema` một dòng, thêm `--no-indent` trước khi upgrade. Treat the community-extension compatibility matrix as the first thing to check when pinning a 2.0.0 environment, especially on non-x86 platforms where coverage historically varies.

### 💡 Example

```python
# From "Gems of DuckDB 2.0.0" (duckdb.org, 26/10/2026).

import duckdb

con = duckdb.connect("warehouse.duckdb")

# 1. Appender buffers rows and writes them in one operation.
with con.appender("duckdb_releases") as a:
    a.append_row(("1.4", "Andium"))
    a.append_rows([("1.5", "Variegata"), ("2.0", "Cyanoptera")])

# 2. SECURE VIEW limits metadata leakage from predicates and errors.
con.execute("""
    CREATE SECURE VIEW users AS
    SELECT username FROM all_users WHERE access_level = 'standard';
""")

# 3. Custom partition paths: human-readable Parquet layout, one pass.
con.execute("""
    COPY orders TO 'orders' (
      FORMAT parquet,
      PARTITION_BY (year),
      PARTITION_PATH CASE WHEN year < 2020
          THEN 'archive/' || year
          ELSE 'recent/'  || year END,
      ORDER_BY (customer_id)
    );
""")
```

### 🔭 Overview (Tổng)
On 26 October 2026 Yu-Ju Huang, Ankit Vij, Vadim Antonov, and Dima Kotlyarov published a Databricks engineering post extending Databricks AI Search beyond Delta tables to three new source kinds: Streaming Tables, Materialized Views, and Managed Iceberg tables at the v3 or later format version. The post matters because it narrows the gap between a lakehouse's primary tables and the search indexes built on top of them. Previously, teams running fraud detection on a Streaming Table, personalisation on a Materialized View, or an open-format Iceberg warehouse had to maintain a parallel Delta copy and the sync pipeline keeping it fresh. The announcement removes that intermediate step: a Delta Sync index can now point at any of the four source kinds and be created from the same UI or API path.

### 🔬 Details (Phân)
Each source carries its own semantics into the index. Streaming Tables are the right primitive for append-mostly event streams — fraud, IoT telemetry, clickstreams — and the index sees the same incremental writes the table does, without a batch step in between. Materialized Views cover the aggregated-or-joined pattern (session-aware search, personalised ranking, dashboards that reuse the same join as the search query), and the index refreshes against the view's incremental maintenance schedule rather than a separate materialisation. Managed Iceberg tables are the open-format path: because Databricks AI Search can read the Iceberg format directly, the same table that Spark, Trino, or Flink reads is also the source of truth for the search index, with no second write to a Delta mirror. The index type itself is a Delta Sync index, so the surface the application calls stays unchanged — only the source side opens up.

The practical cost of the previous pattern was two-fold, and the post leans on that framing. First, a parallel Delta copy doubled storage and compute for every table that fed search. Second, the sync pipeline keeping the Delta copy fresh was a hand-built artifact — a job, a trigger, an error path — that each team re-implemented and then had to monitor. By letting the index be created directly against the Streaming Table or Materialized View, both costs disappear for the common case; by supporting Managed Iceberg v3+, an organisation standardising on Iceberg does not need a Delta sidecar just to serve search. The post is explicit on the v3-or-later requirement for Iceberg, which is the version floor where Databricks AI Search can read the format natively. The index creation workflow — in the UI or through the Vector Search API — stays identical across the four source types.

The honest limits of the announcement are its silences. The post does not publish ingest-to-visible latency numbers for any of the three new sources, does not state whether every embedding model and index tier is supported across all four source kinds, and does not name regional availability or quotas. On Iceberg specifically, the piece is clear that v3 is required but does not describe behaviour against external Iceberg catalogs or non-Managed Iceberg tables, which is the harder case for most Iceberg-first teams. For a daily-digest reading, that puts this release in the category of "architectural line is firm, operational numbers are not": the elimination of the Delta sidecar is the structural win worth adopting a staging pilot for, with throughput and freshness measured in that pilot rather than taken from a benchmark that was not published.

### 🎯 Takeaway (Hợp)
If your search surface today is backed by a Delta copy fed by a hand-built sync job from a Streaming Table or Materialized View, this release lets you delete the sidecar and the job — stand up a Delta Sync index against the original source in a staging workspace, measure the end-to-end freshness your fraud or personalisation path actually tolerates, then switch over. Với team đang chuyển dần sang Managed Iceberg v3+, đây là bước để search cũng chuyển cùng chứ không bị kẹt lại ở Delta. Keep the Delta mirror where you have external, non-Managed Iceberg catalogs or where you need v2 Iceberg today, until the next format bump brings those paths into scope.

### 🔭 Overview (Tổng)
On 28 October 2026 Leonardo Pedretti, Software Engineer at RELOC, posted on the Espressif Developer Portal introducing SCINTIX P4, a compute module that packages an ESP32-P4 into the Raspberry Pi CM4/CM5 mechanical and connector form factor. The post's engineering substance earns a digest slot because the module is positioned as "likely the first MCU-based compute module in this form factor", meaning existing CM4/CM5 carrier boards — of which there are many commercial ones — can be reused as the physical and I/O substrate for an ESP32-P4 project. Three carriers were tested on real hardware (Raspberry Pi CM4 and CM5 IO Boards, Waveshare CM4-DUAL-ETH-MINI, Waveshare CM4-NANO-C) and several more were checked against their schematics. The piece also runs a Hello World and an Ethernet iperf3 pass that measured roughly 73 Mbit/s uplink and 79 Mbit/s downlink on the on-board 10/100 PHY.

### 🔬 Details (Phân)
The silicon mix is specific. The main processor is the ESP32-P4NRW32X with two 400 MHz RISC-V cores plus a low-power core, paired with 32 MB PSRAM and 32 MB NOR flash on the module. The ESP32-P4 has no built-in radios, so wireless comes from a companion ESP32-C6 bringing Wi-Fi 6, Bluetooth 5, and IEEE 802.15.4 (the physical layer for Thread and Zigbee), connected to the P4 over a 4-bit SDIO link plus UART for coexistence. The on-module Ethernet PHY is a Microchip KSZ8091RNACA 10/100, which is the piece that lets the iperf numbers above hold on an off-the-shelf CM4 IO carrier. Display and camera land on the ESP32-P4's 2-lane MIPI-DSI and 2-lane MIPI-CSI, exposed on the Hirose DF40C-100DP connector pair at the carrier edge. USB-C handles power and programming, and a separate USB 2.0 OTG line goes out to the carrier for host-side ports.

The compatibility story is where this release is interesting and where the honest limits sit. 23 ESP32-P4 GPIOs appear on the carrier's 40-pin header, which is enough for a wide carrier bring-up but less than a full CM4 pin complement, and some pins are shared or tied together to fit the mapping. Power comes from a 5 V carrier input with a shared 3.3 V rail; there is no 1.8 V output, which rules out any carrier design that depends on it. Any CM4-specific feature that depends on Broadcom-only interfaces — HDMI and PCIe are the two the post names — is not present because the ESP32-P4 does not drive them. The practical consequence is that a CM4/CM5 carrier can be a drop-in for the SCINTIX P4 only when its peripherals route through SPI/I2C/UART/SDIO/MIPI, and the article's compatibility note is that some tested carriers still need a jumper or component change to bring up cleanly.

The one engineering number from the post is the Ethernet throughput: iperf3 on the KSZ8091 PHY measured roughly 73 Mbit/s uplink and 79 Mbit/s downlink against a 100BASE-TX ceiling of 100 Mbit/s, which is in line with ESP32 Ethernet performance in the literature but is useful as a module-level anchor rather than an SoC-level one. Mechanicals are 55 × 40 mm at 8.2 g, operating range −20 to 70 °C, dual Hirose DF40C-100DP connectors. Availability is pre-launch on Crowd Supply with samples by contacting info@reloc.it; the post does not state unit pricing, so a cost comparison against a Raspberry Pi CM4 or against the ESP32-P4-Function-EV-Board is not yet possible from public material.

### 🎯 Takeaway (Hợp)
For a team building an industrial HMI, a small-footprint camera node, or a Thread/Zigbee gateway that benefits from the ESP32-P4's dual RISC-V cores and MIPI interfaces but wants to reuse an off-the-shelf CM4/CM5 carrier, this is the first module where that reuse is directly tested. Trước khi commit một carrier CM4/CM5, kiểm tra bản schematic — một số carrier cần jumper hoặc component change, và bất cứ tính năng nào phụ thuộc HDMI/PCIe của Broadcom đều không có trên ESP32-P4. Validate the KSZ8091-plus-ESP32-C6 split against your workload before picking SCINTIX P4 over an SoC-level ESP32-P4-Function-EV-Board; the convenience of the CM4 pinout only pays off if your carrier doesn't need the pins the P4 cannot drive.

### 🔬 Details (Phân)
The emulator half is the substantive engineering. According to the post, Cirkit's runtime is an "instruction-accurate emulator built from scratch in Rust, compiled to WebAssembly" that executes Xtensa instructions for the ESP32 and ESP32-S3 and runs locally in the browser. The modelled peripheral surface named in the article is GPIO, UART, I2C, SPI, ADC, timers, LEDC PWM, and RMT, with the author's claim that unmodified Arduino firmware runs against those peripherals. Firmware is compiled through Arduino CLI on Cirkit's backend — so compilation is remote and the simulator is local, which is the opposite of the usual arrangement — and AI prompts plus external network calls (for example, the ISS tracker sample project calling `wheretheiss.at`) also go through the backend. The AI agent can create simulation component models when a part is missing, with the example in the post being an I2C LCD; the resulting model is written against the same peripheral surface the ESP32 firmware exercises, so the LCD is driven over simulated I2C rather than through a UI hook.

The context is where the honest reading lives. There are already serious embedded simulators in the ecosystem — QEMU with the Espressif fork, Wokwi for browser-based ESP32 simulation, and ESP-IDF's host build — each with its own set of accuracy claims. The novel part of this post, if the accuracy claims hold up, is the combination of in-browser WebAssembly execution with peripheral register fidelity for the ESP32-S3 and an AI agent that generates both circuit and firmware. The caveat Espressif attaches — that the content has not been independently verified — is the signal that an engineer should treat the "runs unmodified firmware" line as a claim to validate on their own workloads before trusting it for anything other than tutorials or quick prototypes. The accompanying material in the post is practical: a sample ISS tracker project link, a networking guide, an ESP32-S3 platform doc, and a May 2026 engineering overview of the simulator — enough to kick the tyres.

What the post leaves out is the usual list of embedded-simulator limits: no cycle counts, no reporting on worst-case accuracy on wide SIMD or FPU paths, no coverage of SPIFFS/LittleFS, no discussion of Wi-Fi stack modelling (which is non-trivial given the ESP32-S3's radio behaviour), and no stated license for the emulator itself. The AI component builder is useful for one-off models but, like all generated code, needs a human review before it anchors a reproducible test. For a daily-digest reading, this is less a release and more a notable-project launch worth tracking — a well-engineered in-browser Xtensa simulator with first-class peripheral modeling would change the shape of ESP32 CI, but the independent verification is still to come.

### 🎯 Takeaway (Hợp)
If you are running ESP32 or ESP32-S3 CI today on Wokwi, QEMU, or the ESP-IDF host build, Cirkit's in-browser Rust/WebAssembly simulator is the one to clone and run against your own peripheral traces — the deliverable is not the AI agent but whether an unmodified firmware image you already trust produces the same register sequence under this emulator as it does on hardware. The experiment answers the current-draw part cleanly, and the endurance half remains open-ended but with a 2.16-million-frame data point and no permanent damage observed yet.

### 🔬 Details (Phân)
The current numbers are the specific contribution. Running the full emulator-plus-display at 30 FPS, the whole system averages about 115 mA, which with the 400 mAh battery works out to roughly 3.5 hours of untethered operation. Pausing display updates drops that to about 90 mA, and running the greyscale frame calculations without actually driving the panel brings it to 107.6 mA. The display itself is therefore responsible for approximately 7.4 mA — a number the Hackaday write-up calls "negligible" in the system-level sense, since the ESP32-S3 and the emulator compute dominate the budget by more than ten to one. For an engineer sizing a battery for an interactive e-paper device, the practical implication is that pushing refresh rate costs very little display power until the panel itself starts to fail.

That failure is the second half of the piece. Waveshare's datasheet quotes a typical panel life of 1,000,000 updates. At 30 FPS with full refreshes, that budget is consumed in roughly 9.3 hours — a number small enough that any "always-on" use case is out of scope. The experiment ran a 2.16-million-frame endurance test, past twice the typical rating, and observed some ghosting that was cleared by subsequent refreshes, with no permanent damage detected. That does not disprove the 1-million-cycle rating in the general case — panels can vary batch to batch and the detection method here is visual — but it does establish that this specific panel at this specific refresh profile exceeded its typical rating by a factor of two before any irreversible degradation showed up. The Hackaday piece is also explicit that Waveshare recommends against high-FPS use and that warranty will not cover damage caused by it, which is the operational constraint any product-grade adaptation of this pattern needs to respect.

The engineering surface the project exercises is modest — a Waveshare ESP32-S3 e-paper board, a Game Boy emulator ported to it, a frame rate chosen to stress the display — but the measurement discipline is the useful part. The split of current between "panel updating", "frame calculations only", and "no display, no compute" is the right way to size any interactive-display power budget, and the number this gives for the e-paper panel itself (7.4 mA on this board, this driver, this duty cycle) is a reusable anchor. The limit of the piece is that there is no cycle count on the microcontroller side, no spectral analysis of the ghosting, and no comparison against another panel vendor, so the data point is specific to the Waveshare ESP32-S3 e-paper board rather than to e-paper in general.

### 🎯 Takeaway (Hợp)
If you are planning an interactive e-paper device, size the battery to the compute cost (around 100 mA on an ESP32-S3-class MCU running an active loop) and treat the display current as noise — the 7.4 mA figure here is the anchor. Nếu bạn muốn chạy e-paper ở high FPS trong consumer product, nhớ rằng Waveshare tính rating lifetime theo cycle, và 2.16 triệu frame mới chỉ là một board — không thay đổi cho mọi batch. Keep high-FPS modes behind a user opt-in or a short-duration animation, both to stay inside typical panel ratings and to keep warranty coverage.
