### 🔭 Overview (Tổng)
On 29 October 2026 Matt Martin, Geertjan Wielenga, and Tim Cox published "From Spreadsheets to DuckLake: A Data Engineer's Road to DuckDB" on the DuckDB blog. The post is framed as a career narrative — Excel and VBA, then Teradata and BigQuery, then Spark, then DuckDB — but underneath it carries the clearest head-to-head yet between the Iceberg metadata model and DuckLake, which stores catalog state in a SQL database rather than in nested metadata JSON and manifest files. It also demonstrates three DuckDB v2.0 features that make the DuckLake story operational: dynamic `ATTACH` paths resolved from environment variables, asynchronous S3 I/O that the post benchmarks against the previous blocking path, and the Quack remote protocol that exposes a DuckDB instance over HTTP without AWS credentials on the client. The piece earns a digest slot because those three features and the metadata contrast together describe the shape a DuckDB-plus-DuckLake deployment is converging on, not just a one-off ergonomic win.

### 🔬 Details (Phân)
The metadata contrast is the structural claim. Iceberg stores a growing chain of metadata JSON, manifest lists, and manifests on object storage, and query planning has to read and reconcile them; the post reports catalog operations taking seconds in the author's workload. DuckLake instead keeps the catalog in a SQL database — attached to DuckDB as a database file — and the author reports catalog operations under one millisecond on the same shape of workload. That is a lived-experience number, not a benchmark, but it names the mechanism correctly: the Iceberg manifest chain forces metadata reads at plan time, and a SQL catalog collapses them to an indexed lookup. The post also shows DuckDB's Iceberg extension attaching an AWS Glue catalog in three statements — `INSTALL iceberg`, `LOAD iceberg`, and `ATTACH ... (TYPE iceberg, ENDPOINT_TYPE glue)` — against the 20-plus-line Spark setup the author previously maintained, which is a different kind of win: Iceberg stays reachable even when the primary store becomes DuckLake.

The v2.0 features are the operational substance. Dynamic `ATTACH` lets the catalog path be computed from a SQL expression — `getenv('AWS_ACCOUNT_ID')` in the post — rather than a literal string, which collapses the "render a config file and restart" step most warehouses carry. Asynchronous I/O is the one with an explicit number: the author benchmarks reads of 1,000 and 10,000 Parquet files from S3 against the previous blocking path and reports 67% to 70% less wall time, with no code changes. The Quack remote protocol exposes a running DuckDB over HTTP so that a client only needs an address and a token — no AWS credentials — to issue queries; the author has already served a DuckLake from an EC2 instance via Quack and built a DuckDB-Wasm dashboard on top of it, with the dashboard's Wasm build still on v1.5 pending the v2.0 Wasm update.

The honest limits of the piece are two. First, the DuckLake-versus-Iceberg metadata numbers are the author's single workload rather than a public benchmark harness; the mechanism is sound but the magnitudes are not generalisable. Second, the Quack server and the DuckLake catalog are both single-process DuckDB instances, so an organisation moving a warehouse off Iceberg plus Glue onto DuckLake plus Quack is swapping a managed catalog surface for one it operates itself. The post is explicit that the current path for a team is to use the Iceberg extension to keep the Glue catalog reachable while a DuckLake side runs in parallel, rather than a one-step cutover.

### 🎯 Takeaway (Hợp)
If you are running an Iceberg warehouse on Glue today and metadata-read latency is already visible in query planning, the DuckLake pattern — SQL-database catalog, attached to DuckDB, served via Quack to downstream clients — is worth standing up in a staging workspace against the same tables. Measure your own metadata-op latency before and after, because the post's "seconds versus under one millisecond" is one engineer's workload, not a benchmark. Chú ý rằng Quack server và DuckLake catalog hiện là single-process; nếu bạn cần HA cho warehouse serving, cần tự chuẩn bị proxy/replica thay vì trông cậy vào managed catalog.

### 💡 Example
```python
# DuckDB 2.0 — dynamic ATTACH + async S3 + DuckLake catalog in SQL.
# From "From Spreadsheets to DuckLake" (duckdb.org, 29/10/2026).

import duckdb

con = duckdb.connect()

# S3 credentials from the environment, no hard-coded path.
con.execute("""
    CREATE SECRET s3_creds (
        TYPE s3,
        PROVIDER credential_chain
    );
""")

# Dynamic ATTACH: catalog location computed at run time (v2.0).
con.execute("""
    ATTACH 'ducklake:s3://warehouse-' || getenv('AWS_ACCOUNT_ID') || '/catalog.db'
    AS wh (DATA_PATH 's3://warehouse-' || getenv('AWS_ACCOUNT_ID') || '/data/');
""")

# Async S3 reads (v2.0): same code, 67–70% less wall time for 1k–10k files.
con.sql("""
    SELECT month, SUM(amount) AS spend
    FROM read_json('s3://audit-logs/2026/*.json')
    GROUP BY ALL
""").show()
```

### 🔭 Overview (Tổng)
On 29 October 2026 Omnia Ibrahim posted the Apache Kafka 4.4.0 release announcement on the Confluent blog, covering 25 KIPs and 963 commits since 4.3.0, with 151 human contributors and 8 AI assistants credited. The release is substantial on three axes — Streams finally gets transactional state stores under exactly-once processing, the share-groups surface added in recent releases picks up a dead-letter queue, and the broker side cleans up a long-standing storage-directory version rule and adds controller unregistration — rather than one headline feature. For teams running Kafka in production the practical shape of 4.4.0 is: Streams operators get a durability win that removes state-store rebuilds on error, cluster administrators get a cleaner KRaft lifecycle, and client authors get an async bootstrap option that previously forced a synchronous DNS wait at connection time.

### 🔬 Details (Phân)
On the Streams side, KIP-892 is the headline. Transactional state stores (`enable.transactional.statestores`, default false) mean that under exactly-once processing, the store is no longer wiped and rebuilt from the changelog on error — the store participates in the transaction. KIP-1340 adds `ValueJoinerWithStreamAndMappedKey` and new KStream-GlobalKTable join overloads, deprecating the older `ValueJoinerWithKey`-based overloads; KIP-1331 lets brokers store a topology description for a Streams group; and KIP-1357 adds broker-side custom task assignors. KIP-1356 adds four IQv2 query types that return record headers from headers-aware state stores. For share groups — Kafka's new consumer model — KIP-1191 adds a dead-letter queue, taking effect once `share.version` is upgraded to 2, and KIP-1323 lets `kafka-share-groups.sh` initialise share-group offsets from a file (including from a consumer group's committed offsets), which is the migration primitive most teams need.

The KRaft and broker lane carries the more operationally sensitive changes. KIP-1170 unifies cluster metadata bootstrapping and now requires that a broker be the same version as or newer than the `kafka-storage` tool that formatted its directory — a rule that lands cleanly on new clusters but can trip rolling-upgrade paths that reused an older storage format. KIP-1312 adds first-class controller unregistration through `kafka-cluster.sh unregister-controller`, a `--unregister` flag on `kafka-metadata-quorum.sh remove-controller`, and `Admin#unregisterController`, with error code 136 (`CONTROLLER_ID_NOT_REGISTERED`) and metadata version 4.4-IV2 required. KIP-1241 adds `remote.copy.lag.bytes` and `remote.copy.lag.ms`, closing a gap in tiered storage observability where operators previously had no first-class way to see how far behind the remote copy was running. KIP-1242 adds cluster and node information in connection setup so misrouted connections surface at the client, and KIP-1291 exposes additional Linux I/O metrics via JMX.

Client and admin surface changes are the ones to plan for in client-library upgrades. KIP-909 adds `bootstrap.resolve.timeout.ms`, keeping synchronous bootstrap resolution at the default of 0 but allowing async resolution with a positive value that surfaces failures later as `BootstrapResolutionException`; the post flags that Streams and Connect do not yet support this. KIP-1319 brings TxnOffsetCommit v6 in line with OffsetCommit, using topic IDs instead of names and renaming `GenerationId` to `GenerationIdOrMemberEpoch`. KIP-1321 adds a headers-aware `StreamPartitioner.partitions(...)` overload, deprecating the existing method. On the Connect side, KIP-1209 adds `internal.topics.automatic.creation.enable` and a `connect-internal-topics.sh` tool, so operators who disable automatic creation have a supported way to pre-provision. Deprecations are also broad: `broker.id` broker config, `ClientQuotaCallback#updateClusterMetadata` (removed in 5.0), the remaining Yammer-based classic-group metrics, and `kafka-broker-api-versions.sh` in favour of `kafka-cluster.sh api-versions`.

### 🎯 Takeaway (Hợp)
For Streams operators, 4.4.0's single biggest practical change is KIP-892 — flip `enable.transactional.statestores` on in staging, measure recovery behaviour on an induced failure, and remove the state-store rebuild step from the runbook if the numbers look right. Trước khi upgrade, kiểm tra storage-directory version — nếu format được tạo bằng `kafka-storage` cũ hơn broker, KIP-1170 sẽ reject và việc rolling upgrade bị kẹt giữa chừng. Client library teams should treat KIP-909's async bootstrap and KIP-1319's TxnOffsetCommit v6 as the two upgrade coordinates that need matching library versions downstream.

## 3. Databricks Makes Real-Time Mode for Spark Declarative Pipelines Generally Available With Millisecond Latency and a 92% Advantage Claim Over Apache Flink

### 🔭 Overview (Tổng)
On 29 October 2026 Jerry Peng, Abhay Bothra, Sudhanva Huruli, Navneeth Nair, Anant Pingle, and Murali Talluri announced on the Databricks blog that Real-Time Mode (RTM) for Spark Declarative Pipelines (SDP) is now generally available. RTM is an evolution of Structured Streaming where all query stages run at once and data is passed between stages as it is produced, which is the architectural shift that lets Databricks claim "end-to-end latencies in the millisecond range" rather than the micro-batch floor Structured Streaming has carried for years. The release matters not just as a latency win but as a positioning move: the post pitches RTM-on-SDP as a single framework that covers batch, ETL, and low-latency streaming, with the explicit framing that teams no longer need a separate engine like Apache Flink to hit sub-second targets.

### 🔬 Details (Phân)
The latency and throughput claims are the specific numbers to anchor on. The post describes end-to-end latencies in the millisecond range and cites earlier work that RTM can be up to 100x faster than micro-batch processing. The Databricks Feature Store runs on top of RTM and is reported at p99 latency of 200 ms from Kafka to the online store, which is the deployed-system number worth taking literally. The headline comparison — up to 92% faster than Apache Flink on customer feature-computation workloads — is more specific than the usual engine-versus-engine claim because the post links a GitHub repository with the datasets and queries used, which is the right standard for anyone wanting to verify the number against their own topology.

The pipeline-authoring surface stays declarative. RTM is enabled by setting pipeline mode to `continuous` and the config `spark.databricks.streaming.realTimeMode.enabled` to true, then defining a sink with `dp.create_sink()` and wiring a flow with the `@dp.update_flow` decorator (with `pipelines.trigger` set to `"RealTime"` and `target` pointing to the sink). Writes to operational stores — the post names Lakebase, Redis, and other OLTP targets — go through a ForEach sink that implements the classic `open`, `process`, `close` triad, which is the point at which an application developer actually has to think about per-partition writer lifecycle. The piece is explicit that RTM retains SDP's declarative primitives — dependency resolution, incremental processing, orchestration, failure recovery, and data quality enforcement — so an existing SDP pipeline is not re-authored to go real-time, only re-configured.

The limits sit in two places. First, the GA scope is defined around serverless SDP; the post frames serverless as the main path, with versionless upgrades and low-downtime maintenance as RTM-specific operational properties, and does not detail the self-managed-SDP path. Second, two capabilities are explicitly upcoming rather than available: bin-packing multiple RTM flows into one pipeline with auto-tuned partitions, and a native Lakebase sink with batching, retries, and UC-managed authentication. The practical read is that the Lakebase path works today via the generic ForEach sink but will see a first-class optimisation later. For teams running existing Flink pipelines, the post gives a benchmark harness to verify the 92% claim against their own workload rather than taking the single number at face value.

### 🎯 Takeaway (Hợp)
If you have a Flink pipeline feeding an online store with sub-second-latency requirements and your lakehouse is on Databricks, this release lets you reconsolidate under SDP without accepting micro-batch latency — the deliverable is a staging pilot where you port one of your feature-computation jobs, run it against the datasets Databricks ships in its linked repository, and measure against the 92% claim on your own topology. Nếu stack bạn đã sẵn Lakebase, viết ForEach sink thủ công bây giờ, và khi native Lakebase sink ra mắt thì swap in để lấy UC auth và retry built-in. Keep self-managed SDP evaluations separate — the GA framing is serverless-first, so expect the production surface and the versionless-upgrade promise to be tighter there.

### 💡 Example
```python
# Real-Time Mode on Spark Declarative Pipelines (serverless, GA).
# From Databricks blog, 29/10/2026.
# Config:
#   pipelines.realTimeMode.enabled = true
#   pipeline mode = continuous

import dp

# 1. Define a sink: in this release the generic path is ForEach.
class RedisForeachWriter:
    def open(self, partition_id, epoch_id):
        self.conn = redis_pool.connect()
        return True
    def process(self, row):
        self.conn.set(row.feature_key, row.feature_value)
    def close(self, error):
        self.conn.close()

foreach_sink = dp.create_sink(
    name="feature_store_online",
    writer=RedisForeachWriter(),
)

# 2. Wire a flow in RealTime trigger mode.
@dp.update_flow(
    target=foreach_sink,
    pipelines={"trigger": "RealTime"},
)
def kafka_to_online_store():
    return (
        spark.readStream.format("kafka")
             .option("subscribe", "features.events")
             .load()
             .selectExpr("CAST(key AS STRING) AS feature_key",
                         "CAST(value AS STRING) AS feature_value")
    )

# Databricks Feature Store on RTM: reported p99 200 ms Kafka -> online store.
# Benchmark harness (vs Flink, up to 92% faster) linked from the post.
```

### 🔭 Overview (Tổng)
On 28 October 2026 the Zephyr Project announced Zephyr RTOS 4.5, credited to release managers Henrik Brix Andersen and Tom Burdick and contributions from over 1,200 individuals — a new record according to the post. The release reaches two new silicon architectures that matter outside the hobbyist ESP32/STM32 corridor: Infineon's TriCore (the Aurix family that drives much of the automotive MCU market) and Qualcomm's Hexagon DSP (found in many Qualcomm SoCs). Alongside the architecture work it ships an experimental multimedia subsystem called `mpipe` with a GStreamer-style source/transform/sink model, a networking stack upgrade that adds QUIC, HTTP/3, SSH, and TCP SACK by default, SPDX 3.0 output for the EU CRA reporting obligations that have been in force since September, and measurable throughput and kernel-performance improvements over 4.4.

### 🔬 Details (Phân)
The architecture additions are the "shape of the ecosystem" change. TriCore brings Zephyr into AURIX territory, which is where ISO 26262 automotive projects live, and Hexagon makes Zephyr a viable guest on Qualcomm's DSP cores for workloads that previously stayed on vendor RTOSes. Both are shipped with QEMU targets (`qemu_tc3x`, `qemu_tc4x`, `qemu_hexagon`) so a developer can boot either architecture without silicon in hand, with the honest caveat that the QEMU builds and toolchains for both are not yet in the Zephyr SDK — they ship as separate downloads for 4.5. On the drivers side, six new driver classes land (buzzer, clock monitor, DALI, LIN, MUX, and Pulse IO), and 178 new boards plus 29 new shields are added, with about 80 of those boards being vendor dev kits.

The `mpipe` subsystem is the one worth kicking the tyres on. It models multimedia as source, transform, and sink elements with caps negotiation, buffer pools, and a `tee` for branching, which is close enough to a GStreamer mental model that engineers moving down from Linux-class devices will recognise it. The post's demo uses YOLOX-nano object detection with TensorFlow Lite Micro — the practical point is that a Zephyr device can now assemble a camera-to-inference-to-display path without hand-rolled plumbing. Video and display elements were still under review at the post's publish time, so the subsystem is experimental in both label and status; teams planning around it should expect its API to settle in a point release.

Networking lifts and security hardening are the places where 4.5 pays off for already-deployed Zephyr fleets. The zperf loopback benchmark measures up to 21% higher TCP throughput and up to 12% higher UDP throughput against 4.4, with TCP SACK enabled by default. HTTP/3 lands in the HTTP server on top of QUIC transport, and an SSH server and client both ship; IPv4 forwarding and NAT, DHCPv6 prefix delegation, and IPv6 router advertisements fill in the IP-stack gaps that previously required Linux. On an STM32F412 running Thread-Metric, kernel-exercising tests are 3–15% faster than 4.4, with semaphore give/take over 15% faster and message-queue round trips nearly 14% faster. For CRA alignment, `west spdx` adds opt-in SPDX 3.0 support (2.3 remains default), the hardening tool maps checks to CWEs and can fail CI builds, and a FIDO2 authenticator subsystem supporting USB and BLE lets Zephyr targets act as security keys. The one disruptive breaking change to watch: the ring-buffer claim/finish API is replaced by `ring_buf_put_ptr()` and `ring_buf_get_ptr()`, and the CMake `flash` and `debug` targets are removed in favour of their `west` equivalents.

### 🎯 Takeaway (Hợp)
For teams running an existing Zephyr fleet, 4.5 is a straight upgrade on the networking and performance axes — expect modest kernel-latency improvements on the same silicon, and plan to adopt QUIC/HTTP/3 only after retiring whatever home-grown transport you have in place. Nếu dự án của bạn phải tuân CRA, SPDX 3.0 opt-in trong `west spdx` cộng với hardening tool mới chính là phần cần kiểm tra sớm chứ không phải TriCore hay Hexagon. Treat `mpipe` as experimental: build a prototype on a dev board, but hold the production API decision until the video and display elements merge in a point release.

The piece earns a digest slot because it is the first large third-party showcase of what engineers are building on the Arduino UNO Q, which the post describes as a "dual-brain" board aimed at edge AI workloads, with Edge Impulse and the Arduino App Lab as the software stack. The competition drew 4,028 registrants, 1,202 hardware applications, and 153 final submissions — numbers worth noting because they put UNO Q adoption on the same scale as past high-profile Arduino launches rather than a boutique one. For a daily digest the useful part is not the leaderboard itself but the specific engineering choices the winning projects made, which read as early signal on which patterns UNO Q is good for and which it still has to prove.

### 🔬 Details (Phân)
Three winners show the on-device inference pattern that the UNO Q plus Edge Impulse combination is targeting. The Best in Show entry, Jorge Eldis González's Edge-AI Spectrophotometer, pairs a UNO Q with a SparkFun AS7343 Triad Spectroscopy Sensor and runs on-device inference to flag deviations from known spectral baselines — a workload where the latency and privacy case for not round-tripping to a cloud model is unambiguous. Best in Gaming went to Kevin Loeffler's RCT IRL, a wearable in a fanny pack that records ride movement through a SparkFun 9-DoF IMU and runs three Edge Impulse models that output Excitement, Intensity, and Nausea scores — a classic multi-model-on-one-microcontroller shape. Best Social Impact, KOCHONI Biaou David Barthélémy's Smart Water Guardian AI, monitors temperature, pH, turbidity, and dissolved-solids levels in real time to detect anomalies, which is the kind of multi-sensor-plus-anomaly-detection workload that moved to microcontrollers only once edge ML frameworks became practical.

Two other winners are useful for a different reason — they show where UNO Q's dual-brain architecture is being used for more than inference. Coders Cafe's Smart Coop 2.0 (Best in Home Automation) handles feed scheduling, heating control, and local AI-based detection of eggs and predators (the post names coyotes and foxes), which is a mixed real-time-control-plus-vision workload where a dual-brain board earns its keep. Mohammed Akramuddin's Curie robot (Best in Robotics) is a desktop assistant with OLED facial expressions, aimed in part at users with ADHD, that connects to external APIs such as Groq for the heavier conversational layer — so the pattern there is edge sensing and interaction on the UNO Q with a cloud LLM behind it. Pasquale887's HaloSense V1 (Best in Industrial IoT) is more hardware-oriented: a haptic feedback headset with 13 vibration motors conveying information from sensors attached to the UNO Q, which exercises the board's I/O surface more than its inference side.

The honest limits of the piece as a daily-digest item are two. The post does not list UNO Q board specifications — no processor, memory, or I/O counts — so a reader is left to look those up separately, and no prize amounts or hardware deliverables are described, so this is a project showcase rather than a release. The engineering signal is the project list itself, not a benchmark or a feature announcement; the useful read for a team evaluating UNO Q is that Edge Impulse plus the Arduino App Lab is a credible stack for multi-sensor, on-device inference workloads at the hobbyist-to-small-prototype scale, with 153 shipped builds as the proof point.

### 🎯 Takeaway (Hợp)
If you are deciding between the UNO Q and an ESP32-S3-plus-TensorFlow-Lite Micro stack for an edge AI prototype, treat this competition as a project corpus rather than a benchmark — the Edge-AI Spectrophotometer and the three-model wearable are the two shapes most worth cloning to compare DX on your own workload. Với team đang dùng Edge Impulse sẵn, UNO Q bắt đầu có đủ dự án tham khảo để không phải pioneer the integration path. Hold off on taking the board's "dual-brain" positioning at face value until the post or a successor piece gives processor-level numbers; today the signal is adoption, not silicon.
