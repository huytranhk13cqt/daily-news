### 🔭 Overview (Tổng)
On 30 October 2026 Priyanka Chaudhary and David Victoria of AWS published a feature post on the Big Data Blog introducing "designations" in Amazon SageMaker Unified Studio. Designations are named permission sets, defined by a domain administrator and attached to project members, that control what each member can do inside a project. The permission language is Cedar, the permission categories are Catalog, Project, Subscriptions, Connections, and Notebooks, and the piece names two managed designations — Owner and Contributor — plus a path to create your own. The feature answers a specific and long-running SageMaker Unified Studio problem: before designations, teams either gave everyone the same broad project role or spun up a separate project per persona, which fragmented data and added provisioning overhead.

### 🔬 Details (Phân)
The governance model is two-layer. IAM evaluates the API call at the AWS boundary and the designation evaluates whether the project member can perform the specific action; both must allow and an IAM deny wins. The authorizing IAM actions for administrators are `datazone:CreateDesignation`, `UpdateDesignation`, `DeleteDesignation`, and `datazone:CreateProjectMembership` for assignments. The APIs themselves are `CreateDesignation`, `CreateProjectMembership`, and `UpdateProjectMembership`, and designations are supported as CloudFormation resources with an opt-in `--deletion-protection` property. Members can be IAM roles, IAM users, or IAM Identity Center users and groups; a user with both a direct designation and a group designation gets the union of their permissions. A member with no designation has no permissions in the project, which is the intended default.

The two managed designations split along membership-management lines. Owner has full control including membership management. Contributor has full access except membership management and project deletion. Both are read-only, so a project that needs a different split uses user-created designations. The post calls out one dangerous permission — Manage Membership — because a holder can assign designations that carry more permissions than their own; the guidance is to grant it sparingly. The example Cedar policy in the post defines a "Data Engineer" designation that permits `DataZone::Action::"CreateDataSource"`, `UpdateDataSource`, and `CreateAsset`, and the companion CLI call attaches it to a project member via `aws datazone create-project-membership`. Deletions are gated by an `allow-delete` property that is off by default; when enabled, deleting an in-use designation leaves affected members in the project but strips their permissions until a new designation is assigned.

The honest limits are two. First, this is a feature of SageMaker Unified Studio projects, not a general-purpose data governance layer — teams whose workloads sit outside Unified Studio projects won't get the benefit. Second, the Swiss Life Germany customer quote in the post is a usage statement rather than a benchmark, so the "add no infrastructure or cost beyond SageMaker Unified Studio itself" claim is the practical note worth repeating. Changes to a designation's permissions apply immediately to all assigned members in all projects — this is powerful for revocation but means a bad edit lands fast; CloudTrail is the audit path called out.

### 🎯 Takeaway (Hợp)
If you already run Unified Studio and have been workaround-managing permissions by splitting personas across projects, consolidate: one project per data domain, Cedar designations per persona, Manage Membership kept narrow, and `--deletion-protection` on. Dùng CloudFormation để quản version của các designation thay vì tạo tay qua portal — immediate-propagation semantics vừa là tính năng vừa là rủi ro, nên bạn muốn git-history và review trước khi apply. Keep the two managed designations (Owner, Contributor) for small projects where the split is clear; user-created ones carry a maintenance burden.

### 💡 Example
```bash
# AWS SageMaker Unified Studio — Designations, 30/10/2026.
# 1) Define a Data Engineer designation via Cedar policy.

aws datazone create-designation \
  --domain-identifier "dzd_example1234" \
  --name "Data Engineer" \
  --description "Runs data source and asset creation tasks" \
  --policy 'permit(principal, action in [
      DataZone::Action::"CreateDataSource",
      DataZone::Action::"UpdateDataSource",
      DataZone::Action::"CreateAsset"
    ], resource);' \
  --deletion-protection

# 2) Attach it to a project member (IAM Identity Center user).

aws datazone create-project-membership \
  --domain-identifier "dzd_example1234" \
  --project-identifier "proj_example5678" \
  --member '{"userIdentifier": "u-abc123def456"}' \
  --designation "USER_CREATED_DESIGNATION" \
  --user-created-designation-id "123456789"

# IAM still evaluates the call at the API boundary (e.g. datazone:CreateListingChangeSet
# requires the Manage Asset Publishing permission in the designation itself).
```

### 🔭 Overview (Tổng)
On 29 October 2026 Piyush Singh and Vijay Raja of Databricks posted "Smarter cost controls for serverless", a product post that packages three governance layers for serverless compute: attribute, control access, and limit spend. The framing responds to a stated 3x growth in Databricks' own serverless usage in the past year, and the three layers map to specific features at distinct availability stages — Serverless Compute tags are Beta, Serverless Compute Access Controls are generally available, and per-compute rate limits are Beta behind preview settings. The post is practical rather than architectural: it names the system table, the IAM permission levels, the S/M/L/XL sizes, and the suggested rollout order.

### 🔬 Details (Phân)
Attribution is anchored on tags that flow into `system.billing.usage` with a new `serverless_compute_id` column, giving a per-compute-object break-down of DBUs, available across AWS, Azure, and Google Cloud; account-console cost dashboards render the data without SQL. Access control is a GA feature with two permission levels — "Can Use" and "Can Manage" — on the two default compute objects every workspace gets: Default Serverless Interactive Compute (notebooks and Databricks Connect) and Default Serverless Automated Compute (jobs and Spark Declarative Pipelines). The default on both is "All Users: Can Use", so enabling the feature changes nothing until an admin removes the broad group and grants specific ones; the UI effect is that users outside a group see Serverless grayed out in the notebook compute selector, and running workloads are not interrupted.

Rate limits are the Beta piece and the one with the most operational nuance. They sit on individual compute objects and come in four sizes — S, M, L, XL — enabled through Databricks preview settings. For notebook and job workloads a size is an autoscaling ceiling, not a fixed cluster size, which means a job that only needs Medium but is assigned XL is allocated Medium. The pattern the post pushes is per-team custom compute objects with their own limits; a group-wide shared budget for interactive compute is called out as "coming soon", with a per-session maximum as the underlying guardrail. Budgets and alerts are GA on top of all of this: the account console sends email alerts when serverless spend crosses a threshold, and a SQL alert on prior-day spend can close the loop within hours.

The honest limits are two. First, the post does not publish numeric dollar values for S/M/L/XL — sizing is left to teams to calibrate against their own workloads. Second, three features sit at different maturity levels and the rate-limit piece is behind a preview setting, so the full three-layer story requires one Beta flag today. The suggested setup order makes those caveats concrete: tag serverless compute, build cost dashboards on `system.billing.usage` and add a budget alert, audit current serverless users and spend, decide which groups get interactive versus automated access, and only then turn on Serverless Compute Access Controls.

### 🎯 Takeaway (Hợp)
If your Databricks bill shoots up more because of serverless than any other line item, start with tagging and `system.billing.usage` to see where it goes before touching anything else — attribution first, control later. Khi bật Serverless Compute Access Controls thì workloads đang chạy không bị kill nhưng user ngoài group sẽ không khởi tạo được compute mới, nên đổi cấu hình vào cửa sổ bảo trì chứ không phải giờ cao điểm. Hold off on rate limits until you have a baseline from tags; the Beta flag plus S/M/L/XL ceilings is a lot of knobs to turn without data.

### 💡 Example
```sql
-- Databricks serverless — attribute first (Beta tags + system.billing.usage).
-- Post reports 3x YoY serverless growth; dashboard before you add controls.

-- 1. Tag a serverless compute object (Beta) via UI/API; every DBU inherits it.
-- 2. Read spend by owner, product, and tag.

SELECT
  usage_metadata.serverless_compute_id   AS compute_id,
  usage_metadata.custom_tags.team        AS team,
  billing_origin_product                 AS product,
  SUM(usage_quantity)                    AS dbus,
  SUM(usage_quantity * list_price)       AS list_cost_usd
FROM system.billing.usage
WHERE usage_date >= current_date - INTERVAL 7 DAYS
  AND usage_metadata.serverless_compute_id IS NOT NULL
GROUP BY compute_id, team, product
ORDER BY list_cost_usd DESC;

-- 3. Only after this baseline:
--    - Serverless Compute Access Controls (GA): Can Use / Can Manage per group.
--    - Rate limits S/M/L/XL (Beta, enable via preview settings).
--    - Budgets + email alerts (GA) in the account console.
```

### 🔭 Overview (Tổng)
On 29 October 2026 Debashis Das of CNX Software covered the BeagleBoard.org introduction of the BeagleConnect QuadESC, a four-channel brushless DC motor controller carrier board paired with the new BeagleConnect Torque system-on-module. The pair matters because it is BeagleBoard's first open-hardware motor-control platform with a built-in neural-network accelerator — the Torque SoM uses Texas Instruments' AM13E23019, an Arm Cortex-M33 at 200 MHz with an FPU, a trigonometric math unit (TMU), TI's TinyEngine NN accelerator, three 12-bit ADCs, and motor-control PWM. The ecosystem shape — KiCad hardware designs, firmware sources, and documentation on GitHub (embedconsult/quadesc), with Zephyr RTOS and OpenOCD support planned — is the signal that distinguishes this from a vendor evaluation kit.

### 🔬 Details (Phân)
The Torque SoM is a 25.4 × 38.1 mm four-layer board with 128 KB SRAM and 512 KB flash alongside the AM13E23019. Connectivity goes out through a CAN FD port backed by a TCAN844 transceiver and the usual UART/SPI/I²C set, plus a Qwiic connector for sensors. Security is at the SoC level: secure boot, secure debug, secure firmware updates, and crypto acceleration. The module expects a regulated 5V carrier supply (not raw battery voltage), a separate analog reference (VAA) for the ADCs, and a 5V rail for CAN. Developers get an underside 100-pad LGA interface and two 12-pin expansion rows on the carrier for building their own boards against the same SoM.

The QuadESC carrier itself is 60 × 48 mm and accepts 3S–6S batteries (9–25.2V), with a 32V board design maximum that the article explicitly flags as not an operating supply. Motor drive is built on four TI DRV8323SRTAR gate drivers plus twelve CSD88599Q5DC half-bridge devices — three per motor — and a dedicated PWM module per channel. The design targets 40A continuous and 70A burst per motor, which the post notes are unverified figures with unspecified burst duration and real capability dependent on cooling, ambient, and load profile. Sensing is thorough: twelve low-side phase-current channels, twelve phase-voltage channels, four NTC temperature sensors, and battery-voltage monitoring, with power from a TPS54360B buck for logic and a TPS7A4701 analog regulator for the sensing chain. Interfaces include an eight-pin flight-controller header carrying four DShot routes plus telemetry, current reporting, battery voltage, and ground; motor outputs on J2–J5; battery solder terminals on J1; a 10-pin ARM/JTAG header for SWD; and a two-pin buzzer port.

The practical caveat is the software stack: the board ships without motor-control firmware, so a developer writes field-oriented control (FOC), gate-driver setup, current sensing, DShot decoding, telemetry, and fault handling themselves. Flashing is through TI's ROM bootloader over CAN, I²C, or UART; SWD debugging uses an XDS110 and Code Composer Studio; and TI's AM13E2X SDK (drivers, examples, SysConfig, FOC tools) is the fastest starting point. Zephyr RTOS and OpenOCD are called out as planned but not confirmed. Pricing and availability are not announced in the post.

### 🎯 Takeaway (Hợp)
If you are building a drone, a four-wheel differential robot, or any BLDC-heavy project and want KiCad-level control over the hardware, QuadESC is the open-stack option now and worth prototyping against the TI SDK with modest expectations on the 40A/70A ceilings — those numbers are design targets, not datasheet-grade specs. Teams betting on Zephyr for an eventual production path should hold off until the Zephyr port lands, since bringing it up on bare AM13E23019 without upstream BSP support is a meaningful investment. Về mặt hệ sinh thái, Torque SoM với TinyEngine on-die mở ra khả năng tích hợp inference phát hiện bất thường mô-tơ ngay trên controller, chứ không phải chỉ chạy FOC — đó mới là lý do board này đáng chú ý hơn một ESC quad-channel thông thường.
