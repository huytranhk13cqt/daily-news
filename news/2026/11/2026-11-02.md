## 1. AWS SageMaker Unified Studio Ships Designations: Cedar-Policy Permission Sets at the Project Boundary, Stacked on IAM at the API Boundary

### 🔭 Overview (Tổng)
On 30 October 2026 Priyanka Chaudhary and David Victoria of AWS published a walk-through of Designations in Amazon SageMaker Unified Studio, a new named-permission-set construct for governing access inside a project. Designations are written in Cedar — the same policy language AWS uses in Verified Permissions and that Unified Studio already relies on for permission grants — and are assigned per project rather than per domain. The post is explicitly framed as a least-privilege reference: Designations are added on top of IAM, with every API call having to pass both the IAM check at the API boundary and the Designation check at the project boundary before it succeeds. For teams building shared analytics or ML workspaces, this is the piece of the model that was previously handled either by hand-written per-project policies or by very broad roles.

### 🔬 Details (Phân)
Mechanically the model has three moving parts. Members of a project can be IAM roles, IAM users, or IAM Identity Center users and groups, and when a user is a member both directly and through a group the union of permissions applies. AWS ships two managed Designations out of the box — `Owner`, which has full control including member management, and `Contributor`, which has full access except member management and project deletion — and custom Designations are authored as Cedar policies covering Catalog, Project, Subscriptions, Connections, and Notebooks groups. Deletion protection is on by default and controlled via a `--deletion-protection` flag, and changes to a Designation propagate immediately across every project it is assigned to, which is a useful blast-radius property for an admin pushing a tightening change but also means a loosening change needs the same discipline.

The API surface is the piece most relevant to anyone automating the model. The post names `datazone:CreateDesignation`, `UpdateDesignation`, `DeleteDesignation`, and `CreateProjectMembership` as the primary verbs, and gives a concrete example of mapping a DataZone-style action — `datazone:CreateListingChangeSet` — to a "Manage Asset Publishing" permission inside the Designation's Cedar policy. CloudFormation is supported, which pulls Designations into the usual IaC pipeline rather than making them a console-only operation. The combination of Cedar policy, project-level scope, IAM at the API boundary, and SCIM-provisioned IdC groups is the kind of plumbing that enterprise security teams usually want to see before they bless a shared analytics platform.

The honest limits are two. First, the examples in the post stay close to the managed Designations and the CLI create flow, so teams designing a full catalog of custom Designations will spend meaningful time with the Cedar language itself and with the exhaustive mapping of SageMaker/DataZone verbs to groupable permissions — those mappings matter for correctness and the post lists only a handful. Second, Designations govern the project boundary, so cross-project workflows (shared assets, publishing between projects) still rely on the existing subscription/listing model and the IAM boundary; Designations tighten the inside of a project rather than redesigning the sharing surface.

### 🎯 Takeaway (Hợp)
If your team already runs SageMaker Unified Studio with broad per-project roles, Designations are the right unit to migrate to — start by replacing custom roles with `Owner` and `Contributor` for the common case, then author one or two custom Designations for the roles your governance team actually names (data engineer, model reviewer, read-only analyst). Nên nhớ Designation không thay thế IAM: nó là lớp thứ hai, nên nếu IAM boundary vẫn mở rộng thì least privilege chưa thực sự đạt — rà soát IAM song song với rollout. Keep deletion protection on by default and treat `UpdateDesignation` as a change with wide blast radius; the propagation is immediate across every project the Designation is attached to.

### 🔭 Overview (Tổng)
On 30 October 2026 Databricks and SAP jointly announced an extension of their SAP Business Data Cloud (BDC) partnership. The core offerings — SAP Databricks (Databricks embedded inside SAP BDC) and SAP BDC Connect for Databricks — remain generally available, and the news is the layer being added on top: a new SAP Application Data Foundation that exposes SAP application data to SAP BDC engines across cloud and on-prem sources, and a stated commitment that data sharing between SAP and Databricks is zero-copy and bidirectional via OpenSharing. The flagship integration is a planned bidirectional link between Databricks Genie and SAP Joule, which would let an SAP user ask Joule a question that is answered by Genie on Lakehouse data without either side moving the data. The authors are Sanjay Chheda, Katie Cummiskey, Patrick Werns, Akram Chetibi, and Qi Su.

### 🔬 Details (Phân)
The architecture is a four-capability extension. Lakeflow is pitched as the ingestion and orchestration layer that lands SAP, IoT, CRM, and third-party data in Delta without replication; Unity Gateway is positioned as the governance and cost plane across agents, tools, models, and MCPs; Lakebase (Databricks' serverless Postgres) is the operational-database layer for SAP-adjacent apps and agents; and Unity Catalog is the governance surface that covers both SAP and non-SAP objects. The example flow the post uses is SAP ECC on-prem order history flowing into SAP Databricks and feeding a demand-forecasting model that reads SAP business semantics directly, with the model portable to the SAP cloud migration without rewriting against a new catalog.

The partnership shape is more concrete than most announcements of this kind. SAP Databricks and SAP BDC Connect for Databricks are available today; the Genie ↔ Joule bidirectional integration and the Lakeflow/Unity Gateway/Lakebase extensions onto SAP are explicitly labelled "coming" with no GA dates, which is useful honesty on the roadmap but limits what a buyer can design around this quarter. The customer evidence is SAF-Holland unifying more than 100 million customer, delivery, and material records with "5x faster analyses" and planning in minutes versus weeks — vendor-reported, so take as directional. Earlier named customers remain Adidas, Zalando, Mondi, and CAF.

The piece worth sitting with is the data-sharing contract. OpenSharing (the open subset of Delta Sharing) is the mechanism for the zero-copy claim, and bidirectional means SAP objects can be exposed to Databricks and Databricks objects can be exposed back to SAP's semantic surface. That changes the integration question from "which side is the system of record for this table" to "which side owns the model and which side owns the governance", because both sides can read without copying. The practical implication for a DE team is that the historical move-everything-into-the-lake approach becomes optional for SAP sources, which has real cost and lineage consequences.

### 🎯 Takeaway (Hợp)
If you run SAP alongside Databricks, the useful lift from this update is not the headline integration but the data-sharing contract — model your next SAP-touching pipeline as a zero-copy OpenShare instead of a DMS-landed Delta table and measure the latency and governance consequences on a real workload before committing. Nếu đội đã dùng BDC Connect for Databricks thì nên theo dõi hai mốc: Genie ↔ Joule GA và Lakebase trên SAP, vì đó là lúc operational apps/agents chạm được dữ liệu SAP mà không copy. Treat the SAF-Holland "5x faster" and "weeks to minutes" numbers as directional until you have your own measurements — vendor-reported customer metrics travel poorly across industries and data shapes.

| Field | Value |

| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `apache-kafka` · `kraft` · `kafka-streams` |
| ⚡ Impact | High |

### 🔭 Overview (Tổng)
On 29 October 2026 Omnia Ibrahim announced Apache Kafka 4.4.0 on the Confluent blog, covering a release that landed 25 KIPs across 963 commits since 4.3.0. The headline themes are broker and client ergonomics (KIP-909 for asynchronous bootstrap resolution, KIP-1312 for unregistering controllers), the ongoing topic-ID migration (KIP-1319 moves TxnOffsetCommit to v6), new share-group operational features (KIP-1191 dead-letter queues for share groups), and a cluster of Streams-side upgrades (KIP-892 transactional state stores, KIP-1357 broker-side custom task assignors). The release also tightens tiered-storage observability (KIP-1241 adds `remote.copy.lag.bytes` and `.lag.ms`), introduces a Connect-side internal-topics toggle (KIP-1209), and prepares a few deprecations for 5.0.

### 🔬 Details (Phân)
On the broker side the most impactful change is KIP-1319. TxnOffsetCommit v6 now identifies topics by UUID rather than by name, which closes a long-standing class of race conditions when a topic is deleted and re-created with the same name mid-transaction. The field previously called `GenerationId` becomes `GenerationIdOrMemberEpoch` to accommodate both classic and consumer-group protocol clients, and the server returns more granular errors — `GROUP_ID_NOT_FOUND`, `STALE_MEMBER_EPOCH`, and `UNKNOWN_TOPIC_ID` — which make transactional producer failure diagnosis materially cleaner. KIP-909 adds `bootstrap.resolve.timeout.ms` to the client: the default of 0 preserves today's synchronous DNS behaviour, and a positive value enables asynchronous bootstrap and surfaces failures as `BootstrapResolutionException`; Streams and Connect do not yet support the async path. KIP-1170 is the operational trap worth reading closely — storage directories formatted with `kafka-storage.sh` are no longer forward-compatible, so brokers must be at least at the formatter's version or they will refuse to start.

For Streams and share groups the changes are substantial. KIP-892 introduces transactional state stores: a Streams app can enable `enable.transactional.statestores` to commit its state atomically with its offsets, bounded by `statestore.uncommitted.max.bytes`, and interactive queries can run against a specified isolation level via `default.interactive.query.isolation.level`. KIP-1357 lets brokers host custom task assignors for Streams groups, which pushes more rebalance control into the broker without needing a side service. KIP-1191 adds dead-letter queues for share groups when `share.version=2`, with the familiar Connect-style configuration namespace — `errors.deadletterqueue.topic.name`, `.auto.create.topics.enable`, `.group.enable`, `.topic.name.prefix`, `.copy.record.enable`. KIP-1312 lets operators call `kafka-cluster.sh unregister-controller` and surfaces a new error 136, `CONTROLLER_ID_NOT_REGISTERED`, provided the metadata version is at 4.4-IV2.

The deprecation list is small but worth planning for. KIP-1232 deprecates `broker.id` (it survives but will go away in 5.0), KIP-1200 deprecates `ClientQuotaCallback#updateClusterMetadata` with a 5.0 removal, and KIP-1301 removes the remaining Yammer-based classic-group metrics in favour of the OpenTelemetry/Micrometer-friendly path. Connect gets `internal.topics.automatic.creation.enable` (default `true`) via KIP-1209 and a new `connect-internal-topics.sh` tool for pre-provisioning the config, offset, and status topics outside the worker lifecycle.

### 🎯 Takeaway (Hợp)
If you run transactional producers against Kafka, 4.4.0 is a release to adopt deliberately — KIP-1319's move to topic IDs on TxnOffsetCommit v6 is a correctness improvement for the delete-and-recreate failure mode, but it is also a wire-protocol change you want paired with a client bump. Nếu đội đang chạy Streams với stores lớn, bật `enable.transactional.statestores` cho một job thí điểm trước khi áp dụng rộng — gain chủ yếu ở semantic, overhead cần đo riêng. Hold on KIP-1312 and KIP-1170 for operators: `kafka-cluster.sh unregister-controller` is a useful tool for recovering from a stuck controller membership, and the storage-dir forward-compatibility rule is a legitimate rollback hazard that belongs in the upgrade runbook.

### 🔭 Overview (Tổng)
On 28 October 2026 the Zephyr Project tagged v4.5.0, a major release with support through 28 October 2027. New architecture support covers Infineon's TriCore family (the AURIX automotive microcontrollers) and Qualcomm's Hexagon DSP, each of which is a materially new target for Zephyr and widens the project's reach into automotive and signal-processing silicon that previously ran bespoke RTOSes. The release also brings a new experimental Multimedia Pipeline (`mpipe`) subsystem, a networking stack with first-class QUIC and HTTP/3 and an SSH server plus client, six new driver APIs, hardware-accelerated PSA Crypto on selected Silicon Labs, NXP, and STM32 parts, and SPDX 3 SBOM generation. The release page lists 178 new boards, 29 new shields, and 1,297 contributors.

### 🔬 Details (Phân)
The piece worth lifting first is `mpipe`. It is a GStreamer-inspired zero-copy pipeline of source, transform, and sink elements intended for audio and video on-device, which is the right architectural level for the next round of microcontroller-class ML and audio-processing workloads that bounce buffers between a sensor, a DSP, and an accelerator without wanting Linux. The subsystem is experimental in 4.5.0, so the API shape should be expected to shift, but the direction is clear enough that teams building a camera or microphone pipeline on Cortex-M + Hexagon or Cortex-M + a vendor NPU can start prototyping against it rather than against ad-hoc hand-rolled buffers.

The networking stack is the other heavy update. QUIC and HTTP/3 land in-tree, which means encrypted-by-default modern transport without having to pull in a separate TLS/QUIC library and reconcile it with the Zephyr net buffers. The release adds an SSH server and client with a shell backend (so a device can expose its Zephyr shell over SSH rather than UART), an experimental Model Context Protocol (MCP) server for exposing device state to agentic tools, RTP (RFC 3550), IPv4 forwarding and NAT, an IPv6 router implementation, and DHCPv6 prefix delegation. The release notes also claim a 21% TCP throughput improvement in the `zperf` loopback benchmark, which is a reasonable guide to the kernel work on the net path but not a cross-device number.

New driver APIs are Buzzer, Clock Monitor, DALI (lighting bus), LIN (automotive bus), MUX (analog multiplexers), and Pulse IO — the LIN API in particular is a natural pair with the new TriCore support. Hardware-accelerated PSA Crypto now lands on selected Silicon Labs, NXP, and STM32 parts, which is the right story for the devices that previously had working accelerators but used vendor-specific wrappers rather than the PSA API. For test and build infrastructure, Twister grows multi-device testing and multi-toolchain builds in one run, `native_sim` gains Wi-Fi, audio, video, LED, and host-directory-mount peripherals, and VirtIO drivers (block, input, GPIO, I2C, SPI) make QEMU targets more usable. New kernel instrumentation includes `ZASSERT()`, `CONFIG_SYS_HEAP_SANITIZER_ASAN`, and `CONFIG_SYS_HEAP_KASAN`.

### 🎯 Takeaway (Hợp)
If you ship Zephyr on an existing in-tree architecture, 4.5.0 is a routine upgrade worth taking for the net-stack and crypto work alone — the QUIC/HTTP/3 landing lets you retire a bolted-on library, and PSA Crypto hardware acceleration on supported silicon reduces a familiar class of RTOS porting cost. Nếu đội đang có kế hoạch sản phẩm trên AURIX hoặc Hexagon, đây là bản phát hành đầu tiên có support thực sự in-tree — nên clone và chạy sample để đo gap với vendor BSP trước khi commit. Treat `mpipe` as a direction rather than a stable API this cycle; a prototype audio/video pipeline is a safe investment, a shipping product on 4.5 is not.

Mechanical and thermal design is the usual trade-off for this class. Operating temperature is specified at -20 °C to +50 °C with Windows 11, Ubuntu 24.04, and Windows 11 IoT Enterprise 24H2 named as supported. The storage story is single-slot NVMe plus a 2230 M.2 for Wi-Fi and Bluetooth and a 3042/3052 M.2 Key-B for cellular — a realistic feature set for a field device that needs out-of-band connectivity. The post notes that the design is almost certainly derived from BIOSTAR's own BIWCL-PAT 3.5-inch SBC, which is a plausible source of the port layout and places this box in the long line of mini-PCs built around a reference SBC.

### 🔭 Overview (Tổng)
On 29 October 2026 Debashis Das at CNX Software covered BeagleBoard.org's BeagleConnect QuadESC, an open-source four-channel brushless-DC motor controller built as a carrier board for a new "Torque" system-on-module. The Torque SoM centres on TI's AM13E23019 — a Cortex-M33 at 200 MHz with 128 KB SRAM and 512 KB flash, a TinyEngine AI accelerator, three 12-bit ADCs, and motor-control PWM — and the carrier board drops four motor channels, 12 phase-current senses, 12 phase-voltage senses, and four NTC inputs onto a 60 × 48 mm footprint. The project is open source with firmware and hardware on GitHub, and the roadmap names Zephyr RTOS support, which lines up with the Zephyr 4.5.0 release above.

### 🔬 Details (Phân)
The SoM is the piece most of the engineering lives in. TI's AM13E23019 brings CAN FD via an on-board TI TCAN844 transceiver, UART, SPI, and I²C, together with secure boot and secure debug — the latter is the quiet-but-important detail for anyone shipping a motor controller in a system where firmware integrity matters. The physical interface is a 1.27 mm-pitch 100-pad LGA on the underside of a 25.4 × 38.1 mm, four-layer SoM, which lets a product team swap SoMs without redesigning the control board. The SoM is intended as a reusable control brain for applications beyond this specific motor carrier.

The QuadESC carrier is a conventional four-channel ESC design with specific component choices. The gate drivers are four TI DRV8323S gate drivers; the half-bridges are twelve TI CSD88599Q5DC parts (three per motor). The design targets 40 A continuous and 70 A burst per motor on a 3S–6S battery (9–25.2 V, 32 V board design maximum) — numbers the post explicitly calls targets, not vendor-verified figures. The board exposes an 8-pin flight-controller interface that supports DShot, which is the common signalling for drone ESCs today. Debug is TI's XDS110 SWD, the software environment is the TI AM13E2X SDK with SysConfig and the TI field-oriented-control tools, and the current state of the project is that out-of-the-box motor firmware is not yet shipping — teams have to build on top of the SDK.

The honest limits are three. The 40 A / 70 A figures are design targets rather than measured values, so sustained-current behaviour and thermal headroom need testing on the real motor and battery. The Zephyr RTOS support is planned, which means the near-term development path still runs through TI's SDK rather than Zephyr. And no pricing is published yet; without one, the comparison against established four-channel ESCs (and the handful of existing BLDC SoMs with secure boot) cannot be scored.

### 🎯 Takeaway (Hợp)
If you are prototyping a quadruped, a mobile robot, or a drone around a Cortex-M-class control brain with CAN FD and secure boot, the QuadESC/Torque pair is a credible open-hardware alternative to a vendor dev kit and worth tracking for the first firmware drop — in the meantime, build on the TI AM13E2X SDK and plan a Zephyr migration once that support lands. Lưu ý rằng con số 40 A continuous và 70 A burst là mục tiêu thiết kế chứ chưa đo thực tế; phải chạy thử trên motor cụ thể của bạn trước khi dựa vào đó cho spec sản phẩm.
