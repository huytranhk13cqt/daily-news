### 🔭 Overview (Tổng)
On 3 November 2026 Databricks announced that UNIQUE constraints — primary keys, nullable unique keys, and foreign keys — are now in Public Preview on Unity Catalog Delta tables. The feature is available on Databricks SQL and Databricks Runtime 18.2 and later, and the query-rewrite half runs only on Photon-enabled compute. These are informational constraints: they are not enforced at write time, they are a signal to the optimizer. For Lakehouse teams who have been living without the informational-constraint-driven rewrites Snowflake and Redshift have shipped for years, this closes a long-standing gap and gives the Photon optimizer licence to delete work that would otherwise be shuffled.

### 🔬 Details (Phân)
The constraint shape is standard SQL with two custom hints: `RELY` tells the optimizer to assume validity without validation, and the default `NORELY` records intent only. A table has at most one PRIMARY KEY, non-nullable; multiple UNIQUE constraints are allowed and the columns can be nullable, but nullable UNIQUE still permits repeated NULLs, so DISTINCT-removal rewrites require an `IS NOT NULL` filter on those columns. Foreign keys reference either the parent PRIMARY KEY by omitting the parent column list, or a named UNIQUE constraint. The post stresses that the parent column order must match the UNIQUE definition's order — mismatches don't error, they just make join elimination silently not fire. DROP CASCADE drops dependent foreign keys; the default is RESTRICT.

The two benchmarks are what makes the preview worth watching. On 10 TB TPC-DS (SF10000), joining `store_sales` to `customer` through a FK-to-PK relationship saw median engine execution time fall from 23.6 s to 3.0 s — a 7.9x speedup when the optimizer eliminated the join entirely. On a composite UNIQUE across `(ss_item_sk, ss_ticket_number)` in `store_sales`, median time for a DISTINCT query fell from 33.7 s to 2.8 s, a 12.0x speedup. Both rewrites removed over 99.99% of shuffle, which is the mechanism underneath the wall-clock numbers. The architectural piece is that these are informational constraints on an open table format — the correctness contract sits with the producer pipeline, not with the storage layer.

The sharp edge is correctness. An incorrectly declared `RELY` constraint lets the optimizer return wrong results silently, because it will remove duplicates it believes do not exist. The post is explicit that teams should validate for duplicates and orphaned foreign keys before adding `RELY`, and Delta Lake does not have primary-key enforcement in the write path to catch a mistake later.

### 🎯 Takeaway (Hợp)
If your Lakehouse already runs on DBR 18.2 with Photon, add PRIMARY KEY `RELY` on dimension tables and FK `RELY` on fact tables after a one-time integrity scan; the free join-elimination and DISTINCT-removal wins are real and large on star-schema workloads. Đừng dán `RELY` lên các cột bạn chưa thực sự verify — optimizer sẽ tin lời bạn và trả về kết quả sai mà không cảnh báo. Treat the 7.9x–12x figures as vendor TPC-DS numbers and measure on your own workload before writing them into a capacity plan.

### 💡 Example
```sql
-- Declare informational PK/FK with RELY on Unity Catalog Delta tables (DBR 18.2+).
-- The RELY hint authorises Photon to rewrite queries assuming the constraint holds.

ALTER TABLE customer
  ADD CONSTRAINT customer_pk PRIMARY KEY (c_customer_sk) RELY;

ALTER TABLE store_sales
  ADD CONSTRAINT ss_customer_fk
  FOREIGN KEY (ss_customer_sk) REFERENCES customer (c_customer_sk) RELY;

-- Join elimination fires: Photon can drop the join to `customer` entirely
-- when the query does not reference any customer columns.
SELECT ss_item_sk, SUM(ss_sales_price)
FROM store_sales s
JOIN customer c ON s.ss_customer_sk = c.c_customer_sk
GROUP BY ss_item_sk;
```

### 🔭 Overview (Tổng)
Home Assistant published a post on 3 November 2026 titled "Naming things in Home Assistant," previewing the entity-naming overhaul landing in the 2026.11 release the next day. The core change: an entity is named for what it is (a switch, a sensor, a temperature), and Home Assistant composes the display name from the device and area at render time. The second big piece is child devices — a complex physical device such as a four-socket power strip becomes one parent device plus four child devices, each a first-class citizen with its own name. For install teams and automation authors who have hand-tuned `friendly_name` across hundreds of entities, it is a breaking display-layer change wrapped around an explicit deprecation announcement.

### 🔬 Details (Phân)
A new "main entity of the device" flag lets one entity — typically the switch on a smart plug — display just the device name in dashboards, so a user does not see "Coffee Machine Coffee Machine." Three new template functions replace most `friendly_name` reads: `entity_name(entity_id)`, `device_name(entity_id)`, and `area_name(entity_id)`. Entity IDs are unchanged, so every automation, scene, script, and dashboard keeps resolving by ID. Child-device support ships on day one for Z-Wave, MQTT, ESPHome, and some Tuya devices; Matter and ZHA are in progress but not in 2026.11.

Home Assistant's naming has historically been a hand-woven mix of integration defaults, `friendly_name` overrides, and per-card renames. The team is not deprecating `friendly_name` in 2026.11 — the post says they "plan to deprecate … and eventually remove it" with the removal announced in advance — but every integration author and dashboard template is now on notice. Voice assistants keep working: old names are retained as aliases for Assist, Alexa, and Google Assistant. The affected-surface list is long: Lovelace dashboards, custom cards that read `friendly_name` via the state object, backup/restore of names, and anything downstream that scrapes names via the websocket API.

Entities whose names already begin with the device name will lose the duplicated prefix after upgrade, so pre-2026.11 screenshots of a Lovelace dashboard will not match post-upgrade reality one-for-one. Custom-card authors who read `state_attr('…', 'friendly_name')` will see different values after the upgrade for renamed entities; the documented fix is to set the name on the card. For a large install the right move is to upgrade a staging HA instance first, screenshot the top dashboards, and port templates to the new functions before pushing to production.

### 🎯 Takeaway (Hợp)
Treat 2026.11 as a soft migration: `friendly_name` still works, but every template that reads it is now on borrowed time, so put a lint in your Home Assistant Git repo for `friendly_name` references and port them to `entity_name()`, `device_name()`, and `area_name()`. For power users on Z-Wave, MQTT, or ESPHome multi-endpoint devices, the child-device model is the real quality-of-life win. Đừng nâng cấp production vào đúng tối thứ Tư — screenshot dashboard cũ trước, chạy trên staging một tuần đã.

### 💡 Example

{# e.g. compose a short alert label without the device name #}

       in the {{ area_name('switch.coffee_machine') }}.

### 🔭 Overview (Tổng)
On 3 November 2026 Databricks and Anthropic announced that Claude Platform now exports OpenTelemetry (OTel) spans natively into Databricks MLflow — Anthropic SDKs, the Messages API, and Claude Managed Agents all emit traces over OTLP, and Databricks stores them in Unity Catalog tables linked to an MLflow experiment. The integration is Public Beta; MLflow Issues, the ticket-tracker piece, is also Beta. For teams already standing up LLM observability on Langfuse, Weights & Biases, or Phoenix inside the Databricks estate, this adds a first-party path with Unity Catalog governance on the trace table itself.

### 🔬 Details (Phân)
Each trace captures model calls, tool-call activity, timing, and — only when the opt-in content mode is set to "full" — the request and response payloads. Setup requires installing the integration packages and configuring the OTel tracer provider with an OTLP exporter pointed at the Claude Platform endpoint. Claude Code and the Claude Agent SDK also support OTel, but through additional environment variables that the announcement links out to instead of enumerating. The transport that lands spans into the Unity Catalog table is Databricks' Zerobus, so trace volume is governed the same way as other streaming writes to the lake.

The attraction over a third-party LLM observability stack is governance. Spans land as Delta tables under Unity Catalog, inheriting the same role-based access, column-level masking, and lineage as the rest of the Lakehouse. A platform team can grant read-only trace access to an application team without provisioning a second tenant in another SaaS, and can join traces to upstream features or downstream business metrics via SQL. The practical limits are two: (a) Public Beta means SLA language is not available and schema evolution is still on the table, and (b) MLflow Issues — the piece where a trace becomes a tracked defect — is also Beta, so the trace-to-ticket closed loop is not yet GA.

The post does not include a code snippet, a sample span schema, or notes on sampling-rate defaults; those will matter for high-throughput production agents, where exporting every span into Unity Catalog becomes costly. The OTel content mode is also the piece most likely to drive legal and compliance review — "full" captures tool arguments and responses verbatim, which for a customer-facing agent means PII and system prompts landing in the same governed table.

### 🎯 Takeaway (Hợp)
If you already run Claude agents in production alongside Databricks, wire the OTel exporter in a non-prod MLflow experiment and watch the Unity Catalog trace table grow for a week before picking a sampling rate. Keep content mode off "full" until privacy review signs off on the trace table's governance. For teams on Langfuse or Phoenix, this is not yet a reason to migrate, but it is a reason to sketch what Unity-Catalog-governed trace storage would unlock in a quarter.

Integration is via DuckDB's Java client. The pattern across the three tools is the same shape: a heavy remote query — Hamilton gives 20 minutes as a representative worst case — runs once on the central kdb+ or SQL system, and the result set materialises to local Parquet files via DuckDB.
