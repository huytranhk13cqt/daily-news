### 🔭 Overview (Tổng)
Databricks announced Apache Spark 4.3 on 5 November 2026 and shipped it inside Databricks Runtime 19 the same day, with the release also marking the shift to a quarterly feature cadence that ends the six-month rhythm Spark has held for most of its history. The headline items span three layers of the engine: Real-Time Mode gets a full stateful streaming surface with measured P99 end-to-end latency of 136-141 ms on three reference workloads, Project Feather adds an opt-in single-task execution path for small-data fragments, and SCD Type 2 lands as an Auto CDC primitive in Python, SQL, and Spark Connect. The release closed 1,100+ Jira tickets from 200+ contributors, which puts it closer to a major than the quarterly label suggests. For Databricks teams this is a runtime upgrade with material streaming and small-data implications; for anyone running vanilla Spark, the same 4.3 tag will be the reference downstream.

### 🔬 Details (Phân)
Real-Time Mode is the piece worth reading closely. Spark 4.3 adds streaming aggregation, `dropDuplicates`, and Scala/Java `transformWithState` to the mode (SPARK-58884), with reported P99 end-to-end latency of 136 ms for `dropDuplicates`, 139 ms for window aggregation, and 141 ms for `transformWithState`. The engine change under the numbers is `PipelinedShuffleDependency` (SPARK-58185) and the new `StreamingShuffleManager` (SPARK-57141), which lets producer and consumer stages run concurrently while the default `SortShuffleManager` keeps the blocking behaviour. Pipelined stages are scheduled as a group so a single failure fails the whole group, and a slot shortage fails fast rather than hanging — relevant when you plan capacity, because partial scheduling is no longer an option in that mode.

Project Feather (SPARK-57851) is the other execution-model change. When a query reduces to a single non-empty small file in one partition, or to a local in-memory relation of up to 1,000 rows, Spark 4.3 can execute without shuffle, as a single task, and pair that with Arrow-native Dataset caching (SPARK-57268) once you set `spark.sql.cache.serializer=org.apache.spark.sql.execution.columnar.ArrowCachedBatchSerializer` at a fresh application start. Broader in-process local repartitioning is deferred to the next release (SPARK-57399), so for now Feather is a narrow but concrete small-data optimisation rather than a general refactor. Auto CDC gets full SCD Type 2 support (SPARK-56249) with `__START_AT` and `__END_AT` metadata columns, but applies with MERGE so the target catalog must implement Data Source V2 row-level operations — Parquet file sources do not qualify, and the release notes point at Iceberg as the common target.

The SQL surface adds a nanosecond timestamp preview with `TIMESTAMP_NTZ(p)` / `TIMESTAMP_LTZ(p)` at precisions 7-9 (SPARK-56822) plus `timestamp_nanos` and `unix_nanos` functions, JSON_TABLE (SPARK-58366), VARIANT field update/remove (SPARK-57804, SPARK-57417) with pushdown extended to aggregate, sort and join queries (SPARK-58089), and an ASOF JOIN preview (SPARK-58092). Spark Connect gains REST endpoints to list sessions and operations, operation IDs for tracing, an experimental `SPARK_LOCAL_CONNECT_REUSE=1` flag for a persistent local server, and ARRAY/MAP/STRUCT result support in the JDBC driver. PySpark adds `DataFrame.zip` for combining projection-only transformations of the same plan (SPARK-55886), byte-bounded pickle UDF batches (SPARK-57593), and opt-in traceback locals (SPARK-57271) — the opt-in is because tracebacks can carry secrets. The nanosecond timestamp, ASOF JOIN, and SCD Type 2 are explicitly preview or feature-flag-gated, so pin a version before relying on their behaviour.

### 🎯 Takeaway (Hợp)
Teams already on Databricks Runtime should pilot 4.3 against a representative stateful-streaming job before rolling cluster images forward — the Real-Time Mode P99 numbers are a real step down, but the group-failure scheduling means capacity planning needs a second look. Treat Project Feather as a targeted small-data win on narrow queries, not a general shuffle elimination, and set `spark.sql.cache.serializer` only in a fresh application because it is static. Nếu pipeline CDC đang chạy MERGE trên Parquet, hãy kiểm tra catalog hỗ trợ Data Source V2 row-level ops trước khi bật SCD Type 2 Auto CDC — Iceberg là bên qualify sẵn, Parquet thì không.

### 🔭 Overview (Tổng)
Databricks published an engineering piece on 5 November 2026 describing a brokerless, push-based CDC path from a source database into Unity Catalog-governed Delta tables using Zerobus Ingest, which ships as a sink in Debezium Server 3.7. The pattern removes the Kafka tier that most Debezium deployments have carried in front of Databricks, letting Debezium Server (the Quarkus standalone runtime, not the Kafka Connect plugin) write change events straight to a serverless endpoint. Two sink modes are supported — a Typed mode that mirrors the source columns and an NVIDIA-contributed Envelope mode that lands every event in a fixed nine-column table — and durability gates source acknowledgment, which keeps the at-least-once semantics but anchors them to a Delta write rather than a broker commit. It is the operational counterpart to the Snowflake Datastream pattern filed in yesterday's digest.

### 🔬 Details (Phân)
Debezium is log-based CDC: it tails the PostgreSQL WAL, MySQL binlog, or MongoDB change stream rather than polling, and emits events with `before`, `after`, `op` (`c`/`u`/`d`/`r`), `source` metadata including LSN and transaction ID, and `ts_ms`. The Zerobus sink introduced in Debezium Server 3.7 takes each contiguous group of records for a table, pushes them to Zerobus, waits for durable commit, and only then lets Debezium advance its offset — so the delivery guarantee is at-least-once anchored to Delta write durability. Oversized records are rejected before ingestion in Envelope mode, which means their offsets are never committed and they do not quietly disappear downstream.

Envelope mode is the mode worth understanding first. Every event lands in nine fixed columns — `target_table`, `destination`, `partition`, `operation`, `idempotency_key`, `key`, `value`, `source_position`, `headers` — with the value column encoded as JSON (in a `VARIANT` column) or Protobuf. The `idempotency_key` is a SHA-256 derived from destination, partition, key, operation, and source position; it identifies events but does not by itself order them or deduplicate them. Databricks' recommended medallion layout therefore puts raw events in Bronze, applies dedup by `idempotency_key` and ordering by source position in Silver with inserts/updates/deletes resolved there, and promotes to Gold for business tables. Typed mode is simpler and maps straight onto source columns, which is what most teams used to run through Kafka Connect.

The soft spots in the post are the ones a capacity planner looks for. Databricks publishes no concrete throughput or latency figures and no code or configuration examples, only a reassurance that the approach "continues to work during your peak hours, without tuning"; the Databricks Community how-to is the path to a working Debezium Server config, Zerobus setup, and AUTO CDC transforms. The envelope-mode row shape and the SHA-256 definition are concrete enough to design against, and pairing this with AUTO CDC in Spark 4.3 (item 1 today) builds Type-1 current-state tables sequenced by source LSN, with Type-2 history available as an alternative. One real caveat is that `idempotency_key` includes `operation`, so the same row before and after an update is not deduplicated by the key alone — Silver still needs an explicit ordered merge.

### 🎯 Takeaway (Hợp)
If you already run Debezium into Kafka and then Kafka into Databricks, prototype Zerobus Ingest on a non-critical source first — Debezium Server 3.7 is the version to pin, and Envelope mode is the safer starting point because its nine-column contract is stable across sources. Build Silver dedup on the full ordered key (`key`, `source_position`) rather than on `idempotency_key` alone, since the key includes `operation` and will not collapse before/after rows on its own. Hãy xác nhận kích thước record tối đa với team Zerobus trước khi đẩy workload có large payload, vì Envelope mode từ chối record quá kích thước trước khi commit offset.

### 💡 Example

```yaml
# Community how-to for the current property names.

  sink:
    type: zerobus
    zerobus:
      mode: envelope                   # typed | envelope (NVIDIA-contributed)
      endpoint: https://<workspace>.zerobus.databricks.com
      target.table: main.bronze.pg_cdc_events
      key.format: json
      value.format: variant            # or protobuf
  source:
    connector.class: io.debezium.connector.postgresql.PostgresConnector
    database.hostname: pg-primary.internal
    database.dbname: app
    publication.name: dbz_pub
    slot.name: dbz_slot
    topic.prefix: pg_cdc
```

### 🔭 Overview (Tổng)
The DuckDB blog published a JetBrains-authored write-up on 5 November 2026 explaining how DataGrip now embeds DuckDB as the engine for cross-database queries, letting users join data from PostgreSQL, MySQL, MongoDB, and any other supported connection in one SQL statement without external infrastructure. The piece is useful mostly for what it says about the architecture choice, not for new DuckDB features. JetBrains evaluated Apache Calcite and handling queries inside PSI — the firm's own code-representation layer — and considered H2 as a lighter alternative; it picked DuckDB because custom table functions were "the simplest option to integrate" and because DuckDB brings more capabilities than H2, including projection pushdown. The release also promotes DuckDB from a join engine to a first-class SQL dialect in DataGrip, with syntax highlighting for DuckDB 2.0 syntax contributed by community member Epelbaum.

### 🔬 Details (Phân)
The integration shape is the interesting part. DataGrip exposes each configured database connection as a DuckDB custom table function, so a cross-database query is literally a DuckDB SQL statement that calls one function per source and joins the results in DuckDB. That shifts the heavy lifting — projection pushdown, join planning, the execution of the actual join — into DuckDB, while DataGrip retains its existing per-connection execution for single-source queries. The practical consequence is that the user-visible SQL dialect for cross-source work is DuckDB, with every supported connector as a virtual table. Before this change, DataGrip could run queries on each connection independently but had no way to combine the results in a single query, which is the gap the post calls out directly.

The post cites PostgreSQL, MySQL, and MongoDB as examples but does not limit the mechanism to those connectors; the article's framing is "any other supported database." JetBrains explicitly treats this as an initial version and plans to watch adoption before layering more DuckDB-specific optimisations on top; two roadmap items are flagged — fuller use of DuckDB's query optimizations, and using DuckDB to read file-based data sources (i.e. CSV/Parquet/JSON through DuckDB's own scanners). The post does not quote a DataGrip version number, does not include SQL examples, and does not share performance numbers — all three gaps are relevant because the real question for a DE team is whether this replaces an airflow-style extract-then-join pattern for ad-hoc work.

The alternatives JetBrains ruled out are worth logging. Apache Calcite would have been heavier to embed and would have duplicated optimisation logic. Handling queries inside PSI would have meant writing an execution layer in JetBrains' internal representation, which is the kind of work that pays back only across many features. H2 was "lighter" but did not reach DuckDB's capability set — projection pushdown is the example the post names. The underlying claim in the post is that for a tool whose job is ad-hoc SQL authoring, a well-integrated embedded analytical engine beats a custom-built one: a point that transfers to any team building an analytics-adjacent IDE or notebook stack.

### 🎯 Takeaway (Hợp)
If your team routinely pulls one dataset from Postgres and one from MongoDB into a scratch Jupyter notebook to join them, try the new DataGrip cross-source feature first — it collapses that round trip into a single SQL statement and keeps credentials inside the IDE's existing connection manager. Hãy coi đây là tool ad-hoc, không phải pipeline production: JetBrains chưa cam kết tối ưu profile, và các DuckDB-specific optimizations đang trong roadmap. Nếu bạn tự xây data IDE hoặc notebook, lưu lại architecture lesson ở đây — custom table functions là seam ngắn nhất để ghép một analytical engine vào một UI đã có.

### 💡 Example
```sql
-- DataGrip + embedded DuckDB. Each DataGrip connection is exposed to DuckDB
-- as a custom table function (shape inferred from the blog, which does not
-- publish exact function names). The query runs in DuckDB and pushes
-- projections down to each source.

SELECT
    o.order_id,
    c.email,
    s.status
FROM pg_conn.public.orders       AS o
JOIN mysql_conn.app.customers    AS c  ON c.id = o.customer_id
JOIN mongo_conn.ops.shipments    AS s  ON s.order_id = o.order_id
WHERE o.created_at >= CURRENT_DATE - INTERVAL 7 DAY
ORDER BY o.created_at DESC
LIMIT 100;
```

### 🔭 Overview (Tổng)
CNX Software covered P4 Launcher on 5 November 2026, an open-source firmware that boots an ESP32-P4 board with an attached touchscreen into a desktop-style launcher and loads `.papp` application bundles from microSD into PSRAM at run time. The piece matters less for the game catalog than for the architecture choice: the launcher loads applications from external storage without reflashing, supports OTA firmware updates from GitHub with automatic rollback if a new image fails to start, and reimplements both the Odroid Go `odroid_*` API and the earlier PAPP v1 service table so existing community code runs without a rewrite. Twenty-one PAPP apps are listed today, mostly emulators and games such as Doom, Quake, Duke Nukem 3D and OpenTyrian, plus Clock and Files utilities. Three Guition and M5Stack boards are supported out of the box.

### 🔬 Details (Phân)
The boot and runtime model is what distinguishes this from a single-firmware demo. PAPP app bundles live on the microSD card; when the user launches one, the launcher copies the binary into PSRAM and executes it there, which means the user adds, removes, or upgrades apps simply by changing files on the card. The launcher is built on LVGL, with a compositor that scales the UI to different resolutions — the three supported boards cover 800×480 (Guition ESP32-P4 4.3-inch), 1024×600 (Guition JC1060P470C 7-inch), and 1280×720 (M5Stack Tab5), and the compositor handles the delta. The firmware itself can be updated from a file on the microSD card or directly from GitHub, with automatic rollback if the new firmware fails to boot; that is OTA with a real recovery path rather than the bricking risk that still blocks hobby firmware from production-adjacent use.

The compatibility story is the other reason this project is worth noting. The launcher re-implements the Odroid Go `odroid_*` API and the earlier PAPP v1 service table on top of its new runtime, so games and utilities written against those older platforms can be ported with minimal changes. The project is built on ESP-IDF v5.5.2 and the source lives on GitHub at `giltal/ESP32_P4_Launcher`; the CNX Software piece does not quote a license and notes that development was heavily assisted by Anthropic's Claude coding assistant. Input is a notable detail — up to four input devices for multiplayer games, with PS3 and Nintendo controllers mentioned explicitly — and the audio engine supports up to 8 streams at sample rates from 4 to 192 kHz. The article does not publish minimum RAM or flash figures, nor specific codec lists, and the codec surface the hardware exposes (H.264/JPEG on ESP32-P4) is a separate matter from what the launcher's audio engine does.

Where this fits in the ESP32-P4 ecosystem: the chip has been through a year of maker-board releases — the Wireless-Tag WT99P461-S1 covered in yesterday's digest, M5Stack Tab5, Guition's lineup — and the piece that has been missing is a low-friction way to run community code on those boards without rebuilding firmware. P4 Launcher fills that niche in the way EmulationStation and RetroPie do on Raspberry Pi, with the extra twist that the whole OS fits on a microcontroller. It is not a production platform; it is a plausible base for internal tooling, kiosks, or demonstrators where swapping functionality by swapping an SD card is useful.

### 🎯 Takeaway (Hợp)
If you already own one of the three listed boards, P4 Launcher is the shortest path from retail hardware to a multi-app device you can hand to a tester — flash once, iterate by copying `.papp` files to the SD card, and let OTA rollback catch the broken images.
