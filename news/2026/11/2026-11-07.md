### 🔭 Overview (Tổng)
Databricks published a two-part engineering series on 6 November 2026 that frames OpenSharing as the production replacement for the recurring SFTP drops, API pulls, and managed-connector feeds that most B2B data pipelines still run on. The first part lays out why the pattern is broken — per-customer quirks, drift in last-processed bookkeeping, painful backfills, duplicate storage, and no provider-side visibility of who read what. The second part shows how Databricks-to-Databricks and Databricks-to-Open sharing is implemented on top of Delta Lake and Iceberg so the recipient reads the table in place rather than copying a snapshot. The combination matters because the protocol is positioned as open — "you don't even need to be on Databricks to read what your customer shares" — and because the consumer-side mechanics are Structured Streaming checkpoints, which is the API teams already run their ingestion pipelines on. For any team maintaining dozens of customer-specific exporters, this is the article to read before the next pipeline is written.

### 🔬 Details (Phân)
The implementation flow is concrete. The provider creates the Delta or Iceberg table, publishes it in a share with `WITH HISTORY`, and registers the recipient by sharing identifier; Part 2 states explicitly that "History is what makes the table an incremental source." Enabling Change Data Feed via `delta.enableChangeDataFeed` is optional unless the consumer needs insert, update, and delete events, and on Databricks Runtime 19 or later automatic Change Data Feed can replace that table property. The recipient mounts the share as a catalog and reads it with `spark.readStream.format("deltaSharing")`, pairing the stream with `Trigger.AvailableNow` for scheduled incremental runs; Databricks recommends storing the checkpoints in UC Volumes. In the worked example the first scheduled run ingests 1,000 rows and the second writes 200 new rows (not 1,200), with the target history showing two `STREAMING UPDATE` versions on top of the initial `CREATE TABLE` version — the bookkeeping drift the first article names as a failure mode of SFTP and API loops.

Consumer semantics split between `ignoreChanges`, which Part 2 warns "may re-emit rows and does not propagate deletes," and Change Data Feed, which carries explicit event types for downstream merges. For non-Databricks recipients the same share is read through a credentials file: pandas, Snowflake, or a BI tool connects through the OpenSharing credential flow, and recipients on open-source Spark use the same `readStream` pattern through the delta-sharing connector; consumers without Spark can still pull changes by version range. Access control is Unity Catalog permissions for D2D, and `CREATE SHARE` / `CREATE RECIPIENT` require metastore-level privilege rather than workspace admin. Neither article gives bandwidth or cost percentages, so the case for OpenSharing here is operational — onboarding becomes a `GRANT` instead of a new SFTP endpoint, and backfills use historical table versions instead of re-exported files — not a benchmark pitch.

The ecosystem framing is deliberate. The series describes OpenSharing as "an open protocol for reading a table in place, built on open table formats such as Delta Lake and Iceberg," which keeps it aligned with the lakehouse push against vendor-managed exchange formats. For an existing pipeline, the migration cost is real but bounded: the provider side needs schema stability and history retention, the recipient side needs a Structured Streaming job with a checkpoint location and a `Trigger.AvailableNow` schedule, and the governance side needs the metastore-level privileges and a credentials-file story for any D2O consumer. There is no mention of OpenSharing-specific SQL beyond share and recipient DDL, so the daily-driver surface stays `readStream` with existing Spark operators.

### 🎯 Takeaway (Hợp)
Teams running recurring customer exports should pilot OpenSharing against one feed before touching the rest — start with a Delta table published `WITH HISTORY`, a recipient granted via Unity Catalog, and a Structured Streaming job with `Trigger.AvailableNow` writing checkpoints into a UC Volume. Default to `ignoreChanges` for simple incremental landing and reach for Change Data Feed only when the downstream consumer actually needs explicit deletes. Nếu khách đang chạy pandas hoặc BI tool không phải Databricks, dùng credentials file với OpenSharing connector thay vì mở thêm một endpoint SFTP mới.

### 💡 Example
```python

# and a UC Volume checkpoint, following Databricks' Part 2 recipe.

(spark.readStream
    .format("deltaSharing")
    .option("ignoreChanges", "true")
    .load("shared_in.providers.customers")
    .writeStream
    .format("delta")
    .option("checkpointLocation",
            "/Volumes/catalog/ops/checkpoints/customers_stream")
    .trigger(availableNow=True)
    .toTable("catalog.silver.customers"))
```

### 🔭 Overview (Tổng)
AWS Big Data posted on 6 November 2026 that Amazon Redshift has lifted the SUPER data type's per-string ceiling from 65,535 bytes — the VARCHAR limit SUPER inherited at launch — up to 16,000,000 bytes, which is roughly 244x more headroom for a single semi-structured value. The ceiling change targets the exact cases Redshift users have been splitting and truncating around: large JSON documents, weblog payloads, IoT telemetry, and application logs where one field can legitimately pass the 64 KiB line. The release also pairs with case-insensitive collation inside SUPER, which smooths migrations from legacy warehouses that defaulted that way. Operationally the feature is gated behind a parameter and a specific maintenance patch rather than being on by default, so the rollout is opt-in and auditable by cluster. For any team currently normalising large JSON into separate tables because of the old ceiling, this changes the shape of the ingestion pipeline.

### 🔬 Details (Phân)
The gating is explicit. You need Redshift patch 206 or later on the current maintenance track, and you must set `enable_large_strings_opt_in` to Yes — via a parameter group plus reboot on provisioned clusters, or at the workgroup level on Serverless — then confirm with `SELECT is_large_string_enabled();`. Once on, table columns defined as `VARCHAR(MAX)` stay at 65,535 bytes (that part of the schema is unchanged), but inside a view `VARCHAR(MAX)` resolves to `VARCHAR(16000000)` so cast and projection expressions can carry the longer values through downstream queries. The AWS post says strings past the VARCHAR limit are processed in memory, which avoids the truncation and disk-spill behaviour the old pipeline fell into when a string pushed over 64 KiB. The shown examples cover a `COPY ... FORMAT JSON 'noshred'` into a `SUPER` column, and a `LEN(LISTAGG(data.detailedDescription::VARCHAR, ', '))` aggregation that returns 1,212,008 characters — a result that would have been unrepresentable in the old world.

The casting rules sit at the sharp edge. The post notes that calling `lower(data.customerId)` on a SUPER field errors; the working form is `lower(data.customerId::VARCHAR)`, i.e. SUPER values must be cast to VARCHAR before string functions. PartiQL path syntax still applies for traversal, `JSON_PARSE` and `LISTAGG` are the primary helpers, and the `COLLATE` attribute at the column level now lets a SUPER column keep case-sensitive semantics inside a `CREATE DATABASE ... COLLATE CASE_INSENSITIVE` parent — so a migrated application can keep its old string comparison behaviour on scalar columns while routing large JSON through case-sensitive SUPER. Benchmark figures and regional availability are not in the post, so for planning purposes assume the usual provisioned/serverless split and validate on a non-production cluster before flipping the parameter group.

The ecosystem framing matters for lakehouse-adjacent workloads. Redshift's SUPER column has been the on-ramp for semi-structured data inside the warehouse; moving the ceiling to 16 MB closes the gap with Snowflake's `VARIANT` (16 MB soft limit) and with BigQuery JSON. It does not replace landing large blobs in object storage with a pointer column, but it removes the lazy-shard pattern where teams were splitting one JSON document across multiple Redshift rows to avoid VARCHAR truncation.

### 🎯 Takeaway (Hợp)
Check your Redshift cluster's maintenance patch level and plan a parameter-group update to enable `enable_large_strings_opt_in` before merging any schema that relies on the new ceiling — the reboot is unavoidable on provisioned clusters. Audit existing SUPER-to-VARCHAR casts in views and materialised views because `VARCHAR(MAX)` now resolves to `VARCHAR(16000000)` inside a view and may push row sizes you are not expecting. Nếu đang cắt JSON lớn thành nhiều hàng để tránh cap 64 KiB, feature này giúp gom lại nhưng vẫn nên benchmark trước — AWS chưa công bố số hiệu suất và việc xử lý in-memory không phải miễn phí về RAM.

### 💡 Example
```sql

```

### 🔬 Details (Phân)
The design choice to skip micro-ROS is the article's technical headline. Micro-ROS pushes DDS onto the microcontroller via a dedicated transport; Arduino's approach tunnels ROS 2 primitives through RouterBridge/MsgPackRPC between the microcontroller sketch and the Linux-side proxy, which then speaks to whatever ROS 2 middleware (RMW) vendor is running on the Linux CPU. The article is explicit that the library "works regardless of which ROS middleware (RMW) vendor runs on Linux." That gives two concrete properties: the sketch does not need a DDS implementation sized to fit the MCU, and the Linux side can keep using the RMW the rest of the robot already runs. The API uses an `ros2ino` namespace and follows rclcpp conventions so that `rclcpp::Publisher` / `rclcpp::Subscriber` patterns translate directly into sketch code. The published example topics are `/imu/data` for streaming IMU telemetry from the sketch to ROS 2 and `/cmd_vel` for receiving motor velocity commands back; services and actions are supported but not demonstrated in the announcement.

The post names only the VENTUNO Q as a supported board; the tutorial links point to UNO Q material but the announcement does not state that the UNO Q runs the library. No ROS 2 distribution (Jazzy, Rolling, Kilted, etc.) is named, no pricing or release date is stated, and the Zephyr-based microcontroller sketch runtime on VENTUNO Q is the inherited build target. The article also does not describe a fully plug-and-play setup — sketch and Linux proxy must both be configured — but it frames the win as removing the need for bespoke serial protocols and separate bridge nodes between the micro and the ROS 2 graph. For a VENTUNO Q user wiring an IMU on the micro and running SLAM on the Linux side today, that collapses a two-protocol stitch into one rclcpp-style API.

The ecosystem placement matters because this is an Arduino-side alternative to micro-ROS and because VENTUNO Q is the newest Arduino "linux + MCU" board. Together they tilt the Arduino ROS 2 story from "write a sketch that forwards bytes to a bridge node on Linux" to "write a ROS 2 publisher in the sketch." Whether that pulls community momentum away from micro-ROS depends on how widely the library expands beyond VENTUNO Q.

// Arduino_RouterBridge_ROS — minimal sketch publishing /imu/data and
// subscribing to /cmd_vel on an Arduino VENTUNO Q (micro side).

#include <Arduino_RouterBridge_ROS.h>
using namespace ros2ino;

Node node("ventuno_q_micro");
Publisher<sensor_msgs::msg::Imu>      imu_pub("imu/data", 10);
Subscriber<geometry_msgs::msg::Twist> vel_sub("cmd_vel", 10,
    [](const auto& msg) {

}
