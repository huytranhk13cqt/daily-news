## 1. Apache Airflow 3.4.0 Ships AIP-111 Task Loops, AIP-85 Non-Python DAG Authoring (TypeScript/Go/Java/YAML), a Drain State, psycopg3 as the Default Postgres Driver, One-Run-Per-Event Assets, and Drops Python 3.10

### 🔭 Overview (Tổng)
The Apache Airflow project cut 3.4.0 on 6 November 2026, with the release published by vatsrahul1001 from commit `619a787` and a run of 1,011 commits already on `main` since the tag. The feature set is the biggest shift in the 3.x line so far: `.loop()` on decorated task groups turns a runtime-sized iteration into a first-class graph construct, and a pluggable DAG importer lets a DAG be written in TypeScript, Go, Java, or a native YAML schema instead of Python. Day-to-day operations change too — Airflow now defaults to psycopg3 for the metadata database, asset-triggered DAGs stop batching events by default, and a new draining state pauses a DAG without killing the runs already in flight. The upgrade is not drop-in: Python 3.10 is dropped, images move to Debian 13, and a downgrade below 3.4.0 has to copy XCom rows back to the old table. For any team still running one scheduler per environment, this is the release to plan around.

### 🔬 Details (Phân)
AIP-111 wires `.loop()` into the Task SDK so a task group repeats a runtime-determined number of times with `do ... while` semantics. Conditional loops take an `until` predicate and a `max_iterations` cap; iterations run sequentially while tasks within an iteration keep running in parallel. AIP-85 is where the project leaves its Python-only history: a `$schema` marker identifies a native YAML DAG file and a pluggable Dag Importer loads DAGs written in TypeScript, Go, or Java through their respective SDKs. The release notes label both the importer framework and the language SDKs as experimental, so they can change in 3.5. On the operations side, `drain_dag` (REST API) or the UI's **Drain** action moves a DAG into `draining`, which stops new scheduled and asset-triggered runs and pauses the DAG once the in-flight ones finish. psycopg3 replaces psycopg2 and asyncpg as the default Postgres driver, and bare `postgresql://` URLs are rewritten to `postgresql+psycopg://` at runtime.

The breaking changes concentrate around assets, scheduler internals, and heartbeats. Single-asset and OR schedules now create one run per event; teams that rely on batching must set `batch_asset_events=True` or the `[scheduler] batch_asset_events` config and reparse affected DAGs. `[workers] max_failed_heartbeats` is now the only heartbeat retry budget and its default rose from 3 to 30. Clearing a task instance deletes its task state store entries unless the request passes `keep_task_state=True`, and `try_number` on up-for-retry instances now points at the upcoming try, so `/tries/{try_number - 1}` is what fetches the failed try. Team names must match `(?!.*__)[a-z0-9_-]{3,50}` and `airflow db migrate` lowercases existing names before refusing to run on case collisions. Removed features include the deprecated `Dataset` alias (replaced by `Asset` from `airflow.sdk`), `airflow info --file-io`, and the `PYTHON_LTO` build argument; the old base image flavour is still available for one more cycle via `AIRFLOW_IMAGE_FLAVOR="legacy"` until 3.5.0.

Ecosystem reach is significant. psycopg3 as the default closes a long-standing fragmentation between sync and async drivers on the same cluster, and the non-Python DAG path opens the project to pipelines maintained by teams that would otherwise stand up a parallel orchestrator. The downgrade caveat deserves attention: on MySQL, a failed 3.4.0 to earlier downgrade can leave the schema partly downgraded, so a backup should precede any upgrade of the metadata database.

### 🎯 Takeaway (Hợp)
Teams on Airflow 3.3.x should stage 3.4.0 in a non-production environment and decide early whether to keep batching asset-triggered runs — flipping `batch_asset_events=True` after the upgrade avoids a scheduler-load spike. Pilot `.loop()` on a single idempotent task group before porting dynamic task mapping patterns, since conditional loops are the first iteration primitive Airflow offers with runtime-sized behaviour. Giữ psycopg2 trong một pod tạm cho rollback nếu cần, nhưng tránh downgrade metadata DB khi đã migrate — AIP-111 XCom migration không rollback nhanh.

### 💡 Example
```python
# AIP-111 task loop in Apache Airflow 3.4.0 — a do ... while over a
# decorated task group, bounded by max_iterations.

from airflow.sdk import dag, task, task_group

@dag(schedule=None)
def crawl_pages():
    @task
    def fetch_next_page(state: dict) -> dict:
        return {"page": state["page"] + 1, "done": state["page"] >= 10}

    @task_group
    def crawl(state):
        next_state = fetch_next_page(state)
        return next_state

    crawl.loop(
        start={"page": 0, "done": False},
        until=lambda s: s["done"],
        max_iterations=20,
    )

crawl_pages()
```

### 🔭 Overview (Tổng)
AWS Big Data published a reference architecture on 5 November 2026 for building a multi-tenant data agent on Bedrock AgentCore that runs under Lake Formation governance. The post is a worked pattern rather than a feature launch: it shows an AgentCore Gateway fronting a Text-to-SQL agent, with per-user authentication landing a Cognito ID token that is exchanged for IAM credentials scoped to the user's team, after which Athena queries hit the Glue Data Catalog under Lake Formation's row- and column-level controls. The contribution is operational — the application does not implement filtering logic at all, and any per-team data boundary lives in LF-Tags and data cell filters rather than in agent prompts. For teams that have been duct-taping SQL `WHERE team_id = ...` injection onto an LLM, this is the blueprint to replace it.

### 🔬 Details (Phân)
The pipeline is specific. A Cognito User Pool stores a custom `team` attribute per user, and a Cognito Identity Pool uses rule-based mapping to pair each `custom:team` value with an IAM role. When an agent request arrives, the AgentCore runtime forwards the token to the gateway, which calls a Lambda target that invokes Cognito's `GetCredentialsForIdentity` and returns temporary credentials for that role. The agent's Text-to-SQL action calls Athena with those credentials, and Lake Formation enforces access to the Glue Data Catalog table referenced in the query. Lake Formation grants in the walkthrough use LF-Tags — `SELECT` and `DESCRIBE` granted on tables tagged `team=TeamA` or `team=shared` — and data cell filters for the row-level cut. The post shows three artefacts: an AWS CDK (Python) definition of the user pool with the custom `team` attribute, a CDK snippet that attaches identity-pool role mapping to the `custom:team` claim, and an AWS CLI `grant-permissions` invocation that binds the role to the LF-Tag filter.

Positioning against alternatives is worth naming. The usual pattern — a single IAM role for the agent, with row filters generated inside the SQL — fails open on prompt injection and leaves auditors dependent on the LLM's output. Running Athena under per-user credentials means Lake Formation evaluates the permission on the identity that actually submits the query, so a prompt-injected agent that tries to widen the `WHERE` clause can only widen it within the LF-Tag and data cell filter scope of the caller's role. The architecture also keeps the agent surface clean: the Model Context Protocol (MCP) tooling attached through AgentCore Gateway does not need to know about team boundaries. Caveats the post does not quantify: Cognito's `GetCredentialsForIdentity` adds latency on every call unless credentials are cached, Athena cost per query attributes to the per-team role which affects chargeback, and the walkthrough names no service limits or failure modes for the token-exchange Lambda.

The ecosystem framing is the direction AWS has been pushing all 2026 — move authorisation out of the LLM app and into the data plane. Pairing AgentCore with Lake Formation is the first concrete AWS Big Data post that assembles the full chain — user → token → role → catalog filter → query — in one place.

### 🎯 Takeaway (Hợp)
Teams building a Text-to-SQL agent on AWS should take this post as a checklist: tag tables with LF-Tags by tenant, write data cell filters for row-level cuts, and move the per-user identity into a Cognito-mapped IAM role instead of letting the agent decide what to filter. Cache the credentials from `GetCredentialsForIdentity` with the Cognito token's expiry, since re-exchanging per agent step adds measurable latency on a long tool-call chain. Nếu tenant mapping đang nằm trong prompt hay trong SQL template, viết lại theo pattern này trước khi mở agent cho khách hàng thứ hai.

```python
# role on an Identity Pool, so Athena queries under that role are filtered
# by Lake Formation LF-Tags and data cell filters.

from aws_cdk import aws_cognito as cognito

user_pool = cognito.UserPool(
    self, "AgentUsers",
    custom_attributes={
        "team": cognito.StringAttribute(min_len=1, max_len=64, mutable=False),
    },
)

identity_pool = cognito.CfnIdentityPool(
    self, "AgentIdPool",
    allow_unauthenticated_identities=False,
    cognito_identity_providers=[{...}],
)

cognito.CfnIdentityPoolRoleAttachment(
    self, "AgentIdRoleAttach",
    identity_pool_id=identity_pool.ref,
    role_mappings={
        "userpool": {
            "type": "Rules",
            "ambiguous_role_resolution": "Deny",
            "identity_provider": f"cognito-idp.ap-southeast-2.amazonaws.com/"
                                 f"{user_pool.user_pool_id}:{user_pool_client_id}",
            "rules_configuration": {"rules": [
                {"claim": "custom:team", "match_type": "Equals",
                 "value": "TeamA", "role_arn": team_a_role.role_arn},
                {"claim": "custom:team", "match_type": "Equals",
                 "value": "TeamB", "role_arn": team_b_role.role_arn},
            ]},
        }
    },
)
```

### 🔬 Details (Phân)
The architecture details are the headline. The 4 KB PRAM is where everything custom lives. The FFT port is the most quantified result: an in-PRAM C program compiled to LR2021 machine code computes FFTs on raw I/Q samples delivered via DMA, with CPU compute overlapping DMA capture, and the waterfall rate goes from 6.6 FPS (default) to 462 FPS — a 70x speedup — on the same silicon. The custom code also demonstrates a MeshCore repeater with direct and flood routing, trace packets, adverts, a four-message TX queue, and a 64-entry dedup table; the advert cadence uses a 32 kHz counter at `0xF11014`.

The limitations are real and worth naming. MeshCore and the Meshtastic payload both run without encryption: adverts are pre-signed with a fixed timestamp because there is no persistent clock in PRAM context, and the custom code has to live with volatile storage — power-cycling the chip reloads Semtech's PRAM baseline. The LR2021 cannot trigger a transmit from its own processor directly, so Beal uses an unconventional path: toggling internal pull-ups and pull-downs on the SPI lines to clock messages back into itself. The chip lacks Bluetooth, Wi-Fi, and USB, which caps how far the "standalone node" pitch goes. Beal's prior work by SAMS0N1TE is explicitly credited — an undocumented opcode that streams raw I/Q samples, originally demonstrated on an nRF52 companion, was re-implemented on-chip.

Positioning matters. For security teams, the inverse is also true: a 4 KB PRAM slot that runs custom ARCv2 code is a payload target. ## 6. Linebender vic-2350 Puts a JIT Behind Bitmap Text on the RP2350: ~6 Cycles/Pixel Race-the-Beam DVI, Dot-Product Kerning, ~21k-Cycle JIT Compile Before Scanout of a Single Video Line

### 🔭 Overview (Tổng)
Raph Levien of the Linebender project published an engineering post on 7 November 2026 that describes `vic-2350`, a JIT-compiled bitmap text renderer for the RP2350 that draws proportional, kerned text at about six CPU cycles per pixel — the race-the-beam budget needed to feed the RP2350's HSTX peripheral driving DVI without a framebuffer. Rather than iterate over glyphs at runtime, the renderer compiles a short program to blit a specific string, then runs that program line by line into the scanout buffer. The piece is a reusable technique: it covers a glyph-packing method that shrinks a packed font bitmap from 1140 to 960 bytes by sharing overlapping bits between glyphs, a "dot-product kerning" scheme that uses two per-glyph bitvectors and a popcount, and the concrete cycle budget for each stage. For anyone building a text-capable display on an MCU without a framebuffer, this is a long-form reference.

### 🔬 Details (Phân)
The numbers are explicit. The RP2350 provides 520 kB of SRAM, which is enough to hold the JIT buffer and a double-buffered display list without fighting for memory. The core loop costs 23 cycles per glyph plus 3 cycles per row of glyph height for bitmap generation; the JIT adds about 20 cycles plus two cycles per row of height for every 32 bits of output width. In a test render, the JIT compile was about 21,000 cycles and running the generated code took about 42,000 cycles — Levien characterises that as roughly 2.6% of one core's total throughput. The 1bpp-to-RGB565 expansion that follows runs at about 1.75 cycles per pixel sustained. The JIT compile completes in under 100 µs, below the time to scan a single video line, which is the invariant that makes "recompile when the string changes" viable. The post names the related dvhstx renderer — about 2 to 2.5 cycles per pixel — for comparison, and explains why dvhstx is faster but limited to a 14x24 grid and RGB222. "Dot-product kerning" uses a left and right bitvector per glyph; the kerning distance is the popcount of the AND of the previous glyph's right vector and the current glyph's left vector, with each glyph's kern data taking two bytes.

Toolchain and provenance are documented. The compiler and assembly language for the generated code is `symbolasm`, and the pipeline is written in Rust (the draft JIT core was first hand-written in Rust before being codegen'd). The project builds on Linebender's earlier `pico-dvi-rs` work. The repository lives at `github.com/raphlinus/vic-2350`. The post does not name a crates.io crate, so integration today is a git dependency rather than a published release. Power and heat numbers are not in scope: the RP2350 at race-the-beam duty on a Pico 2 draws what the published platform datasheet lists, and no measured figures are in the article.

Positioning matters because the embedded-graphics ecosystem on RP2350 so far has been dominated by framebuffer-based renderers (where the full image is written to memory before scanout) or by tile-based terminal renderers (like dvhstx). A JIT path is new on this class of hardware, and the core idea generalises beyond text — any time per-frame content is small and known in advance, the compile-then-render pattern beats the interpret-every-pixel pattern. The caveat the post is explicit about: cold-start latency for arbitrary strings is bounded by compile time plus run time, so a first frame with a never-seen string costs both, while cached strings run only the JITted program.

### 🎯 Takeaway (Hợp)
If you are building a status display, a serial-terminal front panel, or a small UI on an RP2350 without a framebuffer, read the Linebender post before committing to a scanline-sprite renderer — the JIT path gives proportional kerned text at RGB565 within the HSTX timing budget. Keep an eye on the compile-then-cache pattern more broadly: the same technique applies to fixed glyph routes on other Cortex-M33 / RISC-V parts. Code đã open-source trên GitHub nhưng chưa publish lên crates.io, nên tạm thời nhập dự án qua git dependency trong `Cargo.toml`.
