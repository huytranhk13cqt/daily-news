## 1. Bare-Metal STM32MP257F-EV1 Bring-Up Finds a TrustZone/RISAF5 Bypass Through PCIe — ST Advisory SB0070 and Errata 2.3.33, EL3 Boot in 808 kB SRAM

| Field | Value |
|---|---|

| 🌐 Domain | IoT |
| 🔑 Keywords | `stm32mp2` · `trustzone-bypass` · `bare-metal` |
| ⚡ Impact | High |

### 🔭 Overview (Tổng)
Andrew Zonenberg has written up a long bare-metal bring-up of ST's STM32MP257F-EV1 — the dual Cortex-A35 1.5 GHz plus Cortex-M33 400 MHz plus Cortex-M0+ 200 MHz application-class SoC, with 808 kB SRAM, running at EL3 with no U-Boot, no Linux, and no vendor HAL in sight. The work is interesting on its own as a reference path for using an STM32MP2 as a very capable microcontroller rather than as a Linux board, but the headline is that while debugging PCIe link training he found a RISAF5 memory-protection bypass that lets a non-secure master poke TrustZone-tagged regions through the PCIe aperture. ST confirmed the issue, published it as advisory SB0070, and added it to the device errata as 2.3.33. For anyone deploying an STM32MP2 in a role where TrustZone isolation is part of the threat model — secure element pass-through, measured boot keys, OTA signing material held in secure RAM — that errata is now a datapoint that cannot be ignored. The bring-up is also useful as a teardown of how far you can get on this SoC without the ST ecosystem: Zonenberg built his own FSBL header tool, his own PCIe root-complex setup, and his own iATU map, all from the public RM0457 reference manual.

### 🔬 Details (Phân)
The boot path puts the entire image in the 808 kB internal SRAM: ROM loads an FSBL from SPI NOR, the FSBL maps RAM, enables caches, and jumps into a flat C runtime. Zonenberg released a small tool that stamps the FSBL header onto a plain binary so you can skip the ST tooling. PCIe Gen1/2 x1 refused to train until he switched the COMBOPHY reference clock from the internal 25 MHz RCC path to an external 100 MHz source, flipping `COMBOPHYCR1` from `0xc8` to `0x33`; configuration space lives at `0x1fff_0000`, and he mapped a 256 MB BAR window at `0x1000_0000` via the iATU. Measured bandwidth: PIO with 16-byte TLPs tops out around 1.77 Gbps, and DMA with 256-byte TLPs reaches a theoretical peak of 3.71 Gbps — enough to make an STM32MP2 interesting as an FPGA host, well above the 977 Mbps FMC path he had previously benchmarked on the H735.

RISAF is ST's bus-level access filter for the A35/M33 TrustZone split: a transaction carrying the wrong CID or the wrong secure attribute is supposed to be rejected before it reaches DRAM or peripherals. During the PCIe experiments, writes that traveled through the PCIe region arrived at the RISAF5 target without the filter consulting the CID or security bit on the originating master, so a non-secure master effectively inherited secure access rights. ST acknowledged the behaviour, listed it in device errata 2.3.33, and published guidance under advisory SB0070. The practical mitigation is to leave the PCIe window out of any attack surface that is supposed to be secure — in particular, do not share a RISAF-protected region with a BAR window, and keep untrusted hosts (plug-in cards, FPGAs run by non-secure drivers) off the inbound DMA path.

Adoption-wise, this is easier to reason about than many TrustZone advisories because it is a hardware errata rather than a software vulnerability: no firmware patch closes it, and secure-world designs that depend on RISAF5 need to be re-audited against the PCIe path. The matching bright side is that the bring-up comes with a working reference for projects that want to use the STM32MP2 away from Linux.

### 🎯 Takeaway (Hợp)
If you ship or evaluate an STM32MP2-class board, pull SB0070, open errata 2.3.33, and verify your RISAF layout does not overlap a PCIe inbound window. Cho các dự án đang nhắm MP2 làm "MCU to", đây cũng là tài liệu bare-metal hiếm hoi đáng đọc kỹ.

### 💡 Example
```c
/* COMBOPHY clock fix that unblocks PCIe Gen1/2 x1 on STM32MP257F-EV1
 * Default is internal RCC 25 MHz, which does not meet PCIe refclk spec.
 * Switch to external 100 MHz before de-asserting the PCIe controller reset.
 */
#define COMBOPHY_BASE    0x480C0000u
#define COMBOPHYCR1     (COMBOPHY_BASE + 0x04u)

/* iATU and BAR window per bring-up notes */
#define PCIE_CFG_BASE    0x1FFF0000u
#define PCIE_BAR_WINDOW  0x10000000u  /* 256 MB inbound */

static inline void pcie_combophy_external_100mhz(void) {
    /* 0x33 = external 100 MHz; 0xc8 = internal RCC (fails to train) */
    *(volatile uint32_t *)COMBOPHYCR1 = 0x33u;
}
```

### 🔭 Overview (Tổng)
`hedgerow-dev/coldframe` is a new low-interaction ICS/OT honeypot aimed at a very specific target: the supermarket refrigeration controllers that sit near the top of internet-exposed-ICS counts. It implements two personas — `danfoss` emulates a Danfoss AK-SM 800A StoreView login with a fake store dashboard, refrigerated-case list, and defrost controls, plus the Danfoss XML API at `/html/xml.cgi` and `/xml.cgi`; `dixell` emulates a Copeland (formerly Dixell) XWEB EVO supervisor with the CGI paths that appear in public XWEB 500 exploits. The project is deliberately boring on paper: one Python file using the standard library, no external dependencies, HTTP plus HTTPS plus optional Modbus TCP, events written as JSON lines to stdout and to `events.jsonl`, a separate `summary.py` for reports. The containerised run uses a read-only filesystem, drops all capabilities, pins to a non-root UID, and runs in its own user namespace; the code never spawns a shell, reads files outside its work directory, or forwards traffic.

### 🔬 Details (Phân)
The Danfoss persona serves a plausible login page, a session cookie flow, and a fake live view of case temperatures, setpoints, and defrost states; the fake XML API returns schema-correct documents keyed on the device IDs seen in public AK-SM documentation. The Dixell persona targets the CGI endpoints and parameter names that appear in published XWEB 500 exploitation notes, which means the honeypot picks up the specific exploit payloads those endpoints attract rather than generic web scans. Modbus TCP is off by default; when enabled, it serves a small register map of fake case temperatures, setpoints, and a defrost register — enough to make a scan look like a real refrigeration PLC without implementing the full write-side state machine. Events landed on stdout and in `events.jsonl` include the timestamp, the persona hit, the path or function code, the full request body, and a session identifier.

The containerisation choices matter because an ICS honeypot that is itself exploitable is a bigger problem than the one it is trying to measure. Coldframe runs with `--read-only`, `--cap-drop=ALL`, and an unprivileged UID; the HTTPS path takes a mounted cert and key, so you can either generate a self-signed pair that looks period-correct or front it with a real certificate behind a reverse proxy. Commits in the repository reference Shodan data from November 2026 for targeting; the authors argue — reasonably — that refrigeration supervisors are an unusually good honeypot target because they are numerous, consistent in fingerprint, and attract both opportunistic scans and targeted intrusion attempts.

Adoption caveat: a low-interaction honeypot catches payloads and reconnaissance patterns, not full intrusion chains. If you want to study post-auth behaviour on AK-SM or XWEB EVO, Coldframe will not stand in; it is explicitly scoped to the pre-auth and credential-stuffing surface.

### 🎯 Takeaway (Hợp)
If you run or research OT infrastructure, Coldframe is a low-cost way to gather real-world scan telemetry on two of the most-exposed refrigeration controller families. Cài trong container, kẹp vào một IP dự phòng, bật Modbus nếu muốn đo cả bên PLC.

  --user 10001:10001 \

### 🔭 Overview (Tổng)
LoreKit's Mads Thines argues that the current agent-memory landscape rhymes with tracing in 2018: many stores, no interchange, and every vendor defining its own record shape. The proposal is explicitly modelled on OpenTelemetry's split — a shared data model plus semantic conventions plus a small protocol, with vendors competing on storage and ranking rather than on envelope format. The post surveys the existing landscape in some detail, which is the most immediately useful part even if you ignore the spec: AGENTS.md, CLAUDE.md, Cursor `.mdc` instruction files, Anthropic's `/memories` memory tool, GitHub Copilot Memory with its 28-day idle deletion, Letta's character-limited blocks, Mem0, LangGraph's `BaseStore` with `namespace`+`key`, the MCP knowledge-graph server, Graphiti/Zep's temporal graph, and LoreKit itself. It then catalogues the existing export-only proposals — MacPaw's Portable Memory with `.mem` bundles, the April 2026 Open Memory Protocol ZIP+manifest draft, and Cognee's COGX — and notes they are all export formats rather than interchange formats.

### 🔬 Details (Phân)
The proposed record is a YAML frontmatter plus Markdown body under `spec: agent-memory/0.1`, with an `id`, an `address` object of `{level, value}` (so a memory can be scoped to an org, user, repo, branch, or session), a `key` path inside that address, a `kind` tag (`observation`, `fact`, `preference`, `plan`, etc.), a `written_by` identifier for the agent, a `content_type`, a `lifecycle` block with `expires_at` and an optional `extended_by` reference, and namespaced `attributes` using OpenTelemetry-style keys — `vcs.commit`, `ci.job`, `agent.session`, and so on. The spec layers are deliberate: a versioned conventions registry defines what keys mean, a small MCP-exposed contract covers `write`/`read`/`list`/`search`/`archive`, and a conformance test suite anchors interop. What the spec explicitly does not define is storage, ranking, embeddings, or UI — those are left to vendors, matching how OTel leaves backend storage out of the data model.

The post is honest about limits. It is not an adopted standard, not yet backed by a working group, and not yet accompanied by a reference implementation beyond LoreKit's own product. But the problem it names is real: anyone who has run more than one agent against the same codebase has watched them each rediscover the same facts because there is no shared place to write them down. The survey portion is factual (the dates and quotas for Copilot Memory, the frontmatter fields for `.mem` bundles, the API shape of LangGraph `BaseStore` are verifiable from each project's own docs) and useful on its own.

### 🎯 Takeaway (Hợp)
Treat the spec draft as a conversation-starter rather than a dependency, but save the survey — it is the most compact overview of the current agent-memory tooling landscape to date. Nếu bạn đang chọn memory store cho agent pipeline của mình, phần so sánh đáng đọc trước khi cam kết vendor.

### 🔭 Overview (Tổng)
Hrvoje Čavrak has released `hrvach/unixpc`, a MiSTer-compatible FPGA softcore of the AT&T UNIX PC — the 1985 convergence-era workstation built around a 10 MHz Motorola 68010 with up to 4 MB of RAM. The core is written in a mix of SystemVerilog, Verilog, and VHDL, and in a demo video it boots a fairly complete UNIX PC environment on a DE10-Nano. Because the DE10-Nano's Cyclone V on-chip memory is too small to hold the 4 MB target, the project requires an SDRAM add-on board — the same daughterboard used for other MiSTer cores that exceed on-chip RAM budgets. The author is upfront about the project being a "works on my MiSTer" effort: he does not own real UNIX PC hardware to validate every corner, and parts of the code were drafted and validated with LLM chatbots before manual cleanup.

### 🔬 Details (Phân)
The UNIX PC is an interesting preservation target because it was one of the first mass-market UNIX workstations and because its hardware — bitmapped display, phone integration, floppy and ST506 hard disk — sits awkwardly between the home-computer and workstation MiSTer canon. The softcore implements the 68010, the memory map, and enough peripheral emulation to boot the shipped UNIX environment; the readme and demo imply full-system boot rather than just a CPU harness. The legal footing is the same as every retro FPGA core: the HDL in the repository is new work under an OSS licence, but the AT&T boot ROM and the UNIX PC disk images are copyrighted material, and the project does not ship them. Users have to source those lawfully — originals, legitimate archival sources, or AT&T successors' permissions — before the core is useful.

The LLM-assisted development disclosure is worth reading on its own. Čavrak describes using chatbots to translate between the available documentation (service manuals, scanned schematics, enthusiast reverse-engineering notes) and SystemVerilog, then doing manual verification against the demo boot. For embedded engineers watching the "LLMs for HDL" trend, this is a concrete data point: a single-maintainer retro core shipped with that workflow, with the author flagging which parts are known-weak.

Adoption-wise, the core is interesting mostly to MiSTer preservationists and to people who want a 68010 target that is less overused than the Mac Plus or the Atari ST. It is not aimed at Linux-on-FPGA or at modern embedded workloads.

### 🎯 Takeaway (Hợp)
A niche but tangible OSS release: another 68K-class system walks into the MiSTer canon, and the development notes are a candid case study in LLM-assisted HDL work. Cho những ai muốn chơi 68010 trên DE10-Nano mà không rơi vào Mac Plus hay Atari ST.
