### 🔭 Overview (Tổng)
AWS has published the `aws-samples/sample-agentic-data-ingestion` solution and a long-form AWS Big Data post that walks through an end-to-end, agent-driven ETL pipeline that turns an upload to an S3 source bucket into a queryable Iceberg table on S3 Tables, without a human writing the PySpark transform. The stack is unusually complete for a sample: a React dashboard behind CloudFront and AWS WAF for approvals, Amazon Cognito with MFA for sign-in, EventBridge → SQS → Lambda to kick off an AWS Step Functions workflow, and foundation models on Amazon Bedrock running as agents built with the open-source Strands Agents SDK on Bedrock AgentCore. The whole thing deploys with the AWS CDK. What makes it worth reading rather than filing as another agent demo is the operational scaffolding: two approval gates that fail closed after 72 hours, mapping reuse that still goes to review by default, Glue Data Quality rules that quarantine failing rows before they land in Iceberg, and a self-healing agent that retries Glue jobs when the failure class is one it can actually fix.

### 🔬 Details (Phân)
The documented pipeline is ten steps: validate file format and size from object metadata; extract field names and types; compare that schema against the target to detect drift; run a foundation model to map source fields to target fields with per-pair confidence scores; generate the PySpark transform and the matching Data Quality rules; run the transform inside an AWS Glue interactive session on the same Spark version as the eventual job to check its output; provision the target if it does not exist; create the Glue job with a validated configuration; record which Data Quality rules the job will enforce; and launch the job. Targets can be Amazon S3 Tables (Apache Iceberg) — queryable from Athena, EMR, or Redshift once the analytics integration is enabled — a JDBC database via Glue's JDBC connector with credentials pulled from Secrets Manager, or partitioned Parquet in S3. The generated code calls `getResolvedOptions` to parse Glue job parameters, which the solution parses back to confirm the code only reads parameters the job will set.

Two agents sit above that pipeline. A complex-mapping agent adds sample values and targeted questions to the mapping review when field-level confidence falls below threshold, so a human reviewer in the React UI sees the specific ambiguity rather than a raw diff. A self-healing agent inspects a Glue job failure and chooses one new run: it regenerates code when the failure is a schema or type mismatch, promotes to a larger worker when the failure is out-of-memory, and refuses to retry when a rerun could duplicate already-written data or when the error class is outside its repair set. The two approval gates sit after step 4 (schema mapping) and step 6 (code testing), with a forced review loop when tests keep failing; approvals and rejections record the reviewer's identity, and a gate waiting for a human for 72 hours fails the run rather than silently proceeding.

The architecture is mostly reusable rather than magic. The interesting pieces for teams who want to copy it are the explicit confidence threshold that governs when mapping review can be skipped (only when every field pair is high-confidence and a name match corroborates the FM), the fact that reused mappings still default to review (so a mapping is not grandfathered in when new sources join), and the decision to run the generated transform inside a Glue interactive session before persisting the job definition — which catches most code-gen errors before they reach the Step Functions state machine and keeps the agent loop idempotent. The post does not publish code snippets inline; the companion GitHub repo is where the Strands agent prompts, the Jinja2 templates for the generated PySpark, and the CDK app live.

### 🎯 Takeaway (Hợp)
If you are evaluating "agents for data engineering" as more than a demo, this is the first fully-wired reference from a cloud vendor that bakes in approval gates, Data Quality enforcement, and a scoped retry policy rather than hoping the agent gets it right the first time. Nếu team đang pilot AgentCore, repo `sample-agentic-data-ingestion` là chỗ bắt đầu nhanh hơn viết lại từ đầu.

### 🔭 Overview (Tổng)
Databricks has launched UCDataset, a native PyTorch data loader in Beta on the Databricks AI Runtime that streams Unity Catalog Delta tables directly from cloud storage to the GPUs in a training job. The target workflow it replaces is a familiar one: exporting the table to Parquet before each run (which creates a stale second copy outside Unity Catalog lineage), loading the table into memory via `toPandas()` (which fails on large tables and pins everything on the driver), or streaming through a warehouse endpoint not designed for simultaneous GPU feeders. On a benchmark that trains a recommendation model against a 300 GB feature table across 8× NVIDIA H100 GPUs, Databricks reports an average 10x speed-up versus reading the exported Parquet copy. For teams whose training data already lives in Unity Catalog and who have been building their own per-GPU shard splitters, UCDataset moves the sharding into the loader and keeps lineage, deletion vectors, and run-time appends on the same path as the rest of the governance surface.

### 🔬 Details (Phân)
UCDataset reads table files directly from cloud storage and splits matching rows evenly across every GPU and data-loader worker in a distributed run, so the user does not write the balancing logic that is a common source of duplicated or skipped rows. Filters and Delta deletion vectors are applied at read time; appended rows picked up between epochs show up automatically on the next pass. The loader yields whole batches, so the recommended wrapper is a standard PyTorch `DataLoader` with `batch_size=None`. Training jobs run as the identity that launches them and Unity Catalog permissions apply on every read, which is the piece that was awkward with an export-to-Parquet path because the Parquet copy lived outside UC. Jobs are launched with `torchrun` via a `workload.yaml` and the AI Runtime CLI, with GPU count selected through `num_accelerators`.

Framework support is PyTorch-only at launch: the post explicitly names standard PyTorch training loops, PyTorch DataLoader, and DDP; it does not mention TensorFlow, Ray, or JAX. Beta limitations are specific enough to call out before planning adoption: UCDataset cannot read tables that have row filters or column masks, so governance patterns that lean on either will not work here yet. Multimodal support through the FILE type is called out as in progress, and a related `UCVolumeDataset` handles unstructured data in Unity Catalog volumes. The install story is a single pip line, `pip install databricks-uc-dataset`; the headline benchmark is not accompanied by throughput or latency numbers in the post, and no GA date is given.

Context-wise, UCDataset sits in a crowded space: Mosaic StreamingDataset, Hugging Face `datasets` with `IterableDataset`, Ray Data for materialised sharded reads, and NVIDIA DALI all exist as training data loaders, and some teams were already pointing Mosaic Streaming at Unity Catalog via a manual Delta → MDS conversion. The differentiator here is that UCDataset keeps Unity Catalog as the source of truth and makes permission enforcement part of the read path, which matters more for regulated data than for benchmark workloads.

### 🎯 Takeaway (Hợp)
If you train PyTorch models on Databricks and your source is a Delta table in Unity Catalog, UCDataset is the first-party data-loader path to start trialling now; just plan around the Beta limitations on row filters and column masks. Nếu team phụ thuộc vào row-level security hoặc column mask ở bảng training, chờ GA hoặc tiếp tục với Mosaic Streaming / Ray Data cho đến khi hạn chế này được gỡ.

The post does not specify quotas, rate limits, or supported regions, so capacity planning has to come off of the Glue documentation and Workday admin guide it links.

Pricing is $9.90 for the bare board and $10.90 for the pre-soldered version on Seeed's store; AliExpress is listed at $18.85 and the article flags the markup.

The IMU heater is the differentiator worth reading on. The LSM6DS3TR-C is a familiar 3-axis accelerometer plus 3-axis gyroscope part with a known drift characteristic as temperature changes — fine for motion detection, mediocre for anything where the gyro bias needs to be stable at sub-dps precision. Seeed has routed resistive heaters around the IMU package and brought them out under PWM control so firmware can run a simple closed-loop regulator against the IMU's built-in temperature sensor, holding the die at a fixed reference and side-stepping the drift curve. A 0.58 W budget is small enough to run off USB-C, and large enough to lift a 21 × 17.8 mm PCB above ambient by a meaningful margin — the effectiveness depends on enclosure thermal resistance and how often the system can tolerate the heater being on.

Software coverage ships for STM32CubeIDE, PlatformIO with Zephyr RTOS, and MicroPython, with CAN FD and IMU examples in the Seeed wiki. Wireless connectivity is deliberately absent — this is a wired-only board, which fits the CAN-bus and industrial-logger brief rather than the ESP32 wireless-first brief.

### 💡 Example
```c
// Sketch of a simple PWM-driven IMU heater loop (Zephyr pseudocode)
// Target: Seeed XIAO STM32C5, LSM6DS3TR-C with die temperature.
// Heater circuit rated up to 0.58 W; keep duty bounded to stay in spec.
#define IMU_TEMP_TARGET_C  40.0f
#define HEATER_PWM_PCT_MAX   60   // cap to keep <= 0.58 W in enclosure

void imu_heater_task(void) {
    for (;;) {
        float t = lsm6ds3_read_temp_c();
        float err = IMU_TEMP_TARGET_C - t;
        int duty = clamp((int)(err * 8.0f), 0, HEATER_PWM_PCT_MAX);
        pwm_set_duty(HEATER_PWM, duty);
        k_sleep(K_MSEC(200));
    }
}
```
