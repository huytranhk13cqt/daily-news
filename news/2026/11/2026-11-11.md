Databricks Pushes Unity Catalog Metric Views Into Power BI: Private Preview "Publish to Power BI" Turns Each Metric View Into One Semantic-Model Table, Maps Measures to DAX, Keeps Row Filters, Column Masks and ABAC on DirectQuery Against Lakehouse/RT or Databricks SQL, With One-Way Sync and No Materialization Yet

### 🔭 Overview (Tổng)
Databricks has opened a Private Preview of "Publish to Power BI" that lets Unity Catalog metric views project directly into Power BI semantic models, closing a gap that has hurt governance in nearly every Databricks-plus-Power-BI shop: metric logic rebuilt as DAX inside each `.pbix`, with each report free to drift to its own definition of revenue, ARR, or ROAS. The feature turns each metric view into one table in the semantic model, maps dimensions to Power BI columns and measures to native DAX measures, and keeps the join graph on the Databricks side — Power BI does not need to recreate relationships because the joins declared in the metric view execute in Databricks. Access control carries over as well: on DirectQuery, Unity Catalog row filters, column masks, and ABAC still apply, so the same report shown to two users can legitimately return two different numbers. For teams who have treated Power BI as the final mile of governance, this moves the metric contract from PBIX files into a Unity Catalog object that lineage, versioning and permissions can see.

### 🔬 Details (Phân)
The authoring shape is familiar to anyone who has used metric views. A metric view declares dimensions and measures over a source table or join graph, and the publish step walks the view and emits a matching Power BI table: dimensions become columns under the view's own name, each measure becomes a DAX measure, and joined dimensions appear as attributes on the generated table. The post gives a concrete example on a `campaign_performance` metric view — `total_spend = SUM(spend)` becomes `total_spend = SUM('campaign_performance'[spend])`, and the ratio `roas = MEASURE(total_revenue) / MEASURE(total_spend)` becomes `roas = DIVIDE([total_revenue], [total_spend])`. The modelling surface covered at preview includes joins, relationships, measure metadata (currency, decimal, percentage formats and descriptions), the standard aggregations (SUM, COUNT, AVG, MIN, MAX, MEDIAN, STDDEV, VARIANCE), distinct counts, ratios, filtered measures, and measures composed of other measures. Window measures land as current, offset and trailing windows — enough for most "rolling 28 days" and "same period last year" patterns without hand-written DAX. Publishing runs on demand from Catalog Explorer or automatically through a Power BI task in a Lakeflow Job, on schedule or after upstream tables refresh.

Storage mode matters more than usual here because it decides which governance surface wins. DirectQuery (default) against Lakehouse/RT or Databricks SQL pushes every slice back to the warehouse at query time, so Unity Catalog's row filters, column masks and ABAC remain authoritative and no second copy of the data lives in Power BI. Import mode is supported, but the copy follows Power BI permissions rather than UC access controls — a trade-off the post is explicit about. Lakehouse/RT with DirectQuery is pitched as the real-time-dashboarding story: no separate serving layer, no extract step, and the same AI/BI dashboards and Genie that talk to metric views can share the same numbers with Power BI report consumers. Changes propagate through republish rather than hot-reload, so a metric definition update becomes visible in Power BI after the next manual Publish or the next scheduled Lakeflow task run.

Preview caveats are specific enough to plan around now. Sync is one-way: an analyst editing a published DAX measure in Power BI is not writing back to Unity Catalog, so edits get overwritten on the next republish and governance stays at the view. Materialization of metric views for faster Power BI queries is explicitly "coming soon" — until then, DirectQuery performance follows the underlying metric view's query path, which matters for very wide dimension slices. Access is still gated through account teams, and the post does not pin supported Power BI versions, connector details or Databricks Runtime versions; teams planning a pilot should expect to confirm those through their Databricks contact rather than from the public docs. The accompanying Microsoft Learn page covers the actual publish workflow.

### 🎯 Takeaway (Hợp)
If your Databricks stack already uses Unity Catalog metric views and your BI tier is Power BI, this is the first-party path to collapse duplicated DAX into one governed metric contract — start a pilot on a single semantic model with DirectQuery and compare the numbers tool-by-tool before expanding. Nếu team còn giữ nhiều measure DAX trùng định nghĩa nhưng lệch số, Publish to Power BI là lý do rõ ràng để dọn phần này quý tới, đừng đợi GA.

### 🔭 Overview (Tổng)
AWS and Confluent have co-published a production migration case study of Confluent's internal observability platform, which indexes hundreds of terabytes of logs per day across Kafka, Connect and Flink fleets using Amazon OpenSearch Service with cross-cluster search for reads and direct writes into P0 and P1 domains. The headline change is a hot-tier move from the previous-generation r6gd (Graviton2 with local NVMe) to OpenSearch Optimized oi2, the current-generation OpenSearch-specific instance that uses local NVMe as a primary tier and copies data synchronously to Amazon S3 for 11-nines durability. Across four production domains the fleet dropped from 168 to 90 nodes, a 46% reduction, while indexing latency roughly halved from 0.18–0.19 ms to 0.08–0.10 ms and write queues collapsed from 8–38 operations to under one. The post is worth reading because the migration happened in two measurable phases — a same-footprint swap, then rightsizing — with numbers for each.

### 🔬 Details (Phân)
In Phase 1, every r6gd node was replaced with an oi2 node of equivalent size via an in-place blue/green re-provision through the Amazon OpenSearch Service control plane, and CPU dropped to roughly one-third of baseline on the same ingest — about 2.7x more headroom per node. Phase 2 rightsized by removing nodes one step at a time while watching heap, CPU, indexing latency, write queues, write rejections and search p90/p99. By the end, Domain A went from 30 to 12 nodes (-60%) with average CPU 49% → 43% and indexing latency 0.19 → 0.08 ms; Domain B went from 36 to 18 (-50%) with CPU 60% → 40% and latency 0.18 → 0.08 ms; Domain C from 39 to 27 (-31%) with CPU 58% → 39% and latency 0.19 → 0.09 ms; Domain D, a lower-volume tier, from 63 to 33 (-48%). Each oi2 node ended up carrying roughly 1.9x the load of an r6gd node, with zero write or primary-write rejections in the final state. AWS's internal benchmarks (not the Confluent production numbers) list oi2 as up to 9% higher indexing throughput than the earlier OR2 and up to 33% more than I8g, across sizes from large to 24xlarge with up to 22.5 TB of storage.

The architectural reason the ratios land the way they do is that OpenSearch Optimized Instances use physical replication — segments copy between primaries and replicas — rather than document replication, so indexing CPU happens only on primaries. Combined with local NVMe fronting synchronous S3 durability, the write path shortens and heap pressure per shard falls, which is what lets the fleet consolidate without rejections. The tuning guidance that fell out of the migration is prosaic but worth quoting: use ~10 MB bulk requests, use multiple parallel clients, consider raising primary shard count but avoid over-sharding, and keep refresh interval at 10 seconds or higher (the Optimized Instance default). Reporting also shifted: with replicas, the indexing-rate metric understates real throughput because it only counts primaries, so capacity planning needs to compensate for that.

On cost, AWS quotes an estimated 18% lower hot-tier spend at on-demand list, and 47–51% below the original r6gd on-demand baseline with 1-year reserved pricing (figures excluding UltraWarm, snapshots and dedicated-master tiers, and pending quoted reserved rates). The honest caveats are also called out: heap, not CPU, set the rightsizing floor — removing nodes concentrates shards per node and raises average heap on every domain — and Domain D is the one outlier, where CPU rose from 43% to 56% even after rightsizing and the write queue, while much lower, is the only one not near zero. R8gd was not benchmarked here, so the comparison is specifically against r6gd.

### 🎯 Takeaway (Hợp)
If you run a high-throughput OpenSearch logging or observability tier on r6gd or OR2, the direction of travel is clear: a blue/green swap to oi2 first, then rightsize while watching heap more than CPU, and expect roughly half the node count with faster indexing. Trước khi migrate production, nhớ tính lại shard density để heap/shard không vượt ngưỡng sau khi gộp node.

### 🔭 Overview (Tổng)
STMicroelectronics has started shipping the STM32G5, a mixed-signal Arm Cortex-M33 series aimed squarely at digital power supplies, photovoltaic inverters, EV chargers, robotics and motor control — the workloads where the analog front-end and the PWM back-end usually matter more than core throughput. The G5 pushes the Cortex-M33 to 280 MHz with TrustZone, FPU, DSP and MPU, hits 1,136 CoreMark (roughly double the STM32G4's 569), and pairs that with up to 112 KB SRAM, 64 KB to 512 KB dual-bank flash with ECC and read-while-write, and up to 96 KB of high-endurance data flash rated for 100,000 cycles — the kind of EEPROM-emulation budget that embedded power controllers eat through quickly. The headline analog pieces are an HRTIM with 12 PWM outputs at 111 ps resolution (down from 184 ps on G4), three 12-bit 5 MSPS ADCs with up to 39 channels and hardware oversampling, up to eight analog comparators with 20 ns propagation delay, three PGA op-amps on G55x/56x, CORDIC and up to two FMAC filter accelerators, and a 16-element programmable logic array with 128 inputs and 16 outputs for custom signal routing without burning CPU.

### 🔬 Details (Phân)
Memory and I/O scale with the sub-family. G53x/54x stop at 60 KB SRAM, 23-channel dual ADC, 62 GPIO and 24 KB data flash per bank; G55x/56x take those to 112 KB SRAM, three ADCs with 39 channels, 103 GPIO and 48 KB data flash per bank, and add the 16-element PLD, the three PGA op-amps, two position encoder interfaces (Hiperface DSL and EnDat 3.0), USB Full-Speed plus USB Type-C Power Delivery 3.1 on selected packages, and an XSPI interface to external PSRAM, NOR/NAND flash, HyperRAM and HyperFlash. Fieldbus coverage is three FDCAN controllers, up to four I²C (SMBus/PMBus), one I3C, and the usual mix of USART/UART/LPUART, SPI and I²S. Timers include the HRTIM, up to three advanced motor-control timers, four 32-bit and nine 16-bit general-purpose timers, four basic timers and a low-power timer. Security is a full TrustZone stack with ST immutable Root of Trust, secure boot, secure firmware install/update, debug authentication, OTFDEC for external XSPI on the G56x crypto variants, AES/PKA/HASH/TRNG, hide protection, active tamper, 1 KB OTP and a 96-bit unique ID; post-quantum cryptography is software-only here, and SESIP Level 3 plus PSA Certified Level 3 are described as in progress.

Placed next to the field it has to fight — TI C2000 F28P65 for fast-loop digital power, NXP MCX-A, Renesas RA4T for motor control, Infineon XMC4 and the earlier STM32G4 itself — the G5's pitch is that it keeps the G4 pin map and tool chain (STM32CubeG5 with HAL2, STM32CubeMX2, STM32CubeIDE, X-CUBE-MCSDK for motor control, X-CUBE-DPOWER for digital power) while doubling CoreMark, cutting HRTIM step resolution to 111 ps, raising ADC sample rate from 4 to 5 MSPS, and adding on-chip PGA op-amps and the PLD so a current-sense front end or a protection chain can live inside the MCU rather than on a separate op-amp and CPLD. The packages span 32 to 128 pins (QFN, QFPN, LQFP, UFBGA), and exposed-pad TQFP/LQFP options exist for thermal paths that matter in power applications.

Availability and tooling are set. STM lists the MCU in production at about $1.0340 per unit at 10,000-piece volumes, with the NUCLEO-G564RE Nucleo-64 board at $47.59 and the B-G564E-MC1S motor-control Discovery kit with EnDat 3 and HIPERFACE DSL interfaces at $78.61 on the ST eStore (orders of two or more). A B-G564E-DPOW1 digital-power Discovery is listed as "coming soon," and a dual-core STM32G5D series with hardware post-quantum cryptography acceleration is on the roadmap for 2027. For teams who have been chasing microsecond-class control loops with external CORDIC and discrete comparators, most of that discrete work moves inside the part.

### 🎯 Takeaway (Hợp)
If your current STM32G4 design is bottlenecked on HRTIM step resolution, ADC sample rate, or the missing on-chip PGA, the G5 is a drop-in-tooling upgrade rather than a rewrite — NUCLEO-G564RE is cheap enough to prototype the control loop against this quarter. Với các design tiếp theo cần PQC hardware trên Cortex-M33 ST, chờ G5D 2027 hoặc tiếp tục làm PQC bằng software stack trên G5 hiện tại.

The MCU is a Microchip PIC32CK2051SG01144 (32-bit Cortex-M33 at 120 MHz) paired with 2 MB of flash and 512 KB of RAM, which is a generous budget for a Nano-sized board and leaves room for a full Arduino sketch stack alongside a lwIP-class TCP/IP stack and a CAN FD application profile. ### 🔬 Details (Phân)
The decision to use Microchip's PIC32CK — a Cortex-M33 with TrustZone normally seen on Microchip's own evaluation boards — rather than another STM32 or RA MCU gives Arduino a secure-boot story on an industrial board without having to add a separate secure element, and the 2 MB / 512 KB memory budget is bigger than what Nano 33 BLE or Nano RP2040 Connect currently offer. The on-board fieldbus set is the real differentiator: CAN FD and RS485 transceivers in particular remove a routine source of bring-up pain on prototype industrial boards (buggy transceiver wiring, mis-selected termination, 5 V level mismatches), and Ethernet on a Nano footprint has previously required an external PHY module or a hat. Arduino is positioning the board for real-time machine controllers, fieldbus gateways, motor drives, smart sensors, touch panels, smart lighting and HVAC zone managers, and energy management nodes — all cases where a $30 Nano-compatible with three buses already wired is a materially faster path to a working prototype than stacking shields.

Context-wise the Nano XL Link sits in the same conversation as the Phoenix Contact PLCnext-style compact industrial controllers, the Siemens IOT2050 and IOT2040 Linux gateways, Advantech's WISE-series IoT edge boards, and — much closer in price and spirit — Seeed's XIAO STM32C5, which shipped last week with dual CAN FD. The Nano XL Link gives up CAN controller count (one vs. two on the XIAO STM32C5) but picks up on-board RS485 and 10/100 Ethernet, which is the combination industrial retrofits actually ask for. The Connector Carrier makes that more explicit: a DIN rail form factor compatible with 4U enclosures and screw terminals rather than Dupont headers is a direct bid for low-volume industrial control production rather than hobby work, and it doubles as a reference design that customers are implicitly invited to clone.

### 🔭 Overview (Tổng)
LabWired, released under the MIT license by Andrii Shylenko, is a MCU firmware simulation core that runs compiled firmware against modeled CPUs and peripherals, with emphasis on board-level simulation rather than just CPU emulation. That distinction is the project's pitch against alternatives in the same space (QEMU, Renode, Wokwi): the simulator models the full board — sensors, displays, bus devices — so a test can check not only that the CPU reached the end of `main()` without a fault, but what the firmware actually said over I²C, how the SPI framing looked, and what frames went to the display driver. The headline example on CNX Software builds a Unity test binary with PlatformIO for a virtual Nordic nRF52840 development kit and runs `pio test --without-uploading -e nrf52840_dk`, passing all three unit tests in 1.18 seconds with no J-Link cable and no DK on the desk. For embedded CI, that is the metric that matters.

### 🔬 Details (Phân)
Architecture coverage spans Arm Cortex-M0+, M3, M4, M7 and M33, RISC-V, and Xtensa LX6/LX7 (which gives it some ESP32 variants), with platforms explicitly named including STM32L476, RP2040, nRF52840 and ESP32. The example directory in the repository ships 200+ board configurations, and a validation matrix enumerates supported boards and peripherals with their current fidelity against real hardware. That last part is the uncommon design choice worth calling out: a Fidelity Ledger documents where the model is incomplete or substitutes for the real device, so a test author knows which assertions are safe and which rely on fixtures that would fail on silicon. The primary interface is a CLI designed to be called from a terminal, from CI (GitHub Actions, GitLab CI) or from an AI coding agent via MCP — the project page mentions that Claude Code was used in development mainly for MCP integration, and the simulator can be driven from an agent's tool loop to check whether a firmware change actually behaves the way the agent claimed.

In practice the simulator captures UART and bus output, exposes register state, and lets tests assert on whole scenarios — "after boot, the LCD controller received this sequence of commands, and the I²C transaction to the IMU returned this frame." A browser-hosted Playground demonstrates a NUCLEO-L476RG wired to an ultrasonic sensor, a Nokia display and a logic analyser, which is useful for showing colleagues what full-board simulation looks like without installing anything. Licensing is a split model the article is explicit about: the core simulator and validation assets are MIT-licensed, while the application UI, hosted Playground behavior and product surfaces are closed source and live outside the open package. A pricing page covers hosted usage via "LabWired AI Tokens" if a team wants to run tests against LabWired's infrastructure rather than locally.

Where this lands relative to the existing tools is the question. Renode is still the reference open-source full-system simulator for embedded Linux and multi-node RF testing, QEMU remains the broadest architecture coverage, and Wokwi is the easiest for Arduino-shaped projects. LabWired's distinguishing bets are the MIT license on the core (QEMU is GPL, Renode is MIT but harder to adopt for CI-only use), the Fidelity Ledger as a documented contract on where the model is incomplete, and the PlatformIO + MCP integration that fits how embedded teams increasingly run tests from code assistants. Numbers to plan around: the 1.18 s run-time on three Unity tests is the only published benchmark; tests that exercise RF stacks, DMA at nominal speed, or timing-sensitive peripherals will not necessarily match hardware, and the Fidelity Ledger is the place to look before trusting a green CI run for a safety-relevant change.

### 🎯 Takeaway (Hợp)
For teams who want firmware CI on a PR without a per-branch hardware rack, LabWired is worth a weekend trial: build the current test suite, point `pio test --without-uploading` at a matching virtual board, and compare which Unity tests pass or fail versus the real hardware. Nếu CI hiện tại đang skip test vì không có board trong runner, đây là cách bật lại — nhưng vẫn phải đọc Fidelity Ledger trước khi tin các test timing-sensitive.
