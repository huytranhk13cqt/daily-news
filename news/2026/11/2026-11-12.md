### 🔭 Overview (Tổng)
Databricks has taken Genie Ontology to general availability and used the launch to collapse several adjacent pieces into one governed knowledge layer for analytical agents. The post describes the ontology as an agentic artifact — built by agents, governed by people — that stitches together modeled knowledge from Unity Catalog with learned knowledge mined from dashboards, SQL queries, notebooks and Power BI semantic models. The release lands alongside the GA of Genie Search over Google Drive, Jira, Confluence and Workday, Ontology Snippets, an organizational directory connector for Workday, and Unity Catalog Domains, Subdomains and Pages, plus a preview of a dedicated Ontology Manager. Importantly, the same ontology is exposed through Genie MCP, so external agents such as ChatGPT, Claude and Microsoft Copilot can consume the context under Unity Catalog permissions rather than through ad-hoc connectors. For teams who have spent 2026 pinning agent answers to their own numbers, this is the first Databricks release that treats the business layer — not just the data layer — as a Unity Catalog object.

### 🔬 Details (Phân)
The components break along a modeled-vs-learned line. On the modeled side, Metric Views (now GA since mid-2026) carry certified KPIs, while Unity Catalog Domains and Subdomains organize catalogs, schemas and tables by business area and Pages hold authoritative definitions of business concepts attached to those objects. On the learned side, Ontology Snippets are generated from existing Databricks artefacts — dashboards, saved SQL, notebooks — and external knowledge sources, with Power BI supported as a beta source and Tableau and Sigma listed as "coming soon." OntoRank is the ranking function that picks which snippets and pages get served into an agent's context, prioritizing authoritative sources and respecting the caller's Unity Catalog permissions. A separate preview, the Ontology Manager, exposes entities and relationships as an interactive graph and lets stewards curate rather than hand-edit. The external-agent surface is Genie MCP; under the hood, Unity Gateway governs usage limits, guardrails and auditing for every agent connection.

The published benchmark is the first time Databricks has attached specific numbers to the agentic-analytics claim. The scenario is "Calderwick Energy," a fictional UK electricity and gas supplier built with Turing, with hundreds of tables (the largest at ~120 million rows of half-hourly meter data), scheduled jobs, dashboards, saved SQL and existing Genie Agents. Each agent ran five times per task against the same live workspace. Genie with Genie Ontology posted a 91% pass rate at 100.3 s and 431,829 tokens per run on average. Two unnamed frontier agents — Agent A and Agent B — scored 45% and 58% at 434.6 s and 306.5 s, consuming 889,019 and 1,051,070 tokens respectively. The title's "1.6×" matches 91/58 on the stronger baseline; the token-economy claim is "less than half" (≈51–59% fewer than the two agents). The example that is easiest to reason about is a historical rate lookup: the `cfd_rate_p` column reflects the current FY25/26 assumption (0.31 p/kWh), but notebook `45_mart_bill_cost_stack` documents the correct historical FY24/25 rate (0.52 p/kWh), and only Genie returned 0.52 on all five runs because the ontology surfaced the snippet.

Caveats are worth reading before planning migrations. Genie Search's SharePoint connector remains in beta, and Ontology Manager is described as "coming soon" in preview, so authoring workflows will stabilize after GA rather than at it. There is no published comparison of Genie with the ontology versus Genie without it, so the delta the ontology adds inside the same platform is not quantified — the headline numbers are against external frontier agents. Finally, "learned from Power BI semantic models" is a one-way import today, so DAX-level edits Power BI authors make after a learn step are not reconciled back into the ontology. For teams already running Unity Catalog metric views and heavy dashboard inventories, the pieces to try first are Domains plus Ontology Snippets, since those get the most knowledge into the context with the least new authoring.

### 🔭 Overview (Tổng)
AWS and Samsung Ads have co-published an architecture for reading Snowflake-managed Iceberg tables from AWS analytics engines without copying the dataset, driven by a real feature-engineering workload on Amazon SageMaker AI. The pipeline's terminal stage writes Iceberg tables backed by Samsung Ads' own S3 bucket but managed by Snowflake's Horizon Catalog, and AWS Glue Data Catalog federates to that Snowflake catalog so Athena (and, per the post, any engine Samsung Ads chooses) can read the same tables under AWS Lake Formation permissions. The authentication path is the part that is worth studying: Amazon Cognito issues External OAuth tokens via the `client_credentials` grant, a Pre Token Generation Lambda trigger (V3_0) injects the `aud` claim Snowflake External OAuth validation requires, and the Glue connection runs inside a private VPC subnet over PrivateLink. It is a template more companies will copy because the moving parts — Cognito user pool, External OAuth security integration, Glue Iceberg federation, Lake Formation enforcement — are now stable AWS primitives.

### 🔬 Details (Phân)
On the Snowflake side, tables are created with `CATALOG = 'SNOWFLAKE'` and an external volume pointing at the customer S3 bucket, so the data files live in AWS while metadata and transactions live in Snowflake Horizon. A `CREATE SECURITY INTEGRATION ... TYPE = EXTERNAL_OAUTH` statement pins token type `CUSTOM`, trusts the Cognito user pool's issuer, and reads the user pool's JWKS URL to validate incoming JWTs. Samsung Ads chose Cognito over Snowflake-issued keys so that new machine-to-machine clients become a self-service user-pool app client with its own read-only Snowflake role — rather than a shared secret handed out by the data platform team. The default Cognito access token omits the `aud` claim Snowflake insists on, so a Pre Token Generation V3_0 Lambda trigger stamps it in before the token is signed; scope is `snowflake/catalog.read`. On the AWS side, an AWS Glue connection carries the client credentials and talks to the Snowflake Iceberg REST endpoint for metadata and S3 object locations.

The networking around that connection is worth replicating. The Glue connection runs in a private VPC subnet and reaches Snowflake over PrivateLink, while the Cognito token endpoint — which is public — is reached through a NAT gateway. Because the Snowflake PrivateLink endpoint service does not provide private DNS, Samsung Ads uses an Amazon Route 53 private hosted zone to resolve the Snowflake hostname inside the VPC; without it, the Iceberg REST client cannot find the endpoint. From that point, the Glue Iceberg REST client resolves table metadata, and Athena delegates catalog resolution and permission checks to Lake Formation, which generates short-lived scoped S3 credentials for the actual Parquet reads. The result is that Athena never holds long-lived S3 credentials to Samsung Ads' S3 bucket, and permission policy lives in Lake Formation as table/column/row grants rather than in bucket policies.

What is explicitly in the published piece is the authentication plumbing and the Snowflake-side security integration; what is not pinned in the visible content is the usual set of numbers — data volume, query latency, cost delta against a copy-based alternative — nor which engines beyond Athena were exercised in production (the post says engineers "can choose the query engine that fits each training job" but names Athena). Teams planning to clone this should expect to firm up two choices themselves: whether to also enable Lake Formation fine-grained access control on the federated catalog entry, and how to rotate the Cognito app-client secrets without disrupting active SageMaker training jobs that hold refresh tokens. The Snowflake-Iceberg-plus-Cognito pattern has sharp operational edges — the `aud` claim behavior, the private DNS requirement, the NAT-vs-PrivateLink split — that are easier to get right by starting from this reference than from the component documentation alone.

### 🎯 Takeaway (Hợp)
If your team is already storing Iceberg tables in Snowflake Horizon and your analytics is on AWS, this is a workable zero-copy path — stand up a Cognito user pool and a Pre Token Generation Lambda on a sandbox account first, confirm the Iceberg REST endpoint resolves over your private DNS, and prove a Lake Formation grant before moving production tables. Nếu kiến trúc hiện tại đang nhân bản dataset từ Snowflake sang S3 chỉ để Athena/EMR đọc được, mẫu federation này là lý do để đánh giá lại pipeline đó trước khi tiếp tục trả tiền cho hai bản copy.

### 🔭 Overview (Tổng)
AWS has shipped Part 2 of its playbook for running HBase on Amazon EMR, this time scoped to compaction — the subsystem that most often causes the symptoms operators mistake for RegionServer failure. Part 1 covered coordinator startup, RegionServer stops and regions in transition; Part 2 covers how to confirm that compaction is the cause of latency spikes, which parameters to tune in which order, and when the problem has outgrown tuning. The post is useful because it quantifies EMR-specific defaults that differ from upstream HBase: `hbase.hstore.blockingStoreFiles` is 10 on Amazon EMR for HBase-on-S3 but 16 on Apache HBase 2.x, and a specific window of EMR versions (7.10 through 7.13) with HBase-on-S3 ships with the wrong S3A read policy for the workload, which slows compaction and keeps HFile counts rising. For teams running HBase on S3 — the dominant deployment model on EMR today — this is the operational playbook that pins the exact knobs to turn.

### 🔬 Details (Phân)
The symptom cluster is specific enough to recognize. Latency climbs on some RegionServers but not others, and the affected set rotates over time; compaction queue length grows on the affected server; clients see `RegionTooBusyException`, call timeouts and retries, and the RegionServer log carries a "too busy" warning about exceeding the memstore limit; writes stall periodically. On HBase-on-S3, 503 Slow Down responses from S3 appear in logs. A tell-tale cadence is a weekly rhythm that lines up with the ~seven-day default major compaction interval (with a jitter factor of 0.5). On Amazon EMR 7.10–7.13 specifically, the post calls out slow compactions and HFile counts that keep growing because the S3A read policy is set to `normal` instead of `sequential` — a configuration mismatch for the large sequential reads that compaction performs, and the first thing to fix.

The tuning order is prescriptive. Step 1, on EMR 7.10–7.13 with HBase-on-S3, set `fs.s3a.experimental.input.fadvise=sequential` through the `hbase-site` classification and restart HBase. Step 2, lower the `hbase.hstore.compaction.throughput.*` bounds to cap the I/O compaction uses; the post notes that HBase lifts this throttle anyway once a store reaches `hbase.hstore.blockingStoreFiles`, so the throttle is a budget, not a ceiling. Step 3, tune `hbase.hstore.compaction.min`, `hbase.hstore.compaction.max` and `hbase.hstore.compaction.min.size` so that compactions trigger less frequently per store. Step 4, move the work out of peak hours with `hbase.offpeak.start.hour` and `hbase.offpeak.end.hour`. Step 5, if the automatic major compaction is the specific source of instability, set `hbase.hregion.majorcompaction=0` and schedule major compactions externally. Step 6, escalate to AWS Support only once these fail, because the remaining causes are usually capacity or schema design rather than configuration.

For diagnostics, the post avoids CloudWatch and sends operators to the HBase web UI (port 16010 for the coordinator, 16030 for RegionServers) for compaction queue length, store file count, request count and BlockCache/BucketCache hit rate, and to `hbase canary` for per-region read-latency baselines. It also points at log searches for compaction start/completion messages, "too many store files" and JVM pause messages, and at `hbase hfile -m -s` for store file layout. The one numeric trap worth internalizing is the interaction between `hbase.hstore.blockingStoreFiles=10` (EMR default), `hbase.hregion.memstore.flush.size` and `hbase.hregion.memstore.block.multiplier` — once blocking kicks in, write latency goes from steady to bursty and clients experience the "too busy" warning rather than slow writes, so alerting on queue length is more useful than alerting on average write latency alone.

### 🎯 Takeaway (Hợp)
Before raising cluster size on an HBase-on-S3 EMR cluster that is "stalling writes weekly," walk the six-step list against the exact EMR version the cluster runs — on 7.10–7.13 the first step alone has moved several clusters back under their SLAs without a resize. Nếu team đang chạy HBase-on-S3 trên EMR 7.10–7.13, đặt `fs.s3a.experimental.input.fadvise=sequential` là thay đổi rẻ nhất và có thể roll-forward được trước khi chỉnh compaction throughput.

### 🔭 Overview (Tổng)
Renesas has opened the RZ/T2N industrial MPU, a 14-variant family pairing up to two Cortex-A55 application cores at 1.2 GHz (600/1200 MHz options) with two Cortex-R52 real-time cores at 800 MHz (400/800 MHz options) on a single die. The intent is a one-chip controller that runs Linux on the A55 side for HMI, OPC UA and condition monitoring while handling deterministic control — EtherCAT or PROFINET IRT slaves, four-axis motor control, encoder interfaces — on the R52 cores, with ECC memory throughout to meet the reliability expectations of industrial deployment. Pricing is set at about $50 per chip and the RZ/T2N-EVKIT evaluation kit lists for $583; DigiKey and Mouser both show 50 units in stock, so the part is in production rather than on sampling. For teams who have been running Linux and real-time firmware on separate SoCs wired over EtherCAT or dual-port RAM, this is the first Renesas family that collapses that into a single package without giving up the R52 TCM budget.

### 🔬 Details (Phân)
The compute budget is unusually generous on the real-time side. Each Cortex-R52 has 16 KB I/D cache, NEON and FPU, and — critically — 576 KB of ECC-protected tightly coupled memory (512 KB ATCM + 64 KB BTCM); the A55 side carries 32 KB L1 I/D cache per core, 128 KB L2 per core and a shared 256 KB L3. On-die SRAM is 2 MB with ECC. External memory is a 16-bit LPDDR4-1600 interface supporting up to 2 GB with inline ECC, so a single-ECC-error-correct path exists end-to-end. Storage coverage is two SD/eMMC, two xSPI (Quad/Octal SPI, HyperFlash, HyperRAM) and an 8-bit NAND controller. Networking is where the differentiation is: three Gigabit MACs, a three-port TSN switch and a three-port EtherCAT slave controller on selected variants, with PROFINET RT/IRT, EtherNet/IP, HSR/PRP (on some variants), DLR, FRER, IEEE 1588 PTP, 802.1Qbv scheduled traffic and 802.1Qbu/802.3br frame preemption all listed.

For motor control, the RZ/T2N carries up to four-axis three-phase complementary PWM, a 31-channel GPT and nine-channel MTU3, and up to eight encoder channels covering A-format, EnDat 2.2, BiSS-C and HIPERFACE DSL, with up to four channels available for EnDat 3.0 and BiSS-Line. There are up to 15 ΔΣ channels (13 on 489-pin parts), two trig accelerators, and three 12-bit ADCs across 16 channels. Field-side peripherals round out with two CAN/CAN FD (FD by variant), six SCI plus eight SCI dedicated to encoders, three I²C, four SPI, USB 2.0 HS OTG, PCIe Gen2 x1 and up to 201 GPIOs. Security tracks what industrial customers now expect: TrustZone across the family, secure boot and secure update, JTAG authentication on selected variants, hardware AES/RSA/ECC/SHA and a TRNG on selected variants, and security variants that add on-the-fly LPDDR4 and external flash decryption. Packages are 537-pin FBGA (21×21 mm, 0.8 mm pitch) or 489-pin FBGA (16×16 mm, 0.65 mm pitch), and junction temperature is −40 °C to +125 °C.

Software is the piece that decides whether the part is adopted on schedule. Renesas ships the RZ Flexible Software Package (FSP) for the R52 side with sample programs for EtherCAT, EtherNet/IP, OPC UA, Modbus, encoders and four-axis motor control, and the RZ Linux BSP Plus (Linux kernel 6.12, Yocto 5.0 Scarthgap) plus a Multi-OS package with OpenAMP for the A55 side; e² studio is the IDE. Functional safety software is called out as planned for H2 2027, which matters for designs that need SIL2/SIL3 claims in the near term. Accessories are a nontrivial outlay: the Inverter Board Kit lists at $941.20 (currently out of stock at DigiKey and Mouser), a standalone inverter board at $411.80 and an MC-COM communication board at $176.47. Compared with Renesas' own RZ/T2H (quad-core A55 variant) and the R52-only RZ/T2M / RZ/T2L, the T2N is the mid-tier that lets a single board carry both Linux and hard real-time on the same silicon; against TI's AM243x / AM24xM, NXP's MCX-N / i.MX RT1180 and ADI's ADSP-CM41x in the same slot, the TSN+EtherCAT+four-axis combination on one SoC is the specific gap the T2N fills.

### 🎯 Takeaway (Hợp)
If your current servo-drive or industrial-gateway design carries a Cortex-A MPU wired to a separate R-core MCU across a backplane, prototype a single-board replacement on the RZ/T2N-EVKIT and validate the EtherCAT slave + PROFINET RT paths before committing to the layout — the $583 kit price pays for the layout and bring-up time saved on dual-chip designs. Với các team đang chờ silicon có functional safety, chú ý rằng Renesas lộ trình SIL stack vào H2 2027, nên những design cần SIL ngay nên tiếp tục kết hợp RZ/T2H + MCU chuyên dụng.
