### 🔭 Overview (Tổng)

Sergey Melnik's follow-up to Reynold Xin's Lakebase post lays out how Databricks is positioning LTAP — a lakehouse-anchored transactional engine — against the more common CDC-based pattern of running Postgres beside a mirrored lake. The central claim is that LTAP does not replicate the database to the lake at all; the lake is the only durable copy of the table, and the Postgres compute node is a cache in front of it. That framing changes how recoverability, consistency, and write amplification should be reasoned about when choosing between LTAP and a classic replicated warehouse feed. The piece is explicitly aimed at engineers who have been asked "is this just CDC with extra steps?" and want a mechanical answer.

### 🔬 Details (Phân)

Mechanically, a write becomes durable once its WAL entry reaches a quorum of safekeepers; the pageserver then applies the log, holds hot pages in memory and local disk, and materializes data to object storage. Reads start at the compute node's buffer cache and local file cache and only fall back to the pageserver on a miss. Storage carries a dual physical layout — point lookups land on 8 KB Postgres heap pages, while scans read Parquet behind Delta or Iceberg, and the Parquet files carry heap block, offset, and MVCC version metadata so the engine can rebuild heap pages from columnar data; values Parquet cannot represent spill into an overflow field in the same table. Indexes stay in the hot tier and are never transcoded to Parquet.

Consistency for analytical queries is pinned at a single LSN: the planner picks a current LSN, pulls almost all rows from object storage up to that LSN, then merges recent dirty pages from the pageserver so all tables in the query are read at one point in time, which Melnik positions as REPEATABLE READ-equivalent. Small tables stay in the page cache and skip Iceberg commits outright. The materialized snapshot can lag by the compaction interval, which the post pegs at "several minutes" rather than a tunable knob. Two layers that could look like replicas — the page cache and the local file cache — fail the article's test for a replica, which is whether you could query it or fail over to it as its own database.

The CDC critique is quantitative in shape, even without a benchmark table. On write-heavy workloads, logical decoding has to read at least the WAL volume because it cannot collapse repeated page changes, while LTAP's dirty-page compaction reads a fraction of that because it parallelizes over pages using WAL summaries (Postgres 17+) or pageserver LSM trees and commits one Iceberg snapshot. Replication slots pin WAL on disk until the consumer catches up, logical decoding doesn't emit DDL, and tables without a primary key need `REPLICA IDENTITY FULL` — all operational scars the LTAP design sidesteps. The acknowledged limitation is the one every lakehouse hits: columnar files are heap-ordered, which is a poor clustering key for range predicates like `order_date`, so silver-table clustering is still required.

### 🎯 Takeaway (Hợp)

For teams deciding whether to pipe Postgres into a warehouse via Debezium or adopt Lakebase, the new content here is the explicit tier-vs-replica frame and the WAL-volume-vs-dirty-page math. That is the pitch to evaluate: not just "unified storage" but "we read less than your CDC pipeline does per commit." Đọc bài này trước khi quyết định kiến trúc Postgres-to-lakehouse tiếp theo, kể cả khi bạn vẫn ở lại với CDC.

### 💡 Example

```sql

-- (A) Point lookup -> 8 KB heap page path
--     Served from page cache / pageserver, never scans Parquet.
SELECT *
FROM   orders
WHERE  order_id = 93217841;

-- (B) Scan -> Parquet path (Delta/Iceberg)
--     Reads columnar files at a single LSN picked by the planner;
--     recent dirty pages are merged in from the pageserver.

       count(*)                    AS n,
       sum(amount)                 AS gmv
FROM   orders
WHERE  order_ts >= now() - interval '30 days'
GROUP  BY 1
ORDER  BY 1;
```

### 🔬 Details (Phân)

The in-place Spark path uses Iceberg's `add_files` procedure to generate Iceberg metadata directly over the existing Parquet files; the Iceberg table inherits the source schema, partitioning, and file layout, and none of those can change during the migration — if you want hidden partitioning or a different file size, this path is a non-starter. The second in-place path runs Apache XTable on an EC2 host, reads the Hudi commit timeline, and writes matching Iceberg metadata that points at the same Parquet files, so both formats share one physical copy of the data; this is the lowest-risk option for environments that still have Hudi readers. The full-migration path uses `CREATE TABLE AS SELECT`, `INSERT INTO ... SELECT` or Spark's `writeTo()`, and this is the one you pick when you want to rewrite the layout: change schema, apply hidden partitioning, re-sort, or target a larger file size. For very large tables the post recommends seeding with a small CTAS and then loading partition by partition in parallel batches with checkpoints, acknowledging that this approach needs extra compute and a window of temporary double storage.

The notebook-level configuration is spelled out concretely: Glue 5.1, `G.1X` workers, five workers, a 30-minute idle timeout, and the magic `--datalake-formats: hudi,iceberg` that pulls both runtime extensions into the job. The limitations are stated plainly in the article: in-place methods can't change schema, partitioning or file shape; full migration doubles storage while the source and target coexist. -- Sketch of the dynamic MVT tile query from the post:
```sql
-- select features near the tile, reservoir-sample, simplify, encode as MVT.
WITH bounds AS (
  SELECT ST_TileEnvelope(:z, :x, :y) AS env
),
candidates AS (
  SELECT id, properties, geom
  FROM   features, bounds
  WHERE  geom && ST_Expand(env, 16 * (ST_XMax(env) - ST_XMin(env)) / 4096)
),
sampled AS (
  SELECT * FROM candidates USING SAMPLE reservoir(50000 ROWS)
),
encoded AS (
  SELECT id, properties,
         ST_AsMVTGeom(
           ST_Simplify(geom, GREATEST(0.1,
             (ST_XMax((SELECT env FROM bounds)) -
              ST_XMin((SELECT env FROM bounds))) / 4096 * 0.5)),
           (SELECT env FROM bounds), 4096, 16, true
         ) AS mvt_geom
  FROM sampled
)
SELECT ST_AsMVT(encoded.*, 'features', 4096, 'mvt_geom')
FROM encoded
WHERE mvt_geom IS NOT NULL;
```

### 🔭 Overview (Tổng)

Amazon OpenSearch Service now offers managed cross-Region disaster recovery for domains on OpenSearch 3.7 or later, documented by Cedric Pelvet and Michael Torio on the AWS Big Data Blog. The feature replaces the common user-built pattern of dual-write pipelines or snapshot shipping with a managed replication path controlled by a small set of API operations, and gives committed numbers: an RPO under one minute and an RTO under twenty minutes. For teams who have been building their own OpenSearch DR with CloudWatch alarms over snapshot age, this is a direct replacement — if their version is current and their domains are shaped the same on both sides.

### 🔬 Details (Phân)

Pairing is managed from the primary Region with `add-replication-peer`, with a prior `CompareDomainConfiguration` call that flags any configuration differences before you pair the domains; `DescribeDomainReplication` then surfaces peer role and replication status. There are two state transitions on top of a steady replication state: `SwitchoverReplication` is a planned, coordinated role swap with zero data loss, called on the secondary once pending writes have replicated, and is the one to use for regulatory exercises, maintenance windows, or planned Region moves; `FailoverReplication` is the unplanned promotion, requires `--allow-data-loss`, and bounds the loss to the replication lag at the moment of failover. `RemoveReplicationPeer` stops replication entirely with each domain keeping its data.

Architecturally, both domains index all data — the secondary isn't a cold snapshot but a live indexed copy that can take over at any time; only the primary accepts writes. Replication traffic stays within the OpenSearch Service network so no VPC peering is required, and traffic is encrypted in transit with support for customer-managed KMS keys at rest. The service does not redirect application writes after a role change: your application or runbook has to repoint clients, which means DNS, CloudFront behavior rules, or client-side failover logic is still on you. Monitoring is driven by a small set of CloudWatch metrics on the secondary domain — `DisasterRecoveryReplicationLagTime`, `DisasterRecoveryReplicationLagOps`, `DisasterRecoveryBootstrappingIndices`, `DisasterRecoveryDegradedIndices`, `DisasterRecoveryFailedIndices` — and the post gives explicit alarm thresholds (e.g. alarm when `DegradedIndices > 0` for 15 minutes, alarm on any `FailedIndices > 0`).

The constraints are the ones that will decide whether you can adopt this feature or not. Both domains must be in the same AWS account in different Regions, with the same number of primary shards and replicas and similar CPU/memory/storage. UltraWarm, Writable Warm, and the OpenSearch Optimized engine for log analytics (the oi2 path Confluent and AWS just benchmarked) are not supported in this release. ISM policies, index templates, settings, and roles are not replicated and must be managed on both sides — the authors explicitly suggest infrastructure as code. For pre-3.7 domains, the post walks a clone-based upgrade path for Elasticsearch 7.10 and OpenSearch 1.1+, and an in-place upgrade for older versions.

### 🎯 Takeaway (Hợp)

If you run a production OpenSearch cluster on 3.7+ with hot storage only and you own the DNS flip, this probably ends a quarter of DR-runbook toil overnight — the RPO and RTO numbers are already in the "defensible to an auditor" range. The single most important action before enabling it is to put your ISM policies, templates, and roles under Terraform or CloudFormation, because that's the gap this feature does not close for you.

### 💡 Example

```bash
# Pair primary (us-east-1) with secondary (us-west-2), then exercise failover.

# 0) Check shape/parity before pairing.
aws opensearch compare-domain-configuration \
  --domain-name search-prod \
  --target-domain-arn arn:aws:es:us-west-2:111122223333:domain/search-prod-dr

# 1) Pair (run in the primary Region).
aws opensearch add-replication-peer \
  --domain-name search-prod \
  --target-domain-arn arn:aws:es:us-west-2:111122223333:domain/search-prod-dr

# 2) Watch bootstrap finish and lag stay under RPO budget.
aws cloudwatch get-metric-statistics \
  --namespace AWS/ES --metric-name DisasterRecoveryReplicationLagTime \
  --dimensions Name=DomainName,Value=search-prod-dr \
  --statistics Average --period 60 \
  --start-time 2026-11-13T00:00:00Z --end-time 2026-11-13T00:10:00Z

# 3) Planned role swap (run on the SECONDARY).
aws opensearch switchover-replication --domain-name search-prod-dr

# 4) Unplanned failover (run on the SECONDARY; data loss bounded by lag).
aws opensearch failover-replication \
  --domain-name search-prod-dr --allow-data-loss
```

### 🔭 Overview (Tổng)

WeAct Studio has released a second-generation 16-channel logic analyzer built around the WCH CH32H417, one of the first dual-core RISC-V parts from WCH to show up in a dedicated test tool rather than an evaluation board. ### 🔬 Details (Phân)

The CH32H417 inside combines a 400 MHz RISC-V5F core with a 144 MHz RISC-V3F core, 896 KB SRAM, and 960 KB flash of which 304 KB is reserved for a user-firmware slot that can be flashed to repurpose the board. The analyzer presents 16 channels (D0–D15) on a 20-pin GPIO header, samples at 4–200 MHz over USB 3.0, and drops to 4–20 MHz at 16 channels or 4–40 MHz at 8 channels when forced onto USB 2.0; capture length is memory-bounded at the host side and lands around 45 seconds at 200 MHz with all 16 channels engaged. Input range is 1.0–3.3 V with a 0.6–1.5 V threshold, so the device is firmly targeted at modern low-voltage CMOS targets; 5 V TTL and higher-voltage buses need a level shifter. There are 132 protocol decoders in the shipped app covering the usual embedded set — UART, I²C, SPI, CAN — plus more niche options, and the board carries a USB 3.0 Type-C port for power, data and programming, a WS2812 RGB LED, and a user button to switch between loaded apps.

Software is the catch. The analyzer and DAP firmware are closed-source binaries, and PulseView support is delivered through U3LogicAnalyzer, a Windows/Linux Sigrok/PulseView fork maintained by WeAct rather than upstream Sigrok. Aufranc notes that upstream Sigrok support is unlikely because mainline development appears dormant, which is relevant for buyers who want their investment to outlive the vendor's release cadence. The GitHub repository does ship open-source tools and a Slot 2 user-app sample, so the board itself is scriptable at the firmware level even if the capture stack is not.

Positioned against the WeAct V1 and the many 24 MHz USB 2.0 Saleae clones, the V2 is a real step up — 200 MHz sampling and 896 KB SRAM in a $10 form factor is a different device class — and against the 10× more expensive mid-tier commercial analyzers it is a reasonable "always in the toolbox" option. The caveat flagged in reader comments is that 200 MHz is a sample rate, not an analog bandwidth, so sharp-edged signals at that rate will alias; treat it as a sub-100 MHz-signal device if you want clean captures.

### 🎯 Takeaway (Hợp)

For a hobby firmware bench, a classroom lab, or a travel debug kit, the WeAct Logic Analyzer V2 is an obvious buy at the price.
