### 🔭 Overview (Tổng)

Shiyu Xu, Jiuzhi Yu, Madhukiran Vaddi, Srishti Mittal and Xiening Dai land multi-statement transactions for Apache Iceberg tables in Amazon Redshift, available from Patch 206 onward. The pattern Iceberg teams had to work around until now — several DML statements against one table producing several Iceberg snapshots and several catalog updates — collapses into one BEGIN/COMMIT that publishes a single snapshot and a single catalog revision. For data engineers who already use Redshift as an Iceberg writer against S3 Tables or a Glue Data Catalog, the practical outcome is that staging-table swaps, backfill batches, and audit-before-publish flows become plain SQL transactions instead of orchestrated snapshot management. The feature is shipped as a behavior change, not new syntax, which also means some previously accepted patterns now fail.

### 🔬 Details (Phân)

Inside a transaction you can issue any number of INSERT, UPDATE, DELETE and MERGE statements against a single Iceberg table and a subsequent SELECT on that same table name reads the uncommitted writes — the post calls this "read your own writes," useful for running audit queries before deciding to COMMIT or ROLLBACK. Writing to a second Iceberg table inside the same transaction, executing Iceberg DDL inside BEGIN, or running an Iceberg write from a stored procedure are all rejected, and a rejected statement aborts the whole transaction. Referencing one table through two external schemas — or through an external schema and `awsdatacatalog` at once — counts as two tables and is also rejected. Repeatable-reads semantics are first-read-wins per table, so a table first read later in the transaction may include writes committed by other sessions between BEGIN and the first touch.

The benchmark section is specific rather than hand-waved. On 500 small statements, batching 25 per commit reduced run time 14.77% for INSERT and 11.29% for DELETE versus one commit per statement. At 32 concurrent writers against the same table, four-INSERT transactions reached 10.37x normalized throughput versus 2.89x for auto-commit, with the gain attributed to fewer catalog commits and to Redshift's conflict handling rebasing a transaction when its writes do not overlap concurrent commits. Only true conflicts fail COMMIT and have to be retried from the application. The authors call out the opposite case as well: for heavy per-statement work the batching wins are modest, because the bottleneck is the data work, not the commit overhead.

Operationally, the biggest trap is orphan files. Writes made before a ROLLBACK still land in S3 and have to be cleaned up; S3 Tables enable unreferenced file removal by default, but on a Glue Data Catalog table you must explicitly enable the orphan file deletion optimizer, and it only removes files created after it is enabled. Redshift managed storage (RMS) tables inside the same transaction use their own snapshot taken at the first statement and are not coordinated with the Iceberg catalog, so teams mixing RMS and Iceberg writes need to think about which engine is the source of truth per step. The behavior change — Iceberg DDL inside BEGIN is now rejected — will surface as broken deploy scripts for any team that wrapped DDL in an explicit transaction until this week.

### 🎯 Takeaway (Hợp)

If you were orchestrating Iceberg writes from Redshift with one-snapshot-per-statement and reconciling at the catalog layer, Patch 206 removes that whole layer. The first thing to do is audit DDL scripts for Iceberg tables wrapped in BEGIN and move those statements out; the second is to batch small writes into commits of around 25 statements and measure the drop in snapshot pressure on your catalog. Pattern này đặc biệt phù hợp cho staging-table swap và backfill job nhiều bước.

### 💡 Example

```sql
-- Patch 206+: multi-statement transaction against ONE Iceberg table.
BEGIN;

INSERT INTO lake.orders_iceberg (order_id, user_id, amount, order_ts)
VALUES (10001, 42, 19.90, CURRENT_TIMESTAMP);

UPDATE lake.orders_iceberg
   SET amount = amount * 1.10
 WHERE user_id = 42 AND order_ts > CURRENT_DATE - 7;

-- Read-your-own-writes: audit BEFORE committing.
SELECT count(*), sum(amount)
FROM   lake.orders_iceberg
WHERE  user_id = 42 AND order_ts > CURRENT_DATE - 7;

-- Decide based on the audit result.
COMMIT;   -- or: ROLLBACK;

-- Rejected: Iceberg DDL inside BEGIN.
-- BEGIN; CREATE TABLE lake.x (...) STORED AS ICEBERG; COMMIT;   -- fails.
```

### 🔭 Overview (Tổng)

Iván Fernández Perea benchmarks the five ways to write a PySpark UDF on AWS Glue 6.0 — Spark SQL, standard Python UDF, Arrow-optimized Python UDF, pandas UDF, and the new native Arrow UDF introduced in Spark 4.1.0 — and separates data-transfer cost from compute cost against the same 100M-row Parquet input. The practical headline is that `arrow_udf` passes `pyarrow.Array` directly in and out and runs against PyArrow compute kernels, skipping the pandas conversion that the vectorized UDF has to do on both sides. For teams that already picked pandas UDFs to escape serialization overhead, this is the first time Spark gives them a UDF type that is pandas-free end to end.

### 🔬 Details (Phân)

The environment is spelled out: Glue 6.0 on Spark 4.1.1, Python 3.13 and Scala 2.13, ten `G.1X` executors plus the driver in us-east-1, two `bigint` columns in Parquet, best-of-seven after one discarded warm-up, and a cache flush between iterations. Perea highlights that an earlier attempt which reused a cached DataFrame produced timings that did not scale with row count and made Spark SQL look slower than the UDFs — a trap worth noting in anyone's own benchmark harness. The streaming shape is `sum(op(a, b))` with `op` instantiated three ways: `arith` (`a + b`), `mathheavy` (a heavier compute), and `pyheavy` (a bounded Collatz-style loop capped at 1,000 iterations that cannot be expressed in SQL or PyArrow). At 100M rows on `arith`, the numbers are Spark SQL 0.99 s, native Arrow UDF 2.81 s, pandas UDF 3.13 s, Arrow-optimized Python UDF 8.94 s, standard Python UDF 11.68 s; on `mathheavy` it is 1.22 s, 3.13 s, 3.83 s, 11.01 s, 13.82 s respectively.

The gap between native Arrow UDF and pandas UDF is the point. On a trivial arithmetic workload, the two are within a few hundred milliseconds — there is almost nothing to vectorize and the transfer cost dominates either way. On the heavier `mathheavy` workload the native Arrow UDF opens an ~18% lead because the pandas UDF still pays for a `pyarrow.Array → pandas.Series → pyarrow.Array` round trip around the actual compute. The Arrow-optimized Python UDF stays at the row-at-a-time surface for user code and so lands far closer to the standard Python UDF than to either batched path. The `pyheavy` scenario is the honest ceiling: when your logic cannot live in SQL or in PyArrow compute, the Python-based UDFs are your only option, and the article acknowledges its `pyheavy` detailed numbers were cut off so there is no table to quote yet.

For readers choosing a UDF type, the ranking is clean when the operation is expressible in Spark SQL — use SQL. When it is expressible in PyArrow compute, use `arrow_udf`. When it must fall back to Python but the logic is still vectorizable per batch, pandas UDF remains the fallback; standard Python UDFs stay the last resort. The caveats deserve attention: only the streaming-shape numbers are reported in full, the stateful (`GROUP BY`) shape is described as having the same ranking with only a single `mathheavy` example shown, and all figures come from one Glue configuration with one two-`bigint` dataset in one Region.

### 🎯 Takeaway (Hợp)

For any Glue 6.0 pipeline that still uses pandas UDFs for arithmetic or lightweight transforms, rewriting them as `arrow_udf` is a near-free ~18% execution-time win on heavier compute, and the code change is small — swap the decorator and work in `pyarrow.Array`. The deeper takeaway is procedural: run the benchmark with a cache flush between iterations and measure streaming and stateful shapes separately, because that single methodological choice reverses the ranking.

### 💡 Example

```python
# AWS Glue 6.0 + Spark 4.1.1: native Arrow UDF.
import pyarrow as pa
import pyarrow.compute as pc
from pyspark.sql.functions import arrow_udf

@arrow_udf("bigint")
def add_bigints(a: pa.Array, b: pa.Array) -> pa.Array:
    # Stays in pyarrow all the way — no pandas conversion.
    return pc.add(a, b)

# vs. the pandas UDF you probably have today:
# @pandas_udf("bigint")
# def add_bigints_pd(a: pd.Series, b: pd.Series) -> pd.Series:
#     return a + b   # arrow -> pandas -> arrow round-trip on each batch.

df = spark.read.parquet("s3://bucket/two_bigints/")
df.selectExpr("sum(add_bigints(a, b)) AS total").show()
```

### 🔭 Overview (Tổng)

Jon Handler publishes a hands-on primer for Amazon OpenSearch Service's span query family, aimed at teams whose searches have outgrown `match_phrase` — legal document search, patent search, compliance, and contract matching — and who keep hitting the same two walls: phrase queries cannot enforce term order under `slop`, and they cannot require a term to appear in a specific structural position of a field. The piece is tagged Expert and is deliberately a reference walkthrough rather than a product announcement. For engineers who have been restructuring documents at ingest time to get query-time position semantics right, the point is that OpenSearch already has the DSL for this and it is query-time only.

### 🔬 Details (Phân)

Handler opens with the canonical failure of `match_phrase` + `slop`: a query for "star wars hope" with `slop: 4` also matches "Hope for Star Wars: The Prequel Series", because `slop` allows position swaps as well as position gaps. The fix is to wrap `span_term` in `span_first` with `end: 2`, which requires the term to appear within the first two token positions of the field; combining that with `span_near` at `slop: 12, in_order: true` finds titles that start with "star" and then contain "hope" later, in order, with a bounded gap. The `in_order` flag appears on every multi-child span type and is the piece of the API that `match_phrase` cannot express.

The second half of the article focuses on `span_containing` versus `span_within`. Both take a `big` and a `little` clause and require the little span to fall inside the big one; the difference is which match is returned — `span_containing` returns the big spans, `span_within` returns the little ones. Handler's worked example nests an exact phrase (`slop: 0, in_order: true`) inside a proximity span (`slop: 12, in_order: false`), which is the shape you reach for when you want to find a document where a fixed phrase appears inside a loose-order concept window. The full span-type list he enumerates is `span_term`, `span_multi`, `span_first`, `span_near`, `span_not`, `span_or`, `span_field_masking`, `span_containing`, and `span_within`, and every multi-child form accepts `in_order`.

The caveat flagged in bold is that span queries can only nest other span queries. You cannot mix a span clause and a `match` or `bool` clause inside the same compound; the whole position-aware subtree has to be made of span nodes, with non-span filters applied outside in a surrounding `bool`. For teams that have built query generators on top of `bool`/`must`/`filter`, that is a real refactor: the position-aware branch becomes a self-contained subquery and the non-position filters compose around it, not inside it. The post does not benchmark span queries versus phrase queries, so plan on measuring on your own index before putting them in the hot path.

### 🎯 Takeaway (Hợp)

If your search surface relies on `match_phrase` + `slop` and you are already seeing the term-order drift on real content, this is the DSL to switch to — and the substitution is query-time, so no reindex is required. Steal Handler's pattern of wrapping exact-phrase requirements inside a proximity span with `span_containing`, and plan the query-builder refactor around the "span-only subtree, filters outside" rule.

### 💡 Example

```json
# OpenSearch: find titles that start with "star" AND contain "hope" later, in order.
# This is what match_phrase + slop can NOT do.
POST /movies/_search
{
  "query": {
    "span_near": {
      "clauses": [
        { "span_first": {
            "match": { "span_term": { "title": "star" } },
            "end": 2
        }},
        { "span_term": { "title": "hope" } }
      ],
      "slop": 12,
      "in_order": true
    }
  }
}

# Containing: return docs whose "concept window" (slop=12, any order)
# wraps the exact phrase "a new hope" (slop=0, in order).
POST /movies/_search
{
  "query": {
    "span_containing": {
      "big": {
        "span_near": {
          "clauses": [
            { "span_term": { "title": "star" } },
            { "span_term": { "title": "wars" } }
          ],
          "slop": 12, "in_order": false
        }
      },
      "little": {
        "span_near": {
          "clauses": [
            { "span_term": { "title": "a" } },
            { "span_term": { "title": "new" } },
            { "span_term": { "title": "hope" } }
          ],
          "slop": 0, "in_order": true
        }
      }
    }
  }
}
```

### 🔬 Details (Phân)

The board runs an ESP32-WROOM-32-N4 (4 MB flash) with 2.4 GHz Wi-Fi and Bluetooth LE (including BLE proxy support), exposes four independent 4-pin PWM fan connectors with 1–100% speed control, and has four tachometer inputs for per-fan RPM monitoring. The detail that elevates it above a naive PWM controller is the TPS22810DBVR load switches on each channel, which cut rail power completely so a fan can be commanded to true zero-RPM instead of hovering near its stall point. Power comes in on a 12 V DC barrel jack (12 V/2 A or higher recommended), a TPS5430DDAR buck steps that to 5 V for the ESP32 and switches, and an AMS1117-3.3 provides the 3.3 V logic rail. Firmware is ESPHome, which gives Home Assistant users on/off and variable-speed control, RPM feedback, OTA, Bluetooth proxy, and an HTTP REST API out of the box. An automatic temperature-based mode runs entirely on the ESP32 — the default curve keeps fans off at 30 °C or below and ramps to maximum speed at 50 °C, both thresholds editable from YAML. The v2.0 board adds a three-pin connector for up to four DS18B20 digital temperature sensors and an optional LD2402G 24 GHz mmWave radar on the UART header, which is useful for presence-based noise control (a quiet office when the desk is empty).
