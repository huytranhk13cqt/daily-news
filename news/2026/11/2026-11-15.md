### 🔭 Overview (Tổng)
Kevin Tinn and Utsab Roy on the AWS Big Data Blog publish a reference architecture that wires AWS Glue to Amazon Bedrock AgentCore so an ETL pipeline can diagnose and repair its own record-level failures before the bad rows reach downstream analytics. The stack pairs Glue's Spark runtime with four Strands Agents SDK agents — an orchestrator, a data-correction agent, a data-persistence agent and a code-remediation agent — all invoked through the `InvokeAgentRuntime` API that AgentCore exposes. Anthropic Claude handles agent reasoning, Amazon Titan Embeddings V2 indexes historical fixes into a knowledge base, and Amazon S3 Vectors backs the vector store, while AWS CDK builds ARM64 container images through CodeBuild. The example dataset is a hypothetical NOAA weather feed with 15 schema types (temperature, precipitation, wind, pressure, humidity, visibility, cloud cover, solar radiation and others), and the pipeline treats every validation failure as a routing decision rather than a hard stop.

### 🔬 Details (Phân)
Validation happens inside Glue through a `validate_record` dispatcher that maps each schema type to its validator and classifies failures as `missing_field`, `type_mismatch`, `schema_violation` or `invalid_format`. A failed record is sent to the orchestrator agent, which then runs the correction agent, the persistence agent and the remediation agent in sequence; if any step fails, the pipeline stops rather than passing bad data downstream. The correction agent compares two sources of fixes: a Bedrock knowledge base query (`retrieve` with `numberOfResults = 3`, keeping the top score and content) and a pre-computed strategy file at `s3://.../correction/{schema_type}/{error_type}.json` that carries its own confidence value, and picks whichever source has the higher score. The post's worked example contrasts an S3 confidence of 0.85 with a knowledge-base score of 0.78, with a default threshold of 0.7 below which the orchestrator skips the write and fires an SNS notification for manual review instead.

Positioned against hand-written retry/DLQ logic, the piece argues that moving the "what do we do with this bad row" decision into an LLM-backed agent lets teams encode fuzzier rules (unit conversions, misspelled enum values, out-of-range sensor data) without rewriting the Spark job each time a new failure mode shows up. The persistence agent writes corrected records back to both raw and curated data-lake zones so lineage stays intact, and the remediation agent reads the source repository through Secrets Manager credentials to perform root-cause analysis and can — optionally — propose a pull request that fixes the upstream producer. Supporting services include Amazon SNS for notifications, AWS Secrets Manager for repo credentials, Amazon ECR for agent images, AWS Lambda for glue code and CodeBuild for image builds.

For adopters the caveats are the usual Bedrock ones: you need Claude and Titan model access enabled in the account, Python 3.10+ and Finch or Docker for local testing, and the auto-remediation path depends on giving an agent credentials to a code repository — a trust boundary worth reviewing before going beyond a proof-of-concept. The blog post is categorized Advanced (300), and the published excerpt stops before the end-to-end deployment steps, so some operational detail still has to be read out of the accompanying GitHub sample rather than the post itself.

### 🎯 Takeaway (Hợp)
This is a usable blueprint, not a product launch: AgentCore and Strands are already GA, and the value of the post is the specific prompt-and-threshold wiring that lets an agent decide between a trusted pre-computed fix and a retrieved historical one. Teams building Glue pipelines on sensor or clickstream data can port the `validate → route → score → persist → remediate` loop into their own jobs with the published CDK app as a starting point. Điểm cần lưu ý là blast radius của bước remediation: cấp repo credentials cho agent đồng nghĩa với mở cửa cho PR tự động, nên review kỹ IAM boundaries trước khi chạy ngoài sandbox.

### 💡 Example
```python
from strands import agent_runtime

def route_failed_record(record, error):
    kb = bedrock.retrieve(
        knowledgeBaseId=KB_ID,
        retrievalQuery={"text": f"{error.type} on {record.schema_type}"},
        retrievalConfiguration={"vectorSearchConfiguration": {"numberOfResults": 3}},
    )
    kb_score, kb_fix = kb["retrievalResults"][0]["score"], kb["retrievalResults"][0]["content"]
    s3_fix = s3_json(f"correction/{record.schema_type}/{error.type}.json")
    s3_score = s3_fix["confidence"]

    best = ("s3", s3_fix) if s3_score >= kb_score else ("kb", kb_fix)
    if max(s3_score, kb_score) < 0.7:
        sns.publish(TopicArn=REVIEW_TOPIC, Message=json.dumps({"record": record, "error": error}))
        return None

    return agent_runtime.invoke(
        agentId=CORRECTION_AGENT_ID,
        payload={"record": record, "error": error, "strategy": best},
    )
```

### 🔭 Overview (Tổng)
The Apache Airflow project cut three stable SDKs at once on 13 November, all tagged 1.0.0 and released by maintainer `uranusjr`: the TypeScript SDK as `@apache-airflow/ts-sdk@1.0.0` (git tag `ts-sdk/1.0.0`), the Java SDK under Maven group `org.apache.airflow` with `airflow-sdk-bom:1.0.0` (git tag `java-sdk/1.0.0`), and the Go SDK at `github.com/apache/airflow/go-sdk@v1.0.0` (git tag `go-sdk/v1.0.0`). The releases operationalise AIP-111 "Task Loops" and the non-Python Dag Importer that landed in Airflow 3.4.0 on 6 November, which introduced a native YAML Dag format plus pluggable runtime SDKs so authors no longer have to write orchestration in Python if they would rather stay in their primary application language. In practice, the trio is Airflow's answer to pressure from TypeScript-heavy frontend data teams, Java shops with large Spring/JVM estates and Go teams who previously had to shell out to a Python wrapper.

### 🔬 Details (Phân)
All three SDKs serialise to DagSerialization v3 and support the same set of authoring primitives: task dependencies, task groups, branching, conditions, edge labels, and triggering other Dags, plus Task state store and Variable APIs. The Java release recommends importing the `airflow-sdk-bom:1.0.0` BOM to keep module versions aligned under the `org.apache.airflow` group — the preferred way to pin consistent versions across the authoring, execution and client modules in a multi-module Maven build. The Go module installs with `go get github.com/apache/airflow/go-sdk@v1.0.0`; the published notes do not pin a minimum Go version, so follow the module's `go.mod` when wiring it into a build. On the TypeScript side, the npm package is `@apache-airflow/ts-sdk@1.0.0`, and the only behavioural change called out since beta2 is that tasks passing `queue` as `undefined` now inherit the Dag's queue — a quiet but important default for teams who were relying on explicit queue routing during the betas.

Because 3.4.0 made Airflow's XCom table migration asymmetric — downgrading below 3.4.0 can be slow — the SDK bump lands in a release window where the orchestrator itself is already on a new wire format. Compared with the alternative paths (Kubeflow for TypeScript-adjacent teams via its JS client, Temporal's Java/Go SDKs for workflow-as-code, or writing thin Python wrappers around non-Python tasks), Airflow's trio keeps DAG authoring, scheduling and the existing operator ecosystem on one runtime while removing the Python-source requirement. The announced changes since the betas are mostly polish — the Go build is fixed on 32-bit targets, the Go install command no longer breaks the first bundle build, Go log attributes stop displacing standard log fields, and the TypeScript build no longer scatters `.pnpm-store` directories from a machine-global pnpm config.

For adopters the migration cost is modest if you are already on Airflow 3.4.x: install the SDK, port Dag authoring into the target language, and let the Dag Importer feed serialized Dags to the scheduler. The caveats are that neither the Java notes nor the Go notes publish a required language-version floor in the release page itself, and there is no explicit Asset-support line for the Java SDK, so verify Asset-driven Dags against the Airflow 3.4.0 docs before porting them. The main pitfall for existing teams is the Airflow 3.4.0 default change that asset-triggered Dags now create one run per event, which interacts with how non-Python Dags enqueue tasks.

### 🎯 Takeaway (Hợp)
If your organisation has resisted Airflow because "it's a Python tool," the 13 November drop removes that objection cleanly — three mainstream languages, one serialization format, one scheduler. Teams on Airflow 3.3 can wait a release cycle, but anyone already on 3.4.x can pilot the matching SDK against a small non-Python workload this week. Lưu ý rằng các SDK này mới 1.0.0 nên thư viện operator cộng đồng (Snowflake, Databricks, Kafka…) phần lớn vẫn là Python; multi-language Dag hiện tại hợp cho greenfield hơn là viết lại Dag Python đang chạy.

```typescript
import { dag, task, taskGroup, branch } from "@apache-airflow/ts-sdk";

export default dag({ dag_id: "etl_weather", schedule: "@hourly" }, (d) => {
  const ingest = task("ingest", async () => {/* fetch to s3://.../raw/ */});
  const validate = task("validate", async () => { return "clean"; });
  const route = branch("route", async () => (await validate.result()) === "clean" ? "load" : "quarantine");

  taskGroup("load", (g) => {
    const stage = task("stage", async () => {/* copy to silver */});

    stage.before(publish);
  });

  ingest.before(validate).before(route);
});
```

### 🔭 Overview (Tổng)
Jean-Luc Aufranc's CNX Software covers two independent desktop-OS projects that are turning the Olimex ESP32-P4-PC — a microcontroller board with HDMI, Ethernet and USB — into something that behaves like a small personal computer. Sylphide OS, written by Thomas Capricelli (Orzelf) and licensed under GPL v3, aims for portability: it already runs on ESP32-P4 boards, the Raspberry Pi Pico 2 (with VGA and USB) and the Olimex ESP32-SBC-FabGL (PS/2 input, VGA output), and ships a Linux-host emulator for development. Bare Metal, Do Stuff (BMDS) by Jason Howard targets the ESP32-P4 specifically, licenses under MIT, and leans into richer applications — a Doom port, an FM/wavetable synthesizer, SSH/SFTP, BusyBox + Dropbear and an online package manager. Neither project is an industrial platform, but together they are a useful signal about what the ESP32-P4's dual-core RISC-V plus high-resolution display pipeline can sustain.

### 🔬 Details (Phân)
Sylphide OS builds on FreeRTOS. It renders a monochrome Macintosh-like desktop with a window manager, desktop icons and an information panel; low-level code handles framebuffer, bitmaps and fonts, with drivers for mouse, keyboard, display, storage and network. The project is configured via kconfig, mixes C (low level, drivers, rendering) with C++ (GUI) and a little assembler per target, and lists planned work for microSD and USB storage, Ethernet and Wi-Fi networking, GUI widgets and external programs loaded from microSD. Sources live at `freehackers.org/electronics/sylphide-os` with the project site at `projects.freehackers.org/sylphide-os/`.

BMDS runs on FreeRTOS + ESP-IDF on ESP32-P4 targets such as the Olimex ESP32-P4-PC (HDMI, Ethernet, USB). Its GUI is color, pushed at 1280×720 60 FPS, with a DOS-like character; applications are separate ELF binaries loaded directly from the SD card, which is the key architectural difference from Sylphide OS. The built-in synthesizer includes FM and wavetable engines, networking covers SSH/SFTP server and client, and the BusyBox and Dropbear ports give it a recognisably POSIX-adjacent userland. A stable SDK for third-party apps, a package manager with an online installer and a web installer at `jthwho.github.io/bmds` round out the stack; source, docs and SDK are hosted at `github.com/jthwho/bmds`, and a 34-minute walkthrough video is already published.

Positioning against the field: the ESP32-P4 has become the hobbyist target for "can a microcontroller act like a PC?" experiments because it pairs dual RISC-V cores with a parallel display interface and PSRAM, and both of these projects demonstrate that it is enough hardware to sustain a window system and a Doom-class game loop on bare FreeRTOS. Neither is a Linux replacement — the CNX article does not cover memory footprint, PSRAM usage or multitasking details — but they are useful as reference stacks for teams exploring UI kiosks, retro-style edge devices or offline-first embedded appliances that want more than LVGL alone.

### 🎯 Takeaway (Hợp)
If you are prototyping a kiosk or an embedded appliance on ESP32-P4 and have been building the GUI from scratch, BMDS is worth cloning as a baseline because the ELF-apps-from-SD model gives you a clean separation between firmware and shipped applications. Sylphide OS is the more portable choice if you care about targeting cheaper boards like the Pico 2 or the FabGL. Hai dự án này vẫn là hobbyist, nên đừng kỳ vọng SLA — nhưng dấu hiệu rõ: ESP32-P4 đủ sức chạy một shell desktop thật, không chỉ LVGL.
