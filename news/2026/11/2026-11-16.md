### 🔭 Overview (Tổng)
dbt Labs cut v1.12.7 of dbt-core on 12 November (tag `v1.12.7`, commit `bd46c78d600c8518b5b24be7338c035887054d40`, published by `github-actions`). It is a patch release aimed squarely at teams who already moved to the 1.12.x line and hit edges introduced when `skip_nodes_if_on_run_start_fails` flipped to True by default; the release notes list one small feature, nine fixes and a dependency floor bump. The practical change for most users is that freshness checks and `--cache-selected-only` now behave the way the docs already said they did, and `dbt deps` stops breaking on private git packages pulled from a subdirectory. Positioning: this sits inside 1.12.x maintenance, not the 2.x track, so it is the safe bump to pin for projects that have not yet migrated.

### 🔬 Details (Phân)
The headline fix (#15634) is that when the batch metadata freshness path fails, dbt now falls back to per-source freshness checks instead of silently skipping every selected source — a regression that was masked by the new default of `skip_nodes_if_on_run_start_fails=True`. Alongside it, `compile`, `show` and `docs generate` now scope relation-cache population to the selected nodes' schemas so `--cache-selected-only` is actually honoured (#12944), and `statically_parse_unrendered_config` stops stringifying list and dict config values, which was producing false positives in `state:modified` comparisons across dbt versions (#16133). A new behaviour flag `builtin_macros_prefer_overrides` (default `false`) controls whether an adapter override wins over the base dbt macro inside internal macro search packages such as `dbt` or `dbt_postgres`; the default is `false` because a root-project macro sharing a built-in's name could otherwise intercept calls inside dbt's own macros (#16540).

The other fixes fit the same stability theme. `dbt deps` now supplies git-package credentials through a git credential helper rather than embedding them in the clone URL, which keeps redirecting repositories working under libcurl 7.81.0-1ubuntu1.30 and later and also fixes the `could not read Username` failure when a package was installed from a `subdirectory` with URL credentials — credentials are also passed to the checkout's `git reset --hard` (#16861). Snapshot timestamp-mismatch warnings now name the hard-delete timestamp columns and recommend overriding the `snapshot_get_time` macro rather than editing the snapshot's `updated_at` config (#fs-14450). On the schema side, `dbt_project.yml` accepts the dbt v2-only keys `info_schema`, `check-paths` and `checks` (ignored with a note) (#16640), manifest nodes with unsupported resource types such as dbt v2 checks are ignored when loading a manifest for `--state`/`--defer` (#16849), Databricks Python model keys `access_control_list` and `notebook_access_control_list` validate without `CustomKeyInConfigDeprecation` warnings (dbt-databricks#1661), and the `use_materialization_v2` Databricks config is now recognised by JSON-schema validation (#16879). `dbt-core-experimental-parser` floor is bumped to 2.0.11 (#17117).

For adopters the upgrade cost is low — this is a point release — but the most important thing to evaluate is whether `builtin_macros_prefer_overrides` matters for your project. Most teams will leave it `false`; if you are relying on a root-project macro shadowing a built-in, test with the flag before flipping it. The freshness-fallback fix should also be regression-tested on any source with batch metadata freshness configured, because the previous behaviour was to silently skip all selected sources on batch failure — a quiet gap that may have been hiding stale data in dashboards.

### 🎯 Takeaway (Hợp)
Pin dbt-core to 1.12.7 on 1.12.x projects today; the freshness fallback and `dbt deps` credential changes close real production footguns, and nothing in the release notes looks breaking for a straight patch upgrade. Teams running Databricks adapters or private git packages benefit the most. Nếu project đang dựa vào override macro có tên trùng với built-in của dbt, kiểm tra kỹ `builtin_macros_prefer_overrides` trước khi bật.

### 🔭 Overview (Tổng)
Uber Engineering has open-sourced Shard Manager under the `cadence-workflow` GitHub organisation at `github.com/cadence-workflow/shard-manager`, making shard ownership an explicit, load-aware decision rather than something each service re-derives from a consistent hash ring. The service is per-namespace: a leader-elected Shard Manager instance decides assignments, persists them in etcd, and lets applications integrate through two Go client roles — spectators that look up owners and route requests, and executors that process shards and report load. An `smctl` CLI provides inspection and operational commands (inspecting a shard's owner, listing executors, draining a host, draining or restoring individual shards). The post is framed around Uber's own first mover, Cadence's Matching service, where load-aware assignment replaced hash-ring ownership.

### 🔬 Details (Phân)
Architecturally there are five pieces: the Shard Manager service, spectators, executors, etcd for assignment state and leader election, and `smctl`. Executors expose lifecycle methods for each shard and periodically report their own load; the service feeds those reports into a rebalancing algorithm that aims to keep per-host load close to the fleet average rather than evenly spreading shard counts. The team plans to make etcd optional so Shard Manager can run entirely in memory for smaller deployments, but the released code uses etcd as the store. The post does not publish Go client snippets inline; the described API is "applications supply a shard processor with lifecycle methods and a load report, and Go clients handle heartbeats, assignment updates and ownership lookups," and the `smctl` commands appear as a screenshot (two example invocations in the `cadence-matching` namespace), not as text.

The measured impact comes from rolling Shard Manager into Cadence's Matching service, where shard ownership is the dominant driver of host load. CPU utilisation on the hottest Matching host fell by 38%, and the hottest-to-average host utilisation ratio dropped from about 2.3× to about 1.4×; because sizing a stateful cluster depends on the hottest host rather than the average, that lets the same traffic run on roughly 40% fewer hosts. In a separate evaluation against a constraint-solver baseline, load spread was within 5% of optimal in 23 of 24 workload snapshots, and within 1% in 14 of them; Figure 1 of the post shows a host at 2.22× average load under the previous hash-ring approach for reference. Positioned against alternatives, Shard Manager is closer to Meta's internally described shard manager and to parts of Google's Slicer than to Kubernetes-style scheduling: it is a long-lived control plane for application shards specifically, not containers, and leans on rebalancing rather than consistent hashing to avoid the "one hot shard bakes the host" failure mode.

The caveats for adopters are practical. Integration is not a drop-in — applications have to implement the executor interface, stand up or share an etcd cluster, and migrate away from whatever hash-ring library they were using. Draining with `smctl` is per-host and per-shard, so operational playbooks for rolling upgrades need to be rewritten. The service is new to open source even though it has been running inside Uber, so expect ongoing API churn and a sparser contributor ecosystem than etcd or Cadence themselves. The post does not quote p50/p99 latency numbers for lookups, only the cluster-utilisation improvements, so measure your own routing hot path before committing.

### 🎯 Takeaway (Hợp)
If you run a stateful system where a handful of hot shards dominate capacity planning — matching queues, task routers, session stores — Shard Manager is a serious open-source option to test before rolling your own balancer, and the Cadence Matching numbers are a credible yardstick. Start with a shadow deployment reporting load into Shard Manager without flipping routing, and compare the proposed assignment against your current hash ring. ### 🔭 Overview (Tổng)
The DuckDB Foundation blog published a long-form piece by Ilya Boyandin arguing that for many interactive analytics workloads a local DuckDB engine is a better substrate than a hosted database, and walking through four reference projects that already ship that way. Covered are Flowmap City (mobility flows in DuckDB-Wasm, reading Parquet from S3 via presigned URLs), SQLRooms (open-source React toolkit with a shared DuckDB connection grouped into "Rooms"), Foursquare Spatial Desktop (Electron app built on SQLRooms), and Cosmograph (browser graph exploration with a SQLRooms-powered analytical workspace). It is a pattern post, not a release, but it names enough DuckDB-specific plumbing — particularly in the dynamic Mapbox Vector Tile pipeline — that it functions as a reference for teams building browser- or desktop-first analytics.

### 🔬 Details (Phân)
The technical core of the article is a dynamic MVT tiling query executed entirely by the DuckDB spatial extension. The pipeline computes tile geometry in Web Mercator (`EPSG:3857`), with 256-pixel tiles and per-tile `meters_per_pixel = (ST_XMax(bounds) - ST_XMin(bounds)) / 256.0`. It uses a 16-pixel search buffer (`meters_per_pixel * 16`), a simplification tolerance of `meters_per_pixel * 0.5` with a floor of `0.1`, and a reservoir sample capped at 50,000 rows per tile via `USING SAMPLE reservoir(50000 ROWS)`. The spatial functions it calls directly are `ST_TileEnvelope`, `ST_XMin`/`ST_XMax`, `ST_Buffer`, `ST_Intersects_Extent`, `ST_SimplifyPreserveTopology`, `ST_AsMVTGeom`, `ST_Extent` and `ST_AsMVT`, structured as a four-CTE query: a `tile` CTE for bounds and meters/pixel, a `candidates` CTE for buffered-intersect filtering, a `sampled` CTE for reservoir sampling, and an `encoded` CTE that simplifies and projects to tile coordinates before `ST_AsMVT` packages the output. The article notes production variants also handle invalid geometries, drop very small features and cache tiles, but the pattern itself is DuckDB-native with no server round-trip.

For the browser projects, the architectural claim is that DuckDB-Wasm now covers enough SQL (including the spatial extension) to keep interactive panning, zooming and filtering responsive — Flowmap City reads Parquet from S3 using presigned URLs and reruns DuckDB queries on every interaction instead of calling a back end. SQLRooms is positioned as the glue layer: one DuckDB connection shared across datasets and components grouped into "Rooms," which both Foursquare Spatial Desktop and Cosmograph build on. The post ties this back to a SQLRooms CLI demonstrated at DuckCon #7, which lets developers scaffold a local-first analytics app from the same primitives.

Versus hosted alternatives (Snowflake Streamlit apps, BigQuery+Looker, or warehouse-attached notebooks), the sell is fewer moving parts and lower latency for exploratory flows; the countervailing cost is that the dataset has to fit a browser's memory envelope, or be chunked into Parquet partitions behind a signed-URL scheme. The post does not quote benchmarks or specific memory footprints for the tiling pipeline, so teams should profile with their own geometry types and reservoir sizes; the 50,000-row cap is a reasonable default for city-scale datasets but may be low for dense point clouds.

### 🎯 Takeaway (Hợp)
Use this piece as a shopping list for local-first geospatial analytics: SQLRooms for the app skeleton, DuckDB-Wasm for the engine, and the four-CTE `ST_AsMVT` pattern for dynamic vector tiles that work in-browser without a tile server. Start by porting one tile layer to the DuckDB pipeline and compare rendering latency against your existing MVT service. Nếu dataset nặng (ví dụ point cloud mật độ cao), tăng reservoir sampling hoặc chuyển sang pre-generated tiles cho các zoom cao thay vì generate thuần động.

### 💡 Example
```sql
-- Condensed dynamic MVT pipeline (DuckDB spatial extension, in-browser via WASM).
-- Parameters :z, :x, :y come from the tile request.
WITH tile AS (
  SELECT
    ST_TileEnvelope(:z, :x, :y)                                    AS bounds,
    (ST_XMax(ST_TileEnvelope(:z, :x, :y))
     - ST_XMin(ST_TileEnvelope(:z, :x, :y))) / 256.0               AS meters_per_pixel
),
candidates AS (
  SELECT f.*, t.bounds, t.meters_per_pixel,
         GREATEST(t.meters_per_pixel * 0.5, 0.1)                   AS simplify_tol
  FROM features f, tile t
  WHERE ST_Intersects_Extent(f.geom, ST_Buffer(t.bounds, t.meters_per_pixel * 16))
),
sampled AS (
  SELECT * FROM candidates USING SAMPLE reservoir(50000 ROWS)
),
encoded AS (
  SELECT ST_AsMVTGeom(
           ST_SimplifyPreserveTopology(geom, simplify_tol),
           ST_Extent(bounds)
         ) AS geom,
         id, properties
  FROM sampled
)
SELECT ST_AsMVT(encoded, 'layer') AS mvt FROM encoded;
```

### 🔬 Details (Phân)
Encoding options are H.264, H.264 (WS), H.265 and MJPEG; H.264 is served over WebRTC, H.264 (WS) is a WebSocket fallback. Resolution and frame-rate choices run from 1280×720/30Hz up to what the UI labels "260×1440/30Hz" (very likely a typo for 2560×1440); the reviewer tested 2560×1400/30Hz with "Regular" scaling and image quality from Low to High. H.265 over WebRTC worked in Chrome and rendered the idle desktop at 60 FPS in high quality; in Firefox, H.265 failed with "Unable to negotiate video codec" and device discovery required flipping `security.mixed_content.block_active_content` to false in `about:config`, plus Alt+Tab did not work in full-screen mode. Edge and Safari are listed as supported but not tested in the review. Typing failures surfaced when the laptop was on Wi-Fi while the Linkr was on Ethernet; moving the laptop to a wired connection fixed them.

On the security side, the firmware's HTTPS story is partial: initial setup runs over plain HTTP, and a Wireshark capture during the setup flow showed the username, device name and hashed password on the wire — the review recommends completing initial setup over the USB Network (USB Gadget) interface instead. 2FA is Google Authenticator-style, enabled under System Settings → Account & Security → Safety by scanning a QR code; login then requires a username, password and a 6-digit TOTP. Account & Security also exposes Access Tokens for programmatic access and an OpenClaw entry. HTTPS is configured in Advanced Settings; the reviewer used a self-signed certificate and notes that Firefox still labels the connection "Not Secure" because the certificate is not from a recognised public authority. The Tailscale path is independent of HTTPS: install the Tailscale client on the host, enable Tailscale in the Linkr's Advanced Settings, add both to the tailnet, and reach the device via its Tailscale IP — the reviewer verified this from Firefox Mobile on Android over cellular.

For adopters, the headline caveats are two: Chrome-only for H.265 right now, and the plain-HTTP first-run exposure that argues for USB-first provisioning. The OTA to v1.6.0 was a manual file upload (no integrated OTA UI), took about an hour and wiped all settings, so plan for re-provisioning. The review does not disclose the Linkr's SoC, RAM or flash — those remain gaps if you are evaluating against alternatives like PiKVM (Raspberry Pi-based) or TinyPilot. Positioned against those, the Linkr's distinguishing features are built-in Tailscale support and native H.265 over WebRTC, both of which are fiddly to retrofit on DIY builds.
