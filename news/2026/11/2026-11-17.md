## 1. ESP-IDF v6.1.1 Patches HTTP Request Smuggling, Locks Plain HTTP Out of `esp_https_ota`, Removes Key Manager on ESP32-C5/P4/S31, and Flips BLE Audio Addresses to LSB-First

### 🔭 Overview (Tổng)
Espressif cut ESP-IDF v6.1.1 on 16 November as the first bugfix release on the 6.1 line (tag `v6.1.1`, commit `051e4c4eb20346e043cdd47bc388fde75ff8af63`, published by `github-actions` and GPG-signed by maintainer Peter Dragun). The release is small in commit count but materially security-driven: it closes an HTTP request-smuggling path in the built-in HTTP server, forces `esp_https_ota` to refuse plain HTTP by default, and ports supplicant fixes from upstream wpa_supplicant. Alongside those sit several breaking changes that are easy to miss in a "1.1 patch" — Key Manager support was removed on three chips, BLE Audio address byte order flipped to LSB-first, and two BLE Audio callback signatures changed. For most teams the right action is to track the 6.1 line through this patch, but with a short audit pass on Bluedroid address handling and HTTP body sizes before shipping.

### 🔬 Details (Phân)
The security-relevant changes are small but surgical. The HTTP server fix (`eb0faad`) addresses Content-Length truncation and introduces a new Kconfig option, `HTTPD_MAX_REQ_BODY_LEN_KB`, that caps accepted request body size with a default of 16 MB; this is explicitly listed as a breaking change because existing deployments that relied on larger or unbounded bodies will now see requests truncated at the new ceiling. `esp_https_ota` (`d886460`) now rejects non-HTTPS downloads unless the application explicitly opts into plain HTTP through the existing allow-HTTP flag — the net effect is that an OTA endpoint silently downgraded to HTTP on a misconfigured firmware will fail closed instead of running. The TEE change (`27892e5`) snapshots REE-supplied secure service arguments into TEE memory before use, closing a time-of-check-to-time-of-use window for TrustZone-style secure services. A separate supplicant commit (`8d10833`) ports security fixes from upstream wpa_supplicant; no CVE numbers appear on the release page.

The breaking-change surface is wider than the security section suggests. Key Manager was removed from ESP32-C5, ESP32-P4 and ESP32-S31 (`9058e75`) because the hardware peripheral needs further design work before it can ship as a production feature — projects targeting those parts and already generating keys through Key Manager will need to fall back to software key derivation. On the BLE Audio side, `esp_ble_audio_tmap_set_role()` and `esp_ble_audio_tbs_register_cb()` now return `esp_err_t` instead of void (`3b666c4`), `esp_ble_audio_bap_base_get_subgroup_codec_data()` and `..._codec_meta()` take an extra out-parameter for length (`0205859`), and BLE ISO/BLE Audio addresses are now LSB-first across the API — Bluedroid applications still operate MSB-first and must swap bytes at the boundary (`aeecbbd`). The TX sent callback's `esp_ble_iso_tx_cb_info_t` was also trimmed: `completed_pkts`, `not_txd_pkts`, `pkt_cnt` and `pkt[]` are gone, replaced by a per-SDU `completed_pkts` field. An eFuse fix (`3911fd0`) corrects the `MAC_EXT` byte order on ESP32-C5 and ESP32-H21 so the derived IEEE 802.15.4 EUI-64 is now correct.

On the feature side, ISP (`f7502ee`) now accepts raw image input from memory, which lets the image signal processor operate without a sensor interface — useful for test harnesses and for using the ESP32-P4 as a post-processing engine. RGB LCD panels (`5005636`) gain DMA2D-accelerated bitmap drawing. Two ESP32-P4 boot-reliability fixes (`7c4e19e` and `1e74088`) resolve repeated `CHIP_LP_WDT_RESET` loops on v3.x applications built with bootloaders from ESP-IDF v5.5.2–5.5.4 and L1-cache staleness after bootloader remapping that could fail `esp_mmu_map_init` and `pmu_init`. Together they close a long tail of P4 boot-failure reports.

### 🎯 Takeaway (Hợp)
Pin ESP-IDF to v6.1.1 on 6.1-track projects, then run three targeted audits before shipping: HTTP endpoints that accept bodies above 16 MB (raise `HTTPD_MAX_REQ_BODY_LEN_KB` deliberately rather than inheriting the new cap), OTA flows that rely on plain HTTP (enable the flag explicitly or move to HTTPS), and Bluedroid-based BLE Audio code (swap address byte order and update the two changed callback signatures). Projects on ESP32-C5, ESP32-P4 or ESP32-S31 that use Key Manager need a software-key fallback plan for this release. Patch nhỏ nhưng kéo theo đủ breaking changes để không nên bump qua mà không review Bluedroid và HTTP body size.

### 💡 Example
```c
// menuconfig knobs to review when moving to ESP-IDF v6.1.1.
// 1. HTTP server body cap — new default is 16 MB; raise only if required.
#define CONFIG_HTTPD_MAX_REQ_BODY_LEN_KB  (16 * 1024)

// 2. esp_https_ota now rejects plain HTTP unless this is enabled.
//    Leave it off in production; HTTPS-only is the safer default.
// CONFIG_OTA_ALLOW_HTTP is NOT set

// 3. BLE Audio addresses are now LSB-first. Bluedroid apps must swap.
static inline void swap_addr_le(uint8_t dst[6], const uint8_t src[6]) {
    for (int i = 0; i < 6; ++i) dst[i] = src[5 - i];
}

// 4. BLE Audio callbacks changed return type; capture errors.
esp_err_t err = esp_ble_audio_tmap_set_role(role);
if (err != ESP_OK) { ESP_LOGE("ble-audio", "tmap role: %d", err); }
```

### 🔭 Overview (Tổng)
Alongside the AI Index launch, Databricks engineering published a longer field-guide post on 16 November — by Marc Susagna Holgado, Javier Poveda Panter, Puneet Jain and Ryuta Yoshimatsu — covering tabular foundation models (TFMs) and how to run them on the Databricks AI Runtime. TFMs are pretrained transformers that classify or regress on new tabular datasets without task-specific training: labelled rows go in as in-context examples, unlabelled rows go in as queries, and a single forward pass returns predictions. The post benchmarks five contemporary TFMs across parameter counts and licensing, shows where each sits on cost versus flexibility, and ships a reference repository — `databricks-industry-solutions/tabular-fm-databricks` — with zero-shot and fine-tuning notebooks so teams can reproduce the setup end-to-end. For ML and DE engineers who have treated tabular as "just use XGBoost," this is the first serious platform write-up of a TFM runbook.

### 🔬 Details (Phân)
The technical shape of a TFM is worth absorbing. Rows are tokenised into a shared representation that handles numerical, categorical and boolean features; TabPFNv2 applied attention first within rows and then within columns, while TabICLv1 compressed every row into four tokens to cut inference cost, an approach that TabPFNv3, TabFM and KumoTabular later adopted. Pretraining relies predominantly on synthetic data, often generated with Structural Causal Models, which is how these models generalise to unseen schemas without fine-tuning. The post benchmarks five candidates: TabICLv2 (February 2026, ~28M params, BSD 3-Clause), TabFM (June 2026, ~400M, TabFM Non-Commercial License v1.0), TabPFNv3.5 (September 2026, ~220M, TABPFN-3.5 License v1.0 with commercial-use agreement required), Mitra v2 (September 2026, ~77M, Apache-2.0) and KumoTabular (September 2026, ~215M, OpenMDW-1.1). Mitra v2's Apache licensing and TabICLv2's BSD licence are the two cleanest commercial paths; TabFM and TabPFNv3.5 have usage restrictions that need legal review before production.

Operationally, the Databricks AI Runtime side is where the post adds substance. The authors highlight on-demand managed serverless GPUs, built-in GPU utilisation observability, MLflow experiment tracking, Unity Catalog integration, Docker and remote-SSH support via the Databricks CLI, an in-notebook Genie Code agent for writing and debugging training code, and deployment to auto-scaling REST endpoints through Databricks Model Serving. The practical ceiling they publish is that H100 GPUs can host TabPFN-3 at up to 1 million rows × 200 features in a single context window — large enough for most structured datasets short of full warehouse tables. The repo demonstrates zero-shot inference across the five models and fine-tuning examples for classification and regression specifically on KumoTabular.

The honest caveat is in the cost sentence: TFMs cost more per prediction than CPU-based XGBoost, so the trade is GPU inference cost versus time-to-market. For a one-off exploratory classifier or a dataset where feature engineering would take weeks, a TFM round trip may win on calendar time; for a stable production pipeline with monthly retraining, XGBoost (or LightGBM) still likely wins on unit economics. The post does not quote dollar figures; teams should profile their own row counts and feature cardinalities against the H100 context limits before standardising on a TFM.

### 🎯 Takeaway (Hợp)
Start from the Apache-2.0 and BSD-licensed models — Mitra v2 and TabICLv2 — if the goal is a drop-in commercial pilot, and clone the `tabular-fm-databricks` repo as the starting harness; use TabPFNv3.5 only after reviewing its commercial-use agreement. Treat TFMs as a prototyping accelerator rather than a universal replacement for gradient-boosted trees, and benchmark against an XGBoost baseline on the same dataset before deciding. Số đo cost/prediction là chốt chặn chính — H100 không miễn phí, và XGBoost chưa chết.

### 💡 Example
```python
# Zero-shot classification with Mitra v2 on Databricks AI Runtime.
# Illustrative — mirrors the pattern in tabular-fm-databricks.
import pandas as pd
from mitra import MitraClassifier  # Apache-2.0 TFM

train_df = spark.table("main.default.churn_train").toPandas()
score_df = spark.table("main.default.churn_score").toPandas()

X_train = train_df.drop(columns=["churned"])
y_train = train_df["churned"]
X_score = score_df.drop(columns=["churned"], errors="ignore")

model = MitraClassifier()                         # pretrained weights load lazily
model.fit(X_train, y_train)                       # in-context "fit" — no gradient
preds = model.predict_proba(X_score)[:, 1]        # single forward pass on GPU

out = score_df.assign(churn_prob=preds)
(spark.createDataFrame(out)
 .write.mode("overwrite")
 .saveAsTable("main.default.churn_scored"))
```

The AUX-2 is a $69 (€59) wired-first bridge aimed at pulling legacy audio systems, AV receivers, UPSs and solar inverters into a self-hosted Home Assistant instance without touching the cloud. It is built around an Espressif ESP32-S3R8 and ships with open-source ESPHome firmware; the source lives at `github.com/NabuCasa/aux-2`. The pitch — framed by Home Assistant as "no device left behind" — matters less for its individual specs than for what it tells you about 2026 IoT hardware conventions: PoE is finally baseline on home-automation bridges, and ESP32-S3 has crowded out Zigbee-native SoCs for this class of device because it can do BLE, Bluetooth proxying and audio DAC I/O in the same chip.

### 🔬 Details (Phân)
The hardware is tighter than the price suggests. Networking is a 10/100 Mbps RJ45 port driven by a W5500 Ethernet controller with 802.3af PoE (class unspecified) plus 2.4 GHz Wi-Fi 4 (802.11b/g/n) and Bluetooth 5 LE; the Bluetooth proxy supports up to three active BLE connections alongside passive BLE sensors, which is the practical ceiling for pulling in BLE thermometers and locks over an ESPHome relay. Audio is a TI PCM5122 DAC with a 112 dB SNR driving a combined 3.5 mm analog and optical S/PDIF (mini-TOSLINK) output — one at a time — at up to 24-bit/48 kHz stereo once firmware 2026.11.1 is installed. Supported codecs are FLAC, MP3 and WAV. Serial exposes two 3.5 mm RS-232 ports (±5V) with individual TX/RX switches, enough to drive an older Pioneer or Yamaha receiver or to talk to a UPS/solar inverter. A USB-A host port accepts the Nabu Casa Connect ZWA-2 Z-Wave adapter or a supported USB-to-RS-485 adapter, giving the device a graceful upgrade path. A Grove connector breaks out GPIO and I2C, and an RGB status LED plus a reset button sit on the enclosure.

Power is 5V/2A via USB Type-C or 802.3af PoE, with consumption under 1 W and an indoor-only rating of 0 °C to 65 °C. The enclosure is 106 × 63 × 25 mm at 104 g in semi-transparent white polycarbonate. The software story is the differentiator: firmware is open source and OTA-updatable, the bootloader is unlocked for custom firmware, and audio streaming uses Sendspin with Music Assistant for multi-room sync. Experimental Zigbee requires the Connect ZBT-2 USB adapter and ZHA on Home Assistant 2026.11 or later — Zigbee2MQTT and Thread are not supported, and Bluetooth audio streaming is output-only (no Bluetooth-in pairing). The product page at `home-assistant.io/connect/aux-2/` carries the official documentation; the Seeed Studio store lists the box at $68.90.

Positioned against alternatives, the AUX-2 lands in a thin segment. Dedicated Bluetooth-proxy boards exist, PoE ESPHome boards exist, and ESPHome-controllable DACs exist, but a single device that bundles PoE + RS-232 × 2 + PCM5122 + a Bluetooth proxy with a public PCB and 3D-print plan (Nabu Casa says those design files are coming, though no date is given) is rare. Caveats for integrators are the usual ESP32-S3 ones: it is a single-core-plus-core radio chip, not a mesh coordinator, so Z-Wave and Zigbee require the USB sticks; and 3.5 mm RS-232 ports at ±5V are convenient but non-isolated, so an industrial deployment near line-side gear should add an isolator.

### 🎯 Takeaway (Hợp)
For a self-hosted Home Assistant stack with a PoE switch already in play, the AUX-2 is the cheapest clean way to bring one legacy audio device plus a UPS or AV receiver's RS-232 serial into the dashboard, and the Bluetooth proxy is useful on top. Buy the Connect ZWA-2 separately only if you already run a Z-Wave mesh; otherwise the box is useful without it. Nabu Casa hứa sẽ release PCB design và STL — đáng chờ nếu cần enclosure riêng, nhưng chưa có mốc thời gian cụ thể.

### 💡 Example
```yaml
# Minimal ESPHome config fragment mirroring the AUX-2 wiring.
# W5500 Ethernet (PoE-powered), PCM5122 audio out, two RS-232 UARTs.
esphome:
  name: aux2-bridge

esp32:
  board: esp32-s3-devkitc-1
  framework: { type: esp-idf }

ethernet:
  type: W5500
  clk_pin: GPIO36
  mosi_pin: GPIO35
  miso_pin: GPIO37
  cs_pin: GPIO34

i2s_audio:
  i2s_lrclk_pin: GPIO9
  i2s_bclk_pin: GPIO8
media_player:
  - platform: i2s_audio
    name: AUX-2 Analog Out
    dac_type: external                 # PCM5122
    i2s_dout_pin: GPIO10

uart:
  - id: rs232_a
    tx_pin: GPIO17
    rx_pin: GPIO18
    baud_rate: 9600
  - id: rs232_b
    tx_pin: GPIO15
    rx_pin: GPIO16
    baud_rate: 9600

bluetooth_proxy:
  active: true                         # up to 3 active BLE connections
```
