### 🔭 Overview (Tổng)
Carlota Soto's 17 November post on the Databricks engineering blog is the first production-grade walkthrough of how Lakebase — Databricks' Postgres service that stores durability on object storage — actually serves OLTP reads without inheriting S3-class latency. The piece names the three tiers between a query and object storage, quotes real traffic shares from the production fleet, and describes the two failure modes that push reads to the slow tier. For anyone trying to reason about separating storage and compute in a transactional database, this is the first vendor post of the year that publishes real numbers rather than architecture diagrams alone. It also finally pins down the request shape — GetPage@LSN — that Lakebase borrowed from Neon and that most neon-adjacent writeups have described only in passing.

### 🔬 Details (Phân)
The architecture is a four-layer stack. Postgres compute holds a local page cache but no durable state, so instances can start, stop, scale, or crash without data loss. A quorum of safekeepers replicates the WAL using a Paxos-based protocol for leader election and failover; a commit returns once the quorum acknowledges. Pageservers consume that WAL and materialise pages into an LSM tree on local NVMe, asynchronously pushing immutable image and delta layers to object storage. To answer a GetPage@LSN, the pageserver walks down to the first page image at or before the LSN, then replays collected deltas on top; the delta chain is the hidden cost that eager image creation now mostly amortises away.

The numbers are the headline. On a production fleet slice, the compute local cache serves roughly 1.1 billion page lookups per second and handles about 99.46% of all accesses; pageserver NVMe serves roughly 6 million lookups per second and 0.54%; object storage sees about 39 requests per second, or roughly 1 in 28 million accesses. Durability on object storage is cited at 99.999999999% — eleven nines. The deltas-applied-per-GetPage metric from us-east-1 between 13 and 19 October 2026 held p90 under 1 (most reads need no replay at all) and p99 around 6; a recent change that creates base images more eagerly cut the p99 tail and settled it there. That shift is the operational knob that keeps p99 latency flat as workloads grow.

The two cases where a read does reach object storage are old branches or restores (branches are LSN pointers and deep history may not be resident on pageserver NVMe) and long-dormant projects that have scaled to zero for weeks. After the first reads following a wake-up, data is cached and the next reads stay local. Branching, point-in-time restore, and snapshot restore are described as metadata operations that create a new branch at an LSN without copying data, which is why the previously-reported sub-six-second fork times are physically possible at all. The post stops short of giving S3-vs-GCS cost or latency numbers, so teams planning a self-hosted equivalent will still need to profile their own object stores.

### 🎯 Takeaway (Hợp)
If you are evaluating separation-of-storage-and-compute Postgres options — Lakebase, Neon, or a self-build — this is the baseline to measure against: 99.46% cache hit on the compute tier, p90 < 1 delta per GetPage, and a safekeeper quorum for commit durability. Teams running their own Postgres-on-object-storage experiments should prioritise eager image creation and page-level cache sizing before anything else, because the p99 tail lives in the delta replay chain, not in object storage latency. Số đo 1/28 triệu lượt mới phải xuống object storage là lý do Lakebase chạy được dù dùng S3 phía dưới.

### 🔭 Overview (Tổng)
Shruti Prasanna, Nikhil Tallam and Rob Bajra published a 17 November field report rounding up what Databricks' internal Lakebase Hackathon produced, and the writeup is more useful as a pattern catalogue than as a product announcement. The thesis is that copy-on-write Postgres branches, cheap enough to fork in roughly five to six seconds, change what a database is for: not just a system of record but a scratch space that agents, pull requests and schema designers can use without ceremony. Nine named projects (Lyft, CIBC Branchflight, Arbital Health, Reach Mobile, Markel, Data Axle, PriceWise, Sobeys and an unnamed insurer) are summarised with enough concrete detail to be reproducible. The post includes no code — Databricks links to the Lakebase docs for the SDK side — but the measured outcomes are the sharpest numbers Databricks has published on Lakebase since launch.

### 🔬 Details (Phân)
The hackathon patterns cluster into three buckets. The agent-sandbox bucket contains Lyft (fork a branch, apply the agent's action, read the actual database state, correct, repeat; branches resolved 10 of 11 support tickets within policy versus 2 of 11 with upfront planning) and Jevons Search; forking took about six seconds and the team's own takeaway was that more branches did not produce more passes — the win came from feeding the real database state back into the agent. The pull-request bucket contains CIBC Branchflight (every PR gets a zero-copy branch from a PII-masked template, scale-to-zero, auto-expiry, and a schema-diff check before merge; branch creation under five seconds) and Arbital Health / 7NF (each schema layout as its own branch, models graded on returned rows). The schema-experimentation and online-store buckets contain Reach Mobile (branch-test new product attributes before touching production), Markel (consolidated a search index onto governed gold tables served through Lakebase, retiring an Elasticsearch-style index), Data Axle and PriceWise (pgvector + BM25 hybrid search with Reciprocal Rank Fusion plus PostGIS proximity, pricing responses in ~4 ms across 18,000+ listings), Data Axle's agent-memory-in-Postgres pattern, and Sobeys' multi-agent retrieval stack (Vector Search for recipes, pg_trgm for products, a health agent on allergy profiles).

The platform surface named in the post ties this to the rest of the Databricks stack rather than treating Lakebase as a standalone: Unity Catalog governance covers both lakehouse tables and the Postgres tables serving them; Synced Tables continuously copy Unity Catalog tables into Postgres as read-only tables via managed Spark Declarative Pipelines; Lakehouse Sync pushes Postgres changes back into Unity Catalog Delta tables through CDC; the Lakebase Change Data Feed streams Postgres changes to Delta for analytics; and pgvector, PostGIS and pg_trgm sit on the Postgres side. Online Feature Stores reuse Lakebase as the online layer for features defined on the lakehouse, which is the quiet piece of news for teams who have treated Lakebase as "OLTP next to the lake."

The honest caveat is that all nine success metrics are from one-week hackathon projects on Databricks-internal infrastructure, so the Lyft 2→10 jump should be read as "this pattern worked on one support backlog with 11 tickets" rather than a benchmark. Nothing in the post gives SLOs, p99 latency figures, or branch count ceilings. Per-PR preview environments against a real production dataset also need a serious PII-masking template pipeline, which CIBC had already built; it is not free.

### 🎯 Takeaway (Hợp)
Steal three patterns from this post before writing new Lakebase code: agent sandboxing on branches (fork, act, observe the real database, correct) with precise prompts rather than many branches; per-PR preview environments from a masked template; and consolidating an Elasticsearch-style search index onto governed Postgres tables with pgvector + BM25 + pg_trgm. The 5–6 second branch time is the enabling constant — if your own Postgres fork takes minutes, these patterns are not reachable yet. Thông điệp cốt lõi là feedback-loop ngắn với database thắng bruteforce branch, không phải branching rẻ là xong.

```sql
      refund_amount_cents = 1299

-- Hybrid search pattern from Data Axle / PriceWise.
WITH vec AS (
  SELECT product_id, 1 - (embedding <=> :query_embedding) AS v_score
  FROM listings
  ORDER BY embedding <=> :query_embedding
  LIMIT 100
), bm25 AS (
  SELECT product_id, pdb.score(product_id) AS b_score
  FROM listings
  WHERE name ||| :query_text
  LIMIT 100
)
SELECT product_id,
       COALESCE(v_score, 0) + COALESCE(b_score, 0) AS rrf_score
FROM vec FULL OUTER JOIN bm25 USING (product_id)
ORDER BY rrf_score DESC
LIMIT 20;
```

For engineers used to STM32H7 and i.MX RT boards, this is the first time a mainland Chinese MCU vendor has matched that tier on clock, flash and certification with an EtherCAT slave controller on die.

### 🔬 Details (Phân)
The part differentiation is practical. The `GD32H77R` is positioned as the robotic-joint SKU with two integrated 100 Mbps Ethernet PHYs, EtherCAT latency under 50 ns, FSoE support and 5,632 KB flash — enough on-die PHY work that a joint controller no longer needs an external PHY plus switch. The `H78D`/`H77D` are HMI parts with 2-lane MIPI DSI, a TFT-LCD controller, an Image Processing Accelerator and a digital camera interface, plus 4× SAI, 4× I2S, S/PDIF and PDM — effectively a cost-down path from an application processor for mid-tier panels. The `H78E`/`H77E` are real-time motion control parts with EtherCAT distributed clock cycles as short as 62.5 μs, EnDat / BiSS-C / Tamagawa / HIPERFACE DSL encoder protocols, and a resolver-to-digital conversion module. The `H789`/`H779` are the general-industrial SKUs with the display/camera subsystem but without motion encoder support.

Across the lineup the compute and peripheral baseline is uniform: 3,736 CoreMark, up to 2× OSPI at 200 MHz with DTR, 2× SDIO, 3× CAN-FD, up to 8× USART, 4× I2C, 6× SPI, dual 14-bit ADCs at 4 MSPS, a 12-bit ADC at 5.3 MSPS, two advanced PWM timers, a trigonometric math unit and hardware FFT/FIR filtering. Security covers AES, SHA-256, TRNG, unique chip ID, secure boot, authenticated updates and anti-rollback. Supply is 1.71–3.6 V and the operating range is −40 °C to +105 °C. Packaging is BGA169 on the `H77R`, BGA176 on the HMI/motion parts, and up to BGA176/LQFP176/LQFP144/LQFP100 options on the `H789`/`H779`, which is unusually broad for a part at this clock.

The honest caveats are two. First, pricing was not announced; samples ship by January 2027 with mass production from April 2027, which means these parts show up in production designs in the second half of 2027 at the earliest. Second, IEC 61508 SC3 covers the silicon's systematic-capability claim, but a SIL 2/SIL 3 end product still requires the system-level safety case and a safety manual from GigaDevice (not yet published). Engineers evaluating the parts against STM32H7-SIL or Renesas RA8 should treat this as a design-in window, not a production decision.

### 🎯 Takeaway (Hợp)
If you are speccing a 2027 robotic-joint controller, a MIPI-DSI HMI, or a servo motion board, put the GD32H7 lineup on the short list alongside STM32H7 and i.MX RT — the `H77R` (joint, dual PHYs) and `H78E`/`H77E` (62.5 μs distributed clock) are the two SKUs that most clearly exceed the current Chinese-vendor tier. Start now on development boards (`GD32H77DI-EVAL`, `GD32H77EI-EVAL`, `GD32H779I-EVAL`) since production parts are two quarters out. Kênh encoder đầy đủ cộng EtherCAT slave on-die là tổ hợp hiếm trong Cortex-M7 tier.

### 🔬 Details (Phân)
The compute story is three-sided. NPU-wise, the 44 TOPS sparse figure likely implies a 5-core architecture at up to 8.8 TOPS per core, but Rockchip published no actual AI workload benchmarks, so the number is a peak claim rather than a measured one.

The memory and I/O side is where RK3668 pulls clearly past the RK3588. LPDDR6-10667 with a 96-bit bus is new for a Rockchip SoC and gives up to 90 GB/s usable bandwidth from a 128 GB/s theoretical peak — enough to keep a 44 TOPS NPU fed on medium-size vision workloads. Storage options span UFS 4.0 two-lane up to 11.7 GB/s, eMMC 5.1 HS400, SDIO 3.0, NVMe, SFC and multiplexed SATA 3.1. Networking is 2× RGMII for Gigabit plus multiplexed XGMII for 10GbE, which makes the part credible as a NAS or small-form-factor NVR SoC. Video encode and decode reach 8Kp120 and 8Kp60 respectively (H.265/H.264/VP9/AV1/AVS2), display outputs up to 2× 8Kp60 or 6× 4Kp60 with HDMI 2.1, eDP/DP and MIPI-DSI, and the ISP handles dual 24 MP plus a 16 MP sensor.

The governance and safety side is where RK3668 catches up to automotive-grade competitors: a dual Cortex-M52 safety domain, TrustZone, secure boot, key ladder and HDCP. Rockchip positions the part for Android servers, smart kiosks/HMI, NVR/CVR, robots, NAS, PLCs, automotive dashboards and industrial box PCs. Caveats are the usual Rockchip ones: the roadmap says ES in Q1 2027 and early SBC prototypes in H1 2027, but the RK3688 flagship, nominally end-of-2027 or 2028, has slipped before and the author explicitly cautions against treating the timeline literally. Memory bandwidth and PCIe details are also still preliminary, and no block diagram has been released.

### 🎯 Takeaway (Hợp)
If you are planning a 2027–2028 SBC, NAS or edge-NVR refresh against the RK3588 or RK3399, RK3668 is now the realistic target part — book the 8-core A725/A520 configuration into your cost model with LPDDR6 and 10GbE as optional upsells, and treat the 44 TOPS NPU figure as a ceiling, not a working number, until Rockchip publishes benchmarks. Teams on the earlier 10-core assumption need to redo their cost and power envelopes. Mốc Q1 2027 cho ES là chốt chặn thực tế — SBC thương mại khả thi sớm nhất cuối 2027.

The board is positioned against boards like the Arduino VENTUNO Q ($399) rather than against an NVIDIA Jetson Orin NX, and bundles an eight-core CPU, a 40 INT8 TOPS NPU, 2.5GbE plus Gigabit Ethernet, isolated RS485 and CAN-FD on terminal blocks, and a 24 V DC input in a −40 °C to +85 °C operating envelope. The relevance for IoT and edge-AI engineers is that Qualcomm's industrial SoMs are now reaching second-tier integrators, which puts price pressure on the NXP i.MX 9 and Rockchip RK3588 tiers.

### 🔬 Details (Phân)
The SoC datasheet is the clean bit. The QCS8275-AA is an octa-core design with 2× Cortex-A78 "Kryo Gold Prime" at 2.35 GHz, 2× Cortex-A78 "Kryo Gold" at 2.1 GHz and 4× Cortex-A55 "Kryo Silver" at 1.95 GHz, paired with an Adreno 623 GPU and a 40 INT8 TOPS NPU (dense; the writeup rounds this as "up to 40 TOPS"). On the SoM Forlinx fits 12 GB of LPDDR5 and 256 GB of UFS 3.1 flash, with a microSD slot and an eMMC footprint that shares the interface with microSD via a 0 Ω resistor. Linux support is a Forlinx BSP based on kernel 6.18.44.

Networking and I/O are where the board picks a lane. Wired networking is Gigabit Ethernet plus 2.5GbE on RJ45; optional Wi-Fi and Bluetooth sit on an M.2 Key-E module and optional 4G LTE or 5G on an M.2 USB module. USB is a USB Type-C OTG port (used for flashing), multiplexed with a Type-A port via a switch, plus 2× USB 3.0 (one multiplexed with USB-C) and a USB 2.0 Type-A. Display covers DisplayPort and MIPI-DSI for a 7-inch 1024×600 Forlinx panel; three MIPI-CSI FPC connectors expect Sony IMX577 modules by default. Audio is handled by a MAX98357AETE+ amplifier plus an I2S codec driving speaker, 3.5 mm headphone and microphone. The industrial I/O block is 2× isolated RS485 and 4× isolated CAN-FD on terminal blocks, plus a PCIe x4 slot, pin-header GPIOs, JTAG, and an RTC with button battery.

Positioning against alternatives is the practical question. Against a Jetson Orin Nano with similar INT8 TOPS, the OK8275AA-C is cheaper on the BOM side (QCS8275 modules are lower-priced than Orin SoMs), carries more wired I/O out of the box (isolated RS485/CAN-FD are not standard on Orin Dev Kits), and runs on 24 V DC — the right voltage for a DIN rail. Against an NXP i.MX 93 board the OK8275AA-C is better on CPU and NPU but worse on long-term industrial availability guarantees (NXP's 15-year lifecycle promise is still the benchmark). The caveats in the article are that Forlinx has not announced pricing or availability yet, dimensions are "TBD," and the MIPI-CSI connectors are pinned to IMX577 by default — swapping sensors requires a custom carrier.

### 🎯 Takeaway (Hợp)
If you are building a −40 °C to +85 °C perception node that needs multi-camera MIPI-CSI, isolated industrial serial and 40 TOPS of NPU on a 24 V rail, bench the OK8275AA-C against a Jetson Orin Nano Industrial carrier on three axes: total cost including isolation, BSP maturity (Forlinx kernel 6.18.44 vs NVIDIA JetPack), and camera-sensor flexibility beyond IMX577. Pricing being unannounced is the main blocker. Qualcomm Dragonwing đã ra khỏi nhóm "chỉ dành cho robotics flagship," đây là tín hiệu rõ ràng.

### 🔭 Overview (Tổng)
CNX Software's 17 November hands-on review, by Jean-Luc Aufranc translating Arnon Thongtem's Thai-language review, covers Seeed Studio's OpenDisplay 4.26″ Mono Kit and 7.3″ Color Kit — two BLE e-paper dashboards built on the XIAO nRF52840 Plus board and the EN05 (mono) or EN04 (colour) ePaper carrier. Both panels run 800×480, both ship with the open-source OpenDisplay firmware (2.26.6 preloaded, updated in the review to 2.27.1), both include a 2,000 mAh battery, and both integrate with Home Assistant through the OpenDisplay integration that has been in Home Assistant Core since version 2026.4. Store pricing is $39.90 for the mono kit and $79.90 for the colour kit; the AliExpress 11.11 sale moved them to $33.28 and $76.18.

### 🔬 Details (Phân)
The hardware stack is standard but tidy. Both kits put a XIAO nRF52840 Plus on top of an ePaper carrier board (EN05 for mono, EN04 for colour), a power switch, reset button, three user buttons, a USB-C port and a white 3D-printed enclosure (STLs are free on the Seeed wiki). The mono panel supports partial refresh and was driven with 4-level grayscale for a sensor-page example; the colour panel supports six ink colours. The reviewer flagged that "fast" refresh can leave remnants of the previous image, which matters for dashboards that cycle every few minutes.

The firmware and tooling story is where OpenDisplay differentiates against ESPHome-driven e-paper designs. OpenDisplay is open source and OTA-updatable; configuration happens through two complementary tools, the BLE Tester (browser-based image upload over Web Bluetooth, tested in Edge on Windows 11) and the OpenDisplay Toolbox (configuration over BLE, USB firmware flashing via Chrome or Edge, and UF2 factory-restore files). A QR code on the device links to a landing page for setup. On the Home Assistant side the integration exposes seven entities per display (battery, three buttons, connectivity, temperature), the `opendisplay.upload_image` action takes `dither_mode`, `refresh_mode`, `fit_mode` and `rotation`, button presses fire as `event.<display>_button_1..3`, and the reviewer recommends placing an ESP32-S3 running ESPHome as a BLE proxy if the HA host is not physically close.

Performance was measured end-to-end. Image upload through the action took about 9 seconds on mono and 38 seconds on colour; a sensor page automation rendered an 800×480 PNG through a Python `shell_command` using Pillow, passed the result as Base64 and uploaded it, with about 6 seconds total on mono and 35 seconds on colour. Buttons fire events immediately but the page update that follows is slow, so the reviewer suggests treating buttons as triggers for scheduled automations rather than instant page-switchers. Seeed's battery-life claims — about 2 years on the mono kit with 15-minute updates and about 1 year on the colour kit with 2-hour updates — were not re-measured but match the expected duty cycle for a 2,000 mAh pack driving an nRF52840 that is asleep between refreshes. The HA integration quietly landed in Core 2026.4 in April, so no firmware or integration install is required on fresh Home Assistant installs.

### 🎯 Takeaway (Hợp)
If you want a low-maintenance BLE e-paper dashboard in a self-hosted Home Assistant setup and already have an ESP32-S3 Bluetooth proxy, the mono kit at $39.90 is the cheapest clean option; pay up for the colour kit only if the dashboard needs to encode categorical state (e.g., power source colour, weather icon). Expect ~6 seconds end-to-end on mono and ~35 seconds on colour per refresh, and design automations around that latency. Seeed đang đóng gói hoàn chỉnh một pipeline OpenDisplay + HA tới mức khó chê nếu chỉ cần a BLE e-paper dashboard.
