### 🔭 Overview (Tổng)
Heqing Ya, Tan Zhang, Ankit Batra and Abhishek Rai on the Databricks Compute Platform team published an 18 November engineering writeup that explains why fixed API rate limits break down for cluster creation and how the team replaced them with an adaptive, slot-based scheduler. The headline number is a 7.5× increase in the default cluster-creation rate limit, combined with a reported reduction of more than 99.99% in cluster-creation rate-limit errors and the retirement of more than 100 customer-specific rate-limit overrides. The post is unusually candid about the operational pathology — an API call returns in milliseconds while the background workflow behind it can take minutes, so the same request rate pushes very different amounts of work in flight when a cloud provider is slow — and about the fact that engineers had been manually lowering limits during incidents and raising them afterward. For anyone operating a workload-orchestration control plane behind customer APIs, the pattern it describes is directly transferable.

### 🔬 Details (Phân)
The new scheduler has six moving parts that cooperate. Each cluster-creation workflow holds a slot from the moment the API accepts the request until the background provisioning finishes, so the scheduler bounds work-in-flight rather than request-arrival rate. The limit on those slots is adaptive: congestion signals such as provisioning latency and thread-pool saturation shrink it and recovery grows it cautiously, which keeps the control plane out of a death spiral when a cloud provider slows down. Accepted requests that cannot yet be serviced wait in bounded queues with explicit size and wait-time limits, and anything that expires or becomes unservable is rejected cheaply rather than piling up. Fair scheduling defines per-tenant shares and priorities under contention, and idle capacity can be used where policy allows so that a quiet tenant does not starve a busy one. Retry controls add backoff and attempt limits so that already-accepted work cannot stage a retry storm that the API-level limiter never sees, and running clusters and allocated VMs are tracked on separate counters from the in-flight workflow slots so one does not disguise the state of the other.

The platform context is the part that connects this to the rest of the Databricks stack. The fixed API request-rate limiter is retained as a final guardrail against extreme traffic — the slot scheduler sits in front of it, not instead of it — which matters because customers and internal services talk to the same public endpoints. Observability is separated into three signals: service degradation, per-tenant demand, and scheduling decisions, so on-call engineers can tell whether a backup is caused by a slow dependency, a noisy tenant or the scheduler itself rejecting work. The post is explicit that the rollout analysis above is from an initial measurement window and does not include latency or throughput numbers, which is the honest reading of what the team can confidently claim.

The adoption implication is that teams with similar long-running provisioning workflows — Snowflake virtual warehouses, BigQuery reservations, EMR clusters, CI/CD pipelines, Kubernetes control planes with custom controllers — should audit whether their current rate limiter sees the request or the work. A fixed requests-per-second gauge on an endpoint that fans out to minute-scale background work will always be tuned conservatively for the worst-case fan-out, and the slot-based alternative recovers the headroom. The practical cost is substantially more plumbing: a workflow registry that knows when a slot is released, congestion signals wired into the scheduler, and queue and fairness policy that is itself testable.

### 🎯 Takeaway (Hợp)
If you run a control plane whose public API triggers background work orders of magnitude longer than the API call itself, this is the design reference to copy before adding more fixed per-customer overrides. The honest value here is not 7.5× — it is that the 100+ customer-specific overrides could be retired, which is the operational tax that fixed limits had been quietly collecting. Bỏ limit cứng để đổi lấy slot adaptive là lựa chọn đúng cho mọi control plane có "API millisecond, workflow phút."

## 3. Bluetooth SIG Ratifies Bluetooth 7.0 Core With the Optional HDT Physical Layer Hitting Up to 7.5 Mbps, and a Nordic Semiconductor 2 MB File-Transfer Demo Measures ~3.8 Mbps on HDT7.5 Versus ~1.4 Mbps on LE 2M and ~0.76 Mbps on LE 1M

### 🔭 Overview (Tổng)
Jean-Luc Aufranc's 18 November summary on CNX Software of the Bluetooth 7.0 Core Specification is the first consolidated engineering walk-through of the ratified standard the Bluetooth SIG published on 3 November. The headline addition is HDT (High Data Throughput), an optional LE physical layer that raises the maximum link-layer bit rate to 7.5 Mbps using higher-order coherent modulation plus forward error correction with puncturing. Besides HDT, 7.0 adds four other mechanisms — Isochronous Parameter Update, Encryption Key Schedule, Transient Application Key and Encryption Production Debugging — that collectively change how encryption keys, transient pairings and live CIS parameters are handled. The target use case named for HDT is high-resolution and lossless audio streaming, but a 7.5 Mbps link also expands the envelope for firmware images, camera preview streams and OTA model updates to on-device ML.

### 🔬 Details (Phân)
The HDT PHY is not a drop-in upgrade. It is a new non-GFSK PHY with five bitrates named HDT2 through HDT7.5, synchronization enhancements, adaptive rate selection and new packet architectures; the Link Layer gains a new packet structure, three new packet format variants, an HDT Configuration exchange procedure, and updated PHY Update and CIS Creation procedures. Host-side changes touch L2CAP, GAP, ATT and GATT, and the Security Manager (SMP) is the only LE-stack block left unchanged — which is important for stack implementers scoping an upgrade. The Nordic Semiconductor demo transferred a 2 MB file over a single link and measured roughly 3.8 Mbps average and 3.9 Mbps peak on HDT7.5 for a ~4 s transfer, against roughly 1.4 Mbps average and peak on LE 2M (~12 s) and 0.76 Mbps average and 0.77 Mbps peak on LE 1M (~22 s). The gap between the 7.5 Mbps theoretical ceiling and the 3.8 Mbps measured average is the PHY overhead to budget for in real designs; peak and average being close on HDT7.5 and LE 2M also suggests the demo was link-bound rather than host-bound.

The four non-HDT features change several pain points in deploying LE Audio and secure pairings. Isochronous Parameter Update lets a host change the parameters of an active CIS without tearing down and recreating the CIG, which means a headset switching between music and voice can adjust the isochronous channel in place instead of forcing an audible drop. Encryption Key Schedule combines ECDH key establishment with a CMAC-based key derivation hierarchy, supports key refresh and longer MIC sizes, and underpins HDT encryption — so HDT and the new key schedule arrive as a pair, not two separable features. Transient Application Key enables Link Layer encryption without pairing or bonding, with the application supplying a 128-bit secret and the Host discarding the TAK after starting the Encryption Start Procedure, which is the mechanism that commerce and ticketing applications need for ephemeral encrypted links to anonymous devices. Encryption Production Debugging gives Hosts a controlled way to receive active encryption credentials for protocol analysis, which materially reduces the pain of field-debugging an encrypted LE Audio stream.

The adoption implication is twofold. For audio vendors already in the LE Audio pipeline, HDT plus EKS plus IPU is a practical set that justifies a 7.0 silicon refresh in 2027 — lossless codecs at 48 kHz 24-bit stereo sit comfortably under 3.8 Mbps measured throughput. For IoT vendors outside audio, the TAK-based paired-less encrypted link is the more interesting primitive, because it reframes "pair, bond, store identity" as a workflow specific to long-lived devices. Caveats: HDT is optional, so a 7.0-stamped SoC does not necessarily implement it; vendors must advertise HDT explicitly in their datasheet. Nordic's demo is a single-link, single-file benchmark on prototype silicon, and nothing here measures density under many concurrent HDT links.

### 🎯 Takeaway (Hợp)
If you ship audio or wearable products, put Bluetooth 7.0 with HDT and EKS on your 2027 silicon shortlist and spec HDT support explicitly rather than assuming it from the 7.0 label. For non-audio IoT, prototype a TAK-only encrypted-handshake path to see whether you can retire your pairing/bonding code for short-lived sessions. Lưu ý 7.5 Mbps là trần lý thuyết — thực đo ~3.8 Mbps, nên lên kế hoạch dung lượng theo đó.

Device onboarding uses BLE, device-to-cloud is MQTT, user clients talk HTTPS and admin tools use the AWS SDK; local control over IP is supported alongside Matter, and the platform ships with bridges for Zigbee, BLE mesh and Matter so non-Espressif devices can be consolidated on the same cloud. Voice-assistant integrations cover Alexa, Google Home and SmartThings, which keeps parity with the original hosted RainMaker. The notable addition is a Model Context Protocol (MCP) server, which exposes RainMaker control to AI assistants in a way that lets an agent list devices, read state and issue commands through MCP rather than scraping dashboards or writing bespoke API glue. Combined with the Enterprise Plan option of "private AI agents," Neo is positioning itself as the first open-source IoT control plane with first-class AI-assistant integration baked into the architecture rather than bolted on.

The operational and licensing story is the part that will decide adoption. The open-source core is Apache License 2.0; the paid Enterprise Plan adds SLAs, enterprise identity features, ESP Insights diagnostics, private AI agents and consulting. The pricing is purely AWS consumption — messages, requests, stored bytes — so there is no per-node or platform fee from Espressif on the core, and an online cost calculator is provided. The post deliberately does not publish cross-platform benchmarks or per-million-message cost comparisons against AWS IoT Core standalone, Azure IoT Hub or self-rolled MQTT-plus-DynamoDB stacks; teams evaluating Neo will need to model those costs for their fleet shape. Deployment uses an Installer and the repository ships helper files including a `CLAUDE.md` and slash commands such as `/deploy`, although no snippet is shown in the launch post.

The adoption implication cuts two ways. For Espressif-centric fleets that have been blocked from the old RainMaker by data-residency, procurement or custom-domain requirements, Neo removes the biggest blocker — the cloud runs in the customer's own AWS tenant, under the customer's own IAM. For non-Espressif fleets, the Zigbee, BLE mesh and Matter bridges plus the MCP server make Neo an interesting candidate as a vendor-neutral control plane, although the obvious caveat is that the AI-assistant workflow is specified more in product-pitch terms than protocol terms in the launch post. No roadmap is published beyond "continue to refine and maintain our AI rules and skills and add more as we go."

### 🎯 Takeaway (Hợp)
If you have been running an ESP32 fleet on a self-rolled AWS IoT Core deployment or holding off the original RainMaker over residency rules, pilot Neo in a dev AWS account with the Installer and measure the three-way cost against your current stack plus AWS IoT Core standalone. Treat the MCP server as a differentiator for AI-assistant operations rather than a replacement for a REST or SDK path, and lock the Enterprise Plan decision behind a proof-of-concept on SLA and private-agent features. Trade-off chính là bạn tự chịu chi phí AWS và quản lý tenant, đổi lại hết limit của RainMaker hosted.
