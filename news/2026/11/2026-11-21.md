## 1. DuckDB Ships 2.0.1 LTS With Host-Scoped Extension Repositories, Reversion of the 2.0 Multi-Match UPDATE/MERGE Semantics, Patches for Two CVEs Including a Linux Kernel MADV_FREE Data-Loss Issue, and a Reminder That DuckDB 1.4 LTS Lost Community Support on 17 November

|---|---|

| 🏷️ Topic | Release |
| 🌐 Domain | Data Engineering |
| 🔑 Keywords | `duckdb-2-0-1` · `lts-release` · `cve-patches` |

### 🔭 Overview (Tổng)
The DuckDB team's 20 November release post announces 2.0.1 LTS, the first patch release in the Cinnamon Teal line that shipped on 21 October. The release's surface area is small but opinionated: a new host-scoped `CREATE EXTENSION REPOSITORY` model that tightens how custom extensions resolve, a reversion of the 2.0 semantic for `UPDATE ... FROM` and `MERGE` that restores 1.x behaviour in the presence of multiple source matches, and security patches for two CVEs — one of them the `MADV_FREE` allocator issue that could silently zero memory on affected Linux kernels. The DuckDB 1.4 LTS line, meanwhile, lost community support on 17 November, so the post is also the practical cutoff notice for anyone still on 1.4. For embedded-analytics and local-ETL teams running DuckDB in production, this is the 2.0 patch that fixes the two correctness and safety issues most likely to bite at scale.

### 🔬 Details (Phân)
The extension-repository change is the most invasive piece. Instead of trusting a raw URL at install time, 2.0.1 registers repositories by hostname — `CREATE EXTENSION REPOSITORY duckdb.org;` — and the new default for `allow_extension_repositories` is `hosts`, with `allowed`, `hosts_only`, and `forbidden` as the other explicit modes. The old `undecided` value is no longer accepted, which means operators who used to lean on the implicit path have to either register the host or set the mode to `forbidden` to lock down to DuckDB-signed extensions only. On the DML side, 2.0.0 had enforced "at most one update per target row" for `UPDATE ... FROM` and `MERGE`; 2.0.1 reverts to 1.x behaviour, where the target is updated once per matching source row and the result can be non-deterministic when sources disagree, so teams that leaned on the 2.0 enforcement have to re-check their joins and aggregate matches explicitly. `SECRET` scope matching is also stricter — `s3://bucket-` no longer matches `s3://bucket-1/` — which closes a surprising footgun without touching the wire format.

Security and reliability land in a dense set of smaller fixes. CVE-2026-97945 is the Linux allocator issue: the bundled jemalloc configuration previously used `MADV_FREE`, and on affected kernels that could result in silent zeroing of hot memory; 2.0.1 drops `MADV_FREE`, and for operators who cannot upgrade immediately the post offers the mitigation `DUCKDB_JE_MALLOC_CONF=muzzy_decay_ms:0`. CVE-2026-111497 fixes the Brotli decoder; `CREATE SECRET` is now refused when `enable_external_access=false`; and a remote path-traversal issue is closed. Correctness fixes cover Parquet `IS NULL` pruning, lateral joins reading from CTEs, missing `NULL` rows when filtering tables written by 1.x, plus crash fixes such as `list_select` on empty lists and deadlock fixes in materialized CTEs. The Python client gets hang/crash fixes at exit, including on Python 3.14, and `TIMESTAMPTZ` fetching no longer depends on `pytz`.

Platform, extension, and lifecycle changes round out the release. The `azure`, `iceberg`, `postgres`, and experimental `glue` extensions are updated alongside `pg_duckdb`; the `aws` and `glue` extensions are now available in DuckDB-Wasm; and the `wasm_mvp` platform has been discontinued. `iceberg_rewrite_data_files` now returns Spark's output column names, which is a small but welcome compatibility move for mixed Spark/DuckDB rewrite flows. The honest caveats: the post offers no benchmark figures, lifting filter pushdown into subquery views and Parquet page-index skipping are described only qualitatively, and the end of community support for 1.4 LTS on 17 November is explicit — the recommended path is to move to 2.0 LTS, supported until at least October 2027.

### 🎯 Takeaway (Hợp)
Upgrade from 2.0.0 to 2.0.1 before relying on the new 2.0 `MERGE` enforcement — the semantics are now back to 1.x, so any code that depended on "one update per target row" must be rewritten to aggregate sources upstream. If you are on 1.4 LTS, this is the week to plan the move to 2.0 LTS; community support for 1.4 ended 17 November and there is no newer 1.x patch coming. Nếu chưa kịp upgrade và đang chạy DuckDB trên Linux, đặt `DUCKDB_JE_MALLOC_CONF=muzzy_decay_ms:0` trong môi trường để tránh `MADV_FREE` data-loss, nhưng coi đó là mitigation tạm thời.

### 💡 Example
```sql
-- 2.0.1 LTS: register and lock down extension repositories by host
CREATE EXTENSION REPOSITORY duckdb.org;
INSTALL AND LOAD spatial FROM duckdb.org;

-- Only allow DuckDB-signed extensions from registered hosts:
SET allow_extension_repositories = 'hosts';        -- new default
-- SET allow_extension_repositories = 'forbidden'; -- lock out custom repos

-- 2.0.1 reverts 2.0's MERGE enforcement: a target row can be
-- updated multiple times when multiple source rows match.
-- Aggregate matches explicitly to keep behaviour deterministic.
MERGE INTO customers AS t
USING (
  SELECT customer_id,
         MAX(updated_at) AS updated_at,
         ANY_VALUE(email) AS email
  FROM   staging_customers
  GROUP  BY customer_id
) AS s
ON  t.customer_id = s.customer_id
WHEN MATCHED THEN UPDATE SET email = s.email, updated_at = s.updated_at;

-- Linux mitigation for CVE-2026-97945 if you cannot upgrade yet:
--   export DUCKDB_JE_MALLOC_CONF=muzzy_decay_ms:0
```

### 🔭 Overview (Tổng)
Savannah Longoria's 19 November Databricks post announces that PostgreSQL 19 is available on Lakebase the same day the upstream community released it. The framing is deliberately operational — the piece is not a feature tour so much as a list of the changes a DBA runs into at 3 a.m.: bloated tables, unstable query plans, replica lag, and maintenance work that could not previously run while an application was online. For data platform teams using Lakebase as their application-plane Postgres under Delta-fed workloads, this is the first point in the upgrade cycle where the new in-tree operational features are available without having to wait on managed-service catch-up.

### 🔬 Details (Phân)
The highlighted feature is `REPACK`, which reclaims space and can physically reorder rows; with `CONCURRENTLY`, reads and writes continue through most of the operation. The honest caveats are in the post: `REPACK CONCURRENTLY` uses a replication slot, needs temporary disk space, and has a per-run cap of around 104 million tuples updated or deleted during the run, controlled by `max_repack_replication_slots`. Query-plan stability has a new option: `pg_plan_advice` describes, applies, and reports on planner advice, and the `pg_stash_advice` extension stores advice keyed by `query_id` so it survives application deploys without baking hints into query text. Autovacuum scales out: parallel workers for index vacuuming, a prioritisation score for tables, new views (`pg_stat_lock`, `pg_stat_recovery`, `pg_stat_autovacuum_scores`), and diagnostics covering asynchronous I/O and full-page WAL bytes. Logical replication learns a non-restart enable path, carries sequence values to subscribers, and gains `retain_dead_tuples` so subscribers can detect `update_deleted` conflicts.

The application-facing syntax changes are a shorter list but worth planning for. `WAIT FOR LSN` lets a standby block until replay reaches a given LSN, which is the read-your-writes primitive teams used to fake with stale-check loops. `INSERT ... ON CONFLICT DO SELECT` returns both existing and newly inserted rows without creating a conflict row version — the replacement for the common `DO UPDATE SET col = EXCLUDED.col` workaround done purely to get the row back. `COPY TO JSON` exports one object per line by default, or a single array under `FORCE_ARRAY`; the post is explicit that it is export-only. Smaller sweeteners include JSON path string methods, `random()` support for date and timestamp types, `IGNORE NULLS` / `RESPECT NULLS` on five window functions, automatic I/O worker scaling via `io_method = worker` / `io_min_workers` / `io_max_workers`, and the removal of a handful of features that did not make the cut (SQL/PGQ, `FOR PORTION OF`, partition merge/split, `GROUP BY ALL`, non-text `pg_dumpall`).

Compatibility risk is concentrated in a few defaults that migration plans need to account for. JIT compilation is now off by default; TOAST compression defaults to LZ4 instead of pglz; MD5 password authentication carries stronger deprecation warnings; RADIUS authentication support is removed; `standard_conforming_strings` is always on; `pg_upgrade` rejects clusters with affected `btree_gist` indexes on `inet` or `cidr`; and database, role, and tablespace names can no longer contain carriage returns or line feeds. Databricks' own guidance is conservative: test real workloads in dev or staging, keep production on the current version until results satisfy, confirm every extension is available on PG19 (not all PG18 extensions are), and remember that sequences carried by logical replication are not streamed continuously, so a refresh before cutover is required. The post flags PostgreSQL 19.1, expected around February, as the natural production-upgrade date for cautious teams.

### 🎯 Takeaway (Hợp)
If you already run Lakebase for application-plane Postgres, stand up a 19.0 instance and benchmark your two worst bloat offenders under `REPACK CONCURRENTLY` first — this is the feature that pays back the upgrade on its own for most OLTP workloads. Pilot `pg_plan_advice` on the queries whose plans flip under statistics drift, keeping the advice in `pg_stash_advice` instead of SQL comments, and plan production migration around 19.1 in February unless a specific feature is blocking you now. Chú ý JIT đã off mặc định và TOAST chuyển sang LZ4 — khoan bật nếu benchmark chưa xác nhận.

### 💡 Example
```sql
-- REPACK CONCURRENTLY: reclaim space and reorder without blocking writes
REPACK orders USING INDEX orders_pkey CONCURRENTLY;

-- Durable planner hints stored outside of query text
CREATE EXTENSION pg_stash_advice;
ALTER DATABASE appdb SET pg_stash_advice.use_stash = on;

-- Read-your-writes on a replica
SELECT pg_wait_for_lsn('0/1A2B3C4D');

-- RETURNING both existing and inserted rows without a conflict version
INSERT INTO inventory (sku, qty)
VALUES ('X1', 5)
ON CONFLICT (sku) DO SELECT RETURNING sku, qty;

-- One JSON object per line by default; FORCE_ARRAY emits one array
COPY (SELECT * FROM audit_log) TO '/tmp/audit.json' WITH (FORMAT json);
```

### 🔭 Overview (Tổng)
Jean-Luc Aufranc's 18 November CNX Software writeup covers the Bluetooth SIG ratification of Bluetooth 7.0 on 3 November 2026, the first major specification step after the LE Audio and Auracast track. The headline is an optional High Data Throughput (HDT) mode that raises the peak over-the-air rate to 7.5 Mbps on a new non-GFSK coherent PHY with higher-order modulation, forward error correction, and puncturing. Several specification changes beyond HDT also matter for IoT and wearable design: Isochronous Parameter Update changes stream parameters without recreating the group, Transient Application Keys enable link-layer encryption without pairing or bonding, and a new Encryption Key Schedule brings ECDH and a CMAC-based key hierarchy under HDT's security model. For embedded engineers and BLE stack maintainers, this is the biggest LE-layer revision since LE 2M and the first time HDT has moved from vendor-specific to ratified.

### 🔬 Details (Phân)
HDT is the piece getting the attention and also the piece whose caveats are easiest to miss. The spec defines five HDT bitrates with the top at 7.5 Mbps, and the article is explicit that HDT is optional — "Mandatory and optional HDT rates **if** a device implements HDT." The modulation is a departure from the classic GFSK family: a higher-order coherent PHY with FEC and puncturing, which is why the article says HDT changes most of the LE stack while leaving only the Security Manager unchanged. Real-world numbers are more modest than the 7.5 Mbps peak suggests: Nordic Semiconductor reported about 3.8 Mbps average throughput with HDT, peaking near 3.9 Mbps, in a 2 MB transfer demo, versus LE 2M taking about 12 seconds and LE 1M about 22 seconds for the same payload. Backward compatibility is not addressed directly in the writeup, so stack implementers should assume HDT adds a parallel path rather than replacing the existing LE PHYs.

The non-HDT additions carry most of the near-term practical impact for IoT. Isochronous Parameter Update lets a running isochronous stream change its parameters without teardown and recreation of the group, which matters for LE Audio hearing-aid and multi-stream scenarios where the current path forces a brief silence on every tuning. Transient Application Key is the most interesting new primitive: it enables link-layer encryption without pairing or bonding, with authentication handled by a higher-layer application, which fits "ephemeral gateway reads a sensor once and goes away" patterns that previously had no good encryption story. Encryption Production Debugging adds a controlled way for a Host to receive active encryption credentials for protocol analysis, which is pragmatic for bring-up but obviously needs to be fenced off from shipped firmware. The Encryption Key Schedule — ECDH key establishment plus a CMAC-based key hierarchy — underpins HDT security and is the piece the stack vendors will be porting first.

Silicon lead indicators are already visible but early. The article names Ceva's Links200 IP with early HDT support in 2025, Realtek's RTL8773J microcontroller with HDT support in September 2026, and Nordic's test chip and development platform. The honest gap is that no commercial availability date is given for shipping Bluetooth 7.0 consumer devices, and the article's listed use cases — high-resolution or lossless audio, syncing fitness data from wearables, PC peripherals with small displays, and offloading AI processing from smart glasses to a smartphone — are the design wins HDT is sized for, not promises of shipping product. For low-power sensor networks where LE 2M and LE 1M remain better suited, the writeup is explicit that HDT is not the answer.

### 🎯 Takeaway (Hợp)
If you are shipping an LE Audio or wearable product in 2027, add the HDT optionality to your BT stack selection criteria now and plan an isochronous parameter path that assumes Isochronous Parameter Update is present on peers; it will increasingly be. For sensor-network designs, keep the radio on LE 1M/2M — HDT's non-GFSK PHY is a power and silicon-area cost you do not need. Transient Application Key là primitive đáng để kiến trúc sư security xem lại, nhất là cho các flow "gateway đọc một lần rồi đi" từng phải bỏ mã hoá vì cost của pairing.

### 🔭 Overview (Tổng)
Jean-Luc Aufranc's 20 November CNX Software writeup covers the M5Stack Chain Captain, a $35 ESP32-S3R8 dev kit that packages a 1.54-inch 240×240 colour LCD, ES8311 codec with a 1 W speaker and MEMS microphone, BMI270 six-axis IMU, RX8130CE RTC, IR transmitter and receiver, 800 mAh battery, and a four-pin "Chain" port carrying a UART-based Chain Bus for daisy-chained STM32G031 nodes. Chain Captain is positioned as the controller end of M5Stack's new chain-topology ecosystem — Chain nodes slot onto the same UART bus, and the controller presents a battery-powered touch-less front-end with buttons and an RGB LED. For embedded developers who want an ESP32-S3 desktop appliance class device for BLE Mesh gateways, smart-home panels, or portable data-logging rigs, this is a cheap and fully pre-integrated option.

### 🔬 Details (Phân)
Hardware specification is dense for the price point. The SoC is the Espressif ESP32-S3R8 at up to 240 MHz with its vector instructions available for AI acceleration, paired with 8 MB PSRAM and 16 MB SPI flash, WiFi 4 and Bluetooth 5.0 LE with Mesh. The 1.54-inch LCD is driven by a JD9853A at 240×240, audio runs through an ES8311 codec, AW8737A amplifier, 1 W/8 Ω speaker, and a MEMS microphone, and the sensor fit-out is a BMI270 six-axis IMU with an RX8130CE real-time clock. The IR path uses an XL-IRM0038D receiver and an MHS153IRCT emitter, which together make the unit usable as a universal remote. User I/O is a power button, three user buttons, a programmable RGB LED, a red charging LED, and a green status and boot indicator, inside a 56.0 × 40.0 × 17.0 mm 43.9 g enclosure.

The connectivity story is where Chain Captain differs from a generic ESP32-S3 dev kit. The four-pin Chain port acts as the master of a UART-based Chain Bus, which M5Stack designed for daisy-chaining STM32G031-based nodes — so a developer can grow a small distributed I/O or sensor net off a single Chain Captain without using the GPIO header. Alongside it the board exposes a four-pin Grove port and a 15-pin 2.54 mm GPIO header, and programs load through Arduino IDE, UIFlow2, or ESP-IDF. Power comes in on USB-C at 5 V/2 A with input/output support, and the on-board power management (M5PM1 and M5IOE1) brings standby current down to about 14.39 μA at 4.2 V with a full-load figure of about 301.71 mA (1.267 W). Wake sources cover the button, IMU, RTC, and I/O interrupts, which is enough for most low-duty-cycle appliance patterns.

The adoption implication is modest but real. At $35 on AliExpress and the M5Stack store, with Chain expansion modules priced $2.80 to $11.50, the board is cheap enough to buy on a hunch for a smart-home or data-acquisition prototype, and the Chain Bus is the honest new piece — it is a UART bus with a defined connector pinout, not a magical protocol, so interoperability with hand-rolled nodes is straightforward. The caveats are that Bluetooth is 5.0 LE with Mesh rather than LE Audio or Bluetooth 7.0, that the display is small for a user-facing panel, and that the 800 mAh battery under full load is roughly a 2.5-hour window, so Chain Captain is best treated as a tethered appliance rather than a standalone wearable.

### 🎯 Takeaway (Hợp)
If you already live in the M5Stack ecosystem and are prototyping a portable controller for a sensor chain or a smart-home panel, Chain Captain is cheap enough to buy as a drop-in instead of designing a new ESP32-S3 carrier board — the Chain Bus is a plain UART and interoperable with custom nodes. For a long-run battery product, verify the duty cycle against the 14.39 μA standby figure, not the full-load current, and plan for USB-C tethering anywhere the display needs to stay on. Nếu yêu cầu BLE mới, phải chờ silicon Bluetooth 7.0 — ESP32-S3 vẫn dừng ở Bluetooth 5.0 LE.
