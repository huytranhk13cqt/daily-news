## 1. Valkey 9.2 Release Candidate Replaces the Sorted-Set Skiplist With fbtree, a 61-Fanout B+ Tree That Cuts Per-Member Overhead by Up to 43 Percent and Raises ZADD Throughput 105 Percent and ZREM 76 Percent on a 3-Million-Member Set, With OBJECT ENCODING Returning btree Instead of skiplist

### 🔭 Overview (Tổng)
Rain Valentine and Dragos Andriciuc's 16 November Valkey engineering post, which reached the Hacker News front page on 21 November with 204 points, announces that the large-sorted-set data structure is moving from the classic skiplist plus hashtable to fbtree, a 61-fanout B+ tree variant. The change ships in the Valkey 9.2 release candidate now in testing, and the authors are explicit that this is the biggest layout change to the sorted set since the fork from Redis. Small sorted sets that use the listpack encoding are untouched; this is strictly about the large-encoding path. For teams running Valkey or still on upstream Redis for ranking, leaderboard, rate-limiting and priority-queue workloads, the piece is both the practical headline for the next release and a rare opportunity to see concrete before/after numbers on a core engine swap.

### 🔬 Details (Phân)
The memory numbers are the clearest part of the claim. On a five-million-member test with 20-byte members using only the ordered index, sequential inserts cut per-member overhead from 50.3 bytes to 28.5 bytes, a 43 percent reduction that saves roughly 109 MB; random inserts come in at 32.0 bytes, a 36 percent reduction saving about 92 MB, with the smaller gain attributed to more partially filled nodes. The old skiplist carried about 37 bytes of pointer and span overhead per node before the member string, so savings scale with how small members are. Throughput numbers from a Graviton3 c7g.metal with 64 cores, nine I/O threads and pipeline depth 10 on a three-million-member set are: ZADD score-update +105 percent, ZREM 50/50 add/remove +76 percent, ZCOUNT +27 percent, ZRANK +19 percent, ZRANGE 100-element scan +6 percent, ZRANDMEMBER +2 percent, ZSCORE +2 percent, ZRANGEBYSCORE +1 percent, and ZPOPMIN at parity. Confidence intervals are within 2 percent except for ZRANDMEMBER.

The engineering rationale maps cleanly onto those numbers. fbtree nodes pack 61 entries or child pointers into allocation classes aligned to jemalloc, with 512-byte leaves holding up to 61 value pointers and a packed 8-byte normalized score sitting inline next to the member bytes, so no separate pointer indirection is needed to compare scores. Each anchor carries a 4-byte "feature" that SIMD comparisons can scan without reading the child node or a full anchor string, which is where the ZRANK gain comes from. Leaves form a doubly-linked list so that ZRANGE scans move between leaves without climbing the tree, with the next leaf prefetched while the current 61 items are processed. Leftmost and rightmost leaves are cached, which keeps ZPOPMIN at parity rather than regressing. ZSCORE and ZRANDMEMBER barely change because they use the hashtable and never hit the ordered index.

The compatibility and caveat surface is small but real. Sorted-set commands and their semantics are unchanged, but `OBJECT ENCODING` returns `btree` instead of `skiplist` for the large case, so any monitoring, health-check or test asserting the old string needs updating. The post does not discuss RDB or AOF format changes; teams that persist and restore large sorted sets should check their dumps against the RC before planning production cutover. The benchmark branch (PR #4206) was not re-run on the merged commit, the hardware setup is a single instance type, and the authors explicitly ask users to test the 9.2 release candidate with real workloads — especially those relying on large sorted sets — and report issues before GA.

### 🎯 Takeaway (Hợp)
If you run Valkey or Redis for leaderboards, rate limiting or priority queues on large sorted sets, pull the 9.2 release candidate, replay a representative write-heavy workload, and verify the 43 percent memory and 2x ZADD numbers on your own hardware before planning the GA upgrade. Grep your monitoring and tests now for the literal string `skiplist` under `OBJECT ENCODING` to find brittle assertions before the swap bites. Nếu stack đang dùng listpack encoding cho sorted set nhỏ, đổi mới này không chạm — gain đến từ phần big-encoding sau khi vượt ngưỡng.

### 🔭 Overview (Tổng)
Cloudflare's 20 November security post covers nginx2root, the five memory-corruption vulnerabilities that F5 and nginx.org disclosed on 18 November and that Xint's researchers have tied to a Linux SCTP kernel use-after-free capable of escalating an nginx worker foothold to root. F5 rates each nginx CVE at CVSS 3.1 8.1 and CVSS 4.0 9.2 (Critical). The nginx-side fixes are in nginx Open Source 1.30.7 and 1.31.9 and in nginx Plus 37.0.8.1 and 37.3.0.1 — and F5 lists nginx Plus R34 through R36 as affected without a fixed build, which means a forced jump onto the 37.x line. As of 19 November, Censys counted roughly 8.8 million services running a potentially affected version with HTTP/2 enabled; code execution still requires ASLR to be disabled or bypassed, but the primary trigger — HTTP/2 on TLS — is the default on most production nginx deployments.

### 🔬 Details (Phân)
The five nginx CVEs cover distinct triggers, so the mitigation story is not uniform. CVE-2026-123007 is the headline integer-overflow bug in HTTP/2 flow control, present since 1.9.5 in 2015: the WINDOW_UPDATE handler caps the send window at 2^31 − 1, but `ngx_http_v2_filter_cleanup()` refunds the connection window without that cap when cancelled DATA is dropped, and `ngx_http_v2_send_chain()` later compares the window as a signed `off_t`, so once it wraps past 2^63 the loop produces an invalid buffer whose `last` precedes `pos` and that goes straight into `memcpy()` inside `ngx_ssl_send_chain()`. CVE-2026-123633 is an HTTP/2 use-after-free that fires under connection reuse with `proxy_pass` when `worker_connections` is low. CVE-2026-121810 is the equivalent for HTTP/3. CVE-2026-123634 is a resolver use-after-free that needs `resolver`, variable-driven `proxy_pass`, and a `mirror` or SSI subrequest. CVE-2026-113425 is in the mail proxy path with `proxy on` and `auth_http`.

The Linux SCTP use-after-free is the piece that makes nginx2root a composed name rather than a cluster label. It is in the kernel's SCTP send path, has been present since Linux 4.15, and can promote any nginx-worker foothold to root — including from inside a Docker container. As of 18 November, no kernel fix exists, so the operational mitigation is `install sctp /bin/false` in `/etc/modprobe.d/` (which does not unload an already loaded module or disable a built-in SCTP), with a reboot into the kernel fix when it lands. Exploitation signals to watch on the nginx worker side are SIGSEGV crashes, `worker_connections are not enough, reusing connections` warnings, unexpected child processes under nginx workers (an `auditd` rule on `execve` catches these), and for CVE-2026-123634 the `could not cancel <name> resolving` alert. As of 19 November, none of the five CVEs is in CISA KEV, Rapid7's public PoC is scoped to a fresh local container, and fake exploits are already circulating on GitHub — so signature-based WAF rules would be misleading, which is why Cloudflare released none.

The platform caveats matter for teams relying on Cloudflare in front of nginx origins. Cloudflare's own edge is not affected — most of it now runs on FL2 in Rust — and because it terminates client HTTP/2 and HTTP/3 at the edge and opens separate connections to origin, CVE-2026-123007, CVE-2026-123633 and CVE-2026-121810 are blocked for proxied origins. Origin lockdown is a precondition: the protection only holds if direct-to-origin traffic cannot bypass the edge, which in practice means Cloudflare Tunnel, IP firewall allowlisting of Cloudflare ranges, or Authenticated Origin Pulls with mTLS. CVE-2026-123634 depends on how `proxy_pass` is built and still needs patching. CVE-2026-113425 is unprotected because the HTTP proxy does not carry mail traffic, and Spectrum TCP/UDP applications and DNS-only hosts fall outside the protection as well. Interim config changes if patching has to wait: `http2 off;` (1.25.1 or later; remove `http2` from `listen` on older), remove QUIC listeners or `http3 off;`, use fixed upstream groups instead of variable `proxy_pass`, and bind mail listeners to trusted networks only.

### 🎯 Takeaway (Hợp)
Inventory every nginx instance now — packages, containers, appliances, nginx Plus — with `nginx -V` and `nginx -T`, patch straight to 1.30.7 or 1.31.9 (or nginx Plus 37.0.8.1 / 37.3.0.1), and restart binaries rather than reloading configs. If patching has to wait on a change window, turn HTTP/2 off at the listen directive and move Cloudflare-fronted origins fully behind Tunnel, allowlisted Cloudflare ranges, or mTLS so the edge termination does the blocking work. Chặn SCTP ở kernel bằng `install sctp /bin/false` dưới `/etc/modprobe.d/` để chặn đường escalate khi kernel patch chưa về — và nhớ reboot mới ăn.


### 🔭 Overview (Tổng)
Espressif's 20 November developer blog post walks through a reproducible pipeline that converts video into MJPEG frames with FFmpeg, packs them into a flash data partition, and plays them back from an ESP32-S3 application using ESP_NEW_JPEG 1.0.2 and `esp_lcd`, with the entire chain verified against FFmpeg inside Espressif's QEMU xtensa emulator — no physical board required. The post sits between a tutorial and a workflow design reference, because the QEMU-first setup is what lets the pipeline's correctness be checked pixel-by-pixel. For embedded teams shipping boot animations, product demo loops or short clips on status screens on ESP32-S3, this is the piece that replaces the usual trial-and-error on a dev kit with a deterministic test harness.

### 🔬 Details (Phân)
The toolchain is pinned. ESP-IDF v6.1 runs inside the `espressif/idf:v6.1` Docker image, with QEMU 9.2.2 as the target emulator and FFmpeg 9.0.2 doing the conversion (key behaviours cross-checked on FFmpeg 7.1.5). The decoder is ESP_NEW_JPEG 1.0.2 configured for software baseline JPEG, the display driver is `esp_lcd_qemu_rgb` 1.0.2 as the emulated RGB panel, and the player also pulls in `esp_partition`, `esp_timer` and `esp_lcd`. The FFmpeg example scales and center-crops a source clip to 320x240 at 15 fps, then encodes with `-c:v mjpeg -q:v 5 -pix_fmt yuv420p -f mjpeg`; the post includes a quality-versus-size table from `-q:v 2` to `-q:v 31`, and for a 150-frame clip `-q:v 5` lands at about 1.65 MB with an average PSNR of 38.7 dB — which is the number that makes 3 MB a comfortable single-clip budget.

The packing format is small but intentional. A `"MJV1"` header carries the panel size, fps and frame count, followed by an index of (offset, size) pairs and the 4-byte-aligned JPEG frames; the `pack_video.py` helper walks JPEG markers so frame boundaries survive concatenation reliably. The partition layout defines a 3 MB data partition with subtype 0x40 at offset 0x100000 (size 0x300000) so the clip can be replaced without rebuilding the application, and the player memory-maps the partition and decodes straight from flash. There are two decoder landmines worth calling out: output is RGB565 little-endian for QEMU but many SPI panels such as the ST7789 and ILI9341 want big-endian (`JPEG_PIXEL_FORMAT_RGB565_BE`), and ESP_NEW_JPEG 1.0.2 rejects 4:4:4 MJPEG so 4:2:0 is required — which also means odd-width panels like the 135x240 ST7789 must be encoded at 136x240 with the extra column dropped at draw time.

The QEMU setup is where the correctness story is grounded. Headless runs use `qemu-system-xtensa -nographic -machine esp32s3 -drive file=...,if=mtd,format=raw` with a `-monitor unix:...,server,nowait` and `-serial file:` plumbing; without a display, `draw_bitmap` hangs unless a monitor `screendump` forces the refresh, and QEMU needs an even stride so an odd-width panel still asks for one spare column. The post reports that every checked pixel was within one RGB565 step of the FFmpeg decode, PSNR was roughly 38 to 47 dB between the two decoders, and all 150 frames played on both the 320x240 and 135x240 panels. The honest limits: no decoder speed is measured in QEMU — every frame counted as late — so real decode time, per-frame budget and achievable frame rate have to be measured on the target board using the player's late-frame count.

### 🎯 Takeaway (Hợp)
If you are about to ship a boot animation or a product demo loop on an ESP32-S3 panel, build the conversion and playback pipeline this way first in QEMU and use the pixel-diff plus PSNR check as a CI gate, so a bad encode flag or a swapped endianness is caught before anyone touches hardware. On real panels, pin `JPEG_PIXEL_FORMAT_RGB565_BE` for ST7789 or ILI9341 and keep encodes at 4:2:0, because ESP_NEW_JPEG 1.0.2 still refuses 4:4:4. Lưu ý QEMU không đo được tốc độ decode thật — dùng nó cho correctness, đo FPS trên board thật.

```bash
# Prepare the MJPEG clip with FFmpeg 9.0.2 (320x240, 15 fps, q:v 5 ~ 1.65 MB)
ffmpeg -i in.mp4 \
  -vf 'scale=320:240:force_original_aspect_ratio=increase,crop=320:240' \
  -r 15 -c:v mjpeg -q:v 5 -pix_fmt yuv420p -f mjpeg out.mjpeg

# Pack into the "MJV1" container with an index of (offset, size) frames

# partitions.csv: a 3 MB data partition at 0x100000, type 'data' subtype 0x40
# nvs,      data, nvs,     0x9000,   0x6000

# factory,  app,  factory, 0x10000,  0xf0000

esptool.py --chip esp32s3 write_flash 0x100000 clip.mjv
```
