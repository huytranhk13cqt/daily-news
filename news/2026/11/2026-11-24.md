### 🔭 Overview (Tổng)
Databricks' 23 November engineering post announces general availability of a native Lakebase Postgres sink for Spark Structured Streaming on Databricks Runtime 18 LTS and newer. The sink exposes `format("postgresql")` as a first-class output path through `writeStream.toTable()`, replacing the hand-rolled `foreach` and `forEachBatch` writers that teams have been shipping for years against Lakebase and other managed Postgres backends. For teams running real-time feature pipelines, CDC fan-outs or operational-store sync from Spark into Postgres, this removes the most common bespoke-sink reliability pain point — wiring up idempotency, retry and connection pooling by hand — and makes an OLTP destination a configurable option alongside Delta and Iceberg. DBR 19 is required to unlock the configurable merge strategies and the Unity Catalog external-Postgres path, which is in Public Preview.

### 🔬 Details (Phân)
The user-facing API is deliberately small. A streaming query writes with `.format("postgresql")`, names a target table in `.toTable("catalog.schema.table")`, and configures upserts with `option("upsertkey", "<col>")` plus `option("batchinterval", "<duration>")` and `option("batchsize", "<n>")` to control micro-batch shape against the Postgres side. On DBR 19, `option("mergeStrategy", ...)` lets the writer pick between plain insert, insert-or-update and insert-or-ignore, and the connector handles exponential-backoff JDBC retries internally so transient failures do not propagate as query failures. The checkpoint location is required and used the same way as a Delta sink; schema evolution on the Postgres side is still the operator's job. The post also lands the Unity-Catalog-managed external-Postgres variant in Public Preview on DBR 19, meaning the sink can target any Postgres fronted by UC federation and not only Lakebase.

The benchmark setup is spelled out and makes the perf claim easy to reason about. On a 40-core classic cluster fronting an 8-CU Lakebase instance, with a 5 million-user state and a 1-hour sustained run, the sink averaged roughly 20K events per second and produced 63.5 million upserts end-to-end. End-to-end latency on the same run was P50 183 ms and P99 354 ms, which matches the processing-time trigger of 5 seconds Databricks used in the example. Those numbers are not a headline record — a tuned Delta sink on comparable hardware will push higher throughput — but they are the honest watermark for an upsert-heavy Postgres workload and show that the retry and batching path does not degrade tail latency.

The migration story is cleaner than the one for `foreach` writers. A streaming query written against the previous custom-sink pattern replaces two or three dozen lines (thread pool, connection, batched statement, idempotency logic) with a `writeStream.toTable()` call plus options; the checkpoint carries over if the target table name is unchanged. The caveats worth noting: GA is on DBR 18 LTS, not DBR 17 — so a one-step Runtime bump is required — and the configurable merge strategies and the UC external-Postgres path only work on DBR 19. Teams that need those two pieces today have to run on DBR 19 (Public Preview on that path) rather than staying on LTS.

### 🎯 Takeaway (Hợp)
If you ship feature pipelines or CDC fan-outs from Spark into Lakebase or another managed Postgres, plan the DBR 18 LTS upgrade this sprint and migrate your `foreach`/`forEachBatch` writers over to `writeStream.toTable()` with `upsertkey` — the Databricks-reported 20K events/sec with P99 354 ms is an honest ceiling to validate against your own workload before cutting over. Keep the old writer behind a feature flag until you have replayed a representative hour of traffic and the checkpoint position matches. Nếu bạn cần `mergeStrategy` hay external-Postgres qua Unity Catalog thì phải nhảy sang DBR 19 Preview, chấp nhận trade-off ổn định của LTS.

### 💡 Example
```python
# Databricks Runtime 18 LTS or newer — native Lakebase Postgres sink GA
# Replaces foreach / forEachBatch writers against managed Postgres.

from pyspark.sql.functions import col, current_timestamp

events = (spark.readStream
    .format("delta")
    .table("main.bronze.user_events"))

features = (events
    .withColumn("updated_at", current_timestamp())
    .selectExpr("user_id", "feature_payload", "updated_at"))

(features.writeStream
    .format("postgresql")
    .option("upsertkey", "user_id")              # idempotent on retry
    .option("batchinterval", "5 seconds")        # Postgres-side micro-batch
    .option("batchsize", "20000")                # match target TPS
    # DBR 19+: .option("mergeStrategy", "insert_or_update")
    .option("checkpointLocation", "/Volumes/ck/user_history")
    .trigger(processingTime="5 seconds")
    .toTable("main.feat.user_history"))
```

Serverless pricing moves from the older vCPU-hour accounting to Data Compute Units (DCUs), the metastore story collapses onto an automatic Lakehouse runtime catalog, and the toolchain jumps to Java 25, Scala 2.13, Python 3.13 via Pixi, Iceberg 1.12 and Delta 4.4. ### 🔬 Details (Phân)
The runtime surface matters first because the Spark 4.2 features it exposes are the ones most workloads were waiting on. Lightning Engine is the performance bet. Google Cloud's published price-performance numbers are "up to 3.25x" against "a leading high-speed Spark alternative" (unnamed in the post) and 4.9x against upstream open-source Spark, along with +50 percent faster Iceberg table scans and the +40 percent BigQuery read speed-up above. The Lakehouse runtime catalog is now the default metastore for new batches and replaces the Dataproc Hive Metastore path, which simplifies schema federation across Iceberg, Delta and BigQuery but needs a migration for existing pipelines that still rely on the Hive Metastore endpoint. The release notes also flag Spark 4.2 API breakages against Spark 3.x (continued) and the Java 25 JVM leap — teams still pinned on Spark 3.5 on older runtimes should pin `--version=3.5` explicitly during the transition rather than taking the implicit default.

### 🔭 Overview (Tổng)
Espressif's 23 November developer blog introduces `micro_ros_espidf_component`, an officially maintained ESP-IDF component now on the ESP Component Registry that lets ESP32, ESP32-C3, ESP32-S3 and ESP32-P4 devices join a ROS 2 network as first-class nodes. Prior to this release, every ESP-IDF team wanting ROS 2 had to piece together the upstream micro-ROS build with its own CMake plumbing and transport glue; the new component collapses that into a single `idf.py add-dependency` call. For robotics, drone, service-robot and mobile-sensor teams already running ROS 2 on Linux controllers, this is the shortest supported path to pulling an ESP32-family microcontroller into the same publish/subscribe graph without cutting a custom bridge.

### 🔬 Details (Phân)
The component tracks ROS 2 distros by major version: version family 24.x targets Jazzy, 25.x targets Kilted and 26.x targets Lyrical, so `^24` resolves to the Jazzy line and lets `idf.py update-dependencies` pick up patches without crossing a distro boundary. The transport default is Micro XRCE-DDS over UDP, pointed at a `micro-ros-agent` typically running in Docker on port 8888, with UART framing as the alternative for serial-only deployments and `embeddedRTPS` as an experimental direct-DDS option that removes the agent at the cost of larger flash and RAM footprints. The default build sets `RMW_UXRCE_MAX_NODES=1`, `RMW_UXRCE_MAX_PUBLISHERS=2` and `RMW_UXRCE_MAX_SUBSCRIPTIONS=2` to keep flash and heap modest; these are `Kconfig` options and lift straight away when a node needs more entities.

The onboarding example is a pragmatic `int32_sub_pub` walkthrough on an ESP32-C3 DevKitM-1, which pulls the component, generates a project with `idf.py create-project-from-example` pinned to version 24.0.0, and runs against a Jazzy agent spun up from the `microros/micro-ros-agent:jazzy` Docker image. The same source also builds for ESP32, ESP32-S3 and ESP32-P4 with a target switch, so a mixed fleet shares one firmware recipe. Wi-Fi provisioning is done via the normal ESP-IDF `example_connect` helper, which means UDP transport works on any Wi-Fi-capable ESP32 variant without additional ESP-WIFI-REMOTE wiring; UART transport sidesteps that entirely and is the recommended path on hardware that lacks Wi-Fi, such as some ESP32-P4 kits.

The adoption implication is the one that matters for teams already shipping ROS 2 estates. A C3 or S3 running the micro-ROS transport can advertise `/motor_cmd`, `/imu_raw` or `/sensor_depth` topics into an existing ROS 2 graph and is discovered through the normal micro-ROS agent, so the Linux side of the robot sees it as another node — without the per-vendor shim that teams have been maintaining for serial-attached Arduino, Teensy or STM32 nodes. The caveats are the usual ones for micro-ROS: the per-domain entity limits (nodes, publishers, subscribers, timers) are compile-time and need to be raised when a firmware grows; agent version must match distro family; and the `embeddedRTPS` path is marked experimental, so UDP-via-agent is the production-grade default until that changes.

### 🎯 Takeaway (Hợp)
If you already run ROS 2 and have been bridging ESP32-based sensors or actuators over custom serial protocols, replace that path this week with `micro_ros_espidf_component` on the same distro family as your Linux stack — the `idf.py add-dependency` plus `micro-ros-agent` setup is small enough to prototype end-to-end in a day. Keep an eye on the `Kconfig` entity caps before adding your fifth publisher, and prefer UDP over Wi-Fi for mains-powered devices and UART for battery-constrained ones. Nếu stack đang là Jazzy thì pin `^24`, Kilted thì `^25` — đừng lẫn distro family.

### 💡 Example
```bash
# Add the official micro-ROS component for ESP-IDF and target ROS 2 Jazzy.

# Pull the int32 pub/sub example, target an ESP32-C3 DevKitM-1.

  "micro-ros/micro_ros_espidf_component=24.0.0:int32_sub_pub"
cd int32_sub_pub
idf.py set-target esp32c3

# Wi-Fi SSID/password via menuconfig, then build and flash.
idf.py menuconfig          # Example Connection Configuration

# On the ROS 2 host, verify the node and topics show up.
ros2 node list
ros2 topic echo /microROS/freertos_int32_subscriber
```

### 🔭 Overview (Tổng)
Jean-Luc Aufranc's 23 November CNX Software writeup covers Tessera, an AGPL-3.0 firmware project that turns commodity ESP32 touchscreen devkits into Home Assistant wall panels without the usual ESPHome YAML surgery. The firmware is built on ESPHome plus LVGL and is driven from a Home Assistant add-on that exposes a drag-and-drop dashboard editor, so UI changes push to the panel over Wi-Fi without reflashing. For smart-home builders who have been reaching for commercial Nextion-based panels at $150–$250 or writing their own ESPHome displays from scratch, this is the first turnkey open-source alternative that targets the under-$50 ESP32-S3 and ESP32-P4 touchscreen kits now flooding the market.

### 🔬 Details (Phân)
Hardware support is pragmatic and tracks what is actually in stock. Recommended boards are the Guition ESP32-S3-4848S040 (480×480 round-corner panel with GT911 capacitive touch), the Guition JC8012P4A1 V3 and the Seeed reTerminal D1001 (both ESP32-P4-based with 1280×800 panels and GSL368x touch), plus the ubiquitous "CYD" ESP32-2432S028 and Waveshare 4.3-inch and 10.1-inch ESP32-P4 variants. The underlying ESPHome config uses the familiar `display` + `touchscreen` + `external_components` stack and is generated by the Home Assistant add-on, so operators do not edit YAML by hand unless they want to. Features at launch include voice assist, camera feeds, 10 UI languages and a plugin surface for custom components, and the firmware ships factory binaries that pair to Home Assistant through the standard ESPHome discovery flow.

The architectural choice worth calling out is the dashboard-over-the-air model. Tessera separates the firmware image (flashed once, re-flashed only for feature upgrades) from the dashboard layout (a serialized description pushed over Wi-Fi by the add-on). That keeps iteration cycles short — a UI change is seconds, not minutes — and removes the biggest friction of DIY HA panels, which historically has been full ESPHome recompilation and flashing on every layout tweak. The architectural cost is a dependency on the Home Assistant add-on being available on the network; panels operate in a read-only state if the add-on is offline at boot, which the project documents explicitly as the current trade-off.

The caveats are the usual open-source shape. AGPL-3.0 is the license, so vendors packaging Tessera into commercial panels need to understand the copyleft implications; the project is community-maintained rather than Nabu Casa-sponsored; and the ESP32-P4 boards the project targets still want custom ESP-IDF versions in some configurations, so panel owners should expect short-term churn on firmware images against ESPHome 2026.11-class releases. The adoption calculus is nonetheless favorable: a $30–$50 Guition panel plus Tessera lands feature parity with commercial panels at a quarter of the cost, and the OTA dashboard model fundamentally changes the iteration loop for DIY installers.

### 🎯 Takeaway (Hợp)
If you have been putting off installing Home Assistant wall panels because the ESPHome YAML and Nextion toolchain were too slow, buy one Guition ESP32-S3-4848S040 or reTerminal D1001, flash Tessera from the Home Assistant add-on, and iterate the dashboard over the air until the layout earns its place on the wall before cloning it to the rest of the house. Keep a plan for how the panel behaves when the HA add-on is offline — read-only is fine for most rooms, but critical-switch panels may want a fallback layout. Nếu bạn làm sản phẩm thương mại trên nền này, đọc kỹ AGPL-3.0 trước khi ship.

### 💡 Example
```yaml
# Minimal ESPHome fragment Tessera builds on for a Guition ESP32-S3-4848S040.
# Tessera's Home Assistant add-on generates and maintains the full config.

esphome:
  name: tessera-living-room
  friendly_name: Living Room Panel

esp32:
  board: esp32-s3-devkitc-1
  framework:
    type: esp-idf

external_components:
  - source: github://MaxGramser/homeassistant_espscreen
    components: [tessera]

wifi:
  ssid: !secret wifi_ssid
  password: !secret wifi_password

api:              # Home Assistant native API; add-on discovers the panel
ota:              # firmware OTA (dashboard OTA is a separate channel)

display:
  - platform: ili9xxx
    model: ST7701
    resolution: 480x480
    rotation: 0

touchscreen:
  - platform: gt911

tessera:
  # dashboard layout pushed by the HA add-on over Wi-Fi; no reflash required
  dashboard_channel: default
```
