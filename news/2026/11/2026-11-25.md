## 1. Databricks Lands Catalog Labels in the Apache Iceberg REST Spec With Tag Exchange Beta on Unity Catalog, Exposing Table and Column Tags Through the LoadTable Response With Reader Support Slated for PyIceberg 0.13 Alongside Google Cloud, ClickHouse, Atlan, Collibra and DataHub

### 🔭 Overview (Tổng)
Databricks' 24 November platform post, authored by Daniel Weeks, Andrei Tserakhau, Jason Reid, Michelle Leon and Alex Jiang, announces that the Apache Iceberg REST Catalog spec now carries an optional `labels` field on the `LoadTable` response, merged upstream through Apache Iceberg PR #15750 and implemented on Unity Catalog as a Beta capability called Tag Exchange. Labels are string key-value pairs attached to tables and columns, and a REST-compatible engine or agent can read them at load time without a side-channel call to the catalog's own tagging API. The point of the change is interoperability: Unity Catalog, Polaris, Snowflake Open Catalog and any other REST-backed Iceberg catalog can now ship the same shape of metadata and let downstream engines and governance tools consume it uniformly. For data engineers running federated lakehouses or stitching agents on top of multiple catalogs, this closes the biggest remaining gap in the Iceberg REST metadata surface.

### 🔬 Details (Phân)
The spec addition is deliberately minimal. A `LoadTable` response optionally includes `labels`, a map of string keys to string values at the table level, and a parallel structure on each column entry in the schema. The post's worked example attaches `domain=customer_support` and the Databricks system tag `system.certification_status=certified` to a `support_cases` table, and `content_type=support_case_summary` to its `issue_summary` column. The spec defines the transport shape but intentionally leaves the vocabulary — business domain, PII class, sensitivity level, certification status — to catalog implementations and consumers, which matches the way `properties` has always been handled on Iceberg tables. The clearest practical implication is that a query engine reading a table through `/v1/namespaces/{ns}/tables/{table}` pulls labels in the same round trip it already uses to fetch the table metadata location, without an extra authentication or policy hop.

Tag Exchange is the Unity Catalog implementation and is in Beta, enabled from the Databricks Previews portal under the `Tag Exchange via Iceberg REST Catalog` toggle; the external-access documentation is at `docs.databricks.com/aws/en/external-access/tag-exchange`. On the reader side, Apache Iceberg PyIceberg has merged the complementary PR #4321 for label reads in Python, scheduled for the 0.13 release — which is what makes this consumable from Spark-on-Python, Daft, Trino's Iceberg connector and small-footprint tools without waiting for a catalog-vendor SDK. Databricks lists Google Cloud, Salesforce, ClickHouse, Atlan, Collibra, DataHub, Immuta, Trust3 AI, PhoenixAI and Datastrato as partners aligned with the vision, which signals that discovery tools, governance platforms and agent frameworks intend to consume the field rather than build around it.

The adoption calculus for teams is pragmatic. The spec change itself is non-breaking — a catalog that does not emit `labels` simply omits the field, and readers that do not understand it pass it through — so a cautious rollout can land PyIceberg 0.13 first, then flip Tag Exchange in a sandbox workspace, and only push labels into production catalogs once governance owners agree on the key vocabulary. The caveats worth naming are familiar: Tag Exchange is Beta, so breaking changes to the key-naming convention are possible before GA; labels are strings only, so structured policies still live in your governance tool; and the standard does not define authorization on labels, which means a catalog can expose a label to a reader that already has `LoadTable` permission on the table.

### 🎯 Takeaway (Hợp)
If your platform runs multi-engine access on top of Iceberg REST catalogs, pick two or three label keys you already carry in Unity Catalog tags — domain, certification status, PII classification — and A/B them through Tag Exchange Beta into a staging PyIceberg 0.13 reader before building anything on top. Hold off on an agent-side policy that depends on these labels for masking decisions until the key vocabulary is agreed across your governance and engineering orgs, since string keys are easy to drift. Nếu bạn đang chạy federated Iceberg với Polaris hoặc Snowflake Open Catalog, đây là tín hiệu để pin label contract vào sớm thay vì đợi GA.

### 💡 Example
```python
# PyIceberg 0.13 snapshot — reading catalog labels from an Iceberg REST catalog.
from pyiceberg.catalog import load_catalog

catalog = load_catalog(
    "unity",
    **{
        "type": "rest",
        "uri": "https://<workspace>.cloud.databricks.com/api/2.1/unity-catalog/iceberg-rest",
        "credential": "<client_id>:<client_secret>",
        "warehouse": "main",
    },
)

table = catalog.load_table(("main", "support", "support_cases"))

# Table-level labels, as returned by the Iceberg REST LoadTable response.
for k, v in (table.labels or {}).items():
    print(f"table  {k} = {v}")

# Column-level labels live on each schema field.
for field in table.schema().fields:
    for k, v in (field.labels or {}).items():
        print(f"column {field.name}: {k} = {v}")
```

### 🔭 Overview (Tổng)
Databricks Threat Research — Alessandra Rizzo, Panos Sakkos and Ariel Ropek — published the first part of a series on 23 November analysing about 5,400 confirmed malicious npm packages first seen between December 2025 and October 2026, the twelve months after npm revoked long-lived publishing tokens. The headline finding is a sharp bifurcation: 89 percent of the set is attacker-created packages, but they add up to only 0.2 percent of downloads, while the 7 percent that are hijacked legitimate packages account for more than 99 percent of downloads. For platform teams and data engineers who pull npm libraries into Node-based pipelines, CI runners, Airflow plugin build steps, Spark Thrift clients or TypeScript dashboards, the report is the clearest 12-month baseline yet of what post-token-revocation supply-chain attacks actually look like.

### 🔬 Details (Phân)
The attack-vector breakdown is where the report earns its keep. Three worm-driven hijack waves in May, June and August 2026 account for the download tail, confirming that attackers moved from mass-published typosquats to compromising high-fan-out legitimate packages once long-lived tokens were revoked. OIDC trusted publishing turned out to be a new vector rather than a defence: 85 percent of releases published through trusted publishing in the sample were compromises of real packages whose CI environments the attackers already controlled. Dependency confusion returned at scale in an August 2026 campaign that made up 78 percent of confirmed versions that month, and reconnaissance-only packages appeared every month. Typosquatting is now a minority tactic — 13 percent embed a popular name, under 5 percent sit within two character edits — which inverts the ratio defenders were used to in 2022–2024.

Install-time behaviour is split almost down the middle. Fifty-four percent of malicious packages declare a `preinstall`, `install` or `postinstall` lifecycle script, but the largest single campaign (over 1,000 packages) used a lifecycle script in only 1 percent of its packages and relied on execution at `import` or invocation time. Seventy-two percent carry an obfuscation marker and 30 percent fetch a second stage, so static scanners that key on lifecycle scripts alone miss roughly half the sample. Thirty-eight percent of packages exfiltrate through a legitimate third-party service — serverless hosts, chat webhooks, pastebins, code hosts — which blunts egress-reputation controls. On compromised legitimate packages the picture is different again: 78 percent of compromised versions add or modify a lifecycle script, 23 percent show a maintainer or publisher change, and the median time to an npm security placeholder replacement is 7.1 days.

The remediation list is sober and worth reading as a checklist. Install-script blocking is a partial control and must be paired with lockfile-integrity enforcement and a registry proxy using an allowlist or minimum-age policy. Monitor lifecycle-script and maintainer changes in existing dependencies, not only the arrival of new ones. Treat trusted publishing as provenance rather than assurance: pin CI actions, keep secrets out of pull-request builds and review provenance attestations at publish time. Use allowlist-based egress control instead of domain reputation. Register internal scopes on the public registry so a dependency-confusion republish is refused, and resolve internal scopes only from internal registries. Apply file-integrity monitoring to AI assistant configuration — the report calls out malicious MCP servers, tampering with assistant config and theft of AI service keys as a growing surface.

### 🎯 Takeaway (Hợp)
If your data platform runs anything Node-adjacent — dbt-cli sidecars, Node-based orchestrators, Airflow plugin builds, dashboard bundling — set an npm minimum-age policy in your registry proxy this week, turn on lockfile-integrity enforcement in CI, and audit which pipelines still allow install scripts; those three controls would have caught the bulk of the 2026 sample. Pair them with maintainer-change detection on your pinned dependencies, since lifecycle-script telemetry alone misses almost half of attacker-created packages. Nếu bạn đang chạy agentic coding tools, đặc biệt là MCP servers, bật file-integrity monitoring lên cấu hình assistant của developer — đó là mặt attack surface mới của 2026.

### 🔭 Overview (Tổng)
Espressif's 24 November developer-portal post introduces two ESP-IDF components, ESP-Flux and ESP-GMP, published under the `esp-iot-solution` repository as `components/esp_flux` and `components/esp_gmp` with worked examples under `examples/esp_flux`, `examples/esp_gmp/gmp_ota` and `examples/esp_file_transfer`. ESP-Flux is a reliable message channel that sits above BLE GATT and adds windowed transmission with selective acknowledgment, MTU-aware fragmentation and reassembly of complete messages; ESP-GMP (ESP General Management Protocol) sits above ESP-Flux and adds framing, sequence-number request/response matching, command routing to profiles, status codes and a bounded transmit queue, with OS group capability queries, OTA and file transfer as ready profiles. For teams shipping BLE-only devkits or sensor peripherals that need to push firmware or configuration bundles larger than a single GATT PDU, this is the first Espressif-maintained open-source path that replaces the hand-rolled chunk-and-retry logic most firmware teams currently maintain.

### 🔬 Details (Phân)
ESP-Flux's framing is the right level of simple. Each fragment adds about 7 bytes above the ATT PDU — 3 bytes for ATT headers and 4 for the ESP-Flux header — and the first fragment of a message uses a 13-byte `START` header. Design parameters include a default window size of 6 fragments, a hard cap of 128 fragments per message and a 64 KiB maximum reassembled message, constrained together by the current MTU and fragment count; the SACK bitmap is 16 bytes, two concurrent send streams per session are supported, and the window threshold at which a receiver nudges the sender is configurable with 50 percent as the example value. Named APIs include `flux_session_send()`, callbacks `session_complete_cb` and `data_received_cb`, and the ESP-GMP transport surface `esp_gmp_transport_t`, `esp_gmp_tx_in_flight()`, with error codes `ESP_ERR_ESP_GMP_TX_QUEUE_FULL` and `ESP_ERR_INVALID_STATE`. Buffer ownership is the sharp edge: transmit buffers remain owned by the caller until `session_complete_cb` reports a terminal state, and the application is responsible for `free()` on receive buffers once `data_received_cb` returns.

The comparison the post makes is against a stop-and-wait GATT transfer rather than against BLE L2CAP connection-oriented channels, and Espressif is explicit that the one over-the-air capture shown is qualitative — it occupies nearly all available airtime per connection interval under the test configuration — and "not an absolute benchmark or performance ranking." No throughput number is published, and the post flags that reliability gains narrow on lossless links. For teams already running BLE 5.x with 2M PHY, 247-byte ATT MTU and extended length, the primary benefit is not peak Mbps but delivery semantics: a message either arrives in full with integrity (SHA-256 is used on the complete payload) or the application sees a terminal failure, without the custom half-done-retry logic that BLE OTA stacks typically carry.

The caveats are worth internalising before pulling the dependency. The OTA profile always restarts uploads at offset zero — interrupted uploads do not resume — which is a sharp operational limit for large firmware over flaky links. The example provides no BLE access control and no ESP-GMP authentication, so production deployments are expected to wire up Secure Boot, signed-image verification, Flash Encryption and link-level or business-level authorisation separately. The current GATT wrapper removes its callback registry entry before destroying the ESP-Flux session, so teardown logic should not rely on destroy-time callbacks. The components ship without a preview/beta/GA tag; treating them as initial-release open source — review the API surface, run the OTA example end-to-end on your target SKU, pin the exact commit — is the pragmatic posture.

### 🎯 Takeaway (Hợp)
If you maintain a hand-rolled BLE-OTA path on ESP32-family devices, prototype `components/esp_gmp` with the `gmp_ota` example against one SKU this sprint and compare it against your current chunking logic on size, maintenance burden and corner cases like dropped last-fragment retries — the SACK retransmission and SHA-256 integrity path are what remove most of the production bugs teams accumulate on these stacks. Keep an eye on the offset-zero OTA limit for firmware over marginal links, and layer link-level authorisation under the profile for any production build. Nếu dự án đang gắn với BLE-only, đây là candidate tốt để cắt sang trước khi viết thêm chunking logic mới.

### 💡 Example
```c
/* ESP-Flux / ESP-GMP receive handler sketch — owns the reassembled buffer.
 * See examples/esp_gmp/gmp_ota in the esp-iot-solution repository.
 */
#include "esp_gmp.h"
#include "esp_err.h"

static void on_data_received(void *buf, size_t len, void *user_ctx)
{
    /* Ownership passes to the application on this callback. */
    if (!buf) {
        return;
    }
    process_message(buf, len);
    free(buf);  /* required by the ESP-Flux buffer contract */
}

esp_err_t app_send_request(esp_gmp_transport_t *tx, const void *req, size_t n)
{
    size_t in_flight = esp_gmp_tx_in_flight(tx);
    if (in_flight > 4) {
        return ESP_ERR_ESP_GMP_TX_QUEUE_FULL;  /* bounded TX queue */
    }
    /* Caller keeps the buffer until session_complete_cb reports terminal. */
    return flux_session_send(tx, req, n);
}
```

### 🔭 Overview (Tổng)
CNX Software's Debashis Das covered a new MIT-licensed Arduino library on 24 November — TinyWifiDongle by Phil Schatzmann, at `github.com/pschatzmann/TinyWifiDongle` — that turns an ESP32-S2, ESP32-S3, Raspberry Pi Pico W or Pico 2 W into a USB Wi-Fi adapter the host sees as a native Ethernet device via CDC-NCM. The library is a transparent Layer-2 bridge: the host's DHCP request goes directly to the upstream router and comes back with the router-assigned IP, so there is no NAT and no separate MCU-side IP address during normal operation. For homelab operators, SBC builders, air-gapped-laptop retrofitters and anyone trying to bring Wi-Fi to a single-board computer or a legacy laptop that has only USB, this is the shortest open-source path to a working dongle without hunting for a chipset that still has supported drivers.

### 🔬 Details (Phân)
The supported-board list is pragmatic. ESP32-S3 (tested) and ESP32-S2 use TinyUSB over the native USB-OTG port, with the Arduino IDE `USB-OTG (TinyUSB)` option selected at compile time; Pico W and Pico 2 W (tested) use the Arduino-Pico core with its default Pico SDK USB stack. ESP32-P4 support is experimental and USB networking on it is untested. The original ESP32 and the ESP32-C3/C6 are explicitly out of scope because they lack the required USB device functionality — the C6 can only act as a USB host in this context, not a CDC-NCM peripheral. Host OS support is similarly clean: Linux, macOS and Windows 11 work with native CDC-NCM drivers; Windows 10 needs an additional driver. RNDIS is not supported. USB runs at full speed (12 Mbps), which is the ceiling the benchmark numbers run up against.

Throughput is modest but honest. On an ESP32-S3 the developer's tests land between 530 and 615 KB/s — roughly 5 Mbps — and on a Raspberry Pi Pico 2 W between 110 and 325 KB/s, averaging about 2 Mbps. Those numbers reflect the USB full-speed wall and the realistic cost of pumping Ethernet frames through TinyUSB CDC-NCM on an MCU; they are enough for terminal sessions, config fetches, web browsing on an old laptop or ssh over an IoT lab bench, and under what a cheap commercial USB Wi-Fi adapter does. The library ships a browser-based Wi-Fi setup path through the `TinyWifiDongleSetup` class and a `WifiManager` example, so provisioning does not require a serial console — though the author flags that the browser flow has only been tested on Pico 2 W and that the ESP32-S3 shows occasional USB stalls and the Pico 2 W has an unexplained reboot in some tests.

The architectural significance is the licence choice and the Layer-2 model. MIT means hobbyist and commercial distribution is open, which is why the library is a plausible candidate for homelab racks and retro-laptop revival projects rather than a one-off demo. The Layer-2 bridge keeps the firmware out of the network-stack critical path — DHCP, DNS and TLS all happen on the host — which both simplifies the firmware and means the host sees ordinary Ethernet-like semantics, so container runtimes, kubelets or simple `ip link` scripts work unchanged. The known-issues list — USB stalls, occasional reboots, no Windows 10 out of the box — means production use is out of scope for now, but the installation surface is small enough to try end-to-end in an evening on either hardware family.

### 🎯 Takeaway (Hợp)
If you have a spare ESP32-S3 or Pico 2 W and a laptop or SBC without Wi-Fi, flash TinyWifiDongle this weekend and keep it as a lab-bench travel adapter — 5 Mbps on the ESP32-S3 is enough for terminal, package pulls and web admin UIs, and the MIT licence makes it a reasonable starting point for anyone building a batch of cheap travel dongles. Do not expect it to replace a USB 3.0 Wi-Fi 6 adapter on throughput-sensitive workloads, and leave Windows 10 users on an external CDC-NCM driver until the author publishes a signed build. Nếu bạn đang có SBC không Wi-Fi hoặc laptop cũ thiếu adapter, đây là cách rẻ và hiền để có kết nối trong một buổi tối.

```cpp
// TinyWifiDongle — minimal Arduino sketch for ESP32-S3 or Pico 2 W.
// Select "USB-OTG (TinyUSB)" in the IDE on ESP32-S3; use the default
// Pico SDK USB stack on Pico W / Pico 2 W.

#include "TinyWifiDongle.h"

TinyWifiDongle dongle;

void setup() {
  Serial.begin(115200);
  // Hard-coded credentials shown; for a provisioning UI, use
  // TinyWifiDongleSetup + the WifiManager example instead.
  dongle.begin("your-ssid", "your-wifi-password");
}

void loop() {
  // The library handles the CDC-NCM <-> Wi-Fi bridge in its own task.
  // DHCP, DNS and TLS all happen on the USB host.
}
```
