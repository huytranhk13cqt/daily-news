### 🔭 Overview (Tổng)
Databricks' 26 November Engineering post by Carlota Soto reframes read replicas for Lakebase, the managed Postgres service that sits beside the lakehouse in Databricks' current data platform. The argument is that the traditional Amazon RDS pattern — each replica a full physical clone with its own instance and volume — is wrong for how teams actually scale reads: replicas take minutes to hours to create, double or triple the storage bill and stay on 24/7 because pausing them is manual. Lakebase rebuilds the replica around a compute-storage split borrowed from the Neon lineage: compute holds no durable state, storage keeps authoritative WAL and page history, and a read replica is just another read-only compute attached to the same branch. For teams on Databricks' managed Postgres who have been avoiding replicas because of cost or operational drag, this is the clearest statement to date of how the service's replica model differs from a classical managed Postgres.

### 🔬 Details (Phân)
The architecture has three named pieces on the storage side. Safekeepers receive WAL from the compute and replicate it with a Paxos-based protocol, committing a transaction once a quorum acknowledges it. Pageservers turn WAL into pages and can reconstruct any page at any LSN via the `GetPage@LSN` operation that the post identifies as the key primitive making the design work. Object storage holds long-term, immutable history. Because the compute layer owns no durable state — only RAM for shared buffers and local NVMe as a cache — several computes can attach to the same branch simultaneously. A replica is created by the control plane spinning up a read-only compute, pulling a slim base backup from the pageserver, then streaming WAL from the safekeepers (not from the primary) and reading pages on demand from the same pageservers. Creation time does not depend on database size, and the primary takes on no extra replication work. Write rejection is enforced inside the replica compute itself.

The resource story is the practical hook. Three replicas on a 1 TB database bill 1 TB on Lakebase versus 4 TB on a classical RDS-style setup, because replicas add compute but no storage. Default suspend is five minutes of inactivity; a suspended replica wakes on the next query and is almost immediately current, because the safekeepers keep ingesting WAL while compute is down. Each replica has its own autoscaling range, tracked by the same CPU, memory and working-set algorithm used for the primary and resized in place. The use-case list is pragmatic: splitting application reads from writes, absorbing launch and traffic spikes, analytics and BI, production investigations, read-only access for agents, partners and tools, isolating background jobs such as exports and index rebuilds, and giving agents dedicated read capacity for their own tasks.

The caveats are worth internalising before replacing a classical Postgres read tier. The post gives no numbers beyond "seconds" for creation and the five-minute default, and names no APIs, CLI commands or configuration syntax — anyone wiring this up today works from the Lakebase docs rather than the blog. High availability is deferred to a future post, so the failover path for a replica serving user traffic is not part of this write-up. Lakehouse integration — Unity Catalog, Delta or Iceberg access — is not covered either; the only storage detail is object storage for history, which positions Lakebase as a Postgres-compatible side-car to the lakehouse rather than a lakehouse engine in its own right. Replica cache misses are honest about the trade-off: each wake starts cold and warms on demand.

### 🎯 Takeaway (Hợp)
If your team already runs Lakebase for transactional workloads beside a lakehouse and has been punting on replicas for the usual cost and spin-up reasons, flip one on against a non-production branch this week and measure wake latency and warm-up against your query mix — the storage-free billing and seconds-scale creation are the lines on the invoice worth confirming. Hold any decision to move user-facing reads behind a replica until the forthcoming HA post lands, because the failover semantics materially affect SLA posture. Nếu đang cân nhắc split read/write cho agent và tool workload, đây là route tiết kiệm vs. RDS-style replica.

### 🔭 Overview (Tổng)
Cloudflare's 25 November blog post introduces Search for Agents, a zone-level feature that stands up an AI Search instance for a site, indexes its content and exposes a standard search endpoint on the site's own domain so AI agents can discover and query it without the operator building a retrieval layer by hand. The pitch is a one-toggle alternative to the usual pattern — provisioning a vector store, writing a chunker, deploying an API, documenting it so agents find it — and it leans on two public standards: a `/.well-known/search` well-known URI and the IETF QUERY method defined in RFC 10008. For teams whose content is being scraped for retrieval anyway, this reframes the surface from "block or allow" to "serve, score and control," and it moves retrieval into the same CDN plane that already handles bots and WAF.

### 🔬 Details (Phân)
Setup runs under Quick Actions on the zone page or through the API. Enabling Search for Agents creates an AI Search instance with default settings and begins crawling and indexing the site. Every page then gets `agent:` meta tags in the `<head>` describing the search endpoint, and pages requested with `Accept: text/markdown` receive the same information as YAML front matter — two discovery paths that work with and without JavaScript. The runtime surface is a GET on `/.well-known/search?q=...`, which takes keywords or natural-language questions, and the same endpoint also accepts the IETF QUERY method with a plain-text or JSON body. Results come back as Markdown excerpts with relevance scores, not generated answers; Cloudflare's framing is that the calling agent runs its own model and the endpoint stays a retrieval primitive. Access sits behind bot management, AI Crawl Control and WAF, so the operator can grant specific agents, charge them or deny them by the usual zone controls.

The extensibility is where the design moves beyond a widget. Because Search for Agents is backed by a standard AI Search instance, the owner can enable reranking, change cache settings and expose public REST or MCP endpoints, meaning the same index can power an agent, a human-visible search widget and a Workers-routed API without duplicating ingestion. Pricing follows AI Search — ingestion, index storage and queries — with included usage on the Workers Free and Paid plans; the post is explicit that the feature is available to all customers, including Free, subject to the normal AI Search limits.

The MCP endpoint is described as optional but not specified in the post. And treating Markdown excerpts as the contract is deliberate: it keeps the owner from being on the hook for the agent's generated answer, but it also means a client expecting a conversational answer still has to pipe the excerpts through its own model. Teams considering a quiet rollout should also expect the discovery path — `agent:` meta tags on every page — to make the endpoint visible to any scanner, so bot-management rules do most of the policy work.

### 🔭 Overview (Tổng)
Espressif's 26 November developer-portal post by Filipe Cavalcanti walks through a safe-input design for the ESP32-P4 that targets IEC 60730 Annex H Class C — the tier the standard reserves for burner controls, unvented high-pressure boilers and industrial e-stops where a failure can produce a special hazard. The thesis is that watchdogs do not catch the most dangerous kind of input failure, which is a silent one such as a pad shorted to a rail while firmware reads an "all clear," and the path forward is two complementary defences combined: complementary hardware biasing on two pins so that equal levels are themselves a fault, plus a dual-core reciprocal read that requires both cores to agree the pin was sampled correctly. For firmware teams eyeing the ESP32-P4 for safety-regulated products — HVAC burners, kitchen appliances with gas valves, industrial e-stops — this is the first Espressif-authored reference that treats Class C as an achievable target rather than a specialist's problem.

### 🔬 Details (Phân)
The hardware side is specific. Pin A (GPIO 2, active-low) is pulled up to 3.3 V, with the switch closing it to GND; Pin B (GPIO 3, active-high) is pulled down to GND and driven with the inverted signal. The core invariant is `Level(A) XOR Level(B) = 1`; equal levels indicate a fault. A dual-contact NO/NC switch gives independent coverage across the cable, connectors and traces, and a PCB inverter on a single-wire sensor is the cheaper fallback, with the caveat that a short on the sensor wire past the inverter is not detected. The `safe_gpio_init()` helper uses the ESP32-P4's internal ~45 kΩ pulls, with external 10 kΩ resistors recommended for long cables or noisy environments. The post ships an FMEA table covering shorts to GND or 3.3 V on either pin, inter-pin bridges, pad stuck-at faults and open wires, each mapped to a discrepancy fault and a latched safe state.

The software side is the deeper part. `bist_gpio_input_reciprocal_test(gpio_num)` runs four steps: Core 0 samples the pin into Slot 0, dispatches a sample job to Core 1 via `bist_multicore_call` which writes Slot 1, Core 1 verifies both slots and flags `BIST_ESP_IO_TEST_ERR` on failure or mismatch, then Core 0 repeats the verification, returning `BIST_ESP_OK` only if both cores agree. The driver layer, `bist-safe-gpio`, exposes `safe_gpio_init()`, `safe_gpio_sample()`, `safe_gpio_get_fault()` and `safe_gpio_fault_name()`, with `SAFE_GPIO_MODE_COMPLEMENTARY` as the recommended mode (valid pairs (1,0) and (0,1); closed is (0,1)) and `SAFE_GPIO_MODE_EQUAL` explicitly flagged as not Class C because it cannot detect inter-pin bridges. The skew window is 20 ms, tolerating contact transit skew of roughly 1–10 ms; a persistent invalid pair latches within the window plus one or two sample periods. On fault, the recommended flow cuts the actuator, lights the fault LED and calls `fail_safe_exit()`, whose behaviour is product-specific.

The scope and build notes are also worth naming for planners. The reference is built as a standalone ESP-BIST target with `SOC_TARGET=esp32p4`; ESP-IDF supplies headers and toolchain only, and there is no FreeRTOS — Class C reciprocal GPIO support is described as internal and only available through the standalone flow today, with customer-available release expected after certification. The article covers digital GPIO inputs only; analog inputs and output drivers are deferred. Bench captures on the ESP32-P4-Function-EV-Board run four test cases (nominal cycling, Pin A shorted to GND, Pin B shorted to 3.3 V, Pin A bridged to Pin B) and show the output dropping and the fault latching only after the 20 ms window expires. The post is explicit that formal Class C certification must come from accredited authorities on the finished product, not from the library alone.

### 🎯 Takeaway (Hợp)
If you have a safety-regulated roadmap on the ESP32-P4 and are either waiting on Class C tooling or planning to bolt the invariant check onto application-level code, lift the complementary wiring and the FMEA coverage wholesale and keep the reciprocal GPIO check running outside FreeRTOS for now so the standalone flow does not become a surprise on audit day. Pair safe inputs with fail-closed actuator outputs — high-side and low-side switches in series — because an input layer that latches a fault without a safe output is still a single-point failure. Nếu đội firmware đang làm thiết bị gas/burner trên ESP32-P4, đây là reference tiết kiệm nhiều tuần FMEA work.

### 💡 Example
```c
/* Minimal application flow for a Class C safe input, from the Espressif post. */
#include "safe_gpio.h"

#define PIN_A GPIO_NUM_2   /* active low, pulled up to 3.3 V */
#define PIN_B GPIO_NUM_3   /* active high, pulled down to GND */

void app_main(void) {
    actuator_set_safe();                             /* outputs safe first */

    bist_gpio_input_test();                          /* post-boot BIST */
    safe_gpio_init(PIN_A, PIN_B,
                   SAFE_GPIO_MODE_COMPLEMENTARY,
                   20 /* ms skew window */);

    watchdog_start(200 /* ms */);

    while (1) {
        safe_gpio_sample();                          /* dual-core reciprocal */
        if (safe_gpio_get_fault() != SAFE_GPIO_FAULT_NONE) {
            actuator_set_safe();
            led_fault(true);
            fail_safe_exit();                        /* product-specific */
        } else if (safe_gpio_level_closed()) {
            actuator_drive();
        }
        watchdog_feed();
        vTaskDelay_us(1000);                         /* 1 ms sample */
    }
}
```

### 🔭 Overview (Tổng)
Arduino's 26 November blog post from the Arduino Team describes two platform updates to Arduino Cloud, the hosted environment that pairs Arduino boards and ESP32-class devices with web and mobile dashboards. The first is a custom palette feature for white-label spaces: one seed hex color generates an interactive palette for buttons, links and selection highlights, previews it against light and dark themes and runs an accessibility auto-correction pass to hold contrast standards. The second is an RBAC expansion for Business, Team and Enterprise plans that introduces Service and Viewer roles in addition to the existing Admin and Editor. For fleet operators and teams that ship Arduino-based hardware under their own brand, these are the kind of platform features that quietly unblock customer-facing deployments and operational handoffs.

### 🔬 Details (Phân)
The custom palette feature targets organisations on Cloud Plans with white-label capabilities, and Space Admins configure it under Custom Branding in Space Settings. A single seed color, entered as hex or picked from a swatch, generates the palette, and the editor shows light-theme and dark-theme previews side by side before anything is applied. The accessibility auto-correction toggle is on by default to enforce contrast standards; turning it off is explicitly allowed for brands that want exact colors with the contrast trade-off. The palette applies to interactive elements in both the web app and the IoT Remote mobile app — primary buttons, links, selection highlights — and reverting to default styling is available through a DEFAULT label beside the swatch.

The RBAC story adds two named roles. Service is positioned as operational access with limited editing for specific devices, dashboards, triggers, templates, sketches and recovery operations — the role an on-call engineer or an ops partner can hold without carrying full admin keys. Viewer is read-only with non-destructive actions such as widget usage and data downloads, which is the shape most customers and auditors need. The post states the roles are enforced consistently across the web app, mobile app, CLI and API, with configuration under Space Settings > Roles & Permissions, though the write-up does not list specific API endpoint changes or sample role JSON — the API shape will need to come from the updated Arduino Cloud documentation that this release ships alongside.

The caveats are mostly scope. The palette feature requires the white-label capability on a Cloud Plan, so it is not reachable on individual or free tiers; if your product plan did not include the white-label SKU, this update does not change the deployable branding story. The new RBAC roles are Business-plan features only (Team and Enterprise), and the article does not state whether existing Admin and Editor behaviour changed, which means an audit of the role matrix on upgrade is still work your team has to do by hand. There are no API versioning details, no migration guide and no rollback story in the post, so the usual advice for a mid-flight RBAC change — snapshot the role assignments before the upgrade window — applies.

### 🎯 Takeaway (Hợp)
If you ship Arduino Cloud as part of a white-label product, pull a handful of production seed colors through the new palette editor this week, keep the accessibility toggle on, and move on-call engineers off Admin onto Service unless they genuinely need full rights.
